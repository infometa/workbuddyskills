# 看进展：从哪里看起、怎么判断、怎么写

用户问招聘进展怎么样、哪里卡住、今天该做什么、某个职位或候选人到哪一步时读。全程只读，零写操作。
用户挑了要做的事以后，再按 `@references/workflows.md` 去办：已经定位到的对象直接带过去，写之前照样重新读一遍现状。

这一节不做任何写操作，输出「谁、在哪、事实是什么、建议做什么」。用户挑了要做的事以后，再按上面的办事各节去办：
已经定位到的对象直接带过去，写之前照样重新读一遍现状。

### 从哪里看起

| 用户问 | 先看 |
| --- | --- |
| 今天该做什么、有什么要跟进 | `mcp__moka-go__todo_summary`：五组各最多列 5 条，`count` 是全组条数；范围是整个企业，不只是本人 |
| 某段时间的面试 | `mcp__moka-go__interview_search`：`bucket` 选待安排（unscheduled）、待进行（upcoming）、待反馈（pending）、已完成（done），配合 `scheduledFrom` / `scheduledTo` |
| 某个职位的情况 | `mcp__moka-go__job_get` 加 `mcp__moka-go__candidate_search({ jobId })` 列名单，每项带当前阶段；阶段名用 `mcp__moka-go__pipeline_get_default` 对照 |
| 某位候选人 | `mcp__moka-go__candidate_get`，按需要加 `applications`、`interviews`、`experiences`、`engagements` 分段；流转历史要 `detail: "full"` |
| 面试官排期 | `mcp__moka-go__user_list({ keyword })` 找人，`mcp__moka-go__interview_availability_list({ interviewerId })` 看登记的不可约时段（要翻页） |
| 所有开放职位 | `mcp__moka-go__job_list` 翻到底，停招的单独说 |

只为涉及的人补信息，不把整个人才库拉一遍。没翻完的列表要说「只看了前 N 条」，不能把一页的条数当总数。

### 判断依据

| 看到的事实 | 建议，以及不能说过头的地方 |
| --- | --- |
| 开放职位没有投递，或 JD 是空的 | 补 JD、看渠道 |
| 待筛选，还没有面试 | 建议先筛或安排一面；不替用户下录用判断 |
| 在面试阶段，但没有待进行的面试 | 看是不是都取消了或已出结果；取消不会回退阶段，不要说成数据错了 |
| 面试时间已过，结果还是待反馈 | 建议核实面试有没有进行并补结果；系统没有结束时间，不能断言面试已经结束 |
| 在某个阶段停留很久 | 写出具体天数；用阈值（例如初筛 3 天、Offer 7 天）时说明是建议值 |
| 流转记录里有从后往前退的 | 列出时间、操作人和原因，问是不是有意的；非终态的回退不自动当成错误 |
| 已到 Offer 阶段 | 建议确认 Offer 发了没、候选人怎么答复；阶段名证明不了 Offer 已经发出 |
| 一条投递结束了，候选人没归档 | 先看候选人有没有别的进行中的投递，再提整理人才库 |
| 有人入职，职位还开着 | 问还有没有名额；招聘人数字段不等于编制，不能断定已招满 |
| 同一人在多个职位推进 | 列出来由用户定，不自动淘汰哪一条 |
| 登记的不可约时段和排期重叠 | 提示冲突；没登记不等于有空 |

停留天数按北京时间算：有流转记录时取时间最新的一条（不要假定数组最后一条最新），没有才用投递创建时间，并说明依据。
转化率要先说清时间范围和口径，不能拿当前各阶段人数的比例冒充历史转化率。评价经历时给出材料依据，不编系统匹配分。

### 怎么写结论

- 按紧急程度排：今天就要处理的 → 卡住的 → 待核实的 → 资料补全。没有证据的建议不写。
- 每条一句事实加一句建议，例如：「后端工程师的陈立，原定 9 月 18 日 14:00 面试，结果还没填；建议先确认面试是否进行，再补结果。」
- 用人名和职位名，不写工具名、字段名和 id。

收尾自查：没写任何数据；说清看了多大范围；每条结论都有依据；没把「没记录」当成「没发生」，
没把开始时间当结束时间，没把 Offer 阶段当已发 Offer，没把一次入职当招满。
