# analyze-scenarios — AI 与 CLI 场景路由对照表

> 工具 `analyze.scenarios` · 命令 `sensors ai chat` 或对应 sensors CLI 命令 · 仅用于执行前路由

判定依据：**工作模式**，不是「问题是否开放式」。

**默认走 CLI。** 六个工作模式里只有 **客群发现** 与 **运营增长** 走神策 AI，
其余四个（快速洞察 / 深度分析 / 规则圈选 / 数据管理）走 sensors CLI。
凡是能走 CLI 的，一律走 CLI；链路 A 是两个白名单模式的专用通道，不是兜底。

## 用途

按工作模式选择神策 AI 或 sensors CLI，明确白名单场景与边界。

## 参数

输入为用户原始请求和已确认的业务目标；不接受额外命令参数。

## 输入 Schema

先按下表判断工作模式，再读取对应的 AI 或 CLI reference。

## 输出

输出链路 A/B、场景名称、需要读取的 reference 和后续执行约束。

## 错误

无法判断时默认选择 CLI；多模式请求拆分执行，不猜测业务对象。

## 场景总览

| 工作模式 | 场景数 | 链路 | 绑定专家 | 场景胶囊 |
|---|---|---|---|---|
| 快速洞察 | 4 | B · CLI | 数据分析专家 | 看板解读 / 异常识别 / 经营简报 / 核心指标快速查询 |
| 深度分析 | 5 | B · CLI | 数据分析专家 | 转化漏斗诊断 / 用户旅程分析 / 留存与活跃分析 / 渠道归因分析 / 功能上线复盘 |
| 规则圈选 | 5 | B · CLI | 数据分析专家 | 人群画像速览 / 用户检索 / 标签创建 / 目标分群圈选 / 标签分群资产盘点 |
| 客群发现 | 4 | **A · 神策 AI** | 客群研究专家 | 目标客群预测 / 客群自动分类 / 相似人群拓展 / 语义标签构建 |
| 运营增长 | 5 | **A · 神策 AI** | 运营策略专家 | 策略设计生成 / 策略优化 / 策略效果预测 / 策略洞察 / 模拟用户评价 |
| 数据管理 | 3 | B · CLI | 数据埋点专家 | 埋点方案设计 / 埋点实施 / 埋点测试 |

## 链路 A · 神策 AI（仅客群发现 + 运营增长）

调用方式：`sensors ai chat --skills <平台侧 skill> "<用户原话>"`。
传 `--skills` 前先 `sensors ai resources --resource skills` 核对实际可用名。

### 客群发现

| 场景胶囊 | 触发意图 | 平台侧 skill |
|---|---|---|
| 目标客群预测 | 预测购买 / 流失 / 转化概率；预测最可能购买的品类或目标类别；预测金额、次数等数值；据预测结果找出目标人群及其规模与画像 | `sensors-ml-agent` |
| 客群自动分类 | 没有预设分类规则，想从真实数据里发现「这些人可以分成哪几类」「每类人有什么特点」「找出几类典型消费人群」 | `sensors-ml-agent` |
| 相似人群拓展 | 已有一批种子用户（已有分群、标签人群或其他用户集合），想找到更多特征相似的用户；含拓展人数/倍数诉求 | `sensors-ml-agent` |
| 语义标签构建 | 判断或描述购买意向、品牌好感度、价格敏感度、品类偏好等，但**没有明确的计算规则** | `sensors-semantic-tag` |

边界提示：

- 明确目标类别的预测 ≠ 自动发现用户类型。不要因为用户说了「分类」就按自动聚类理解。
- 用户只要预测结果与画像时，不要默认转成圈人任务。
- 「相似人群拓展」的相似 ≠ 未来一定产生相同表现，不得表述为确定的行为预测。

### 运营增长

| 场景胶囊 | 触发意图 | 平台侧 skill |
|---|---|---|
| 策略设计生成 | 从经营目标 / 业务问题 / 初步运营想法出发，形成完整可执行的策略方案（提升转化、活跃、留存、召回、用户价值） | `sensors-focus` |
| 策略优化 | 已有运营方案、策略草稿或运行中的策略，想改善整体表现或调整其中某个环节 | `sensors-focus` |
| 策略效果预测 | 策略正式执行前 / 下一轮调整实施前，预估覆盖、触达、转化等表现与风险 | `sensors-focus` |
| 策略洞察 | 基于真实运行数据，理解已执行策略的效果、发现问题、寻找后续优化机会 | `sensors-focus` |
| 模拟用户评价 | 投放前从目标用户视角了解对策略、营销内容、权益方案或触达设计的可能反馈 | `sensors-focus` + `sensors-virtual-human-evaluation` |

边界提示：

- 用户只要求局部设计/局部调整时，不要强制扩展成完整方案。
- 效果预测与模拟评价都属**辅助决策**，不代表真实执行效果、真实用户访谈；不自动触发策略修改或发布。
- 交付物要区分「策略建议」「完整方案」「平台策略草稿」。

> `sensors-semantic-tag` 对应平台侧清单里的 `semantic-tag-agent`。
> 名字不一致时以 `sensors ai resources` 的实际返回为准，不要硬传。

## 链路 B · sensors CLI（其余四个工作模式）

本地 skill 随 sensors-cli 包分发，用 `sensors skills install workbuddy -g` 安装，
会平铺到 `~/.workbuddy/skills/<skill-name>/`。
生成命令前先读对应 `references/*.md`。

### 快速洞察

| 场景胶囊 | 做什么 | 本地 skill | CLI 命令 |
|---|---|---|---|
| 看板解读 | 把一张看板在指定时间段的结果跑出来，组织成能读懂的解读；先列图表清单并告知执行数量，等用户确认范围 | `sensors-context` → `看板能力` → `分析能力` | `analytics dashboard-list` → `analytics dashboard-get` → `analytics bookmark-query` |
| 异常识别 | 同一张图跑两遍（本期 + 等长上期），变动幅度 =(本期−上期)/上期，默认阈值 10%；无异常就如实说 | `看板能力` + `分析能力` | `analytics bookmark-query` ×2 |
| 经营简报 | 日/周/月报，本期与对比期各取一次数；结论 ≤3 条且每条对应具体数字；明确告知不具备定时推送 | `看板能力` + `分析能力` | `analytics bookmark-query` ×2 |
| 核心指标快速查询 | 不指定看板，直接按一句话问题取数；一次最多 2 次取数；相对时间必须换算成具体起止日期 | `分析能力`；口径确认用 `元数据能力` | `analytics segmentation` / `funnel` / `retention` / `distribution` / `user-path`；`metadata events` / `fields` / `values` |

约束：

- 某张图执行失败或暂不支持自动执行时**如实列出**，不静默跳过，也不用其他图的结果填补。
- 区分「数据事实」与「推测原因」，推测必须标注待验证。
- 用户追问「为什么」时给候选排查方向，并建议转「深度分析」。
- 这些场景**只读**，不创建也不修改任何看板与图表。

### 深度分析

| 场景胶囊 | 做什么 | 本地 skill | CLI 命令 |
|---|---|---|---|
| 转化漏斗诊断 | 定位流失最大的步骤，至少按一个关键维度（默认渠道）拆解该步；对比类任务把差异归到具体步骤 | `分析能力` | `analytics funnel` |
| 用户旅程分析 | 路径模型（桑基图）+ 行为序列解读；前向看「某事件之后去哪」，后向看「到达某事件前从哪来」；最多 20 节点，数值为会话数 | `分析能力` | `analytics user-path` |
| 留存与活跃分析 | 留存模型 + 活跃趋势；按初始行为日期分组消除新增干扰；关注可干预的后续行为 | `分析能力` | `analytics retention` |
| 渠道归因分析 | 各渠道「量 / 质 / 贡献」对比；量与质用事件分析/漏斗/留存，贡献用归因模型 | `分析能力` | `analytics attribution` |
| 功能上线复盘 | 渗透率看采用、时间对比与版本分组看变化、「用过 vs 没用过」看功能价值 | `分析能力` | `analytics segmentation` + `funnel` + `retention` |

约束：归因结果依赖所选模型与窗口期，是**相关口径而非因果**；上线复盘要提示活动、季节、
用户结构变化等混淆因素。意图与主观感受的推断须标注并留待验证。

### 规则圈选

| 场景胶囊 | 做什么 | 本地 skill | CLI 命令 |
|---|---|---|---|
| 人群画像速览 | 目标人群的属性/行为/偏好，并与整体或对比人群比较；双方口径须一致，否则差异不可比 | `分析能力` | `analytics personas-report` |
| 用户检索 | 按用户 ID / 属性 / 标签 / 分群 / 行为条件定位用户；命中多条时列候选让用户选；敏感字段脱敏 | `分析能力` | `analytics user-list` |
| 标签创建 | 规则标签 / 行为特征标签 / RFM；四步不可跳：检索已有 → 建议规则 → 预估规模 → 复述配置待确认后写入 | `标签能力` | `tag list` / `tag get` → `tag create`（先 dry-run） → `tag evaluate` |
| 目标分群圈选 | 业务目标或模糊人群概念 → 可执行分群规则；按 6 字段输出配置；写入前必须复述完整配置并经用户确认 | `分群能力` | `segment list` / `segment get` → `segment create`（先 dry-run） → `segment evaluate` |
| 标签分群资产盘点 | 资产治理看板（5 板块）；CLI 口径只能拿到名称/显示名/has_data/enable/类型，其余标注「界面导出后可补全」 | `标签能力` + `分群能力` | `tag list` + `segment list` + `segment get` + `analytics dashboard-list` / `dashboard-get` / `bookmark-query` |

约束：

- 事件条件**强制显式指定数据时间窗口**，禁止无时间限制的孤立事件。
- 校验口径存在性与 `has_data`，缺时间范围先澄清，绝不臆测。
- 本组只读场景（画像速览、用户检索）不创建也不修改任何对象。

### 数据管理

| 场景胶囊 | 做什么 | 本地 skill |
|---|---|---|
| 埋点方案设计 | 从链接/文档/图片/PRD/需求/设计稿/自然语言生成埋点采集方案；四阶段逐段确认；交付全量方案 Excel + 新增差量 Excel + 报告 html | `埋点方案能力` |
| 埋点实施 | 把全量方案 Excel 转成项目源码埋点代码，SDK 接入与配置，四端类型安全 Wrapper 并本地编译验证 | `埋点实施能力` |
| 埋点测试 | 真实运行环境验证上报准确性（auto 真实重放 / manual Payload listener），逐事件标通过状态 | `埋点测试能力` |

> 命名待对齐：本仓库当前只随包分发 `埋点能力`（总技能），
> 尚未拆出 `埋点实施能力` / `埋点测试能力`。
> 引用这两个名字前先确认本地是否存在；缺失时按 `埋点能力` 执行。

## 判定兜底

1. 命中「预测 / 建模 / 聚类 / 相似 / 策略 / 仿真评价 / 语义标签」→ 链路 A。
2. 命中「看板 / 概览 / 指标 / 漏斗 / 路径 / 留存 / 归因 / 分布 / 明细 / 用户列表 /
   分群 / 标签 / SQL / 元数据 / 埋点」→ 链路 B。
3. **默认值是链路 B。** 两者都不命中、或场景判断不确定时，直接走 CLI 只读取数
   （可复算、可审计），不要为了「要不要改走 AI」去打断用户确认；
   只有明确命中客群发现 / 运营增长的意图才走链路 A。
4. 三个最容易判错的点：

   - **「圈人 / 找人群」**：给得出规则（事件 + 属性 + 时间窗）→ B 的目标分群圈选；
     只有业务概念（「高潜复购用户」「两融潜客」）或要求预测 / 相似拓展 → A。
   - **「创建标签」**：普通规则标签、RFM、首次末次特征 → B 的标签创建；
     只有语义标签（购买意向 / 品牌好感 / 价格敏感，且无计算规则）→ A。
   - **「报告 / 简报」**：经营简报、周期简报、看板解读 → B；
     链路 A 不承接报告类请求。

5. 跨模式请求要拆步（如「分析下降原因并圈出高潜人群」）：
   按各自场景分别走 A/B，回复中交叉引用 AI 的 `session_id` 与 CLI 的结果。
6. 写操作：链路 B 的分群 / 标签 / 元数据写入走 CLI 并遵守确认流程；
   链路 A 的写（预测结果导入标签或分群、策略草稿）由平台侧能力完成。
