# 查询条件组装规则

本规则只处理“自然语言过滤条件 → `filterGroupList`”的转换。对象、字段和权限的事实仍以本次 Tool 返回为准；不要把 Profile、示例字段名或服务端默认行为当成当前字段契约。

## 一、唯一的条件门禁

调用 `ycrm_form_data_list` 前，先把用户的过滤事实分为主表可执行条件与需要详情核验的子表事实，再逐项确认：

1. 对象已唯一确认；过滤字段来自本任务适用的主表可读字段元数据。
2. 用户每个明确过滤事实都有确定的处理位置：主表条件进入当前列表请求；子表事实仅在[两步分支](form-data-query.md)中由详情核验。主表字段、comparison、值及日期参数兼容；待详情核验不等于忽略条件。
3. 本次提交的主表逻辑转成组内 AND、组间 OR 的 DNF；无空组、冲突、歧义及超限展开。候选查询不得排除原请求可能命中的记录，尤其不能只查询包含主表条件的 OR 分支。
4. 子表事实、展示投影和排序没有混入主表条件；最终结果只有在全部需详情核验的事实完成后才能称为匹配结果。
5. 任一事实既不能由列表表达也无法可靠核验时停止并说明，不发送会改变用户范围的剩余条件查询。

简单原子条件直接核对字段、比较符和值；复杂逻辑、多字段歧义或嵌套表达才展开“原文 → 作用域/字段证据 → 比较符和值 → 逻辑分组 → 未解决项”的内部映射，无需为每次简单查询填写固定模板。

服务端可能清理未知字段、缺项、自然值转换失败条件和无效排序；混合有效/无效条件仍可能继续执行。上述门禁用于阻止查询范围被静默扩大，不能依赖服务端清洗兜底。

## 二、字段匹配和作用域

1. 使用本任务适用的 `ycrm_form_field_list` 结果中的真实 `fieldName`；字段标题、描述和类型必须能唯一确认目标字段。
2. 字段 Tool 默认可能展开一层子表字段。当前列表查询只接受主表过滤字段，不能因为看到了子表字段就把它用于 `filterGroupList`。
3. 字段标题相同、主表与子表均存在或多个候选无法区分时，停止组装并请求确认。
4. 不使用用户提供的内部 ID、Profile 中的提示 ID 或经验拼接字段名。

## 三、字段类型与 comparison

| 字段类型 | 推荐 comparison | 规则 |
|---|---|---|
| 文本 | `EQUAL`、`NOT_EQUAL`、`CONTAIN`、`NOT_CONTAIN`、`START`、`END` | “包含”不能改成“等于”；“是”通常是等于，除非字段明确为布尔字段 |
| 数值、金额 | `EQUAL`、`NOT_EQUAL`、`MORE`、`MORE_EQUAL`、`LESS`、`LESS_EQUAL` | 精确金额/数量使用 `EQUAL`；不使用文本包含；区间上下界放在同一组，用 AND 连接 |
| 日期、时间 | `EQUAL`、`NOT_EQUAL`、`BEFORE`、`AFTER`、`DATE_RANGE`、已验证的相对日期 comparison | 不把日期当普通文本比较；精确日期使用 `EQUAL`，日期范围使用 `DATE_RANGE` |
| 单选、字典 | `EQUAL`、`NOT_EQUAL`、`IN_ARRAY`、`NOT_IN_ARRAY` | 选项值必须来自当前字段元数据，不能猜编码或不存在的名称 |
| 多选 | `IN_ARRAY`、`NOT_IN_ARRAY` | 以字段 Tool 和 Tool Schema 支持的语义为准 |
| 布尔、勾选 | `YES`、`NOT` | 只有字段类型和 Schema 明确支持时使用，不把所有“是/不是”都映射为此类 |
| 人员、部门、关联对象 | 由 Tool 和服务端按自然名称转换 | 不自行构造内部 ID；名称有歧义时按服务端契约处理并向用户说明 |
| 空值判断 | `NULL`、`NOT_NULL` | 不填写 `fieldValue`；空字符串不自动当作空值 |
| 人员或部门集合 | `REVERSE_IN_ARRAY` | 只在字段类型和 Schema 明确支持时使用，不能泛化到普通多选字段 |

`NOT_IN_ARRAY`、`REVERSE_IN_ARRAY` 等反向比较符不能仅按中文名称猜测。字段不支持某个 comparison 时，应停止，而不是改用看似接近的 comparison。

## 四、值和日期规范化

- 关联对象、人员和部门使用自然名称；不把名称转换成模型自造的 ID。
- 字典值必须来自当前字段返回的选项；“黄金级”未出现在选项中时，不能改成模糊匹配或忽略该条件。
- 数值单位、币种和精度不明确时先确认；不擅自把“1 万”当成 `1`。
- `NULL`/`NOT_NULL` 不传 `fieldValue`。
- 自定义日期范围固定为 `comparison=DATE_RANGE`、`dateRangeType=CUSTOM`，并同时提供 `dateRangeFrom`、`dateRangeTo`。用户明确给出的起点晚于终点时先澄清，不静默交换；只有用户明确将两端作为无序边界且均可唯一解析时，才按较早时间到较晚时间规范化。服务端虽会自动交换倒序端点，模型不得依赖该容错。时区、时间粒度或日期边界会改变结果且无法确认时，请求用户澄清。
- 预设日期使用 `comparison=DATE_RANGE` 搭配 `dateRangeType=TODAY`、`YESTERDAY`、`THIS_MONTH`、`LAST_QUARTER` 等当前枚举值；`CUSTOM` 不是独立 comparison。
- “最近 N 天”与“本周/本月”不是同一语义。相对日期使用 `N_DAY_AGO`/`N_DAY_AFTER`/`N_MONTH_AGO`/`N_MONTH_AFTER` 时，`fieldValue` 必须是正整数。服务端可能对负数取绝对值、对小数向零取整，并过滤零值、非数字或超范围值；这些只是实现容错，模型不得依赖。用户值不是正整数时请求改写，不发送可能被静默转换或过滤的条件。
- 日期格式优先使用字段元数据，其次使用 Tool Schema 或描述；两者均未提供且当前 Tool 已验证支持通用日期文本时，使用 `yyyy-MM-dd HH:mm:ss` 兜底。时区和边界不明确时不要自行推断。
- 不依赖服务端把非法 N 值、缺失日期端点或转换失败条件静默过滤。

## 五、AND/OR/NOT 规范化为 DNF

`filterGroupList` 只能表示“多个 AND 组的 OR”：

```text
最终过滤 = 服务端权限 AND 场景条件 AND (组1 OR 组2 OR ...)
组内条件 = 条件A AND 条件B AND ...
```

组装步骤：

1. 先识别括号、否定范围和“且/或”等连接关系；不要按逗号、换行或句号机械分组。
2. 将自然语言转换为析取范式（DNF）。
3. 字段级否定使用 `NOT_EQUAL`、`NOT_CONTAIN`、`NOT_IN_ARRAY` 等已确认的 comparison；不要直接用 `NOT` 否定整个条件组。
4. 展开后每个 AND 分支成为一个条件组，超过 20 组时停止，不截断、不擅自合并。

仅处理能直接映射到字段级 comparison 的否定。整体否定、嵌套否定，或需要用德摩根律展开但作用域不明确的表达不直接组装；请求用户改写为明确的字段级条件。

示例：

```text
负责人是张三且状态为跟进中，或负责人是李四

组 A：负责人 = 张三 AND 状态 = 跟进中
组 B：负责人 = 李四
```

```text
负责人是张三或李四，且状态为跟进中

组 A：负责人 = 张三 AND 状态 = 跟进中
组 B：负责人 = 李四 AND 状态 = 跟进中
```

“A 或 B 且 C”没有明确括号时必须确认优先级，不能依赖模型默认运算顺序。

## 六、同字段优化和冲突检查

- `字段=A OR 字段=B` 在字段支持集合 comparison 时可合并为 `IN_ARRAY`。
- `字段=A AND 字段=B` 不能当作多值查询；通常表示空集或用户表达有误，应确认。
- `字段=NULL AND 字段=NOT_NULL` 是矛盾条件，应在调用前发现。
- 数值和日期上下界要检查是否形成空区间；不要为了“优化”删除其中一个边界。
- 不同字段的 OR 不能合并成一个 `IN_ARRAY`。
- 重复条件可以去重，但只能在确认逻辑等价时进行。

## 七、典型边界

### 可以直接组装

```text
客户名称包含“科技”且客户等级为 A
```

主表文本字段使用 `CONTAIN`，字典字段使用当前选项对应的 `EQUAL`，放入同一组。

```text
客户等级为 A、B、C
```

仅当该字段支持集合比较且语义确实为“任一值匹配”时，使用 `IN_ARRAY`。

### 不能直接组装

```text
查询包含“服务器”产品的订单
```

这是子表存在性条件。当前列表接口不支持子表查询条件，不能将产品名称子表字段当作订单主表字段；按[查询规则](form-data-query.md)中的两步分支核验，并说明实际覆盖范围。

### 条件失败

```text
查询客户等级为“黄金级”的客户
```

如果当前字段选项没有“黄金级”，不能模糊匹配、忽略条件或改查全部客户，应说明当前字段元数据不包含该选项并请求改写。
