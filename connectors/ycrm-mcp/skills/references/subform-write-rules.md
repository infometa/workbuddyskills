# 子表单写入

仅在新增、更新或删除 `SUB_FORM` 行时加载。一个父记录多行子表仍是一次父记录范围的写入；只有多条父记录才进入[通用批量规则](multi-entity-rules.md)。

## 关系与标识

1. 新增父记录时确认目标对象、模板和新增字段，不要求先取得尚不存在的父记录 ID；更新既有父记录或其子表行时，先唯一定位父记录并取得可信 `dataId`。按当前操作场景展开所需子表字段。
2. 识别父字段，从 `referRule` 取得确切关系 key；父字段名或子表名称不能代替该 key。
3. 使用关系 key 对应子表的当前场景字段。多子表分别组装，嵌套层级重新确认能力，不默认递归。
4. 既有行 ID 来自包含该子表行的详情或本任务适用的可信写入结果，不能用主表列表 ID、序号、名称或业务编号代替。父子归属不明确时先澄清。

## 组装与校验

主表实际写入字段放 `data`；`SUB_FORM` 父字段用于识别关系，从其 `referRule` 取得关系 key；子表行放 `relationDatas`，结构为“关系 key → 行数组”。多行不能压成逗号文本或摘要。新增父记录的 `data` 必需性按[通用写入规则](form-data-write.md)处理。

| 行操作 | 字段证据与参数 |
| --- | --- |
| 新增行 | 无 `id`；用当前 `ycrm_form_add_field_list` 对应子表字段校验本行必填和值 |
| 更新行 | 有可信 `id`；用当前 `ycrm_form_upd_field_list` 校验本次变化，不重复提交其他未变必填字段 |
| 删除行 | 从当前子表元数据的 `SUB_FORM` 父字段 `referRule` 取得关系 key，再从展开子表的详情确认行 ID 及父子归属；当前更新 Tool 契约支持 `deleteRelationDataIds` 时，以 `deleteRelationDataIds[关系 key]` 传行 ID 集合，最终结果以服务端返回为准 |

关联、字典、日期及文件按子表本身元数据处理，不套用父表同名字段。缺少新行必填事实时可继续准备其他行，但该父记录尚不能按原范围提交：保留缺项集中补问，不静默删掉问题行后提交其余行。用户明确接受部分写入后，按其接受的父记录、行数和自然值范围执行。

## 增量、删除和清空

- 未提交的子表变化保持不变；遗漏某行不表示删除。
- 关系 key 存在不等于删除一定成功；更新字段 Tool 不提供单独的可删性标志，删除是否允许以服务端结果为准。关系 key 或行归属无法确认，或更新 Tool 契约不支持 `deleteRelationDataIds` 时，不组装逐行删除请求；不能用空集合或省略行替代显式行 ID 删除。`null` 是否表示清空按下一条判断。
- 空集合不自动表示清空。显式 `null` 的清空含义及允许范围由当前更新契约决定，不能与未传混用。
- 清空整个子表先确认支持的方式；需要逐行删除时取得完整行 ID 后构造显式删除，读取被截断时不能称已清空全部。
- 新增/更新同一行或同时删除的冲突应在提交前澄清，不能靠调用顺序猜测用户意图。
- 授权与差异确认按[共享规则](shared-rules.md)，不因行数多而重复确认已明确的操作。

## 最小参数形状示例

先绑定真实 Tool 证据：父记录 `P`、关系 key `R`、可更新备注字段 `F`、现有行 ID `I`。这些符号不是可提交的字符串常量。

```text
更新已有行：relationDatas[R] = [{ id: I, F: 用户的新备注 }]
新增一行：  relationDatas[R] = [{ 当前新增字段及用户事实 }]
删除已有行：deleteRelationDataIds[R] = [I]
```

完整请求按当前 Tool Schema 组装。新增行校验全部必填；既有行更新只需本次变化。若两行新增中一行缺必填，保留两行计划并说明缺项，不能只写一行后报告“两行完成”。

新建订单并同时添加两行产品时，使用新增字段确认主表和子表关系，一次提交 `data` 与 `relationDatas`；此时不查找既有订单 ID。

## 写后核验

使用 `ycrm_form_data_dtl(needSubForm=true)`，按[子表读取规则](subform-read-rules.md)核对父记录、对应关系及行的新增/变化/删除。截断只说明部分核验；真实值差异按通用写入的业务等价规则判断，未知结果进入共享恢复分支。
