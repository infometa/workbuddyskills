# 审批查询和处理

纯审批列表不需要表单发现。按业务对象筛选需要 `deployId` 时先读[发现规则](form-discovery.md)；按具体业务记录定位且需要取得 `dataId` 时读[查询规则](form-data-query.md)；选择下一审批人时才读[组织规则](organization.md)；审批意见带图片或附件时读[文件规则](file-assets.md)。

## 标准链路

```text
ycrm_flow_instance_list
  -> ycrm_flow_instance_detail
  -> ycrm_org_user_list（需要选择下一审批人时）
  -> ycrm_file_upload_by_url（意见附带需要导入的公开文件时）
  -> ycrm_flow_instance_process
  -> ycrm_flow_instance_detail / ycrm_flow_instance_history
```

## 查询

用户意图到参数的常用映射；列表关系、审批状态、业务对象和摘要关键字是不同的过滤维度，按用户实际范围组合：

| 用户意图 | 参数 |
| --- | --- |
| 待我审批 | `tabType=unFinished`（缺省值） |
| 我发起的 | `tabType=create` |
| 我已处理 | `tabType=finished` |
| 抄送我的 | `tabType=copyToMe` |
| 当前处于退回状态的 | 在明确的 `tabType` 范围内叠加 `flowStatus=sendback` |
| 曾经发生退回的 | 在明确的 `tabType` 范围内查列表及必要分页，逐实例读取历史并核对 `sendBack` 动作 |
| 某业务对象的审批 | 使用该对象的可信 `deployId`；不要把对象名称当作 `summary` 关键字 |
| 摘要包含某词的审批 | 使用 `summary`；该参数只匹配摘要文字 |

- 用户只说“被退回的”且当前状态或历史经历会改变结果时，先澄清要查当前仍退回，还是曾经发生过退回。
- 省略 `tabType` 只查询待我审批。用户要求当前用户相关范围内的全部审批、全部当前退回审批、全部曾退回审批或某对象的全部审批时，分别查询 `create`、`finished`、`unFinished`、`copyToMe` 的必要分页，并按 `instanceId` 去重；不能把默认待办范围称为全部。若用户只指定某一列表关系，则只查询该范围；关系范围不明且影响结果时先澄清。
- 查询某条业务记录的审批时，先按[查询规则](form-data-query.md)唯一定位记录并取得可信 `dataId`；同一任务已有该证据可复用。审批列表可按 `deployId` 缩小范围，但没有按 `dataId` 过滤的参数；以列表返回的 `dataId` 核对候选，再读取详情确认业务信息，不能仅凭摘要关键词断言已完整找到目标。
- `tabType` 只能使用 Tool Schema 支持的值；无法确认时不要发送未知值，也不能依赖服务端回退到默认待办，应先澄清用户意图。
- `flowStatus` 只能使用 Schema 列出的当前状态值，常用对照：`wait_submit` 待提交、`pass` 已通过、`copy` 抄送、`refuse` 已拒绝、`process` 进行中、`sendback` 当前已退回、`withDraw` 已撤回；无法确认时停止，不发送列表之外的值，也不依赖服务端退化为不筛选。查询曾经退回时不能先以 `flowStatus=sendback` 筛掉重新提交或已进入其他状态的实例；应在用户指定的列表关系和其他条件范围内完成必要分页，逐实例读取必要历史，按实际覆盖范围报告结果。
- 支持时间范围过滤：`createdStart/createdEnd` 按发起时间，`modifiedStart/modifiedEnd` 按修改时间；“最近一周”“上个月发起的”这类请求应主动使用。
- `page` 默认 1，`pageSize` 默认 20，最大 50；`ycrm_flow_instance_history` 分页参数相同。用户要求全量清单或历史时完成必要分页，不能用首屏覆盖全部审批范围。

## 处理

- 在当前业务任务中定位审批实例，并核对详情中的自然业务信息与用户目标一致；早前任务留下的 `instanceId` 只能帮助查找，不能直接作为本次处理目标。
- 处理前必须读取详情并确认 `availableActions` 包含目标动作。
- `action` 只能使用 Tool 支持的 `pass` 或 `refuse`；用户要求撤回、退回、加签、转交等其他操作时，如实说明当前处理能力仅支持同意和拒绝，不尝试用其他 Tool 或多次调用模拟。
- `comment` 最多 500 字符；是否必填由节点配置和业务错误决定。
- `nextApproverNames` 只用于 `pass` 且下一节点需要人工选择的场景，使用组织 Tool 解析名称。
- 审批意见需要图片或附件时，公开 URL 文件先按[文件规则](file-assets.md)导入；本任务已有可信上传结果可直接使用。`processPictures` 传返回文件对象的 `downloadUrl` 数组，`processFiles` 传完整文件对象数组，各最多 9 个。超过上限时先确定取舍，不把一次审批拆成多次处理调用。
- 上传失败或结果未知时，不静默省略用户要求附带的文件后继续处理审批；按文件规则说明已知结果与未完成范围。
- 执行前核对审批实例、动作、意见、下一审批人及所附图片和附件。用户已明确给出唯一实例、完整动作和必要参数，且详情结果一致时视为已确认；发现多个实例、缺失必要参数、下一审批人不唯一或执行范围变化时再请求确认。
- 批量处理先定位完整实例清单。用户已逐条明确实例、动作和必要参数且详情一致时沿用授权；由模型筛选形成的清单或发现的范围差异先展示并确认。随后逐实例读取当前详情、校验、处理并回读；单条失败不阻断其余独立实例，未知实例不得重复提交，最后分别报告成功、失败、未知和未执行项。
- 处理后读取详情或历史确认状态变化；回读失败保留执行响应并标明核验未完成。详情或历史未展示意见文件时，只说明审批状态已核验，不声称文件持久化已回读验证。
- 创建或更新业务记录不自动授权审批；只有用户明确要求时才执行同意或拒绝。

## 历史动作解读

历史返回领域动作 key，常用含义：`pass` 同意、`refuse` 拒绝、`copy` 抄送、`sendBack` 曾发生退回动作、`withDraw` 撤回、`transfer` 转交；`sys` 前缀（`sysPass`、`sysrefuse`、`systransfer`）表示系统自动处理。`sendBack` 不代表实例当前仍处于退回状态；对照仅为提示，未列出的动作原样展示，不擅自归类。

## 不确定结果

超时或连接中断时，按[共享恢复规则](shared-rules.md)查询详情和历史；不能仅凭历史暂未出现就判断未处理，重试前重新读取当前动作。抄送人能查看实例不代表具备处理权限。
