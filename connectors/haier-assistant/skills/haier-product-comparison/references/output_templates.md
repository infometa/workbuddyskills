# 对比输出模板

对应 PRD 3.3.1.4「对比分析」。场景判定与话术以 `assets/comparison_scenarios.json` 为准，
本文档给出各场景的输出结构。占位符 `{...}` 由工具返回的真实数据替换。

## 角色与输入

- 角色：海尔智家产品顾问，根据产品参数数据生成对比结果。
- 输入：对比产品列表（`comparedProductNames`）+ 各产品参数（`sameAttributeList` / `differentAttributeList`）。
- 输出：**只有「各自优点」+「选购建议」两段**，不出对比表格、不列参数清单。
- 铁律：**所有参数值必须来自输入数据，禁止编造与虚假发散**。`differentAttributeList` 提供各款的
  差异化优点，`sameAttributeList` 只在建议里一句话带过共同水准，两者都不整段铺开。
- 铁律：**渠道不作为对比参数**，任何位置都不出现（宿主已在下发前剔除）。
- 铁律：**价格对用户一律称「官方指导价」**，见下节。

## 价格的展示名：官方指导价

返参里 `attributeName` 为「价格」「价格区间」的那条，写进优点或建议时**一律称「官方指导价」**，
不写「价格」「售价」「参考价」「到手价」「优惠价」：

| 不要写 | 改成写 |
|--------|--------|
| ✅ 价格更低（5299 元 vs 6099 元） | ✅ 官方指导价更低（5299 元 vs 6099 元） |
| 两款差别主要在价格 | 两款差别主要在官方指导价 |
| 售价更实惠 / 参考价更低 | 官方指导价更实惠 |

- **只换标签，不改数值、不改单位、不改判读方向**（价格仍是「越低越省」，见
  `assets/comparison_attributes.json` 的 `judgement_standards.lower_is_better`）。
- **不影响入参**：`attributeNames` 里送出的仍然是标准槽位名「价格」
  （见 `assets/comparison_attributes.json` 的 `slot_name_triggers.common`）——
  把「官方指导价」当参数名下发，后端匹配不到、会返回空参数。
- 用户自己说「价格」「多少钱」「贵不贵」照常理解，不纠正用户用词；只约束**你输出时**的说法。

## 前置：模糊匹配提示

`query_product_comparison` 返回 **`fuzzyMatched=true`**（即 `productList` 里任一款
`matchType="2"`，下游只按前缀命中、返回的型号与用户输入不一致）时，
**在原对比话术之前先加下面这一句**，空一行再接场景3/场景4 的原有结构：

```
您的【{input_models}】有多款产品，已为您挑选了{matched_models} 进行对比，如与您意向产品不同，请告诉我准确的型号名称哦~
```

- `{input_models}`：取 `comparedProductNames`，即**用户本轮输入**的型号，多个之间用「、」分隔，
  不得用命中型号顶替；`{matched_models}`：取 `productList[].productName`，即**下游实际命中**的型号，
  两款写「`[型号1]` 与 `[型号2]`」，多于两款时用「、」分隔、最后两个之间用「与」。
  两者不同正是这句提示存在的理由，都要回填真实值。
- **只加这一句，随后的场景话术一个字不改。** 不解释什么是模糊匹配、不描述前缀命中规则、
  不额外追问用户确认——话术末尾的「请告诉我准确的型号名称哦~」本身就是引导。
- **只要有任一款是模糊匹配就输出这一句**，不必逐款判断、也不必只列模糊的那几款：
  提示里的命中型号写全部参与对比的型号，与正文实际对比的型号保持一致。
- **`fuzzyMatched=false`、`matchType` 均为 `"1"` 或字段缺失时保持原输出模式**，不加这句。
- 不适用于：**场景1**（有效型号不足 2 款，压根没调用工具）、**场景2**（跨品类无法对比）、
  以及所有 `ok=false` 的错误码话术。
- 与**场景5**（截断）同时命中时，顺序为「截断提示 → 本提示 → 对比正文」。

完整示例（用户输入 `BCD-506`，下游模糊命中两款）：

```
您的【BCD-506】有多款产品，已为您挑选了BCD-506WGHTD1BGJU1 与 BCD-513WGHFD1BGJU1 进行对比，如与您意向产品不同，请告诉我准确的型号名称哦~

为您对比 BCD-506WGHTD1BGJU1 与 BCD-513WGHFD1BGJU1：
（以下为原对比输出：各自优点 + 选购建议）
```

## 场景1 有效型号 < 2 款

≤3 句话，直接引导补充型号：

- 已识别 1 款：「已识别到「{model_A}」，再提供至少 1 款型号即可对比~ 比如「{model_A} 和 {model_B} 哪个好？」」
- 未识别到型号：「请告诉我您想对比哪两款产品，比如「BCD-510WDPZ 和 BCD-470WLMDZ 哪个更好？」」

## 场景2 跨品类无法对比

按 `comparison_scenarios.json` 的 `scene2_cross_category.text` 原样输出：说明无法逐项对比，
再给出「同品类对比 / 选购优先级 / 预算分配」三个方向让用户选，结尾反问方向。

## 场景3 默认对比（≤5 款：各自优点 + 选购建议）

**不输出对比表格，也不单独列「相同点」清单。** 只输出两段：各自优点、选购建议。

```
**{model_A}**：✅ {优势1} ✅ {优势2} ✅ {优势3}
**{model_B}**：✅ {优势1} ✅ {优势2} ✅ {优势3}

**选购建议**（≤100 字，按场景推荐，不强行指定唯一答案）
```

要点：

- 优点**完全基于 `sameAttributeList` / `differentAttributeList` 的真实参数**总结，
  **不做任何虚假补充与发散**：参数没给的卖点不写，不推断使用体验，不引入未在参数中出现的说法。
- 每条优点必须能对应到一条真实参数，并带上对比值（`✅ 能效更优（1级 vs 2级）`）。
- 每款 3-5 条；某款可对应的差异不足 3 条时如实少写，不凑数。
- **排序：用户指定了对比参数时优先按用户指定的参数总结**（`attributeNames` 的顺序即用户提问顺序）；
  未指定时按参数影响力排序：**价格 > 功能 > 能效 > 容量 > 尺寸 > 附加**
  （细则见 `assets/comparison_attributes.json` 的 `priority_order`）。价格档写进正文时称「官方指导价」。
- **渠道永远不作为对比参数**：宿主已在下发前剔除，返参里不会出现；即便出现也不得写进优点或建议。
- 共同点不再单独成段，但可以在建议里一句话带过（「两款在能效和容量上接近，差别主要在价格」）。
- `fuzzyMatched=true` 时先输出「前置：模糊匹配提示」那一句，空一行再接本结构，本结构本身不变。

## 场景4 逐项参数详解（用户要求"详细/逐项"时）

**同样不输出表格。** 结构与场景3 一致（各自优点 + 选购建议），区别只在**覆盖面更全、每条更具体**：
场景3 只讲影响力最高的几项差异，场景4 把有值的差异项基本讲全。

```
**{model_A}**：✅ 能效更优（1级 vs 2级） ✅ 噪音更低（36dB vs 39dB） ✅ ...
**{model_B}**：✅ 容量更大（551L vs 506L） ✅ ...

**选购建议**（≤100 字）
```

- 逐条仍必须对应真实参数并带对比值，**不做虚假补充与发散**。
- 排序同场景3：用户指定参数优先，未指定按 价格 > 功能 > 能效 > 容量 > 尺寸 > 附加。
- 不输出「逐项胜出统计」表：胜出结论可在建议里用一句话表达（「A 在能效与噪音上更优，B 胜在容量」）。
- 参数分组口径（基本信息 / 容量与尺寸 / 性能与能效 / 核心功能 / 附加功能 / 售后保障）仅用于
  组织行文先后，见 `assets/comparison_attributes.json` 的 `itemized_groups`，**不作为表格分组**。
- `fuzzyMatched=true` 时先输出「前置：模糊匹配提示」那一句，空一行再接本结构，本结构本身不变。

## 场景5 对比产品 > 5 款

开头插入截断提示，之后接场景3 或场景4 的正文（若同时命中模糊匹配，顺序为
「截断提示 → 模糊匹配提示 → 对比正文」）：

```
您共提供{n}款产品，为方便展示取前5款对比：
✅ {model_1}、{model_2}、{model_3}、{model_4}、{model_5}
⏭ 未包含：{model_6}、{model_7}...
如需对比其他组合请重新告诉我~
```

型号取 `comparedProductNames` 与 `truncatedProductNames`，不得改写或补齐。

## 结果组装

正文只输出**各自优点 + 选购建议**：不出对比表格、不列相同点清单、不附参数摘要。
参数只作为优点的论据出现（「能效更优（1级 vs 2级）」），不单独成段复述——
用户要的是「该选哪个、为什么」，逐项罗列参数只是把判断推回给他。

型号、优点、建议全部由正文承载，正文是对比结论的完整表达。

## 通用规则

1. 所有参数值必须来自输入数据，**禁止编造、禁止虚假补充与发散**：参数没给的卖点不写，
   不推断使用体验，不引入未在参数中出现的说法。
2. 优点总结必须逐条对应一条真实参数差异（或共同项），并带上对比值，不能泛泛而谈。
3. **渠道永远不作为对比参数**，不出现在优点、建议或任何位置（宿主已在下发前剔除）。
4. 排序：用户指定了对比参数时优先按其顺序总结；未指定按 价格 > 功能 > 能效 > 容量 > 尺寸 > 附加。
5. **价格对用户一律称「官方指导价」**（见「价格的展示名」）；送出侧的 `attributeNames` 仍用「价格」。
6. 品类不同时参数项自动适配（冰箱→容量/制冷，洗衣机→洗涤/烘干，空调→制冷量/匹数）。
7. 场景3 讲影响力最高的几项差异，场景4 把有值差异基本讲全，两者不叠加输出。
8. `fuzzyMatched=true`（任一款 `matchType="2"`）时，**对比正文之前先加一句模糊匹配提示**
   （见「前置：模糊匹配提示」）；精准匹配、字段缺失、场景1/场景2 与错误码话术都不加。
