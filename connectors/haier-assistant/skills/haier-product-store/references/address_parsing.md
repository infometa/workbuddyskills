# 地址解析规则（省/市/区三级）

对应 PRD 3.3.2.4(三.1)/3.3.2.5(二)「判断地址/省市区提取」。宿主大模型作为地址解析助手，从用户提问中提取
省、市、区三级地址信息，整理为 `query_store` 的 `province`/`city`/`district`/`address` 入参。

## 一、解析 Prompt

```
你是一个地址解析助手。从用户的提问中提取省、市、区三级地址信息。

规则：
1. 如果用户提到了完整的三级地址，直接输出。
2. 如果用户只提到部分（如只说了市），根据常识补全省级，区级留空。
3. 如果用户提到了区但无法确定所属市（如同名区），输出所有可能，并标记 "ambiguous": true。
4. 如果用户没有提到任何地址信息，输出 province=null, city=null, district=null。
5. 不要编造用户没有提到的地址。

【用户输入】
{user_text}

【输出格式】
JSON 对象，包含 province、city、district，必要时含 ambiguous 与 candidates
```

## 二、取值规则

| 场景 | province | city | district | 备注 |
|------|----------|------|----------|------|
| 完整三级（青岛市市南区…含省） | 直接输出 | 直接输出 | 直接输出 | — |
| 只说市（如「青岛市」） | 常识补全（山东省） | 青岛市 | null | 区级留空 |
| 直辖市（北京/上海/天津/重庆） | **带「市」后缀全称**（北京市） | **留空（null）** | 用户所述区 | 后端直辖市数据 city 存的是「市辖区」，用直辖市名当 city 查不到；province 须补全为全称，不下发「北京」；见 `trigger_dict.address_admin_hint.municipality` |
| 同名区无法确定所属市 | 可能省 | 可能市 | 区名 | `ambiguous=true`，列 candidates |
| 未提到地址（含只说「附近」「就近」） | null | null | null | 不编造；已授权地理位置时留空按当前位置查，未授权则**直接追问地址** |
| **异常地点**（火星/月球/霍格沃茨） | null | null | null | **整个忽略**：不当地址，也不据此把 `intentChannels` 填成「线下」，见下方「异常地点」 |

## 二之零、直辖市的 city 必须留空

北京 / 上海 / 天津 / 重庆四个直辖市，后端门店数据的行政区结构是
`province=北京市, city=市辖区, district=朝阳区`（`city` 存的是「市辖区」而不是直辖市名）。
若按常规习惯把 `city` 也填成直辖市名（`province=北京市, city=北京市, district=朝阳区`）下发，
和后端的「市辖区」对不上，会查不到任何门店。

因此直辖市统一**只下发 `province` 与 `district`，`city` 留空（null）**，
且 `province` 必须是**带「市」后缀的全称**（`北京市`/`上海市`/`天津市`/`重庆市`），
不能下发缺后缀的「北京」——后端省级存的是全称，缺后缀会对不上：

```json
{"province": "北京市", "city": null, "district": "朝阳区"}
```

用户只说了直辖市、没说区时，`province` 填直辖市全称、`city` 与 `district` 都留 null。
用户说「北京朝阳区」时，`province=北京市`、`district=朝阳区`、`city` 留空。

## 二之一、异常地点直接忽略

用户说的地点**不可能有海尔门店**时（地球以外的天体、虚构或神话地名、玩笑式指代），
它不是地址：三级字段全部留 null，**并且不据此命中「线下」意向渠道**。
完整口径见 `assets/trigger_dict.json` 的 `invalid_location`。

关键点是**别把它当地址往下传**。「地址 → 线下」这条规则一旦被误触发，用户的在售渠道范围就被凭空缩小：
实测「XQG120-BLE7AD3WU1在火星有卖吗」下发了 `intentChannels=["线下"]`，
而用户其实只想知道这款在哪能买到——忽略「火星」、`intentChannels` 留空后正常返回线上渠道才是对的。

- 不填 `province`/`city`/`district`/`address`，**也不据此调用 `query_store`**；
- 不据此命中「线下」，`intentChannels` 留空按「未指定意向渠道」处理；
- 话术里**不复述、不点评、不纠正**这个地点（不要说「火星上没有门店哦」），直接正常回答在售渠道；
- 用户同时说了真实渠道（「火星的京东有吗」）时，异常地点忽略、真实渠道照填。

**判断依据是「这个地方不可能有门店」，不是「这个词我没见过」。** 两类容易误判的**不算**异常地点：

| 情形 | 正确处理 |
|------|----------|
| 境外真实城市（纽约、东京、伦敦） | **是真实地址**，只是门店数据不覆盖：照常按地址处理，查不到时走无结果兜底话术 |
| 不完整或有歧义的国内地址（「朝阳区」「青岛市南」） | **是真实地址**：按本文档的 `ambiguous` 流程确认所属城市，不要忽略 |

## 三、输出示例

```json
{"province": "山东省", "city": "青岛市", "district": "市南区"}
```

```json
{"province": null, "city": "青岛市", "district": null}
```

直辖市（city 留空）：

```json
{"province": "北京市", "city": null, "district": "朝阳区"}
```

```json
{"district": "朝阳区", "ambiguous": true,
 "candidates": [{"province": "北京市", "city": null},
                {"province": "吉林省", "city": "长春市"}]}
```

## 四、与门店查询衔接

- 解析出的 `province`/`city`/`district`（及原始 `address`）是 `query_store` **模型侧唯一**的位置来源；
  另一个来源是用户授权后由宿主注入的当前位置，**模型不可见、不填、不构造经纬度**。
  三级全为 null 且未授权时**不要调用工具**，直接追问用户所在省市区。
- `ambiguous=true` 时，可先向用户确认所属城市再查询，避免跨城误召回。
- 按省市区查询时返参**不带 `distance`**（该字段仅按授权位置就近搜索时返回），此时话术里
  **不要提距离**、不要说「最近的一家」；返参真的带 `distance` 时才可展示，且不得自行估算。返参自带的 `province`/`city`/`district` 可用于核对是否跨城误召回，
  但 `storeAddress` 已含行政区时不要重复拼接。
- 地址信息仅用于本次门店查询，不写入日志、记忆或 Prompt。
