# 上下文记忆与槽位提取（PRD 3.3.2.3）

宿主大模型在多轮门店引流中维护三类槽位：**产品型号名称**、**意向渠道**、**地址**。

> **地址槽位只能来自用户说出来的省/市/区/地址**——授权位置由宿主注入、模型不可见，
> 不填、不构造、不复述经纬度。未授权而用户又没给地址（含只说「附近」）时**直接追问地址**，
> 不自行请求授权、不输出授权信号（授权由宿主发起）。

## 一、通用取值

- 本轮输入存在产品型号名称 / 意向渠道 / 地址时，**优先使用本轮输入**。
- 本轮缺失时，回退到**上下文记忆**中的对应槽位。
- 不编造用户未提供的型号、渠道或地址。
- 产品型号名称落到 `query_product_sale_channel` 的 `productName`；意向渠道落到 `intentChannels`。

## 一之一、产品型号名称槽位 → `productName`

用户很少说完整型号，多是「云溪5.0 D3」「小红花502」「卡萨帝601鉴赏家」这类口语说法。按以下**优先顺序**提取：

1. **查别名映射**：`assets/product_name_aliases.json` 的 `aliases`，触发词**取最长匹配**
   （「云溪5.0 D3 12kg洗烘一体机」命中 `XQG120-HBLE7AD3U1`，不是更短的「云溪5.0 D3」）。
   匹配忽略大小写与空格差异；命中后 `productName` 填**标准型号名**，不要回填用户的口语说法。
2. **按型号形态摘取**：映射表未收录时，按该文件的 `fallback_pattern` 从用户话语里原样摘出型号——
   以大写字母或数字开头，含大写字母、数字、`-` `/` `（）` `()` 空格、中文，长度 4~60；
   可能有半角/全角括号、中间空格，结尾可能是中文（一体机、套机等）。**不改写、不补全、不纠正拼写。**
3. **追问**：两者都取不到就追问型号。禁止编造型号，也不得拿相近型号顶替。

一个说法命中多个型号时（如只说「云溪4.0」但有单洗/洗烘、10kg/12kg、Pro/Max 多个版本），
按 `product_name_aliases.json` 的 `series_disambiguation` **只追问缺失的那一个维度**，不要一次抛出全部型号。

> 别名映射**不是在售商品清单**：命中只说明能把口语还原成型号，是否在售一律以工具返回的
> `channelName` / `sceneType` 为准，不得据映射表向用户声称某型号有货。

## 一之三、查询门店数 → `query_store` 的 `size`

用户明确要「多看几家」「再多来几个」时，把条数填到 `request.size`（正整数）；不确定就省略，
由后端按缺省条数返回。它只影响后端取多少家，**面向用户的展示条数仍为最多 5 家**（宿主上限 10）。

## 一之二、意向渠道槽位 → `intentChannels`

`intentChannels` 只接受**真实渠道名**（见 `assets/trigger_dict.json.intent_channels.canonical_channels`，
共八项）。「线下」是唯一的线下渠道名，其余渠道名均视为线上。触发词**取最长匹配**。

| 渠道 | 口径 | 触发词 |
|------|------|--------|
| 抖音 | 抖音电商平台，含抖音商城及直播带货 | 抖音、dy、抖音商城、抖音直播间 |
| 快手 | 快手电商平台，含快手商城及直播带货 | 快手、ks、快手商城 |
| 拼多多 | 拼多多电商平台 | 拼多多、pdd |
| 天猫 | 天猫及淘宝系，含天猫超市、天猫旗舰店 | 天猫、淘宝、淘天、tb |
| 京东 | 京东电商平台 | 京东、jd |
| 小红书 | 小红书平台购物渠道 | 小红书、xhs |
| 视频号 | 微信视频号及微信小程序商城 | 视频号、微信、wx、小程序 |
| 线下 | 线下实体渠道，含专卖店、连锁卖场、超市等 | 线下、附近、门店、专卖店、直营店、实体店、超市、商店、商场、卖场、苏宁、国美、五星、重百、门店在哪、线下店、体验店、专柜、经销商、经销商网点 |

聚合词（**不是渠道名，一律留空**）：

| 聚合词 | 口径 | 触发词 |
|--------|------|--------|
| 线上 | 泛指线上电商渠道 | 线上、电商、网上买、网购、网上、在线买、直播间 |
| 全部 | 不限制渠道 | 不限渠道、全部渠道、所有渠道、都可以、随便哪个 |

| 用户说法 | `intentChannels` |
|----------|------------------|
| 「京东上有吗」「天猫能买吗」 | `["京东"]` / `["天猫"]` |
| 「抖音直播间买得到吗」「pdd 有没有」 | `["抖音"]` / `["拼多多"]` |
| 「附近门店 / 去店里买 / 线下 / 苏宁有吗」 | `["线下"]` |
| 「京东和线下都看看」 | `["京东", "线下"]` |
| 「线上能买吗」（聚合词，未指定平台） | 留空——不要枚举平台名，拿到 `sceneType.detailType` 是否含线上（2/3）再答 |
| 「不限渠道 / 全部渠道 / 都可以 / 随便哪个」 | 留空 |
| 没提渠道 | 留空 |

**未提渠道、只提附近或地址时命中「线下」**——用户想去实体店，不要因为没出现「线下」二字就留空。

### 例外：异常地点不命中「线下」

上面那条**只对真实地点成立**。用户说的地点是**异常地点**（火星、月球、霍格沃茨这类不可能有门店的地方）时，
它不是地址：**直接忽略，不据此命中「线下」，`intentChannels` 留空**。

| 用户说法 | `intentChannels` | 为什么 |
|----------|------------------|--------|
| 「XQG120-BLE7AD3WU1 在火星有卖吗」 | **留空** | 火星不是地址，不能据此推出用户想去线下店 |
| 「这款在月球上买得到吗」 | **留空** | 同上 |
| 「火星的京东有吗」 | `["京东"]` | 异常地点忽略，真实渠道照填 |
| 「青岛有卖吗」 | `["线下"]` | 青岛是真实地址，规则正常生效 |
| 「纽约有卖吗」 | `["线下"]` | 境外城市**是真实地址**，只是门店数据不覆盖，照常处理后走无结果兜底 |

实测踩过的坑：「XQG120-BLE7AD3WU1在火星有卖吗」下发了 `intentChannels=["线下"]`，
把在售渠道范围凭空缩小成只查线下。用户其实只想知道这款在哪能买到，**留空后正常返回线上渠道**才是对的。

处理口径（完整见 `assets/trigger_dict.json` 的 `invalid_location`）：

- **不产出地址槽位**：不填 `query_store` 的 `province`/`city`/`district`/`address`，也不据此调 `query_store`；
- **不产出意向渠道**：`intentChannels` 留空，按「未指定意向渠道」正常查在售渠道；
- **话术里不复述、不点评、不纠正这个地点**（不要说「火星上没有门店哦」），直接正常回答该型号在哪些渠道有售；
- 判断依据是「**这个地方不可能有海尔门店**」，不是「这个词我没见过」：境外真实城市（纽约/东京）
  与不完整的国内地址（「朝阳区」）都**不是**异常地点，前者照常处理后走无结果兜底，
  后者按 `address_parsing.md` 的 `ambiguous` 流程确认。

**是否命中意向渠道由服务端判定**：工具返回 `sceneType.type`（1 命中 / 2 未命中 / 3 不在库）与
`detailType`（1 线下 / 2 线上 / 3 都有）。不要自己拿 `channelName` 与意向渠道求交。

## 二、特殊内容解析（命中后调整槽位再重查）

配合 `assets/trigger_dict.json.slot_adjust` 使用。命中后更新槽位，并重新执行门店/渠道查询与展示。

| 上一轮槽位 | 本次交互内容 | 解析规则（action） |
|------------|--------------|--------------------|
| 门店 | 换一批门店 / 还有别的吗 / 不要这些店 | 上一轮已展示门店名填入 `excludeStoreNames` 重新查询（多轮累计） |
| 地址 | 不要 xx 区的 / 不要 xx 市的 | 从地址范围**排除上一轮命中的省/市/区** |
| 地址 | 换成 xx 省 / xx 市 / xx 区 | 用新的省/市/区**覆盖旧值** |
| 地址 | 可以更远一点 / 更近一点 | **放宽/收窄行政区**（区 → 市 / 市 → 区），不传 `radius`（见第三节） |
| 渠道 | 更换渠道：不要这些渠道 | 上一轮 `channelName` 里命中的渠道填入 `excludeChannels` 重新调用 |
| 渠道 | 不要线上的 / 不要天猫的 / 不要京东的 | 被排除的渠道填入 `excludeChannels`（「线上」需展开成七个真实渠道名） |
| 渠道 | 话术③之后回「要 / 帮我查全部」 | **清空 `intentChannels`** 重新调用 `query_product_sale_channel` 并重走 F1 分流 |

## 三、关于「更远/更近」→ 放宽或收窄行政区，不传 `radius`

`query_store` 有一个 `radius` 入参（单位米），它**仅对按授权位置就近搜索生效**。
按用户给出的省/市/区查询时后端会忽略 `radius`——**这种情况下不要传它**，传了等于什么都没做；
已授权就近查询时「更远/更近一点」才按 ±2000 调整 `radius`。

「更远一点/更近一点」改为调整行政区范围：

| 用户表达 | 动作 |
|----------|------|
| 更远一点 / 远一点 / 范围大一点 / 扩大范围 | 行政区上提一级：区 → 市（已到市级则告知已是全市范围） |
| 更近一点 / 近一点 / 范围小一点 / 缩小范围 | 行政区下收一级：市 → 区；不知道是哪个区就追问一句 |

- 返参**不带 `distance`**（该字段仅经纬度就近搜索时返回），所以话术里不提距离，
  也不要说「最近的一家」这类基于距离的判断。

## 四、门店剔除 → `query_store` 的 `excludeStoreNames`

「换一批 / 还有别的吗 / 不要这些店 / 换几家」命中时，把**上一轮已展示给用户的门店名**
（返参 `storeName` 原文）填入 `request.excludeStoreNames` 重新查询——命中的门店后端不再返回，
**不需要也不应该再在本地过滤结果**。

- **多轮连续换批要累计**：第二次「换一批」时，`excludeStoreNames` 应同时包含第一批与第二批已展示的门店名，
  否则会把用户看过的门店又换回来。
- 门店名按 `storeName` 原文填写，不改写、不截断、不只填一部分（如只填「海尔专卖店」会误伤同名连锁的其它分店）。
- 排除后结果不足时：可放宽范围（行政区上提一级，如区 → 市），或如实说"暂时没有找到新的门店了"，
  不编造门店，**也不要断言"该区域只有这些"**——你只知道本次查询返回了什么，不知道总量。
