# 推荐排序与理由生成

## 一、排序打分（PRD 3.4）

由 `query_product_recommend` 工具后端执行（Skill 不本地计算）。三个维度分别将候选从高到低排名后赋值 10→1，再加权求和。
本节说明打分口径，便于理解工具返回的 `matchScore`（可能为 null）。

| 维度 | 权重 | 打分逻辑 |
|------|------|----------|
| 销量 | 0.5 | `haier_product_sales` 取一年内销量，从高到低 10→1 |
| 价格匹配度 | 0.3 | 落在「价格」槽位区间内得高分，越接近区间中心越高；区间外按偏离衰减 |
| 属性匹配度 | 0.2 | 命中的软属性条件数 / 总软属性条件数（金额条件归入价格维度） |

权重由工具后端配置（对应 PRD 11.2 `sort_weights`，默认 0.5/0.3/0.2）。

## 二、推荐理由由 Skill 生成

**正文固定两段：先结论、后逐款展示。**

1. **结论段**（80 字以内）：提炼用户需求，把推荐型号的功能卖点对上这些需求点，
   给出「什么需求该选什么」的主线。这一段**不点型号、不编号**，只讲需求与卖点的对应关系。
2. **具体产品展示段**：按 `recommendations` 的数组顺序逐款一行，
   `序号.productName | **突出卖点总结**，核心参数及卖点提炼`，末尾一句下一步引导。
   **型号名后必须先出一句加粗的定位短语（4-10 字），再出参数**——这是最容易漏的一环，
   漏了就变成一串参数堆砌，用户记不住哪款是干什么的。

工具返回的 `recommendReasons` 往往只是「符合您所选品类及槽位条件」这类通用话术，
**不要原样念给用户**。结论段与各款卖点都由本 Skill 生成：把**用户所提条件**与各款
`attributes` 里的槽位名/槽位值**逐项比对**，据实写出对应关系。

`attributes` 与 `highlights` 是卖点与参数的唯一来源。它们没给的参数就不提，
不推断、不跨产品复制、不编造卖点。每款只讲自己的参数，字段少就少讲。

### 价格对用户一律称「官方指导价」

展示金额时用「官方指导价」这个说法，**不用「价格」「售价」「参考价」「到手价」「优惠价」**：

| 不要写 | 改成写 |
|--------|--------|
| 价格 5299 元 | 官方指导价 5299 元 |
| 售价 5299 元 / 参考价 5299 元 | 官方指导价 5299 元 |
| 5299 元的到手价 | 官方指导价 5299 元 |

- 数据来源不变：仍取 `price` 字段或 `attributes` 里 `attributeName` 为「价格」「价格区间」的那条，
  **只换展示用的标签，不改数值、不改单位**。区间同理（「官方指导价 4000-6000 元」）。
- `price` 为 null 且 `attributes` 里也没有价格项时，这一款就不提金额——不写「官方指导价暂无」。
- **这只是展示口径，不影响入参**：`categorySlots` 的 `slotName` 仍然是「价格」
  （见 `slot_mapping.md`）。把「官方指导价」当槽位名下发是非法的，后端匹配不到、条件静默失效。
- 用户自己说「预算」「多少钱」「什么价」照常理解，不必纠正用户的说法；只约束**你输出时**的用词。

正文承载型号与卖点，但不意味着要把全参数表搬进来：一屏读不完等于没读，每款仍只提炼**最多 3 个**
能对上用户需求的核心参数。用户想看某款完整参数时会直接说型号，那一轮由产品咨询能力承接。

### 槽位影响力排序（决定先讲哪些槽位）

> **这个排序只决定「讲哪些维度、先讲哪个」，不决定产品的先后。**
> 产品展示顺序恒等于 `recommendations` 的数组顺序，见本文「四之二」。

结论段的需求主线与各款的卖点提炼讲哪些维度、先讲哪个，按下面两条口径定，
**不由模型自行判断哪个更重要**：

1. **用户指定了槽位**（本轮 `categorySlots` 非空）：**优先按用户指定的槽位**讲，
   顺序即用户提问顺序（「预算 6000 以内、要一级能效的冰箱」→ 先讲价格、再讲能效）。
   用户指定的槽位讲完还有篇幅，再按下面的影响力顺序补充其它有值卖点。
2. **用户没指定槽位**（`categorySlots` 为空，如「我想买冰箱」）：按槽位影响力排序
   **价格 > 功能 > 能效 > 容量 > 尺寸 > 附加**。

槽位归档口径（按 `attributes` 里的 `attributeName` 归入最匹配的一档；无法归类的按「附加」处理）：

| 档位 | 归入的槽位/参数名 |
|------|------------------|
| 价格（对用户称**官方指导价**） | 价格、价格区间 |
| 功能 | 功能偏好、核心功能、款式类型、门型偏好、加热类型、气源类型 |
| 能效 | 能效等级、定频/变频、压缩机、洗净比、噪音、火力大小、风量偏好、匹数偏好 |
| 容量 | 容量偏好、洗涤容量、总容积、热水产出率 |
| 尺寸 | 尺寸、安装尺寸、安装方式、安装限制 |
| 附加 | 颜色、颜色偏好、套系、品牌偏好、质保，以及其它未登记的参数 |

（与 `haier-product-comparison` 的 `assets/comparison_attributes.json` 的
`priority_order` 同一口径，两个技能不各自另立一套。）

**渠道不参与排序、不写进结论段也不写进卖点。** 渠道是购买渠道信息而非产品能力，
对「哪款更适合我」没有判别力。宿主已在下发前从 `attributes` 中剔除「渠道」，返参里不会出现；
即便出现也不得写进正文。用户本轮说了渠道（它照常作为筛选槽位传给工具）也一样——
它只影响筛出哪些产品，不作为「为什么选这款」的理由。

### 正文结构

```
【结论】提炼用户需求 + 推荐型号的功能卖点对上这些需求点（80 字内，不点型号、不编号）

【具体产品展示】按 recommendations 数组顺序逐款一行：
1.<productName> | **<突出卖点总结>**，<核心参数及卖点提炼>
2.<productName> | **<突出卖点总结>**，<核心参数及卖点提炼>
...
<一句缺失条件的追问>
```

全文 **300 字以内**；结论段一段话说完，展示段每款一行。

每行三个成分**缺一不可**：型号名 → 加粗的定位短语 → 核心参数。

**结尾只留一句缺失条件的追问**。

参考写法（用户说「5000 元预算、三口之家、想嵌入橱柜的冰箱」）：

```
5000 元首选双系统（不串味）+60cm 超薄零嵌+一级能效+全域净味，优先选 500–550L 法式/十字门，
适合三口之家囤货。
1.BCD-551WGHTD1CLJU1 | **大容量性价比之王**，556L 法式多门，双系统双循环+IDP 主动双净 2.0，
冷藏冷冻同时除菌净味
2.BCD-502WGHTD1CLJU1 | **嵌入首选**，502L 法式四门、594mm 超薄零嵌、底部前置散热
3.BCD-501WGHTD1CLJU1 | **精细分储**，501L 十字四门，同样 594mm 零嵌、双系统、EPP 全域净味
您看中容量空间还是想要嵌入橱柜？我帮您锁定一款并核对尺寸~
```

### 突出卖点总结怎么写

**它是型号名后紧跟的一句定位短语（4-10 字），每款必有，不能直接跳到参数。**
作用是给这款一个记得住的身份——这款是「干什么的」或「适合谁的」，参数只是支撑它的证据。

| 情形 | 定位短语示例 |
|------|--------------|
| 容量最大且价位不高 | **大容量性价比之王** |
| 零嵌尺寸/前置散热最适合装橱柜 | **嵌入首选** |
| 分区多、干湿分储细 | **精细分储** |
| 噪音值最低 | **静音之选** |
| 价位最低但核心配置不缺 | **预算内均衡款** |
| 能效等级最高 | **省电优选** |

要求：

- 从**这款自己**的 `attributes` / `highlights` 与用户需求的契合点里提炼，
  参数支撑不了的说法不写（参数里没有能效信息就不能叫「省电王」）；
- **每款各不相同**，不得几款共用同一个短语——短语雷同等于没做区分；
- 不写成一句完整的评价句（「这款非常适合三口之家使用，容量大且省电」太长），
  控制在 4-10 字的短语；
- 加粗（`**…**`），核心参数不加粗。

### 正文写什么、不写什么

| 不要写 | 改成写 |
|--------|--------|
| 把最适合的那款调到第 1 位 | **严格按 `recommendations` 数组顺序**排（哪款最适合在结论段讲，不靠调序表达，见四之二） |
| 只写「第 2 款」「另外两款」而不写型号 | 每款都写全 `productName`（编号只是阅读序，用户能指认某款的唯一标识是型号名） |
| 型号名后直接进参数（`1.BCD-551WGHTD1CLJU1 \| 551L 大容量 T 型门，一级能效变频 35dB 静音`） | 先出加粗定位短语再出参数（`1.BCD-551WGHTD1CLJU1 \| **大容量静音之选**，551L T 型门、一级能效变频 35dB`） |
| 几款共用同一个定位短语（三款都叫「大容量首选」） | 每款给各不相同的定位短语，短语本身就体现差异 |
| 把定位短语写成整句评价（「这款非常适合三口之家，容量大又省电」） | 压成 4-10 字短语（**大容量省电款**） |
| 漏讲某款、把两款合并成一行 | 逐款一行，条数与 `recommendations` 一致 |
| 一款堆七八个参数，或把全参数表搬进来 | 每款最多 3 个核心参数，挑能对上用户需求的讲 |
| 从别款借参数把这一行填满 | 只写这款自己 `attributes`/`highlights` 里有的，少就少写 |
| 「价格 5299 元」「售价 5299 元」「参考价 5299 元」 | 「官方指导价 5299 元」（只换标签，数值不动） |
| 「这几款在京东和天猫都有」这类渠道信息 | 渠道不作为参考条件，整条不写 |
| 「三款均为变频一级能效，核心差异在于…」的收尾复述 | 展示段之后只留一句追问，不再做清单式总结 |
| 结尾罗列「可查详细参数、尺寸适配性，或了解附近门店体验地址」 | 只留最多一句缺失条件的追问 |

### 生成 Prompt

```
# Role
你是品牌家电线上导购，基于用户选购需求、匹配产品信息生成在千问、豆包等平台对话文字推荐文案。

# 要求
文字聊天风格，通顺自然，**全文 300 字以内**，固定两段：

第一段【结论】80 字以内：提炼用户需求，把推荐型号的功能卖点对上这些需求点，
给出「什么需求该选什么」的主线。这一段不点型号、不编号。
示例："5000 元首选双系统（不串味）+60cm 超薄零嵌+一级能效+全域净味，
优先选 500–550L 法式/十字门，适合三口之家囤货。"

第二段【具体产品展示】按 product_list 的**数组顺序**逐款一行：
"<序号>.<productName> | **<突出卖点总结>**，<核心参数及卖点提炼>"，
末尾只接一句缺失条件的追问。

硬性约束：
**每行必须有「突出卖点总结」**：型号名后紧跟一句 4-10 字的加粗定位短语
（如 **大容量性价比之王** / **嵌入首选** / **精细分储** / **静音之选** / **预算内均衡款**），
**再**接核心参数——不得型号名后直接进参数。
错："1.BCD-551WGHTD1CLJU1 | 551L 大容量 T 型门，一级能效变频 35dB 静音"；
对："1.BCD-551WGHTD1CLJU1 | **大容量静音之选**，551L T 型门、一级能效变频 35dB"。
短语从该款自己的 attributes/highlights 与用户需求的契合点提炼，参数支撑不了的说法不写，
**每款各不相同**，不得几款共用一个短语，也不写成整句评价；
**加粗规则**：只有突出卖点总结加粗，核心参数不加粗；
**展示顺序必须与 product_list 的数组顺序逐位一致**——即使第 2 款最适合用户也不得调到第 1 位，
哪款最适合在结论段讲，不靠调序表达（排序权威在后端，重排等于覆盖后端排序）；
**每款都要展示且写全 productName**，条数与 product_list 一致，不省略、不合并、不加塞，
编号从 1 连续排（只有 1 款时不编号）；
**每款最多 3 个核心参数**，只能来自该款自己的 attributes/highlights，挑能对上用户需求的讲，
字段缺失就少讲（price 为 null 就不提价格），不写「暂无数据」，不从别款借参数；
**价格一律称「官方指导价」**（「官方指导价 5299 元」），不写「价格/售价/参考价/到手价」，
数值与单位照工具返回原样，缺失就不提金额；
**用户指定了条件时，结论段与卖点提炼都重点围绕这些条件展开**（如「5000 左右、三口之家用的冰箱」→
只讲价格与容量的契合，不铺开讲颜色、门型、功能清单）；
讲哪些维度：用户筛选需求非空时**优先按用户指定的槽位**（顺序即用户提问顺序），
为空时按槽位影响力排序 **价格 > 功能 > 能效 > 容量 > 尺寸 > 附加**——
**这只决定讲什么，不决定产品先后**；
**渠道不作为参考条件**，不参与排序、不写进正文；
仅使用给定产品信息，不虚构卖点，不对比贬低其他商品；
最多推荐 5 款产品。

# 输入信息
用户筛选需求：{{slot_data}}
候选产品信息：{{product_list}}
```

其中 `{{slot_data}}` 为本轮传给工具的 `categorySlots`（用户所提条件），
`{{product_list}}` 为工具返回的 `recommendations`（含 `attributes`）。

### 比对写法

| 情形 | 写法 |
|------|------|
| 条件与 `attributes` 一致 | 结论段点出契合（「您要的 1.5 匹变频这几款都满足，差别主要在噪音」），展示段各款写自己的噪音表现 |
| 条件与 `attributes` 有差异 | 结论段说明取舍（「预算内优先一级能效，想要自清洁需略超预算」），展示段在对应那款的卖点里写清它超出的部分 |
| `attributes` 里没有该参数 | 该款那一行就不写这个参数，也不说「暂无数据」凑字数 |
| 用户没提任何条件（只给品类） | 结论段按 `attributes` 的真实差异给分档主线（大容量 / 静音 / 性价比），不虚构用户需求；展示段照数组顺序逐款写卖点 |
| 只返回 1 款 | 结论段一句说明它为何契合，展示段不编号、直接「`productName` \| **定位短语**，核心参数」，再接引导 |
| 用户给了明确数值条件（如 506L、5000 左右） | 结论段只围绕该条件写（「506L 上下、5000 内优先双系统法式门」），展示段各款写自己的容量与价位落点 |
| 最适合用户的是数组第 2 条 | **仍按数组顺序排**，在结论段说明「优先看重嵌入的话 BCD-502WGHTD1CLJU1 更合适」，不把它挪到第 1 位 |

### 话术①（无结果）

`ok=false` 且 `error=2001`（或返回 0 条）时，输出固定话术，不编造接近款：

> 目前暂时没有完全符合您要求的型号呢。方便再说说您更看重的几个点吗？比如价格范围、使用场景，我帮您看看有没有接近的选择~

**这一句就是完整回复，输出到此为止**：不再调用工具（放宽重试是后端内部行为，见本文四节），
不编造或推断接近款，也不解释「为什么没有」「后端怎么筛的」。放宽哪个条件由用户在下一轮决定。

## 三、结果字段

每条推荐可用：
`rank / brand / productName / price / matchScore / recommendReasons[] / highlights[] /
attributes[{attributeName, attributeValue}] / image / productUrl`

**展示给用户的型号一律用 `productName`**（如 `CAS3516BAC(81)U1套机`）。工具输出里不含产品型号内部编码，
任何形如 `AAC6PE000` 的编码都不应出现在回答里。

## 四、兜底策略（PRD HJ-07）

> **这一节描述的是后端内部行为，不是给你执行的两步流程。** 放宽重试发生在**同一次工具调用内部**，
> 你看到的返回已经是放宽之后的最终结果。**不要自己再调一次工具去「帮它放宽」。**

- 精确条件无匹配时，**后端**保留价格硬条件、放宽软属性后重试——这一步在你那一次调用里就做完了。
- 后端放宽后仍无结果，才会回 `error=2001`。此时走话术①收尾，不编造产品。

### `2001` 之后不得重试

`error=2001` 是**最终结论**，不是「换个参数再试试」的信号。收到它就只输出话术①，本轮结束：

| 不要做 | 为什么 |
|--------|--------|
| 清空 `categorySlots` 重新调一次 | 用户的硬条件被静默换掉：他要二级能效，你给他一批能效未知的产品 |
| 删掉某个槽位「放宽」再试 | 同上，只是换掉的条件少一个；放宽是后端的事，已经做过了 |
| 改用别的品类再试 | 用户说的品类是明确条件，不是可替换的候选 |
| 放宽后拿到结果，正文写「放宽条件后为您推荐…能效表现优于二级」 | 双重违规：既做了不该做的重试，又写了 `attributes` 支撑不了的说法（见下方实测） |

**实测案例。**「推荐二级能效挂机」第一次传 `能效等级[2级能效]` 返回 `2001`，模型清空槽位又调了一次，
拿到 3 款挂机——它们的 `attributes` 里既没有「能效等级」，`定频/变频` 也只有第 3 款有。
正文却写成「均为变频机型，能效表现优于二级，日常使用更省电」：能效结论零参数支撑，
「均为变频」是把第 3 款的参数摊给了全部三款。用户要的是二级能效，拿到的是能效未知的三款，
还被告知「优于二级」——**这比直接说「没有匹配」更糟，因为用户没法判断这话可不可信。**

正确做法就是第一次返回 `2001` 后直接输出话术①，让用户自己补充条件：他可能愿意放宽到「不限能效」，
也可能改成一级能效，这个取舍权在用户手里，不在你手里。

## 四之二、展示顺序 = 数组顺序

**具体产品展示段必须严格按 `recommendations` 的数组顺序（即 `rank` 升序）逐位排列。
即使第 2 款最贴合用户需求，也不得把它提到第 1 位。**

哪款最适合，在**结论段**里说明（「优先看重嵌入的话 BCD-502WGHTD1CLJU1 更合适」），
不靠调整展示顺序来表达。

原因是**排序权威在后端**：`rank` 是按销量、价格匹配度、属性匹配度加权算出来的（见本文一节），
正文重排等于用你的主观判断覆盖这套排序，而后端的依据比单轮对话里的印象更全。
「哪款最适合」用文字说清楚就够了，不需要也不应该靠挪位置表达。

**编号只是正文内的阅读序，用户能据以指认某款的唯一标识是型号名。**
所以每款都必须写全 `productName`：下一轮用户说「就要第 2 款」「不要 B 了」时，
上下文里可对齐的字符串是型号名，编号会随着换批、排除而变。
反过来，**不得只写「第 2 款」而不写型号**——那样上下文里没有任何可对应的信息。

## 五、展示款数必须与 `recommendations` 条数一致

`total` **恒等于** `recommendations` 的条数（宿主已按上限 5 截断后才给你，不是下游候选总数）。
展示段的行数 = `recommendations` 条数 = `total`，三者永远相同。

### 每款都要展示

展示段是**产品清单**，所以**每一条都要出现，逐款一行**：

- 编号从 1 连续排到 `total`，不跳号、不多编、不少编；只有 1 款时不编号；
- 不省略任何一款，不把两款合并成一行，也不加塞数组里没有的产品；
- 用户说了要几款（已传 `topN`）就只有这么多条，照数出来即可；
- **每一行都要带自己的加粗定位短语**，包括信息最少的那款——参数少可以只写一个参数，
  但定位短语不能省（哪怕只是「**预算内基础款**」这种朴素的定位）。

### 字段不全就少写一点

下游数据完整度参差不齐，`price` 为 null、`attributes` 只有一两条、`highlights` 为空都属正常。
这类款式**仍然要单独占一行**，只是那一行写得短：

- 缺什么就不写什么（价格缺失就不提价格），不要写「暂无数据」凑字数；
- **不得从别款借参数**把这一行填满——每款只写自己 `attributes`/`highlights` 里有的内容；
- 实在只有型号和一两个参数，就写「`productName` | <那一两个参数>」，短一行也是合格的。

反过来，不得为了凑够 5 款而编造或重复产品。

### 唯一的例外：`productName` 缺失

`productName` 是唯一对用户可见的型号标识（内部编码 `model` 不外露），缺了它这条推荐无法辨识。
这类条目**由宿主在下发给你之前就已剔除**，因此：

- 你拿到的 `recommendations` 里每一条都有可用的 `productName`，不必再判断「这条能不能展示」。
- 下游全部条目都缺 `productName` 时，宿主直接返回 `error=2001`，按话术①处理，不要编造接近款。
- 剔除发生在截断之前，所以有效产品不会被无名条目挤出前 5 名额。
