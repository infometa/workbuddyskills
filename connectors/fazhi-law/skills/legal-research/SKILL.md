# 法律研究(法律分析)

> 不是出具研究报告，不套模板——把问题查得更深、更全、更准，然后给出一个经得起推敲、来源可溯的法律回答。
> 本 skill 使用六工具体系，但仍按三类来源组织研究：

- **互联网公开来源**：`webpage_search（联网搜索）`、`webpage_visit（网页阅读）`
- **法规规范来源**：`legal_article_search（法条综合检索）`、`law_content_visit（法规全文阅读）`
- **司法案例来源**：`case_search（案例检索）`、`case_browser（案例全文阅读）`
其中，三类检索来源保持并行；读取与核验工具基于已取得的检索结果按需使用。

---

## 意图路由与法律兜底

1. 先识别用户是否明确要求专用任务或交付物。法条查询、案例检索、法律文书、法律意见书、企业法律尽职调查、法律尽调报告和案件可视化存在可用专用技能时，优先路由至专用技能。
2. 只要请求仍包含法律判断、规则解释、权利义务、责任风险、争议解决或合规分析，且没有专用技能完整承接，就使用本技能继续处理。
3. 对混合型请求，按交付物拆分并由各专用技能分别完成；本技能仅承接未被专用技能覆盖的综合法律分析，不得以兜底名义吸收法律文书、法律意见书或法律尽调报告。
4. 对简单兜底请求按需缩减论证节点和检索轮次；对复杂、争议性或高风险事项执行完整三源研究流程。
5. 用户明确指定技能或工具时，以用户选择为准。

---

## 核心原则

1. **先想清楚再动手**：先拆解问题为论证主线（3-5 个论证节点），再围绕主线逐维检索。论证节点是阶段 5 最终回答的标题雏形。
2. **三源并行，互相印证**：每轮检索中 `webpage_search（联网搜索）`、`legal_article_search（法条综合检索）`、`case_search（案例检索）` 无优先级差异，必须并行发出；`webpage_visit（网页阅读）`、`law_content_visit（法规全文阅读）`、`case_browser（案例全文阅读）` 作为读取与核验工具，基于检索结果按需使用。三种来源互相补充、交叉验证，共同构建问题全貌。
3. **正反方必须覆盖**：每个法律问题强制检索支持方和反对方两类观点，不可只呈现一面。
4. **孤证不立**：每个关键结论至少两个独立来源印证；只有一个来源的结论必须标注「单一来源，仅供参考」。
5. **时事新闻热点，互联网优先**：先通过 `webpage_search（联网搜索）` 和必要时的 `webpage_visit（网页阅读）` 了解实务动态、新闻热点真实情况，互联网文章中引用的规范性文件和案例必须在后续阶段回到 `legal_article_search（法条综合检索）`、`law_content_visit（法规全文阅读）`、`case_search（案例检索）` 或 `case_browser（案例全文阅读）` 的结果中核实；未核实到的标注「互联网来源引用，检索未核实到对应文件」。
6. **全程静默执行**：阶段 0-4 全部内部完成，不向用户展示任何检索规划、进展、中间结论。用户从提出问题直接到阶段 5 最终回答。
7. **论证草稿贯穿全流程**：阶段 1-4 每轮检索后，将关键发现以索引式记录（≤20 字主旨 + 来源标注）追加到按论证主线组织的内部草稿中，不展开成文。阶段 5 以草稿为蓝本展开写作。
8. **不编造任何内容**：案号、法条编号、网页内容、实务观点——要么来自工具返回，要么标注「未检索到」。
9. **引用必有链接**：最终输出的回答中，凡引用工具召回结果的（具体法条、整部法规、案例、网页等），必须让法规全称及条款编号（如有）、案号或网页序号本身绑定对应链接，确保可溯源核验。

## 工具调用

通过 **fazhi-mcp** 技能调用 MCP 工具，具体调用方式、参数 schema 和工具选择规则见 [../fazhi-mcp/SKILL.md](../fazhi-mcp/SKILL.md)。

本技能使用全部六个工具，按三类来源组织：


| 来源类型    | 检索工具                   | 读取/核验工具             |
| ------- | ---------------------- | ------------------- |
| 法规规范来源  | `legal_article_search` | `law_content_visit` |
| 司法案例来源  | `case_search`          | `case_browser`      |
| 互联网公开来源 | `webpage_search`       | `webpage_visit`     |


三类检索工具同轮并行发出，无优先级差异；读取与核验工具基于检索结果按需使用。每轮每工具检索语句最多 3 条；同一目标失败或空结果最多重试一次，且重试必须改变表述。

## 必须实际调用工具并依据真实返回结果继续研究，不得只输出调用计划或伪造工具结果。



## 核心工作流：Agentic 自主研究循环

阶段 1-3 采用 Plan → Search → Read → Reflect → Decide 五步循环，模型在每轮结束后自主评估信息充分性，动态决定下一步方向。

- **Plan**：基于当前已掌握信息，明确本轮要填补的知识缺口，生成针对性检索语句。
- **Search**：`webpage_search（联网搜索）`、`legal_article_search（法条综合检索）`、`case_search（案例检索）` 同轮并行，无依赖检索任务一次全部发出；`webpage_visit（网页阅读）`、`law_content_visit（法规全文阅读）`、`case_browser（案例全文阅读）` 在 Read 阶段按需调用。
- **Read**：对高相关性条目深度阅读，强制记录文章中引用的法条与案号供后续验证。
- **Reflect**：每轮检索结束后强制执行。按来源类型分别小结，判断信息是否「足够」，不足则生成新检索语句。同时强制回答：正反方是否均已覆盖？互联网引用的法条/案例是否已在法规规范来源/司法案例来源中核实？三源之间是否存在信息冲突？反思轮次最多 3 轮。
  > 对疑难、争议性、新规、案例导向问题，至少进行两轮检索反思。
  > 对规范依据明确、无明显争议、无需案例支撑的问题，完成一次法规核验后即可进入回答，但需在输出前进行简化交叉验证。
- **Decide**：根据综述和对策循环终止信号决定继续或进入下一阶段。



### 循环终止信号

满足 ≥3 条即可终止：

1. 正反方各 ≥2 个独立来源支撑；
2. 关键法条的效力状态均已核实；
3. 本轮与前轮检索结果高度重复，无新增实质信息；
4. 剩余维度缺口仅涉边际问题，不影响核心结论形成。

## Plan 阶段：内部规划结构

阶段 0 完成并拆解完毕后直接进入检索，无需等待用户确认。进入检索前须在内部完成一轮规划，明确本轮要查什么、用什么工具、检索语句如何构造。规划遵循多轮次逻辑（最多 2 轮），每轮根据上轮结果判断是否结束。
规划在思考中按以下结构组织（仅内部使用，不向用户展示）：

1. **你的思考**：内部仅保留简要研究状态，不输出推理过程。每轮记录：核心问题、已确认依据、未确认缺口、下一步检索目标。
2. **用户诉求**：按「法律关系 + 时空范围 + 数据类型」提炼，至少含 1 个法律争议焦点。
3. **工具检索思路**：1-2 句话说明为什么这样检索，含核心检索维度与检索价值；不出现具体检索语句或工具名。
4. **工具调用**：JSON 字典，键为工具（`legal_article_search（法条综合检索）` / `case_search（案例检索）` / `webpage_search（联网搜索）`），值为检索语句列表。仅列需使用的检索工具，每工具最多 3 条。`law_content_visit（法规全文阅读）`、`case_browser（案例全文阅读）`、`webpage_visit（网页阅读）` 在已有明确读取对象后按需列入。
5. **工具检索目标**：对有检索语句的工具各生成 1 个目标（「搜索类动词 + 核心信息」≤15 字）；无检索语句的工具不生成。
6. **是否结束**：「结束」或「继续」。



### 规划结束条件

两个条件同时满足即结束规划：

1. 已明确用户核心诉求（完整主体、关系、争议焦点）；
2. 已界定具体搜索要素——争议焦点、关键事实、主体关联，且各工具检索语句满足规范（互联网含必要背景、案例含 ≥2 维度、法条无具体法规名）。



### 诉求覆盖原则

必须将用户核心诉求拆解为关键维度，每个检索工具语句需：

- **主体全覆盖**：禁止用「相关方」替代；
- **关系全穿透**：直接体现主体间法律关系；
- **焦点全命中**：明确指向争议焦点。
每个维度至少对应一个检索语句。



### 规划注意事项

- 对复杂、争议性、实务动态强或需案例支撑的问题，原则上三源并行检索。
- 对简单、规范依据明确且无需实务背景的问题，可仅使用法规规范来源；但若最终回答涉及裁判趋势、实务观点或争议判断，应补充司法案例和互联网公开来源。
- 历史检索某工具结果不理想，不允许同一输入重复调用，须改变检索语句表述。
- 多次检索仍无结果时，可选择终止规划并注明原因。
- 用户提及具体案号时，查实务文章应重点从核心法律争议点是否相似入手，忽略地域、时间、诉讼层级等非关键元素。

| **补充目标**   | 仅继续时生成，按工具概括核心目的 ≤15 字；停止时空字典                                                                                                          |

## 各来源「足够」标准

三类来源共享同一判断框架，均需满足以下五条件：


| 条件   | 含义                                                      |
| ---- | ------------------------------------------------------- |
| 匹配度  | 检索结果与用户问题的法律关系、争议焦点直接对应，非间接关联                           |
| 数量   | 有效结果足够（案例 ≥3、文章 ≥2 且不同来源、法条覆盖核心 + 配套）                   |
| 多样性  | 覆盖不同情形/来源/维度（案例含不同裁判观点或法院，文章来自不同平台，法条含配套条款）             |
| 完整性  | 内容完整可引用（案例含案情 + 焦点 + 理由 + 结果，文章含实操/风险拆解，法条含适用条件 + 法律后果） |
| 缺口排除 | 已明确排查是否缺少某类特殊情形/场景/主体/时效的覆盖                             |




### 差异化阈值

- **司法案例来源**：≥3 个有效案例（去重后），覆盖 ≥2 种不同情形（不同法院、不同裁判层级或相反观点），裁判理由明确引用核心法条。
- **互联网公开来源**：≥2 篇有效文章且来源不同（律所/法院公众号/专业平台），含具体实操步骤或风险拆解（非仅观点陈述），覆盖全流程关键环节或全维度风险点。
- **法规规范来源**：为现行有效（排除已废止/修订），涵盖「核心法条 + 配套条款 + 司法解释」，内容完整（非片段引用），明确适用条件与法律后果。

---



## 必须继续检索的刚性规则

以下任一情况，必须继续检索：

- 实际反思轮次 < 2；
- 某类来源检索结果未满足上述「足够」标准中任意一项；
- 不同来源结果存在信息冲突（裁判观点矛盾、实务文章与法条解读不一致）；
- 未明确排查潜在未覆盖法律风险/事实场景，或排查后仍有缺口；
- 首轮后某类来源有效结果数量为 0 或仅 1 个；
- 核心法律问题涉及新规（近 1 年生效）或疑难复杂问题，仅一轮未获取权威解读。



### 反思结束条件

满足任一即可结束：

1. 所用来源各自均达「足够」标准，且刚性规则全部满足；
2. 已达最大反思轮次 3。

---



## Query 构造总则

- **多维度关键词组合**：复杂诉求检索语句至少包含以下 2 个及以上维度：法条依据（仅案例/互联网检索语句可含具体法条）、时间范围、具体场景/类型、核心主体、争议焦点。
- **数量限制**：每个检索工具最多 3 条；结束规划时须含基于明确搜索要素的拆解问句；若规划需「继续」，新检索语句须补充更多维度。
- **严禁形式**：简单续写用户问句；「法条」「法律规定」「相关案例」等无意义术语堆砌；与历史失败检索语句同义替换式重复。

## 阶段 0：问题拆解（内部，静默）

> 本阶段全流程不向用户展示，拆解完毕后直接进入阶段 1 检索。



### 0.1 理解问题

先理解用户到底在问什么：涉及什么法律关系、争议焦点在哪、需要从哪几个角度切入。去掉具体人名、金额、日期等个性化信息，保留法律关系和争议焦点。

### 0.2 主体—关系—焦点锚定

严格以用户原始问题的字面表述为依据，仅提炼用户明确提及的要素，禁止擅自添加未提及的前提条件：

- **主体锚定**：完整提取用户明确提及的所有法律主体，不得遗漏或替换为「相关方」「当事人」等。
- **关系锚定**：明确主体间的法律关系，必须直接源自用户表述。
- **争议焦点锚定**：精准锁定核心法律问题，禁止用模糊表述替代。



### 0.3 确定研究维度 + 论证主线

围绕问题焦点，从以下 6 个维度中选取适用维度（实务动态和基础法条为必选，其余按需选择）：


| 编号                                                                                                         | 维度         | 要搞清楚什么             | 推荐度 |
| ---------------------------------------------------------------------------------------------------------- | ---------- | ------------------ | --- |
| ①                                                                                                          | 基础法条       | 相关行为的法律构成要件和法律效果   | 必选  |
| ②                                                                                                          | 司法解释/行政法规  | 相关领域有哪些配套下位规范      | 推荐  |
| ③                                                                                                          | 类案支持方      | 法院支持相关主张的理由和典型案型   | 按需  |
| ④                                                                                                          | 类案反对方      | 法院不支持相关主张的理由和典型案型  | 按需  |
| ⑤                                                                                                          | 实务动态与争议    | 实务界和学术界怎么看、有无分歧    | 必选  |
| ⑥                                                                                                          | 地域/审级/时效差异 | 不同地区、不同审级、不同时期有无差异 | 按需  |
| **论证主线规划（内部）**：研究维度是「查什么」，论证主线是「怎么组织回答」。内部确定 3-5 个论证节点作为最终回答的逻辑骨架和阶段 5 标题雏形，例如「构成要件 → 举证责任 → 法律后果 → 风险提示」。 |            |                    |     |




### 0.4 用户诉求提炼

按「法律关系 + 时空范围 + 数据类型」结构提炼，至少含 1 个法律争议焦点。

#### 热点事件类专项规则

当用户问句涉及特定事件且信息模糊时：

1. **第一步**：必须先用 `webpage_search（联网搜索）` 获取事件「核心事实 + 法律争议焦点」；必要时用 `webpage_visit（网页阅读）` 核验重要网页内容。
2. **第二步**：用户诉求必须包含「事件核心事实 + 至少 1 个法律争议焦点」，禁止仅提「某事件相关信息」。
3. **第三步**：配套生成各工具语句——互联网补背景、案例查裁判、法条找依据。若某类工具与诉求无关，可不使用。



#### 以案搜案专项规则

- 本专项仅适用于用户要求**围绕已知案例继续开展法条、类案、实务文章等多来源扩展研究**的场景。
- 用户仅要求读取具体案号、概括单份裁判文书或查找相似案例时，应作为纯案例检索处理，不启动三源综合研究。
- **规划阶段（强制）**：

1. 必须用 `case_search（案例检索）` 查原案例号背景，格式为「[案例号] 裁判文书 争议焦点 法律关系」；必要时用 `case_browser（案例全文阅读）` 核验原案内容。
2. 可同时用 `webpage_search（联网搜索）` 查媒体报道，但 `case_search（案例检索）` 为必填。
3. 获取原案背景后，基于核心事实 + 争议焦点生成「查类似案例」语句。

- **禁止**：
- 第一步直接生成「[案例号] 类似案例」；
- 仅写「查找与 [案例号] 类似的案例」；
- 生成仅含「地域 + 时间」的空泛语句。
- **反思阶段**：
- 未获取原案背景 → 新语句须含「原案号 + 核心信息检索维度」；
- 已获取原案背景 → 基于「原案核心事实 + 争议焦点 + 类案维度」生成，禁止重复案号 + 类似案例。



#### 非事件类

须含「主体 + 法律关系 + 争议焦点」。

### 0.5 检索策略

三类检索来源无优先级差异，同轮必须并行发出。每轮 `webpage_search（联网搜索）`、`legal_article_search（法条综合检索）`、`case_search（案例检索）` 各 2-3 条检索语句，合计 6-9 条一次全部发出。
通过互联网公开信息获取实务全貌和争议焦点，通过法规规范来源定位规范依据和效力状态，通过司法案例来源补充司法实践图景——三类结果在 Reflect 环节交叉比对、互相验证。`webpage_visit（网页阅读）`、`law_content_visit（法规全文阅读）`、`case_browser（案例全文阅读）` 用于后续读取、核验和补强。

### 0.6 案例查询条件抽取

调用 `case_search（案例检索）` 前，须判断用户问题中是否蕴含案例查询的约束条件。仅三种类型有效，其余忽略：


| 条件类型                                                                                                                   | 定义         | 注意事项                                  |
| ---------------------------------------------------------------------------------------------------------------------- | ---------- | ------------------------------------- |
| **时间**                                                                                                                 | 时间点或时间段    | 可抽象（「近三年」）；具体日期用标准年月日格式               |
| **地域**                                                                                                                 | 案件审理所在行政区划 | 公司所在地不认作地域要求；「全国」「国内」不作为条件；泛指法院名不作为条件 |
| **案号**                                                                                                                 | 判决书/裁定书案号  | 仅此两类有效；决定书、案例库号、指导案例号不作为案号条件          |
| **甄别要点**：用户描述一个具体案例时，须甄别其真实意图是查该案例还是查类似案例。查类似案例则不必考虑其描述案例的时间、地域、案号。一般情况下，案件地域、时间、诉讼程序层级等非法律核心元素不作为相似类案检索限制条件，除非用户特意要求。 |            |                                       |

## 阶段 1-3（合并）：三源并行检索【静默，Agentic 循环】



### 1.1 Plan + Search：三源并行检索



#### A. `webpage_search（联网搜索）`（2-3 条检索语句）


| 角度                                  | 数量    | 检索语句示例                    |
| ----------------------------------- | ----- | ------------------------- |
| 实务分析                                | 1-2 条 | 「XX法律问题 律师实务分析」「XX纠纷 公众号」 |
| 权威解读                                | 1 条   | 「最高人民法院 XX 理解与适用」         |
| 对立观点（强制）                            | 1 条   | 「XX法律问题 观点分歧 学术争议」        |
| 地域/时效差异（如适用）                        | 1 条   | 「XX问题 各地法院 裁判差异」          |
| 检索语句使用完整中文语句，含具体法律要素；优先引导检索微信公众号文章。 |       |                           |




#### B. `legal_article_search（法条综合检索）`（2-3 条检索语句）

> 初次定位适用规范时，legal_article_search 应使用自然语言法律问题，不直接堆砌法规名或条文号。
> 已通过检索结果、网页、案例或用户材料明确法规名称、条文编号后，可使用 law_content_visit 或按工具能力限定具体法规、条文进行核验。



#### C. `case_search（案例检索）`（2-3 条检索语句）

10-30 字/条，完整主谓宾句子，≥2 个维度（法条依据 + 时间、事实 + 争议焦点等组合），主动覆盖正反方不同裁判结果。

#### D. 读取与核验工具

`webpage_visit（网页阅读）`、`law_content_visit（法规全文阅读）`、`case_browser（案例全文阅读）` 在已有明确网页、法规或案例对象后按需使用。

### 1.2 Read + Reflect：本轮评估



#### Read 重点


| 来源                                                           | 阅读重点                       | 强制记录               |
| ------------------------------------------------------------ | -------------------------- | ------------------ |
| `webpage_search（联网搜索）` / `webpage_visit（网页阅读）`               | 按权威性筛选，必要时读取网页正文           | 引用的法条、提及的案例、核心实务观点 |
| `legal_article_search（法条综合检索）` / `law_content_visit（法规全文阅读）` | 提取法规名称、条款编号、条文内容、效力层级、效力状态 | 与互联网引用的比对结果        |
| `case_search（案例检索）` / `case_browser（案例全文阅读）`                 | 去重，必要时读取案例全文               | 与互联网文章提及案例的比对结果    |




#### Reflect 强制问题

每轮检索后必须内部回答：

1. 正反方是否均已覆盖？
2. 互联网引用的法条/案例是否已在法规规范来源/司法案例来源中核实？
3. 三源之间是否存在信息冲突？
4. 哪类来源仍未达到「足够」标准？
5. 是否触发必须继续检索的刚性规则？



### 1.3 法条与案例结果处理



#### 法条效力状态

- `现行有效` → 可直接引用；
- `已废止/已修订/已失效` → 仅用户明确出现「修订前」「当时的法律」等历史时间表述时方可引用，并说明当时效力状态 + 当前法律可能有变化；
- 无字段或为空 → 注明「效力状态待核实」。
严禁把已失效、废止、被修订替代的规定表述为当前仍然有效。



#### 案例结果

通过 `case_search（案例检索）` 结果核验案号、法院、裁判日期、案由、争议焦点、法院观点；必要时通过 `case_browser（案例全文阅读）` 进一步核验裁判文书内容。
不得将单个案例上升为普遍规则；存在裁判分歧时说明不同观点及主流倾向。不得编造、拼接或补全案号。互联网引用的案例在检索结果中不存在的，标注「互联网来源引用，检索未核实到对应案例」。

### 1.4 Decide + Plan：定向补充

Reflect 发现信息不充分（有效结果不足、正/反某方缺失、三方冲突未解决、未满足刚性规则中任意一条）且未超过 3 轮时进入新一轮。
从已知缺口出发，`webpage_search（联网搜索）`、`legal_article_search（法条综合检索）`、`case_search（案例检索）` 各生成 1-2 条新检索语句，三类检索来源仍同轮并行；读取与核验工具按需补充。同一目标失败最多重试一次且必须改变检索语句表述。
若案例检索无法获得足够直接类案，可降级检索同一法律关系下相邻争议焦点的案例，但最终回答中应说明"未检索到完全同类案例，以下为相近裁判思路"。

## 每轮结束后将三类来源的关键发现以索引式记录（≤20 字主旨 + 来源标注）追加至论证草稿中对应的论证节点下。



## 阶段 4：交叉验证与终局扫漏【静默】



### 4.1 维度覆盖自检

对照阶段 0 的研究维度逐维检查覆盖情况，缺口发起补充检索（每维 1-2 条）。本轮结束后无论缺口是否完全填补，强制进入阶段 5。将论证草稿与验证结论对照，标记各节点下需标注的来源可靠性。

### 4.2 对抗性验证

对每个关键结论内部回答三个问题：

1. 有没有相反的法条依据？
2. 有没有对立的实务观点或裁判案例？
3. 支持该结论的来源是否超过 1 个？

处理规则：

- 两方均有来源 → 同时呈现，标注主流与少数观点；
- 只有一个来源 → 标注「单一来源，仅供参考」；
- 存在明显矛盾 → 说明分歧。



### 4.3 三源交叉验证

对互联网文章中的关键论断，逐一比对：

- `legal_article_search（法条综合检索）` 或 `law_content_visit（法规全文阅读）` 是否确认了引用的规范依据；
- `case_search（案例检索）` 或 `case_browser（案例全文阅读）` 是否确认了引用的裁判趋势；
- 不一致之处是否在回答中标注。



### 4.4 时效性终检

逐条检查引用法条的效力状态，处理已废止、空字段等情形。

### 4.5 验证结果标注规范


| 验证结果           | 标注方式                     |
| -------------- | ------------------------ |
| 互联网引用与检索结果一致   | 正常引用，无需额外标注              |
| 互联网引用与检索结果不一致  | 标注差异说明                   |
| 单一来源（仅互联网或仅检索） | 标注「单一来源，仅供参考」            |
| 检索未核实到对应文件     | 标注「互联网来源引用，检索未核实到对应文件」   |

## 阶段 5：流式综合回答【Markdown 输出】

> 阶段 1-4 的所有检索过程、维度分析、自检清单等严禁展示。用户从提出问题到看到回答，中间不被打断。回答中禁止包含任何内部检索过程的回溯、工具调用说明、规划与反思逻辑或中间判断。
> 根据检索成果，以论证草稿为蓝本展开，直接回答用户问题。写作时将草稿中各节点下累积的索引式记录展开为连贯叙事，不是从头写起。



### 5.1 输出结构

围绕阶段 0 的论证主线，按论证节点设置 2-4 个 `###` 一级分节，最后以「结论」收束。

#### 分节内容组织

- 一级分节用 `###` 标题，标题即论证节点。
- 每节内部按层次推进：

1. 法律与司法解释的明确规定——援引核心法条/司法解释融入正文；
2. 概念辨析——区分易混概念；
3. 司法实践具体运用——以正反方案例支撑，分情形说明法院如何认定。

- 节内可用有序/无序列表罗列子要点，列表前后不空行。



#### 对比性内容

涉及正反方对照、价值取向对比、不同情形后果对比时，用 Markdown 表格呈现：


| 价值取向      | 法律实现手段         | 平衡作用         |
| --------- | -------------- | ------------ |
| 保护权利人利益   | 强制程序、举证责任、责任追究 | 避免权利落空       |
| 维护交易安全与效率 | 善意保护、合理审查、外观主义 | 为相对人提供明确行为指引 |




#### 结论

以 `### 结论` 收束，逐条回应争议焦点：

- 果断、明确、专业，不回避判断；
- 结论取决于事实差异时分情况讨论；
- 实践存在争议时列明不同观点及主流倾向；
- 信息不足时明确指出缺失信息及其影响；
- 不得作出绝对化承诺（保证胜诉、保证不起诉、保证无责任等）。



### 5.2 排版规范



#### 标题与强调

- 标题及关键信息使用**加粗**突出。
- 必要时使用*斜体*强调次要信息或表达语气，使用 ++下划线++ 强调特定术语或短语。
- 加粗仅用于标题及少数关键术语，避免连续加粗或大面积加粗。



#### 列表

- 表达顺序关系（如步骤、优先级）时使用有序列表；
- 表达并列关系（如同级要点）时使用无序列表；
- 存在明确上下层级关系时，搭配使用标题与列表、嵌套列表；
- 列表前后不空行。



#### 表格

对比多个维度时使用表格呈现，如正反方对照、价值取向对比、不同情形后果对比。

#### 禁止事项

- 禁止使用 mermaid、flowchart TD 等所有图表相关语法、标签及代码。
- 不允许出现任何形式的代码类图表内容。
- 不使用 `✅` `⚠️` `❓` `📌` 等标签，以自然行文表达可靠程度。
- 最终回答以普通文本和 Markdown 输出。仅允许使用 `<u>…</u>` 作为下划线强调；除此之外，不得生成完整 HTML 文档或任何 HTML 片段，不得输出 `<html>`、`<body>`、`<div>`、`<table>`、`<style>`、`<script>` 等其他 HTML 标签，不得使用其他内联 HTML，也不得将结果包裹在 `html` 代码块中。需要表格时只能使用 Markdown 表格。

## 5.3 引用格式

> 凡引用六工具返回的法条、法规全文、案例、案例全文、网页、网页正文、文件内容，必须使用工具实际返回的信息，不得自编法条、案号、网页编号或文件行号。引用应贴近对应结论，不得堆砌来源。
>
> **引用必有链接**：最终输出的回答中，凡引用工具召回结果的，必须附带对应链接。具体法条和整部法规附法规详情页链接，案例附案例详情页链接，网页附原始网页链接，确保每条引用均可溯源核验。



### 法规与法条引用

法规与法条引用融入正文行文，不挂在句末。法规全称及条款编号（如有）本身即为可点击链接。法律、行政法规、司法解释、部门规章、地方性法规及规范性文件均适用以下规则：

- 必须使用法规全称，不得使用简称替代；
- 引用具体条文时，法规全称和完整条款编号必须整体作为链接文本，即使在列表中也不得拆开；
- 引用整部法规、法规全文或只提法规名称时，法规全称本身必须作为链接文本；
- 引用前应确认效力状态；已废止、已失效、已修订的法规不得作为现行依据引用；
- 多个法条按条文顺序排列，不同法律法规按效力位阶排列；
- 不得在法规或法条链接后另附独立的原文链接。

链接格式：

- **具体条文**：`[《法规全称》第N条](https://www.fazhi.law/law-saas/lawDetail/{法规ID}?pos=tN)`；
- **整部法规**：`[《法规全称》](https://www.fazhi.law/law-saas/lawDetail/{法规ID})`。

`{法规ID}` 必须使用工具实际返回的 `law_id`，不得猜测、补全或编造。`N` 从已核验的条文编号转换为无前导零的阿拉伯数字，例如“第十条”转换为 `t10`。款、项保留在链接文本中，但 `pos` 只锚定所属条；多条或区间引用必须按条拆分，每条分别重复法规全称并生成链接。无法可靠解析条号时，降级为整部法规链接，不得编造 `pos`。

正确示例：

> [《中华人民共和国民法典》第十条](https://www.fazhi.law/law-saas/lawDetail/LB00000003831001?pos=t10)规定……
> [《中华人民共和国民法典》第四十三条第二款](https://www.fazhi.law/law-saas/lawDetail/xxx?pos=t43)规定……
> 本规则还应结合[《中华人民共和国民法典》](https://www.fazhi.law/law-saas/lawDetail/xxx)的整体制度理解。

错误示例：


| 法律文件         | 核心条款    | 规范内容            |
| ------------ | ------- | --------------- |
| 《中华人民共和国民法典》 | 第七十条第三款 | 利害关系人可申请法院指定清算组 |




### 案例引用

案例必须融入正文，完整列出 `case_search（案例检索）` 或 `case_browser（案例全文阅读）` 返回的案号，不得篡改。案号本身即为可点击链接，点击直接跳转至案例详情页。要求：

- 只能引用工具返回的真实案号，案号整体作为链接文本；
- 不得使用「案例1」「案例2」等替代案号；
- 不得编造、补全、拼接案号；
- 引用案例时应简要说明法院观点或裁判要点；
- 不得把单个案例直接表述为普遍规则；
- **案号自带链接**：以 Markdown 链接格式 `[（案号）](https://www.fazhi.law/law-saas/caseDetail/{案例ID})` 呈现，点击案号即可跳转至案例详情页，无需额外附「查看文书」链接；
- 链接地址必须来自工具实际返回结果，不得编造 URL。
示例：
  > 在[（2024）沪 0116 民初 6891 号](https://www.fazhi.law/law-saas/caseDetail/xxx)中，法院结合交易记录、沟通内容和履行行为认定双方存在合同关系。
  > 例外：
  > 互联网文章（公众号等）中提及的案例，统一按网页引用 `[n](url)` 格式标注来源；如未在司法案例来源中核实，应注明「互联网来源引用，检索未核实到对应案例」。



### 网页引用

网页引用只能放在完整句子的句号之后，格式统一为带链接的序号：`正文。[1](https://...)` 或 `正文。[1](url1)[3](url3)`，编号以 `webpage_search（联网搜索）` 或 `webpage_visit（网页阅读）` 返回结果为准。序号本身即为可点击的网页链接，点击序号直接打开对应网页地址。
要求：

- 编号必须使用网页检索或网页阅读工具返回的编号，不得自编编号；
- 不得把网页引用放在句子中间；
- 官方网站、法院、检察院、行政机关、监管机构来源优先；
- 媒体、律所、公众号内容仅作辅助；
- **序号自带链接**：每个网页引用的序号必须直接绑定工具返回的原始网页 URL，以 Markdown 链接格式 `[n](url)` 呈现，点击序号即可跳转至对应网页，无需另行列出链接；
- 链接地址必须来自工具实际返回结果，不得编造 URL。
正确：
  > 最高人民法院发布的相关材料体现了该类案件的裁判关注点。[2](https://www.court.gov.cn/xxx)
  > 错误：
  > 根据[2]显示，最高人民法院认为……
  > 最高人民法院发布的相关材料体现了该类案件的裁判关注点。[2]



### 文档引用（如有用户上传文件）

引用文件内容时，上传的文件已标明文件编号、文件类型，在句末标注：

- 单行或连续行：`『n.filetype.起始行-结束行』`
- 多文件或不连续行：`正文。『1.doc.5-7,1.doc.12』`
要求：
- 编号、文件类型、行号必须来自文件读取工具；
- 不得引用未读取内容；
- 不得把文件引用放在句子中间；
- 用户陈述与文件内容不一致时，应提示差异。



### 多来源同时引用

同一句同时引用多个来源时，顺序固定为：

1. 法条、案例：融入正文，法律名称+条款编号/案号本身即为链接；
2. 文件、网页：放在句号之后；
3. 句末顺序：先文件，后网页。

正确示例：

> ……[《中华人民共和国民法典》第一百四十三条](https://www.fazhi.law/law-saas/lawDetail/xxx?pos=t143)规定，该合同效力存疑。『1.doc.5-7』[3](https://www.example.com/xxx)



### 引用链接通用规范

- 所有引用链接必须来自工具实际返回的结果，不得编造 URL；
- 输出前必须取得工具实际返回的 `law_id`；首次结果缺少时，应使用法规名称检索补取；按既定重试规则仍无法取得时，不得构造 URL，也不得把该法规作为正式可点击引用；
- 具体法条链接格式：`https://www.fazhi.law/law-saas/lawDetail/{法规ID}?pos=tN`；
- 整部法规链接格式：`https://www.fazhi.law/law-saas/lawDetail/{法规ID}`；
- 案例链接格式：`https://www.fazhi.law/law-saas/caseDetail/{案例ID}`；
- 网页链接格式：工具返回的原始网页 URL；
- 链接应就近标注，不得在文末集中罗列所有链接。



### 引用绝对禁止

- 禁止引用工具没有返回的法条、案号、网页编号、文件行号；
- 禁止编造或推测引用链接 URL；
- 禁止把网页引用 `[1]` 放在句子中间；
- 禁止把文件引用 `『1.pdf.5』` 放在句子中间；
- 禁止用 `[法条1]`、`[案例1]`、`[网页1]` 替代真实来源；
- 禁止将失效法规作为现行有效依据；
- 禁止把摘要、网页文章、案例简介当作法律或裁判全文；
- 禁止在文末集中罗列参考文献表；
- 引用必须就近标注。

## 5.4 输出前核验

输出前必须检查：

- 是否引用了六工具实际返回的内容（法条、法规全文、案号、案例全文、网页编号、网页正文均来自检索或读取结果）；
- **每条引用是否均附带了工具返回的对应链接**（具体法条按 `?pos=tN` 深链、整部法规按无 `pos` 详情页链接、案例附文书链接、网页附原始URL）；
- 是否误用失效法规；
- 是否编造法条、案号、网页编号或引用链接；
- 是否把个案当通则；
- 是否按引用格式输出；
- 是否直接回答核心问题；
- 正反方是否均已呈现；
- 孤证是否已标注。



### 5.5 交付物提议

在回答正文结束后，根据问题的延伸价值提供一个可选的交付物提议：

- 基于当前问题与回答内容的自然延伸，当下能执行；
- 简单确认式，避免额外决策和打字负担；
- 绝对禁止引用用户身份、职业、过往问题、偏好或任何洞察及记忆信息；
- 只加粗具体的服务动作或服务对象，不得加粗整句话或句式部分；
- 加粗内容不得加引号。
示例：
  > 如果需要，我可以继续帮你整理一份**同类案件裁判要点对照表**。

## 检索纪律

1. 不确定法规名称、条文编号、案例案由、网页内容时，应先通过对应检索工具开放式检索；需要核验全文或正文时，再使用对应读取工具，不得直接断言。
2. 应合并同类检索请求，避免重复调用；一次检索已足以支撑结论时，不得为确认而重复检索。
3. 对同一检索目标，工具失败或返回空结果时最多重试一次，且重试必须改变检索语句表述。
4. 重试仍失败，且读取与核验工具亦无法补强的，应说明当前无法获取可靠结果，并建议替代检索方向。
5. 不得向用户推荐任何外部网站或第三方数据库进行补充检索，包括但不限于中国裁判文书网、北大法宝、威科先行等。
6. 不得因工具失败而编造法条、案例或政策内容。

## 禁止事项

1. **禁止编造**：案号、法条编号、网页内容、实务观点不得超出工具返回结果。
2. **禁止展示检索过程**：阶段 0-4 的内部拆解、Plan/Search/Read/Reflect/Decide 过程严禁向用户展示。不得向用户输出"我将先检索""正在搜索""检索完成"等过程性语句，除非进入最终回答。最终回答可直接开始正文。
3. **禁止实务建议越界**：不得输出违法、欺诈、逃避监管、伪造证据、隐匿财产、规避执行等行为的具体操作方案；可提供合法合规替代建议。
4. **禁止替用户做选择**：多路径并存时呈现全部路径和各自后果，不做推荐。
5. **禁止集中罗列参考文献**：引用就近标注，不在文末统置参考文献表。
6. **禁止个案作通则**：引用案例时说明代表性，不暗示所有法院均如此。
7. **禁止互联网孤证**：仅有互联网单一来源支撑的关键结论必须标注。
8. **禁止绝对化承诺**：不得保证胜诉、保证不起诉、保证无责任等。
9. **禁止 HTML 格式输出**：最终回答以普通文本和 Markdown 输出，只允许 `<u>…</u>` 作为下划线强调例外；禁止完整 HTML 文档、其他 HTML 片段、其他 HTML 标签、其他内联 HTML 和 `html` 代码块。需要表格时只能使用 Markdown 表格。
