# 六工具研究与引证规则

先完整读取同级 MCP 依赖 [fazhi-mcp/SKILL.md](../../fazhi-mcp/SKILL.md)。本文件仅规定法律意见书场景下的研究与写入方式，不重复或改变 MCP 工具 schema。

## 三源职责

- 法规规范来源确定规则、层级、效力、适用主体、条件和法律后果。
- 司法案例来源说明裁判方法、举证要求、事实差异和相反观点；案例不替代规则。
- 互联网公开来源补充官方背景、实务动态和专业分析；其中转述的法条和案例必须回源核验。

## 检索循环

1. 将每个争点拆为主体、关系、行为、目的、时间、结果和待证明事实。
2. 复杂事项同轮并行调用 `legal_article_search`、`case_search`、`webpage_search`；每工具最多三条语句。
3. 使用 `law_content_visit`、`case_browser`、`webpage_visit` 阅读高相关性对象全文。
4. 每轮后分别评价匹配度、数量、多样性、完整性与缺口，检查正反观点和来源冲突。
5. 同一目标失败或空结果最多改变表达重试一次；仍失败则记录无法核验并降低结论强度。

## 足够标准

- 法规覆盖核心条款、配套规则和必要司法解释，均已核验效力和完整内容。
- 需要裁判支撑时，原则上取得三个有效案例，覆盖至少两种事实情形或不同观点；无法达到时不得宣称裁判趋势。
- 需要实务动态时，原则上取得两个不同来源的有效材料，至少一个为官方或一手来源。
- 每个关键结论原则上有两个独立来源；单一来源不形成无保留肯定结论。

## 法规写入 DOCX

- 仅选择直接设定争点所涉权利、义务、禁止、条件、程序或法律后果，并实际用于后续分析或结论的决定性条、款或项；每个争点通常保留 1—2 项，不为形式完整罗列原则性或间接相关条文。通用专项模板的“适用法律依据”总计最多引用六个具体法律条款，同一规范性文件的不同条款分别计数；候选条款按与委托问题的直接相关性、对结论的决定性及是否在后续分析中实际使用排序。
- 使用法规全称和中文数字条款号，例如 `《中华人民共和国民法典》第五百七十七条第一款`；引用前使用法规全文核验工具确认原文、层级、效力状态、适用主体和法律基准日。
- 通用专项模板的引号内逐字引用直接相关的条、款或项原文；不要求复制同一条中与争点无关的其他款项，不得将摘要、搜索结果或自行改写文本标注为法条原文。每项引文结束后在同一段落紧接 1—3 句规则适用说明，仅说明构成要件、对应项目事实及其影响的争点，不提前重复完整分析或结论；不得另起“简析”段落或保留“简析：”“简析、”标签。
- 咨询回复式模板不适用六条总量上限，使用 `根据《法规全称》第×条，[准确概括的规则]。[结合本事项事实说明法律影响]。` 的连续正文，将经全文核验的规则摘要直接融入分析；摘要不加引号、不冒充法条原文，不保留独立“简析：”标签，也不另设法规汇编式章节。只有争议直接取决于条文措辞时，才引用最小必要的完整原句。
- 同一核心条款服务多个争点时只完整引用一次，其他位置交叉指向，不重复堆砌。
- `law_id`、详情 URL、检索日期和效力字段保存在内部核验记录，不进入最终 DOCX；法规名称不得创建超链接。
- 规范性文件须核查制定权限、地域、主体和效力；征求意见稿不得作为生效规则。
- 国家标准须区分强制性和推荐性，推荐性标准不得表述为当然免责或鉴定结论。

## 案例写入 DOCX

- 仅使用经 `case_browser` 或同等权威全文核验的完整案号、法院、裁判日期和裁判理由。
- 说明案例与本事项的相同点、差异和代表性边界，不将个案当作普遍规则。
- 用户未要求且论证不需要时，案例只用于后台验证，不在正文堆砌。
- 不写案例 ID、后台 URL或不可核验的裁判摘要；不得补全残缺案号。

## 网页材料写入 DOCX

- 网页通常仅用于后台核验；最终正文不显示 URL、网页编号或 Markdown 链接。
- 官方公开事实需要写入时，注明发布主体、文件或公告名称与日期，不创建外部超链接。
- 搜索结果摘要不得当作网页全文，二手文章不得替代法规或裁判全文。

## 对话交付总结

完成并质控 DOCX 后，在对话中提供 `### 交付总结`。总结为 150—300 字的一段连贯文字，概括委托事项、核心判断、结论强度、决定性条件和首要行动；选取 2—5 项对结论具有决定性作用的法规条款，不机械罗列全部依据。

- 只链接本次研究中已全文核验、效力状态与法律基准日相符的法律法规；历史事项适用旧法时明确说明当时效力状态。
- 法规全称和完整条款编号整体作为链接文本并直接融入对应判断，具体条文使用带 `?pos=tN` 的法规详情页深链，不另附“查看原文”。
- 引用具体条文时，法规全称和完整条款编号整体作为链接文本，格式为 `[《法规全称》第N条](https://www.fazhi.law/law-saas/lawDetail/{law_id}?pos=tN)`；款、项保留在链接文本中，但 `pos` 只锚定所属条，例如 `[《法规全称》第四十三条第二款](https://www.fazhi.law/law-saas/lawDetail/{law_id}?pos=t43)`。
- 仅引用整部法规或无法可靠解析条号时，使用 `[《法规全称》](https://www.fazhi.law/law-saas/lawDetail/{law_id})`，不得编造 `pos`。
- 多条或条文区间必须按条拆分，每条分别重复法规全称并生成链接；不得用一个锚点代表多个条文。
- `{law_id}` 必须来自本次 MCP 工具实际返回结果，不得猜测、补全、拼接或使用其他对象的 ID。首次结果缺少 `law_id` 时，使用法规名称检索补取；按既定重试规则仍无法取得时，使用无链接的 `《法律法规全称》第X条`，并在总结中简洁注明“当前 MCP 工具结果未提供可跳转地址”。
- 引用前确认法规效力状态；已废止、已失效或已修订的法规不得作为现行依据链接，历史事项适用旧法时明确说明其在法律基准日的效力状态。
- 总结只为法规条款提供链接，不链接案例、网页、用户文件或其他来源，也不在文末集中列参考文献。
- 总结不得出现 DOCX 未支持的新事实、新结论或更强结论；主体、事实、法律基准日、结论等级、决定性条件和首要待办必须与 DOCX 一致。

示例：

> 已生成法律意见书。本意见主要审查……。依据[《中华人民共和国公司法》第六十九条](https://www.fazhi.law/law-saas/lawDetail/工具真实返回的law_id?pos=t69)，拟定治理结构……。因此，现阶段形成条件式结论，实施前需补齐……。

示例中的法规 ID 仅表示格式，实际输出必须替换为本次工具真实返回值，不得原样输出示例文字。

## 内部核验记录

每条关键依据内部记录：来源类型、标题或法规名、条款/案号、效力或裁判日期、`law_id` 或 URL、检索日期、支持的争点、是否全文核验。该记录不得泄露到最终 DOCX；其中真实法规 `law_id` 仅可按上述规则用于对话交付总结，除非用户明确另行要求“法律依据核验表”。
