## §1 Phase 1：信息接收与预处理

### 输入
用户原始 content + 可选参数

### 处理步骤

1. **内容读取**：完整读取用户输入的 content
2. **参数解析**：解析可选参数（goal / preferred_chart / audience / style / detail_level / output_format / deliver_style / render_adapter / include_source / visual_budget）；缺省时设置 `deliver_style=conversation_inline`、`render_adapter=auto`、`include_source=false`、`visual_budget=3`
3. **格式识别**：判断输入格式
   - 自然语言段落 → 进入文本提取模式
   - 结构化列表（- 开头） → 进入列表提取模式
   - JSON结构 → 进入结构化提取模式
   - 上游技能输出 → 直接映射
4. **语言检测**：确认内容语言（中文/英文/混合）
5. **长度评估**：评估内容长度，超长内容（>5000字）标记可能遗漏

### 输出
- 解析后的参数集合
- 输入格式标记
- 内容长度评估

### 信息不足处理
- 标记缺失项但不停止生成
- 在 Phase 7 的"建议补充信息"中列出

## §2 Phase 2：信息提取与结构化

### 输入
Phase 1 解析结果

### 提取维度

#### 2.1 时间要素
- 具体日期（YYYY-MM-DD）
- 模糊时间（"2023年""去年""三月份"）
- 时间区间（"2023年1月至6月"）
- 时序关系（"之后""之前""同时""先...后..."）
- 时间精度标注（精确/近似/模糊/期间/未知）

#### 2.2 主体要素
- 人物（姓名、称谓）
- 公司/机构（全称、简称）
- 角色（原告、被告、第三人、法定代表人等）
- 群体/部门（项目部、法务部等）

#### 2.3 关系要素
- 合同关系（买卖、租赁、承揽等）
- 股权关系（控股、参股、全资子公司）
- 代理关系（委托代理、法定代理）
- 资金流向（付款、收款、垫付）
- 上下级关系（管理、隶属）
- 关系强度（强/中/弱）

#### 2.4 步骤要素
- 流程步骤（动作+执行者）
- 判断条件（if/then）
- 分支路径（不同情形的处理）
- 循环/回退（退回补充、重新审核）
- 开始/结束节点

#### 2.5 证据要素
- 证据名称
- 证据类型（书证/物证/电子数据/证人证言）
- 证据强度（🟢强/🟡中/🔴弱）
- 证据坐标（{材料ID}/{页码}/{段落号}）
- 可信度（📄原件/📑复印件/💾电子/⚠️待确认）

#### 2.6 争议要素
- 争议焦点
- 矛盾事实
- 风险节点
- 决策分支

#### 2.7 攻防要素
- 我方主张
- 对方可能抗辩
- 回应策略
- 策略风险等级

#### 2.8 数据要素
- 金额/数值
- 计算依据
- 比例/占比
- 资金方向（收入/支出）

### 输出
结构化信息对象，包含上述8个维度的提取结果

## §3 Phase 3：图表类型判断

### 输入
Phase 2 结构化信息 + 用户参数

### 决策逻辑

#### 3.1 用户指定优先
如果 `preferred_chart` 不为 auto → 直接使用指定类型

#### 3.2 自动判断决策树

```
输入 preferred_chart=auto 且无明确指定
│
├─ time_elements 显著（≥3个时间点/期间）
│  └─ 需要证据锚定 → timeline
│  └─ 纯时间梳理 → timeline
│
├─ relation_elements 显著（≥3个主体 + ≥2种关系）
│  └─ 关系复杂（≥4种关系类型）→ relation
│  └─ 关系简单 → relation
│
├─ evidence_elements 显著（用户要求证据可视化/证据≥3个）
│  └─ 需要展示证明链 → evidence
│
├─ step_elements 显著（≥3个步骤 + 判断分支）
│  └─ 有分支/循环 → flow
│
├─ dispute_elements 显著（≥2个争议焦点）
│  └─ 需要展示攻防 → dispute
│
├─ attack_defense_elements 显著（≥2项主张 + 对方抗辩信息）
│  └─ 需要横向对比 → matrix
│
├─ data_elements 显著（≥2项金额/数值 + 需要拆解）
│  └─ 金额/数据结构化 → data_table
│
└─ 混合信息
   └─ 按 goal 选择最匹配类型
   └─ 建议：可补充第二张图
```

#### 3.3 特征权重

| 特征 | timeline | relation | evidence | flow | dispute | matrix | data_table |
|------|----------|----------|----------|------|---------|--------|------------|
| 时间点数量 | +3 | +0 | +1 | +0 | +1 | +0 | +0 |
| 主体数量 | +0 | +3 | +1 | +1 | +1 | +0 | +0 |
| 关系类型数 | +0 | +3 | +1 | +0 | +1 | +0 | +0 |
| 步骤数量 | +0 | +0 | +0 | +3 | +0 | +0 | +0 |
| 判断分支数 | +0 | +0 | +0 | +3 | +1 | +0 | +0 |
| 证据数量 | +1 | +0 | +3 | +0 | +2 | +1 | +1 |
| 争议焦点数 | +0 | +0 | +1 | +0 | +3 | +2 | +0 |
| 主张/诉求数量 | +0 | +0 | +0 | +0 | +1 | +3 | +0 |
| 金额/数值数据 | +0 | +0 | +0 | +0 | +0 | +0 | +3 |
| goal相关性 | +2 | +2 | +2 | +2 | +2 | +2 | +2 |

### 输出
选定的图表类型 + 选择理由

## §4 Phase 4：图表内容编排

### 输入
Phase 2 结构化信息 + Phase 3 图表类型 + 风格参数

### 处理步骤

1. **确定标题**：基于 goal 和材料内容，生成 ≤18 字的图表标题
2. **节点筛选**：
   - `detail_level=简略`：仅保留核心节点（≤8个）
   - `detail_level=标准`：保留主要节点（≤12个）
   - `detail_level=详细`：保留所有节点
3. **节点分层**：
   - 时间轴：按阶段分组（section）
   - 关系图：按群体分组（subgraph）
   - 流程图：按功能区域分组
   - 证据图：按事实主张分组
   - 争议图：按争点分组
   - 攻防矩阵：按风险等级排序
   - 数据表：按金额大小或逻辑顺序排列
4. **连线设计**：确定节点间的连接关系和标签
5. **高亮规划**：标记核心争议/异常节点/关键证据
6. **分图判断**：节点过多时规划拆分策略

### 输出
编排方案（节点列表、连线列表、高亮标记、分组方案）

## §5 Phase 5：图表代码生成

### 输入
Phase 4 编排方案 + 风格配色

### 生成规则

1. **语法正确**：确保 Mermaid 代码可正确渲染，无语法错误
2. **命名规范**：节点ID使用英文小写+数字（如 `company_a`），标签使用中文
3. **标签精简**：节点标签 ≤ 20 字，超过时使用简短概括
4. **样式应用**：按风格方案应用 classDef
5. **代码整洁**：适当缩进，保持代码可读性

### 各类型特殊规则

| 类型 | 关键规则 |
|------|----------|
| timeline | 使用 section 分阶段；时间格式统一 |
| relation | 使用 subgraph 分组；实线=强关系，虚线=弱关系 |
| evidence | 事实在上证据在下；强度用颜色区分 |
| flow | 菱形=判断节点，圆角矩形=普通步骤 |
| dispute | 争议用红色，支撑用绿色，抗辩用黄色 |
| matrix | Markdown 表格；5列标准结构；风险等级红黄绿标注 |
| data_table | Markdown 表格 + 文本柱状条；含计算校验行 |

### 输出
可直接渲染的 Mermaid 代码或 Markdown 表格

## §6 Phase 6：断点矛盾分析

**适用条件**：timeline、evidence、matrix、data_table 类型执行此阶段。relation、flow、dispute 类型跳过此阶段。

### 输入
Phase 2 结构化信息 + Phase 5 生成的图表

### 分析维度

#### 6.1 timeline / evidence 类型

| 断点类型 | 检测规则 | 输出格式 |
|----------|----------|----------|
| 时间断点 | 两个相邻事件间跨度异常（>6个月无任何事件） | "⚠️ 时间断点：{事件A}至{事件B}期间（{跨度}）缺少记录" |
| 证据断点 | 有事实主张但未关联任何证据 | "⚠️ 证据断点：「{事实主张}」无证据支撑" |
| 事实断点 | 事实链条中存在明显缺失环节 | "⚠️ 事实断点：{环节描述}缺少中间过程记录" |

| 矛盾类型 | 检测规则 | 输出格式 |
|----------|----------|----------|
| 时间矛盾 | 不同材料中同一事件的时间标注不一致 | "🔴 时间矛盾：{事件}在不同材料中标注为{时间1}和{时间2}" |
| 内容矛盾 | 不同材料中对同一事实的描述不一致 | "🔴 内容矛盾：关于{事实}，{材料A}记载{描述A}，{材料B}记载{描述B}" |
| 证据矛盾 | 不同证据之间指向不同结论 | "🔴 证据矛盾：{证据A}指向{结论A}，{证据B}指向{结论B}" |

#### 6.2 matrix 类型

| 断点类型 | 检测规则 | 输出格式 |
|----------|----------|----------|
| 策略断点 | 某主张缺少回应策略或支撑证据 | "⚠️ 策略断点：{主张}缺少回应策略" |
| 风险盲区 | 未识别对方可能的抗辩角度 | "⚠️ 风险盲区：未考虑对方可能提出的{抗辩角度}" |
| 证据缺口 | 矩阵中标注为"待补充"的单元格 | "⚠️ 证据缺口：{主张}的支撑证据待补充" |

#### 6.3 data_table 类型

| 断点类型 | 检测规则 | 输出格式 |
|----------|----------|----------|
| 数据断点 | 某项金额缺少计算依据或证据支撑 | "⚠️ 数据断点：{项目}缺少计算依据" |
| 计算矛盾 | 各项之和与总计不一致 | "🔴 计算矛盾：各项之和{合计}与总计{总计}不一致" |
| 比例异常 | 某项占比异常偏高/偏低需核实 | "⚠️ 比例异常：{项目}占比{占比}%偏高，建议核实" |

### 输出
断点列表 + 矛盾列表（可能为空）

## §7 Phase 7：输出组装与优化建议

### 输入
Phase 3-6 的全部产出

### 处理步骤

1. **标准结构组装**：按输出格式（mermaid/markdown/json）组装
2. **优化建议生成**：
   - 设计层面：配色、布局、层次调整建议
   - 内容层面：可补充的信息、可拆分的维度
   - 表达层面：措辞优化、标签精简
3. **补充信息建议**：列出用户可补充以优化图表的信息
4. **视觉预算裁剪**：按结论重要性从候选图表与大型表格中选择 1-3 个视觉单元；超出 `visual_budget` 的内容改为精简文字，不生成未交付的资源文件。
5. **图表渲染与平台适配**：读取 `references/inline-render-adapter.md`。对 timeline / relation / evidence / flow / dispute 校验 Mermaid 后渲染为 SVG；已注册 PureShowWidget 时逐图调用 `mode=inline`。matrix / data_table 保留为 Markdown 表格。
6. **渲染成功门控**：记录 `planned_visual_count` 与 `successful_inline_count`。只有工具返回成功且回复流出现对应组件/图片块才增加成功数；两者不一致时执行适配器降级，禁止输出孤立图名冒充图片。
7. **按逻辑顺序组装**：按“总述 → 图1前置说明 → 内联图1 → 图1解读 → 过渡 → 内联图2 → 图2解读 → 风险与建议”的顺序输出。`include_source=false` 时到此结束，不追加源码。
8. **交付形态检查**：默认 `conversation_inline`，确认图表已在对话回复中直接显示，而非仅提供路径或“文件已保存”。未经用户明确要求不得生成 HTML；仅当 `deliver_style=html_report` 时切换为 HTML 文件。
9. **清洁与可访问性检查**：删除孤立的 `100%`、资源目录、工作区路径、点击放大提示、拆散的 Mermaid 节点文本和未显示图片的标题；所有可见图片包含有意义的替代文本。
10. **一致性检查**：确认文字、图片和源码中的节点、关系、日期、金额与风险标注一致。

### 输出
完整的标准化混合输出：按逻辑顺序交错排列的文字说明与 1-3 张必要图片（适用时）+ 可编辑源码或 Markdown 表格；默认不生成 HTML 报告

## §8 断点矛盾分析规则

### 8.1 严重程度分级

| 等级 | 标记 | 说明 |
|------|------|------|
| 高 | 🔴 | 直接影响案件走向的矛盾 |
| 中 | ⚠️ | 可能影响事实认定的断点 |
| 低 | ℹ️ | 建议关注但不影响核心判断 |

### 8.2 处理原则

- 高严重程度矛盾：必须在图表中标注并在分析中详细说明
- 中严重程度断点：在分析中列出，建议用户关注
- 低严重程度：在建议补充信息中提及

### 8.3 时间断点判断阈值

- 相邻事件跨度 > 12 个月：高严重程度
- 相邻事件跨度 6-12 个月：中严重程度
- 相邻事件跨度 3-6 个月：低严重程度（如有法定期限则参考期限）

## §9 图表分拆规则

### 9.1 分拆触发条件

| 图表类型 | 触发阈值 | 建议拆分方式 |
|----------|----------|-------------|
| timeline | 事件 > 20 | 按阶段/角色/主题拆分 |
| relation | 节点 > 15 | 按群体/关系类型拆分 |
| evidence | 事实+证据 > 20 | 按争议焦点拆分 |
| flow | 步骤 > 15 | 按功能模块拆分 |
| dispute | 争议 > 10 | 按争议大类拆分 |
| matrix | 主张 > 15 | 按争议大类/请求类型拆分 |
| data_table | 行 > 20 | 按类别/阶段拆分 |

### 9.2 分拆建议格式

当触发分拆时，在输出中提供：

```
> 当前信息量较大（{节点数}个节点），建议拆分为以下 {N} 张图表：
> 1. {子图1标题}：包含 {节点列表}
> 2. {子图2标题}：包含 {节点列表}
> 
> 以下为第一张图表的输出：
```
