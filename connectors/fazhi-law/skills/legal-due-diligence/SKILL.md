# 通用企业法律尽职调查

以委托目的为入口、以证据链为基础、以法智/快查共享 MCP 中的快查企业数据能力为主要自动外部核查能力，并在限定事项中以可信公开信息作不足补充，完成调查并生成一份正式、无品牌、纯黑法律公文式 Word 尽调报告。

## 不可变交付契约

1. **唯一正式输出是 DOCX**：不得将资料清单、Markdown 分析、问题表、JSON、PDF、PNG 或查询底稿作为正式交付物；这些只可作为内部临时工作材料。
2. **模板强制**：必须从用户模板或 `assets/法律尽职调查报告模板_正式无品牌版.docx` 复制生成。禁止从空白 `Document` 新建报告，禁止自行设计封面。
3. **固定外层结构**：最终报告严格使用本文件规定的八部分外层结构。现有八章核查框架只作为内部数据模型，不得直接套作报告目录。
4. **纯黑法律公文样式**：所有可见文字、边框、横线、页眉页脚均为黑色 `#000000`；页面白底；不得使用蓝色、深红色、灰色或其他强调色。
5. **无生成痕迹**：不得出现“含 AI 生成”“AI 生成”“公开渠道·律师视角”“按 F9 更新”“模板说明”等内部提示或装饰标签。
6. **逐页渲染门控**：交付前必须渲染并检查每一页。未完成结构校验和逐页视觉检查不得交付。

## 信息源与客户语言契约

1. 用户提供尽调资料或既有底稿时，必须先建立版本受控的“当前采信资料库”，并以其作为正式报告的主信息源。快查及限定范围内的可信公开信息仅用于一致性复核、补充公开线索和发现冲突，不得静默覆盖主信息源。
2. 主管机关原件或其他更高等级材料到达后，必须先完成版本登记并转为当前采信版本，方可替换对应事实的主源；替换前只记录口径冲突和补正要求。
3. 只有未提供任何项目资料时，才进入 `public_information_pre_dd` 模式，并在报告函中明确公开信息核查的范围与限制。
4. 内部底稿可以记录 MCP、工具、接口、参数、分页、空结果、未覆盖、失败状态和查询日志；正式报告不得出现这些内部技术信息或能力评价。
5. 正式报告仅在报告函中使用一次以下来源声明，正文、待核实事项、附件和签署页不得重复：
  `本次公开信息核验以同花顺旗下快查企业数据引擎为主要渠道，并对官网、官方公示及可信公开报道进行有限补充核查；相关结果仅用于一致性复核和线索补充，不替代委托方提供并纳入当前采信范围的资料及原始证明。`
6. 正文引用有限外部检索取得的事实或线索时，必须在该段末尾插入 Word 原生脚注，在当页底部列明来源名称、页面标题、发布日期、URL 和访问日期；仅列入附件清单、普通括号或固定页脚不构成溯源。

## MCP 工具调用

企业信息和法律依据核验均通过同一个法智/快查共享 MCP 完成。开始核查前必须完整读取 [fazhi-mcp/SKILL.md](../fazhi-mcp/SKILL.md)，并以当前会话实际暴露的服务器标识符、工具名和参数 schema 为准。

- 企业公开信息核查使用共享 MCP 的 `discover`、`call`，其业务能力和数据来源称为“快查”；不得将企业数据表述为法智自有法律数据库结果。
- 法律法规依据核验使用同一共享 MCP 的 `legal_article_search`、`law_content_visit`；这不改变企业信息的快查来源属性。
- 不得依赖写死的服务器前缀，不得直接请求 HTTP API，不得使用本地接口包装脚本，不得把凭证放入工具参数或对话正文。
- 企业公开信息核查先使用当前采信资料和快查；只有公司、核心人员、产品/业务、商标/品牌四类事项在资料不足、快查不覆盖或需补充商业真实性及舆情线索时，才按 [references/快查外部核查与底稿规则.md](references/快查外部核查与底稿规则.md) 开展定向外部检索。其他事项不得切换到 WebSearch、浏览器、官网或其他企业数据库。



## 固定外层结构

最终报告只允许以下外层顺序：

1. 无品牌正式封面；
2. 报告致送页/报告函及免责声明；
3. 正文：
  - 目标公司基本情况；
  - 历史沿革；
  - 股权结构、股东及实际控制人；
  - 公司治理；
  - 业务、资质及重大合同；
  - 资产与知识产权；
  - 劳动用工；
  - 税务、诉讼、处罚及合规；
  - 其他实际启用模块；
4. 重大问题及风险提示；
5. 待核实事项；
6. 结论与建议；
7. 附件或资料清单；
8. 签署页。

不得在上述结构前后新增执行摘要、修订记录、快查能力声明、自动目录或其他一级部分。资料覆盖、核查程序、公开信息限制和证据限制可以写入报告函、免责声明、相关正文、重大问题或待核实事项；快查品牌来源仅按本技能规定在报告函披露一次，能力边界和技术状态不得直接写入正式报告。

正文中的固定八个调查主题原则上保留；某主题确不适用时，以简短限定说明代替整章删除。只有“其他实际启用模块”可以按调查范围动态增减。

## 工作流



### 阶段 0：输入归一与委托识别

1. 将用户表述归一为适用的 `engagementType`。类型会改变结论出口时才询问决定性信息，不得默认投融资。
2. 归一 `projectPath / roundFolder / targetEntity / engagementPurpose / reportCutoffDate / materialPath / scope / outputPath`。
3. `materialPath` 与 `ddMaterialPath` 同时存在时，以 `materialPath` 为准并记录冲突。
4. 生成统一内部上下文：
  `engagementType / targetEntity / engagementPurpose / clientName / reportCutoffDate / materialPath / scope / outputPath / enabledModules`

**进入下一阶段的条件**：委托类型、目标主体、委托目的、基准日、调查范围和输出目录均明确；`clientName` 缺失时必须询问。

### 阶段 1：主体锁定与范围建模

1. 名称存在歧义时，使用共享 MCP 的快查企业能力 `discover` 后 `call` 搜索候选。
2. 对照全称、统一社会信用代码、地区、住所、法定代表人和历史名称消歧。
3. 固化企业全称、统一社会信用代码及 `orgid`，后续优先级为 `orgid > creditcode > corp_name`。
4. 无法唯一匹配时暂停实体级核查并请求确认，不得猜测。
5. 读取 `references/调查范围与模块启用规则.md` 生成标签、`enabledModules`、排除项和理由。



### 阶段 2：资料控制与证据基线

1. 扫描材料并建立内部资料 ID、版本 ID、当前采信状态、主体范围、期间、来源路径和缺口。
2. 只有当前采信版本可以直接支持结论；旧版和待确认件仅用于识别演变或冲突。
3. 存在材料时，将 `source_control.primary_basis` 固定为 `current_accepted_materials`，`primary_material_ids` 必须列出当前采信资料 ID，`external_verification_role` 固定为 `corroboration_only`。
4. 没有任何项目材料时，才可将 `source_control.primary_basis` 设为 `public_information_pre_dd`；该模式必须在报告函中加入公开信息核查范围限制。
5. 快查与当前采信资料不一致时，不得改写主资料口径；应在 `source_control.conflicts` 记录冲突并形成客户化限定表述。
6. 资料控制表和 `source_control` 属于内部工作材料，不作为正式输出。



### 阶段 3：模块核查、快查验证与有限外部检索

对每个启用模块执行：规划核查点 → 审阅内部证据 → 共享 MCP 的快查 `discover/call` → 完成分页和事件状态链 → 判断限定外部检索触发条件 → 交叉验证 → 形成限定结论。

硬门控：

- 快查是主要自动外部核查渠道。仅公司、核心人员、产品/业务、商标/品牌四类事项可以在资料和快查不足时补充定向外部检索；财务、税务、社保、合同完整性、资产权属及其他事项仍转资料催收或人工复核。
- 有限外部检索不得登录、付费订阅、注册账户或绕过访问限制；搜索结果摘要不得作为证据。
- 内部查询状态继续使用 `EMPTY_RESULT`、`UNSUPPORTED`、`FAILED`、`INCOMPLETE`；进入正式报告前必须按客户语言映射转换，不得直接输出状态名或技术原因。
- 记录工具、参数、主体标识、页码、总数、停止条件、事件日期、数据更新时间和查询时间。
- 快查数据不得替代工商内档、许可证原件、合同、审计、征信、社保或主管机关证明。
- 查询底稿属于内部工作材料，不作为正式输出。



### 阶段 4：证据交叉验证与问题形成

1. 内外部证据一致且链条完整时才标“已核实”。
2. 冲突证据并列保留并标“口径冲突”；外部单一来源标“外部线索”；链条不完整标“待补正”；能力不覆盖标“未覆盖”；失败标“查询失败”。
3. 每个问题内部记录问题编号、事实、证据状态、风险等级、法律依据、版本、核查程序、待补材料、处理出口和验证状态。
4. 只有已核验的法律来源可直接作为依据；时效或适用条件不明时标“待人工复核”。
5. 问题处理建议按 `engagementType` 映射，不得把 PE/VC 条款作为所有项目默认出口。



### 阶段 5：映射到正式报告

将内部核查结果映射到固定外层结构：

- 主体、沿革、股权、治理等事实分别写入对应正文主题；
- 资料覆盖、调查程序和公开信息限制写入报告函及免责声明；内部能力边界转换为客户可理解的证据限制和补正要求；
- 报告函仅保留一次经批准的公开信息来源声明；其他位置只使用“已核验的公开信息”等中性表述；
- 对投资或决策有实质影响的问题写入“重大问题及风险提示”；
- 证据缺口、冲突、空结果限制、未覆盖和待人工复核写入“待核实事项”；
- 正文、重大问题或待核实事项引用有限外部检索事实时，将结构化 `external_sources` 写入对应内容块，由生成器转换为当页 Word 原生脚注；不得手工伪造上标或把来源集中写入固定页脚；
- 处理出口写入“结论与建议”；
- 已审阅资料、关键外部查询来源或用户要求的清单写入“附件或资料清单”；
- 律师、负责人或日期未知时保留中性签署线，不得虚构姓名。



### 阶段 6：生成 Word 报告

1. 读取 `references/Word报告结构与格式规则.md`。
2. 校验 `reportTemplatePath`；未提供时使用 `assets/法律尽职调查报告模板_正式无品牌版.docx`。模板缺失即停止，禁止空白文档降级。
3. 读取 `references/报告数据契约.md`，将报告内容组织为 `scripts/build_legal_dd_report.py` 所需的结构化 JSON。JSON 只存于临时工作目录。
4. 调用生成器：
  ```text
   python scripts/build_legal_dd_report.py --template <template.docx> --data <report.json> --output <report.docx>
  ```
5. 文件名使用 `[目标主体]_法律尽职调查报告_vN.docx`；不得覆盖旧版。
6. 调用校验器：
  ```text
   python scripts/validate_legal_dd_report.py <report.docx> --json <validation.json>
  ```
7. 校验失败必须修复后重新生成，不得手工忽略错误。



### 阶段 7：渲染、逐页检查与交付

1. 使用文档渲染能力或 LibreOffice 无界面模式将 DOCX 渲染为 PDF 和逐页 PNG。
2. 检查每一页，不得抽样代替最终检查。
3. 检查封面、报告函、各类正文页、长表格、章节切换、附件和签署页。
4. 发现裁切、重叠、异常空白页、孤立标题、跨页表头丢失、字体漂移、页眉页码错误或品牌残留时，修复并重新渲染全部页面。
5. 只交付最终 DOCX；PDF、PNG、JSON 和内部底稿不得作为正式输出。



## 最终硬性失败条件

出现下列任一项即不得交付：

- 模板不存在、不可读或未被使用；
- 最终外层结构、名称或顺序与本文件不一致；
- 出现额外一级章节、自动目录或空目录页；
- 封面出现页眉、页脚或页码；
- 正文无动态页眉，或正文页码未从 1 开始；
- 使用 `1/N` 形式页码；
- 全文只有一个分节；
- 缺少报告函、免责声明或签署页；
- 出现彩色文字、灰色标签、彩色底纹或装饰块；
- 出现“含 AI 生成”“按 F9 更新”等提示；
- 标题未使用命名样式；
- 表格使用自动列宽、百分比宽度、固定行高或字体小于 9.5 pt；
- 残留旧主体、旧律所、旧律师、示例数据、批注、修订或个人元数据；
- 空结果、材料缺失、查询失败或能力未覆盖被写成否定性事实；
- 出现 MCP、discover、call、tool_id、查询日志、分页完整性、参数错误、权限错误、服务错误、快查接口、内部工作材料等内部技术信息；
- 快查品牌未按规定在报告函中恰好披露一次，或在其他部分重复出现；
- 报告数据包含 `external_sources`，但对应正文没有原生脚注，脚注缺少来源名称、页面标题、发布日期、URL 或访问日期，或者脚注编号与正文引用不一致；
- 标题样式仍引用主题字体，或标题有效字体为 MS Gothic、ＭＳ ゴシック等非规定字体；
- 未通过 `validate_legal_dd_report.py`；
- 未完成最终版本的逐页渲染检查。



## 禁止事项

- 禁止编造事实、证据、法条、快查返回值、工具名、参数或查询结果；
