# 法律文书起草技能

## 一、技能定位

本技能以**最终成品文书**为交付目标，覆盖法律文书的起草、撰写、修改、润色、完善、改写、补全等全部场景。

### 文书类型范围


| 类别      | 代表性文书                                     | 处理方式                               |
| ------- | ----------------------------------------- | ---------------------------------- |
| 民事诉讼与执行 | 起诉状、答辩状、反诉状、上诉状、再审申请书、保全申请、执行申请、执行异议、管辖异议 | 有内置模板时优先参考模板；无模板时使用官方范本或通用 Word 规则 |
| 仲裁      | 仲裁申请书、仲裁答辩书、财产保全申请、代理意见                   | 检索适用仲裁机构或权威公开范本后生成                 |
| 刑事      | 刑事自诉状、辩护词、法律意见、取保候审申请等                    | 不套用民事模板，按对应程序体例生成                  |
| 行政      | 行政起诉状、答辩状、复议申请、申诉材料等                      | 不套用民事模板，按行政程序体例生成                  |
| 诉讼辅助材料  | 证据目录、质证意见、代理词、授权委托书、调查取证申请等               | 根据材料和程序用途选择结构                      |
| 非诉法律文书  | 律师函、声明、通知、承诺、合同、协议等                       | 合同和协议是次级类型；无内置模板时按官方范本与通用规则生成      |


法律意见书不属于本技能范围，必须由 `legal-opinion` 处理；企业法律尽职调查及法律尽调报告不属于本技能范围，必须由 `legal-due-diligence` 处理。混合请求按最终交付物拆分，各专用技能分别完成对应成品。

内置资产主要覆盖高频民事诉讼文书，仅表示模板覆盖范围，不限制本技能可处理的文书类别。

核心原则：

- 忠实客户意图，以客户提供的事实和材料为唯一依据
- 客户未提供但文书必要的信息，用 `【待补充：字段名称】` 占位，禁止编造
- 修改、润色已有文书时，保留原文书核心结构与客户明确要求保留的内容，仅作必要调整
- 民事诉讼模板存放于本技能 `assets/templates/`，起草时按第二节路由表选择适用 Word 模板
- 直接输出 Word（.docx）格式成品文书，以文件形式交付
- 禁止把 HTML、HTML 代码块、Markdown 文书或纯文本作为最终成品；DOCX 正文不得包含 HTML 标签、CSS 或 Markdown 链接源码
- 工具返回的 `law_id`、案例 ID、URL 和来源信息仅用于后台真实性核验，不写入最终 Word；不得创建超链接、脚注来源、尾注来源、`[n]` 或参考文献表
- 文书中的法规名称、条款和必要案号使用与正文一致的普通黑色文字，不使用蓝色、下划线或 Word“超链接”样式
- 法规链接规则仅适用于后台核验，或用户另行明确要求的对话内 Markdown 引用：具体条文使用 `[《法规全称》第N条](https://www.fazhi.law/law-saas/lawDetail/{law_id}?pos=tN)`，整部法规使用 `[《法规全称》](https://www.fazhi.law/law-saas/lawDetail/{law_id})`；该规则不改变最终 DOCX 的无链接要求
- 检索、分类、模板选择、工具名称、query 和中间过程静默执行，不向用户展示

## 二、模板体系



### 模板存放路径

本技能只在 `assets/templates/` 中存放高频 Word 模板。按目标文书名称和程序用途读取以下对应资产，不读取无关模板：


| 文书名称            | 适用场景                        | 资产文件名                  |
| --------------- | --------------------------- | ---------------------- |
| 管辖异议书           | 当事人对受理法院管辖权提出异议             | `管辖异议书.docx`           |
| 授权委托书           | 公民、法人或其他组织委托诉讼代理人           | `授权委托书.docx`           |
| 申请人民法院调查收集证据申请书 | 当事人因客观原因不能自行收集证据，请求法院调查收集   | `申请人民法院调查收集证据申请书.docx` |
| 证据目录（证据材料清单）    | 将证据按编号、名称、页数、证明目的和备注整理成提交清单 | `证据目录.docx`            |
| 诉讼财产保全申请书       | 诉前或诉中申请财产保全                 | `诉讼财产保全申请书.docx`       |
| 民事起诉状           | 公民、法人或其他组织提起第一审民事诉讼         | `民事起诉状.docx`           |
| 民事反诉状           | 本诉被告在本诉中提出反诉                | `民事反诉状.docx`           |
| 民事答辩状           | 民事诉讼当事人针对起诉、上诉或再审主张答辩       | `民事答辩状.docx`           |
| 民事上诉状           | 当事人不服第一审民事裁判提起上诉            | `民事上诉状.docx`           |
| 民事再审申请书         | 当事人依法申请再审                   | `民事再审申请书.docx`         |
| 申请执行书           | 生效法律文书确定的义务未履行时申请强制执行       | `申请执行书.docx`           |
| 当事人、利害关系人执行异议书  | 当事人或利害关系人对执行行为提出异议          | `当事人、利害关系人执行异议书.docx`  |




### 模板使用规则

- 起草民事诉讼文书前，先按本节路由表确认是否存在对应 Word 模板
- 若 `assets/templates/` 中存在对应 Word 模板，读取该模板作为体例参考
- 模板仅用于格式、结构、写作要领参考，**不得照搬**其中的当事人、金额、案情等示例信息
- 最高人民法院民事诉讼模板仅适用于相应民事程序，不得误套用于刑事、行政或非诉文书
- 若无适用模板，使用现有互联网工具检索法院、检察院、司法行政机关或律师协会发布的官方范本，并阅读原网页核验结构后，依第六节通用 Word 规则生成
- 不得因内置模板缺失而将现有民事模板误套用于刑事、行政或非诉文书
- 互联网检索材料仅用于格式和结构参考，不得替代客户事实



### 通用模板的主体分支（强制）

- 对每一名当事人分别判断其为公民、法人或其他组织，不得仅按首名当事人的类型处理全部主体
- 支持公民与法人混合、多名原告、多名被告、多名申请人或多名异议人；每名当事人单独成段并采用与其主体类型匹配的字段
- 公民填写姓名、性别、出生年月日、民族、职业、工作单位、住所和联系方式；信息并非该文书法定或必要记载项时可从简，但不得编造
- 法人或其他组织填写名称、住所、法定代表人或主要负责人姓名、职务和联系方式
- 公民落款由本人签名；法人或其他组织落款应为单位盖章，并由法定代表人或主要负责人按适用体例签名
- 模板中的主体分支说明仅是生成控制信息。最终文书只保留适用于该当事人的字段，必须删除另一套字段、空白条件行以及“按主体类型选择”“公民删除本行”等控制文字



### 证据目录规则（强制）

- 用户要求“证据目录”“证据清单”或“证据材料清单”时，使用 `证据目录.docx`，不得套用诉状、申请书的正文结构
- 仅根据用户实际提供的证据文件和说明填写编号、证据名称、页数、证明目的及备注；不得虚构证据、页数、形成时间或证明内容
- 用户已经编号的，原则上保留原编号和顺序；未编号时按材料顺序连续编号，用户要求按争点、时间或证据类型排序的除外
- 证据名称应客观、具体；“要证明的事实”只作中性概括，不将待证事实写成已经法院确认的事实
- 页数、证明目的或提交人信息无法确认时，使用 `【待补充：字段名称】`，不得猜测
- 每项证据独占一行，按实际数量增减表格行；最终删除多余空白行和模板控制文字

## 三、任务类型与意图识别



### 意图分类

根据用户表述，将任务归入以下意图之一：


| 意图        | 典型表述                       | 核心动作                 |
| --------- | -------------------------- | -------------------- |
| **起草/撰写** | “帮我写一份……”“起草一份……”“需要一份……”  | 从零创建完整文书             |
| **修改**    | “把这份……改一下”“修改第X条”“把诉求改成……” | 对已有文书的特定内容进行调整       |
| **润色**    | “润色一下”“优化表达”“改得更专业”        | 优化语言表达、法言法语，不改变事实和结论 |
| **完善/补充** | “补充一下”“完善这份……”“缺什么补上”      | 补充缺失内容、补强论证，不推翻原有结构  |
| **改写/重构** | “重写一份”“换个角度”“结构重新组织一下”     | 重构文书结构或整体改写          |




### 意图判断规则

1. 用户明确说出意图关键词的，直接归入对应类型
2. 用户上传文书但未明确意图的，默认按“完善”处理——保留原文结构，补充缺失要素、优化表达
3. 用户既上传文书又提出具体修改要求的，按“修改”处理——仅针对要求的部分调整
4. 意图模糊时，优先按改动最小的方向处理（润色 < 修改 < 完善 < 改写），避免过度改动
5. 多轮对话中，后续轮次默认延续上一轮的文书类型和上下文，不重新从零开始

## 四、工作流程



### 第一步：意图识别与信息提取（强制）

1. **判断意图类型**：按第三节规则归入起草/修改/润色/完善/改写
2. **确认文书类型**：从用户表述中提取文书名称和所属类别（如民事诉讼、执行、仲裁、刑事、行政、诉讼辅助或非诉文书；合同、协议按非诉文书处理）
3. **提取客户信息**：
  - 起草类：当事人信息、诉求/申请事项、案件事实、证据等
  - 修改/润色/完善类：原文书内容 + 具体修改要求
4. **信息不足处理**：未提供但文书必要的信息用 `【待补充：字段名称】` 占位完成，不向用户反复确认；仅当文书类型或核心诉求完全无法判断时，简要确认一次

---



### 第二步：获取参考材料

**先按第二节模板路由表定位目标文书的 Word 模板**：

- 若 `assets/templates/` 中存在对应模板文件，读取模板获取结构和格式规范
- 参考模板仅用于体例借鉴，不得照搬其中事实、当事人、金额或案情
- 使用通用模板时，逐名识别当事人主体类型，展开实际需要的当事人段落，并在最终文书中删除未使用的主体字段和模板控制文字

**模板不存在或不在规划范围内时**：

- 使用 `webpage_search` 检索该类文书的公开格式或权威范本，再用 `webpage_visit` 阅读原网页并核验结构
- 优先采用法院、检察院、司法行政机关、律师协会等官方来源；无可靠官方范本时，按第六节通用 Word 规则生成并保守使用占位符
- 检索结果仅用于格式体例参考，不得替代客户事实
- 不得引用已经删除的章节参考，也不得为填补模板空缺而误用现有民事模板

---



### 第三步：法规检索（按需）

**仅当文书需要引用或核验具体法律依据时执行**，不需要时跳过。

#### 触发条件

- 诉状类：需明确请求权基础
- 申请书类：需程序法依据
- 律师函：需法规支撑
- 修改/完善任务中涉及法律依据变更或补充的
- 用户明确要求“要有法律依据”“引用法条”

**不触发**：证据目录、证据清单、证据材料清单、纯事实陈述、仅排版调整、仅语言润色不涉及法律论证的。

#### 检索工具

通过 **fazhi-mcp** 技能调用 MCP 工具，具体调用方式、参数 schema 和工具选择规则见 [../fazhi-mcp/SKILL.md](../fazhi-mcp/SKILL.md)。

文书起草按需使用以下工具，不强制三源并行：


| 场景                     | 工具                     | 规则                      |
| ---------------------- | ---------------------- | ----------------------- |
| 核验请求权基础、程序依据、引用法条      | `legal_article_search` | 已知法名和条号时精确检索；未知条号时语义检索  |
| 核验法规上下文、完整内容或适用范围      | `law_content_visit`    | 必须先取得真实 `law_id`        |
| 用户要求案例支持或复杂争点需要裁判理由    | `case_search`          | 以事实、争点和程序场景构造 query     |
| 核验具体案例的案号和裁判理由         | `case_browser`         | 必须先取得真实案号或案件名称          |
| 内置模板缺失、程序实践可能更新、查找官方范本 | `webpage_search`       | 优先法院、检察院、司法行政机关、律协等官方来源 |
| 核验具体官方页面或范本正文          | `webpage_visit`        | 必须使用搜索结果返回的原始 URL       |


纯排版、纯语言润色、证据清单整理等不涉及法律依据或格式更新的任务，不为调用工具而调用工具。相互独立且同时必要的请求可以并行；同一目标失败或空结果最多重试一次，且必须改变检索表达。

#### 检索策略

1. **精确核验**（已知法律名称和条款号）：
  - 参数组合：`law_name` + `item`
  - 示例：`law_name="中华人民共和国民法典"`，`item="第五百七十七条"`
  - 直接核验条款内容是否准确、是否现行有效
  - 注意修正版本（如“2020年修正”“2022年修正”）
2. **语义检索**（知道法律概念，不确定具体条款）：
  - 传入明确的自然语言或关键词 `query`
  - 示例：`query="买卖合同 违约责任 条款"`
  - 从返回结果中定位最相关的法律和条款
  - 找到目标法条后，再用精确核验方式确认条款内容
3. **案由检索**（知道纠纷类型，找请求权基础）：
  - `query` 构造：`"民间借贷 利息 上限 法律规定"`
  - 可加 `status="现行有效"` 过滤失效法规
  - 从返回结果中筛选法律、行政法规、司法解释层级的依据
  - 优先采用上位法和最新有效版本
4. **法规全文研读**（需深读某法规全文）：
  - 先用 `legal_article_search` 定位法规，获取真实 `law_id`
  - 再调用 `law_content_visit`，传入 `law_id`、`goal` 和 `max_length`
  - 按目标提取要点，而非全盘照搬



#### 检索结果使用

- 引用必须经检索核验，不得凭记忆编造法条编号或内容
- 文书需要写明法律依据时，使用法律全称和中文数字条款号，按第五节“法律依据写入格式”作为普通黑色正文写入
- 同时核验 `law_id` 与效力状态，只引用接口明确返回为“现行有效”的法规
- 检索到的法条仅作为论证依据，不得替代客户事实
- 同一文书中引用同一法律的多条法条时，在同一处合并显示
- `law_id` 和法规详情 URL 只用于后台核验，不写入最终 Word；禁止猜测或补全 ID
- 后台记录具体法条来源时，使用 `?pos=tN`，其中 `N` 为已核验条号转换后的无前导零阿拉伯数字；款、项锚定所属条。仅记录整部法规来源时使用不带 `pos` 的法规详情页。多条或区间按条分别记录；无法解析条号时只记录整部法规详情页，不编造 `pos`



#### 案例与互联网工具（按需）

- 仅在用户要求案例支撑或复杂争点确需裁判理由时，使用 `case_search` 检索，并用 `case_browser` 阅读和核验具体案例
- 内置模板缺失、格式或程序实践可能更新时，使用 `webpage_search` 查找官方公开范本，并用 `webpage_visit` 阅读原网页
- 案例案号、案例 ID、网页 URL 必须来自工具真实返回；禁止虚构、补全或拼接。案例 ID 和网页 URL 仅供后台核验，不写入最终 Word
- 相同目标空结果时最多更换一次表达重试；仍无可靠结果时保留占位或说明无法核验，不得用记忆补写

### 第四步：执行写作

按意图类型执行对应写作路径：

#### 路径 A：起草/撰写

1. 基于模板体例和客户事实，从零构建完整文书
2. 诉状、申请书等叙述型文书按“当事人信息 → 诉求/申请事项 → 事实与理由 → 证据 → 落款”的常规结构组织；证据目录直接按第二节证据目录规则生成表格
3. 必要信息缺失处用 `【待补充：字段名称】` 占位
4. 按需检索法规并嵌入论证



#### 路径 B：修改

1. 通读原文书，定位需修改的具体位置
2. **仅修改客户指出的部分**，未提及的内容保持原样
3. 事实变更时，同步调整相关论证和法律依据
4. 修改后通读全文，确保逻辑连贯、前后一致
5. 保留用户源文件，另行输出新的 DOCX；除非用户明确要求，不得覆盖源文件



#### 路径 C：润色

1. **不改变事实陈述和法律结论**，仅优化表达
2. 将口语化表述改为法言法语
3. 调整语序、精简冗余、强化逻辑衔接
4. 统一术语和格式规范



#### 路径 D：完善/补充

1. 保留原文书核心结构和已有的正确内容
2. 对照文书规范要素，找出缺失部分并补充
3. 补强论证薄弱环节，补充必要的法律依据
4. 不推翻原有框架，只做增量完善



#### 路径 E：改写/重构

1. 保留原文书中的核心事实和客户明确要求保留的内容
2. 重新组织文书结构和论证逻辑
3. 按目标文书的规范体例完整重构
4. 完成后对照原文核查，确保客户核心诉求未遗漏

2. 全部通过后，按第六节 Word 格式要求生成 .docx 文件
3. 修改/润色/完善类任务，直接输出成品 Word 文件，不在文件外添加多余说明文字

## 五、写作规则

本节规则是本技能特有的输出约束。通用写作规则（法言法语、禁止编造、来源限定、金额格式等）不在此重复。

### 法律依据写入格式（强制）

法规依据需要出现在文书中时，必须使用完整的 `《法规全称》第×条`，作为与正文格式一致的普通黑色文字嵌入句中。不得创建 Word 超链接，不得附带 URL、`[n]`、脚注来源、尾注来源或参考文献表。

本节是统一法规链接规则的明确 DOCX 例外：即使后台已经取得真实 `law_id` 和 `pos`，最终 Word 仍只写普通黑色法规文字。只有用户另行要求在对话中提供 Markdown 版来源说明时，才对该说明采用统一的可点击法规链接格式，且不得把 Markdown 源码或链接关系写入 DOCX。

**正确**：

- 以普通黑色正文写作：依据《中华人民共和国民法典》第五百七十七条、第五百七十九条，违约方应当承担继续履行、采取补救措施或者赔偿损失等违约责任。
- 以普通黑色正文写作：《最高人民法院关于审理买卖合同纠纷案件适用法律问题的解释》（2020年修正）第十八条第四款规定，……

**禁止**：

- 法条与裁判观点分离，或集中罗列、堆砌依据
- 使用法规简称：禁止只写《民法典》，必须使用《中华人民共和国民法典》
- 使用阿拉伯数字条号：禁止“第577条”，必须使用“第五百七十七条”
- 将同一法律的多条依据拆成彼此割裂的引用
- 为法规名称或条款创建超链接，或者使用蓝色、下划线、“超链接”样式
- 在文书中显示 `law_id`、法规详情 URL、Markdown 链接源码或来源序号



### 案例与网页材料写入格式（强制）

- 案例和互联网材料原则上仅用于后台核验与辅助论证，不在最终 Word 中显示来源链接或引用编号
- 只有用户明确要求在文书中写出具体案例时，才以普通黑色正文写入经案例库核实的完整案号；不得创建超链接，不得显示案例 ID 或 URL
- 禁止补全残缺案号、虚构案例 ID 或拼接裁判文书网地址
- 不在完整句末添加 `[n]`，不显示网页 URL，不生成脚注、尾注或集中参考文献表
- 互联网文章中的案例未经案例库核实时，不作为具体案例写入最终文书



### 标题层级

一、（二）1.（1）① 五级递进。参与人信息、诉讼请求等栏目标题可加粗，正文不宜过度拆分。

### 客户信息处理

- 客户文件与陈述是事实唯一基础；明确要求保留的内容不删，要求处理的部分充分落实
- 未提供但文书必要的信息用 `【待补充：字段名称】` 占位
- 原材料格式错误或逻辑矛盾可在不违背用户意图前提下修正
- 多轮对话中，后续轮次默认继承前序文书的当事人、事实等信息，无需用户重复提供
- 多名当事人逐名处理；不同主体类型可以在同一文书中混合出现，但每名当事人只输出适用于其类型的一套身份字段和落款规则

## 六、Word 格式要求



### 输出格式（最高优先级）

**最终产物为 .docx 文件**，以 Word 文档形式直接交付给用户。禁止输出 HTML、HTML 代码块、Markdown 文书或纯文本；DOCX 正文同样禁止 HTML 标签、CSS、Markdown 链接源码、内部链接标记、来源 URL、`[n]` 和超链接。

### 输出文件安全（强制）

- 最终 DOCX 只写入用户指定的任务输出目录；用户未指定时，写入当前任务的输出目录
- 修改、润色、完善或改写已有文书时，保留用户源文件并另行输出新文件；除非用户明确要求，不得覆盖源文件
- 文件名须清理 Windows 非法字符 `\ / : * ? " < > |`，不得使用路径穿越片段或把用户输入直接当作路径
- 目标目录存在同名文件时，在基本文件名后依次增加 `（2）`、`（3）` 等序号，不得静默覆盖
- 不得把用户材料、最终文书、渲染图片或其他临时文件写入本 Skill 目录；Skill 目录只保留自身规则和模板资产



### 排版规范


| 要素                       | 规范                                      |
| ------------------------ | --------------------------------------- |
| **页面设置**                 | A4 纸，上下边距 2.54cm，左右边距 3.17cm            |
| **文书标题**                 | 居中，黑体二号，加粗，段前距 1 行，段后距 1 行              |
| **当事人信息**                | 宋体小三号，左对齐，每方当事人单独成段                     |
| **栏目标题**（如“诉讼请求”“事实与理由”） | 宋体小三号，加粗，左对齐，段前距 0.5 行                  |
| **正文**                   | 宋体小三号，首行缩进 2 字符，1.5 倍行距                 |
| **落款**                   | 宋体小三号，右对齐，包含具状人/申请人及日期                  |
| **日期格式**                 | 已有日期统一为 `YYYY年MM月DD日`；未提供时使用 `【待补充：日期】` |
| **页码**                   | 底部居中，阿拉伯数字                              |
| **表格**（证据清单等）            | 宋体小四号，边框完整，内容居中或左对齐视情况而定                |




### 格式注意事项

- 全文统一使用中文标点符号
- 金额同时呈现大小写，如“人民币壹万元整（￥10,000.00元）”；用户未提供金额时不得生成示例值
- 法规名称、条款和必要案号按第五节规范写为普通黑色正文；不得使用蓝色、下划线或 Word“超链接”样式
- 未提供信息用 `【待补充：字段名称】` 占位，如“被告：`【待补充：被告姓名或名称】`”
- 生成通用模板文书时，删除所有未使用的主体字段、条件行和模板控制文字；不得同时输出公民与法人两套字段
- 标题层级按“一、（一）1.（1）①”五级递进
- 禁止使用 CSS、Markdown 语法或 HTML 标签



### 生成方式

优先以 `assets/templates/` 中对应 Word 模板为底稿，使用 TRAE 当前运行环境可用的 DOCX 文档处理能力生成或编辑文件；如使用 `python-docx`，按上述排版规范设置字体、字号、对齐方式、行距和缩进，不创建 `w:hyperlink` 节点或外部超链接关系。法规、条款和案号文本明确设置为黑色且无下划线，避免 Word 自动套用"超链接"样式。

生成完成后，以文件附件形式交付。条件允许时，将 DOCX 渲染为逐页图片进行目视检查，确认正文没有蓝色、下划线或引用序号；如运行环境没有可用渲染能力，不得声称已完成视觉验收，但仍须检查 DOCX 结构、占位符、外部超链接关系和文件完整性。
