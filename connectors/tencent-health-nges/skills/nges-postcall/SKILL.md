# nges-postcall — NGES 访后记录（对标 ADP 标品）

本 skill 以 ADP 标品 AI 拜访的 PostCall 提示词为最高参照，拆为 **4 个能力模块**，按用户意图路由：

| 模块 | 触发意图 | 对标 ADP 子 Agent |
|---|---|---|
| ① 拜访录入 | "记录/补录/修改拜访、刚见完某医生" | 拜访录入子 Agent |
| ② HCP360 更新 | "更新医生观念/定级/标签" | HCP360 更新子 Agent |
| ③ 行动推荐 | "下一步该怎么做 / NBA / 下次拜访建议" | 行动推荐子 Agent（NBA & NBC） |
| ④ 兜底拒答 | 不属于以上明确业务意图 | 兜底与拒答子 Agent |

**模块流转**：① 录入成功 → 建议"是否更新 HCP360"（转 ②）或"查看行动推荐"（转 ③）→ ③ 确认后生成拜访计划（转 nges-precall 的 ④ 计划模块）→ 意图超出范围回意图路由。

> **环境差异说明**：ADP 的 `GetHcpProfile`（today_plan/product_key_message）、`SubmitVisit`、`Grade` 生效工具、知识库问答、widget 卡片在 MCP 连接器环境中不存在。本 skill 用已实测 GQL 组合替代取数（见 [references/verified-findings.md](references/verified-findings.md)），用 references 文件替代 GetSkill，用 markdown 替代 widget。**数据红线不变：所有数据必须来自工具返回，不得编造；id 字段（hcp_id/hco_id 等）严禁自己生成，必须用查询回来的值。**

## 0) 前置检查与共享约束

- 确认 tencent-health-nges 连接器可用；任一 MCP 调用返回未连接则提示用户启用后停止。
- **元数据先行**：构造任何 GQL 前用 `GetObjectsByNames` 核对字段与枚举，绝不猜。
- **时间戳一律用工具**：当前时间用 shell `date +%s`，禁止自己推理计算日期；填充到 GQL 的时间戳必须由工具转换而来。
- **行权限自动**：不写 `owner`/`belong_territory` 条件。
- **hcp 查询红线**：任何 hcp 查询必须带 `hcp_territory.id: {_is_null: false}` 过滤（保证医生已分配辖区/岗位），**禁止全量查询 hcp**。
- **输出红线（ADP 强制）**：不展示原始字段名及值（如 status=2）；不展示数据来源；不出现"合规预审/待审核/内部流程"等后台状态词；枚举值先查 options 映射为中文 label；存储的是 id 的字段要附带实际名称展示。
- **状态机（visit_item.status，以元数据枚举为准）**：计划中=0 → 执行中(草稿/待提交)=1 → 已完成(已提交)=2。保存草稿=可继续编辑；提交=不可修改。
- **提交纪律**："提交"动作在 ADP 中必须调专用 SubmitVisit 工具、禁止直接 GraphqlQuery 改状态。MCP 环境暂无 SubmitVisit 工具——保存草稿（status=1）可用 `mutation insert` 直接落库；**提交（status=2）提示代表在 NGES 小程序完成**，或待平台侧提供 SubmitVisit 工具后接入。

## ① 拜访录入模块

**目标**：把代表的语音/文字拜访信息解析成结构化记录，经合规校验后安全写入；支持批量逐条录入。

### 工作流程

**Step 1 校准拜访对象（三种日期分支）**

- **用户明确说"今天"或说了今天日期**：查当天计划校准对象（拜访计划存于 `visit_item`，与拜访记录同表）——
  ```gql
  {visit_item(plan_date: {_gte: <今天0点秒级时间戳>, _lt: <明天0点秒级时间戳>}, _limit: 10) {id hcp_id hco_name plan_date status}}
  ```
  医生姓名优先从当天计划匹配（`hcp_id` 反查 `hcp`，反查时必带 `hcp_territory.id: {_is_null: false}` 过滤）；多匹配触发追问。
- **未来日期**：提示用户日期是否正确、或是否要创建拜访计划（转 nges-precall ④ 计划模块）。
- **过去日期**：用 `date` 工具转换时间戳后查 `visit_item` 那天的记录（走更新流程），**不能用当天计划数据**。
- 用户输入的姓名以查询到的为准；重名列出候选确认。

**Step 2 解析与追问（追问优先级链）**

仅渲染已识别字段块；必填缺失时按以下优先级**一次性集中追问**：

```
姓名 → 拜访类型 → 开始时间 → 结束时间 → 拜访目的 → 选产品 → 产品反馈(积极/中立/消极)
→ KM 反馈（每条 KM 独立选，默认"未讨论"）→（线上拜访额外：关联资料分享记录）
→（填了"下一步计划"则追问"下一次拜访时间"）
```

**推断规则（推断出的字段不再追问确认）**：
- 拜访目的：从产品/讨论点推断（传递产品知识/病理沟通/用药观念沟通/其他）
- 拜访渠道：默认面对面；用户提到在某医院/地点拜访=线下，不追问
- 拜访日期：默认今天（补填走更新流程）
- 开始/结束时间：从描述提取，未精确到分钟默认 00 分（"下午3点到四点半"=15:00-16:30）
- 拜访类型：默认医生拜访
- 枚举命中"其他"语义：不拒答，默认赋"其他"并在备注记录原始语义
- 输入不含有效拜访信息（如闲聊）：提示"输入内容不包含有效拜访信息，请重新输入"并结束本轮

**字段绑定红线**：
- **产品反馈与 KM 反馈绑定**：填了产品反馈，则必须至少填一条 KM 反馈，否则产品反馈也不保存；KM 可能多条需分开展示
- 下一步行动计划非必填，但**填了则"下一次拜访日期"必填**（作为 NBA 依据）
- 关联材料：线下拜访从用户消息提取材料名（如"分享了资料A"），用 GQL 在 `mcm_material`/`mcm_document` 模糊匹配；匹配不到不臆造

**Step 3 更新已有记录的 Case 判定（按状态，不按匹配条数）**

| Case | 当天已有记录状态 | 动作 |
|---|---|---|
| Case1 | 计划中已执行 | 基于本次录入更新，状态改为已执行；若计划由 PreCall 创建且推荐过材料 A 而本次未提 A → 追问"是否使用了资料 A 和医生沟通？" |
| Case2 | 已执行待提交 | 更新记录，保持已执行待提交；仅结合本次输入 |
| Case3 | 计划中（未执行） | 更新材料/渠道，保持计划中；提示"检测到当天存在一条该医生的拜访计划，已更新拜访" |

**Step 4 合规校验**

- agent 输出的 free text 内容经 `CheckStream` 检测（只传 `text`，勿传 `enable_ae_detection`）；受限降级策略与 AE 人工确认兜底见 [references/verified-findings.md](references/verified-findings.md) §5。

**Step 5 确认与写入（两档保存）**

- markdown 呈现录入表单供确认，提供两档操作：**保存草稿**（状态=执行中，可继续编辑）/ **保存并提交**（状态=已完成，不可修改）。
- **✅ 写入已实测可用（2026-09-07 验证）**：正确语法 `mutation insert { visit_item(_values: {...}) }`；`record_type: "oldChannel"` 必填；平台字段（owner/create_time 等）自动填充不传。字段映射：`summary`=拜访小结（报告主体）、`medical_viewpoint`=医生反馈原话、`next_plan`=下一步计划（承诺/遗留）。完整模板见 [references/verified-findings.md](references/verified-findings.md) §1 写入语法。
- **写入流程**：`only_validate: true` 预校验（失败把字段错误转述给用户修正）→ 代表确认 → 正式写入 → **读回验证**（按 id 查回，核对每个字段，特别是日期时间和 id 反查：如 hcp_id 反查 hcp 确认）。保存草稿直接 insert（status=1）；**提交**（status=2）按 ADP 纪律须走专用 SubmitVisit 工具，MCP 环境暂无——提交动作提示代表在 NGES 小程序完成，或待平台侧提供工具后接入。
- **批量录入**：识别到多位医生时逐条执行上述流程，开头提示"识别到医生A、B的拜访信息，会为您依次录入"；每位结束提示进度；单个失败不影响其他；代表中途取消则已录入保留、未录入丢弃。

**Step 6 提交后 KPI 刷新**

提交后查询本月 KPI 完成情况（`visit_item` 按 `status: 2` 计数）展示给用户；指标阈值（如 Monthly customer coverage% >80% 绿）为租户定制项，无定制则不展示阈值判断。

## ② HCP360 更新模块

**目标**：基于本次拜访结果推进医生观念与定级建议，动态更新标签，全程留痕可审计。

**adoption ladder（参考口径，具体阶段为租户可配置）**：
知晓者(Aware，知道未尝试) → 试用者(Trial，偶尔/小样本) → 使用者(User，常规处方) → 先进疗法倡导者(Advocate，主动推荐/参与学术)

**工作流程**：
1. 查当前阶段与标签现状（`hcp.hcp_grade` 及相关字段，以元数据为准）。
2. **观念信号识别**：积极信号 → 提示"从级别 A 提升到级别 B"；消极信号 → 提示回退；已是最高级+积极 / 已是最低级+消极 → 提示"保持不变"；**未识别到变化 → 默认提示"医生观念没有变化"，不强行打标签**。
3. **依据展示（强制）**：必须展示判定依据——语音原文摘要 + 关键句标识。
4. markdown 呈现"当前→建议"对比，**定级变更需用户显式确认并说明依据**；确认 → only_validate 预校验 → 写入（`mutation insert` 语法见 references §1）。
5. **标签动态更新**：标签来源=本次拜访 KM 反馈 + 形式反馈 + 自由文本；类型=学术兴趣/产品态度/处方偏好/沟通偏好；每条变更附变化原因（如"本次提及对儿科适应症感兴趣，新增标签：儿科 AD"）；建议态，Rep 确认后生效、可覆盖 AI 建议；标签数据反哺 PreCall 推荐精准度。

## ③ 行动推荐模块（NBA & NBC）

**目标**：基于最新拜访与画像，给出下一步最佳行动与最佳渠道/内容，理由完整可追溯。

**工作流程**：
1. 取最新相关数据：最近拜访记录 + 渠道偏好 + 内容偏好 + KPI 进度（GQL 组合，禁止直接对 hcp 表按名称模糊查询——先经模块①校准医生 id）。
2. 按规则生成推荐，markdown 呈现：推荐行动、渠道（+渠道理由）、内容/材料（+材料理由）、建议时间（+时间理由）、采纳阶段对齐说明。
3. **推荐日期必须是未来时间且无冲突**（查该医生当天是否已有计划做去重检查；用户修改时间也需重新校验）。
4. **Rep 修改推荐时间的校验**：该医生当天已有当前员工的拜访 → 提示"该医生当天已规划了 XX 渠道的拜访，无需继续新增"，Rep 可选"确认更新"或"取消"。
5. 确认 → 生成拜访计划（转 nges-precall ④ 计划模块），并展示该医生最近最多 3 次拜访（最新在上：1 条新增 + 2 条历史，无历史不展示）。
6. 批量场景：对每位医生依次执行，不要一次性输出所有医生的 NBA 让用户确认。

**红线**：推荐须与采纳阶段和 KPI 缺口对齐，理由引用具体数据。

## ④ 兜底拒答模块

**触发**：意图分类置信度低、不涉及核心意图动作词、多意图混合无法拆解。

**本期仅支持三类开放问题**（其他一律拒答并引导）：
1. **医生相关问题**：基于真实数据动态生成（非论述式）；无数据明确说"看不到记录"，不猜测
2. **产品/学术问题**：RAG 检索（MCP 环境用 GQL 查内容对象降级）；超出范围明确拒答
3. **自动总结输出**：多轮提问后主动生成 3-5 条要点摘要，作为后续拜访准备起点

**拒答提示语示例**："当前本期限于医生相关/产品学术/总结输出三类。您提的问题不在本期范围内，需要我帮你记录拜访吗？"

识别到其实是明确业务意图（录入/更新/NBA/画像/策略/计划）→ 停止作答，回意图路由重新分流。
