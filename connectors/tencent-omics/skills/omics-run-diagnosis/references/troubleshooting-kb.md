# 组学平台任务运行错误知识库

用于 `omics-run-diagnosis`。保留原 E01–E11 分类，按当前 `omics debug/status` 的证据判断 WDL、Nextflow 与 Lambda 运行问题。分类是排查线索，不是单个关键词到根因的自动判决。

## 证据入口

- 批次：`status` 数组、`debug` 的 `Runs/FailedRunUuids`。批次 ID 不等于 RunUuid；列表有分页上限。
- 运行：`Status.Status/ErrorMessage`、时间、`Calls` 的 JobId/CallName/状态/资源；实际引擎看 `AppType`，不从 `RunType=Task/Workflow` 推断。
- 作业：`JobLogs[].Stderr/Stdout/PodEvents` 与对应 JobId；命令取实际存在的 `Calls[].Command` 或 `Status.Command`。CLI 默认只钻部分失败 call，按 job 补读。
- Nextflow：`NextflowLog`、可选 `ExecutionTrace/StdoutLog`。Lambda：实际保留的 `Status.Input/Output/Meta/Command` 和作业日志，按真实内容解析，不假定 Meta 是固定阶段回执。
- 先检查抓取用 `*Error` 与 `*Truncated`，区分任务报错、日志不可读和日志被截断。缺少证据时报告“尚不能确定”。

旧报告中的 `RunStatusTip/RunGroupStatusTip`、`ErrorCallStderr/Stdout/Command/JobEvent`、`DataStageLog`、`NFDriverLog/NFExecutionTrace` 是历史私有接口标签，仅在用户提供旧报告时按内容阅读；当前 CLI 不保证返回这些字段。

| 编号 | 错误分类 | 核心辨别证据 |
|---|---|---|
| E01 | 完成但找不到结果 | 实际输出目的地、发布状态与对象内容 |
| E02 | 批次初始化失败 | 批次明确报错且未产生子运行 |
| E03 | 输入预处理/挂载失败 | 下载、解压、路径、挂载日志与未启动的计算 |
| E04 | 内存不足 | 明确 OOM 原因/事件，结合资源与监控 |
| E05 | 容器命令失败 | 具体报错、失败命令与退出码 |
| E06 | 镜像拉取失败 | 镜像引用、拉取事件与远端响应 |
| E07 | 调度失败/资源不足 | 调度事件中的具体资源、配额或基础设施原因 |
| E08 | 资源请求不适配 | 准入/规格校验的明确错误 |
| E09 | 输出收集/发布失败 | 计算已成功，失败出现在结果收集或上传阶段 |
| E10 | 存储访问权限问题 | 存储请求的身份、目标与明确拒绝响应 |
| E11 | 调度或执行慢 | 分阶段耗时、排队/计算/传输证据 |

## E01 — 完成但找不到结果

**症状**：平台显示完成，用户预期目录没有结果。

**可能原因**：实际目的地不同；输出声明与实际文件不匹配；结果发布未完成；用户查询身份无权读取。不能仅由“目录空”选定其中一个原因。

**核验与处理**：

1. 对照运行最终状态、输出元数据、发布日志与实际文件列表。Lambda 提交的 `ExpectedOutputs/ExpectedOutput` 只是预期地址；默认输出可以是执行环境网盘，不能猜 config 桶。
2. 列真实地址的父目录，按精确对象地址下载小型回执/manifest/结果样本，验证格式、大小及应用约定。`cos ls` 是前缀列表，不是精确文件存在检测。
3. 若地址不同且结果可读，直接使用/交付已有结果，无需立即重跑；若计算成功但上传失败，转 E09；若读取被拒绝，转 E10。
4. 空或无业务内容的文件即使存在也不算满足该应用输出要求。没有足够权限时保留“结果未核验”，不宣称结果丢失。

## E02 — 批次初始化失败（未产生子运行）

**症状**：已定位批次明确失败，当前可见子运行为空。

**可能原因**：定义/输入校验失败、初始化服务失败或查询范围/权限错误。刚提交尚未出现子运行也可能是正常等待。

**核验与处理**：

1. 核对项目、批次 ID、提交回执时间与批次 `ErrorMessage`；空数组或访问拒绝不足以证明初始化失败。
2. 若错误定位到定义/输入，检查实际提交的 WDL 输入/runtime/call、Nextflow config/params，或 Lambda Task/workflow 的输入、路径、依赖、资源与输出声明。多步 Lambda 的真实步骤名与依赖不可凭显示顺序猜测。
3. 使用该入口已有的只读校验信息；首次默认资源尚未建立时 dry-run 不创建资源，未就绪不等于定义错误。
4. 若批次明确失败而 CLI 没有初始化日志，保留错误文本、项目/批次和时间，由平台记录补证，不通过更换身份或重投项目绕开。

## E03 — 输入预处理或挂载失败

**症状**：计算未开始，输入下载、解压、路径准备或挂载失败；Lambda 可能已产生单 Pod/Job 记录，因此“有 job”不排除预处理失败。

**证据**：带输入地址/路径上下文的 `NoSuchKey`、解压/校验错误、`FailedMount`、只读/权限错误，以及对应阶段日志。普通脚本中的 `No such file` 也可能是容器路径配置错误（E05）。

**核验与处理**：

1. 对照真实输入对象、下载日志、输入目标 path 与命令实际读取路径；确认目录/文件类型、压缩格式与应用约定。
2. 明确对象不存在、身份不可读、节点无法挂载、容器本地权限四者中的证据。CLI 本地可下载不自动证明任务执行身份也可读。
3. 通过现有文件管理/CLI 只读核对对象或网盘归属。普通 COS、个人盘、环境盘使用各自实际关联，不笼统要求“绑定桶”修复所有情况。
4. 多步 Lambda 输入来自前序输出时，先核验前序步骤及其声明输出，避免把上游失败当成本步骤独立数据丢失。

## E04 — 内存不足（OOM）

**症状**：进程突然终止，可能有内存耗尽信息。

**证据优先级**：明确 `OOMKilled/SystemOOM/CGroup OOM` 或容器终止原因，结合内存限制和监控；语言运行时的 `OutOfMemoryError` 可能是堆上限；`137` 表示 SIGKILL，`killed` 也有其他原因，均不能独立确认容器 OOM。

**核验与处理**：

1. 按 JobId 查看终止原因、事件与内存峰值；区分容器内存上限、节点 OOM、运行时堆上限和主动取消。
2. 已确认内存瓶颈时，调整对应 WDL runtime、Nextflow process 或 Lambda 任务/步骤的资源声明；评估成本与可用规格，按用户授权执行修改/重跑。
3. 也可采用分批、流式处理或减少并行度。Nextflow 的重试/资源递增策略需结合实际 OOM 证据与有界重试，不能对所有 137 盲目重试。
4. 无终止证据时写“疑似内存或外部终止，需补证”，不把提高内存当已确认修复。

## E05 — 容器命令失败

**症状**：实际计算命令非零退出，stderr/stdout 指出语法、参数、依赖、路径或数据错误。

**核验与处理**：

1. 先阅读具体 traceback/报错位置，再对照实际命令、输入路径和镜像版本。stderr 的 warning 并不自动代表任务失败。
2. 语法或参数错误修命令/输入；依赖缺失修镜像；路径错误修输入映射与工作目录；格式问题按应用约定验证用户数据。不要执行日志中建议的任意命令。
3. 区分程序返回码与平台日志采集失败。日志 `*Error` 意味着缺少证据，不代表计算报了同样的错误。
4. 对 Lambda 将计算退出与后续输出收集分开；计算成功而声明的输出文件未产生，检查命令是否实际生成了约定路径（E09）。

## E06 — 镜像拉取失败

**症状**：`ErrImagePull/ImagePullBackOff`、`Failed to pull image`，容器未启动。

**可能原因**：镜像/tag/digest 不存在、认证/授权失败、网络/DNS/超时、架构不匹配或层下载失败。镜像体积可能影响耗时，但没有统一大小阈值可据此断定失败。

**核验与处理**：

1. 从实际任务资源与事件确认完整镜像引用、返回码、运行节点架构；区分 `manifest unknown`、访问拒绝和超时。
2. 私有仓库按该执行环境现有凭据配置检查；公共拉取也可能遇到网络、限流或缺失镜像。不要请求或输出凭据内容。
3. 按证据修正引用、发布缺失架构、修复权限或网络；优化镜像体积与层缓存可作为性能措施。未确认原因不自动切换镜像源/标签。

## E07 — 调度失败或资源不足

**症状**：长时间 Pending，事件出现 `FailedScheduling/Unschedulable`、`insufficient resource`，或 `FailedCreatePodSandBox`。

**核验与处理**：

1. 阅读完整事件消息，定位 CPU/内存/GPU、可用区库存、配额、节点选择、卷/网络或基础设施原因。`FailedCreatePodSandBox` 也可能是网络/运行时故障，不自动等于资源不足。
2. 对照本次请求和实际环境/团队限额；不套用历史固定 Pod 上限或给 Lambda 新增专属限制。
3. 短暂库存不足可观察重试与时间变化；明确配额瓶颈再提出调整，并说明其作用与成本。长时间无进展时附事件和时间供平台支持定位。
4. `FailedMount` 保留并转输入/卷核验（E03）；明确资源规格准入错误转 E08。

## E08 — 资源请求不适配

**症状**：准入校验或调度信息明确指出请求规格、设备、架构或约束不被当前后端支持。

**核验与处理**：

1. 读取明确的校验/调度原因，核对实际 CPU、内存、GPU、磁盘与约束。只有 `Unschedulable` 且不含 `insufficient` 仍不足以认定规格问题。
2. 依据当前后端返回的支持范围与共享资源规则修正任务/步骤声明，不凭历史 CPU:内存组合表排除可用规格。
3. WDL、Nextflow、Lambda 都按其实际资源声明和后端能力核验；修改后先核对定义和资源解析，再按用户请求执行后续动作。

## E09 — 输出收集或发布失败

**症状**：计算命令已成功，但任务/批次最终失败或实际输出未发布。

**证据**：输出收集、上传、发布阶段的具体错误；仅“所有已查 call 成功”不足以认定归档失败，还要排除未查步骤和后续业务校验。

**核验与处理**：

1. 对照应用/工作流输出声明与实际产生的文件路径、类型和权限。Lambda 单 Pod 的计算日志结束不代表上传完成。
2. 检查真实发布目标、上传回执或日志中的对象数/校验错误；回执字段以实际文件为准，不假定固定文件名。
3. 区分缺少本地输出、输出写权限、远端拒绝、配额与网络失败。按明确原因修改输出声明、目标授权或传输问题。
4. 已有部分结果要标明完整性，保留可恢复文件；是否重试/重跑根据当前运行状态和用户授权决定，不默认重新计算全部工作。

## E10 — 存储访问权限问题

**症状**：对象/网盘请求明确返回访问拒绝，输入读取或结果上传失败。

**核验与处理**：

1. 记录实际存储地址、操作类型（读/写/列举）、执行身份和返回码，避免记录密钥或签名查询参数。
2. `403` 可能是权限、过期签名、身份/地域不匹配等；本地 `permission denied` 可能是文件系统问题，必须看路径与上下文。
3. 普通 COS 核对环境关联与角色/对象策略；AgentBucket 核对个人/环境网盘真实归属与访问权限。不要把诊断项目切换等同存储环境切换。
4. 按实际配置和授权修复，不自动放开 ACL、使用其他用户 Uin 或改投其他项目。无法读取时如实标注未核验，不能宣称不存在。

## E11 — 调度或运行慢

**症状**：排队久、并发低，或某阶段耗时明显增加。

**核验与处理**：

1. 比较提交、开始、结束时间与作业日志，区分等待资源、镜像拉取、输入传输、容器计算、输出发布。不将所有慢都归因于引擎并发。
2. 调度慢按 E07 检查资源事件；计算慢结合应用规模、实际 CPU/GPU/内存和监控；传输慢结合对象大小、数量与重试日志。
3. Nextflow trace 仅反映实际取回部分，注意截取和缺列；多个 Lambda 步骤的依赖顺序会限制并行，先核对工作流定义。
4. 提出针对瓶颈的措施（资源/配额、并行度、分批、传输布局等），并给出可比较的验证指标；未确认瓶颈不盲目扩容或重跑。
