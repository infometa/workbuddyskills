# Lambda 运行与结果验收

本说明用于提交后的取证、结果核验和复用仓库验收记录。CPU 与 GPU 使用相同判定；资源类型不决定是否验收通过。

## 三层结论

| 已有证据 | 可报告的结论 | 仍需完成 |
| --- | --- | --- |
| dry-run 就绪、输入及目标已核对 | 预览通过，尚未执行 | 正式运行 |
| 平台整次 Run 为 SUCCESS | 平台运行成功 | 定义、日志/事件、输出发布与实际产物核验 |
| 定义绑定正确、所有步骤证据齐全、产物通过对应语义校验器 | 本次输入与模式已验收 | 对新数据或其他模式按其要求继续验证 |

请求已接受、计算步骤成功、输出存在和算法结果正确是不同事实。没有校验器记为待验收；校验器与当前入口不匹配记为验收覆盖缺口；确实运行了匹配校验器且断言失败才记语义校验失败。缺本地依赖、读取日志失败也不能直接解释为算法失败。

## 默认无公网与离线证据

官方封装的计算阶段只消费已声明输入与固定镜像内资产。外部数据、权重、MSA、参考库、注释和服务响应在提交端提前准备，保存原 URL、查询或请求、版本、取得时间、大小及 SHA256；软件、字体和包依赖在镜像构建时固定。输入缺失、来源不符或校验失败时直接报错，不在计算容器内下载、安装或联网兜底。替换数据内容时同时替换相应来源清单和指纹；同内容对象仅迁移目录或地域时，保留原始来源清单及其指纹，另记地址映射。

在线查询快照须绑定完整原请求和原响应。离线消费证明复核与后处理，不能写成本次重新查询了服务，或本地实现了服务端全库计算。新数据需要新的服务查询时先完成准备，再传入快照；确实要求实时服务的部分，在技能说明及 GAPS 中明确服务、触发条件和不能离线完成的范围。

| 离线证据 | 可报告的结论 |
| --- | --- |
| 审阅实际默认入口及依赖资产 | 默认入口支持离线设计，尚未独立断网验证 |
| HTTP、DNS、进程 API 拦截下通过输入/输出核验 | 已在该应用拦截范围内验证；不等于容器网络隔离 |
| 平台实跑同一入口并保留拦截、输入、源码、定义和全部输出证据 | 平台应用入口在所声明拦截范围内通过；仍不等于 Pod 网络隔离 |
| 实际禁用计算容器公网并核验完整产物 | 对该镜像、定义及输入具有真实无网执行证据 |

平台在计算前搬运 COS 输入、计算后发布输出，以及客户端准备和查询平台，不属于应用计算访问公网。普通平台 SUCCESS 不能自动升级为离线通过；只看源码中没有 URL 也不足以证明。未验证或尚未采用的新入口单独标为待验证，保留旧运行证据，不重复运行已经验收的科学分析。

## 定义身份和等价比较

1. 保存原 YAML 字节及 SHA-256、覆盖文件/应用参数、项目、环境、RunUuid、RunGroupId 和实际响应。用 `run-definition` 返回的 `SnapshotJson.SourceAudit.rawSha256` 核对服务端收到的提交字节。直接提交且未经 CLI 转换的完整 YAML 可与原文件比较；workflow 使用 `steps[].name` 覆盖，或 CLI 按实际环境地域改写直接 YAML 输入时，服务端指纹对应处理后实际提交内容，应另外保留这份提交字节。不能把它与原 YAML 的 hash 差异误判成源文件被改动；无法取得实际提交字节或服务端证据时，源绑定标记待核实，不能靠本地重建 JSON 自证。
2. 核对冻结 `EffectiveTaskYaml` 或 `WorkflowYaml` 与本次预期的最终定义。若使用 override、应用参数或示例展开，比较合并后的定义，并记录 `EffectiveSpecHash` / `ExecutionHash`；源文件 hash 相同不代表这些运行参数相同。平台托管输入还需按本次实际执行环境核对 [地域适配](cli_commands.md#lambda-托管输入的地域适配)：指定广州源桶的 `inputs[].url` 可替换为北京/上海对应桶，统一目录下 key 不变；仅已核实迁移清单内的旧 key 可在北京/上海目标补 `omics-lambda-apps/`。执行指纹与冻结快照对应替换后的定义，不将这些明确映射误判为原文件被修改，也不据此忽略其他输入差异。
3. 输入和输出以唯一 `name` 作为身份，步骤以唯一 `steps[].name` 作为身份。服务端会排序具名输入输出，并按依赖图规范化步骤顺序。比较名称、完整字段和依赖边，不能直接按 YAML 文本或数组位置比较。
4. 只归一化协议已有的默认值和等价表示。保留命令 argv 顺序、镜像版本/摘要、资源、输入 URL/content/from、输出 type/path/required、步骤引用及依赖。重复名称、缺失节点、未知引用、循环或不能解释的字段差异均不作为已通过。

多步不能只检查最后一步。工作流对外导出的别名与每一步内部输出名可能不同；以冻结运行的步骤与执行计划身份，核对各步发布回执。输出未知、缺失、类型/目标不符或发布失败都不能通过；可选输出只有明确 `SKIPPED` 回执且定义允许省略时才可跳过。

## 取证与真实产物

```sh
omics run-definition --run <RunUuid> --project <本次项目> --format json
omics debug --run <RunUuid> --project <本次项目> --with-stdout -o json
omics cos download <回执中的真实cos地址> <本次新的本地路径>
```

目录输出按 `omics cos download --help` 使用 `--recursive`。使用团队智能体项目时，将上述项目参数替换为本次一致的 `--agent-project`，不要改变目标。

检查各步骤是否有相应日志与事件，区分空 stdout/stderr 与读取失败：CLI 的空字段可能省略，单独的 `StdoutError` / `StderrError` / `PodEventsError` 不能忽略。保留日志截断信息，不把截断片段称为完整日志。

每次下载到新的证据目录，防止旧文件残留造成假通过。核对回执地址、文件清单、大小与 SHA-256，再用应用现有且覆盖本次模式的校验器核验内容。例如样本标识、矩阵维度、有限数值、结构/序列一致性以及步骤间传递校验和。不能为了通过验收放宽科学断言，也不能把文件非空作为所有算法通用的正确性证明。

## omics-lambda-apps 的可复用入口

若当前任务已经取得 `omics-lambda-apps` 仓库，可在该仓库使用其通用平台验收脚本（`<仓库根目录>/validate_platform`）。技能包本身不携带这份仓库，未检出时使用上述原生 CLI，不假定相对路径可用。

这个入口验收应用目录中未经额外 override 或 schema 参数修改的 `lambda.yaml` 示例。脚本当前不接收覆盖文件或合并后预期定义；用户指定了 override、应用参数或另一份 YAML 时，按前文单独核对该次冻结定义和真实产物，不能直接套用默认示例的结论，也不能仅凭原始 YAML hash 相同就视为参数相同。

```sh
python3 "<omics-lambda-apps仓库>/scripts/validate_platform.py" --submit --apps <应用ID列表> \
  --project <项目> --environment <环境> --attempt-id <本轮批次ID> \
  --rerun-success --verify-outputs --evidence-root <本轮新的证据目录>
```

固定批次 ID 用于中断恢复，本批已成功应用不重复投递；提交结果不明时先恢复已保存 token 对应的请求，不新建一单。只补验已有 SUCCESS 记录时省略 `--submit`，不触发新的云任务。具体依赖、退出码和参数以该仓库 README 与脚本 help 为准。

同一应用、版本、YAML 和项目/环境的失败或取消结果默认保留；排除具体原因后，只有显式 `--retry-failed` 才重新投递，`--rerun-success` 不代表允许重试失败。旧定义或其他目标的失败不阻止新定义首次验收。脚本默认逐项串行执行，但单次运行内部仍可能并发上传。

发布错误需按实际类型处理：`UploadConcurrencyLimit` 表示目标桶活跃上传会话达到限制，检查已有上传及其收尾状态；`QuotaLimitReached` 表示本次上传未通过容量配额检查，原因可能涉及已用量、仍预留的上传容量或生效配额，降低并发或等待不保证恢复。暂停继续提交和自动重试，先核实原因；没有可用查询入口时明确记录未查明。计算成功而回执为 `FAILED` / `OUTPUT_TRANSFER_FAILED` 仍是平台发布失败，科学验收尚未完成，不能记为算法失败。

在本次授权范围内，可选择已有环境已关联且验证可用的其他输出桶，显式指定 `--output-prefix`（仓库脚本使用 `--bucket`），先 dry-run，再保存新环境、桶和新 Run 的独立证据；保留旧目标的失败记录。扩容、删除数据或清理上传会话不属于验收脚本的自动恢复动作。

新证据位于 `<omics-lambda-apps仓库>/validation/platform/<app>/<version>.json`，完整验收保存在其中 `acceptance` 及相应 `acceptance/<version>.json`。脚本负责同步 `app.json.validation`，不能手改 `accepted` 代替执行。当前 `cloud`、`note` 和平台待办随该回执同步，旧混合说明保存在 `historical_validation`；历史本地通过不替代当前云端验收。旧 `validation/gpu-platform` 是历史兼容来源，缺少当前定义绑定时不计当前通过。

内嵌验收与独立验收文件是同一次取证的两份副本，跨文件写入不保证原子性。两份都存在时，必须完整一致；结论、时间或下载证据目录不一致均记为 `ACCEPTANCE_CONFLICT`，保留待核实状态，不能任选“通过”的一份或按时间猜测权威来源。只有一份时，仍须通过全部身份和指纹检查；发生冲突应重新取证并同步完整证据。

独立验证器的 `--update-app` 同时写回运行记录（隐含 `--write-record`），且要求 `--record` 指向 `<omics-lambda-apps仓库>/validation/platform/<应用>/<版本>.json`；历史或临时记录可单独取证，不写当前应用状态。这可防止新失败只更新应用元数据而旧通过仍被 runner 缓存复用。runner 遇到冲突或非法验收副本也不复用通过状态；不能通过重新整理元数据消除证据冲突。

应用校验配置 `platform-verifier.json` 声明当前 YAML、结果校验器及参数映射；复杂多步明确绑定 `{output:步骤名.输出名}`，不要靠目录位置猜测。未覆盖当前入口的旧校验器保留为历史能力，当前入口标记待验收。已通过缓存还要核对通用验收器、应用校验器、配置及显式声明的校验依赖文件指纹；依赖不自动按所有 Python import 递归追踪，本地辅助模块应在 `dependencies` 中登记，参数所引用的参考文件用 `{app:相对路径}` 绑定。

通用引擎的 `engine_files` 显式绑定上游仓库的平台运行验收引擎模块；任一文件变化或旧证据缺少这些指纹，都需要按当前规则重新取证。不能仅核对应用自身 checker 就继续复用通过状态。

只有验收器、配置或参考文件变化时，可对原运行重新取证，不必先重跑计算。YAML、实际输入或运行参数变化后，旧 Run 不能证明新定义已验收。
