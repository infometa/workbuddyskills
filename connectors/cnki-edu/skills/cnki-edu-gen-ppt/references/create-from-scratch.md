# 从零构建PPT的教程

## 需求澄清

1. **只问缺失的，文字提问 ≤ 3 个**，一轮问完，禁止多轮追问
2. **风格预览卡按需触发**：默认弹出，但当用户已明确风格偏好、要求快速出稿、或命中预设风格分支时可跳过（详见 [human-alignment.md](human-alignment.md) §2.3）

沟通术语统一用「页 / 封面 / 目录 / 这一页」，不暴露内部实现。

完整对齐逻辑与关键信息优先级见 [human-alignment.md](human-alignment.md)。

## 目录结构规范

每个 PPT 对应一个独立的 `project_dir`，多个 PPT 项目并存于用户的 `workspace_dir` 下：

```markdown
<workspace_dir>/                    # 用户工作目录，可包含多个 PPT 项目
├── <project_dir>/                  # 单个 PPT 的完整工作目录（目录名 = pptx 文件名去后缀）
│   ├── DESIGN.md                   # PPT 视觉设计文档
│   ├── STORY.md                    # PPT 内容叙事文档
│   ├── assets/                     # PPT 页面引用的静态资源文件
│   ├── slides/                     # PPT 页面，即 SlideDSL 源文件（每页一个 .slide 文件）
│   │   ├── 01.slide
│   │   ├── 02.slide
│   │   └── 03.slide
│   └── <pptx_name>.pptx           # 生成的演示文稿
```

命名约定：
- 项目目录名：与 pptx 文件名去 `.pptx` 后缀一致（如文件名 `季度汇报.pptx` → 目录名 `季度汇报/`）。
- 页面文件：`{两位序号}.slide`，如 `01.slide`。
- 资源文件：禁用中文、空格、特殊字符。

## 环境介绍

slidep 已安装到 Node 托管环境中，可直接使用以下子命令（**仅用于生成阶段**；生成完成后的改稿走 [edit-existing](edit-existing.md)，不要再用 slidep / SlideDSL）：

| 命令 | 用途 |
|------|------|
| `slidep create <file>` | 创建空白 PPTX 文件 |
| `slidep upsert-dsl <file> --dsl-file <path> [--page-index N]` | 向 PPTX 插入或替换 DSL 页（替换时须指定 `--page-index`，省略则追加） |
| `slidep lint <file> --dsl-file <path>` | 校验 DSL 页内容（语法与溢出检测） |

## 制定任务计划

> **任务命名约束（强约束）**：本表仅为内部执行参考。在创建 TODO / 任务（TaskCreate）或向用户汇报进度时，**必须使用面向用户的术语**（如「内容大纲 / 风格设计 / 创建演示文稿 / 逐页制作 / 检查页面 / 交付」），**禁止暴露任何内部实现字眼**（如 `JSX`、`DSL`、`*.jsx`、`slidep`、`lint`、`upsert-dsl`、`slidep create`、`OOXML`、`success=true`、源码、组件文件名等）。

| Step | 职责（内部）                                   | 产物（内部）                                 |
| ---- | ---------------------------------------------- | -------------------------------------------- |
| 1    | 信息收集（可选）                               | 背景资料 / 行业数据                          |
| 2    | 需求对齐（轻量确认 + 风格预览卡）              | 关键信息已确认 + 风格参数已锁定              |
| 3    | 依据主题+信息构建PPT的叙述逻辑                 | `STORY.md`                                   |
| 4    | 构建页面风格的设计逻辑                         | `DESIGN.md`                                  |
| 5    | 使用 `slidep create` 创建PPTX，并立即调用 `present_files` 在预览面板中打开呈现给用户查看 | 目标 `.pptx` 已创建并打开                    |
| 6    | 逐页生成 PPT（按大纲顺序，每页循环：如需生图则先生成本页所需图片 → 写页面 → `slidep lint` 单页校验 → 修复直到通过 → `slidep upsert-dsl` 写入，循环至全部页面完成） | 全部页面已生成并写入                         |



## 各步骤要求
### Step1：信息收集 （Optional）
当模型的信息不足、数据过时或需要行业标杆案例时，主动调用网络搜索的工具进行信息的收集，挖掘有深度、有据可查的实时内容。
判断信号：
- 主题涉及 `数字 / 市场 / 行业 / 新闻 / 分析` 等具有时效性的信息时 → 需要最新统计数据。
- 主题含`陌生缩写 / 专业术语 / 生僻词组` → 先查清楚。
- 用户明确要求 或 用户需要要“有说服力”但未提供素材 → 补充外部佐证。

若用户已提供完整参考材料（长文本、`.docx`、`.pdf` 等），本步可跳过或降级为只查陌生概念。

### Step2：需求对齐
按 [human-alignment.md](human-alignment.md) 执行。要点：
- 能推断就推断，文字提问 ≤ 3 个
- 风格预览卡按需触发（详见 human-alignment.md §2.3 的跳过条件）
- 无论预览卡是否触发，进入 Step3 前必须确保风格参数已确定（用户选定或 AI 推导）
- 对齐结果中的主题/目标 → 作为 Step3 构建叙事的输入
- 对齐结果中的风格参数（色板/字体/密度基线）→ 作为 Step4 设计阶段的硬约束

### Step3：构建叙事逻辑 （STORY.md）
阅读 [story-principle.md](story-principle.md)，最后生成一个STORY.md的文件。

### Step4：构建页面风格的逻辑 (DESIGN.md)

#### 风格匹配流程

收到用户需求后，执行以下推理判断是否命中预设风格：

**第一步：提取用户意图特征**
从用户 query 中识别：主题领域、目标受众、使用场合、调性倾向。

**第二步：与预设风格比对**

| 风格 | 核心调性 | 适用场景 |
| :--- | :--- | :--- |
| 学术风 | 可信、证据驱动、蓝白克制 | 高校答辩、科研结题、教学课件（理工医）、学术会议、学科评估、临床/医学汇报、课题开题、实验室组会、科研申报 |
| 商务咨询 | 权威、数据密集、结构化分析 | 战略/行业研究、高管 review/董事会、投行/IPO 路演、咨询交付物、企业转型/组织变革、私募/风投/行研、尽职调查 |
| 红金政务风 | 庄重、红金热烈、中文优先 | 党政机关汇报、政务/公共部门、国企央企汇报、党课/学习宣讲、周年庆典/红色文化、表彰大会、纪检巡察 |

**第三步：做出判断**

判断标准：用户的场景是否**明确属于**上表某风格所服务的特定领域和受众。

- **命中**：用户场景明确落在某风格的适用场景内 → 使用该预设风格；
- **不命中**（默认路线）：用户场景不属于上述三类特定领域，或场景模糊/泛化/跨领域 → 走通用设计原则；

> ⚠️ **重要原则**：预设风格是为特定垂直领域定制的，不应泛化使用。大量常见场景（如：产品介绍、项目提案、工作总结、培训课件、技术分享、营销方案、团队介绍、述职报告、年终总结等）都应走通用设计原则，由 AI 根据具体需求自由设计。只有当用户场景**明确且典型地**属于学术科研、专业咨询、或党政红色这三个垂直领域时，才使用预设风格。

**判断示例**：
- "做一个硕士毕业答辩PPT" → 明确属于学术场景 → 命中学术风 ✅
- "做一个麦肯锡风格的行业分析" → 明确属于咨询场景 → 命中商务咨询 ✅
- "做一个党支部年度工作汇报" → 明确属于党政场景 → 命中红金政务风 ✅
- "帮我做个述职报告" → 职场通用场景，不属于上述三类特定领域 → 走通用 ✅
- "做一个产品发布会PPT" → 产品/营销场景 → 走通用 ✅
- "做一个季度工作总结" → 职场通用场景 → 走通用 ✅
- "做一个AI技术分享" → 技术/科普场景 → 走通用 ✅

#### 匹配后的执行

- **命中预设风格**：以[通用设计原则](design-principle.md)为骨架，按上表该风格的调性（色彩倾向、信息密度、装饰尺度）落地，结合用户实际需求设计PPT，**禁止额外生成DESIGN.md**，可以显式声明哪些颜色、字体等内容需要结合用户需求微调；
- **不命中（默认路线）**：读取通用[设计原则](design-principle.md)，结合用户实际需求生成DESIGN.md；


### Step5：创建 PPTX 文件并打开预览

> **本步是硬约束**：进入逐页生成前，必须完成 `slidep create` 创建目标 `.pptx`。如下是运行要求：
>
> 运行 `slidep create "<project_dir>/<filename>.pptx"`，创建空白 `.pptx` 文件。
>
> **文件名命名约束**：`.pptx` 文件名默认使用中文（如 `"季度汇报.pptx"`、`"项目提案.pptx"`），只有在用户明确要求英文文件名时才使用英文。
>
> **打开预览（硬约束）**：`slidep create` 成功后，必须**立即调用 `present_files` 工具**将该 `.pptx` 在预览面板中打开呈现给用户查看，确保在后续逐页制作过程中就能实时看到渲染效果。这是必须的启动动作，不得推迟到最终交付阶段，也不得仅在回复文字中说明而不实际调用 `present_files`。


### Step6：逐页生成 PPT（按大纲顺序）
> 动笔前的心智校准：每一页是一个 `.slide` 文件，但**它不是 React**——这是一套受限 DSL，工程直接编译成 OOXML（.pptx）。把它当 HTML + 内联 CSS 来写。禁止引入 React 生态任何概念（`import` / `export` / `module` / hooks / state / 函数组件定义），文件最后一个表达式必须是 `<Slide>`。
>
> 动笔前必读：
> - `STORY.md` - 当前PPT的叙事逻辑
> - `DESIGN.md` — 当前 PPT 的设计稿（画布、配色、字号、布局、元素、密度）
> - 相关组件规范 — 本页用到哪个组件，就读取 `references/component-*.md` 中对应文档
>
> **动笔前禁读**：本项目目录之外的任何 PPT 项目源码（详见 §Step 5 设计依据封闭原则）。本页 JSX 的全部依据应来自 `DESIGN.md` + 命中分支 `design-principle.<id>.md` + `component-*.md`，不得"借鉴"历史项目的 jsx 写法或视觉选择。
>
> 严禁仅靠记忆动笔。

约束如下：
- 充分结合 `STORY.md` 和 `DESIGN.md`，按照大纲顺序从第 1 页生成到第 N 页，一次写完全部页面；
- 配图前置（仅限当前页）：每页动笔前，先生成**本页**所需的图片，完成视觉检查（清晰、无水印、符合上下文）后再写该页内容；**禁止一次性生成全部页面的图片后再开始写页面**；
- 写入页面源文件： write_to_file 到 slides/{NN}.slide；
- **写完立即校验（硬约束）**：每页写完后先跑单页校验，校验通过才提交：
  ```bash
  slidep lint "<pptx路径>" --dsl-file "slides/{NN}.slide"
  ```
  若校验未通过，根据 `error` 字段修复 `.slide` 文件后重新校验，直到通过为止；
- **校验通过后立即提交（硬约束）**：校验通过后，必须立即运行 `slidep upsert-dsl` 将该页写入 `.pptx`：
  ```bash
  # 追加新页（--page-index -1 或省略）
  slidep upsert-dsl "<pptx路径>" --dsl-file "slides/{NN}.slide"
  # 替换已有页（--page-index 为 0-based 页序号）
  slidep upsert-dsl "<pptx路径>" --dsl-file "slides/{NN}.slide" --page-index <N>
  ```
  返回 `{ ok: true, ... }` 才继续下一页；返回 `{ ok: false, error }` 须根据错误信息修复当页 DSL、重新校验通过后再提交；
- 动笔自检（每页提交前 10 条硬约束，逐项确认；任意不通过 → 当页返工） 
  - 母版区齐全：默认三区（A 标题块 0–120px / B 内容区 120–660px / C 页脚条 660–720px 含右下页码 NN/TOTAL）； 
  - 标题块右侧不得塞装饰小图（200×70 这种），全篇位置严格一致； 
  - 本页 L1 主视觉占 B 区面积 ≥ DESIGN.md 规定（默认 30%）；不得用 L3 角标顶替 L1 
  - 仅使用项目 DESIGN.md 列出的 ≤ 4 种 hex 与 ≤ 2 套字体家族 
  - 与上一页版式不重复；本页留白比例 ≤ DESIGN.md 上限（常规页 ≤ 35%） 
  - 本页有 ≥ 1 个视觉锚点（≥ 44px 元素 或 ≥ 40% B 区面积的图）；如无 → 必须补充巨型数字/大图/大色块 
  - 本页与上一页视觉重量有显著差异（最大元素面积比 > 1.5:1 或版式结构明显不同）；连续 ≥ 2 页等宽卡片横排 → 返工 
  - 本页色彩分配符合 DESIGN.md 页面映射表：强调色只出现在焦点元素上，主色/辅色/强调色面积比合规 
  - 本页的 role 与 STORY.md 一致：hero 页必须有 ≥ 40% B 区主视觉或 ≥ 48px 锚点数字；supporting 页不得使用 hero 级视觉投入
