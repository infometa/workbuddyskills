# 企鲸客SCRM（WeCom Qijingke SCRM）

## 概述

本 Connector 通过 6 个 MCP Tool 实现与 企鲸客SCRM 开放平台的交互。MCP Server 在连接时会下发全局规则（instructions）；本文件补充工具说明、沟通口径与错误处理，调用规则与流程以 instructions 为单一真源。

> 本文件与 MCP Server instructions 规则一致，如有冲突以 instructions 为准。

## 可用工具

### get-identity — 获取身份

获取当前身份，验证 SCRM_APP_KEY 是否有效，返回用户与角色信息。这是所有操作的第一步，必须在调用其他工具前先执行。

**参数**：无

**返回**：`data.userId`、`data.userName`、`data.role`（admin / dept_admin / staff）、`data.roleDescription`、`data.mainDeptId`（本人主部门 ID）、`data.deptIds`（本人归属部门 ID 列表，未分配时为空数组）。

### search-apis — 接口搜索

按关键词模糊搜索可用的 SCRM API 目录（匹配接口名称、别名、描述与分类）；关键词留空则列出全部接口。调用前必须先通过 fetch-url 阅读远程接口目录。可多次调用不同关键词以覆盖目标接口。

**参数**：

| 参数    | 类型   | 必填 | 说明                                             |
|---------|--------|:----:|--------------------------------------------------|
| keyword | string |  -   | 搜索关键词，多个关键词用逗号分隔；留空则列出全部 |

**返回**：`{ success, data: { total, records } }` 结构，records 中每条记录包含 apiName（接口名称）、description（描述）、docUrl（文档地址）。

### fetch-doc — 读取接口文档

获取指定接口的完整文档内容，包括接口说明、字段清单（FIELD_INPUT_SPEC）与业务参数数据来源说明。这是 call-api 的前置条件，未阅读直接调用会报错。

**参数**：

| 参数    | 类型   | 必填 | 说明                                    |
|---------|--------|:----:|-----------------------------------------|
| docUrl | string |  ✅  | 接口文档 URL，从 search-apis 返回结果获取 |

**返回**：`data.content` 为文档正文，含 FIELD_INPUT_SPEC 行（字段名、类型、必填、枚举）与「业务参数数据来源说明」。字段名与类型以 FIELD_INPUT_SPEC 为准；服务端用同一份 spec 做最终硬校验，未声明的参数会被整单拒绝。

### call-api — 调用接口

调用指定的 SCRM API 接口。前置条件：必须先调用 fetch-doc 阅读该接口文档。

**参数**：

| 参数       | 类型   | 必填 | 说明                                                           |
|------------|--------|:----:|----------------------------------------------------------------|
| docUrl    | string |  ✅  | 接口文档 URL，从 search-apis 返回结果获取                      |
| bizParams | string |  -   | JSON 格式的业务参数，字段参考 fetch-doc 返回的文档，默认 `{}` |

**返回**：包含 data.response（接口响应数据）、data.isWrite（是否写操作）、data.apiName（接口名称）。

### upload-file — 上传文件

上传本地文件到 SCRM 平台，返回公网访问 URL 和 fileId。适用于某些接口需要传入图片或文件 URL 的场景。

**参数**：

| 参数      | 类型   | 必填 | 说明                 |
|-----------|--------|:----:|----------------------|
| filePath | string |  ✅  | 本地文件的绝对路径 |

### fetch-url — 读取远程内容

读取远程 URL 的文本内容。首次调用 search-apis 前必须先使用本工具阅读远程接口目录；也可用于读取 Markdown 等远程文本内容。

**参数**：

| 参数 | 类型   | 必填 | 说明                                                       |
|------|--------|:----:|------------------------------------------------------------|
| url  | string |  ✅  | 文档名（`CLAW_SUMMARY.md`）、文档相对路径（`user/xxx.md`）或完整 URL |

**说明**：文档名与相对路径会按当前部署的服务地址自动补全，**不要自己拼域名或猜主机**；读取用户提供的第三方地址时照原样传即可。文档不存在（4xx）返回 `CONTRACT_ERROR`，不要重试。

**返回**：`data.url`（最终 URL）、`data.content`（文本内容）、`data.truncated`（是否被截断）。

## 用户沟通口径

对普通用户回复时，默认使用业务语言和结果导向表达，不要主动使用过多技术术语。

1. **默认不用技术词堆砌**：除非用户主动追问，否则不要直接说 docUrl、bizParams、JSON 等术语。
2. **先说能帮用户做什么**：优先说"我先帮你看看""我来帮你查一下"，再说明还需要用户补充什么。
3. **权限提示说人话**：不要直接说 `role` 的取值（admin / dept_admin / staff），改为"你当前可以看团队数据"或"你当前只能看自己的数据"。
4. **参数收集说业务信息**：不要说"请提供 bizParams"，改为"还需要补充时间范围、客户名称、标签等信息"。
5. **反馈结果先讲结论**：查询成功时先总结查到了什么；失败时先说发生了什么和下一步怎么办。
6. **用户看不懂的内部信息不主动暴露**：接口路径、服务名、文档地址仅在用户明确要求时展示。
7. **查询结果回显实际条件**：反馈时将实际传给接口的所有业务筛选条件用用户能理解的方式列出，尤其是时间范围、员工/部门名称、标签名等。示例："帮你查了 2026-04-28 至 2026-05-28（最近一个月）、归属员工「张三」、标签「VIP客户」的客户数据，共找到 32 条"。

### 推荐话术示例

| 场景           | 推荐话术                                                                     |
|----------------|------------------------------------------------------------------------------|
| 查询前         | 我先帮你看一下                                                               |
| 继续追问       | 还需要你补充一下时间范围 / 客户名称 / 标签信息，我再继续帮你查               |
| 凭证未配置     | 你这边还没有完成 企鲸客SCRM 授权，需要先获取 APP KEY 后我才能继续帮你查   |
| 普通员工查团队 | 你当前只能查看自己的数据，团队数据这边暂时查不了                             |
| 越权调用       | 你当前的角色暂时没有这个权限，无法执行；我可以帮你做 XXX（给出可行替代）   |
| 查询失败       | 这次没有查成功，我把原因和下一步怎么处理跟你说一下                           |
| 查询结果反馈   | 帮你查了 [时间范围]、归属员工「[姓名]」、标签「[标签名]」的数据，共找到 N 条 |

## 调用流程

调用步骤（Step 1 get-identity → Step 2 fetch-url → Step 3 search-apis → Step 4 fetch-doc → Step 4.5 对话收集业务参数 → Step 5 call-api）以 MCP Server 下发的 instructions 为单一真源，本文件不复述步骤编号，避免与 instructions 漂移。

要点：

- call-api 之前必须先调用 fetch-doc 阅读文档；未阅读直接调用会返回 DOC_READ_REQUIRED 错误。
- 首次调用 search-apis 前，必须先使用 fetch-url 阅读远程接口目录 CLAW_SUMMARY.md。**直接传文档名即可**（如 `fetch-url(url="CLAW_SUMMARY.md")`）：工具会按当前部署的服务地址自动补全，不要自己拼域名或猜主机。
- 需要来自前置接口的参数（如 ID 类值）时，回到 search-apis 查找前置接口并依次执行。
- upload-file 和 fetch-url 可在任意步骤中按需使用，不受顺序限制。

### 接口匹配规则

- 匹配到唯一接口时直接使用，无需询问用户。
- 匹配到多个候选接口时，列出候选项让用户选择。
- 无法匹配时，告知用户当前无匹配接口。

## 身份与权限

get-identity 返回的角色为三档：`role` 是机器判定值（`admin` / `dept_admin` / `staff`），`roleDescription` 是它的展示文案。判定以 `role` 为准，对用户表述用 `roleDescription`：

- **管理员**默认使用团队视角，可查看全部数据。
- **部门管理员**可查看其管理部门子树（含本人）的数据。
- **普通员工**只能使用个人视角，仅能查看自己的数据。

可调用的接口由**服务端按角色授权**：search-apis 返回的目录已是当前角色可调用的接口集合，AI 无需自行判断；越权调用会返回 PERMISSION_ERROR，且不要重试。

### 本人部门

get-identity 同时返回 `mainDeptId`（本人主部门 ID）与 `deptIds`（本人归属部门 ID 列表），与角色无关，管理员也返回。

- 用户问「我在哪个部门」「我部门有哪些员工」时，直接用 `mainDeptId` / `deptIds` 作为部门 ID 去查，**不要用搜索接口反查自己**：搜索接口按姓名或员工 userid 模糊匹配，姓名与 userid 不同名时会搜不到，从而误判成「查不到我的部门」。
- 手上只有某个员工的 userid 时，可以先「批量根据员工ID查询员工信息」拿到 `depart_ids` / `main_department`。
- 普通员工即使拿到了部门 ID，也仍然不能查询组织架构（见下方限制二）：此时如实告知「当前角色不能查询组织架构」，不要尝试其它接口绕过。

### 普通员工操作限制

**限制一：禁止指定其他员工**

普通员工只能操作自己的数据，不能将接口参数中的员工相关字段指定为其他员工。服务端数据范围亦会兜底（普通员工仅本人）。

强制检查流程：

1. 查看 get-identity 返回的 userId 和 userName。
2. 检查业务参数中是否包含员工名称、员工ID相关参数（如 userIds、addUserIds、staffId 等）。
3. 如果包含，此类参数必须且只能是 get-identity 返回的 userId 或 userName。
4. 如果用户要求使用其他员工，必须拒绝执行并告知"您的身份是普通员工，只能操作自己的数据（{userName}），无法指定其他员工"。

示例：用户说"创建活码，使用员工=张三"，但 get-identity 返回 userName=李四 → 张三≠李四，拒绝执行。

**限制二：禁止调用员工/部门搜索接口**

普通员工无权搜索企业组织架构。员工&部门分类下的搜索接口，以及任何用于获取员工列表、部门列表、组织架构树的接口，普通员工均不得调用——**服务端会对普通员工直接拒绝（PERMISSION_ERROR）**。

### 数据范围参数说明

不同接口用于区分团队/个人的参数名和枚举值各不相同，必须通过阅读文档确认，不得自行猜测或复用其他接口的值。

## 接口间数据依赖

docUrl 文档中的「业务参数数据来源说明」描述了每个参数的值从哪里获取。AI 组装业务参数（bizParams）时，必须先识别依赖关系，按正确顺序调用前置接口获取参数值。

### 参数来源识别表

| 来源描述                           | AI 行为                                |
|------------------------------------|----------------------------------------|
| 「对话收集」「用户输入」           | 通过对话向用户收集                     |
| 「XX 接口返回数据中的 field 字段」 | 必须先调用前置接口获取，再用返回值填充 |
| 「预设枚举值」                     | 根据用户意图从固定选项中匹配           |
| 「展示选项让用户选择」             | 先调接口获取选项列表，让用户选择       |

### 典型场景：按标签名查客户

用户说"查一下有多少客户打了高意向客户标签"，正确做法：

1. search-apis 搜索"客户列表" → 找到「客户列表分页查询」
2. fetch-doc → 发现 tagIds 参数依赖「获取客户标签列表」接口
3. search-apis 搜索"标签" → 找到「获取客户标签列表」
4. call-api 调用标签列表接口，匹配标签名，提取 tagId
5. 将 tagId 填入 tagIds 参数，调用客户列表接口

> **错误做法**：直接猜测或构造 tagId 去查询。对于来源为其他接口的字段（如 tagId、userId、deptId），绝不能凭用户输入的名称自行构造，必须通过前置接口查询获取真实值。

## 写操作限制

1. call-api 返回结果中 data.isWrite: true 表示该调用为写操作（新增/修改/删除）。
2. 写操作执行前，必须等待用户明确确认后再调用 call-api；读操作可直接执行。
3. 写操作失败或超时后，禁止自动重试，必须告知用户失败原因，由用户决定是否重试。
4. 读操作（查询类）不受此限制。
5. 少数读接口在读取时会推进服务端状态（例如「会话分析结果」轮询会更新分析进度，并在特定分析类型下写入客户标签）：接口文档的「约束」段会写明，按文档提示在用户确认后使用。
6. 轮询类读接口超时后，重试同一个读接口，不要改用写接口（例如轮询分析结果超时后，不要重新创建分析）。

## 分页数据完整性

本节适用于所有返回分页结构的接口，不限于特定业务模块。

### 任务类型判断表

| 任务类型 | 触发关键词示例                     | 数据遍历要求             |
|----------|------------------------------------|--------------------------|
| 分析类   | 分析、统计、排名、汇总、趋势、占比 | 需全量遍历               |
| 列举类   | 列出全部、导出、完整列表           | 需全量遍历               |
| 查询类   | 查找、搜索、有没有                 | 找到可提前终止，标注比例 |

### 规则一：数据量超过 5000 条时的强制协商（最高优先级）

分页接口首次调用后，若任务要求全量或大面积遍历且总记录数超过 5000 条，必须先暂停并与用户协商，禁止直接全量遍历。

向用户反馈时，不暴露内部阈值，只描述实际数据量和选项。给出以下选项供用户选择：

- **全量分析**：继续翻页获取全部数据后再分析（最准确）。
- **缩小筛选条件**：增加时间范围、关键词等过滤条件减少数据量后重新分析。
- **抽样分析**：基于已获取的部分数据进行分析，必须在报告中标注样本比例（如"本次分析基于前 230/2094 条数据，占比约 11%"）。

> 对外沟通约束：向用户反馈时，禁止提及内部阈值数字，只描述实际数据量大小和选项。

### 规则二：分析类/列举类任务必须遍历全部页面

- 必须遍历全部页面后才能输出结论，禁止仅读前几页就输出全局性结论。
- 禁止使用"所有""全部""整体"等全称量词，除非已遍历完所有页面。

**禁止行为：**

- 仅读前 1~3 页就输出全局性结论（如"90% 是系统噪音""大部分都是 XX 类型"）。
- 将部分数据的统计结果作为整体结论呈现。
- 在未遍历完所有页面的情况下使用"所有""全部""整体"等全称量词。

### 规则三：查询类任务的标注要求

- 允许在找到目标后提前终止。
- 必须标注已查看的数据量比例（如「已查看前 3 页，约 300/5000 条」）。
- 禁止在只查了部分数据时使用"没有找到""不存在""查不到"等全称否定结论。

### 数据量硬上限

总记录数超过 50000 条时，必须告知用户实际总量和本次最多查询的条数。后续分析结论中必须标注数据覆盖比例。

## 错误处理

工具调用失败时，返回结果带 `isError: true`，正文是一段 JSON：

```json
{"success": false, "code": "错误码", "message": "中文说明", "details": {}}
```

必须先读 `code` 再决定动作。`details` 可能带被截断的原始响应（`truncated: true` 只保留了预览），但 `details.hint` 永远不会被截断——它是平台准备好的、可直接转述给用户的下一步动作，有 hint 时照它说，不要自己编操作步骤。成功结果的正文是 `{"success": true, "data": {...}}`，两者用 `success` 字段区分。

| 错误码                                | AI 处理方式                                         |
|---------------------------------------|-----------------------------------------------------|
| DOC_READ_REQUIRED                     | 先调用 fetch-doc 阅读文档再重试                     |
| VALIDATION_ERROR / PATH_PARAM_MISSING | 重新阅读文档调整参数，不要盲目重试                  |
| AUTH_ERROR                            | access_token 失效，客户端已自动刷新并重试过一次；仍失败时说明连接异常、稍后再试。不等于"查无数据" |
| CREDENTIAL_INVALID                    | APP KEY 本身不可用（填写有误、已被重置，或被管理员停用）。不可重试，换一种调用方式也不会成功。把 `details.hint` 用业务语言转述给用户，并说明需要更新 APP KEY |
| TENANT_BLOCKED                        | 企业状态异常（到期/未授权）。不可重试；让用户找企业管理员处理，不要让用户重填 APP KEY |
| PERMISSION_ERROR                      | 当前角色无权调用该接口（服务端接口级授权拒绝）。不要重试，用业务语言说明权限不足 |
| CONTRACT_ERROR                        | 接口目录与文档不一致（缺 spec、docUrl 对不上等）。重试无用，告知用户该功能暂不可用 |
| NETWORK_ERROR                         | 网络异常或响应非 JSON，请求未到达业务层；读操作可重试，写操作先确认 |
| SERVER_ERROR                          | 服务端处理这次请求时内部出错，与入参无关。**不可重试**：换参数、换关键词都不会成功。把 `details.hint` 用业务语言转述给用户，然后停在这一步 |
| SCRM_API_ERROR                        | 用业务语言转述原因，询问用户是否调整条件            |
| CONFIG_ERROR                          | 用业务语言说明缺少什么配置，引导用户完成下一步      |
| INTERNAL_ERROR                        | 未归类的客户端异常。不要把原文抛给用户，用业务语言说明并建议稍后重试 |

补充说明：

- 仅 SCRM_API_ERROR 且用户主动要求时才重试；其他类型错误优先修复根因。
- 只有 NETWORK_ERROR（读操作）和 AUTH_ERROR 允许主动重试；其余错误码要么修根因，要么直接告知用户。
- 同一接口连续失败两次且 `code` 相同，就必须停下来把情况告诉用户，不得把「改参数再试一次」当成探索手段。
- AUTH_ERROR、CREDENTIAL_INVALID 和 VALIDATION_ERROR 都不能被解释为"空结果"或"无此数据"。
- CREDENTIAL_INVALID 与 TENANT_BLOCKED 都**不可重试**，但下一步不同：前者是「用户重填 APP KEY」，后者是「找企业管理员续费/授权」。不要把两者混为一谈。
- PERMISSION_ERROR 表示角色权限不足，**不可重试**，直接告知用户并给出可行替代。

## 参数收集标注含义

文档中的参数标注，AI 必须严格按对应行为执行：

| 标注               | AI 行为                              |
|--------------------|--------------------------------------|
| 必须对话收集       | 执行前通过对话明确获取，不得自行推断 |
| 展示选项让用户选择 | 列出所有选项含默认推荐，等用户选择   |
| 展示默认值后确认   | 告知默认值，询问是否修改             |
| 默认值：xxx        | 展示默认值，用户无需主动回复         |
| 可选               | 用户未提及时跳过                     |

## APP KEY 获取方式

如提示凭证无效或需要更新，请前往：企业微信 → 工作台 → 企鲸客 → 企业管理 → 我的 APP KEY，获取后在工作空间连接器设置中更新。

APP KEY 永久有效，只有本人重置或被管理员停用才会失效：

- 本人重置：旧 KEY 立即失效，用新 KEY 替换即可。
- 被管理员停用：重填同一把 KEY 不会恢复，需要管理员先解除停用。
