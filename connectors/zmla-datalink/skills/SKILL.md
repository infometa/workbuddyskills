# 数脉通 ZMLA DataLink

## 选择工具与查询范围

先读取客户端发现的工具清单及各工具的 `description`、`inputSchema`，据此选择与问题直接相关的工具。工具由服务动态提供，不固定数量，不编造工具名称、参数或未开放的能力。

按下表确定查询方向，并只使用当前清单中明确支持对应能力的工具：

| 用户需求 | 选用方向与适用场景 |
| --- | --- |
| 核实企业身份、了解企业概况 | 工商基本信息；先核对企业全称、统一社会信用代码等返回标识，避免同名误判。 |
| 了解企业人员或股权关系 | 主要人员、股东、对外投资等对应查询；按用户问题选择，不默认展开全部关联企业。 |
| 排查合作方风险 | 与问题相关的经营异常、行政处罚、司法案件、被执行、失信等对应查询；区分不同风险类型。 |
| 供应链尽调 | 先确认供应商或客户主体，再按关注点查询其工商、经营和司法信息；不要把工商关联直接解释为供应或交易关系。 |
| 企业研究或比较多家企业 | 对各主体使用可比较的查询维度，分别记录查询范围和时间；工具未提供的数据明确标为未查询或不可得。 |

某类能力不在当前工具清单中时，说明可用范围，不调用名称相似但用途不符的工具。用户只询问已有结果时，先复用本次会话中可用的数据，避免无必要的付费重复查询。

## 参数填写

- 严格使用所选工具声明的参数名、类型、必填项、枚举和分页规则；各工具的业务参数可能不同。
- `keyword` 仅用于声明了该参数的工具。按该工具说明填写企业名称、统一社会信用代码或其他支持的检索值，不假定所有工具都支持同一种输入。
- 企业简称或模糊名称匹配到多个主体时，先结合用户给出的地区、全称或信用代码确认目标，再查询其风险数据；缺少关键信息时向用户澄清。
- `idempotency_key` 和 `include_field_descriptions` 与业务参数放在同一层，不额外包装为 `params`，不放入 `keyword` 或业务对象内。

例如，只有当工具明确支持 `keyword`，且其余必填业务参数已补齐时，可按以下形式构造工具参数。示例中的企业名称和幂等键仅作格式展示，实际调用时替换：

```json
{
  "keyword": "待查询企业全称",
  "idempotency_key": "query-20261022-8c6ba270",
  "include_field_descriptions": true
}
```

## 计费与幂等重试

业务查询会按用户应用的计费规则执行。不要承诺免费、固定单价或包月包含；以平台配置及调用结果中的 `fee` 为准。多主体、多工具或翻页会形成多次调用，在执行前向用户说明拟查询的范围和可能产生的费用；范围不明确时先确认。

每次新的业务调用生成新的 `idempotency_key`，建议使用 UUID。该值必须为 8–128 个字符，只允许英文字母、数字、`.`、`_`、`:`、`-`。

- 同一工具、同一业务请求因超时或网络中断重试时，保留原业务参数和原幂等键，不因未收到结果而换键重新查询。
- 改企业、改筛选条件、改页码或明确重新查询最新数据，都属于新请求，应生成新键；不要跨工具复用同一个键。
- `request_in_progress` 表示原请求仍在处理，稍后使用原键、原参数重试，避免并发重复请求。
- `idempotency_conflict` 表示同一键对应了不同业务参数；先检查原请求。若确实需要新查询，再使用新键，不通过换键盲目绕过报错。
- 已完成调用可返回历史结果，并以 `idempotency_replayed: true` 标识重放；不要将重放结果描述为刚刚刷新取得的数据。
- 已记录的上游失败也可能被重放，复用原键不会重新向上游查询。确需重新执行时，应先说明可能再次计费，再作为新请求处理。
- 幂等机制用于防止同一次请求重复执行，不意味着所有调用免费，也不意味着更换幂等键后仍可免于再次计费。

## 字段说明与结果解读

`include_field_descriptions` 为布尔值，默认 `false`。当前会话首次调用某个工具、尚未取得字段说明，或用户询问字段含义时设为 `true`；已掌握字段含义的重复调用可设为 `false`。该开关不发送给上游数据供应商。

优先读取 MCP 返回的 `structuredContent`；若客户端只展示文本，则解析其中的 JSON。先检查 `success`，失败时不要将返回内容作为成功查询结果。

| 字段 | 使用方式 |
| --- | --- |
| `mapped_response` | 业务数据，以实际结构为准；不同工具的返回字段不同。 |
| `field_descriptions` | 请求字段说明且业务成功时附加的说明映射。路径相对于 `mapped_response`，`.` 表示嵌套层级，`[]` 表示数组元素，例如 `items[].name`。 |
| `fee`、`balance_after` | 本次结果返回的费用和余额信息；保留原币种、单位与精度，不自行推测。 |
| `request_id` | 查询追踪标识，可用于问题排查；不要将其视为企业标识。 |
| `error_category`、`message` | 失败类别与说明，用于决定修正参数、停止调用或重试。 |
| `idempotency_replayed` | 为 `true` 时表示复用历史结果。 |

字段说明未提供单位、枚举含义或时间口径时，不凭字段名猜测。确需补充说明时，可使用原业务参数、原幂等键并设置 `include_field_descriptions: true` 再取结果；服务当前只对业务参数进行幂等冲突校验。

## 常见失败处理

| 失败类别 | 处理方式 |
| --- | --- |
| `payload_invalid` | 对照工具输入定义修正参数；业务参数改变后使用新幂等键。 |
| `app_unavailable` 或连接鉴权失败 | 提示用户检查连接器中的 MCP Key 和应用状态，不索要或回显密钥。 |
| `api_unavailable` | 说明当前接口不可用；可刷新工具清单核对，不用其他接口名猜测替代。 |
| `balance_not_enough` | 提示余额不足并停止付费查询，交由用户处理。 |
| `request_in_progress`、`idempotency_conflict` | 按上述幂等规则处理。 |
| `upstream_failed`、`system_error` 或网络超时 | 保留原幂等键和参数，结合错误说明判断是否稍后重试；持续失败时停止，记录 `request_id` 供排查，避免无限重试或换键重复扣费。 |

## 输出分析结论

先给出与用户问题相关的查询事实，再说明据此形成的判断。列明企业主体、实际查询维度，并在返回数据包含日期时注明对应日期；区分数据日期与本次查询时间。

“返回为空”“未查询该维度”“接口失败”与“未发现记录”是不同情况。未查到风险记录不等于企业没有风险；被执行、失信、案件记录等也不能相互替代。合作建议应写明证据与查询范围，避免仅凭单项记录给出确定性承诺。
