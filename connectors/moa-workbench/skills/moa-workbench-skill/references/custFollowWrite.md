# 跟进写入场景

用于销售在拜访/通话结束后口述经过：AI 提取沟通时间、方式、对象、需求、结果、问题和下一步动作，生成**跟进记录、阶段变更、回访提醒**三份草稿；用户确认后**三个独立写操作分别执行并回查**，创建人取当前口袋授权账号。

## 场景工具

参数结构以工具 schema 为准，本文档不写死字段。

| 工具 | 用途 |
|---|---|
| whoami | 查询当前登录用户的简要信息（pid/did/姓名），用于确认当前登录身份 |
| searchCustomer | 按客户名称或联系人（姓名/手机号/微信）搜索客户，返回资料与当前跟进阶段 |
| getCustomerFollowLevel | 获取当前租户的跟进阶段配置（跟进过程/跟进结果/售后跟进三组阶段列表） |
| editCustomer | 编辑客户信息（本场景仅用于更新跟进阶段 followLevel；需【编辑客户】权限） |
| createCustomerFollowRecord | 创建客户跟进记录（会话沟通），创建人自动为当前登录账号（需【创建跟进记录】权限） |
| getCustomerReminds | 按客户 ID 查回访提醒（未完成/已失效两组），用于创建前查重 |
| createRemind | 创建回访提醒（关联客户，指定提醒时间与重复规则） |

## 工作流

### 1. 确认身份与定位客户

先调用 whoami 确认当前授权账号（后续写入的创建人即该账号，不得冒用客户原跟进人），再调用 searchCustomer 定位客户：

- name 与联系人条件（contactName/mobile/wechat）至少提供一个，且联系人条件至多提供一个（底层同为联系人搜索字段）。
- **命中多条时必须向用户展示候选并确认唯一客户后再继续**。
- searchCustomer 返回的 followLevel 为客户当前阶段（可能为空），阶段变更草稿以此为准。

### 2. 要素提取与草稿生成

从用户描述中提取以下要素，缺失必填项时向用户追问（不要臆造）：

- **必填**：客户标识（第 1 步定位）；沟通时间、方式（拜访/电话等）、对象。
- **必填**：沟通主题或客户需求、结果、关键问题、下一步动作；用户表示无下一步时须提供结束原因。
- **可选**：更新阶段时的目标阶段；创建提醒时的内容、时间、成员、重复规则。

跟进记录草稿正文使用结构化模板（沟通对象/方式/需求/结果/问题/下一步没有独立字段，一律写入正文）：

```
【沟通时间】<用户口述的真实沟通时间>【方式】<拜访/电话/...>【对象】<沟通对象>
【内容】<沟通主题与过程要点>
【关键问题】<关键问题，多个以、分隔>
【下一步】<下一步动作与约定时间>（无下一步时写结束原因）
```

注意：跟进记录的 publishTime 由服务端取写入时刻（不可自定义），与正文中【沟通时间】的真实沟通时间是两个概念，向用户展示草稿时应说明这一点。

阶段变更草稿（用户要求更新阶段时才生成）：调用 getCustomerFollowLevel 获取配置——

- levels 为跟进过程阶段（第 1 个固定为"待跟进"）、resultLevels 为跟进结果阶段（固定不可修改）、afterLevels 为售后跟进阶段；followLevelOff=true 表示该租户关闭了跟进阶段功能，此时不得更新阶段。
- 目标阶段名必须**精确匹配**三组列表之一中的阶段名称；用户口述的阶段名列表中不存在时，向用户展示可选阶段列表让其选择，不得臆造。

回访提醒草稿（用户约定了下次沟通时间时才生成）：调用 getCustomerReminds 先查重——与既有未完成提醒内容/时间高度重合的，向用户指出并确认是否仍要创建。

三份草稿（跟进记录/阶段变更/提醒）一并向用户展示，**全部经用户确认后才执行写入**；写入内容以用户确认的原文为准。

### 3. 写入（经确认，三个独立操作）

- **createCustomerFollowRecord**：入参 customerId（取自 searchCustomer 返回）+ content（用户确认的正文）；返回 tkid 与 publishTime（服务端当前时间）。
- **editCustomer** 更新阶段：custmid + followLevel（阶段名称）+ editFields: ["followLevel"]（部分更新语义，只动阶段字段）。
- **createRemind**：customerIds 取自 searchCustomer 返回；awokePids/awokeGids 不指定时默认提醒当前登录用户；remindTime/beginTime 为提醒时刻、endTime 为其后 24 小时（GMT 毫秒时间戳），repeatType=1（不重复）时 repeatEndTime 须非 0（填 endTime）；重复规则未指定时默认不重复。
- 三个写操作相互独立：用户确认哪项就执行哪项，某项失败不影响其他项，分别如实回报结果。

### 4. 回查并汇报

- 阶段更新后必须回查 searchCustomer 的 followLevel 确认已变更为目标阶段：**服务端对阶段名不做配置校验**，非法阶段名会直接落库为脏数据（App 端可能无法正常显示），因此更新前精确匹配配置列表是唯一防线，回查发现写入了列表外的阶段名时须立即用合法阶段名纠正并告知用户。
- 创建提醒后回查 getCustomerReminds，确认新提醒出现在未完成列表中，将提醒 id/sid 与 nextScheduleTime 单独回报。
- 跟进记录以 createCustomerFollowRecord 返回的 tkid+publishTime 为准回报（本场景未挂载跟进记录查询工具）。

## 常见异常

| 现象 | 处理方式 |
|---|---|
| 401 / 未授权 | 提示用户重新发起扫码授权（AGENT 会自动打开授权页） |
| 搜索命中多条客户 | 展示候选列表让用户确认唯一客户，不要自行猜测 |
| editCustomer 后阶段异常 | 服务端对阶段名不做配置校验，非法名会直接落库为脏数据；重新 getCustomerFollowLevel 拿合法阶段名，向用户确认后纠正重写 |
| 创建跟进记录报错 | 核对 customerId 是否为搜索返回的真实客户；content 不得为空 |
| 写操作报权限错误 | 需对应【编辑客户】/【创建跟进记录】权限，提示用户联系管理员在权限组中分配 |

## 注意事项

- 一切客户 ID（custmid）、阶段名称取自工具返回，不要臆造。
- 沟通时间、方式、对象、需求、结果、问题、下一步动作没有独立写入字段，全部体现在跟进记录正文模板中，不得遗漏必填要素。
- 写入操作（创建跟进记录、更新阶段、创建提醒）必须先经用户逐项确认，不得擅自写入。
- 图片和附件本场景不支持（用户描述为纯文字）；如用户需要带图，如实说明当前限制。
