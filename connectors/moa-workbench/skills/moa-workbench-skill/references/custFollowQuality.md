# 跟进质检场景

用于销售经理检查指定部门/员工在时间窗内的跟进记录质量：拉取跟进明细（沟通/通话与外勤两类合并），按记录中的客户 ID 批量反查客户信息与标签（含变更时间），按完整性、空泛记录、标签疑似冲突口径生成**员工与客户维度的问题清单及整改建议**；经用户确认后将整改建议写入对应跟进记录的评论（只增评论，不改原记录与标签）。

## 场景工具

参数结构以工具 schema 为准，本文档不写死字段。

| 工具 | 用途 |
|---|---|
| whoami | 查询当前登录用户的简要信息（pid/did/姓名），用于确认评论人身份 |
| findPersons | 按姓名/手机号模糊查成员，用于把"小王"等口述人名转为 PID |
| getAllPerson | 获取部门树与成员列表，用于把"销售一部"等部门名转为 GID |
| getCustomerLabels | 获取客户标签配置树（标签组/名称/ID，标签 ID→名称映射） |
| getFollowRecords | 按成员/部门+时间窗拉取跟进记录明细（沟通/通话+外勤，时间倒序） |
| getCustomersByIds | 按客户 ID 批量查客户信息（名称/跟进阶段/跟进人/标签含变更时间/跟进次数） |
| addFollowRecordComment | 在跟进记录下新增评论（整改建议），评论人自动为当前登录账号 |

## 工作流

### 1. 确认身份与解析范围

先调用 whoami 确认当前授权账号（后续评论的评论人即该账号），再用 findPersons/getAllPerson 解析范围：

- 用 findPersons/getAllPerson 把用户口述的部门/员工解析为 GID/PID；解析不到或有歧义时向用户展示候选确认，不要臆造。
- 范围（部门或员工）与时间窗是必填项，用户未说清时必须追问（如"昨天"按自然日折算为 GMT 毫秒时间窗）。
- 同时向用户确认质检口径：完整性规则（默认检查沟通对象/客户需求/沟通结果/下一步动作/下次联系时间五要素）、待检查的标签及判定规则、输出范围（只输出清单，或同时写入评论）。

### 2. 拉取跟进明细

调用 getFollowRecords：

- personIds/groupIds 至少传一个（groupIds 服务端递归展开为成员）；startTime（含）与 endTime（不含）构成时间窗，GMT 毫秒时间戳。
- recordType 默认 0（外勤+沟通混合）；用户只关心某类记录时传 1（仅外勤）或 2（仅沟通）。
- 返回 records 按时间倒序，每条含 id（记录 ID）、source（talk=沟通/通话、legwork=外勤）、customerId、uid（创建人）、content、time、forms（自定义表单，值为空的表单项不返回）。
- **服务端自动叠加跟进记录保护权限**：范围内被保护成员的记录不可见。返回条数少于预期或某成员无记录时不代表数据缺失，如实呈现即可，不得臆断"漏写"。
- hasMore=true 时用返回的 nextPrevTime 作为 prevTime 续拉（其余参数不变），直至 hasMore 不再返回。

### 3. 反查客户与标签配置

调用 getCustomersByIds 与 getCustomerLabels：

- customerIds 取自第 2 步各条记录的 customerId（去重，最多 500 个）；**不要臆造客户 ID**。
- 返回 customers（含 name/followLevel/followers/fcnt/labels，标签含 on 选中态与 updateTime 变更时间）与 failed（不存在/已删除的客户及原因，单独说明，不视为质检异常）。
- getCustomerLabels 返回标签配置树，用于标签 ID→名称映射与判定规则核对。

### 4. 质检并生成清单

对每条跟进记录按以下口径判定（口径属于 AI 分析职责，不下沉到工具）：

- **漏填**：沟通对象、客户需求、沟通结果、下一步动作、下次联系时间——任一无法从 forms 结构化字段**或** content 正文提取即为漏填。
- **空泛记录**：正文只有"已联系、继续跟进、待沟通、无进展"类内容，且无需求、结果或下一步动作。
- **标签疑似冲突**：记录内容与客户等级标签矛盾（如正文写"客户明确拒绝"但等级标签为 S 级）。**时间对齐规则**：标签 updateTime ≤ 记录 time 时，记录发生时标签已是当前值，可判冲突；updateTime > 记录 time 时标签系事后调整，不判冲突（或标注"标签系事后调整"）。没有明确标签规则时**只标记疑似冲突，不判断正确标签**。
- **完整率**：完整真实跟进数 ÷ 真实跟进总数；无样本时输出"无样本"。

按员工与客户两个维度汇总问题清单与整改建议（建议必须引用具体记录 id 与证据原文），连同完整率一并向用户展示。**未获用户确认前不得写入任何评论**。

### 5. 写入评论（经确认，逐条独立）

调用 addFollowRecordComment：

- recordId 与 recordType **必须原样取自第 2 步返回的记录 id 与 source 字段**：工具写入前会校验记录存在性，不存在的记录 ID 会报参数错误。
- content 为用户确认的整改建议文本；createPid 传该记录的 uid 字段（被评论人收到通知），用户明确不想通知被评论人时不传。
- 逐条独立写入：某条失败不影响其他条，分别如实回报评论 replyId 与 publishTime。
- 只能新增评论：不得修改原跟进记录、不得修改客户标签、不得另建跟进记录。

## 常见异常

| 现象 | 处理方式 |
|---|---|
| 401 / 未授权 | 提示用户重新发起扫码授权（AGENT 会自动打开授权页） |
| getFollowRecords 返回空列表 | 可能是时间窗内无记录，也可能是范围内成员被跟进记录保护过滤；向用户如实说明两种可能，不要臆断 |
| getCustomersByIds 出现 failed 条目 | 该客户不存在或已删除（原因见 failed 列表），对应记录单独说明，不影响其余客户质检 |
| 成员/部门解析不到 | 用 findPersons/getAllPerson 换关键词重查，仍找不到时向用户确认范围口述是否准确 |
| 评论写入失败 | 核对 recordId/recordType 是否原样取自 getFollowRecords 返回；content 不得为空；若报"跟进记录不存在"，确认记录 ID 正确且未被删除 |

## 注意事项

- 一切 PID/GID/客户 ID/记录 ID 取自工具返回，不要臆造。
- 时间戳一律为 GMT 毫秒；"昨天/本周"等相对时间先折算为明确时间窗并经用户确认。
- 标签 updateTime 为 0 或缺失时表示变更时间未知，标签冲突判定降级为"疑似"并注明证据不足。
- 写入评论必须先经用户确认（用户选择"只输出清单"时不得执行任何写入操作）。
- 本场景没有客户详情/跟进人修改等写入工具，超出质检范围的写入请求如实说明不支持。
