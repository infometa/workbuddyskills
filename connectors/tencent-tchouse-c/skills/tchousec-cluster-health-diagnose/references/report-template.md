# 集群健康诊断报告模板

> **何时使用本文件**：在步骤 7（综合分析与生成报告）时，按此模板格式输出诊断报告。
> **何时不使用**：根因分析逻辑请参考 `diagnosis-framework.md §4`；工具调用参数请参考各工具的 reference 文档。

---

## 报告格式

```markdown
# 集群健康诊断报告

## 集群概况

- **集群 ID**：xxx
- **集群名称**：xxx
- **版本**：ClickHouse xxx
- **状态**：Serving / Init / Modify
- **节点数**：数据节点 x 个，ZK 节点 x 个
- **HA 模式**：是/否
- **节点规格**：xC xG（CPU/内存）
- **磁盘**：类型 xxx，容量 xxx GB/节点

## 健康评分

🟢/🟡/🔴 **[等级] XX / 100 分** — [一句话总结当前集群健康状况]

### 扣分明细

（若未扣分则标注"无扣分项"；数据不充分时仅给定性等级，不填分数）

| 扣分项 | 具体现象 | 扣分 | 依据（见 diagnosis-framework.md §3） |
|--------|---------|------|-------------------------------------------|
| 节点异常 | 例：节点 10.x.x.x DATA 非 Running | -20 | 扣分项 A |
| 告警事件 | 例：1 条待处理 DiskHigh | -15 | 扣分项 B（🔴） |
| 监控指标 | 例：DiskUsage 92%（严重阀值） | -15 | 扣分项 C（磁盘容量） |
| ... | ... | ... | ... |
| **合计** | | **-XX** | 最终得分 = 100 - XX = **YY** |

> 若因"强制降级规则"导致等级与分数不一致（如得分 92 但存在节点宕机），在此标注降级原因。

## 节点状态矩阵

| 节点 IP | 角色 | 状态 | CPU | 内存 | 磁盘 | 备注 |
|---------|------|------|-----|------|------|------|
| 10.x.x.x | DATA | Running | 45% | 62% | 78% | 正常 |
| 10.x.x.x | DATA | Running | 82% | 71% | 92% | ⚠️ CPU高/磁盘高 |
| 10.x.x.x | COMMON(ZK) | Running | 15% | 30% | 20% | 正常 |
| ... | ... | ... | ... | ... | ... | ... |

## 告警事件

（如果有未处理的告警事件则展示，无则标注"无待处理告警事件"）

| 时间 | 事件类型 | 描述 | 严重程度 | 状态 |
|------|---------|------|---------|------|
| 2026-xx-xx HH:mm | DiskHigh | 磁盘使用率超过90% | 🔴 高 | 待处理 |
| 2026-xx-xx HH:mm | InstanceRisk | 实例运行隐患 | 🟡 中 | 待处理 |
| ... | ... | ... | ... | ... |

## 异常项详情与根因分析

### 问题 1：[问题标题，如"节点 10.x.x.x 磁盘使用率 92%"]

- **严重程度**：🔴 高 / 🟡 中 / 🟢 低
- **影响范围**：[受影响的节点/服务/业务]
- **根因分析**：[基于数据的根因判断，说明推理过程]
- **证据**：
  - [支撑结论的监控数据，如"disk_usage_percent 从 xx:xx 开始持续上升"]
  - [关联的告警事件，如"DiskHigh 告警于 xx:xx 触发"]
  - [其他佐证，如"parts_count 异常高达 xxx"]

### 问题 2：[问题标题]

- **严重程度**：...
- **影响范围**：...
- **根因分析**：...
- **证据**：...

（如无异常项，标注"未发现异常，集群运行健康"）

## 修复建议

| 优先级 | 操作 | 预期效果 | 风险 | 建议执行时间 |
|--------|------|---------|------|-------------|
| P0 | [立即执行的操作] | [预期效果] | [风险说明] | 立即 |
| P1 | [建议执行的操作] | [预期效果] | [风险说明] | 低峰期 |
| P2 | [后续优化建议] | [预期效果] | [风险说明] | 计划内 |

> ⚠️ 涉及重启、配置变更等操作，建议在低峰期执行。HA 集群可逐节点滚动重启以降低影响。

## 后续建议

1. [长期优化建议1，如"建议配置 TTL 策略自动清理过期数据"]
2. [长期优化建议2，如"建议将高频小批量写入合并为大批量"]
3. [监控建议，如"建议对 disk_usage_percent 设置 80% 预警阈值"]
```

---

## 格式要求

1. **数据真实性**：所有诊断结论必须基于工具返回的真实数据，不得编造监控指标或告警信息
2. **证据链完整**：每个根因分析必须有对应的监控数据或事件作为证据支撑
3. **建议可执行**：修复建议必须具体到可执行的命令或操作步骤
4. **风险标注**：涉及数据变更或服务中断的操作必须标注风险和建议执行时间
5. **优先级明确**：多个问题并发时，按"防数据丢失 → 恢复服务 → 性能优化"排序
6. **关联引导**：如果问题根因涉及其他 Skill 的能力范围（如慢 SQL），在报告末尾建议用户使用对应 Skill
7. **评分可追溯**：健康评分必须附扣分明细表，总分 = 100 减去各项扣分；扣分规则遵循 `diagnosis-framework.md §3`，不得自行发挥分数

## 特殊场景报告补充

### 场景：集群正在变更中

在报告开头增加提示：

```markdown
> ⚠️ **注意**：集群当前有操作进行中（{FlowName}，进度 {FlowProgress}%），部分诊断数据可能受影响。建议等待操作完成后重新诊断。
```

### 场景：监控数据部分缺失

在对应章节标注：

```markdown
> ⚠️ **数据缺失**：{时间段} 的监控数据不可用（可能是采集中断），以下分析基于可用时段的数据。
```

### 场景：根因无法自动定位

在根因分析部分：

```markdown
### 问题 N：[问题标题]

- **严重程度**：...
- **影响范围**：...
- **根因分析**：无法自动定位根因
- **已排查**：
  - ✅ 已排除：[原因A]（证据：...）
  - ✅ 已排除：[原因B]（证据：...）
  - ❓ 待确认：[原因C]（需要更多信息：...）
- **建议**：建议提工单并附上本诊断报告，由运维团队进一步排查
```
