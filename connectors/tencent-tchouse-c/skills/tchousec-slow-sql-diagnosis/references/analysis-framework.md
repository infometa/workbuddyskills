## §1 性能瓶颈识别

从执行计划中识别以下问题：

| 问题类型 | 执行计划特征 | 严重程度 | 优化方向 |
|---------|------------|---------|---------|
| 全表扫描 | `ReadFromMergeTree` 无索引裁剪，Granules 读取比例接近 100% | 🔴 高 | 添加分区过滤/跳数索引 |
| 索引缺失 | WHERE 条件字段不在 ORDER BY 键中，无跳数索引命中 | 🔴 高 | 添加跳数索引/调整排序键 |
| 分区裁剪失败 | 查询条件未命中分区键，读取了所有分区 | 🔴 高 | 添加分区键过滤条件 |
| JOIN 顺序不优 | 大表在 JOIN 右侧（被 broadcast），或未使用合适的 JOIN 算法 | 🟡 中 | 调整 JOIN 顺序/使用 GLOBAL JOIN |
| 数据倾斜 | 某些分区/分片数据量远大于其他 | 🟡 中 | 调整分片键/预聚合 |
| 排序开销大 | `MergingSorted` 或 `MergeSorting` 处理大量数据 | 🟡 中 | 减少排序数据量/利用排序键 |
| SELECT * 宽表 | 读取大量不必要的列文件 | 🟡 中 | 只选需要的列 |
| 子查询重复执行 | IN (SELECT ...) 未被优化为 JOIN | 🟡 中 | 改写为 JOIN |
| 查询 _local 本地表 | SQL 中表名以 `_local` 结尾，仅查询当前分片数据 | 🟡 中 | 确认是否应查分布式表（去掉 `_local` 后缀）；若为有意行为则确认数据完整性 |

### 判定优先级

当一条 SQL 存在多个问题时，按以下优先级排序处理：

1. 分区裁剪失败（影响最大，通常是数量级的差异）
2. 全表扫描 / 索引缺失
3. JOIN 顺序不优
4. 其他问题

## §2 执行计划关键字段解读

### ReadFromMergeTree 节点

```
ReadFromMergeTree (database.table)
  Indexes:
    PrimaryKey
      Keys: column1, column2
      Condition: ...
      Parts: 15/200        ← 裁剪后的 parts 数 / 总 parts 数
      Granules: 1200/50000 ← 裁剪后的 granules / 总 granules
    Skip
      Name: idx_xxx
      ...
```

**关键判断**：
- `Parts: A/B` — 如果 A ≈ B，说明主键索引未生效（全表扫描）
- `Granules: A/B` — 如果 A/B > 50%，说明过滤效果差
- 无 `Skip` 段 — 说明没有跳数索引命中

### JOIN 节点

```
Join (INNER/LEFT/RIGHT)
  Algorithm: HashJoin / MergeJoin / ...
  Right table size: xxx rows
```

**关键判断**：
- 右表行数远大于左表 → JOIN 顺序不优
- Algorithm 为 HashJoin 且右表过大 → 可能 OOM，建议改用 partial_merge

### Aggregating 节点

```
Aggregating
  Keys: column1, column2
  Aggregates: sum(x), count(y)
```

**关键判断**：
- Keys 基数过高（如用户 ID）→ 聚合开销大，考虑预聚合或物化视图

## §3 输出报告格式

### 报告模板选择

根据步骤 3.5 的去重结果，选择对应的报告模板：

- **标准模板**：去重后有 ≥ 2 个不同 SQL 模式 → 使用下方标准格式
- **高频单一 SQL 模板**：去重后仅 1 个模式（或某模式占比 > 90%）→ 使用 [高频单一 SQL 变体](#高频单一-sql-报告变体)

```markdown
# 慢 SQL 诊断报告

## 集群概况
- 集群 ID：xxx
- 版本：xxx
- 状态：xxx
- 节点规格：xxx

## 慢查询概览
- 时间范围：xxx
- 慢查询阈值：xxx ms
- 慢查询总数：xxx
- Top N 慢 SQL 平均耗时：xxx

## 趋势分析
（慢查询数量/耗时的时间趋势，判断是突发还是持续恶化）
- 趋势类型：突发 / 持续恶化 / 稳定
- 关键时间点：xxx（如有突变）

## 逐条诊断

### SQL #1
- **SQL 文本**：（完整 SQL，过长则截断并标注）
- **执行耗时**：xxx ms
- **读取行数**：xxx
- **扫描 Granules**：xxx / xxx（裁剪率 xx%）
- **性能瓶颈**：
  - 🔴 [问题1：具体描述]
  - 🟡 [问题2：具体描述]
- **诊断依据**：🟢 执行计划确认 / 🟡 表结构分析推断 / 🔴 仅 SQL 文本推断
- **优化建议**：
  - [建议1：SQL 改写方案 + 改写后的 SQL]
  - [建议2：索引建议 + 具体 DDL]
- **预期收益**：扫描行数从 xxx 降至 xxx（约 xx% 提升）

### SQL #2
...

## 综合优化建议
| 优先级 | 操作 | 影响范围 | 预期收益 |
|--------|------|---------|---------|
| P0 | [最高优先级] | [影响的 SQL 编号] | [预期提升] |
| P1 | [次优先级] | ... | ... |
| P2 | [后续优化] | ... | ... |

## 注意事项

- [需要重建表的操作（如有）需用户确认]
```

### 高频单一 SQL 报告变体

当去重后仅 1 个 SQL 模式（或某模式占比 > 90%）时，使用以下报告结构替代标准的"逐条诊断"部分：

```markdown
## 高频慢 SQL 深度分析

### 基本信息
- **SQL 模式**：（归一化后的 SQL 文本）
- **执行频次**：共 xxx 次（时间范围内）
- **执行频率**：约每 X 分钟/小时执行一次
- **最大耗时**：xxx ms
- **平均耗时**：xxx ms
- **累计资源消耗**：平均耗时 × 频次 = xxx 秒（总计浪费）

### 执行频次分析
- 时间分布：（是否集中在某个时段？如每天凌晨 2:00-3:00）
- 频率模式：固定间隔 / 随机触发 / 业务高峰集中
- 持续天数：从 xxx 开始，持续 N 天

### 高频原因推测
| 可能原因 | 判断依据 | 可能性 |
|---------|---------|--------|
| 定时任务/Cron Job | 固定间隔执行 | 高/中/低 |
| 应用层轮询 | 高频随机触发 | 高/中/低 |
| 缓存失效后回源 | 突发集中执行 | 高/中/低 |
| ETL/数据同步任务 | 凌晨集中执行 | 高/中/低 |

### 性能瓶颈（同标准模板）
- **诊断依据**：🟢/🟡/🔴
- **瓶颈详情**：...

### 优化建议

#### SQL 层优化
- [SQL 改写方案]

#### 应用层优化（针对高频特征）
- **缓存策略**：对结果集添加 TTL 缓存，降低查询频次
- **增量同步**：如为全量同步任务，改为增量方式
- **降频建议**：将执行间隔从 X 分钟调整为 Y 分钟
- **物化视图**：对固定聚合查询创建物化视图，将查询耗时降至毫秒级

#### 预期收益
- SQL 优化收益：单次耗时从 xxx ms 降至 xxx ms
- 频次优化收益：若降频 50%，累计节省 xxx 秒/天
- 综合收益：xxx
```
