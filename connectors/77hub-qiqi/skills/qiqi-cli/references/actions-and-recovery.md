# 记录动作与未知结果核查

## 发现并执行记录动作

对提交、撤回、审批或其它业务动作：

1. 用稳定 `RecordRef` 确认目标记录和当前状态。
2. 用 `describe actions <RecordRef>` 读取此刻允许的动作及其 `inputSchema`。
3. 核对用户意图、当前返回的动作 ID、参数和影响。
4. 用 `do-action` 执行一次，并依据返回记录或后续最小读取确认结果。
5. 若返回 `BUSINESS_WARNING`，先向用户展示警告明细；只有用户明确确认后，才追加 `--ignore-warn` 再执行一次。不得自动补该开关重发。`--ignore-warn` 只控制请求头 `Ignore-Warn`，不是动作业务参数。

不要直接改写状态字段，也不要用其它记录曾经出现过的动作推断当前记录可执行。qiqi 已提供专用业务命令的流程必须使用该专用命令，不用名称相近的 `do-action` 代替。具体参数和传参形式以当前 `do-action --help` 及 `describe actions` 返回为准。

## 删除确认

删除不可逆。先按当前 `records delete --help` 执行预检查，向用户呈现目标摘要和影响；只有用户明确确认且目标无歧义时才执行确认删除。只有最终返回明确表示删除成功时才报告删除成功。

## 未知结果核查

超时、连接中断、响应不完整或定义变化时，CLI 不能恢复、回滚或补造原调用结果。应标记“状态未知”，停止重放，并按最窄的业务事实核查：

- 已知 `RecordRef`：读取该记录的当前状态和关键字段。
- 已知唯一业务编码：按精确条件查询并确认唯一记录。
- 仅知道工作列表变化：重新读取对应 View，但不把列表变化单独当作动作成功证明。
- 创建或登记类意图：按用户已确认的业务事实和时间窗口寻找候选；仍无法唯一确认时保持未知。

核查只能确认当前事实，不能证明原调用一定成功。仍有歧义时向用户呈现候选和未知状态，由用户决定下一步。
