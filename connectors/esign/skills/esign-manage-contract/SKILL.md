# 合同管理

查询和操作已有合同流程及合同、用印审批任务。开始时读取[通用依据规则](references/evidence-rules.md)和[结果规则](references/result-rules.md)，所有查询、操作、展示与失败分支均适用。

## 1. 判断意图和对象

| 用户意图 | 执行规则 |
| --- | --- |
| 查合同、列表、筛选、待我签署、列表中的进度 | [合同流程管理](references/process.md) |
| 查看、填写、单份签署链接、批量签署入口 | 合同流程管理 |
| 撤回符合条件的流程、单个或批量下载入口 | 合同流程管理 |
| 待我审批、合同或用印审批列表、审批历史 | [审批流程](references/approval.md) |
| 审批访问入口、意愿认证 | 审批流程 |
| 单条或批量同意、拒绝审批 | 审批流程 |
| 本次批量成功几条、失败几条 | 已保存的真实执行结果，不再次提交 |

仅咨询方法、要求方案或明确暂不执行时，不调用业务命令。“批量审批”未明确同意还是拒绝时澄清；“作废”不能擅自解释为撤回。已确认当前接入能力不支持时直接友好说明，如“目前暂不支持通过这里作废这份合同”，不拿撤回等其他操作试探，不追加无必要的确认或技术解释。权限、状态限制或临时故障按实际原因说明，不能一律说能力不支持。

合同内容分析和具体流程事实解释由问答等能力处理；本 Skill 可以直接展示列表中的状态，不为每个状态字段反复转交。不发起新合同、不起草、不作风险判断，也不替用户决定应否审批通过。

## 2. 定位目标和保存上下文

- 操作选项来自真实目标及当前可用能力；未定位目标时不编造可签、可撤回、可审批等选项。
- 已有明确且有效的目标就使用；缺少目标时查询对应列表，再只询问不能确定的信息。不让用户手动填写内部 ID，不按名称猜标识。
- 分别保存合同列表和审批列表的真实对象、展示序号、筛选条件、排序规则、页码、账号、企业和环境；查询失败或成功空结果时，不把旧列表当成新结果。
- 合同对象使用真实 `processId`，保存名称、状态、操作项和 `dedicatedCloudId`。审批对象使用真实 `approvalCode + taskId`，保存名称、状态、类型、业务编号及真实流程关联。两类标识不得互换。
- “下载第 2 份合同”使用合同列表；“同意第 2 条审批”使用审批列表；“打开第 2 条”有歧义时先澄清，不用最近任意列表猜测。
- 从合同进入审批，可用 `approval list --process-id` 取得真实任务。反向进入合同操作时使用返回的真实流程 ID，并补齐状态和操作项；合同处于审批中不表示当前用户有审批权。
- 翻页沿用原排序与筛选，不能把“最近”偷偷换成即将到期优先。新列表重新编号时说明，后续序号绑定实际展示对象。数量与分类从同一批真实对象计算，不能总计4条分类却合计5条。
- 用户要求“全部”时核对筛选范围和分页，不把当前页或当前企业可见范围冒充更大范围；不静默剔除不支持操作的条目后执行剩余项。
- 切换账号、企业或环境后，清除旧列表指代、待执行动作、原因意见绑定、认证和批量结果上下文，再查询。

## 3. 执行业务

读取所选分支与[参数说明](references/parameters.md)。依赖可执行的业务 CLI，使用当前执行身份；审批在企业空间处理。CLI 缺失先按 CLI 准备规则安装；登录未知或失效按[登录与恢复](references/login.md)处理。缺少其他能力、权限或空间不符时说明实际限制，不继续依赖该条件的操作。

- 查询和访问入口按用户意图执行。写操作必须来自用户明确请求，目标、动作、范围及必要信息已齐备后直接继续，不反复询问同一事项。
- 执行前使用当前可见的状态和操作项核对允许条件；已有信息过期、目标变化或刚结束长时间中断时重新查询。展示过操作项不代表后续调用必然成功，以服务端结果为准。
- 用户已提供的当前目标意见、原因或“无意见”直接复用；缺少必填信息时才补充，不使用命令默认值冒充用户输入。撤回和拒绝原因必填；同意审批中，用户明确表示“不填写”“无”“无意见”“没意见”“空着”时，将本次审批意见值设为“无”：单条传 `--reason '无'`，批量传 `--remark '无'`，不省略、不传空值。未回复不能自动填“无”；具体意见原样使用，此映射不适用于拒绝或撤回原因。
- 沿用业务对原因和意见的字符限制；明确不支持的表情或字符提示修改，不静默删改。现有约定没有精确字符集，不另造白名单，也不据猜测批量清洗用户意见；实际服务端校验失败按原错误反馈。
- 原因、意见、意愿认证绑定当前账号、企业、环境、操作意图和完整目标集合。换目标、范围或同意/拒绝意图后重新核对原因意见，不复用不匹配的认证结果；认证要求按审批流程和服务端实际返回处理。
- 审批不统一前置查询意愿认证。用户明确要求同意或拒绝，目标、范围及业务必填信息齐备后，按审批流程直接提交，由服务端判断认证要求；已明确需要认证的任务直接提供审批入口，不再无认证提交。仅请求认证入口不自动审批，账号登录或用户口头确认不能替代平台要求的认证。
- “这几份一起签”“把这些都签了”“签第1和第3份”等明确选择多个合同的签署请求，统一进入批量签署；不要求用户必须说出“批量”二字。
- 多合同签署必须将完整选中范围放入同一次 `esign sign process batch --process-ids '<processId1>' --process-ids '<processId2>'` 调用，每个 ID 对应一个 `--process-ids` 参数。禁止逐份调用 `process url`，也禁止按单个 ID 循环调用 `process batch`。成功后只交付本次完整范围对应的一个真实 `redirectUrl`，合同名称另作简短列表。
- 未取得有效批量入口时说明“未生成批量签署入口”及实际可读原因，不自动生成或展示多个单份签署链接；仅在用户明确要求或同意改为逐份签署后，才按单份流程处理。不能因卡片展示失败而拆分已有批量入口；批量入口生成成功无需再问是否改为逐份签署。
- 明确只选一份合同时用 `process url`；批量下载、批量审批和意愿认证保持各自参数格式，不混用。
- 业务命令使用实际支持的输出形式，不统一追加不存在的参数。用户文本和 JSON 作为参数数据传递，正确处理空格、引号和特殊字符，不拼成可执行代码。

## 4. 核对结果、恢复与交接

按结果规则检查退出状态和业务响应；错误优先于任何展示数据。无有效结果不能猜成功。失败按[恢复规则](references/recovery.md)处理，保留必要原请求。

写操作返回不明或连接中断时，通过已有只读能力核查，不盲目重放命令。部分成功分别报告实际成功、失败、未知及待处理对象；列表状态不足以证明本次操作结果时明确说尚不能确认。

用户取消后清除待执行动作，不继续认证后的旧操作。业务已成功但展示失败，只重试展示或输出文本，不再次提交业务。

选定合同后，可将真实流程或文件引用、用户原问题、来源及已读取范围、当前账号企业上下文交给实际可用的摘要、比对、审查或问答能力；不传凭据、不声称已读取正文。用户已明确要求“找到后摘要／问答／比对／审查”时，取得目标后继续对应 Skill，不要求用户重复原任务；缺少对应能力时说明已定位目标和所缺能力，不虚构完成。

## CLI 准备

首次需要执行 `esign` 命令时，先按[CLI 检测与安装](references/cli-bootstrap.md)确认命令可用；确认本机未安装时，完成安装并验证后继续原步骤。本包其他规则中的“CLI 不可用时停止”指完成该准备后仍不可用。只处理 CLI 缺失，不改变材料选择、业务处理、用户确认及结果展示规则。

## 平台访问与展示规则

业务操作需访问 e签宝平台。已有有效连接和身份时直接执行；登录状态未知、明确未登录或登录失效时，按[登录与恢复](references/login.md)检测、引导授权并恢复原请求。账号登录与审批意愿认证分别处理，不自动切换账号、企业或环境。

列表、操作结果和真实访问链接直接用文本或 Markdown 展示，不依赖平台专用卡片。仅有卡片数据而没有可读取的业务结果或真实链接时说明缺少可展示结果，不猜协议、构造链接或再次提交操作。意愿认证仍按审批规则执行，账号登录不能替代它。

- 需要 CLI 处理文件或访问平台时，按[CLI 检测与安装](references/cli-bootstrap.md)解析可用入口；确认未安装时完成安装、验证后继续原步骤。不把其他 CLI 当成替代，不扫描用户文件或读取凭据，不自动升级已有 CLI；不得仅因命令缺失宣称业务不支持。

## 结构化提问节点

仅在以下必要澄清节点调用 `AskUserQuestion`，遵循[结构化提问规则](references/workbuddy-question-rules.md)。查询结果和操作结果仍用原有文本或 Markdown 展示；这里使用的是宿主提问工具，不是业务接口返回的专用卡片。

- 已有真实合同或审批候选，但同名、指代或操作范围存在歧义时选择目标；以合同名称、状态、发起人等实际信息区分，不显示内部编码。明确的“第N条”直接复用有效映射，不重复选取。
- 用户要求“批量审批”但没有明确同意还是拒绝等操作意图时，用必要的操作选项澄清；用户已明确动作时不再询问，不把“作废”改成“撤回”选项。
- 当前目标的同意审批意见尚未提供时，若工具支持同一卡片自由输入意见并提供“无意见”的选项（说明将以“无”提交），可用卡片替代审批规则中的纯文本询问。不要自行补一个虚假的意见选项凑数量，也不要先选“填写意见”再问第二次；参数不能表达这一交互就沿用简短文字。用户已给出意见时原样复用；明确“不填写”“无”“无意见”“没意见”“空着”时按审批规则传值“无”，不再弹卡片或重复确认；未作答不能视为无意见。该适配只替换同意／批量同意的意见提问方式，不改变意见绑定和提交条件。

拒绝及撤回原因继续以简短文字收集，不生成预设理由。普通查询不强制选择下一步，已明确动作、对象、范围和必要信息时按原流程执行，不新增写操作确认。认证要求以服务端为准，不把选项点击当成认证结果。

## 文件分析衔接

查询、撤回和审批本身不增加正文抽取或 OCR。用户还要求摘要、问答、比对、审查或基于文件起草时，定位选定文件后传递真实文件引用、当前版本和原任务，由对应 Skill 按[文档处理规则](references/document-processing.md)读取；已有本次同版本正文可以复用，不重复抽取，不把流程元数据当正文。审批执行与认证分支遵循本包审批规则。
