# 合同与用印审批

执行对应业务前读取本文件和[参数说明](parameters.md)，同时遵循 SKILL.md 的对象绑定、写操作及结果规则。是否需要意愿认证由服务端判断，不把意愿认证查询作为所有审批的统一前置。

**审批列表查询**
1. 执行 `esign sign approval list`，根据用户条件追加列表查询参数。常用参数：`--query-type`、`--approval-type`、`--approval-name`、`--contract-no`、`--process-id`、`--page-num`、`--page-size`。补充筛选参数：`--approval-codes`、`--approval-status-list`、`--initiator-name`、`--initiator-subject-name`、`--participant-name`、`--participant-subject-name`、`--min-create-time`、`--max-create-time`、`--min-operate-time`、`--max-operate-time`。
2. 若用户未指定范围，待我审批优先使用 `--query-type 3`；审批记录/历史优先使用 `--query-type 4`；我发起的使用 `--query-type 2`；我收到的使用 `--query-type 1`。
3. “今天”、“现在”等在“我今天有哪些待审批任务”、“现在有什么要审批”中表示询问当前所有待处理任务，不因这类对话性时间表达自动添加创建时间或操作时间筛选。只有用户明确限定“今天创建的”、“今天发起的”或“今天已审批的”等具体时间维度时，才追加对应的创建时间或操作时间参数。
4. 命令执行成功后，按以下优先级处理结果：
   - 返回明确的 `total=0`，或未返回总数但命令明确表示查询成功且审批数据集合为空：使用纯文本提示后结束本轮，不展示空表格，不询问用户选择第几条。
   - 若结果为空，本次查询是未附加筛选条件的全部待我审批任务，且用户说了“今天”时，返回：`截至现在，你没有待审批的合同或用印任务，今天暂时无需处理。`
   - 若结果为空，本次查询是未附加筛选条件的全部待我审批任务，且用户未说“今天”时，返回：`截至现在，你没有待审批的合同或用印任务。`
   - 若结果为空且用户明确指定了筛选条件，必须用用户易懂的中文回显实际传给 CLI 的关键条件，并给出一个直接可执行的放宽建议。例如：`未找到由张三发起且仍待你审批的任务。你可以去掉发起人条件后重试。`
   - 若结果为空，提示只能回显已实际传给 CLI 的筛选条件，禁止回显未实际使用的条件，不展示 `query-type`、毫秒时间戳等技术参数。
   - 若 `total>0` 但当前分页无数据，不得说没有待审批任务；应提示当前页无数据并建议调整页码。
   - 若无法可靠判断查询是否成功或结果数量，按异常处理，不得误报为没有审批任务。
   - 列表非空时按结果规则展示总数、明确序号、审批名称、类型、状态、发起人及业务时间，必要时展示用户可识别的业务编号。任务 ID、内部审批编码和操作编码仅保存在执行上下文，不在普通用户列表中展示。
5. 列表非空时，保留 `approvalCode`/`approval-code`、`taskId`/`task-id`、审批名称、审批类型、审批状态、流程ID、合同编号、操作项，供后续"第 N 条"等指代使用。
6. 结果过多时最多展示 100 条并提示缩小范围。

**获取审批访问地址**
1. 获取 `approval-code`；用户说"第 N 条"时使用最近一次有效审批列表中的第 N 条。
2. 执行 `esign sign approval url --approval-code '<approvalCode>'`。
3. 返回 URL；若未获取到 URL，返回可识别的审批名称或业务编号并提示用户到系统内打开，不展示内部编码。

**从合同列表衔接批量审批**

- 用户在合同列表后说“这些全部审批通过”时，保存已选合同的真实processId及范围，逐份使用 `esign sign approval list --process-id '<processId>' --query-type 3` 查询关联的当前待审批任务。建立合同到approvalCode＋taskId的映射，不把processId当审批ID，也不按同名猜任务。
- 无任务、多个候选、已处理或权限不明时先只读核实；仍有歧义仅询问对应对象，不把缺少的对象静默跳过。多个任务确实均属于明确的全部待审批范围时纳入完整集合，同一任务去重。
- 从审批列表继续时直接复用有效任务映射，不再次转回合同列表。意见和原因绑定实际任务集合，已明确的内容不重问。
- 批量签署交付签署页面入口；批量审批提交真实同意或拒绝动作并返回结果，不一律只给链接。只有明确需要认证或当前操作受限且有可用恢复路径时给审批页面。
- 当前CLI没有已核实的统一批量审批页面命令。多个需认证任务可分别给真实approval url，不编造批量认证入口或承诺一个链接覆盖所有任务。

**审批提交与认证分支（所有同意、拒绝及批量操作适用）**

- 用户已明确请求当前动作，目标、范围和业务必填信息齐备，且当前任务没有已明确的认证要求时，直接调用对应审批命令。不先调用 `approval will`，不要求先取得 `NeedAuth=false`。没有认证参数时省略 `--will-auth-id`、`--will-auth-type`，不是传空字符串，不编造认证参数。
- 这不表示任务“默认免认证”。只有服务端实际返回才决定认证要求与操作结果；用户说“按无需认证提交”也不能覆盖已经明确的认证要求，不主动索要这句确认。
- 若历史 `approval will` 仅返回 `success:true` 且数据为空，这既不能证明需要认证，也不能证明免认证。单凭该查询空结果不阻止当前已授权且信息齐备的首次审批提交；若审批写命令已执行过，则先按结果和恢复规则判断，不能借此重试结果不明的写操作。
- 当前任务已明确需要认证（无论来自审批提交响应或此前有效查询）时，停止无认证提交，执行 `esign sign approval url --approval-code '<approvalCode>'`，返回真实审批入口。简短提示：“这条审批需要完成意愿认证，请打开审批页面继续处理。”不再自动调用审批命令，不让用户填写认证 ID，不将审批地址当作认证成功的凭据。
- 明确审批成功时说明处理对象和结果；仅提交成功、处理中或结果不明时不能说已审批通过。`success:true` 不能脱离业务响应单独作为审批完成的证据。
- 只有明确的认证要求才进入认证分支，不把所有参数错误、无权限、环境不支持、空数据或超时都解释为需要认证。若 CLI 本地拒绝缺少认证参数且未明确业务认证状态，提供真实审批入口继续处理，说明“暂时无法通过对话完成，请打开审批页面处理”，不能声称一定需要认证。
- 未取得有效审批地址时，说明无法取得入口，并用审批名称引导用户到平台待审批列表打开；不拼接链接。
- 用户在页面处理后回来询问结果，先只读查询当前任务状态；页面已处理的任务不重复提交。点击链接、用户说“认证好了”或链接返回成功，都不能单独证明审批完成。用户仅完成认证并要求继续时，先查询状态；仍待审批且未取得可验证的认证凭据时继续引导到该审批页面处理，不回到无认证提交。
- 普通回复只给业务结果、需要用户补充的信息或处理入口，不解释内部检查、返回字段、认证参数与重试机制。

**单条同意审批**

1. 获取目标 `approval-code` 和 `task-id`；缺少时先查询，不让用户提供内部 ID。
2. 复用当前任务已提供的审批意见。用户明确“不填写”“无”“无意见”“没意见”或“空着”时，以字面值“无”作为当前审批意见，必须传 `--reason '无'`，不省略参数、不传空字符串，不再追问或改成“同意”。从未提供意见时，简短询问一次：“请填写审批意见；没有补充意见可回复‘无’，将以‘无’提交。”不得把未回答、关闭卡片、空返回或超时当作无意见。此映射仅适用于用户已明确同意当前任务的场景，不代替审批动作授权；其他具体意见原样传入。
3. 核对已知业务限制，不自行推测字符限制或静默删改意见。当前任务已明确需要认证时直接按上述认证分支提供入口。
4. 有意见时执行 `esign sign approval agree --approval-code '<approvalCode>' --task-id '<taskId>' --reason '<审批意见>'`；明确无意见时执行 `esign sign approval agree --approval-code '<approvalCode>' --task-id '<taskId>' --reason '无'`。
5. 按“审批提交与认证分支”处理实际结果，不再额外索要“按无需认证提交”的确认。

**单条拒绝审批**

1. 获取目标 `approval-code` 和 `task-id`；缺少时先查询。
2. 拒绝原因必填且必须绑定当前任务；缺少时用简短文字收集，不代编理由。按已知限制校验，不猜限制、不静默改写。
3. 当前任务已明确需要认证时直接给入口；否则执行 `esign sign approval refuse --approval-code '<approvalCode>' --task-id '<taskId>' --reason '<驳回原因>'`。
4. 按“审批提交与认证分支”处理实际结果。

**批量同意审批**

1. 确定真实任务集合及完整范围，补齐分页；不能把当前页当作全部，也不能静默剔除某些任务。
2. 意见复用和补充规则与单条同意一致；“不填写”“无”“无意见”“没意见”“空着”等明确无意见时，必须传 `--remark '无'`，不省略、不传空值，不再追问。用户未回复时仍需收集意见，不能默认填“无”。拒绝原因不可用于同意意见，目标集合变化后重新核对绑定。
3. 集合内已有明确需要认证的任务时，说明这些任务需在页面处理并提供对应真实审批入口；其余任务是否另行提交由用户明确选择，不擅自缩小范围。
4. 无已明确认证要求且业务信息齐备时，有意见执行 `esign sign approval batch-agree --operate-data '[{"approvalCode":"<code1>","taskId":"<id1>"},{"approvalCode":"<code2>","taskId":"<id2>"}]' --remark '<审批意见>'`；明确无意见时执行同一批量命令并传 `--remark '无'`。
5. CLI 自动轮询后保存真实结果，分别记录成功、失败、待认证及结果未知的任务。对明确需要认证的任务提供审批入口；部分成功不重新提交整批。无法对应具体任务时先只读核查，不猜哪些需要认证。

**批量拒绝审批**

1. 确定真实任务集合和完整范围；收集与该集合绑定的必填驳回原因，按已知限制校验。
2. 对集合内已明确需要认证的任务采用批量同意第3步的处理方式，不擅自缩小范围。
3. 无已明确认证要求且业务信息齐备时执行 `esign sign approval batch-refuse --operate-data '[{"approvalCode":"<code1>","taskId":"<id1>"},{"approvalCode":"<code2>","taskId":"<id2>"}]' --remark '<驳回原因>'`。
4. 结果按批量同意第5步处理，不重复提交成功或结果未知的任务。

**仅获取意愿认证地址**

1. 仅用户明确要求认证地址时，获取真实任务标识后执行 `esign sign approval will --approval-tasks '{"approvalCode":"<approvalCode>","taskId":"<taskId>"}'`；多个任务分别重复传 `--approval-tasks`。此查询不是审批提交的统一前置。
2. 有有效认证链接时返回真实链接；明确无需认证时如实说明；`success:true` 但数据为空时仅说明暂未取得认证入口，不推断认证是否必要，可获取并提供真实审批页面继续处理。
3. 仅获取入口的请求到此结束，不自动同意、拒绝或批量审批。
