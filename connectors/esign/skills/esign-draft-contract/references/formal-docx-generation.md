# 正式 DOCX 生成参考

本文件只服务 `esign-draft-contract` 的正式文件生成阶段。用户确认 Markdown 草稿后，正式 DOCX 脚本的参考来源是：

- 用户确认后的 Markdown 合同正文。
- `references/drafting-boundaries.md` 的正式文件边界。
- 本文件的 DOCX 结构和排版规则。

## 脚本契约

- 使用自包含 Python 脚本，只依赖 Python 标准库和 `python-docx`。
- 脚本保存 DOCX 到 本次任务实际可写目录中的 `<合同名称>.docx`。
- stdout 只能输出一行 JSON：`{"docx_path":"<本次实际生成DOCX的绝对路径>"}`。
- 调试信息如必须输出，只能写 stderr；不要污染 stdout。
- Python 字符串优先用单引号，正文含双引号时避免转义错误，例如 `add_body('以下简称"租赁房屋"')`。
- 文件名使用业务文档名，不使用 `output.docx`、`result.docx` 等泛化名称。

## 默认排版

- 沿用当前正式合同的排版要求。
- 页面：A4。未明确指定时使用常规 A4 页边距。
- 正文中文字体：`宋体`。
- 正文西文字体：`Times New Roman`。
- 标题中文字体：`黑体`；条款标题中文字体：`黑体`。
- 主标题字号 18 pt；条款标题字号 14 pt；正文字号 12 pt，整份文件保持一致。不要使用 22 pt 这类会明显放大标题的公文式字号。
- 正文行距：1.5 倍；首行缩进约 0.74 cm。
- 不用连续空段落制造距离；使用段前、段后、行距和单元格边距控制版面。

## Markdown 转 DOCX

- `# 合同标题` 转为居中标题段落，只保留标题文字。
- `## 第X条 标题` 转为条款标题段落，不把后续正文拼到标题同一段。
- `###` 可转为加粗小标题；没有必要时按正文处理。
- 普通条款、款项、列表转为正文段落。
- 草稿中的 `**...**` 和 `__...__` 必须转换成加粗 run，不得把 `**` 或 `__` 写入 DOCX。
- `**{待补充：xxx}**` 在 DOCX 中保留为 `{待补充：xxx}`。待补充占位符在正式文件中统一使用黑色加粗文本，不添加彩色高亮或底纹。
- 如果草稿正文被误包在代码块中，生成脚本前应移除代码块围栏，不能写入正式文件。
- 草稿后的待补充信息提示、对话引导、工具说明、内部检查说明都不是合同正文，不得写入 DOCX。

## 语义组件

脚本应先定义组件函数，再写入合同内容。建议至少包含：

- `set_run_font(run, ...)`：统一设置中文/西文字体、字号、加粗。
- `add_markdown_runs(paragraph, text)`：把 Markdown 加粗语义拆分成多个 run。
- `add_title(text)`：生成合同标题。
- `add_heading(text)`：生成条款标题。
- `add_body(text, first_line=True)`：生成正文段落。
- `add_party_grid(parties)`：生成当事人信息区。
- `add_signature_grid(parties)`：生成签署区。
- `add_page_footer(doc)`：生成页码页脚。

## 当事人信息区

- 标题后直接展示当事人信息，不加“当事人信息”等概括性小标题。
- 单方文件或单个主体：全宽单列。
- 双方主体：左右双列，左列甲方/发函方，右列乙方/收函方。
- 三方及以上：每行两列，最后落单的一方合并为全宽。
- 主体信息区不显示任何边框。双方信息仍使用左右双列布局，左右列之间保留清晰留白作为视觉分隔。
- 单元格顶部对齐，避免左右信息行数不一致时文字垂直居中。
- 当事人信息区结束后，与其后的鉴于段或第一条正文之间保留一个完整的视觉行距。优先给后续首段设置 `space_before = Pt(12)` 至 `Pt(18)`（即 12-18 pt），不得靠连续空段落撑开距离；具体数值可按正文行距微调。
- 仅对草稿正文中已有的核心缺失字段保留 `{待补充：xxx}`；不得在渲染阶段补造联系电话、邮箱、联系人、签署地点等可选字段。合同签署日期只渲染固定空白标签，不得使用待补充占位符。

## 签署区

- 签署区放在正文尾部，不作为编号条款。
- 双方主体默认双列；三方及以上按每行两列，最后落单全宽。
- 默认无外框，不加中间竖线。
- 每方先显示合同角色和主体名称或姓名。企业或组织主体使用独立字段 `盖章：`，个人主体使用独立字段 `签字：`。只有用户明确要求企业的法定代表人、负责人或授权代表签字时，才增加对应签字栏；不得从首部主体信息推导签字要求。
- 签署区不重复首部已经列明的身份证号、统一社会信用代码、法定代表人或负责人、注册地址、通讯地址、联系电话或邮箱。
- 不得使用孤立的 `（签字）`、`(签字)`、`（盖章）` 或 `(盖章)` 充当签署字段，也不得只在主体名称旁写括号提示；使用带冒号的独立字段并预留合理签署空间。
- 签署日期只渲染空白字段 `签署日期：`，冒号后不得附加日期值、空白线或待补充占位符。不自动填写当前日期，不读取系统日期，不向用户确认日期，也不设置跨日刷新逻辑。
- 签署地点只渲染草稿正文中已经存在的字段。
- 填空线长度保持稳定，避免左右栏错位。
- 签署区尽量与其前一段保持连贯，不默认强制分页。签署区标题、双方名称、签章/签字字段和签署日期应作为一个完整区块尽量保持在同一页；通过段落 `keep_with_next`、表格行禁止跨页、孤行控制和合理段前距，使签署区整体可读，同时避免签署区单独占据一张大面积空白页；不得通过缩小正文字号解决分页问题。

双列签署区的内容结构示例：

```text
甲方（委托方）：杭州某科技有限公司    乙方（受托方）：王晓明
盖章：                              签字：
签署日期：                          签署日期：
```

## 表格与固定布局

用于当事人信息区、签署区或真实数据表时，应固定表格几何：

- `table.autofit = False`。
- 设置 `tblW`、`tblLayout=fixed`、`tblGrid`。
- 为每个单元格同步设置 `tcW`。
- 设置单元格边距和垂直对齐。

真实数据表默认使用浅灰蓝表头、细灰蓝边框、固定列宽和适度单元格内边距。

- 多个重复标的、设备、货物、成果或阶段应使用正文内真实数据表；一个单元格只承载一个可独立填写的事实，例如型号、规格、编号分别设列，不得把多个待补充事实合并到一个单元格。
- 长主体名称或占位符允许在单元格内自然换行，并根据页宽设置列宽和内边距；不得裁切文字，也不得为了塞入一行而把字号降至正文标准以下。

## 分页与版面自检

- 主标题、条款标题不得出现在页末而其正文全部落到下一页；对标题使用 `keep_with_next`。
- 表格标题与首行尽量同页；整个签署区及同一签署方的签章字段不应被拆到两页。
- 除用户明确要求外，不为签署区插入固定分页符。若末页只有签署区且大面积空白，先调整前文孤行控制、表格间距和签署区段前距，再重新生成。
- 页脚应调用 `add_page_footer(doc)` 生成连续页码，并检查页码未与正文重叠。
- 正式文件完成后检查：当事人信息区后视觉间距、复合占位符、长文本换行、标题孤行、签署区分页、页码、Markdown 标记和草稿外说明。发现问题后修正脚本并重新生成，再调用交付命令。

## 交付命令

DOCX 脚本生成并自检后，只调用：

```bash
esign document finalize-draft-contract --script '<scriptPath>'
```

命令负责正式 PDF 转换及交付结果，不重复执行底层上传、下载、登记或手工追加链接参数。返回检查、失败处理与真实文件入口展示按[执行规则](execution.md)处理。

脚本必须适配当前工作目录，使用真实绝对路径，不依赖自有平台固定目录或页面会话工具。必要运行依赖缺失时按文档处理规则说明，不自动安装或升级。
