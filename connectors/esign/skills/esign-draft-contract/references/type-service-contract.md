# 服务合同起草规则

信息收集遵循 [通用规则](intake-common.md)：下列字段为按场景选用的候选，不要求首稿前补齐；首轮询问缺失立场，回复仍未说明则直接中性起草。初稿后只引导补充 2～4 个真实缺失的重要变量，不足时不凑数，不默认列出全部。

## 适用场景

适用于咨询、设计、运营、技术支持、外包服务、项目服务、维护服务等以提供服务为核心标的的合同。

不适用于以劳动关系为目的的劳动合同、以货物所有权转移为核心的买卖合同、以软件订阅为主的 SaaS 服务合同、以具体技术成果研发为主的技术开发合同。

## 角色与起草立场

- 甲方通常为委托方、采购方、付款方。
- 乙方通常为服务方、承接方、收款方。
- 代表甲方：强化服务范围、交付验收、付款条件、违约救济、资料返还。
- 代表乙方：强化服务边界、甲方配合义务、需求变更、付款保障、免责边界。

## 初稿与信息补充

服务类型或成果模式不明确且会影响合同结构时，生成初稿前集中询问；其他信息不要求先补齐。缺失的具体事实先用原子化占位符生成完整初稿，初稿展示后，可按需补充以下信息：

优先收集：

1. 服务内容和服务目标。
2. 服务期限或项目周期。
3. 服务费用和付款节点。
4. 是否有交付物。
5. 验收方式或服务确认方式。
6. 用户代表甲方还是乙方。

对应场景已经出现时，初稿展示后还可补充服务地点、资料提供、知识产权归属、是否允许转包、是否涉及保密或数据处理。联系人仅在用户提供或协作机制明确需要时补充。

## 具体信息处理

| 变量 | 初稿缺失处理 |
|---|---|
| 服务事项 | 使用原子化占位符，初稿展示后补充 |
| 服务期限 | 使用原子化占位符，初稿展示后补充 |
| 服务费用 | 使用原子化占位符，初稿展示后补充 |
| 付款方式 | 使用原子化占位符，按需补充 |
| 交付物/成果 | 无明确交付物时写服务确认机制 |
| 验收方式 | 缺失时写常规验收流程 |
| 起草立场 | 按通用首轮立场规则处理：用户首轮回复仍未说明立场时直接中性、均衡起草，不提示默认选择 |

## 可默认写入内容

- 乙方按约定服务范围、标准和期限提供服务。
- 甲方按约提供资料、确认需求、组织验收并支付费用。
- 交付物验收设置书面异议和整改复验机制。
- 需求变更需书面确认。
- 双方对合作中获悉的商业信息承担保密义务。
- 争议解决按国内民商事合同路径处理。

## 条件触发变量

- 驻场服务：补充驻场地点、人员管理、安全和考勤边界。
- 阶段交付：补充里程碑、阶段验收和阶段付款。
- 数据处理：补充数据安全、个人信息保护、访问权限、删除返还。
- 知识产权成果：补充成果归属、使用许可、第三方素材责任。
- 转包或分包：补充是否允许及责任承担。

## 标准章节结构

首部：标题后直接列明各方信息（不加小标题，不作为编号条款）。

1. 鉴于条款
2. 服务内容和服务范围
3. 服务期限和服务方式
4. 服务费用与支付
5. 交付物与验收
6. 双方权利义务
7. 需求变更
8. 知识产权
9. 保密
10. 违约责任
11. 合同变更、解除和终止
12. 不可抗力
13. 通知与送达
14. 争议解决
15. 其他约定
尾部：签署区（不作为编号章节）。

## 每章起草要求

- 服务内容：具体列明服务事项、服务目标、服务标准、服务边界。
- 服务期限：写明开始日期、结束日期、阶段节点或完成条件。
- 费用支付：写明金额、付款节点、发票、收款方式、逾期付款责任。
- 交付验收：写明交付对象、验收期限、验收标准、异议、整改、复验、逾期未验收后果。
- 双方义务：甲方资料和确认义务，乙方人员、质量、进度、报告义务。
- 需求变更：写明变更提出、评估、费用和工期调整、书面确认。
- 违约责任：区分迟延付款、迟延服务、服务不合格、擅自转包、泄密等。

## 输出前强制自检与自动补写

在通用合同质量框架基础上，逐项检查并自动补齐：服务范围及明确排除项、履行方式和双方配合、交付物或服务记录、确认/验收及异议整改、费用与付款前提、需求或工作量变更、服务不达标的补救、暂停/解除及终止结算。每个已触发节点必须写明责任人、时间或触发条件、完成标准和未履行后果；不得只写“按甲方要求服务”或把验收、变更、违约责任留作整段待补充。

持续服务应写明周期记录和结算依据；成果交付型服务应写明交付、验收、整改和复验；现场或设备相关服务应按条件加入安全、进场、停工和第三方损害处理。未触发的模块不机械加入。

## 禁止写法

- 服务范围只写"提供相关服务"。
- 验收只写"甲方验收合格"而没有标准和期限。
- 付款条件与验收条件互相矛盾。
- 代表乙方时无限承担甲方需求变化造成的延期责任。
- 代表甲方时不设置整改和解除路径。

## 生成前边界

生成草稿时应覆盖服务范围、期限、费用、付款、交付/验收、双方配合、需求变更、违约责任。正常规则适配不向用户说明，只有用户信息明显冲突时才简短提醒。

## 待补充信息规则

以下是内部核对用的字段候选，初稿后只挑实际缺失的 2～4 项友好引导：服务费用、服务期限、服务地点、交付物清单、验收标准、付款账户。联系人仅在协作机制明确需要时列入。
