# 起草边界规则

本文件仅作为内部起草约束，不得向用户输出本文件标题、内部过程或规则判断结论。

## 用户可见输出边界

草稿生成前不得输出任何内部核对过程、规则判断结论、符号化确认或过程类说明。

追问缺失变量时，只问变量，不输出日期推算、期限推算、法律规则解释、条款依据说明或附加解释类补充说明。

用户提供的信息未明显违反强制性要求时，直接追问或起草，不输出通过型结论。

用户提供的信息与强制性要求明显冲突时，只用一句话提醒并给出建议处理方式；用户仍希望保留的，继续推进草稿生成，不反复阻断。

## 缺失信息

合同正文里的缺失事实使用加粗占位符，例如：

- `**{待补充：甲方统一社会信用代码}**`
- `**{待补充：乙方身份证号}**`
- `**{待补充：合同金额}**`
- `**{待补充：服务期限}**`
- `**{待补充：交付地点}**`

一个占位符只能对应一个可独立填写的事实。不得使用 `{待补充：型号、规格及编号}`、`{待补充：付款时间、比例及方式}` 等复合占位符；应分别拆成型号、规格、编号或使用明细表，每个表格单元格只承载一个事实。多个重复标的应逐行列示或使用正文内明细表。

专业履行机制不得使用待补充占位符。付款流程、交付确认、验收异议、整改复验、维修替换、风险转移、解除结算、违约救济等应按合同类型和交易特征直接写成可执行条款；只有实际金额、既定交易日期、比例、地点、型号等真实事实无法取得时才留作占位符。尚未约定的常规通知、验收、整改等机制及合理期限可直接拟定，不能因为其中有天数就全部留空；不把拟定方案说成已有共识或法律标准。

合同主体身份必须按类型使用明确字段：个人使用姓名、身份证号；企业或组织使用名称、统一社会信用代码、法定代表人或负责人；个体工商户使用名称、统一社会信用代码、经营者姓名。不得在正式草稿中使用“身份信息”“证件信息”或“身份证号/统一社会信用代码”等笼统字段。主体类型无法可靠判断时先确认类型，不得同时输出两套字段。

准备发起签署的补齐阶段，以[文件交付与签署衔接](delivery-rules.md)的每轮3—5项规则为准，全部补齐才交付签署版本。

草稿正文后可以在对话中友好引导补充重要事实；该提示不是合同正文，不得出现在最终文件中；初稿后只选择 2～4 个实际缺失的重要变量友好引导，不默认枚举全部。

## 可选字段抑制

- 联系电话、电子邮箱、联系人、签署代表、签署地点等不是默认完整性字段。
- 用户、底稿和场景均未要求时，不追问、不提示、不生成字段、不生成待补充占位符。
- 合同签署区只保留空白字段 `签署日期：`。不自动填入当前日期或其他日期值，不追问、不确认、不生成待补充占位符，也不设置跨日刷新逻辑。
- 企业或组织主体的签署区显示角色和名称，并另起一行保留明确的 `盖章：` 字段；个人主体显示角色和姓名，并另起一行保留明确的 `签字：` 字段。只有用户明确要求法定代表人、负责人或授权代表签字时才增加对应签字栏；首部的主体身份信息不能视为签字要求。
- 签署区用于表达签署行为，不重复主体识别信息。不得重复身份证号、统一社会信用代码、法定代表人或负责人、地址、联系电话或邮箱；不得使用孤立的括号“签字”提示代替明确字段。
- 只有核心事实缺失时才使用待补充占位符；不要把“可能有用”误判为“必须补齐”。

## 正文完整性

草稿应是可供用户审阅和修改的完整正文。禁止输出：

- 只有大纲。
- 只有摘要。
- 只有条款标题。
- 只有问题清单。
- 用"后续补充"替代核心条款正文。

关键条款应形成履行闭环：

- 付款条款：金额、节点、方式、逾期责任。
- 交付条款：交付对象、时间、方式、风险或责任。
- 验收条款：标准、期限、异议、整改、复验。
- 违约条款：违约行为、责任方式、违约金/赔偿、解除权。
- 通知条款：地址、方式、生效时间、变更义务。

合同/协议类生成后必须按 `contract-quality-framework.md` 执行输出前强制自检与自动补写。发现已触发的履行节点缺失、条款只有抽象原则、专业机制被写成占位符或复杂交易明显过于简略时，先补写或重写，再向用户展示；不得输出内部检查过程。

## 起草边界

- 不编造用户未提供的事实变量。
- 不编造法律依据。
- 不写明显违法或高风险无效条款。
- 不把特定合同类型的规则误用于其他类型。
- 不默认设置过高违约金或明显单方压迫条款。
- 用户明确代表某一方时，可在合理范围内倾斜保护该方，但不得牺牲条款有效性和可执行性。

## 正式文件边界

写入正式文件的内容只能是合同正文，不包含草稿后的待补充信息提示、对话引导语或其他说明文字。草稿中的 `**{待补充：xxx}**` 只表示加粗语义；正式文件必须保留占位符文本 `{待补充：xxx}`，不得保留 `**` 字符，并以黑色加粗样式表达醒目效果。

用户已表达发起签署意图时，最终 PDF 确认是移交签署流程的硬停止点。补齐正文中的待补充变量后，必须重新生成并交付最新版 PDF，然后结束当前轮次；只有用户在后续消息中明确确认当前版本，才能移交该版本。正文发生任何修改都会使旧确认失效。
