# 合同质量框架

本文件适用于全部合同、协议类起草。它用于补足合同类型 reference 的共性执行要求，不是某一种标的物的模板。证明、通知、函件、声明、委托书等单方文书不适用本框架，按 `type-proof-letter.md` 的功能闭环生成。

## 核心原则

- 不以固定模板、固定章节数或固定字数衡量质量；以交易能否执行、异常能否处理、合同能否退出和结算为准。
- 不编造用户未提供的金额、数量、日期、地址、型号、主体身份等事实。
- 专业履行机制由本 skill 按合同类型和已识别场景直接写成完整条款，不把条款设计问题留给用户填写。
- 简单交易保持精炼；复杂交易不得因为用户信息少而只输出骨架。

## 交易特征识别

生成合同前，先在内部识别交易特征。至少检查下列信号，命中时启用对应条件模块：

- 标的是单项还是多项，能否唯一识别，是否需要正文内清单或逐项记录。
- 标的是全新、在用或二手状态，是否存在现状、历史、瑕疵、维修或权利负担问题。
- 履行是一次性、分批、分阶段还是持续性，是否存在里程碑、周期记录或滚动结算。
- 是否涉及运输、安装、调试、操作、维护、修理、替换、停机或返还。
- 是否涉及登记、备案、审批、过户、权属转移、许可或第三方同意。
- 是否需要同时交付证照、附件、配件、账号、数据、文档、源代码或其他附随资料。
- 是否可能发生灭失、损坏、停用、第三人损害、保险理赔或第三方索赔。
- 是否涉及个人信息、保密信息、知识产权、开源软件、客户资源或数据迁移。
- 是否涉及保证、代收代付、分成、对账、审计、长期结算或退出清算。

交易特征只用于内部选条款，不向用户展示风险标签或检查表。

## 条件模块

只在交易特征触发时写入对应模块，不机械堆砌：

| 模块 | 触发信号 | 至少覆盖 |
|---|---|---|
| 明细与识别 | 多项标的、编号设备、批次、多个成果 | 名称、唯一识别字段、数量/单位、状态；重复项用正文内表格 |
| 现状与历史 | 二手、在用、维修、既有瑕疵 | 已知现状、陈述保证、检查确认、隐瞒或不符时的补救 |
| 运输与交接 | 物流、现场交付、资料随附 | 交付对象、时间地点、费用、交接凭证、风险转移 |
| 安装调试与试运行 | 设备、系统或现场部署 | 双方准备、安装调试、试运行、验收、不通过处理 |
| 持续服务与记录 | 持续服务、周期履行 | 服务频次、记录、确认、缺陷整改、月度/阶段结算 |
| 维修停机与替换 | 租赁物、设备、系统可用性 | 报修、响应、费用归属、停用期间计费、替换或解除 |
| 登记过户与审批 | 车辆、股权、许可、备案 | 材料提供、办理期限、费用、配合、未办成的后果 |
| 数据与账号 | SaaS、软件、平台、数据处理 | 权限、备份、安全、导出、返还/删除、终止后的迁移 |
| 知识产权 | 研发、咨询成果、设计、软件 | 既有权利、成果归属/许可、第三方材料、侵权处理 |
| 对账分成与审计 | 分成、佣金、长期结算 | 口径、周期、凭证、异议、审计、少付漏付处理 |
| 担保与增信 | 保证、抵押、质押 | 担保主体、范围、期间、实现方式；无事实不得虚构 |
| 退出与清算 | 长期合作、阶段项目、持续服务 | 解除触发、通知/整改、在途事项、资料返还、费用结清 |

## 履行闭环矩阵

起草时在内部逐项检查以下节点。某节点与交易无关可以省略；与交易有关则必须形成可执行条款：

1. 主体、签约资格和处分/履行权限。
2. 标的、范围、数量、标准及明确排除项。
3. 对价、计价口径、税费、支付或结算节点。
4. 履行顺序、期限、地点、方式及双方配合条件。
5. 交付、验收、确认、异议、整改、复验或返还。
6. 所有权、使用权、风险、保管责任及第三方权利。
7. 延迟、瑕疵、故障、不能履行等异常处理和补救。
8. 变更、暂停、解除、终止、移交和终止结算。
9. 违约责任、实际损失、继续履行、替换/修复、解除等救济。
10. 按场景适用的保密、知识产权、不可抗力、争议和签署安排。

每个已触发的重要节点至少回答：谁负责、做什么、何时或在何种条件下做、按什么标准完成、未履行后果是什么。不能只写“双方另行协商”“依法处理”或“承担违约责任”。

## 事实、机制与可选字段

- 事实变量：只能来自用户或其已明确提供、选定的材料，不自动另找文件或独立附件。初稿前仅询问影响结构的缺口及尚未询问的立场；普通事实缺失直接使用原子化待补充占位符。初稿后少量引导补充，签署前再完整核对。
- 专业机制：依据合同类型和交易特征自动写成中性、可执行的默认条款；不得写成“待补充付款安排”“待补充违约责任”等占位符。
- 可选字段：未提供且场景未触发时直接省略，不追问、不占位。合同签署日期按全局规则只保留空白字段 `签署日期：`。
- 区分既有交易事实与本次拟定条款：真实成交价、实际日期、已谈妥比例、税率等不得编造；尚无约定的验收、通知、整改、响应等常规机制，可以结合交易背景拟定合理期限并直接写入初稿，不留大量天数空格，也不声称这些数值是法定标准、行业惯例或双方已确认事实。用户或底稿已有约定优先，不覆盖。违约金等专门约定仍按对应类型规则处理。

## 输出前强制自检与自动补写

完成草稿后、向用户展示前，必须在内部执行以下检查：

1. 根据交易特征复核已触发的条件模块。
2. 用履行闭环矩阵检查正文；发现缺失节点时直接补写或重写相关条款。
3. 检查每个重要节点是否包含责任人、行为、时间/条件、标准和未履行后果；只有抽象表述时改为可执行文本。
4. 联动核对付款、违约、解除等条款的触发条件、期限、例外；同一条件不能在不同条款里说两套，不同适用情形必须说明。检查占位符是否只承载一个事实，复合占位符必须拆开；重复标的改为正文内明细表。
5. 检查专业机制是否被错误写成占位符；发现后改为默认机制，只有不可推断的事实继续留空。
6. 检查可选字段是否被无条件生成；未触发的联系电话、邮箱、联系人、签署代表、签署地点等直接删除。
7. 复杂交易若只形成少量概括性条款，重新检查是否遗漏交付、验收、异常处理、解除和结算；不要通过重复套话凑篇幅。

这一步是内部质量控制，不得向用户展示“已通过检查”、覆盖矩阵、风险标签、评分或思考过程。完成自动补写后直接输出完整草稿。
