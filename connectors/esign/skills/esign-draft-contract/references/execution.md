# 执行规则

## 输入与底稿读取

只使用用户上传或明确选定的底稿文件、当前明确粘贴的正文。没有文件时引导上传，不自行搜索其他文件；粘贴正文直接使用。普通从零起草不要求连接或上传平台。

用户明确指定平台文件时，按实际可用的文件列表和获取能力取得选定文件或真实 fileKey；不根据文件名猜标识。多个目标无法确定时只确认具体文件，不扩展检索，不要求用户提供内部 ID。独立附件不纳入本期联合处理。

本地文件使用：

```bash
esign document extract-contract-body --file '<文件的真实可访问路径>'
```

已选平台文件且取得真实 fileKey 时使用：

```bash
esign document extract-contract-body --file-key '<真实fileKey>'
```

两种方式按来源选择一种，不重复调用。文本提取、必要转换和 OCR 由命令处理；接入、完整性检查和必要辅助核对遵循[文档处理规则](document-processing.md)。检查进程成功、业务 `code == "0"` 且 `data.content` 非空，才将实际正文交给底稿起草流程，识别真实角色与已有事实，不重复询问已提供内容。返回契约不符、空正文、链接、日志和处理中状态均不能当成成功读取。

成功仍需核对缺页、截断、表格关系和关键数字。影响起草时说明具体缺口并引导补充，不编造缺失内容，不擅自改为从零起草。用户明确改为无底稿起草时才切换。

## 正式 PDF 生成与交付

进入正式文件阶段后，以用户当前认可的完整正文生成自包含 python-docx 脚本，遵循[正式文件生成规则](formal-docx-generation.md)与[文件交付规则](delivery-rules.md)。采用本次任务实际可写目录，不硬编码自有平台路径；脚本 stdout 只输出包含真实 docx_path 的一行 JSON，调试日志写 stderr。

统一使用：

```bash
esign document finalize-draft-contract --script '<本次生成脚本的真实路径>'
```

由命令完成脚本执行、上传转换、产物登记和最终结果返回。不另行重复执行上传、转换或登记，不手工拼接下载链接，不默认走底层命令兜底。

检查进程成功、返回可解析、业务 `code == "0"`，且 `data.url` 是真实可访问的 PDF 入口，才交付正式 PDF；不能将 DOCX、中间产物、卡片描述或错误页面冒充 PDF。已有真实文件入口按 WorkBuddy 可用方式展示，不调用自有页面专用发布工具。链接期限只在实际返回或明确契约支持时说明。

保存实际返回的 `data.fileKey`、`data.fileName`、`data.url`，与当前正文版本关联，供后续发起。没有发送所需标识时不得猜测或使用旧文件；PDF确已交付而发送引用缺失时，如实区分已交付与衔接受阻。文件已变更而新文件未生成成功时，不用旧 PDF 冒充更新结果。

生成、转换、登记或访问失败时保留当前正文和已知阶段结果，只说明实际受阻步骤；结果不明时先核对已产生的文件或实际状态，不直接重跑整条命令。命令依赖或返回不符合契约时停止该交付步骤，不切生产或改用未经验证的输出方式。

对用户只提供实际文件入口和简短查看、修改或签署引导，不展示生成脚本、转换过程、产物登记、检查表或排版日志。正文一致性和排版检查仍在内部完成。

## 签署衔接

按[文件交付与签署衔接](delivery-rules.md)处理：准备签署时先每轮3—5项补齐核心必要事实，消除所有待补充项后生成当前 PDF。最新版 PDF 交付后结束当前轮次；用户后续确认当前 PDF 并要求发起后，才交给实际可用的签署能力。正文再次变更使旧文件确认失效。

将当前版本的真实文件及可用平台引用交给发起合同能力，不要求重复上传，不拿已有流程签署入口代替新建签署流程。接收方按当前主体权限核实能否复用，不能跨主体复用未知有效的引用。
