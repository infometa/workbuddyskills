# 通用信息收集规则

## 目标

帮助用户从自然语言、上传底稿或粘贴长文本开始起草合同和文书。采用“先出初稿，再补信息”的顺序：先识别文档类型、已有材料和基本交易结构，尽快生成完整初稿；用户查看条款安排后，再补充具体事实。

## 文档类型识别

优先识别以下类型：

- 合同类：服务合同、劳动合同、买卖/采购合同、租赁合同、保密协议、借款合同、委托合同、合作协议、技术开发合同、SaaS/软件服务合同、股权转让协议、咨询顾问合同等。
- 文书类：证明、通知/告知/催告函、声明、承诺函、授权委托书、申请书、情况说明、邀请函、确认书、收据等。

类型无法判断时，不直接生成正文，先向用户确认。用户已提供底稿时，先从底稿识别类型，不重复询问底稿中已有的信息。

## 通用首次提问

用户只说“起草合同”“写协议”时，用一组编号问题了解合同类型和基本交易结构。生成初稿前原则上只集中询问一次，每次 3-5 个问题；问题数是上限，不需要凑满。不要使用解释性引导语，不要额外询问“合同类还是证明函件类”。

示例：

> 好的，先确认几项会影响合同安排的信息，暂时不确定的可以先不填：
>
> 1. 要起草哪类合同？比如劳动合同、服务合同、买卖合同、租赁合同、保密协议、借款合同等。
> 2. 你代表合同中的哪一方？例如买方、卖方、出租方、承租方、用人单位或劳动者。
> 3. 合同双方分别是个人、企业还是其他组织？已经能从现有信息判断的无需重复说明。
> 4. 合同核心事项是什么？比如岗位/薪资、服务内容、货物信息、租赁物、金额、期限等。

如果用户已经提供其中部分信息，询问尚未明确且尚未问过的起草立场，以及仍缺失且会改变文书类型、主体字段结构或交易模型的内容，不重复询问。主体名称、证件号码、金额、具体日期、账号、型号、编号等事实值缺失时，不在生成初稿前追问，使用原子化占位符处理。

用户可见提问使用自然表达，不暴露内部处理阶段。不得向用户展示“第一轮”“第二轮”“本轮”或“进入下一轮”等流程词。

用户回复后原则上直接生成完整初稿。只有合同或文书类型、主体类型或交易模型仍无法判断，且无法选择合理正文结构时，才针对该关键点补问一次：

> 收到。还需要确认以下信息：

不得重新展开一轮信息收集，也不得因普通事实值仍然缺失而延迟出稿。

## 已知信息提取

用户回复后，先提取已有信息，再决定是否追问。不要重复询问用户已经明确提供的内容。

通用字段包括：

| 字段 | 说明 |
|---|---|
| documentType | 合同、协议、证明、通知、函件、声明、委托书等 |
| contractType | 劳动、服务、买卖、租赁、保密、借款等 |
| partyA | 甲方/出具方/用人单位/出租方/出借方等 |
| partyB | 乙方/接收方/劳动者/承租方/借款方等 |
| partyType | 个人、企业或组织、个体工商户 |
| partyIdentity | 与主体类型匹配的明确身份字段 |
| perspective | 用户代表哪一方 |
| subjectMatter | 标的、岗位、服务、货物、房屋、借款、合作事项 |
| amount | 金额、单价、租金、工资、服务费等 |
| term | 合同期限、服务期限、租期、借款期限等 |
| place | 履行地、交付地、工作地点、房屋地址等 |
| payment | 付款节点、发薪日、支付周期、还款方式 |
| deliveryOrAcceptance | 交付、验收、入职、返还、结算等 |

## 补充回复的逐字段映射

在正式生成或发起签署前补齐占位符时，内部维护仍待补充的字段列表，并遵守以下规则：

- 只将能够与某一待补充字段唯一对应的回复标记为已补充。用户使用字段名、合同角色、主体名称明确指向，或者回复数量、顺序和格式与全部待补充字段一一对应时，可以直接映射。
- 存在歧义、冲突或无法唯一对应时，不得根据常识猜测。只记录已经明确的值，保留相关占位符，并用主体角色和名称重新询问。
- 用户只回复部分值时，不得把未回复字段标记为已完成；只继续询问剩余字段，不重复询问已经明确映射的内容。
- 回复格式明显不完整时不得清除字段。例如只说“招商银行”不能视为已经提供“开户银行及支行”；普通姓名不能视为身份证号。
- 账户户名、主体姓名、联系人姓名等值可能相同，但字段含义不同。用户没有明确指向时必须确认，不能因为文本相同就自动复用。
- 只有仍待补充字段列表为空且正文复扫不存在占位符时，才能说明信息已经齐全。

追问时使用明确字段，不使用“您的身份信息”等模糊说法。例如：

1. 甲方（出借人）张磊的身份证号。
2. 乙方（借款人）董红建的身份证号。
3. 乙方收款账户户名。
4. 乙方收款开户银行（请具体到支行）。
5. 乙方收款账号。

## 主体类型识别

先使用用户消息、底稿和字段内容判断主体类型，不重复询问已经能够可靠识别的类型：

- 用户明确说“个人、自然人、本人、先生、女士”，提供普通中文姓名且上下文没有机构或经营主体特征，或者提供身份证号时，可以判断为个人主体。
- 名称包含“公司、有限责任公司、股份有限公司、集团、银行、学校、医院、协会、基金会、委员会”等明确企业或组织特征，或者用户提供统一社会信用代码、法定代表人/负责人时，可以判断为企业或组织主体。
- 用户明确说“个体工商户、个体户、经营者”，或营业执照信息明确标示为个体工商户时，可以判断为个体工商户。仅出现“店、经营部、工作室”等名称不足以确认，仍需结合上下文判断。
- 品牌简称、英文名、项目名、门店简称、个人姓名与商号混用等情况不能可靠判断。主体类型无法可靠判断时，只追问一个问题确认主体类型，不得同时生成个人和企业两套字段。
- 名称特征只能用于选择字段结构，不能用于编造证件号码、法定代表人、负责人或经营者姓名；用户后续信息与推断冲突时，立即按新信息改正。

合同主体信息必须使用明确字段：

- 个人主体：姓名、身份证号。
- 企业或组织主体：名称、统一社会信用代码、法定代表人或负责人。
- 个体工商户：名称、统一社会信用代码、经营者姓名。

不得在正式草稿中使用“身份信息”“证件信息”“身份证号/统一社会信用代码”等合并或模糊字段。缺失值应写成与已识别主体类型对应的明确占位符，例如 `**{待补充：出卖方身份证号}**` 或 `**{待补充：承租方统一社会信用代码}**`。

证明、通知等文书中的对象不当然是合同主体；只有文书功能需要唯一识别对象时，才按上述规则加入相应身份字段。

## 字段分层与使用顺序

除首轮尚未明确的起草立场外，生成初稿前只询问以下会阻止选择正文结构的信息：

1. 合同类型。
2. 合同双方的主体类型，或者文件出具方/接收方的角色类型。
3. 核心标的类别或核心事项。
4. 会导致合同采用不同权利义务结构的交易模型。

起草立场按通用首轮立场规则处理：用户首轮回复仍未说明立场时直接中性、均衡起草，不提示默认选择。主体名称及身份号码、金额、期限、履行地点、付款日期、账户、型号、编号等事实值可以先使用原子化占位符，不作为初稿生成前的必问项。

条件字段只在场景明确触发时按需补充；其普通事实缺失不阻塞初稿，例如发票、保证、安装、装修、转租、联系人、专门送达地址。

以下属于展示型可选字段：

- 联系电话。
- 电子邮箱。
- 联系人。
- 签署人姓名。
- 签署地点。

用户未提供且未要求时，不追问、不提示补齐、不在正文或签署区生成字段，也不生成待补充占位符。合同签署日期例外：签署区始终只保留空白标签 `签署日期：`，不收集日期值、不自动填写当前日期，也不生成待补充占位符。通讯/联系地址只有用于主体识别、标的定位或送达机制时才是条件字段；否则同样省略。

## 底稿优先与提问顺序

基于底稿起草时，先取得并读取用户指定文件，再执行必要的信息收集。无文件只引导上传并等待，不把“首轮集中询问”理解为同时让用户选未知角色。已读出的类型、主体和交易信息不再问。选项使用实际角色及必要名称，不硬套甲乙方或默认双方；从零起草可以开放了解交易与立场，无需先上传。

## 起草立场

用户已经说明立场时直接采用。基于底稿时先按上述顺序取得并读取底稿。尚未说明时，将“你希望主要保护哪一方，还是双方均衡？”放进首轮必要问题；其他信息足够时可以只问这一项，不凑题数。用户首轮回复仍未说明、跳过或暂不确定时，直接中性、均衡起草，不再追问立场，不提示采用默认立场。尚未收到回复不等于用户已经跳过；后续明确立场时据此调整。

## 初稿展示与后续补充

- 已经足以确定文书类型和基本交易结构，且立场已明确或已完成首轮询问时，直接生成完整初稿，不继续追问具体事实。
- 正文展示后友好邀请修改条款，并挑选 2～4 个真实缺失的重要变量引导补充；不足 2 个按实际数量，没有缺失就不凑数。用户可以先改条款，暂未确定的事实保留占位，不反复催填。
- 初稿必须包含完整条款正文，不得只输出大纲、章节标题或问题清单。
- 初稿展示后不主动复述全部待补充字段，不使用“合同大纲”“可审阅范本”“待补充字段可以后续逐项填写”等流程化表达。
- 用户提出修改时直接更新文本；用户直接补充具体信息，或在同一消息中同时提出修改和补充信息时，一并处理，不要求先回复固定确认语。
- 问题可以按自然的信息组组织，但合同中的每个待补充占位符仍只能对应一个可独立填写的事实。
- 用户暂时无法提供的核心事实继续保留原子化待补充项；非核心或可选信息直接省略，不生成占位符。

## 追问输出边界

- 只问缺失变量，不输出日期推算、期限推算、法律规则解释、条款依据说明或通过型结论。
- 用户给出的信息未明显违反强制性要求时，直接继续追问或生成草稿。
- 需要提示风险时，只用一句话给出建议值，不反复阻断。

## 不应直接追问的问题

不要把专业条款设计直接抛给用户，例如：

- 是否需要设置复杂违约责任结构。
- 是否选择仲裁或诉讼的法律策略。
- 是否采用某种专业法律术语。
- 是否需要不可抗力、通知送达等常规条款。

这些应由对应 reference 按合同类型和交易场景写入，用户需要修改时再调整。

准备发起签署时，补齐阶段优先遵循[文件交付与签署衔接](delivery-rules.md)：每轮3—5项核心未知事实，全部补齐后生成并确认最新文件；不将初稿后少量引导变成完整字段长清单。
