# 平台接入与发送主体

## 接入与真实身份

本地文件按文档处理规则读取；涉及远端转换或 OCR，以及文件上传、模板选择、草稿与最终发送时需访问 e签宝。已有有效连接就继续，不重复登录。CLI自管登录态且未知时可用 `esign auth status`；授权失效通过已有连接或授权入口恢复，不索取、读取或回显凭据，不擅自切账号或环境。

使用已确认可执行的 CLI 入口。短命令找不到时，先按[CLI 检测与安装](cli-bootstrap.md)检查已有安装路径；确认未安装才执行安装，验证成功后继续原步骤。不把命令缺失当成业务不支持，不自动升级已有 CLI，不扫描用户文件。

在平台文件注册、模板查询或创建草稿前，取得真实当前企业与可用企业身份列表。使用 `esign auth tenant list`；本业务按已确认约定，将当前账号可用企业列表作为当前授权主体列表。数量以完整成功结果中的唯一真实主体为准，不把分页、过滤结果、请求失败或字段缺失当成只有一个主体。当前主体必须来自真实执行身份或明确返回，不能从合同抬头、签署方名称或列表第一项推断。

## 单主体与多主体

- 只有一个授权主体且与当前执行身份一致：直接沿用，不额外问主体、不增加选择步骤；正常签署信息确认仍保留。身份不一致时先核实并纠正实际上下文，不能只改展示名称就发送。
- 多个授权主体：默认沿用真实当前主体，不在前面单独弹主体选择。在同一份发送信息中展示“发送主体：实际名称（当前主体）”，同时展示文件或模板及签署人；缺联系人时也在这份信息中补齐。
- 用户对这份完整信息说“确认”“可以发”，就是确认其中的主体及签署配置，无需再单独说“以当前主体发送”。用户已明确指定某个授权主体时，按指定处理，不默认回当前主体。
- 发送主体和合同签署方分别记录，不能把发起企业自动加入签署名单。
- 没有可用主体或无法确认当前主体时，说明具体缺口并保留任务，不能按单主体分支跳过检查。真实权限或状态问题按实际原因说明，不误报为整个能力不支持。

## 更换主体后重建

用户明确要求切换，且目标在真实授权列表中才使用现有企业切换能力；`esign auth tenant set` 的入参按当前实际帮助或已验证调用契约使用，不猜标识或旗标。核对返回和当前身份确实变为目标企业，失败不继续。

按旧草稿不能跨主体复用处理：切换后停止使用旧 `draftId`，清除旧检查结果、文件/模板绑定及发送授权。保留用户原任务和其明确提供的签署信息；在新主体下重新校验或注册文件，再新建草稿。已选模板要重新核对新主体可访问性及真实配置，不因同名就复用旧ID；无法确认需用户选择该主体下的可用模板。

用户只要求换主体时，展示新主体及最新完整发送信息，再等待确认；不单开主体确认，也不默默提交旧草稿。不在切换时撤回、删除或提交旧草稿。不能为降低重填成本复用跨主体未知有效性的标识。

最终发送前核对当前执行身份仍与本任务记录和确认信息一致。等待期间被外部切换，或账号/环境改变时按同样规则失效处理，不在新身份下提交旧草稿。

## 文件读取与发送注册

先使用用户上传、选定的实际文件。只有需要从文件识别签署人时才使用 `esign document extract-contract-body`，按[文档处理规则](document-processing.md)传入真实本地路径或已选文件的真实 fileKey。用户已提供完整签署名单时不强制抽取或 OCR，不将识别结果合并进用户名单。用户仅有正文时先由合同起草等真实文件生成能力产出并确认可发送文件，本 Skill 不改写正文。

实际发送前，当前同版本文件已有有效且本主体可用的平台引用时直接复用；只有缺少可用引用时，使用真实平台上传能力：

```bash
esign file upload --file '<用户选定文件的真实可访问路径>'
```

DOC/DOCX只有发送接入确需转PDF时，才按命令支持添加 `--convert2Pdf`；本地阅读不因此强制走平台转换。返回真实文件标识和名称后映射为草稿 `files` 要求的 `file_key`、`file_name`。校验上传结果和文件对应关系，不猜返回字段、路径或文件名。命令只返回URL而缺少可注册引用时核实实际契约，不能伪造。

上游起草已经交付当前文件，可直接接续，不让用户重复上传。上游或明确平台文件目标已有可靠可用的文件引用时，只在当前主体权限及文件对应关系可验证的前提下复用；这是发送接口内部参数，不要求第三方用户提供 `fileKey`。切换主体后重新确认可访问和可注册，必要时重新上传明确选定的文件，不跨主体猜测复用。

## 一份文本发送信息

不用内部卡片工具。使用实际数据以文本或简短表格展示当前文件/模板及签署信息；授权多主体时加入当前发送主体。没有信息的可选项不显示，必要联系人缺失则标明待补充并集中询问。不要把签署信息识别和最终发送拆成两次重复确认，不展示CLI命令、内部ID或日志。

检查返回只有卡片、无法读取实际签署信息或明确业务结果时，不能宣称检查通过；通过已有实际可用的结构化/文本输出取得数据，缺少能力则说明受阻。用户补齐必要字段并明确同意发送时，按[确认规则](confirmation.md)处理，不额外问一次“是否以这个主体发送”。

## 套餐余量或余额不足

- 适用于 `esign sign draft submit` 检查和带 `--yes` 的真正发送。读取实际业务结果及 `message`；只有明确说明电子签名套餐余量、份数或余额不足时才进入本分支。不能仅凭 `code: FAILED`、存在 `url` 或非零退出码推断余额不足。
- 提交因套餐不足明确失败时，直接说明“合同未发送成功，电子签名套餐余量不足”，并在同一条回复中展示本次 CLI 返回的真实 `url`，使用链接文字为“购买套餐”、目标为该真实 URL 的可点击 Markdown 链接。检查阶段发现不足则说“当前套餐余量不足，暂无法发送”，不把检查描述为已执行发送。业务返回的购买入口是用户继续操作所需信息，不属于应隐藏的技术日志。
- `url` 是普通 URL 时直接作为链接目标；如果返回值本身是 Markdown 链接，提取其真实链接目标，避免嵌套 Markdown。仅清理明确的展示包装，不补写或猜测域名、路径、查询参数，不硬编码示例地址。值损坏或链接目标无法可靠确定时，按缺少有效链接处理。
- 没有返回有效购买链接时，说明“当前未返回可用的购买链接，请进入 e签宝平台的套餐管理页面订购”，不伪造链接；其他失败类型按实际原因处理，不套用套餐不足话术。
- 不回显命令、内部草稿 ID、错误码或完整 JSON。保留本任务的草稿、文件和签署信息；不为此重建草稿、不自动购买、不自动轮询余额或反复发送。用户完成订购并明确要求继续发送后，核对当前主体、草稿配置及发送授权仍对应本次任务，再按原有检查和确认规则继续。结果不明或超时仍按[结果与恢复规则](recovery.md)核查，不能当成明确失败直接重放。

用户回复示例（仅适用于本次返回该真实链接的情况，不是默认购买地址）：

> 合同未发送成功，电子签名套餐余量不足。[购买套餐](https://web.esign.cn/organ-manage/account/info)。订购完成后告诉我继续发送即可。
