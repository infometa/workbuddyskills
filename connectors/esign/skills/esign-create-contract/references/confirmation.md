# 发送信息与确认

## 一份信息，完成核对与补齐

发送信息包括实际合同文件或所选模板、可辨识的流程名称，以及当前签署名单中的主体类型、名称、企业签署联系人、手机号或邮箱。签署顺序、审批流、发起部门等仅在实际适用且已知时展示。平台额外展示要求由[执行规则](execution.md)处理，不额外拆确认轮次。

有缺项时用同一份信息引导补充，而不是先取得一句“确认发送”再调用发送发现缺项。比如：

> 合同：用户已选的采购合同.pdf  
> 签署方：用户已提供的乙公司  
> 签署联系人及手机号或邮箱：待补充  
> 请补充乙公司的签署联系人和手机号或邮箱；其他信息需要修改，也可以一起告诉我。

以上只是文案示意，名称必须换成当前真实已知内容。无缺项时直接请用户确认本次发送信息，无需复述固定口令。不额外生成确认报告文件。

## 判断用户回复

| 用户回复 | 动作 |
| --- | --- |
| 只补手机号/联系人或只要求修改 | 更新草稿，重新检查，展示最新完整发送信息，等待同意发送 |
| 已展示本次发送信息，用户精确补齐缺项或修改现有签署人字段，并说“其他不变，可以发” | 实际更新并检查，确认最新配置恰好等于已展示内容加用户明确变更，无其他差异且信息齐全时直接发送，不再确认一遍 |
| 信息完整且检查通过后说“确认”“可以发”“就这样发” | 当前配置与已展示内容一致才发送 |
| 信息缺失时只说“确认” | 仍请补齐具体缺项，不发送、不猜值 |
| 更换文件/模板、增删或替换签署人集合，或后台产生用户未见的配置变化 | 更新后展示当前完整发送信息，不使用旧确认 |
| 取消、先别发、暂不发送 | 停止提交，清除待发送授权，保留必要材料供之后明确恢复 |

信息是否完整、用户是否授权、草稿检查是否通过是三个独立条件，不能互相代替。用户初始一句“帮我发合同”没有覆盖尚未选定的文件或未知签署人；命令返回的“请确认”等业务文字也不是用户同意。

## 更新后的CLI检查

签署信息通过 `draft set` 实际更新后，再执行不带 `--yes` 的 `draft submit`，核对返回中的当前配置或真实检查结果。没有卡片不等于有缺项；有卡片也不代表最新草稿全部字段已知且检查成功。已知缺项在调用前先补齐，服务端检查仅负责剩余的真实业务校验。

“补齐并明确可以发”的情形不强制再发布一张卡片或问一遍；若返回了额外修改、未知项、错误或待处理要求，则停止自动推进并解释具体问题。其余需要用户确认时，按执行规则展示一次卡片或文本并等待，不在同一轮自行回答确认。

签署信息、文件及草稿状态要绑定当前任务；拿不到真实检查结果、无法确认用户授权覆盖最终配置时不执行 `--yes`。用户当前的精确修改可以更新授权范围，但不能涵盖助手自行添加的人员、文件或设置。


## 审批流与必要设置

- 判断依据是当前主体和任务的真实业务规则或明确返回。“有审批流候选列表”既不证明必选，也不证明可不选；未知时先核对真实能力说明，不自造字段、不通过真正发送试探。
- 必选且未确定时，直接列当前主体下真实可用审批流，逐项名称及必要区分信息，友好说“本次发起需要选择审批流，请选择一个”。不先问是否要审批、不展示内部ID、不把多个名字塞入长括号。读取失败或无可用项时说明具体阻塞，不默认绕过。
- 已有明确有效选择或模板已固定适用审批流时沿用，在当前发送信息中展示，不重复选择。可选且未请求设置时不因返回列表就强加选择；保留实际已有配置，不擅自清除审批。
- 用户选择后实际设置并核对；必要项齐全才引导最终发送确认。用户仅选审批流不自动等于批准发送；若已展示完整发送信息，用户精确补齐所列审批选择并明确“其他不变，可以发”，且实际结果无其他变化或缺项，可按该授权继续，不再重复确认。
- 发起部门等同理：仅实际需要且缺失才收集，与当前相关缺项一起处理。当前CLI设置审批模板时要求发起部门；已有有效部门直接沿用，否则与审批流一起提供真实选项或引导补充，不增加无必要确认。此处是新建流程的审批配置，不改变已有合同审批的意愿认证规则。

## 简洁交互示例

- 缺信息：“已选用‘实际模板名称’，请补充签署方信息。”仅列当前真实缺失字段；已知信息不重问。
- 信息完整：“请确认以下发送信息。”随后展示当前文件／模板、名称、签署人及实际必要设置，主体展示依执行规则。
- 不在这些回复前后加“草稿绑定完成”“平台检查通过”“返回请确认”“名单变化所以再核对”“补齐后重新检查”等说明。内部设置与检查照常进行。
