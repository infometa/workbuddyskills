# 签署信息来源与完整性

## 名单来源只能选定一套

1. 用户对本次任务明确提供或修改的签署信息优先。使用用户名单；缺名字、联系人或联系方式就请用户补充，不再从文件里拼入其他人或补齐未提供的联系人字段。用户提供的信息与正文有明确冲突时简短指出具体冲突，不擅自覆盖用户信息或修改正文。
2. 用户没有提供签署人，文件发送才从所选合同识别候选。企业主体与签署联系人分别识别，手机号、邮箱须能可靠对应具体联系人。正文中的收货人、业务联系人、法定代表人不能无依据地当成实际签署联系人；甲乙丙方也不自动等于所有应签人。
3. 模板发送、用户未提供名单时使用模板实际返回的签署配置供确认，不自行读取其他文件补名单。模板默认名单与用户提供名单不得拼接。
4. 用户后续明确修改某人的字段时，更新同一名单中的对应对象并保留其余未改项；用户明确增加、删除或替换签署人时，按其意图更新完整数组。这不属于自动合并不同来源名单。指代不清只澄清对应对象，不猜。

## 提前检查，而非等待发送报错

| 类型 | 最少必要信息 |
| --- | --- |
| 企业 | `type=enterprise`、企业名称`name`、签署联系人`contactName`、`phone`或`email`至少一个 |
| 个人 | `type=individual`、自然人姓名`name`、`phone`或`email`至少一个 |

类型不明不同时套两套字段；发送主体不自动加入签署名单。不可从企业名或平台账号猜联系人，不补造手机号或邮箱。不要求两种联系方式都填，已有一种可靠接收账号即可。格式检查不等于号码归属、实名认证或实际可送达已验证。

展示发送信息时同时标出本次真正缺少的字段，集中请用户补充；已知字段不重复问。尚未取得任何签署名单时请其提供，不展示虚构的甲方/乙方名单。缺失项只是对话中的提示，不把“待补充”等文字写入CLI参数。

信息完整后才用CLI做草稿业务检查；如果后台返回额外必填项或格式不符，只说明具体字段并回到同一份发送信息补齐，不把检查失败说成合同已经发送失败，也不重新开启整个流程。
