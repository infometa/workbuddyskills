# 系统域 — 操作日志（审计留痕）

## 它记录什么

运营端产生的**写操作**：新增、编辑、删除、启停、审核、导入导出等。由公共切面在接口层自动采集，落库为操作日志文档，包含：

| 字段 | 含义 |
|---|---|
| `module` / `action` | 业务模块与动作（中文语义词，检索时均为精确匹配） |
| `targetId` | 操作对象 ID（如商品、活动、订单号） |
| `description` | 一句话描述，由路由语义模板生成；未登记语义时退化为「操作人 + 方法 + 路径」 |
| `operatorName` / `operatorId` | 操作人 |
| `uri` / `httpMethod` / `requestBody` / `responseCode` | 请求与响应概要；`requestBody` 已脱敏 |
| `success` | 是否成功 |
| `ip` / `ipRegion` | 来源 IP 与归属地 |
| `costMs` / `createdTime` | 耗时（毫秒）与发生时间（毫秒时间戳，倒序返回） |

## 请求体怎么读（`requestBody`）

`requestBody` 是**提交参数的 JSON 字符串**，字段多为英文驼峰（`spuId`、`status`、`auditRemark`、`items[]`），直接念给用户等于没说。必须先解析，再翻译成业务语言：

| 步骤 | 要求 |
|---|---|
| 解析 | JSON 字符串先解析；为空、`{}` 或非 JSON 就说明「本次操作无提交参数」，不要臆测 |
| 翻译 | 英文驼峰字段翻成业务含义（`status: ON_SHELF` → 上架；`items[]` → 明细条目） |
| 取舍 | 只讲与本次操作相关的字段（目标对象、关键变更值、备注）；技术字段（`_t`、trace、签名、分页参数）不讲 |
| 摘要 | 明细数组先给条数与代表项（「共 12 个 SKU」），用户追问再展开，不要整段罗列 |

示例：`description` 为「张三 审核通过了商品 2058365707555589633」，`requestBody` 为 `{"spuId":"2058365707555589633","auditRemark":"资料齐全","phone":"13812345678"}`。

正确表述：「张三审核通过了商品 2058365707555589633，备注『资料齐全』」——手机号不出现在回复里。

## 用 `uri` 关联业务域接口描述

`uri` 是**原始请求路径、不含 query**（形如 `/admin/product/spu/2058365707555589633/audit`），配合 `httpMethod` 可以定位到具体业务接口，从而借业务域的接口描述翻译参数——业务域 Skill 的入参表与 `requestBody` 是同一套字段，字段名与取值含义可直接对照。

**第一步：uri 第二段定位业务域**（下表按现有全部已开放能力统计，收敛且稳定）

| uri 前缀（`/admin/…`） | 业务域 | Skill 目录 |
|---|---|---|
| `product` | 商品域 | `skills/product` |
| `trade` | 交易域 | `skills/trade` |
| `promotion`、`coupon`、`coupon-template` | 促销域 | `skills/promotion` |
| `marketing` | 营销域 | `skills/marketing` |
| `merchant`、`decoration`、`material`、`region` | 商户域 | `skills/merchant` |
| `member`、`member-level`、`member-benefit`、`point`、`growth-task`、`upgrade-gift`、`user`、`feedback` | 会员域 | `skills/member` |
| `live` | 直播域 | `skills/live` |
| `logistics` | 物流域 | `skills/logistics` |
| `data-tag` | 数据标签域 | `skills/data-tag` |
| `common` | 系统域（本域自身） | — |

**第二步：在该域接口描述里定位接口并翻译**

1. 把 uri 中的长数字 ID 段视为占位（`/admin/product/spu/2058365707555589633/audit` → `/admin/product/spu/{id}/audit`）。
2. 用 `httpMethod` + 这个形态，在该域 `references/apis/<domain>/*.md` 里找对应的接口条目（按路径与语义最接近者）。
3. 用该条目的**入参表**翻译 `requestBody` 的每个字段：字段名→中文含义，枚举值→字典含义（如 `status` 0/1 各代表什么）。
4. 该域文档里的出参说明同样可用于解释本次操作影响了什么。

**兜底与边界**

- 先读 `description`（服务端已生成的一句话摘要），再用 uri 补细节；两者冲突时以 `description` 为准，`requestBody` 为准的原始参数最能反映实际提交值。
- 找不到对应接口很正常——**多数后端接口并未对外登记能力**。此时按字段名字面直译，并说明「该接口尚未对外登记，按参数名直译」，**不得编造接口含义**。
- 关联只用于「读懂」，不代表可以反过来调用：日志里的 uri 属于历史留痕，执行任何操作都必须走对应业务域已开放的能力。
- 跨 Skill 目录读取请用本地文件读取工具按路径打开（本域文档不提供跨目录链接）。

## 输出脱敏纪律（Agent 侧强制执行）

服务端只对固定的口令、令牌、密钥、证件、银行卡等键名做脱敏，且**只处理顶层字段**；手机号、收货地址、邮箱、金额等不在其列，嵌套对象里的敏感键也漏网。因此**无论上游返回是否已脱敏，回复用户时一律执行**：

| 信息 | 处理 |
|---|---|
| 手机号 / 电话 | 保留前 3 后 4（`138****5678`） |
| 身份证 / 银行卡 / 证件号 | 只留末 4 位，或整体写「已隐藏」 |
| 收货 / 详细地址 | 只到省市区，门牌与详细地址隐藏 |
| 密码 / 令牌 / 密钥 / 授权码 / 短信码 | 一律「已隐藏」，**绝不复述**，即便显示已被替换成星号 |
| 姓名 / 昵称 | 审计需要时可保留操作人姓名；被操作对象的个人信息非必要不全量罗列 |
| 金额 / 价格 / 库存 | 可保留（审计场景需要核对） |
| 拿不准是否敏感 | 按敏感处理 |

另两条硬约束：

- **禁止把 `requestBody` 原样整段贴给用户**，也禁止全量罗列内部 ID 清单——摘要成「共 N 个对象 + 代表项」。
- 日志里看不到某个字段，不等于该字段没提交（采集可能截断或嵌套未展开），不要据此断言。

## 采集边界（决定查全率）

1. **只采 `/admin/**` 的非 GET 请求**——纯查询动作（列表、详情）不产生日志。
2. 日志查询接口自身、`/internal/**`、健康检查与监控端点被排除，不会自递归。
3. **按服务开启**：只有开启了采集的服务才写日志，未开启的服务的操作不会出现在结果里。
4. **语义登记决定可读性与可检索性**：`module`/`action` 来自路由语义（配置、缓存、语义表或兜底推断），取值为中文语义词，**没有固定枚举**，只能用筛选接口取到的值。未登记语义的接口可能缺这两个字段；`keyword` 只匹配 `description`，不做全文检索。
5. **两个筛选字段的匹配方式**：`module` 与 `action` 均为**精确匹配**（必须完全相等，否则零结果），取值只能来自筛选选项；不确定精确值时宁可只用 `keyword`/`operatorName` 宽筛，也不要猜值。

## 租户边界

结果恒为当前授权账号所属租户的日志，服务端按登录态强制过滤，**不需要也不能指定租户**。若当前连接的账号属于平台侧超管，其可见范围由服务端权限决定——此时不得把结果当作单租户结论输出。

## 与分析域的分工

- 本域回答「谁做了什么」（操作审计，单条事件）。
- 经营指标、趋势、归因走分析域（数仓指标与 SQL），两者数据源不同，不要互相印证后下结论。
