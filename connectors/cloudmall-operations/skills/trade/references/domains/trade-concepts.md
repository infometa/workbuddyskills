# 交易域 — 实体模型与业务概念

> 实体模型、对象标识边界、发货方式分野、资金链路、配置体系、关键业务规则与实现缺口。
> 状态机迁移与枚举值查 `trade-enums.md`（文中枚举名均在该表）；物流子域实体见 `logistics.md`。
> 能力契约见 `references/apis/trade/`，操作流程见 `references/flows/`。

---

## 核心实体模型

| 实体 | 关系与关键语义 |
|---|---|
| 订单（Order） | 交易凭证。`ParentOrder 1:N Order 1:N OrderItem`——一个父订单拆多个子订单，每个子订单多个商品行；同一 SKU 可出现多行。发货按商品行（`bizItemId`），售后按售后商品行（`orderItemId`），两类行标识不通用。 |
| 周期购（PeriodBuy） | 一次购买按周期分多期履约：`PeriodBuyParentOrder 1:N PeriodBuyChildOrder`，每期子单独立发货、独立售后；`expectedShipTime` 可运营修改。购买单聚合态 `PERIOD_FULFILLING` 仅 ES 聚合不落 DB。 |
| 支付单（PayOrder） | `Order 1:1 PayOrder 1:N RefundOrder`（一次支付可多次部分退款）。`payType`（现金/积分混合）、`channelCode`、微信发货上报状态 `shippingReported`。合并支付场景一个支付单对应多个子订单（`child-orders` 反查）。 |
| 退款单（RefundOrder） | 记录每次退款的金额/状态/关联支付单；失败可手动重试（护栏见支付契约）。 |
| 售后单（AfterSale） | `OrderItem` 关联售后记录；售后状态、订单状态、退款状态三者独立演进。 |
| 发票（Invoice） | `Order 1:1 Invoice`（含明细行），关联销方 `InvoiceSeller` 与开票平台 `InvoicePlatformConfig`；税收配置=税收分类编码 `TaxCategory` + 商品类目映射 `GoodsTaxMapping`。蓝票/红票，红冲产生新红票。 |
| 对账（Reconcile） | `ReconcileTask 1:N ReconcileDiff 1:N ReconcileHandleLog`。 |
| 服务订单（ServiceOrder） | 服务类商品履约：购买单 1:N 履约子单（按次数拆），三层标识见下文服务订单节。 |
| 预约单（Appointment） | 到店服务预约凭证，独立状态机（小写枚举），与订单/服务订单均不同体系。 |

所有长整型标识保留十进制字符串（vibe-common 全局 Long→String 序列化保障）；业务单号保留原字符串。展示名称、脱敏联系方式、状态文案不能替代实际标识或枚举。

## 对象关系与标识

| 对象 | 标识和使用边界 |
|---|---|
| 订单与商品行 | `orderNo` 定位订单；商品行不是 SKU。发货与代客售后分别读取契约指定的行标识，不能互换 `bizItemId`、`orderItemId`、`skuId`。 |
| 包裹 | 一单可多包裹，一行可分批发货。新增发货提交本次数量；修改发货提交完整目标方案，不是只提交修改的一个单号。 |
| 售后单 | `afterSaleNo` 定位一次售后。订单完成不代表售后已结算。 |
| 支付与退款单 | 分别使用 `payOrderNo`、`refundOrderNo`，不能以订单号代替。审核通过不等于渠道退款成功。 |
| 预约、发票、对账差异、退货地址 | 分别使用契约指定的 `id` 或 `diffId`，不能以名称代替。实物自提核销码不是服务预约 ID。 |

## 发货方式分野、标记与周期购

- 三种批量发货严格分野：`batch-ship` 逐包裹逐商品行指定（一单多包裹）；`batch-full-ship` 后端自动计算整单（每单一套物流）；`merge-ship` 多订单合并共用运单（2~3 单，服务端要求同收货人、同一下单账号、同一发货门店、创建时间 3 天窗口内且均待发货/部分发货）。Excel 导入发货（import-ship / import-multi-package-ship）按文件内容执行，多包裹版是异步任务。
- 订单标记是运营侧颜色便签，与订单状态、售后状态无关；批量设置/清除，同单重复标记为替换。
- 周期购：`PERIOD_FULFILLING` 是购买单聚合态（状态机中为不可流转态），处置对象是履约子单；退订（unsubscribe）**直接创建退款单并以取消原因关闭订单，不创建售后单**（返回的 `afterSaleNo` 恒为 null，退款跟进用支付域退款单检索）；发货计划更新（delivery-plan）运营端只改发货日期。
- 订单导出双模式：小量同步（`mode=sync` 直接下载 URL，≤2000 行）、大量自动转异步任务（`mode=async` + taskId 轮询）；任务仅提交人本人可见，状态机 `PENDING→RUNNING→SUCCESS/FAILED`，取消对 PENDING 与 RUNNING 均可用（执行中取消由 Worker 自行中止），已取消任务对外归并为 FAILED。

## 支付渠道、微信发货与 CPS

- 支付渠道配置是租户支付链路的底层依赖：列表返回**脱敏**的 appId/mchId/证书序列号；渠道**创建与密钥配置不在开放范围**（敏感凭据面），开放面只有列表读取、启停与微信发货开关。禁用渠道影响全部新支付。渠道区分微信支付 API 版本 `V2` / `V3`（V3 需商户私钥/证书，V2 需 P12 证书）。
- 微信发货信息管理：渠道开关控制发货信息自动上报微信；手动补报（`wx-shipping.report`）按支付单雪花 ID 定位，小程序未配置时补报必失败（400），不是网络问题。
- CPS 是订单的推广分佣投影：同订单数据 + 佣金总额 + 导购/门店/员工归属标记；`@SensitiveApi` 敏感接口，收货人信息脱敏。CPS 视图只读，订单操作回订单契约。支付单与子订单是合并支付父子关系（一个支付单多个子单），用 `child-orders` 反查。

## 资金与退款链路

退款触发链：售后审核通过 → 按支付阶段（定金 FINAL → 全款 FULL 顺序）分阶段分配退款额 → 事务提交后异步调渠道；零现金无积分的售后不生成退款单，零现金有积分落纯积分退款单。部分退款产生多笔退款单，每笔独立跟踪状态；退款失败先确认原因再重试。关闭支付时若渠道已支付，最终可能是支付成功而非已关闭。

## 售后配置与原因库

四组租户级售后配置相互独立，保存均为全量覆盖（先读现值再完整提交），写入带分布式锁并记配置操作日志（模块 `AFTER_SALE_CONFIG`，可在交易运营日志查询追溯）：

- **自动退款**：开关 + 金额阈值（单位**分**）+ 用户限次（次数/天数窗口）+ SKU/用户黑名单阈值。注意实现缺口：trade-center 内当前只有存储与 Feign 读取，未发现自动退款执行消费方，配置生效范围以如实描述为准。
- **退运费规则**：固定 11 条规则矩阵（售后类型 × 发货状态维度），运费字段是中文枚举文本（见 `trade-enums.md`），不是金额；`editable=false` 的规则不可改；重置覆盖全部自定义。
- **售后时效**：售后发起时间窗（天）、审核超时（小时，超时自动通过）、用户寄回超时/商家自动收货超时（天，超时分别自动关闭/自动确认）、自提超时未核销检测（天数 + `AUTO_CANCEL`/`AUTO_AFTER_SALE` 处理路径）。
- **售后退库存**：开关 + 适用售后类型，决定售后完成后是否自动回补商品库存。

原因库是售后类型三选一维度的词库：原因含名称、大类、责任归属（`USER`/`MERCHANT`/`SHARED`）、凭证要求、视频许可与排序权重；`applicableTypes` 决定原因出现在哪个子 Tab（`REFUND_ONLY`/`RETURN_REFUND`/`EXCHANGE`）。原因与售后单是快照式关联：售后单保存原因 ID/名称/大类/责任的当时快照，词库后续修改不回写历史售后。修改待审核售后（`modify`）会整体覆写申请快照并要求 ≥10 字修改说明落运营流水；线下拒绝（`reject-complete-offline`）仅适用自行退回自提点且待买家退回阶段，与线下完结是同一阶段的两个互斥处置出口（一个完结、一个拒绝），执行其一即终态。

## 预约、发票、对账（规则语义）

- 预约全局配置（预约契约）：防重复预约、取消限次、活跃上限、超时自动完成、提醒提前小时数（1~48）、并发控制；保存为**非 null 字段级合并**（未传字段保留旧值——与售后四组配置的全量覆盖语义不同，不能套错模式）。预约提醒记录含 `user_before`/`staff_before` 两类、三渠道（sms/wechat_template/site_inbox）、三状态（mocked/sent/failed），详情 contentJson 已脱敏。
- 开票基础配置：平台（同一时间仅一个启用；凭据配置不开放）、销方（默认销方不可删）、税收分类编码（树形，被映射引用不可删）、商品类目-税收映射（无映射回退全局默认税率）。税率统一小数（0.13=13%）。代客开票：已签收订单立即开票、未签收打标待自动触发。平台认证阻塞（`auth-status` blocked=true）会暂停失败重试，认证完成后需手动清除标记。
- 对账：对账任务状态 `PENDING` 排队 → `RUNNING` 执行中 → `SUCCESS` / `FAILED`（手动触发异步返回任务 ID）。节点配置（频率/告警阈值）与告警通知按对账契约维护。标记差错和确认结论不会自动补收或退款；升级不是解决。

交易设置：订单超时（支付取消/自动收货/秒杀/改址窗口）与赠品仓库规则；与售后时效配置相互独立。配置操作日志（`AFTER_SALE_CONFIG` 等模块）可按操作日志能力审计变更前后值。

## 服务订单

服务订单（[服务订单契约](../apis/trade/service-order-query.md)）：服务类商品（`HOME_VISIT` 上门 / `PICKUP_DELIVERY` 取送）按次数拆履约子单。三层标识：`purchaseOrderNo` 购买单（预约入口）、`fulfillmentOrderNo` 履约子单（派单/改约/核销入口）、`sequenceNo` 次数序号。履约链路：待预约 → 协助预约（先查时段容量）→ 待派单 → 派单/改派 → 待服务 → 服务中 → 核销（`PICKUP` 取件 / `COMPLETION` 完成，4 位核销码；取送类须先取件核销再完成核销）。`rescheduleCount` 是改约计数展示，服务端当前不限制改约次数。与到店预约（appointment 台账）是两套体系，核销码长度也不同（4 位 vs 实物自提 6 位）。

## 订单角色与父子结构

订单有三种结构角色（`orderRole`）：`STANDARD` 独立订单（大多数）、`PURCHASE` 购买单（周期购/合并支付的聚合单）、`FULFILLMENT` 履约子单（购买单下的实际履约对象）。**支付单关联的是父订单号**（`parentOrderNo` / 购买单号），不是子订单号——用户给子订单号查支付流水时，`bizOrderNo` 直接传子订单号会命中 0 条，须先取 `parentOrderNo` 或详情 `payment.transactionNo`。存在 `subOrders` 时先定位实际履约子单再操作；周期购购买单聚合态 `PERIOD_FULFILLING` 不作为处置对象。

## CPS 结算状态跨域差异

CPS 订单的结算状态 **`CpsSettleStatus`（本域，整数）**：`1` 未结算 / `2` 结算中 / `3` 结算失败 / `4` 结算成功——`settleStatus=1` 表示**未结算**。营销域结算明细的 `settleStatus` 是另一套枚举（`0` 待结算 / `1` 已结算），**同名不同值域**；两个域都可能被加载，以本表解释交易域 CPS 订单的结算状态，不得混用营销域枚举。

## 特殊订单类型生命周期

| 类型 | 生命周期 | 关键点 |
|---|---|---|
| **定金预售**（`PRE_SALE_DEPOSIT`） | `PENDING_PAYMENT`（定金）→ `PENDING_FINAL_PAYMENT`（尾款窗口）→ `PENDING_SHIPMENT`；尾款超时或取消尾款 → `CLOSED`（定金退还） | `finalPayment.transactionNo` 单独存在；`finalPayStartTime`/`finalPayEndTime` 决定窗口；预售订单不能当普通订单发货 |
| **送礼**（`GIFT`） | 支付后进入 `PENDING_RECEIVE`（待好友领取）→ 好友全部领取 `GIFT_ALL_CLAIMED`（可人工完成）→ 领取超时 `GIFT_CLAIM_ENDED`（可完成或关闭） | `giftInfo` 含领取进度与祝福语；送礼单不走常规发货流程 |
| **拼团**（`GROUP_BUY`） | 支付后 `PENDING_GROUP`（待成团）→ 成团 `PENDING_SHIPMENT`；拼团失败 → `CLOSED` | `groupBuyInfo.groupStatus`（PENDING/SUCCESS/FAILED）判断成团结果；未成团不可发货 |
| **积分兑换**（`POINTS_MALL`） | 属于用户域（积分商城）的兑换流程，交易域仅可见关联订单 | `payType` 为 `POINTS_ONLY` 或 `POINTS_AND_CASH`；纯积分无需微信发货上报；发货操作走用户域积分商城能力，不走交易域 `order.ship` |

## 关键业务规则

- 积分订单支付类型为 `POINTS_ONLY` / `POINTS_AND_CASH`；纯积分支付无需微信发货上报（shippingReported=2）。
- 定金预售两阶段：先定金后尾款，尾款超时订单关闭；定金售后退款后订单同样关闭。
- 门店自配（deliveryMethod=self_service）发货需配送人姓名电话，不需承运商与运单号；修改发货无自配分支。
- 已签收订单可人工完成；服务端双重校验：仅 `RECEIVED` 状态且无进行中售后（终态售后除外）。
- 自提订单须确认备货（进入待自提）后才能核销。
- 红冲是冲销已开发票的操作，产生一张新红票；红字确认单确认前红票停留在开票中。
- 同一时间仅可启用一个开票平台；启用即切换全部开票链路目标。
- 退货地址用于售后审核时指定退回地址；默认地址不允许删除；**列表接口对联系电话脱敏，详情接口返回原始值用于编辑回填**——不能把脱敏值回写。

## 更新语义与实现缺口

- 订单收货地址：省略省市区可能覆盖为空；必须按订单契约准备完整目标地址。
- 退货地址：更新合并非 null 字段，省略或 JSON null 保留旧值，空字符串会覆盖；不要为"补全"而回填脱敏手机号。删除检查默认地址，不等于证明没有售后引用。
- 售后审核：只提交契约确认实际生效的字段。DTO 中存在不代表实现会消费；不可用的运费调整、审核备注等不能承诺生效。
- 售后媒体文本和换货对象按售后契约的实际结构解释，不把 `Object` 当自由扩展区域。
- 分页与状态计数可能采用不同筛选集合，不能用计数定位目标，或将两者不一致直接判为异常。
- 历史迁移记录（dataSource=MIGRATED）可能只读，不能仅凭状态发起写入。
