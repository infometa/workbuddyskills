# Moka 员工档案维护

以人事负责人视角更新、删除员工档案分组中的记录，并在写入前后用花名册定位与验证。本技能编排两项 Moka 能力：

- **花名册查询**：按业务场景查询人事列表数据——用来定位员工、读取字段当前值与可选范围，以及写后读回验证。
- **员工档案维护**：更新或删除档案分组中的一条记录——覆盖任职信息、个人信息、合同、培训经历、家庭成员等场景。

## 找到要用的工具

Moka 的能力由当前平台上的 Moka 服务提供。用平台的工具发现能力，找到实时 description 与上述能力相符的 Moka 工具后调用；工具的确切名称、入参与取值协议，以发现到的实时 description 与参数 Schema 为事实源。找不到 Moka 服务或对应能力时如实告知用户，不改用其他来源。

适用于「把某某的工作地点改成北京」「修改员工的合同信息」「新增一条培训经历」「删除这条家庭成员记录」等请求。只查询不修改的需求（盘点名单、查记录列表）不要用本技能的写入能力。

## 调用规范

1. 先定位、再写入：
   - 用花名册场景按姓名或工号查到目标员工，员工标识取自查询结果，不向用户索要内部编号；同名员工必须列出候选请用户选择。
   - 用户没说清目标值时先追问，并把该字段的可选范围（枚举字段用字段候选展开）带给用户选择，不自行猜测或改写为相近取值。
2. 写入时 `entity` 直接传字段名与目标值；花名册返回的「业务域#字段名」形式（如 `job#office_address`）可直接作为字段键使用，选项类与工作地点这类引用类字段传选项名称或候选标识均可，工具会解析为写入协议形态，解析不到会返回候选供改正。
3. 任职关键字段（部门、职务、职位、职级、管理职级、员工类型、直属上级、虚线上级、导师、工作地点及企业自定义任职字段）的变更属于人员异动：
   - 首次调用会返回可选的异动事件与原因候选；把候选如实交给用户选择，再从候选中原样选取事件类型与可选原因补齐异动参数后重新调用，禁止编造事件类型或原因标识。
   - 生效日期只支持当天；用户要求未来生效时，说明需在 Moka 中走企业变更流程，不要强行写入。
4. 确认链固定为三步，缺一不可：
   - 首次调用只返回操作摘要与确认码，不会实际写入。
   - 向用户完整复述摘要（操作类型、场景、员工、变更内容、异动事件与生效日期），等待明确同意。
   - 用户明确同意后，用完全相同的参数加确认码再调用一次才执行；任何参数变化都会使确认码失效，必须重新预览，不得沿用旧确认码。
5. 删除操作不可逆：摘要会明确标记，确认前向用户讲清后果；任职信息、个人信息、合同信息、异动记录四个场景只能编辑已有记录，目标记录由工具自动定位，存在多条记录时才需要用户补充，不得用员工标识充当记录标识。
6. 写后读回：执行成功后，用花名册重新查询该员工的对应字段，确认新值已生效再向用户交付；读回未生效时如实说明，不声称已改好。
7. 相对日期先按用户所在时区换算成绝对日期再调用，回答里说明实际生效日期。

## 结果与权限

- 返回不可重试的参数错误时（取值不在候选、记录标识不匹配、确认码失配等），按提示改正后重新发起完整流程，不要原样重放同一请求。
- 写入需要该档案场景的管理权限；权限不足或服务端拒绝时如实转达工具提示，不要绕行或换字段硬写。
- 空结果按「未返回数据」处理，不得反推为无权限。

## 安全边界

- 未获用户明确同意前不得执行任何写入或删除；用户中途改主意就放弃本次确认码，按新意图重新预览。
- 不向用户展示访问令牌、确认码、内部记录标识或原始技术响应；这些值只用于串联工具调用。
- 本技能会修改员工数据，只在用户为人事管理目的提问时使用；操作摘要中的敏感字段值已被脱敏，不要向用户许诺提供明文。
