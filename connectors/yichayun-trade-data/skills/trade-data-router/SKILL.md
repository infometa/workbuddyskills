# 贸易数据问题分诊

## 为什么存在

真机实测两次：用户问"锂电池对美国出口这两年的趋势"，模型走了网页搜索，
拿到的是行业协会转引的二手数字；被追问"没查贸易数据吗"才改口。
第二次修了工具描述仍然如此——因为**工具描述只影响"选哪个工具"，
决定"用不用工具"的是技能层**。

理由不是偏好，是数据性质：网页上的贸易数字基本都是二手转引（协会、新闻、
研报），滞后且口径不明；易查云贸易数据给的是提单与官方统计原始记录，
带明确的时间口径和数据来源。用二手数字回答"趋势"，用户没法追溯，也没法对账。

## 多步骤目标：先取剧本再动手

用户要的是"开发客户 / 进入新市场 / 深挖某买家 / 供应商尽调"这类**多步骤目标**
（而不是单条事实查询）时，先 `get_playbook` 拿方法步骤，再按步骤调数据工具；
无参调用可先看有哪些剧本。

直接开查名单是最常见的失败：跳过选市场、跳过排序依据、跳过风控与触达链，
拿到一串公司名却回答不了"该先开发谁"。

## 分诊表：问题 → 工具

| 用户在问什么 | 用哪个 | 关键点 |
|---|---|---|
| 市场有多大 / 什么走势 / 哪些国家在买 / 单价水平 | `analyze_market` | 官方统计口径，一次直出。**不要**用提单工具聚合来凑大盘 |
| 某产品在某国有哪些**采购商** | `find_buyers` | 要去噪(滤掉一次性/误配)改用 `search_trade(product=…, aggregate_by="buyer", min_transactions=3)`——`min_transactions` 只在 `search_trade`/`discover_customers` 上有 |
| 某产品有哪些**供应商/工厂** | `find_suppliers` | 找中国供应商用 `find_suppliers_via_imports`（中国无出口提单库） |
| 目标市场本国数据不全，要更全的买家名单 | `find_buyers_via_exports` | 用别国出口数据反查目的国买家 |
| 某公司**具体买了/卖了什么**、什么节奏 | `search_trade` | 见下"聚合优先" |
| 要看**具体哪几票货** | `search_trade_records` | 只在真要逐票时用 |
| 这家公司**什么来头**（地址/规模/行业/联系方式） | `enrich_company`（有编号）/ `search_companies`（只有名字） | |
| 这家公司**能不能做**（信用/风险） | `get_company_credit` | 需要企业库编号 |
| 找**决策人/联系方式** | `find_contacts` → `find_company_website` → `find_emails_by_domain` → `verify_email` | 后三个需单独开通 |
| 这个市场**能查什么** | `describe_market` | 免费，规划前先问 |

## 两源关系：互补，不是先后

> **凡能被交易记录证实的事实，以易查云贸易数据为准**——不要拿网页二手转引覆盖一手记录；
> **覆盖不到的如实让位**（认证/关税/展会/跨境电商卖家）；
> **两源冲突时并列呈现并标注口径**（成交价 vs 报价、注册名 vs 品牌名），静默取一比缺数据更糟。

按信息类型查表，不要套用一个全局顺序：

| 信息类型 | 主源 | 另一源的角色 |
|---|---|---|
| 交易事实（谁买了什么/量/频次/成交单价） | **易查云贸易数据独有** | 网页没有提单记录，联网在此无角色 |
| 市场规模 / 趋势 | **易查云贸易数据**（官方统计，可溯源） | 联网补预测、驱动因素、解读（数字之外的"为什么"） |
| 玩家名录 | **易查云贸易数据先**（有交易证据的真实玩家） | 联网查漏：尚无进口记录的新品牌、跨境电商卖家 |
| 公司身份与背景 | **易查云贸易数据定身份**（注册名/规模/行业结构化底座） | 联网追动态（最新新闻、官网、高管变动） |
| 联系人 | 三段链：易查云贸易数据出名单 → 联网交叉验证官网 → `verify_email` 验实时可达 | |
| 资信 / 风险 | **并行都要**：易查云贸易数据（承保/报损硬记录）+ 联网（负面新闻/诉讼） | 冲突时并列，不静默取一 |
| 认证 / 关税 / 渠道 / 展会 | **联网为主** | 易查云贸易数据无此数据，如实让位 |

## 三条最容易做错的

1. **要统计就别拉明细**——`aggregate_by` 在服务端一次聚合完成；翻页拉明细自己分桶，
   一个中等买家就要几万到十几万 token，而且口径未必和服务端一致。
2. **空结果先看第一条 warning**——那是本次为空的**原因**，常见是参数用错，
   不是"真的没有数据"。别把参数错误当业务结论。
3. **中国没有出口提单库**——找中国供应商用 `find_suppliers_via_imports`
   （扫目标进口市场 + 按原产国过滤），不是 `find_suppliers`。

## 结果怎么读(口径纪律全集)

分诊表告诉你调哪个工具;这份告诉你**拿到结果后怎么解释才不会错**。
每条都对应一次真实误读——照着读,能少替用户编造结论。

## 公司名

- **以 `registered_name` 为准**,不要自己音译海关抬头。没有中文注册名的公司保持原样,
  不得硬造中文;
- **`name_match` 是 `mismatch` 时**,该行的档案关联可疑(上游按名称/地址模糊匹配错绑,
  抽样约 13%)。这时只用海关原始名,**不要**引用它的注册名、画像、资信和联系方式;
- **同名公司很多**:凡是按公司名查的工具,结果里都会回显实际匹配到的公司名,用它核对再往下走;
- 收货人写成"真买家 C/O 货代"时,**真买家是 C/O 之前那段**(展示保留海关原文)。

## 数量与时间

- **`meta.data_freshness` 是"本次结果集里最新一条记录的日期"**,不是"数据库更新到哪天"。
  某公司最新记录停在两年前,通常是它自己不再以该名义进口,不是数据滞后;
- **品类聚合各桶之和会大于总票数**(一票货可含多个品类),算占比要用 `meta.total` 当分母,
  不能拿各桶相加;
- **按名称分桶、按编号合并**:上游聚合的桶是公司名字符串,同一家公司的不同写法各自成桶。
  服务端按编号合并后行数会少于 `meta.total_buyers`/`total_suppliers`(那是全量名称基数),
  **这是正常的**,合并发生时 warnings 会出声;
- **排序基准不固定**:金额/数量/重量/提单数由索引填充率自动选,实际值在
  `reasoning.ranking_basis`。所以 `shipment_count` 在列表里看着乱序很正常
  (实测美国家具:第 1 名 10,109 票、第 3 名 35,404 票,因为按数量排),
  **别据此判定排序有 bug**。

## 空结果与故障(最容易搞混的一对)

- **返回 0 行时,warnings 的第一条就是本次为空的原因**。常见是参数用错(比如按品类钻取
  漏给级别),不是"真的没有数据";
- **只有 warnings 里含"查询失败"才是数据源故障**;没有这四个字就是真的查不到。
  **绝不能把"查询失败"表现成"该企业没有数据"**——这是诚实降级的红线;
- 看到"部分数据分区正在更新"这类提示,是服务端已自动跳过失效分区并照常返回,
  结果少一片但可用,不是故障。

## 各源的特性

- **联系人数据没有时间戳**——如实说"无时效",不要给它编一个日期;
- **资信是按需采集的快照,不是全量库**:查不到 ≠ 资信差,是"没采过"。按"未知"处理,
  用付款条件对冲,不要据此淘汰客户;同名集团的不同法人各有独立记录,以回显的公司名为准;
- **营收是当地币种原值**,不要当美元用,也不要跨市场直接比大小。

## 成本纪律(省 token、省钱、省时间)

贸易数据的坑不是"查不到",是"用错方式查到了,代价高十倍"。

## 一、要统计就别拉明细

问"他买了哪些品类""主要供应商是谁""每月走势如何"——这些 `search_trade` 一次聚合就给:

```
search_trade(buyer="XX", aggregate_by="category")                        # 品类分布
search_trade(buyer="XX", aggregate_by="supplier")                        # 供应商排名
search_trade(buyer="XX", aggregate_by="time", granularity="month")       # 月度趋势
search_trade(buyer="XX", aggregate_by="supplier", cross_by="category")   # 交叉表
```

翻页拉明细自己分桶,一个中等买家就要几万到十几万 token,大买家直接超出上下文——
而且**你自己分桶的口径未必和服务端一致**。

真要看明细时,用 `fields` 只取需要的列(省一半以上输出):

```
search_trade_records(product="XX", fields=["date","exporter","product_desc","quantity"])
```

## 二、翻页的两条实测规则

- **单页上限**:贸易工具 `limit` 最大 100,超限直接被参数校验拒绝(不计费);
- **终止条件要同时看两个**:`next_cursor` 为空 **或** 累计已达 `meta.total`。
  实测**最后一页(累计已达 total)仍带着 cursor**,只看 cursor 会多打一次空转请求;
- 分页是守恒的:翻到底的累计条数恰好等于 `meta.total`(真库实测 8,995 = 8,995,91 页)。
  如果你算出来对不上,先怀疑自己的循环,再怀疑服务端。

## 三、计费口径

- 6 个贸易工具:**1 点 = 50 条档位**,基价 × `ceil(limit/50)`。`limit=50` 与 `limit=1`
  同价,所以**要 30 条就传 30、别传 100**;翻页每页独立计费;
- `describe_market` / `get_balance` / `get_playbook` 免费——规划阶段放心用;
- `enrich_company` 的 `depth="full"` 是基础档的 5 倍,只在真要深挖结构/财务/人时用;
- 邮箱三件套须单独授权,未开通会明确报错(不计费),不影响其余步骤;
- **数据源故障不计费**(warnings 含"查询失败"时免扣),空结果照常计费——
  查询确实发生了。

## 四、先问再查

`describe_market` 是免费的:规划跨市场任务前先问一遍每个市场"能查什么、按什么排、
数据多新",比查完发现"这个市场没有金额字段"再返工便宜得多。

## 覆盖边界(能查什么、查不到什么)

用户问的东西不在覆盖面里时,**如实让位比硬凑答案有用**——凑出来的答案用户没法追溯,
而且会挤掉他本该去做的事(比如该联网查认证的时候在翻提单)。

## 提单数据的形状

- **71 个市场**:70 个有进口数据、52 个有出口数据(只有出口没有进口的目前只有 tw);
- **52 个市场的进口数据覆盖到 2025 年及以后**,其余停在更早年份——
  规划前用 `describe_market` 确认(免费),别假设某国一定有近年数据;
- **默认只查近 3 年**。要更早的传 `date_from`;命中默认窗截断时 warnings 会出声提醒;
- 市场之间**能力不齐**:有的没有金额只能按提单数排、有的只有 HS 编码没有货描
  (按货描搜的过滤会被自动跳过并出声)。`describe_market` 一次说清。

## 明确查不到的(该联网就联网)

- **中国没有出口提单库**。要找中国供应商,用 `find_suppliers_via_imports`
  (扫目标进口市场 + 按原产国过滤),不是 `find_suppliers`;
- **跨境电商卖家**:没有报关记录的线上卖家,提单里不存在;
- **服务贸易**:只有货物贸易报关数据;
- **认证 / 关税 / 展会 / 渠道政策**:本服务没有,联网为主;
- **公司最新动态**:新闻、官网改版、高管变动——企业画像有滞后,动态靠联网。

## 几个容易误解的市场标识

- 结果里出现 `go` / `en` / `sp` 这类**不是国家码**,是跨国聚合源;
  其中的记录来自多个国家,**别把它当成某个国家的进口量**。要按国别分析,
  用结果里的原产国/目的国维度;
- 少数市场是"全量不分年"的库(没有年份段),任何时间范围的查询都会覆盖它。

## 官方统计 vs 提单(两套数据,别混用)

- `analyze_market` 走**官方统计**:月度、可溯源、无企业名——看大盘、算份额、取单价基准;
- 其余贸易工具走**提单**:有企业名、可查到具体谁在买——找客户、看供应链;
- **不要用提单聚合去凑市场大盘**(样本口径不同,数字对不上官方统计,用户拿去对账会翻车)。

## 须单独开通的能力

邮箱三件套(`find_company_website` / `find_emails_by_domain` / `verify_email`)默认不开通,
调用会明确报错且不计费。前面的市场分析、名单、画像、资信步骤**不受影响**——
遇到报错就把触达那一步标注为"需开通",不要因此中止整个任务。
