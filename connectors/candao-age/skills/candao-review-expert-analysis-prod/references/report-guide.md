# 报告规则

## 分析原则

结论先行、数据严谨、聚焦本期核心问题。所有数字、日期、门店、餐品和引用必须来自工具返回。

1. 按 `commentDetails[].badCommentTags` 实时汇总的累计命中评价数分析 Top3：报告图表与文案的「差评原因」维度**统一用 `badCommentTags`**，按「-」拆为**一级（「-」前大类，如「口味问题」「异物问题」「制作/错漏送」）/ 二级（「-」后细项，如「味道异常」「毛发人体异物」）**两层下钻；不再用一级 `commentTags`（`commentTags` 仅作差评明细卡片并列展示）。Top3 取一级大类（新版 schema 已无 `negativeTagSummary`）。
2. 结合 `dailyCommentTrends` 定位变化日期，但没有明显波动时明确写“未见单日集中爆发”（新版 schema 已无独立的日趋势标签数组，标签级日趋势须从 `commentDetails` 按 date+tag 实时汇总）。
3. 每个 Top3 从 `commentDetails`（level=='差评'）中挑选 1～3 条语义确实匹配的原话（新版 schema 证据唯一来源即差评明细）。标签与正文不符时跳过，不能硬凑。
4. 同一条评价在整份报告最多引用一次。引用时只保留分析所需内容，并标注评价日期和门店。
5. “其他原因”（badCommentTags 中「-」前大类为「其他原因」的兜底分类）进入 Top3 时，只报告量级并说明分类信息不足；不得据此编造具体原因。在图表报告的「差评原因分布」一级条形图中强制置底；在「改进建议」中直接剔除（不渲染弱化框、不占编号），不得据此编造具体可执行建议。
6. **重点问题为双项结构**：① 食安预警——存在命中「异物问题」前缀的差评明细（`commentDetails[].badCommentTags` 含该前缀，如「异物问题-毛发人体异物」「异物问题-卫生致病」）时红色；**结论跟随筛选**——命中条数 / 未回复条数均基于 `filteredQuotes()`（随日期/门店/渠道/原因筛选实时变化，与命中门店分布·每日趋势·差评明细同一口径），确保与报告其余模块筛选联动一致；**下方举例才抽样**，**重点列出未回复/高风险条目（最多 5 条，未回复优先排序），超出以「…等共 N 条食安红线命中」概括**，避免一份报告被食安条目刷满而失去重点；不存在时不隐藏、也不展示「0 条」，改为绿色「食安表现良好 ✅」好评提示，正向强化。② 差评24h回复效率——**直接引用指标卡「24h差评回复率」同一指标**（共用 `replyMetric()` 单一数据源；**接口原生口径**：分子 `replyWithin24Hours`、分母 `badCommentCount`，来自 `reviewMetricSummary`、与服务端 `replyWithin24HoursPer` 一致，**不再**用「是否已回复」代理 24h 时效），有未回复差评则红色列出未回复原文（最多 5 条，超出「…等共 N 条」），全部已回复则绿色达标。**仅①②两项均无问题才判定「重点问题·整体良好 ✅」；任一有问题则红色容器列出「存在待处置项（N 项）」并分项标注状态。**
   **改进建议（数据驱动）聚焦核心问题**：仅展示命中数 **Top5 一级标签**（跳过食安红线「异物问题」与兜底「其他原因」），其余低频长尾合并为一条「**长尾问题**」概括（含各类命中数与占比），避免大量低频数标签稀释重点；每条命中门店列表**最多展示 3 家**、超出以「等 N 家」概括，避免门店名刷屏。常量集中在模板顶部 `FS_SAMPLE=5` / `TOP_SUG=5` / `STORE_SHOW=3`（与差评明细 `QSAMPLE=5` 一致），数据量小时仍展示全部、仅在超出上限时才截断概括。
7. 建议只能针对本期数据已经暴露的问题。不要承诺确定效果，不要杜撰制度、设备、补偿金额或监管动作。
8. 下期好评率可提出“较本期提升 2%”的管理目标，上限为 100%；必须写成目标，不得写成预测。

## 输出结构

正文使用以下纯净标题，禁止在标题中加入括号或内部说明：

```markdown
## 1. 宏观经营绩效评价
- **经营概况**：评价总数、好评率、差评总数与上期的绝对变化及可计算的变化率。**注意口径统一：率指标（好评率/差评率）的环比一律用「百分点（pp）」表述（如 67.1%→73.5% 记「−6.3pp」），与报告指标卡一致；计数指标（评价数/好评数/差评数）环比用相对 %。**
- **核心态势定性**：一句话概括，不夸大。

## 2. 核心问题总结
### 标签名称
- **问题量级**：命中评价数及占差评总数比例。注：分子为「去重差评条数」（一条差评带多个同大类二级标签只计 1 次），单类占差评比例恒 ≤100%；跨大类横向相加合计可 >100%（一条差评可同时命中多类），属正常，非 Bug。
- **原因诊断**：仅基于每日趋势和语义匹配原文。
- **真实评价还原**：
> “评价原话” —— **日期，门店**

## 3. 食品安全红线专项
仅在存在菜品异物证据时输出。

## 4. 针对性优化建议
### 后厨制作环节
### 打包出餐环节
### 渠道与服务环节

## 5. 下期目标建议
- 明确这是管理目标而非效果预测。
```

重点数字用粗体。正文不得出现 Java、SQL、字段名、工具名、数据集编号或“根据提示词”等内部措辞。

## 图表（自动生成：交互式 HTML 报告）

本 skill **默认自动生成一份自包含的交互式 HTML 图表报告**，作为与上方「文案总结」配套的两类交付物之一（总结讲结论，HTML 讲数据可视化与交互下钻）。报告用内置 `references/interactive-report-template.html` 填数据生成，**不依赖 Mermaid、不依赖外部 CDN、不联网**；**禁止使用 Mermaid 等需额外渲染器的语法**——客户端无法保证其可用性，曾导致整块内容渲染失败。报告须包含以下图表（具体布局与联动见下方「交互筛选与标签趋势追踪」）：
⚠️ **交付物仅 HTML 报告文件一份**：`data.json` 为生成临时输入不交付；生成统一用 `scripts/build_report.py`（一步生成+校验、无计时），不要手写或另存「模拟 / 测试」版本。

1. 顶部指标区使用同一行的 5 个紧凑卡片，依次展示总评论数、好评数、差评数、好评率和**24h差评回复率**；窄屏（≤760px）自动换行。每个卡片以本期值为主，并展示**环比**；**色调按指标"向好方向"定色（非按涨跌）**：好评数/好评率/24h差评回复率 为「good」向（涨=绿、跌=红），差评数 为「bad」向（涨=红、跌=绿），总评论数 为「neutral」恒灰。**环比可用条件：日期须全选**（上期 `reviewMetricSummary` 的 `preXxx` 字段只到门店×渠道粒度、无逐日数据），门店/渠道筛选不影响环比；日期子集筛选时如实标注「仅完整周期可比对」，不编造上期值。**率指标环比统一用百分点（pp）**（如「好评率 环比 -6.3pp」），计数指标（评价数/好评数/差评数）环比用相对 %。**差评回复时效不再作为独立模块，已合并为「24h差评回复率」卡片（与重点问题②共用 `replyMetric()` 单一数据源）。
2. 主图区域左侧约占三分之二，展示“差评原因分布”**两级下钻**条形图。**一级条形图**：按 `badCommentTags` 中「-」前大类汇总（如「口味问题」「异物问题」「制作/错漏送」），“其他原因”强制置底、其余按命中差评数降序，按一级大类前缀着色（`TAGCOLOR`）。**点某一级分类名 → 下钻出该一级下的二级细分条形图**（「-」后细项，如「味道异常」「毛发人体异物」，同一级同色）；点二级名 → 继续联动命中门店/每日趋势/明细。每条：标签名 + 实长条形（宽度∝命中差评数）+ 右侧“N 条”；图下方固定灰字注明一条评价可命中多个标签、占比可能重叠。
3. 主图区域右侧约占三分之一，展示“评分分布”环形图。SVG 环形（stroke-dasharray 实现），圆心显示平均分（仅 1–5 分）。**悬停交互：鼠标移到某色块，显示 tooltip（如“5分：40 条，占 74.1%”）。图例修正：每个图例项单独一行，格式为“色块 · 分数标签 —— 数量”，分数与数值用空格/横线分隔、不可粘连；顺序严格按 5分 → 4分 → 3分 → 2分 → 1分（score=0 置底并标注“评分缺失”，绝不显示为 0 星）。** 配色语义固定：5分=绿（好评）、3–4分=橙/黄（中评）、1–2分=红（差评）。
4. **每日评价趋势**组合图（默认包含，评价数用棒棒糖图表现）：左轴=比率%（好评率/差评率），右轴=评价数（棒棒糖图：细杆+蓝点+柱顶数值），双轴刻度与单位必须画出，数据点用圆点标记，图上图例区分系列，x 轴日期完整标注；好评率/差评率为双折线，24h差评回复率为**周期级参考虚线+末端百分比药丸**（数据源无逐日拆分，不得画成逐日折线或假 0% 直线）；谷底/异常日用文字注记。
5. 图表标题、图例和卡片文案使用中文。控制图表高度和留白，避免同一图表占据大面积页面。
6. 若客户端不支持 HTML 渲染，降级为：五指标紧凑表格（含24h差评回复率）+ 差评原因表 + 评分分布表，不输出图表代码。

## 交互筛选与标签趋势追踪（默认生成，自动启用）

> **实现捷径**：不要每次从零写几百行 JS。直接复制本 skill 的 `references/interactive-report-template.html` 作骨架，按文件内注释替换「数据」数组即可（实现要点见 `references/interactive-report-guide.md`）。下面的规则即该模板的约定，改模板时须同步遵守。

**本 skill 默认在「文案总结」之外自动生成该交互式面板**（自包含 HTML + 内联 JS，不联网、不依赖外部库），无需用户额外要求"筛选/联动/下钻"：

1. **顶部筛选器（必须可扩展，禁止平铺长列表）**：当选项可能较多（日期跨多日、门店数十家）时，**不得**把所有选项平铺成 chip——改用以下紧凑控件：
   - **日期**：提供快捷区间按钮（如“本周 / 近 7 天 / 全部”）+ 起止日期选择（`<input type="date">` 或下拉），按区间过滤而非逐日勾选。
   - **门店 / 渠道等离散维度**：使用「可搜索多选下拉」——含搜索框、全选/清空、已选计数（如“已选 3/25”），选项过多时内部滚动，不撑满页面。**差评类型（一级分类）不再单独设下拉筛选器，改由「差评原因分布」条形图点击标签名联动筛选**（见第 3 条）。**多选下拉展开时必须位于最上层（`.ms.open{z-index:1000}` 且容器不得 `overflow:hidden`），避免被后续筛选行遮盖。**多选下拉选中任一选项后应保持面板打开、支持连续勾选，不得选中即关闭面板（反人类交互）；仅在点击面板外部区域时才收起。**
   - 整个筛选区放在**可折叠面板**（标题栏点击展开/收起），默认展开，节省纵向空间。
   - 仍保留“重置全部”按钮。
2. **联动重算**：筛选后，指标卡、差评原因条形图（含趋势）、每日评价趋势图、差评明细均需按所选集合实时重算/过滤（纯前端 JS，数据内联）；**差评明细展示当前筛选条件下全量差评、分页展示、每页 10 条**（排序优先露出未回复、命中食安/异物的条目），筛选条件变化时回到第 1 页。

   - **筛选联动范围（新版 schema 口径）**：
     - **日期 / 门店 / 渠道 三维度**：指标卡、评分分布（`commentScoreDistribution`）、每日整体趋势（`dailyCommentTrends`）、差评原因分布、命中门店、差评明细、总结 —— **全模块联动**（各聚合均已带门店/渠道维度）。
     - **差评原因（标签）维度**：只作用于**明细类模块**（差评原因分布、命中门店、每日命中趋势、差评明细、总结）；因接口未提供标签级的评分/订单/回复数据，**不**影响指标卡、评分分布、每日整体趋势。选中原因时报告顶部自动提示该边界。
     - **订单量 / 实收金额**（`orderAndReceiptSummary`）无日期维度，只随门店/渠道联动，不随日期联动。

3. **差评原因面板结构**：上方为**一级原因(badCommentTags 中「-」前大类)**差评条数汇总条形（“其他原因”置底）；**点某一级分类名 → 下钻出该一级下的二级细分条形图**；再点二级名 → 选中该二级分类，联动下方「命中门店分布」柱状图（各门店条数之和 = 该二级分类命中数，口径自洽）与每日趋势/明细/总结。未选任何分类时提示“请点上方一级 / 二级分类，查看其命中门店分布”。**面板内不再放独立的每日趋势图**——每日趋势图统一放在下方独立面板，并随上方所选分类联动（见第 5 条）。
4. **分类固定配色（强制一致性）**：建立标签↔颜色映射（如 菜品口味=蓝、菜品份量=橙、配送超时=绿、餐具漏送=紫、餐品包装=青、其他原因=灰）。**差评原因条形图、每日趋势图、二级分布柱状图的同一分类必须使用同一种颜色**；趋势/折线图未选时各标签均显示其专属色（不得统一为灰/蓝以免无法区分），选中后该分类加粗、其余变浅。面板底部提供分类颜色图例（色块+标签名）。
5. **每日评价趋势图（随筛选与选类联动）**：位于独立面板，柱=评价数、双折线=好评率/差评率（右轴百分比），圆点悬停显示当日率值。**联动规则（优先级：二级细分 > 一级分类 > 整体）**：未选分类时显示整体每日评价趋势；选中上方某分类（可多选）后，本图改为展示选中分类的每日命中趋势——灰柱=当日选中分类命中合计，各选中分类一条专属色折线（点悬停显示“分类：日期 命中 N 条”），y 轴为命中数；选中某二级细分后（见第 8 条），本图进一步下钻为该二级的每日命中（父级配色，标题标注“联动二级细分：X ✕清除”）。标题随联动状态变化。
6. **门店 / 渠道筛选（新版 schema 已带维度）**：`dailyCommentTrends` / `commentScoreDistribution` / `reviewMetricSummary` / `orderAndReceiptSummary` **均已带门店 × 渠道维度**，故指标卡、评分分布、每日整体趋势、经营对照都能真正按门店/渠道重算，**不再**是"整体周期口径冒充筛选后数"。但 `orderAndReceiptSummary` **无日期维度**，订单量/实收金额不随日期筛选变化，须在页面上标注。**同样**：24h差评回复率（指标卡 `replyMetric` 与每日趋势紫色参考线）数据源 `reviewMetricSummary` 无 `date` 字段，属**周期级指标，不随日期联动**；当用户选择了日期子集时，指标卡「24h差评回复率」sub 追加「（按全周期，不随日期筛选）」、每日趋势图紫色线旁加「按全周期·不随日期」标注，显式消除「差评数随日期、回复率不随日期」的口径矛盾（store/channel 维度下仍随筛选重算）。
7. **日期筛选边界**：工具返回为固定周期，无更细粒度。日期筛选仅能在已返回日期内勾选重算，不得虚构区间。**UI 已强制**：起止日期框 `#dStart`/`#dEnd` 在初始化时由 `initDateBounds()` 设 `min=PERIOD.start`、`max=PERIOD.end`，日历面板中范围外日期自动置灰且不可选；`customDate()` 对手输/越界值再做兜底夹回（早于起点→起点、晚于终点→终点、起止颠倒→交换），确保所选集合恒落在 `DATES` 范围内。
8. **原因下钻（一级 → 二级 → 命中门店分布）**：差评原因分布以 `badCommentTags` 按「-」拆**一级/二级**两层——**一级** =「-」前大类（如「口味问题」「异物问题」），**二级** =「-」后细项（如「味道异常」「毛发人体异物」）。**点一级分类名 → 下钻出二级细分条形图；点二级名 → 选中该二级分类，联动其命中门店分布柱状图**（各门店条数之和 = 该二级分类命中数，口径自洽）。一级 `commentTags` 仅作差评明细卡片并列展示、不再驱动原因分布。两级同色按一级大类前缀（`TAGCOLOR`）。二级标签在差评明细中以「一级-二级」整串 chip 呈现，一级以 chip 并列。
   - **横向滚动（门店多时必须）**：门店数较多（如 20 家）时，下钻柱状图外层容器 `#tag2Wrap` 启用**横向滚动条**——每家固定独立宽度（按店名长度 `max(66, 店名×12+22)` 像素），SVG 自然像素宽随门店数增长，外层 `overflow-x:auto` 出现滚动条，店名一律可读；**绝不可**退化成无滚动的整体窄图（旧版所有门店挤进左侧面板约 360px、店名糊成一片）。SVG 内联 `width:Wpx;max-width:none` 覆盖全局 `svg{width:100%}`；无选中 / 空状态时回退 680px。
   - ⚠️ **滚动必须严格锁在 `#tag2Wrap` 内，不得外溢到整页**：`#tag2Wrap` 外层 `.panel` 是 `.grid2` 的 grid 子项，grid 子项默认 `min-width:auto` 不会被压到比内容更小——SVG 一旦变宽（如 2106px）会把 `2fr` 轨道撑到同等宽、整个 `.grid2` 超出 `.wrap`、body 出现整页横向滚动条（拖动"整个报告都在动"即此 bug）。治本：`.panel{min-width:0}`（让 grid 子项能收缩到轨道宽）+ `#tag2Wrap{width:100%}`（滚动容器宽度显式等于面板内容宽）；`body{overflow-x:hidden}` 作兜底，确保永不出现整页横向滚动。重改此模块布局后务必实测：点一级分类后只有该模块内部出现滚动条、其余模块纹丝不动。
   - 柱体**可点选**（再点取消）。选中某门店后**必须同时联动**下方「每日评价趋势」与「差评明细」：① 每日趋势切到该门店的每日命中（父级配色，标题标注“联动门店：X ✕清除”）；② 差评明细只显示该门店（标题标注“筛选门店：X ✕清除”）。
   - 切换一级 / 二级分类时清空已选门店（`sel.subStore=null`），避免错位。
   - 若该门店本期内该分类无明细，日趋势图显示诚实缺口说明，不得编造命中曲线。
   - ⚠️ **序列化破损**：两个标签字段返回的都是字符串化的 Python 列表，`gen_report.py` 的 `clean_tags()` 用 `ast.literal_eval` 还原；**额外兜底**：数仓偶发把两条标签用 `]` 拼接残留（如 `"笼统差评-笼统不满]口味问题-味道异常"`）或带尾随空格，`clean_tags()` 在 literal_eval 失败时按 `|` / `,` / `[` 拆分、并二次清洗单标签内残留的 `[]`，将其还原为多条干净标签（已验证：0817–0823 批次 35 条脏值→33 条干净）；嵌套双引号损坏（如 `"[['其他原因-其他''门店出品']"`）仍按数仓原样保留（属已知脏值，仅差评明细卡片展示，不进原因分布）。若接口修复序列化缺陷，该函数会自动退化为正常解析。
9. **筛选条件下总结分析（置于指标卡上方、随筛选联动）**：在交互面板顶部、指标卡之前增加一段文字总结，至少覆盖：
   - **当前范围**（日期天数 / 已选原因 / 门店 / 渠道）。
   - **整体表现**：评价数、好评数及好评率、差评数及差评率、平均分（1～5 分加权自算，须注明分母为有效评分条数、评分缺失不计入）。
   - **差评集中**：Top3 原因及命中条数。
   - **相关性分析（v2 已落地，门店×渠道聚合层面，但结论不在总结区展示技术段）**：以门店×渠道为粒度（本期约 20 个组合）计算差评（率/密度）与订单量、实收的关联，包含三层：① **Pearson 线性相关**；② **Spearman 秩相关**（捕捉单调型非线性）；③ **分位桶三分位**（按订单量 / 实收各分低/中/高三桶，对比各桶差评率/密度，捕捉 U 型 / 阈值型非单调）。**结论判定（按三分位「形状」，结论必须始终与表格数字一致）**：先取差评率最高桶——① 高单量桶(高)最高 → 「订单量越高、差评率越高，高单量门店差评率最高」；② 低单量桶(低)最高 → 「低单量门店差评率反而最高」；③ 中单量桶(中)最高且 ≥ 两侧 → 真·U 型「生意中等的门店差评反而最多（两头低、中间高）」；④ 三桶极差 < 3pp → 「差评率与订单量无明显关联」。Pearson/Spearman（订单量↔差评率）**仅调节尾部强弱标注**（强/一定/弱相关，r≈），**不改变主结论的形状判定**（旧版曾把任意非单调形状一刀切写成「中等最多」，是 bug，已修）。⚠️ 仅门店×渠道粒度、无逐日数据、**样本量小（N≈20）、相关性≠因果**、分位桶仅粗略三分位，仅作量级参考。
   - **结论落位（用户要求）**：「经营对照」块已按用户要求**移除**；总结分析区**仅保留「当前范围 / 整体表现 / 差评集中」三段**，相关性技术段不再出现在总结区。相关性分析的**结论须改写为业务人员能看懂的话术、并内嵌一点点量化数据锚点**（如「按订单量三分位，差评率分别为 5.7% / 14.9% / 6.3% — 低/中/高」），**置于「改进建议」下方的「业务结论」红框**中；**不再单列「数据说明」技术脚注**。**业务话术（由三分位形状自动生成，结论须与表格数字自洽）**：高单量桶最高→"本期呈现「订单量越高、差评率越高」的趋势：高单量门店差评率最高（X%），明显高于低/中单量门店（…%），建议优先排查高单量门店的菜品稳定性与服务峰值应对"；低单量桶最高→"低单量门店差评率反而最高（X%），小店品控/服务更易出问题，建议针对性帮扶"；真·U 型(中桶最高)→"生意中等的门店差评反而比好/差门店都多（两头低、中间高），建议优先排查中等规模门店的品控/服务波动"；三桶极差<3pp→"差评率与订单量（生意规模）没有明显关联，差评主要源于具体菜品的品质问题，建议按标签逐店整改"。
   - **重点问题（双项）**与**改进建议（数据驱动）**，口径见上文第 6、7 条。
