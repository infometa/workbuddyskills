# SQL 语法参考（data-query skill）

> 本文件由 data-query skill 加载。本会话第一次调用 `dataset_jdbc_query` 前，必须完整读完本文件；并且对将要在 SQL 中触碰的每个数据集，先用 `dataset_search(action="info")` 读过详情。
> 共享流程（意图、时间口径、路由、可行性、澄清门）在 SKILL.md；通用 SQL 知识不在此重复。本文件只写**这个后端环境特有**、凭通用 SQL 经验会写错的内容：工具契约、数据字典用法、方言硬约束、错误语义。

## §1 工具契约：dataset_jdbc_query

| 参数 | 说明 |
|------|------|
| `sql` | SQL SELECT 语句（必填）；不支持 DDL/DML |
| `purpose` | **必填**。6-12 字中文短语，描述这条查询取什么；会成为用户文件区里 CSV 的文件名和引用卡片标题（如 "3月订单明细"）。用真实业务名词，不含"查询"二字或日期 |
| `visibility` | **必填**，三选一：`"internal"` / `"default"` / `"export"`，选择规则见下 |

> 所有查询统一走指标平台语义层，产品里不存在"选数据源"这个概念：**不要传 `datasource_alias`**（工具默认即语义层后端）。若报 `Error: 数据源不存在`，说明传了该参数——去掉后重试。
> 多段点分的物理表名（形如 `catalog.db.table`）是数据字典里 `PHYSICAL_TABLE` 的整体，不要拆出第一段当"数据源"。

**visibility 选择规则**：
- `export`：用户要行级原始明细 / 流水 / 逐条记录 / 全量数据。强信号：订单明细、交易明细、库存明细、流水、每一笔、逐条、原始记录。即使用户没说"导出/下载"也用 export——完整明细的交付物就是 CSV。
- `internal`：schema 探查、中间验证、字段范围检查、JOIN 可行性检查、财期探测、数据起始探查（`SELECT MIN(...)`）等不直接给用户看的查询；结果保持小（LIMIT 50 或更窄过滤）。
- `default`：小型非明细结果（用户明确 Top-N / 预览 N 条，或非标分析返回的聚合摘要）。行级明细不要用 default。

**limit / LIMIT 用法**：默认**不要写 LIMIT**——工具自动分页全量取数；行级明细配 `visibility="export"` 发布 CSV。只在用户明确 Top-N（"前 50"）或明确预览（"看 20 条样本"）时写。不要为"防数据多/保护性能"主动加 LIMIT——那会让用户拿不到完整 CSV。

**行为**：
- 未写 LIMIT 时自动分页拉取至硬上限（默认 100 万行）；超上限返回截断警告，必须复述并引导用户加过滤
- 结果超过 8000 字符自动截断，完整结果保存为文件（`jdbc-query-{timestamp}.txt`）；截断时会提示用 `read_file` 查看
- 成功时返回 Markdown 表格，末尾是 `N row(s) returned.`；失败时返回纯文本错误信息

## §2 数据模型：数据字典是唯一真相源

数据字典由 `dataset_search` 工具提供，分两级——**总览**（`action="list"`：数据集名称、显示名、描述；keyword 过滤 + 翻页）与**详情**（`action="info", name="a,b"`：字段名、展示名、类型、原始数据类型、关联关系）。它只承载模型事实；**怎么用**这些事实的规则全在本文件，而**本文件不出现任何真实表名、字段名、日期**——正是这个分离让字典的来源可以更换而不动这些规则。

写任何 SQL 前：先用总览完成路由和可行性判断，再读将要触碰的每个数据集的详情（多个数据集名逗号并传，一次 info 拿全）。

- **唯一来源**：意图匹配、字段映射、数据集名 / JOIN 条件全部取自字典。严禁编造字典没有列出的数据集或字段。
- **数据起始不在字典里**（SKILL.md「字典盲区」）：请求时间范围可能早于数据覆盖时，先对该数据集主日期字段发 `SELECT MIN(...)`（`visibility="internal"`）确立起点，再按 SKILL.md Step 4 处理——"该时段数据不存在"是首要回复；严禁替代口径，替代方案只能 ask_human 提议。
- **Schema 漂移**：后端拒绝字典返回的数据集/列 → 不猜替代品，如实告知字典与线上不一致。

**字典字段怎么用**：
- **PHYSICAL_TABLE（详情"基本信息"区块返回）** → **FROM/JOIN 必须使用的完整多段物理表名**（形如 `catalog.db.table`，常带很长的生成前缀）。⚠️ `name`（数据集名）和 `PHYSICAL_TABLE`（物理表名）是两套东西：前者**只用于** `dataset_search(action="info", name=...)` 这类工具调用入参，**不能**写进 SQL 的 FROM/JOIN——混用会报 `Table not found`。**PHYSICAL_TABLE 为空**的数据集不可直接 SQL 查询——换一张表，或如实告知用户。
- **字段名** → SQL 列名；**展示名**只作 `AS` 别名。**非 ASCII（如中文）别名必须加当前方言的标识符引用符**（多数后端为反引号，如 `` AS `订单号` ``；以 §3 的 sql_style 为准）——裸中文别名是语法错误。
- **类型 / 原始数据类型** → 决定过滤写法；日期类字段类型可能混杂（DATE / TIMESTAMP / VARCHAR），见 §3。
- **joinOn** → 一个**已知可用**的关联条件，可直接用于 ON 子句（数据集名替换成你的表别名）；`MANY_TO_ONE` / `ONE_TO_MANY` 提示行数膨胀风险。它是指标平台当前建模的关联，**不是唯一合法的关联**：只要两列确实标识同一个东西，按别的列关联完全可以。要你自己负责核对的是——两列真的是同一个标识（同实体、同口径、类型兼容），以及行膨胀有没有把你要聚合的行数放大。
- **数据主题范围**：`dataset_search` 报 `not in the current data theme` → 数据集存在但不在当前会话选中的数据主题内，**不是"数据不存在"**。如实告知用户：把数据集加入所选主题，或把会话主题切到"全部主题"后重试。

## §3 本后端的 SQL 硬约束

> 🚫 **不能用 CTE / WITH**。服务端校验器返回 `Only SELECT statements are allowed`——**报错文字不提 WITH，但 WITH 就是真实原因**；引擎只接受裸 SELECT（允许子查询）。所有中间结果用子查询/派生表改写：
> ```sql
> -- ❌ WITH t AS (SELECT ... FROM x) SELECT * FROM t;
> -- ✅ SELECT * FROM (SELECT ... FROM x) t;
> ```

**API 侧强制**（违反即报错）：只能 SELECT（允许子查询）；禁 UNION；禁分号拼多条 SQL；未写 LIMIT 自动分页至硬上限；服务端查询超时（时长为系统设定）。

**方言跟随 sql_style**：`dataset_search(action="info")` 的返回末尾会附 `sql_style=...` 提示——**SQL 必须按这个方言写**（标识符引用符、分页写法、函数集），不许用其它引擎的语法（如该方言不支持的 LATERAL VIEW）。本会话还没见过 sql_style 提示时，先调一次 info 拿到它再写 SQL。

- 标识符与非 ASCII 别名用该方言的引用符包裹（多数后端为反引号：`` AS `订单号` ``）——裸中文别名是语法错误。
- **FROM/JOIN 必须逐字使用字典详情给出的完整 `PHYSICAL_TABLE`**（多段式 `catalog.database.table_name`，常带很长的生成前缀）；只写数据集短名会报 `Table not found`（§2）。

**日期字段类型混杂**（DATE / TIMESTAMP / VARCHAR）——过滤和 JOIN 前先在字典里确认该字段类型，必要时显式转换。很多展示名读起来像"时间"的字段实际是 VARCHAR，对它们适用字符串比较规则，不是日期运算——**以字典详情里的类型为准，不看字段名像什么**。

**两个日期类字段类型不一致时 JOIN 会静默匹配不到任何行**——不报错，只返回 0 行，读起来和"没有数据"一模一样。在 ON 子句里对齐类型，例如与 `'YYYY-MM-DD'` 字符串键关联时：DATE 用 `ON t.{date_col} = k`，TIMESTAMP 用 `ON DATE(t.{ts_col}) = k`，VARCHAR 日期时间串用 `ON LEFT(t.{str_col}, 10) = k`（函数名按 sql_style 方言取等价写法）。写任何日期字段的 JOIN 前，两边类型都要先在字典里确认。

**区间字符串字段不能当日期过滤**：有些字段把整个区间以文本存储（示例值形如 `YYYY-MM-DD ~ YYYY-MM-DD` 就是信号），无法按日期比较。到字典详情里找该数据集单独的起止时间字段，用那两个字段做边界。**示例值就是识别信号——写任何日期条件前先看它**。

**本地约定**：
- 表名用字典完整 `PHYSICAL_TABLE`，列名用字典英文原名；字典的 `joinOn` 覆盖到你要的关联时优先用它（见 §2，joinOn 里给的是数据集名，写进 SQL 时替换成你给物理表起的别名）。
- **过滤条件的右边界，精度不能比数据本身粗**。右边界只到「日」而字段是时间戳或日期时间串 → 上取整到次日零点并用 `<`：`>= '起始' AND < '结束次日'`。用 `BETWEEN` 或 `<= '结束日'` 会静默丢掉结束日当天 00:00 之后的所有行——少了近一整天，不报错，结果看起来完全正常。（VARCHAR 日期时间串同理：字典序下 `'2026-03-31 14:00:00' > '2026-03-31'`。）
- **右边界本身已达到该字段的精度**（如精确到秒的活动起止时间）→ 不存在精度错配，按该字段自身的区间语义写，**从示例值判断**：结束值形如 `23:59:59` 说明是闭区间 → 用 `<=`；结束值是次日 `00:00:00` 说明是左闭右开 → 用 `<`。**绝不对精确到秒的边界机械加一天。**
- **大区间分段拆查时一律用左闭右开**，否则合并结果时边界那一刻会被计两次。
- **VARCHAR 日期边界依赖"字典序 = 时间序"**，而这只在存储格式等宽、零填充时成立。按字符串比较前先看示例值确认格式统一。
- 大事实表查询尽量让口径中已有的时间条件落在主日期字段上；口径本身是全量历史（用户已确认）时照常执行——**不许为性能擅自加条件**。

**综合示例**（一条示例覆盖全部本地约定；示意名必须替换为字典真实数据集名与字段名）：

```sql
-- 行级明细：不加 LIMIT；调用时 purpose="3月订单明细", visibility="export"
SELECT t.order_id AS `订单号`, t.order_date AS `日期`, t.amount AS `金额`,
       p.product_name AS `商品名称`
FROM catalog.db.fact_orders t                  -- 完整 PHYSICAL_TABLE（取自 info 基本信息）
JOIN catalog.db.dim_item p ON t.sku = p.sku    -- 关联条件已对照字典 joinOn 核对
WHERE t.order_date >= '2026-03-01' AND t.order_date < '2026-04-01'   -- 左闭右开
ORDER BY t.order_date DESC
```

## §4 执行与错误处理

失败时**先读返回的错误文本**，按下表处理。严禁不读错误就凭猜改 SQL。

| 错误 | 处理 |
|------|------|
| `数据源不存在 — xxx` | 传了 `datasource_alias` 参数 → 去掉后重试同一条（§1） |
| `Table not found` / `Table not allowed: xxx` | 几乎必然用了数据集短名（或自造名）→ 换 `dataset_search(action="info")` 返回的完整 `PHYSICAL_TABLE` 逐字重试；完整名仍报错 = schema 漂移 → 如实告知用户，不猜替代表 |
| `not in the current data theme` | 数据集不在当前数据主题内，不是不存在 → 告知用户调整主题（加入数据集或切"全部主题"）后重试（§2） |
| `Only SELECT statements are allowed` | **首先怀疑 WITH / CTE**（报错文字从不提它）→ 改嵌套子查询（§3）；其次才查 DDL/DML/分号 |
| SQL 语法错误 | 按报错定位；先检查是否用了 sql_style 之外的方言写法（引用符、函数、分页） |
| `Query timed out`（超时时长是系统设定，不是固定值） | 先做**口径不变**的等价优化：时间条件落在主日期字段、大区间按时间分段拆查后合并。仍超时 → 如实告知用户；收窄范围只能 ask_human 提议（SKILL.md Step 7） |
| 成功但**意外 0 行** | 依次检查：日期字段 JOIN 的类型对齐（§3）→ 存储值格式与你的过滤值是否一致（存 `'03'` 的期间不会匹配 `'P3'`，看字典的示例值）→ 时间范围早于数据起始（`SELECT MIN(主日期字段)`，internal 探查）。查完仍为空才下"没有数据"结论 |

**重试纪律**：修复后可自动重试一次，只允许**语义等价**的修改（修语法、等价改写、执行方式优化）；**严禁静默丢弃或收窄任何过滤条件**（SKILL.md Step 7）。重试仍失败 → 通俗解释问题，把可行的调整（如收窄范围）通过 ask_human 提给用户。
