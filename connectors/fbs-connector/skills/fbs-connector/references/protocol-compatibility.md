# MCP 兼容目标与当前证据边界

本文件从原公共引用目录迁入；业务能力仍受当前工具面和审定合同限制。

本连接器保留以下两个兼容目标，但当前宿主证据状态不同：

1. `2025-11-25`：已有兼容路径；本候选宿主会话仍需实际协商回读。
2. `2026-07-28`：独立候选路径，必须由目标 WorkBuddy 宿主实际发现、协商和调用验证后才能宣称支持。

## 资源分支与协商责任

下文两个修订路径是旧API2合同讨论。已审查的OAuth画像Gateway基线仅接受2025-03-26、2025-06-18、2025-11-25，使用initialize/tools/list/tools/call；它不支持2026-07-28的server/discover。不把旧候选协议路径扩展为新资源能力。各资源实际版本由本轮宿主协商决定，服务源码支持列表不是宿主兼容证明。

- `mcp.json` 不静态设置 `MCP-Protocol-Version`；协议探测、选择和每请求协议头由 WorkBuddy 宿主负责。
- 连接器不从包版本、专家版本或自定义业务头推断 MCP 修订。
- 服务端支持某修订不能反推 WorkBuddy 已支持。实际协商结果来自本次宿主会话；落到更早修订时只能标记兼容降级。
- 在 `2026-07-28` 未取得独立宿主回执前，不得使用“官方双协议已验证”或等价表述。

## `2026-07-28` 路径

- 宿主先使用 `server/discover` 获取服务信息与能力。
- 请求按该修订携带自描述协议头；连接器不依赖 `initialize` 或 HTTP 会话才能调用业务工具。
- 响应中的未知能力、缓存和 `_meta` 字段按向前兼容原则忽略，不能覆盖业务成功/失败判断。
- 当前路径尚待宿主验证；Skill 不得仅因服务端存在 `server/discover` 就主动声称或模拟该能力。

## `2025-11-25` 路径

- 宿主使用 `initialize` 完成版本与能力协商，再调用 `tools/list` / `tools/call`。
- 若服务端返回会话标识，由宿主管理；福帮手业务连续性仍以工具返回的绑定参数为准，Skill 不自行维护 HTTP 会话。

## 两个修订共用的业务合同

- JSON-RPC 2.0 包络与请求 ID 必须正确。
- `tools/list` 是工具与 input schema 真源。
- `tools/call` 的工具级错误、业务失败与缺失回执必须失败关闭。
- 主线语义保持为身份确认 → 场景读取 → 真实交付后的幂等进度记录。
- 不把协议协商成功等同于工具可用、自然业务或上架成功。

## Streamable HTTP 与 SSE

- 当前已知基础路径按无状态 Streamable HTTP 处理；重连只能重新发现能力和读取状态，不能自动重放写工具。
- 只有当前 `tools/list`、服务响应和宿主能力共同给出会话恢复或事件游标语义时，才可携带相应 session/cursor。
- 未证明时不发送 `Last-Event-ID`，不声称断点续传，不把 JSON-RPC request ID 当恢复游标。
- 取消、断网、超时和业务失败分别处理；连接中断不等于用户取消，也不证明写入失败。
