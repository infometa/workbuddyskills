# GenUI 卡片编排规范（扫呗数电票**开具**场景）— 默认输出形态

> 🚨 **本文件是默认输出形态，不是可选风格。** 只要有数据要展示就走这里；
> 文字形态仅在卡片完全无法产出时降级使用（见 `SKILL.md` 9.7）。
> 实际可用组件以当前环境渲染能力为准；若不可用，仍须按本规范生成 card.json
> 并做等效可视化渲染，**不得直接改用文字形态**。
> 可复制的 JSON 模板见 `@references/card-templates.md`。

## 一、通用原则

1. **一条消息只保留一个 Card。** 字段、指标、表格、说明放进同一个 Card。
2. **整条消息最多一个含 Button 的卡片块。**
3. **卡片代替同内容 Markdown。** 卡片已含标题、结论、字段时，不要在卡片外再复述一次。
4. **展示组件与输入组件不混用。** `Text`/`Statistic`/`Table`/`Descriptions` 只展示；
   `RadioGroup`/`Select`/`CheckboxGroup`/`Input`/`Textarea` 只收集。
5. **能选就不要让用户手输。** 固定候选优先 `RadioGroup`（≤12）→ `Select`（≤30）→ `ChoiceList`。
6. **用户可见文案用自然中文业务语言。** 不出现 `total_fee`、`out_trade_no`、`goods_id` 等内部字段名。
7. **一个 Card 内的信息层级固定为：顶部 → 中部 → 底部。**
8. **★ 待确认的开票清单不放确认按钮。** `blueInvoice` 是写操作，确认必须来自用户明确的
   文字指令（"确认""无误""开票"），按钮点击不作为唯一凭据。

## 二、场景一：开票信息清单（待确认，最常用）

**触发场景**：订单开票、自定义开票（商品/油枪），已凑齐抬头、商品、邮箱，等待用户确认。

| 位置 | 组件 | 内容 |
|---|---|---|
| 顶部 | `Text` | 一句引导，如「开票信息确认一下～」 |
| 中部 | `Descriptions` | 抬头类型、发票抬头、商品、税收类目、税率、单价、数量、合计、接收邮箱 |
| 底部 | 不追加 | **不放确认按钮**，等用户回复「确认」 |

**注意**：
- 字段顺序**固定不变**：抬头类型 → 发票抬头 → 商品 → 税收类目 → 税率 → 单价 → 数量 → 合计 → 接收邮箱。
- **★ 九项字段一项都不许少**。查不到的项保留该行、值写「待补充」，并用 `Alert` 说明哪几项待补；
  **不允许把商品/税率/单价/数量整行省略**。`check_card.py` 会校验（`INFO-FIELDS-MISSING`）。
- **合计行永远有值**：订单金额来自订单，不因商品税率缺失而缺席。
- **订单开票**时金额取订单金额，单价/数量按商品口径展示；**⛔ 不得挑商品凑数量倒推金额**（见 SKILL.md 3.4）。
- 数量按实际单位：「1 个」「2 件」「1 升」。
- 税收类目取不到填 `-`，不编造。
- 单价接口返回多少就展示多少，**不评价是否异常**。
- 抬头类型为个人写「个人」，不写「个人/非企业」。
- 金额已是元（接口原值为分，已 ÷100）。
- **★ 用户已明确授权商品/税率口径时**（"按店里常用的来就行"），按用户口径填实际值并注明来源，
  **不退回成「待补充」**。

## 三、场景二：开票结果回执

**触发场景**：`blueInvoice` 已提交且 `invoice_getInvoiceDetail` 确认状态后。

| 位置 | 组件 | 内容 |
|---|---|---|
| 顶部 | `Text` | 一句结论，如「已为您提交开票，发票开具后会发送至邮箱 xxx，请留意查收」 |
| 中部 | `Descriptions` | 发票号码、开票状态、开票时间、接收邮箱 |
| 底部 | 不追加 | **不重复展示**抬头、商品、金额等开票前已确认的信息 |

**注意**：
- 状态枚举说「已开票 / 开票中 / 开票失败 / 已红冲 / 红冲中 / 红冲失败」，**不说「冲红」**。
- **只有 `invoice_getInvoiceDetail` 确认成功后**才能用"已开票"。
- 卡片内不放纯文字下载入口（点不了）；PDF 通过文件交付通道发。

## 四、场景三：开票状态回查

**触发场景**：用户问「那张票开好了吗」「查一下发票状态」。

| 位置 | 组件 | 内容 |
|---|---|---|
| 顶部 | `Text` | 标明是哪一张发票 |
| 中部 | `Descriptions` | 发票金额、发票类型、开票状态、开票来源、开票时间 |
| 底部 | 不追加 | — |

**注意**：
- 状态未知（返回 0 或空）→ 如实说「状态暂时查不到，建议稍后再试」，**不猜**。
- 未确认成功前不说"开好了"。

## 五、场景四：订单明细

**触发场景**：用户查订单、查最新一笔订单、要求"查看更多"。

| 位置 | 组件 | 内容 |
|---|---|---|
| 顶部 | `Text` | 一句结论，如「今天（10月13日）共 3 笔订单～」 |
| 中部 | `Table` | 订单号 / 订单金额 / 交易时间 / 门店 / 支付状态 |
| 底部 | 不追加 | 顶部结论句已含笔数，**不再重复**「总条数 / 是否节选」；仅超 10 行节选时补一句 `Text` |

**单笔订单查询**（场景四之补）：

| 位置 | 组件 | 内容 |
|---|---|---|
| 顶部 | 不追加 | ⛔ **不加结论句**，标题已说明一切 |
| 中部 | `Descriptions` | 交易时间 → 门店 → 支付方式 → 交易金额 → 交易状态 → 商户订单号 → 渠道订单号 |

**注意**：
- 🚫 **不展示查询时间、查询范围**（定稿，适用所有场景）：查询时照常显式传
  `begin_time`/`end_time` 取数，卡片上不出现查询口径字段。
- `Table` 适合 1—6 列、最多 10 行（默认近 10 条）；超出时只放前 10 行并在底部说明总数。
- **表格容器宽度放宽到 520px**（其余卡片类仍用 280px）：五列信息量较大，
  过窄会让 20 位订单号与金额列粘连。
- **列间必须留白**：每列 `padding-right:12px`（最后一列为 0），行高留足不粘连。
- 订单号完整展示，禁止省略号截断。
- **查单笔订单时严禁附带汇总数据**（今日总笔数、总金额）。
- 两个订单号各自完整展示，不得省略号截断、不得合并成一行。
- 支付状态只写「支付成功 / 支付中 / 已撤销 / 支付失败」。
- 用户回复「查看更多」→ 用上一页最后一条的 `id` 作为 `start_id` 续查。

## 六、场景五：异常、未开通与失败提示

**触发场景**：数电票未开通、开票失败、连接器不可用、状态取不到。

| 位置 | 组件 | 内容 |
|---|---|---|
| 顶部 | `Descriptions` | 已确认的真实信息（订单号、时间、抬头等）；**不含查询时间/查询范围** |
| 顶部 | `Alert` | 状态说明（未开通 / 异常 / 暂时取不到） |
| 底部 | 不追加 | — |

**注意（底线）**：
- 数电票未开通（`invoice_switch = 0`）→ Alert 说「当前商户还没有开通数电票功能哦～」，
  **不引导用户使用外部应用或联系外部人员**。**必须先查开关再断言**。
- 接口异常 / 连接器不可用 → 只能说「暂时取不到」，**不得**说成没有开票，
  **不得**断言商户未开通数电票；授权引导只写「扫呗商户服务」，不出现技术标识。
- 开票失败 → 先核实（授权状态 + 开关状态）再说明，**不未经确认直接归因**。
- 降级时**不得**出现任何接口没返回的金额与笔数。

## 七、场景六：待补信息

**触发场景**：用户只给了部分开票信息（只有抬头、只有邮箱、没给数量），需要列出还缺什么。

| 位置 | 组件 | 内容 |
|---|---|---|
| 顶部 | `Text` | 一句说明，如「开票信息还差一点～」 |
| 中部 | `Descriptions` | 已确认的字段 |
| 底部 | `Descriptions` 或 `Text` | 待补字段清单 |

**注意**：待补字段是**要问用户的东西**，不是数据，**不得**编造默认值填充。
能通过接口查到的（商品单价、税率、税收类目）**先查再列**，不把能查的推给用户。

## 八、组件选择速查（本技能场景）

| 需求 | 用哪个组件 | 不用什么 |
|---|---|---|
| 展示开票字段清单 | `Descriptions` | 不用多行 `Text` 硬凑 |
| 展示金额/数量 | `Statistic` | 不用 `Text` 硬凑数字 |
| 展示一句核心结论 | `Text` | 不用 `Alert`（除异常外） |
| 订单明细列表 | `Table` | 不用 `Text` 逐行罗列 |
| 门店/抬头类型选择 | `RadioGroup` / `Select` | 固定候选不用 `Input` |
| 下载、继续等动作 | `Button` | 不在 `Table` 行内放按钮 |

## 九、与文字输出的关系

- **默认卡片**；只有两种情形可退回文字：① 环境完全无法产出卡片 JSON；
  ② **★ 用户明确要求用文字发送**（"文字发我""别用卡片"）——此时以用户指令为准，
  **不算违规降级**，也**不需要**解释"为什么没能出卡片"。
- 文字输出时，**字段、顺序、术语、数值与卡片完全一致**，版式见 `SKILL.md` 9.7；
  开票信息清单同样**必须给全九项字段**，不允许整行省略。
- 两种形态的**数值必须同源**：都来自 `scripts/calc_amount.py` 的输出，不得各算各的。
- 字段不换行、说明文案不换行、查询时间/查询范围不展示、emoji 语义化等硬约束见 `SKILL.md` 9.2 / 9.4。
