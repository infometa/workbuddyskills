## 场景一：订单开票

**触发说法**："开最新一笔订单的发票"、"给这笔订单开张发票"、订单号 + "开票"

### 步骤

1. **只读探测并行发出**（开关/订单/商品可同时查）；开关未开通则终止。
2. 取得订单号：用户已给则用；未给则按"最新一笔"规则查（见场景五）。
3. `invoice_getTradeList` 取真实 `out_trade_no`、金额、时间、状态、门店。**金额自动读订单金额，禁止挑商品凑数量倒推。**
4. **商品/税率按 SKILL.md 3.4 顺序**：读默认商品税率 → 有默认和用户确认一下，没有默认让用户选或新增。
5. 商品/税率确认后，让用户填抬头类型、发票抬头、接收邮箱（一次问齐）。
6. **一次性展示完整信息清单**（卡片·信息清单），等确认。
7. 用户确认 → `invoice_blueInvoice`（传 `out_trade_no`）。
8. `invoice_getInvoiceDetail` 确认状态 → 卡片·开票结果。

### 边界

- ❌ 没拿到真实 `out_trade_no` → **禁止**调用开票。
- ❌ 商品明细查不到 → 说清缺什么，**不要编造 `goods_list`**。
- ❌ 用户未确认 → **停在清单状态**，绝不自动提交。

## 场景二：自定义开票（商品）

**触发说法**："开一张包子的发票，数量 2 个"、"开张发票抬头是 XX 的"

### 步骤

1. **不查订单**——用户明确说自定义开票。
2. 商品/税率按 SKILL.md 3.4 顺序：读默认商品税率 → 有默认和用户确认，没有默认让用户选或新增；用户已点名商品则按该商品查 `invoice_getGoodsList` 取商品 ID、税率。
3. `invoice_getGoodsDetail` 补税收类目（取不到填 `-`）。
4. 填抬头类型、发票抬头、接收邮箱（一次问齐）。
5. 展示清单 → 确认 → `invoice_blueInvoice` → 详情核实。

### 边界

- ❌ 抬头只写了抬头没写类型 → 追问「个人还是企业？」
- ❌ 邮箱格式明显不对 → 提示确认
- ❌ 单价看着奇怪（比如 0.01 元）→ **照常展示，不评价**
- ❌ 用户没说数量 → 按 1 个，或追问

## 场景三：自定义开票（油枪，成品油行业）

**触发说法**："开一张 95 号汽油的发票"

### 步骤

1. 开关校验。
2. `invoice_oilGunlist` 查油枪（匹配 95 号）。
3. `invoice_oilGunLatestPrice` 查**最新生效价**（单位分）。
4. 收集抬头、邮箱。
5. 展示清单 → 确认 → 开票，**不得遗漏成品油专用字段**。

### 边界

- ❌ **绝不编造油枪编号、开票地点**——必须来自接口。
- ❌ 不用历史价，必须用 `invoice_oilGunLatestPrice`。
- ❌ 漏掉成品油专用字段 → 会开错票。

---

## 场景四：开票状态回查

**触发说法**："我那张票开好了吗"、"查一下发票状态"

### 步骤

1. 开关校验。
2. `invoice_getInvoiceList` 找到目标发票，或 `invoice_getInvoiceDetail` 查指定发票。
3. **状态枚举做术语映射**（冲红 → 红冲）。
4. 如实告知（卡片·状态回查）。

### 边界

- ❌ 未确认成功前不说"开好了"。
- ❌ 状态未知（返回 0 或空）→ 如实说"状态暂时查不到，建议稍后再试"。

## 场景五：订单查询与分页

**触发说法**："查今天的订单"、"查看更多"、"查最近的订单"

### 步骤

1. 换算时间范围：未指定 → 最近 7 天；**跨度不超过 6 个月**。
2. `invoice_getTradeList` **显式传** `begin_time`/`end_time`，`search_type=1`。
3. 解析 `trade_list`（JSON 字符串），金额 ÷100。
4. 展示**最近 10 条**，提示可"查看更多"。
5. 用户回"查看更多"→ 用上一页最后一条的 `id` 作 `start_id` 继续查。

### 查"最新一笔"

用 `invoice_getTradeList` 显式传时间范围，取**交易时间最近**且 `pay_status_code="1"` 的一笔，
以卡片·单笔订单呈现（交易时间 → 门店 → 支付方式 → 交易金额 → 交易状态 → 商户订单号 → 渠道订单号）。

### 边界

- ❌ **不传时间参数** → 会只拿到当天，甚至拿不到"最新"。
- ❌ 查 6 个月以外的订单 → 明确告知不可查（最早可查日期要说清楚）。
- ❌ 查单笔订单时附带"今天共 X 笔共 X 元" → **禁止汇总**。
- ❌ 一次展示超过 10 条。
- ❌ 把失败、支付中、已撤销的当成可开票订单。
- ❌ 未指定门店时**反复追问门店**。

## 场景六：开票失败排查

**触发说法**：开票时报错、"额度不足"、"服务异常"、"资源包已过期"

### 步骤

1. **不盲目重试**——`invoice_blueInvoice` 是写操作。
2. `invoice_getCrownAuthInfo` 查微信/支付宝官方电票授权状态。
3. `invoice_getSwitchByType` 查相关发票开关状态。
4. 根据**实际查询结果**说明情况（卡片·异常提示）。
5. **保留本次已确认的开票信息**，问题解决后可重试。
6. 查 `references/mcp-tools.md` 错误码速查表定位报错含义。

### 边界

- ❌ 未经核实就归因"是您额度不够"。
- ❌ 失败后自动重发开票请求。
- ❌ 让用户重新填一遍已确认的信息。

## ★ 场景七：连接器不可用（降级交付）★

**这是本 skill 最容易做错的场景，也是评测最容易命中的失分点。**

**触发情形**：调用任一 `扫呗商户服务` 接口返回未授权 / 授权失效 / 连接器不可用。

### 核心原则

> **只阻断"问扫呗"的部分，不阻断"处理用户已给的真实数据"的部分。**

用户已经给了订单号、贴了订单文件、说了抬头邮箱——**这些都在你手上，直接用**。
拿不到的只是"扫呗侧的状态核验"，不是"全部信息"。

### 7.1 用户给了订单号

整理出已知字段（订单号、时间、金额），用卡片·降级交付呈现：顶部 `Descriptions` 列出已知信息，
底部 `Alert` 说明卡在哪一步 + 给出「扫呗商户服务」授权指引。
**没有拿到金额和时间就只列订单号**，不编造。**没有回绝用户。**

### 7.2 ★ 用户给了订单文件（直接整理，绝不可回绝）

把文件里的订单**完整整理成订单明细卡片**（`Text` 结论 + `Table` 明细 + 状态说明），
再补一张「待补信息」卡片列出还缺的抬头/邮箱。
状态列标为「待核验」——因为需要连接扫呗核对支付状态与是否已开票。

> ⭐ **这是本场景的核心。** 用户提供了真实数据，**必须完整整理成清单**——
> 这是完全不依赖连接器的工作，是底线 2 的直接体现。**绝对不能**因为"连接器不可用"就说"我无法处理您提供的文件"。

### 7.2.1 ★★ 开票信息清单必须给全九项字段（不可整行省略）

只列了订单号、时间、金额、门店、支付方式，而把**商品 / 税收类目 / 税率 / 单价 / 数量整行省略**，
是本场景最高频的交付缺口。**九项字段一项都不许少**：

抬头类型 / 发票抬头 / 商品 / 税收类目 / 税率 / 单价 / 数量 / 合计 / 接收邮箱。

- 查不到的项**保留该行、值写「待补充」**，并在卡片上用一句 `Alert` 说明哪几项待补、为什么。
- **合计/金额行永远有值**（订单金额 ÷100，`calc_amount.py` 取值），不因商品税率缺失而缺席。
- **「待补充」是占位说明，不是数据**——绝不编造商品名或税率去填。
- 用户已授权口径（「商品和税率按店里常用的来就行」）时，商品/税率**写实际用的值**，
  并注明来源是「按您说的口径」；**不得**因为"没读到接口默认值"就退回成「待补充」。

卡片模板见 `@references/card-templates.md`「模板一之补」。

### 7.2.2 ★★ 未核实的事实不得说成结论

- 不得在没读到接口数据时说「商品和税率是按店里默认那套来的」——这是对未核实事实的断言。
  可写：「商品/税率待扫呗侧确认」或「按您说的『餐饮』，税率 1%」（用户授权口径）。
- 不得在没实际探测过时把原因归给用户（「扫呗侧数据取不到，需要您先授权」）。
  照实说探测结果：未授权 / 连不上 / 工具不可用，三种说法不同（见 SKILL.md 1.3）。

### 7.3 只问开票流程

纯信息问答，不需要连接器，必须完整回答：抬头、抬头类型、邮箱、商品与数量（成品油另需油枪编号与升数；订单开票另需订单号）。

### 7.4 错误示范（这些都算过度阻断，禁止）

```
❌ "连接器不可用，我无法帮您开票。"                    → 只丢一句，未交付任何信息
❌ "我需要连接器才能处理您的文件，请先授权。"          → 拒绝处理用户已给的数据
❌ "请先完成接口或部署名层面的授权。"                  → 对商户暴露内部标识
❌ 明明清单齐全却因"无法查状态"而不整理                 → 该做的没做
```

### 7.5 降级交付检查清单

- [ ] 用户已给的订单号 / 订单文件，我整理了吗？
- [ ] 用户已给的抬头、邮箱、金额，我用上了吗？
- [ ] **开票信息清单的九项字段列全了吗**（商品/税收类目/税率/单价/数量不许整行省略）？
- [ ] 金额行有值吗（来自订单，不因商品税率缺失而缺席）？
- [ ] 用户已授权商品/税率口径时，我用的是他的口径而不是「待补充」吗？
- [ ] 我说明具体卡在哪一步了吗？说法与实际探测结果一致吗？
- [ ] 我给出了可操作的授权指引吗？
- [ ] 指引里用的是**「扫呗商户服务」**这个名字吗？
- [ ] 我有没有编造金额、时间、状态、商品、税率？

**前四条是底线，中间两条是及格线，最后三条是红线。**

## ★ 场景八：开票卡单补确认（蓝票后一直开票中）★

**触发说法**：用户说「开成功了吗」「怎么还没开出来」「一直开票中」「帮我把它开成功」等，
而 `invoice_getInvoiceDetail` 显示 `issue_status=0`（开票中）且 `error_msg` 为空。

### 8.1 现象判定（实测）

- `invoice_blueInvoice` 已返回 `invoice_id`（开票单已建立）。
- `invoice_getInvoiceDetail` 多次回查（间隔数十秒，可查 2~3 次）：
  `issue_status` 持续为 `0`，`ticket_sn`/`ticket_code` 为空，`error_msg` 为空。
- 提交时可能收到「资源包已过期」等报错文字——**该文字不等于失败**，实测报此错后开票单仍正常、最终出票成功。

### 8.2 步骤

1. **⛔ 禁止重发 `invoice_blueInvoice`**（重复开票风险）；⛔ 禁止只是反复只读回查干等。
2. 调用 `invoice_confirmInvoice` 补确认：
   - `invoice_id`：蓝票返回的开票记录 ID（整数）
   - `total_fee`：开票总金额，**单位分**（与订单金额一致）
   - `goods_list`：与蓝票同格式 JSON 字符串（id/数量/单价/别名齐全，见 `mcp-tools.md` §8）
   - `ability_code`：`BASE_ABILITY`（成品油等按行业传 `REFINED_OIL_ABILITY`）
3. 回查 `invoice_getInvoiceDetail`：`issue_status=1` → 开票成功，出场景二卡片（发票号码/开票状态/开票时间/接收邮箱）。
4. 补确认后仍不成功 → 如实告知状态、保留开票信息、不编失败原因，走场景六排查。

### 8.3 边界

- `confirmInvoice` 是**写操作**，一次调用后必须先查详情再决定是否继续，**不盲目重发**。
- 金额单位是分，走 `scripts/calc_amount.py` 取展示值。
- 补确认成功后，卡片只呈现状态与凭证，**不重复展示抬头、商品、金额、邮箱**（已在开票前确认过）。
- 若用户在卡单期间提出新订单开票，先按该新订单走订单开票流程，卡单单据另行补确认，两者不混。

## 全场景通用边界

| 场景 | ❌ 禁止 |
|---|---|
| 全部 | 编造扫呗侧任何数据 |
| 全部 | 评价单价是否异常 |
| 全部 | 暴露 MCP 名称、参数、内部票种信息 |
| 全部 | 授权不可用时拒绝处理用户已给数据（★ 过度阻断）|
| 全部 | 待确认信息未获明确确认就提交开票 |
| 全部 | **有数据要展示时用文字形态而非卡片**（★ 默认卡片）|
| 全部 | **把接口返回的分当成元展示**（单价/金额必须 ÷100）|
| 全部 | **订单开票时挑商品、凑单价×数量倒推金额**（金额一律读订单）|
| 全部 | **把订单开票与自定义开票混用**（见 SKILL.md「快与准」判断口诀）|
| 订单 | 没拿到真实订单号就提交 |
| 自定义 | 把 `invoice_type` 当必填（实际可选） |
| 查询 | 不传时间参数 / 查超 6 个月 / 单笔订单附汇总 |
| 回查 | 未确认就说"开好了" / 状态说"冲红"（应说"红冲"）|
| 失败 | 盲目重试 / 未经核实归因 / 让用户重填信息 |
| 卡单 | **蓝票后一直"开票中"却干等、或重发 `blueInvoice`**（应走 `confirmInvoice` 补确认）|
| 卡单 | **把提交接口报错文字（如"资源包已过期"）当作对商户的失败原因**（详情显示开票中时禁止）|
