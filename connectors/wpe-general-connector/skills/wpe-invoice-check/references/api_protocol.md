# invoice_check 接口规范

| 项 | 值 |
|---|---|
| api key | `invoice_check` |
| 标签 | 发票查验 |
| 方法 / 路径 | POST `/third/invoice/v1/check` |
| service | `wpe-third-server`（Consul 解析，实测 10 个候选实例） |
| 调用方式 | `call_internal_api(api="invoice_check", params={...})` |
| 通道 | MCP 连接器 `wpe-general-connector`（腾讯数电发票），通过 `call_internal_api` 工具调用 |

## 请求参数（**严格大驼峰**，后端 @JsonProperty 强制大写）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `InvoiceType` | string | ✅ | 票种代码，不同代码走不同查验渠道，**不可臆造**（枚举见 `invoice-types.md`） |
| `InvoiceNo` | string | ✅ | 发票号码（数电票 20 位） |
| `InvoiceDate` | string | ✅ | 开票日期，**必须 `yyyyMMdd` 紧凑格式** |
| `Amount` | number | ✅ | 金额，单位 **分**（整数，Java Long）。**口径随票种变化**：31/32/61/83 传价税合计；01/09/23、04/10/24、11/14 传不含税金额（04/10/24 可置 0）；03/15 传车价合计 |
| `InvoiceCode` | string | 视票种 | 数电票（31/32/61/83）可空；其余票种**必填**，纸质票 10-12 位代码 |
| `CheckCode` | string | 视票种 | 01/02/03/08/15/23/31/32/61/83 可省略传 `""`；`24` 传全电号码后六位；04/09/10/11/14 传校验码后六位 |

> 传小写驼峰（invoiceType 等）会报「参数不能为空」。
> 传 `InvoiceDate="2026-09-16"` 会报「查询发票不规范」——**这是入参问题，不是票有问题**。
> 实测 `"2026-09-01"` 与 `"20260901"` 都能过参数校验进入业务层，但只有紧凑格式能真正查到票。

### ⚠️ `Amount`：单位「分」+ 口径随票种变化（2026-09-17 修订）

- **单位一律是分**（Long 整数）：`Amount = int(round(元 × 100))`。
- **口径随票种变化**（这是最容易错的地方）：

| 票种 | 取票面哪一栏 | 示例 |
|---|---|---|
| 01 / 09 / 23 | **不含税金额**（票面「金额」栏） | 8.26 元 → `826` |
| 04 / 10 / 24 | **不含税金额**（可为空，置 `0`） | 8.26 元 → `826`；拿不到 → `0` |
| 11 / 14 | **不含税金额** | 8.26 元 → `826` |
| 31 / 32 / 61 / 83 | **价税合计**（票面「价税合计」栏） | 9.00 元 → `900` |
| 03 / 15 | **车价合计** | 120000.00 元 → `12000000` |

- 换算速查：

  | 场景 | 票面取值 | `Amount`(分) |
  |---|---|---|
  | 数电票（31/32/61/83）价税合计 9.00 | 价税合计 | `900` |
  | 专票（01/23）不含税 8.26 | 金额（不含税） | `826` |
  | 普票（04/10/24）不含税 8.26 | 金额（不含税） | `826` |
  | 普票（04/10/24）金额为空 | — | `0` |
  | 机动车（03/15）车价 120000.00 | 车价合计 | `12000000` |

- 用户口头说的"开票金额 X 元"通常指**价税合计**；当票种口径是「不含税金额」时，
  **必须问到票面「金额」栏或税率**，不要拿价税合计直接填（也不要自行按税率反推后不告知用户）。

⚠️ 单位或口径写错，税局只会回「发票信息不一致」，看不出是金额问题还是票不存在，极易误判成假票。
历史教训：26617200000018867073 传 `300`（元）与 26507200000011978330 传 `9`（元）都因此未命中；
改成「分」（30000 / 900）后后者立即查通。

### `CheckCode`（校验码）规则

| 情形 | 取值 |
|---|---|
| 01 / 02 / 03 / 08 / 15 / 23 / 31 / 32 / 61 / 83 | 可省略，传 `""` |
| 24 | 全电号码（数电号码）的**后六位** |
| 04 / 09 / 10 / 11 / 14 | 票面右下角「校验码」的**后六位** |

`InvoiceCode` 同理：31/32/61/83 数电票可空，其余票种必填（纸质票右上角 10-12 位代码）。

## 响应信封（腾讯云风格）

```json
{ "Response": { "RequestId": "xxx", "Error": null, "Data": { ...票面... } } }
```

- `Error == null` → 查验通过
- `HTTP 200 + Error.Code="InvoiceCheckError"` → 业务查验失败，`Error.Message` 是中文
- `HTTP 400 + Error.Code="InvalidParameter"` → 参数校验失败
- **没有 `code` 字段，不要找 code**

## 税局中文 Message 对照表

| Message | 含义 | 处置 |
|---|---|---|
| 所查发票不存在 | 税局无此记录 | 核对号码/日期录入；不等于假票 |
| 发票信息不一致 | **要素组合未命中税局记录**（金额单位/票种/日期任一不对，或票未同步） | 先验查 `Amount` 是否传了「元」而不是「分」——这是最高频原因 |
| 查询发票不规范 | 多为入参问题（日期格式/渠道不匹配） | 先改 `yyyyMMdd` |
| 超过该张票当天查验次数 | 该票当日 5 次配额用尽 | 次日再查，勿重试 |
| 二维码参数不合法 | 该票种走二维码渠道，缺校验码/代码 | 换票种或补全要素 |
| 区块链发票查验异常 | 区块链渠道（`09`）异常 | 换票种 |
| 处理业务异常 / 查验异常 | 下游渠道异常 | 记 RequestId，稍后重试 |

## 票种代码（InvoiceType）

**完整清单见 `references/invoice-types.md`**（唯一数据源，直接读该文件获取全部票种）。

接口侧未返回枚举，`list_internal_apis` 只写：「`"01"` 增值税专用发票、`"04"` 增值税普通发票等，
不同代码走不同查验渠道，取值请向用户确认，不要臆造」。因此：

官方票种字典（2026-09-16 用户确认）：`01` 增值税专用发票、`03` 机动车销售统一发票、
`04` 增值税普通发票、`09` 区块链发票、`10` 增值税电子普通发票、`11` 卷式发票、`14` 通行费发票、
`15` 二手车销售统一发票、`23` 电子发票（纸质专用）、`24` 电子发票（纸质普通）、
`31` 数电/电子发票（专用发票）、`32` 数电/电子发票（普通发票）、
`61` 数电/电子发票（航空运输电子客票行程单）、`83` 数电/电子发票（铁路电子发票）。

早期按「渠道响应」反推的票种名称（如 `02` 机动车、`11` 电子专票、`14` 电子普票）**已作废**——
渠道表现与票种名称是两回事，名称一律以上表为准。

## 配额：按票号统计、跨票种共享（2026-09-16 实测）

对同一张票（26617200000018867073）先后用 `11`、`14`、`31`、`32` 查验，
四个票种**均**返回「超过该张票当天查验次数」→ 当日 5 次配额是**按票号**计的，与票种无关。

推论：**换票种重试不会获得新配额**，只会加速耗尽。票种不确定时必须先问用户，
确认后一次查准；不要把"换几个代码试试"当成排查手段。

## 超时与重试语义（脚本内置）

| 分类 | 判定 | 是否重试 |
|---|---|---|
| 瞬时故障 | 文本含「失败：超时」「超时（10000ms）」、`timeout`、网络异常（`ECONNRESET`/`ETIMEDOUT`/`fetch failed`）、响应无 `Data` | ✅ 重试 2 次，退避 2s → 4s |
| 业务失败 | 「所查发票不存在」「发票信息不一致」「查询发票不规范」「超过该张票当天查验次数」「二维码参数不合法」 | ❌ 立即返回 exit 2 |
| 下游业务异常 | 「处理业务异常」「查验异常」 | 默认 ❌；`RETRY_ON_BUSINESS_ERROR=1` 时 ✅ |
| 鉴权/网关 | HTTP 403 / JSON-RPC `-32007` | ❌ 立即返回 exit 1 |

- 网关对下游有 10s 超时上限，超时原文：`调用内部接口 invoice_check 失败：超时（10000ms）`。
- **重试同样消耗该票当日配额**（超时不代表下游没收到请求），`MAX_RETRIES` 不要超过 2。
- 重试耗尽 → exit 3，脚本打印每次尝试的 `RequestId`；调用方须如实告知用户"未取到票面"并给出后续建议。

## 配额与排障

- 税局对**同一张票每天限查 5 次**，超限返回「超过该张票当天查验次数」。
  排查时不要批量扫票种，扫 20 个代码必然打满配额。
- ⚠️ **未命中的请求同样计数**：成功票面里的 `CheckCount` 是当日累计查验次数，
  实测「2 次未命中 + 1 次命中」= `CheckCount=3`。所以「超过查验次数」**不能证明票存在**。
- 对照实验：号码末位 +1 重查。若返回「所查发票不存在」说明链路正常；
  ⚠️ 但票种 `32` 实测对未命中统一报「发票信息不一致」，此时对照实验**失效**，
  不要据此推断目标票存在。
- 网关对下游有 10s 超时上限，超时返回「调用内部接口 invoice_check 失败：超时（10000ms）」。
