## 二维码纠错案例（v3.1.1 实测 2026-09-17）

永辉超市数电普票 26507000000247844178（164.49 元，2026-07-27）：
- **视觉识别把 20 位号码读成 21 位**（`265070000000247844178`，多读一个 0）；
- 渠道对错误长度号码报「二维码参数不合法」而非「不一致」，先后试 32 无校验码 /
  32+校验码(后6位) / 24+不含税+校验码 三种组合均复现，白烧 3 次配额；
- **解码票面二维码**（`scripts/decode-qr.py`，cv2）拿到权威 20 位号码后第 4 次查验通过；
- 教训：入口 A 识别后**必须**先跑二维码交叉校验再查验（SKILL.md §1.1 第 1 步）；
  「二维码参数不合法」优先怀疑**号码长度/位数错误**，而不是校验码缺失。
- 注意：该渠道对超时自动重试计数进 CheckCount（1 次超时 + 1 次成功 → CheckCount=2）。

## 案例：26617200000018867073（2026-09-16，300 元，数电票）

### 坑 1：日期格式导致全表「查询发票不规范」

用 `InvoiceDate="2026-09-16"` 时，票种 `01/03/04/08/11/14/15/20`
全部返回 `Error.Code="InvoiceCheckError"` + `Message="查询发票不规范"`、`Data: null`。
换成 `20260916` 后立即进入税局业务层（返回「发票信息不一致」/「所查发票不存在」）
→ 说明**是入参格式问题，不是票的问题**。

### 坑 2：对照实验确认票存在

| 号码 | 日期 | 返回 |
|---|---|---|
| `26617200000018867073` | 20260916 | 发票信息不一致（01/03/04/08）/ 超过该张票当天查验次数（11/14） |
| `26617200000018867074`（末位+1 对照） | 20260916 | **所查发票不存在** |

对照票返回「不存在」而目标票从不返回「不存在」→ 目标票在税局有记录。

### 坑 3：批量扫票种打满当日配额

为确定票种一次性扫了 `01,02,...,16,20,51,52` 共 19 个代码（此前另有约 20 次探测），
随后票种 `11`/`14` 稳定返回「超过该张票当天查验次数」，当日再也拿不到票面。

**教训：票种不确定就问用户，一次只查一个票种。**

## 票种代码纠错（v2.2.0）

- 早期按渠道响应反推票种名称，写成了 `02` 机动车 / `11` 电子专票 / `14` 电子普票，**全部是错的**。
  用户提供官方票种字典后更正为 14 个代码：`01/03/04/09/10/11/14/15/23/24/31/32/61/83`，
  其中数电票专票 = `31`、普票 = `32`（此前误用 `11`/`14`）。
- 实测 `31`/`32` 查 26617200000018867073：均返回「超过该张票当天查验次数」
  （RequestId `8525ead2b8cbe75c` / `39d147baa9b8bade`）→
  **当日配额按票号统计、跨票种共享**，换票种不会获得新配额。
- 因该票当日配额已耗尽，`31`/`32` 是否命中无法验证，需次日以 `InvoiceType=31`（或 `32`）重查确认票面。

## 超时重试（v2.0.0 起脚本内置）

- 触发条件：文本含「失败：超时 / 超时（10000ms）」、`timeout`、网络异常、或响应无 `Data`。
- 行为：重试 2 次（合计 3 次尝试），退避 2s → 4s，逐次打印 `RequestId`。
- 不重试：不存在 / 不一致 / 不规范 / 超限额 / 二维码不合法 / 鉴权失败 —— 重试只会白烧配额。
- 三次仍无票面 → 记录每个 RequestId 与"次日重查 / 找下游排查"建议，由调用方如实转达用户。

自测（不消耗真实票配额的方式）：用对照票（不存在的号码）通过连接器
`call_internal_api(api="invoice_check", ...)` 验证业务失败分支——应只尝试 1 次、立即返回业务失败。

## 通道与鉴权

- 税号走连接器 `wpe-general-connector`（腾讯数电发票）的连接头 `X-Subject-Id`（不是接口参数）。
- 税号未接入（access_status ≠ 00）→ 网关 `403 / JSON-RPC -32007`，
  表现是 WorkBuddy 把**整个连接器下线**（工具从调用列表消失），不是单个接口报错。
- 连接器未加载时，用名称 `wpe-general-connector`（或「腾讯数电发票」）在连接器列表查找并加载；
  首次调用不带 token，返回 401 则停下提示用户完成 MCP 授权。

## 实测：26507200000011978330（数电普票，2026-09-16）

用户要素：票头「电子发票（普通发票）」→ 票种 `32`；价税合计 9.00；开票日期 20260916。

| 步骤 | 参数 | 返回 | RequestId |
|---|---|---|---|
| ① 目标票查验 | `32` / ...330 / 20260916 / 9 | 发票信息不一致 | `11218eab6edbd97a` |
| ② 对照实验（号码 +1） | `32` / ...331 / 同 | **也是**「发票信息不一致」 | 目标 `46ac35083b5bb044`、对照 `6ac86c3766e155dd` |
| ③ 渠道自检（已知有记录的票） | `32` / 26617200000018867073 / 300 | 超过该张票当天查验次数 | `849ba411a9d2ef03` |

结论链：

1. ②说明票种 `32` 渠道对**未命中**统一报「发票信息不一致」，**对照实验在该票种下失效**，
   不能像票种 `11` 那样靠"对照返回不存在"来反推目标票存在。
2. ③证明渠道能命中记录（有记录的票会走到配额计数而非报"不一致"）→ ①的「不一致」是真实的
   要素未命中，**不是渠道故障**。
3. 由此给出归因排序，如实反馈"无法判定为真票"，未下真伪结论。

### ✅ 复盘：根因是 `Amount` 单位错了（不是票的问题）

用户纠正：**`Amount` 是价税合计总金额，单位【分】**。此前按「元」传（9 / 300）全都未命中。

| 参数 | 结果 |
|---|---|
| `Amount=9`（元） | 发票信息不一致 |
| `Amount=900`（分 = 9.00 元） | **查验通过，票面完整返回**（RequestId `7b4a7f0143bf1694`） |

返回的票面关键字段（可作字段字典用）：

InvoiceItems[]                     明细行：GoodsName / TaxClassCode / GoodsTaxRate / GoodsAmount ...
