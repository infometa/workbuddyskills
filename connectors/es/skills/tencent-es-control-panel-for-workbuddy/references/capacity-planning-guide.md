# 腾讯云 ES 容量规划指南

> 本文档只承载**领域知识**：操作优先级、规格选择表、扩容量计算的业务含义、最佳实践。
>
> 🔴 **不在本文档定义阈值与算法** —— 全部指标阈值、偶发/持续判定条件、线性回归与外推公式、推荐分流规则，一律以 [`capacity-forecast-rules.md`](capacity-forecast-rules.md) 为唯一权威来源。
> 🔴 **不在本文档定义 tool 参数** —— 见 [`mcp-tools-reference.md`](mcp-tools-reference.md)。
> 🚫 **所有数值计算必须由 `scripts/forecast_calc.py` 完成，禁止 Agent 心算。** 本文档的公式仅用于向用户解释推荐依据。

## 核心原则

> **扩容是最后手段，不是第一反应。**
>
> 在推荐任何扩容操作前，必须先区分：是业务增长导致的持续性压力，还是偶发事件（大查询、数据导入、配置不当）？
> 只有确认是持续性、结构性的资源不足，才推荐扩容。

> ⚠️ **职责边界**：根因分析属于 `tencent-es-diagnose` skill。本 skill 在判定为「偶发型」时，应**明确建议转由 diagnose skill 排查**，而不是自己下根因结论、也不是直接推荐扩容。

### 操作优先级原则

| 优先级 | 操作类型 | 对应 MCP tool | 说明 |
|--------|---------|--------------|------|
| ① 最优先 | **扩云硬盘容量** | `UpdateInstanceDiskSize` | 不搬迁数据，影响最小 |
| ② 次优先 | **升配规格** | ⛔ 暂无 MCP tool → 只读推荐 + 控制台 | 涉及数据搬迁，但属扩容方向 |
| ③ 再次 | **横向扩容（增加节点）** | `UpdateInstanceNodeNum` | 需数据均衡（Rebalance），有一定 IO 开销 |
| ④ 禁止 | **缩容节点、降配规格、切换磁盘类型** | — | 涉及数据搬迁，风险高，本 Skill 不执行 |

> ⚠️ **涉及数据搬迁的操作**：纵向扩容（升配规格）、横向扩容（rebalance）、缩容节点、切换磁盘类型（本地盘 ↔ 云硬盘）。
> ⚠️ **单次单一变更**：腾讯云不允许一次同时变更多种类型。多维度告警时按上表优先级**串行执行，一次只做一项**。

## 各维度的处理方向（阈值见 capacity-forecast-rules.md）

### 磁盘使用率偏高

```
Step 1：识别磁盘类型（DescribeInstances 的 DiskType 字段）
  ├── 本地盘（LOCAL_SSD）→ 只能横向扩容（增加节点）
  │                          容量与机型绑定，无法单独扩磁盘
  └── 云硬盘（CLOUD_PREMIUM / CLOUD_SSD / CLOUD_HSSD）
                          → 优先扩云硬盘容量（原地扩容，无数据搬迁）
                              ↓ 若已达 DescribeClusterDiskRange 的 Max
                              → 再考虑横向扩容（增加节点）

Step 2：分析增长原因（扩容前必须先问）
  ├── 是否有大量历史数据未清理？→ 建议先清理冷数据 / 配置 ILM 策略
  ├── 是否有索引副本数过多？→ 副本会占用成倍磁盘
  └── 确认是业务数据持续增长 → 执行扩容
```

### CPU 使用率偏高

```
Step 1：判断偶发还是持续（看 P50 / P95，不看瞬时值）
        判定条件见 capacity-forecast-rules.md §5.2

Step 2（偶发打高）：⚠️ 不推荐扩容
  转由 tencent-es-diagnose skill 排查尖刺原因，常见方向：
  ├── 大查询 / 深度聚合
  ├── 大批量写入
  ├── Merge 操作集中触发
  └── Snapshot 备份集中执行

Step 3（持续高）：推荐扩容
  ├── 优先：纵向扩容（升配规格，增加 CPU 核数）
  │         ⛔ 暂无 MCP tool → 按下方规格表给推荐目标规格 + 控制台引导
  └── 若已是最高 CPU 规格：横向扩容（UpdateInstanceNodeNum）
```

> ⚠️ **偶发打高不推荐扩容**。扩容无法解决查询 / 写入模式问题，应先优化业务。

### JVM 内存使用率偏高

```
Step 1：先排查内存占用原因（转 tencent-es-diagnose skill）
  ├── 是否有大量 fielddata 缓存？→ 检查 text 字段是否开启了 fielddata
  ├── 是否有大量聚合查询？→ 聚合占用大量堆内存，考虑改用 keyword 字段
  ├── 是否有大量 segment？→ force merge 减少 segment 数量
  ├── 是否有内存泄漏迹象？→ 查看 GC 日志，分析 Old Gen 增长趋势
  └── 确认是业务规模增长导致 → 进入 Step 2

Step 2：推荐纵向扩容（升配规格，增加内存）
  ⛔ 暂无 MCP tool → 按下方规格表给推荐目标规格 + 控制台引导
  💡 ES 默认 JVM 堆 = 节点内存的 50%，升配后自动增大，无需手动配置
```

### 查询延迟偏高

```
Step 1：先排查查询本身（转 tencent-es-diagnose skill）
  ├── 是否有 wildcard / regexp 查询？→ 性能极差，建议改写
  ├── 是否有深度分页（from+size > 10000）？→ 改用 search_after
  ├── 是否有大量 script 查询？→ 尽量避免，改用 runtime fields
  ├── 是否有 text 字段做聚合？→ 改用 keyword 字段
  └── 查询是否命中大量文档？→ 添加过滤条件缩小范围

Step 2：排查资源瓶颈
  ├── CPU 是否同时高？→ 参考 CPU 处理方向
  ├── JVM 是否同时高？→ 参考 JVM 处理方向
  └── 磁盘 IO 是否高？→ 需升级磁盘类型（⛔ 切换磁盘类型本 Skill 不执行）

Step 3：确认是资源不足导致 → 推荐扩容
  ├── CPU 瓶颈 → 纵向扩容（升配规格，⛔ 暂无 tool）
  └── 并发查询量大 → 横向扩容（UpdateInstanceNodeNum，分散查询压力）
```

> ⚠️ 查询延迟**不作为单独的扩容触发依据**。必须先排除查询写法问题。

## 扩容量计算的业务含义

> ⚠️ 具体公式与取整规则由 `forecast_calc.py` 实现，口径定义在 [capacity-forecast-rules.md §5.1](capacity-forecast-rules.md)。本节只解释**为什么这样算**，供向用户说明推荐依据时引用。
> ⚠️ 计算结果是**目标值**，正好对应 MCP tool 的入参语义（`NodeNum` / `DiskSize` 均传目标值，不是增量）。

**为什么目标使用率取 60%（扩云盘）/ 50%（加节点）**：扩容后需保留增长余量，避免刚扩完又逼近阈值；加节点路径余量更大，因为节点数变化涉及 rebalance，不宜频繁操作。

**示例（云硬盘）——用于向用户展示推导过程：**

- 当前：3 节点 × 500GB = 1500GB，使用率 75%（已用 1125GB）
- 目标使用率 ≤ 60% → 目标单节点 = 500 × 0.75 / 0.6 = 625GB
- 向上取整到 100GB 整数倍 → **700GB**
- 调用：`UpdateInstanceDiskSize(Type="hotData", DiskSize=700)`
- 扩容后总容量 = 3 × 700 = 2100GB，预计使用率 ≈ 1125 / 2100 = 53.6% ✅

> 📌 若用户以「总容量」表述需求（如「扩到 2100G」），需换算 `2100 / NodeNum(3) = 700`，**换算过程必须展示给用户核对**。

### 扩容节点数建议

| 当前节点数 | 建议每次扩容 | 说明 |
|----------|------------|------|
| 3-5 | +2 | 保持奇数节点，避免脑裂 |
| 6-10 | +2~3 | 按需扩容 |
| 10+ | +3~5 | 大集群可批量扩容 |

> ⚠️ 建议值仍需换算为**目标总数**后传给 `UpdateInstanceNodeNum`，并校验落在允许区间（见 [mcp-tools-reference §3](mcp-tools-reference.md#3-updateinstancenodenum节点数量扩容-)）。

## 最佳实践

1. **先分析原因，再推荐扩容**：每次推荐扩容前必须给出数据支撑；根因分析交由 `tencent-es-diagnose`
2. **优先无搬迁操作**：扩云硬盘容量 > 升配规格 > 横向扩容（增加节点）
3. **保留 30% 余量**：扩容目标是使资源使用率降到 50~60%，而非刚好达标
4. **提前 30 天规划**：磁盘预计 30 天内达危险线立即规划；CPU / JVM 预计 14 天内达危险阈值规划升配
5. **维护时间窗口**：涉及重启的操作建议在业务低峰期（凌晨 02:00-06:00）执行
6. **变更前确认备份**：高风险变更前用 `DescribeClusterSnapshot` 确认存在近期成功快照
7. **一次只做一项变更**：多维度告警时按优先级串行，等前一项完成再做下一项
