# 评分等级与扣分规则

> **本文档是健康打分的唯一权威来源。** Agent 执行健康检查/批量巡检时**必须严格照此表逐条执行**，禁止凭感觉估分。
>
> 历史版本中这些规则由 `scripts/health_check.py` 实现；v3.0.0 改为 MCP 驱动后，脚本已删除，规则完整固化于本文档。

---

## 评分等级与触发动作

| 等级 | 分数范围 | 状态 | 触发动作 |
|------|---------|------|----------|
| A | 90–100 | 🟢 健康 | 无需操作 |
| B | 85–89 | 🔵 良好 | 关注趋势 |
| C | 70–84 | 🟡 警告 | 需要尽快处理 |
| D | < 70 | 🔴 危险 | 立即介入 |

> **深度诊断阈值 = 85 分。** `score < 85`（即 C/D 级）标记 ⚡ 并触发深度诊断；B 级（85–89）只需关注趋势，不触发。
> 单独磁盘 > 80% 即得 85 分（100 - 15），属 B 级边界，不触发深度诊断。

**统计口径必须与上表四档一一对应**，不得三档合并：

| 桶 | 分数 | 等级 |
|---|---|---|
| 🟢 健康 | ≥ 90 | A |
| 🔵 良好 | 85–89 | B |
| 🟡 警告 | 70–84 | C |
| 🔴 危险 | < 70 | D |
| ❓ 跳过 | — | `Status != 1`，不打分 |

> ⚠️ **⚡ 标记与颜色分档是同源的**：⚡ = `score < 85` = 🟡 + 🔴 两桶之和。不存在"⚡ 按 85、颜色按 70"的双标准。

## 打分执行顺序（必须按此顺序）

1. **初始化** `score = 100`，准备空的 `issues[]` 和 `suggestions[]`
2. **清洗所有监控指标**（见下方「哨兵值清洗算法」）—— 这一步在任何判断之前完成
3. **解析集群健康色**（见下方「集群健康色判定」）—— 三路信号取最严重
4. **执行第一层：一票否决项** —— 用 `score = min(score, 上限)` 压分，**逐条全部检查**，不要命中一条就停
5. **执行第二层：扣分项** —— 在一票否决结果上继续 `score -= N` 累减
6. **收尾**：`score = max(0, score)`，然后按等级表定级
7. **建议去重**：`suggestions` 保持原顺序去重

> ⚠️ 一票否决与扣分项**叠加生效**。例如集群 RED（≤30）且写入拒绝（-25），最终为 `min(100,30) - 25 = 5` 分。

---

## 哨兵值清洗算法（最关键，必须先做）

腾讯云云监控在探针失联时返回 **`-2`**（偶见 `-1`），而非`null`。对**每个**指标的时序数组执行：

```
raw          = [v for v in Values if v is not None]      # 去掉 null
values       = [v for v in raw if v not in (-2, -1)]     # 剔除哨兵值
sentinel_cnt = len(raw) - len(values)
total_points = len(raw)

若 values 为空:
    →该指标标记 data_missing = True
    → max / min / avg 全部为 None（不要填 0！）
    → 展示为 ❓ "无有效数据（{sentinel_cnt}/{total_points} 为哨兵值 -2，探针失联）"
否则:
    max = round(max(values), 2)
    min = round(min(values), 2)
    avg = round(sum(values)/len(values), 2)
    std = round(标准差(values), 2)
    anomaly_threshold = round(avg + 2*std, 2)
    anomaly_count     = len([v for v in values if v > anomaly_threshold])
    data_missing = False
```

**取指标代表值的规则**：优先取 `max`，`max` 为 None 时取 `avg`。

**判定「指标无有效数据」的完整条件**（任一成立）：
- 调用失败
- `data_missing == True`（全是哨兵值）
- `count == 0` 且 `max`、`avg` 均为 None

**为什么这是最重要的一步：**
- ❌ 把 `-2` 当真实磁盘使用率展示为 "2%"
- ❌ 把 `-2 < 95` 当磁盘健康，跳过一票否决
- ❌ 把 `-2 < 阈值` 当 CPU/JVM 正常，错失告警

**典型失联场景：** 磁盘打满 → ES 进程僵死 → 探针无法采集；节点宕机 / 网络分区；监控 Agent崩溃。

## 集群健康色判定（三路信号取最严重）

MCP 版本比历史版本多了一路数据面信号，可靠性更高：

| 信号源 | 来源 | 特点 |
|--------|------|------|
| `DescribeInstances.HealthStatus` | 管控面快照 | 可能延迟，极端情况返回 `-1`（Unknown）**不可单独采信** |
| 监控指标 `Status` | 时序采样（5min周期）| 近实时，持续上报 0/1/2；可能被哨兵值污染 |
| `CesClusterHealth`（`_cluster/health`）| **ES 数据面直连** | **最权威**，返回 `status: green/yellow/red`，无哨兵值问题 |

**判定规则：**

1. 收集所有可用信号，映射为 level：`green/0 → 0`，`yellow/1 → 1`，`red/2 → 2`
   - 管控面：仅当 `HealthStatus∈ (0,1,2)` 时采信，`-1` 丢弃
   - 监控指标：取清洗后的代表值；为浮点数时**向上取整**到最严重档位，并夹到 `[0,2]`
   - 数据面：`CesClusterHealth.status` 字符串直接映射
2. **取最严重**（level 最大）作为最终判定
3. 只有一路有数据 → 以该路为准
4. **三路都无数据** → 标记 `unknown = True`，触发 `score = min(score, 60)`
5. 各路结果不一致时，在报告中标注「多路信号不一致（API=x, Metric=y, DataPlane=z），取最严重」

> ⚠️ 历史 bug：仅依赖 `HealthStatus` 会导致 Red 集群被漏判为 100 分。任意一路检出 Red 均必须触发 ≤30 分一票否决。

## 第一层：一票否决项（`score = min(score, 上限)`）

**逐条全部检查，不要短路。**

| # | 条件 | 上限 | 生效前提 |
|---|------|------|---------|
| 1a | 集群健康色 = **RED** | ≤ 30 | 三路任一检出 Red |
| 1a' | 集群健康色 **Unknown**（三路都无数据）| ≤ 60 | — |
| 1b | `DiskUsageMax >= 95%` | ≤ 40 | **仅当磁盘指标有有效数据**（`data_missing=False`）|
| 1c | `NodeOldGcDifMax >= 1`（近 1h 发生 Old GC）| ≤ 40 | **仅当该指标有有效数据** |
| 1d | `DescribeInstances.Status != 1`（非正常运行）| ≤ 40 | — |
| 1e | **CORE 关键指标 ≥ 2 个无有效数据** | ≤ 30 | 检查集合：`DiskUsageMax`、`CpuUsageMax`、`JvmMemUsageMax` |
| 1f | 磁盘水位/只读阻塞 ERROR 日志 **≥ 5 条** | ≤ 30 | 关键字见下|

**1e 的意义**：磁盘打满/节点宕机时所有资源指标都变成 `-2`，若不识别此模式会得出「集群健康」的致命错误结论。这是最重要的守卫规则。

**1f 磁盘阻塞关键字**（在 `LogType=1` 主日志的 ERROR 中检索，单token 匹配，不要带空格）：
`read_only_allow_delete`、`FORBIDDEN`、`DiskThresholdMonitor`、`flood_stage`

> ✅ **检索方式**：用 `SearchKey` 下推到接口逐个关键字查，取返回 `TotalCount` 判断是否 ≥ 5 条：
> `DescribeInstanceLogs(LogType=1, LogLevels=["ERROR"], SearchKey="message:read_only_allow_delete", StartTime=..., EndTime=...)`
> 四个关键字命中数之和 ≥ 5 即命中 1f。**不要**拉全量日志再做本地子串匹配（`Limit` 上限 100，会漏计）。

> 📌 **MCP 版本的增强兜底**：当 1e 命中（监控指标集体失联）时，**必须**补充调用 `CesGetAllocation` 和 `CesClusterHealth` 核实集群真实状态——数据面直连不受探针失联影响，比日志关键字更可靠。若`CesGetAllocation` 显示某节点 `disk.percent >= 95`，等价于 1b 命中。

**对应建议话术：**
- RED → 立即检查 ERROR 日志与 `CesClusterAllocationExplain`，查找分片未分配原因（磁盘满/节点宕机）
- 磁盘 ≥95% → ①立即扩容至≤70% ②扩容后解除只读 `PUT /_all/_settings {"index.blocks.read_only_allow_delete": null}` ③仅紧急且确认有旧数据可删时才清理索引（不建议缩副本为 0）
- Old GC → 立即查 GC 日志（`LogType=4`），检查 JVM Old 区占用，排查大对象或内存泄漏，考虑紧急扩容
- 指标集体失联 → 立即用 `CesClusterHealth` / `CesGetAllocation` 核实真实状态

## 第二层：扣分项（在一票否决结果上累减）

### 2a. 集群健康色

| 条件 | 扣分 |
|------|------|
| YELLOW | -20 |

### 2b. JVM（连续超阈值判断）

| 条件 | 扣分 |
|------|------|
| 连续 15min > 90% | -25 |
| 连续 15min > 80%（未达上一档）| -15 |
| 偶尔超 80%（未连续，已回落）| -3 |

### 2c. CPU（连续超阈值判断）

| 条件 | 扣分 |
|------|------|
| 连续 15min > 90% | -25 |
| 连续 15min > 60%（未达上一档）| -10 |

> CPU 与 JVM **独立计算、叠加扣分**。两者同时高压时合计扣分更多，反映集群严重过载。

#### 「连续超阈值」判断算法

监控采样周期 `Period=300`（5 分钟），**取时序数组最后 3 个点** = 最近 15 分钟：

```
recent = raw_values[-3:]
若 len(raw_values) < 3:
    → 退化为用 max 值判断：max >= threshold
否则:
    → 全部满足才算连续：all(v >= threshold for v in recent if v is not None)
```

> 📌 打分时**必须保留原始时序数组**（`raw_values`），否则无法做连续性判断，只能退化为 max 判断（更容易误报瞬时毛刺）。

### 2d. 磁盘（≥95% 已被1b 否决，此处处理 <95% 区间）

| 条件 | 扣分 | 处置建议（优先级从高到低）|
|------|------|------|
| ≥ 90% | -30 | **①立即扩容至 ≤70%**（ES 已停止分配副本分片，即将触发只读）→ ②清理旧索引仅作过渡，不建议缩副本 |
| ≥ 80% | -15 | **①提前规划扩容（目标 ≤70%）** → ②如有明确旧索引可先行清理 |
| ≥ 75% | -5 | 预警，关注增长趋势 |

> ⚠️ **为什么扩容优于清理？**
> 1. **安全性**：扩容不动业务数据，零风险；清理/缩副本可能导致数据丢失或可用性下降
> 2. **可持续性**：磁盘增长是趋势问题，清理只是一次性缓解，扩容才是根治
> 3. **业务无感**：腾讯云 ES 磁盘扩容在线进行，业务无中断
> 4. **留有余量**：扩容目标 ≤70%，预留 30% 缓冲，避免短期二次告警

### 2e / 2f. 写入 / 查询拒绝率

| 条件 | 扣分 | 说明 |
|------|------|------|
| `BulkRejectedCompletedPercent > 0` | -25 | 有写入被拒，业务数据可能丢失 |
| `SearchRejectedCompletedPercent > 0` | -25 | 有查询被拒，用户请求直接失败 |

> 两者**独立计算、叠加扣分**，同时触发扣 50 分，直接进入危险区。

### 2g. 分片使用率（`ShardNumLimitPercen`）

| 条件 | 扣分 |
|------|------|
| ≥ 90% | -15 |
| ≥ 80% | -5 |

### 2h. Master 任务积压（`ClusterNumberOfPendingTasks`）

| 条件 | 扣分 | 说明 |
|------|------|------|
| 0 ~ 100 | 0 | 正常范围 |
| > 100 | -10 | 开始积压，需关注 |
| > 500 | -20 | Master 明显过载 |
| > 1000 | -30 | 严重积压，集群不稳定 |

### 2i. 集群只读

| 条件 | 扣分 |
|------|------|
| `IsReadOnly >= 1` | -20 |

### 2j. 其余 EXTENDED 指标（通用规则）

对下表指标，`代表值 >= critical` 扣 **10** 分，`代表值 > warn` 扣 **5** 分（`ShardNumLimitPercen`、`ClusterNumberOfPendingTasks`、`IsReadOnly`、`SearchRejectedCompletedPercent` 已单独处理，此处跳过）：

| 指标 | warn | critical | 单位 | 命中 critical 时的建议 |
|------|------|----------|------|---------------------|
| `SearchQueueMax` | 10 | 50 | 个 | 查询线程池积压，排查大查询/高并发 |
| `WriteQueueMax` | 10 | 50 | 个 | 写入线程池积压，降低写入并发 |
| `WriteRejectedDifMax` | 0 | 10 | 次 | 写入拒绝，增大 batch 或升配|
| `NodeDiskUtilMax` | 80 | 95 | % | 磁盘 IO 打满：排查高 IO 索引，限速写入或升级磁盘类型 |
| `NodeDiskAwaitMax` | 20 | 100 | ms | IO 等待过高：磁盘性能瓶颈，检查大量 merge/flush |
| `JvmOldMemUsageMax` | 80 | 90 | % | Old 区极高，Full GC 风险大，紧急扩容或减少写入 |
| `NodeParentBreakerDifMax` | 0 | 5 | 次 |熔断频繁：减少大聚合，检查 FieldData 占用 |

### 2k. ERROR 日志（分析时段内）

| 条件 | 扣分 |
|------|------|
| > 1000 条 | -15 |
| 100 ~ 1000 条 | -7 |
| 1 ~ 100 条 | -3 |

> 🔴 **条数取值口径**：必须用 `DescribeInstanceLogs(LogType=1, LogLevels=["ERROR"], StartTime=..., EndTime=...)` 的返回 **`TotalCount`** 作为条数。
> `TotalCount` 是匹配总数，不受 `Limit`（最大 100）影响。**禁止**用返回数组的长度计数 —— 那样最多只能数到 100，「> 1000 条」这一档将永远无法命中，直接导致少扣 15 分。

### 2l. 失败变更操作

| 条件 | 扣分 |
|------|------|
| 存在 `Progress == 0` 的操作 | -10 |

## 典型场景示例

| 场景 | 扣分明细 | 最终得分 | 等级 |
|------|---------|---------|------|
| 磁盘 82% | -15 | 85 | 🔵 良好（B 级下边界，不触发深度诊断）|
| JVM 连续15min > 80% + CPU 连续 15min > 60% | -15 + -10 | 75 | 🟡 警告 |
| 写入拒绝 + 查询拒绝 | -25 + -25 | 50 | 🔴 危险 |
| 集群 RED | 强制 ≤ 30 | ≤ 30 | 🔴 危险 |
| 集群 RED + 写入拒绝 | min(100,30) - 25 | 5 | 🔴 危险 |
| 近 1h Old GC | 强制 ≤ 40 | ≤ 40 | 🔴 危险 |
| 磁盘/CPU/JVM 全部返回 -2 | 强制 ≤ 30 | ≤ 30 | 🔴 危险（探针失联，需核实）|

## 报告展示规范

**指标状态图标：**

| 情况 | 图标 |
|------|------|
| 无有效数据 / `data_missing` | ❓（**必须**，不可显示为 ✅）|
| 代表值 ≥ critical | 🔴 |
| 代表值 ≥ warn | ⚠️ |
| 其他 | ✅ |

**评分条**：`"█" * (score // 5) + "░" * (20 - score // 5)`，格式 `[████...░░░] 85/100 B（良好）`

**巡检Dashboard**：按分数**升序**排列（最差排最前），`score < 85` 的行标记 `⚡`；统计口径严格按上文「评分等级与触发动作」的四档表（🟢≥90 / 🔵85-89 / 🟡70-84 / 🔴<70 / ❓跳过），**每行同时显示分数与等级字母**（如 `86/100 B🔵`）。

## 定时巡检推荐配置

按「批量巡检工作流」（见 [SKILL.md](../SKILL.md#批量巡检工作流多集群)）每小时执行一次，阈值建议 85 分：

1. `DescribeInstances` 拉取目标地域全量集群（`Limit=100` + 分页）
2. 跳过 `Status != 1` 的集群
3. `GetMonitorData` **按指标维度批量取数**（`InstanceIds` 传全部集群 ID，8 次调用覆盖全量）
4. 逐集群按本文档规则打分
5. 对分数 < 85 的集群，执行单集群健康检查流程并调用数据面 tool 定位根因
