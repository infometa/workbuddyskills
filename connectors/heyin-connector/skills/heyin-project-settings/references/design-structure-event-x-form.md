# 事件 × 表单结构矩阵使用说明

事件 × 表单结构矩阵用于决定 eCRF 方案中的各事件包含哪些表单。

## 功能总览

| 功能 | 说明 | 可修改 |
| --- | --- | --- |
| 查询事件—表单矩阵 | 获取当前设计候选或指定方案版本的事件、表单与关联矩阵 | 否 |
| 编辑事件—表单结构 | 新增或取消一个事件—表单关联 | 是 |

本页只覆盖事件与表单的结构关系。事件和表单对象自身的属性及增删改排序分别见[事件 / 访视使用说明](design-event.md)和[表单设计使用说明](design-form.md)。

## 查询事件 × 表单结构（只读）

### 接口一览

| 用途 | 方法 | 路径 | 请求参数 |
| --- | --- | --- | --- |
| 获取当前事件—表单矩阵 | `GET` | `/api/project/settings/design/structure/get_event_form_dsn_grid/` | 无 |
| 获取已发布事件—表单矩阵 | `GET` | `/api/project/settings/design/structure/get_event_form_def_grid/` | `--query`：`meta_data_version_id` = 先从当前项目方案版本列表唯一定位的方案版本 ID（必填） |

### 只读接口返回内容

| 接口 | 业务返回内容 | 定义 |
| --- | --- | --- |
| 获取当前事件—表单矩阵 | `data: EventFormDsnGrid` | 当前项目的设计态事件、表单和关联矩阵，是关联写操作定位设计 ID、判断现有关系和写后回读的唯一依据。 |
| 获取已发布事件—表单矩阵 | `data: EventFormDefGrid` | 指定方案版本的正式事件、表单和关联矩阵，只用于查看或比对。 |

### 事件—表单矩阵结构

`EventFormDsnGrid` 与 `EventFormDefGrid` 的属性如下：

| 属性 | 类型 | 定义 |
| --- | --- | --- |
| `event_dsn_list` | `EventDsn[]` | 当前项目按 `ranking` 升序排列的设计态事件候选。写操作只能使用其中仍有效且唯一定位的 `id`。 |
| `form_dsn_list` | `FormDsn[]` | 当前项目按 `ranking` 升序排列的设计态表单候选。写操作只能使用其中仍有效且唯一定位的 `id`。 |
| `event_form_relations` | `Record<event_dsn_id, EventFormDsn[]>` | 设计态关联矩阵；键是事件设计 ID，值是该事件的表单关联项数组。键缺失或数组为空表示返回结果中没有该事件的表单关联。 |
| `event_def_list` | `EventDef[]` | 指定方案版本按 `ranking` 升序排列的正式事件定义，只读。 |
| `form_def_list` | `FormDef[]` | 指定方案版本按 `ranking` 升序排列的正式表单定义，只读。 |
| `event_form_relations` | `Record<event_def_id, EventFormDef[]>` | 正式关联矩阵；键是事件定义 ID，值是该事件的表单关联项数组。 |

`EventFormDsn` 与 `EventFormDef` 关联项的属性如下：

| 属性 | 类型 | 对象 | 定义 |
| --- | --- | --- | --- |
| `form_dsn_id` | integer | `EventFormDsn` | 当前设计中与事件关联的表单设计 ID。 |
| `form_def_id` | integer | `EventFormDef` | 指定正式版本中与事件关联的表单定义 ID。 |
| `is_rtsm_related` | boolean | 两者 | 该事件—表单关系是否被 RTSM 使用，是平台返回的只读事实；为 `true` 时不能取消关系。 |

设计态表单候选还会返回表单属性、失效状态和关联状态。只使用平台实际返回的矩阵和 ID；空列表、缺失的关系键或部分响应不得被补造为默认候选或默认关联。

### 定义态与设计态边界

- `*_def` 接口读取指定 `meta_data_version_id` 的正式版本快照，只能用于查看或比对。
- `*_dsn` 接口读取当前项目的设计候选，是结构写操作定位 `event_dsn_id` 和 `form_dsn_id` 的唯一来源。
- 正式定义 ID 与设计候选 ID 属于不同对象空间。即使名称或 `vid` 相同，也不能把 `event_def_id` 或 `form_def_id` 传给任何 `*_dsn` 写接口。
- 需要对比正式版本与当前设计时，应分别保留两次读取的对象及 ID，不得按数组位置或排序把两类 ID 相互替换。

## 编辑事件 × 表单结构（写）

### 接口一览

| 用途 | 方法 | 路径 | 请求参数 |
| --- | --- | --- | --- |
| 新增事件—表单关联 | `POST` | `/api/project/settings/design/structure/create_event_form_dsn_grid_relation/` | `--body`：`event_dsn_id`、`form_dsn_id` = 从同一次当前事件—表单矩阵唯一定位的设计 ID（必填） |
| 取消事件—表单关联 | `POST` | `/api/project/settings/design/structure/delete_event_form_dsn_grid_relation/` | `--body`：`event_dsn_id`、`form_dsn_id` = 从同一次当前事件—表单矩阵唯一定位、且当前确有关系的设计 ID（必填） |

### 写接口返回内容

两个写接口均输出 `null`。响应成功只表示平台接受并处理了本次请求，不足以证明目标关系已经生效；必须回读当前事件—表单 Grid，以实际返回结果确认。

这些写接口没有 dry-run，也不返回预计影响人数或数据量。执行前必须使用最新完整矩阵展示拟变更关系及完整参数，并确认已有授权覆盖同一目标与实际影响，否则补充确认；用户只要求查看、比较或评估时，返回只读结果后停止，不执行 POST。

### 通用写入流程

1. 读取当前设计的完整 `EventFormDsnGrid`。
2. 从同一次当前项目读取中唯一定位目标事件和表单，核对 `id`、`vid`、名称、失效状态、RTSM 状态和当前关系。新增关系必须确认尚不存在，取消关系必须确认当前存在。
3. 向用户展示完整目标矩阵、拟变更关系、完整请求参数和可识别的联动影响，核对已有授权是否覆盖同一目标与实际影响；未覆盖时补充确认。任何 ID 或操作方向变化后重新核对授权范围。
4. 批准后只调用一次目标 POST。拒绝、超时或失败后立即停止，不得通过改 ID、反转操作方向或省略字段自动重试。
5. 重新读取当前设计的完整 Grid。只有回读结果与目标一致时才能确认变更生效；回读失败或结果不一致时，只报告写请求结果和“变更未确认生效”。

### 事件—表单关联约束

- `event_dsn_id` 与 `form_dsn_id` 必须是正整数，来自同一次当前项目事件—表单 Grid，并且对应事件与表单属于同一项目。请求不携带 `project_id`，不能使用正式定义 ID、其他项目 ID 或猜测值。
- 新增已存在的关系会被平台拒绝，取消不存在的关系也会被拒绝。初始事件 `STUDY_START` 最多关联一个表单；它已经有关联时，不能再新增第二个表单关系。
- `EventFormDsn.is_rtsm_related=true` 的关系不能取消，也不能忽略或覆盖该平台状态。
- 取消事件—表单关系可能使引用该事件与表单组合的逻辑核查参数、逻辑核查和自动计算失效，并触发随访通知规则有效性重算。批准前必须向用户说明这些设计联动；平台没有提供本操作的影响演练或影响计数。
- 取消关系后若初始事件原先因关联多个表单而失效，平台会按剩余关系重新计算该失效状态。最终状态必须以写后 Grid 和相关对象回读为准。

### 结果核验

新增或取消关系时，必须保留写前读取，写后再次 GET，并用 Markdown 明确区分“用户确认的拟变更”和“GET 验证后的实际结果”。所有值都必须来自写前或写后的 GET 响应，不能根据 POST 请求体补写结果。

关系变更必须使用完整矩阵，不能只展示发生变化的关系条目。矩阵行列必须覆盖写前 GET 返回的全部未删除事件和表单，并按接口返回的 `ranking` 排序；如果关联操作依赖刚刚创建的事件或表单，应在对象创建通过 GET 验证后重新读取 Grid，并以该次读取的完整候选生成确认矩阵。

写入前确认矩阵的单元格标记规则如下：

- `✓`：当前和目标矩阵中均存在的关系。
- `✓（新增）`：当前不存在、目标矩阵中拟新增的关系。
- `~~✓~~（删除）`：当前存在、目标矩阵中拟取消的关系。
- `✓（RTSM）`：关系受 RTSM 保护且保持不变；不得标记为拟删除。
- 空白：当前和目标矩阵中均不存在的关系。

事件—表单关系以事件为列、表单为行展示完整矩阵。写入前确认示例：

| 表单 \\ 事件 | 筛选期 | 基线期 | V1 | V2 | 计划外访视 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 知情同意书签署 | ✓ |  |  |  |  |
| 人口学资料 |  | ✓ |  |  |  |
| 生命体征 |  | ~~✓~~（删除） | ✓（RTSM） | ✓ | ✓（新增） |
| 血常规 |  | ✓（新增） | ✓ | ✓ | ✓（新增） |

确认矩阵中的拟删除关系必须同时展示已知依赖影响。`is_rtsm_related=true` 的关系必须显示为 `✓（RTSM）` 并保持不变，不能生成删除请求。

写入完成后，重新 GET 完整事件和表单候选及对应关系 Grid，生成服务端实际完整矩阵。实际矩阵不再使用 `✓（新增）` 或 `~~✓~~（删除）`：已存在的普通关系统一显示 `✓`，RTSM 保护关系显示 `✓（RTSM）`，不存在的关系留空。把实际矩阵与写前快照及用户确认的目标矩阵逐项比较，确认新增关系、取消关系、保留关系、行列对象和 RTSM 状态全部符合预期。

如果目标矩阵与当前矩阵完全一致，不调用写接口，也不把当前关系报告为新变更。写后 GET 失败、候选不完整、目标关系状态与预期不一致、保留关系意外变化，或者 RTSM 状态不一致时，应报告“变更未确认生效”，不得仅依据写接口返回成功得出结论。
