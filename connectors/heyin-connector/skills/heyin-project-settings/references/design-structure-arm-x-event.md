# 分组 × 事件结构矩阵使用说明

分组 × 事件结构矩阵用于决定各方案分组适用哪些事件。当前设计还通过分组事件差异模式表示各分组是否可以采用不同事件配置。

## 功能总览

| 功能 | 说明 | 可修改 |
| --- | --- | --- |
| 查询分组事件差异模式 | 获取当前设计候选或指定方案版本是否按分组配置不同事件 | 否 |
| 查询分组—事件矩阵 | 获取当前设计候选或指定方案版本的分组、事件与关联矩阵 | 否 |
| 编辑分组—事件结构 | 切换当前设计的分组事件差异模式，新增或取消一个分组—事件关联 | 是 |

本页只覆盖分组与事件的结构关系。分组和事件对象自身的属性及增删改排序分别见[分组设计使用说明](design-arm.md)和[事件 / 访视使用说明](design-event.md)。

## 查询分组 × 事件结构（只读）

### 接口一览

| 用途 | 方法 | 路径 | 请求参数 |
| --- | --- | --- | --- |
| 获取当前分组事件差异模式 | `GET` | `/api/project/settings/design/structure/get_arm_dsn_with_different_event/` | 无 |
| 获取已发布分组事件差异模式 | `GET` | `/api/project/settings/design/structure/get_arm_def_with_different_event/` | `--query`：`meta_data_version_id` = 先从当前项目方案版本列表唯一定位的方案版本 ID（必填） |
| 获取当前分组—事件矩阵 | `GET` | `/api/project/settings/design/structure/get_arm_event_dsn_grid/` | 无 |
| 获取已发布分组—事件矩阵 | `GET` | `/api/project/settings/design/structure/get_arm_event_def_grid/` | `--query`：`meta_data_version_id` = 先从当前项目方案版本列表唯一定位的方案版本 ID（必填） |

当前分组事件差异模式 GET 要求 `PRJ_SETTINGS_DESIGN_ACCESS` 且项目方案处于 `DESIGNING`；当前分组—事件 Grid GET 不要求该设计阶段，持有任一项目级设置权限即可读取。在 `DRAFT` 或 `PUBLISHED` 阶段查看版本模式时，应使用已唯一定位 MDV 的定义态模式接口；不得为了只读查询自动把项目切换为设计中。

### 只读接口返回内容

| 接口 | 业务返回内容 | 定义 |
| --- | --- | --- |
| 获取当前分组事件差异模式 | `is_arm_with_different_event: boolean` | 当前设计候选是否按分组配置不同事件，是解释和修改当前分组—事件矩阵的模式依据。 |
| 获取已发布分组事件差异模式 | `is_arm_with_different_event: boolean` | 指定方案版本的正式模式快照，只读，不代表当前设计候选的设置。 |
| 获取当前分组—事件矩阵 | `data: ArmEventDsnGrid` | 当前项目的设计态分组、事件和关联矩阵，是关联写操作定位设计 ID、判断现有关系和写后回读的唯一依据。 |
| 获取已发布分组—事件矩阵 | `data: ArmEventDefGrid` | 指定方案版本的正式分组、事件和关联矩阵，只用于查看或比对。 |

### 分组事件差异模式

`is_arm_with_different_event` 表示方案是否按分组配置不同事件：

| 值 | 含义 |
| --- | --- |
| `false` | 各分组采用相同的事件配置。 |
| `true` | 各分组可以采用不同的事件配置，具体关系以分组—事件矩阵为准。 |

模式值和关联矩阵是两个独立的返回内容。设置模式的接口只更新 `is_arm_with_different_event`，不会自动新增、取消或重排任何分组—事件关联；切换后必须同时回读模式与完整矩阵，不能根据目标模式推测关联结果。

### 分组—事件矩阵结构

`ArmEventDsnGrid` 与 `ArmEventDefGrid` 的属性如下：

| 属性 | 类型 | 定义 |
| --- | --- | --- |
| `arm_dsn_list` | `ArmDsnName[]` | 当前项目按 `ranking` 升序排列的设计态分组候选。写操作只能使用其中仍有效且唯一定位的 `id`。 |
| `event_dsn_list` | `EventDsn[]` | 当前项目按 `ranking` 升序排列的设计态事件候选。写操作只能使用其中仍有效且唯一定位的 `id`。 |
| `event_arm_relations` | `Record<event_dsn_id, arm_dsn_id[]>` | 设计态关联矩阵；键是事件设计 ID，值是与该事件关联的分组设计 ID 数组。键缺失或数组为空表示返回结果中没有该事件的分组关联。 |
| `arm_def_list` | `ArmDefName[]` | 指定方案版本按 `ranking` 升序排列的正式分组定义，只读。 |
| `event_def_list` | `EventDef[]` | 指定方案版本按 `ranking` 升序排列的正式事件定义，只读。 |
| `event_arm_relations` | `Record<event_def_id, arm_def_id[]>` | 正式关联矩阵；键是事件定义 ID，值是与该事件关联的分组定义 ID 数组。 |

设计态候选中的 `id`、`vid`、`name`、`ranking` 和 `alteration` 用于定位和展示；`is_invalid`、`invalid_message` 与 `is_rtsm_related` 是平台计算的当前状态，不能由客户端覆盖。只使用平台实际返回的矩阵和 ID；空列表、缺失的关系键或部分响应不得被补造为默认候选或默认关联。

### 定义态与设计态边界

- `*_def` 接口读取指定 `meta_data_version_id` 的正式版本快照，只能用于查看或比对。
- `*_dsn` 接口读取当前项目的设计候选，是结构写操作定位 `arm_dsn_id` 和 `event_dsn_id` 的唯一来源。
- 正式定义 ID 与设计候选 ID 属于不同对象空间。即使名称或 `vid` 相同，也不能把 `arm_def_id` 或 `event_def_id` 传给任何 `*_dsn` 写接口。
- 需要对比正式版本与当前设计时，应分别保留两次读取的对象及 ID，不得按数组位置或排序把两类 ID 相互替换。

## 编辑分组 × 事件结构（写）

### 接口一览

| 用途 | 方法 | 路径 | 请求参数 |
| --- | --- | --- | --- |
| 设置当前分组事件差异模式 | `POST` | `/api/project/settings/design/structure/set_arm_dsn_with_different_event/` | `--body`：`is_arm_with_different_event` = 用户明确批准的目标模式（boolean，执行时必须显式提供） |
| 新增分组—事件关联 | `POST` | `/api/project/settings/design/structure/create_arm_event_dsn_grid_relation/` | `--body`：`arm_dsn_id`、`event_dsn_id` = 从同一次当前分组—事件矩阵唯一定位的设计 ID（必填） |
| 取消分组—事件关联 | `POST` | `/api/project/settings/design/structure/delete_arm_event_dsn_grid_relation/` | `--body`：`arm_dsn_id`、`event_dsn_id` = 从同一次当前分组—事件矩阵唯一定位、且当前确有关系的设计 ID（必填） |

### 写接口返回内容

三个写接口均输出 `null`。响应成功只表示平台接受并处理了本次请求，不足以证明目标模式或关系已经生效；必须回读当前设计模式和分组—事件 Grid，以实际返回结果确认。

这些写接口没有 dry-run，也不返回预计影响人数或数据量。执行前必须使用最新完整矩阵展示拟变更关系及完整参数，并确认已有授权覆盖同一目标与实际影响，否则补充确认；用户只要求查看、比较或评估时，返回只读结果后停止，不执行 POST。

### 通用写入流程

1. 读取当前设计的 `is_arm_with_different_event` 和完整 `ArmEventDsnGrid`。
2. 关联操作从同一次当前项目读取中唯一定位目标分组和事件，核对 `id`、`vid`、名称、失效状态、RTSM 状态和当前关系。新增关系必须确认尚不存在，取消关系必须确认当前存在。
3. 向用户展示当前模式、完整目标矩阵、拟变更关系、完整请求参数和可识别的联动影响，核对已有授权是否覆盖同一目标与实际影响；未覆盖时补充确认。任何 ID、目标值或操作方向变化后重新核对授权范围。
4. 批准后只调用一次目标 POST。拒绝、超时或失败后立即停止，不得通过改 ID、改布尔值、反转操作方向或省略字段自动重试。
5. 重新读取当前设计模式和完整 Grid。只有回读结果与目标一致时才能确认变更生效；回读失败或结果不一致时，只报告写请求结果和“变更未确认生效”。

### 分组事件差异模式约束

- `is_arm_with_different_event` 可省略，但执行时必须显式提供用户确认的 boolean，不能依赖默认值。
- 目标模式与当前值相同时，平台按无变化成功处理。没有实际变化时应直接说明当前已是目标模式，不重复执行写接口。
- 模式切换不会自动改写分组—事件关联。批准前展示当前完整矩阵，写后同时回读模式与矩阵，分别报告模式变化和关系是否变化。

### 分组—事件关联约束

- `arm_dsn_id` 与 `event_dsn_id` 必须是正整数，来自同一次当前项目分组—事件 Grid，并且对应分组与事件属于同一项目。请求不携带 `project_id`，不能因此省略当前项目边界校验。
- 新增已存在的关系会被平台拒绝，取消不存在的关系也会被拒绝。失败后应重新读取矩阵，不得把相同 POST 当作幂等请求重复发送。
- 取消 RTSM 相关的分组—事件关系会被平台拒绝。当前 Grid 不直接返回关系自身的 RTSM 标记，因此即使候选状态看似允许，仍须保留平台拒绝的可能并如实反馈。
- 新增、取消关系只处理指定的一对分组与事件；不能根据模式值推断平台会批量补齐或移除其他关系。

### 结果核验

切换模式或新增、取消关系时，必须保留写前读取，写后再次 GET，并用 Markdown 明确区分“用户确认的拟变更”和“GET 验证后的实际结果”。所有值都必须来自写前或写后的 GET 响应，不能根据 POST 请求体补写结果。

模式变更使用属性 diff：

| 属性 | 变更前 | 变更后 | 结果 |
| --- | --- | --- | --- |
| `is_arm_with_different_event` | `false` | `true` | 已生效 |

关系变更必须使用完整矩阵，不能只展示发生变化的关系条目。矩阵行列必须覆盖写前 GET 返回的全部未删除候选，并按接口返回的 `ranking` 排序。写入前确认矩阵的单元格标记规则如下：

- `✓`：当前和目标矩阵中均存在的关系。
- `✓（新增）`：当前不存在、目标矩阵中拟新增的关系。
- `~~✓~~（删除）`：当前存在、目标矩阵中拟取消的关系。
- 空白：当前和目标矩阵中均不存在的关系。

分组—事件关系以事件为列、分组为行展示完整矩阵。当前 Grid 不返回关系自身的 RTSM 标记，因此该矩阵不使用 `✓（RTSM）`；删除请求仍可能被平台按实际 RTSM 关系拒绝。写入前确认示例：

| 分组 \\ 事件 | 筛选期 | 基线期 | V1 | V2 | 计划外访视 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 对照组 | ✓ | ✓ | ✓ | ~~✓~~（删除） |  |
| 试验组 | ✓ | ✓ | ✓ | ✓ | ✓（新增） |

写入完成后，重新 GET 当前模式、完整分组和事件候选及对应关系 Grid，生成服务端实际完整矩阵。实际矩阵不再使用 `✓（新增）` 或 `~~✓~~（删除）`：已存在的关系统一显示 `✓`，不存在的关系留空。把实际矩阵与写前快照及用户确认的目标矩阵逐项比较，确认新增、取消、保留关系和行列对象全部符合预期。

如果目标矩阵与当前矩阵完全一致，不调用写接口，也不把当前关系报告为新变更。写后 GET 失败、候选不完整、目标关系状态与预期不一致或保留关系意外变化时，应报告“变更未确认生效”，不得仅依据写接口返回成功得出结论。
