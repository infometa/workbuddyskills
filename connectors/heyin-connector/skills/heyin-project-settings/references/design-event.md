# 事件 / 访视使用说明

事件是 eCRF 方案中的时间节点，用于组织研究开始、计划访视、计划外访视及通用事件，并通过日期类型、随访相对时间和访视窗定义研究参与者何时完成相关表单。

## 功能总览

| 功能 | 说明 | 可修改 |
| --- | --- | --- |
| 查询事件设计与定义 | 获取当前项目设计态事件，或指定方案版本的正式事件定义 | 否 |
| 编辑事件设计 | 创建（含演练）、变更、排序、删除（含演练）事件设计 | 是 |

## 查询事件设计与定义（只读）

### 接口一览

| 用途 | 方法 | 路径 | 请求参数 |
| --- | --- | --- | --- |
| 获取当前事件设计 | `GET` | `/api/project/settings/design/event/list_event_dsn/` | 无 |
| 获取已发布事件定义 | `GET` | `/api/project/settings/design/event/list_event_def/` | `--query`：`meta_data_version_id` = 先从当前项目方案版本列表唯一定位的方案版本 ID（必填） |

### 只读接口返回内容

两个只读接口成功时的业务返回内容都是包含必填 `list` 属性的对象：

| 接口 | `list` 类型 | 定义 |
| --- | --- | --- |
| 获取当前事件设计 | `EventDsn[]` | 当前项目的设计态事件列表，是后续设计写操作定位 `id` 和写后回读的唯一依据。 |
| 获取已发布事件定义 | `EventDef[]` | 指定方案版本的正式事件定义列表，只读；其中的定义 ID 不能作为设计态写操作的事件 ID。 |

`EventDsn` 与 `EventDef` 的属性定义如下。“是”表示对象必定包含该属性，“否”表示该属性可能不返回。

| 属性 | 类型 | `EventDsn` 必填 | `EventDef` 必填 | 定义 |
| --- | --- | --- | --- | --- |
| `id` | integer | 是 | 是 | 事件 ID，正整数。`EventDsn.id` 是当前项目的事件设计 ID；`EventDef.id` 是指定方案版本的正式事件定义 ID，二者不可混用于设计写操作。 |
| `name` | string | 是 | 是 | 事件名称；设计写入时长度为 1–16。 |
| `vid` | string | 是 | 是 | 事件变量名；设计写入时长度为 1–32，须匹配 `^[A-Z_][A-Z0-9_]*$`（大写字母或下划线开头，后续仅大写字母、数字或下划线；不接受小写，后端不自动转换），并在同一项目内大小写不敏感唯一。变更 `vid` 可能使引用该事件的自动计算、逻辑控制或逻辑核查失效。 |
| `ranking` | integer | 是 | 是 | 当前事件排序位置，正整数。创建时由服务端追加到末尾；排序目标超过当前最大位置时，服务端归一到最大可用位置。 |
| `type` | string | 是 | 是 | 事件类别：`STUDY_START`（初始事件）、`SCHEDULED`、`UNSCHEDULED` 或 `COMMON`；随访事件和基线事件必须为 `SCHEDULED`。 |
| `date_type` | string | 是 | 是 | 日期记录类型：`NO_NEED` 表示不记录日期，`DAY` 表示记录日期，`DAY_TIME` 表示记录日期和时间，`PERIOD` 表示记录日期区间。基线事件最终至少记录日期，服务端会将不合适的基线类型归一为 `DAY`。 |
| `is_baseline` | boolean | 是 | 是 | 是否为基线事件。一个项目最多一个基线事件；它必须为计划访视、不能重复、不能同时为随访事件，设置后会自动关联所有分组。 |
| `is_follow_up` | boolean | 是 | 是 | 是否为随访事件。随访事件必须为计划访视，且不能同时为基线事件。 |
| `is_repeating` | boolean | 是 | 是 | 是否允许重复发生。基线事件和初始事件 `STUDY_START` 不能重复；RTSM 或药物供应关联事件不能从不重复改为重复。 |
| `is_required` | boolean | 是 | 是 | 事件是否必填。 |
| `relative_target_value` | integer | 否 | 否 | 计划随访相对目标时间值，可为负数。随访事件的非负值参与随访/ePRO 执行，负值只保留设计记录且不参与执行；非随访事件或基线事件会归零。 |
| `relative_target_unit` | string | 否 | 否 | 计划随访相对时间单位：空字符串、`DAY`、`HOUR` 或 `MINUTE`。有数值但单位为空时按 `DAY` 处理；只有当前项目的基线事件为 `date_type=DAY_TIME` 时，事件才可使用 `HOUR` 或 `MINUTE`；非随访事件或基线事件会清空。 |
| `pre_window_value` | integer | 否 | 否 | 访视窗前偏移值，非负。非随访、非基线事件会归零；可执行的非负相对时间随访事件，其前窗口不能大于相对目标时间。 |
| `pre_window_unit` | string | 否 | 否 | 访视窗前偏移单位：空字符串、`DAY`、`HOUR` 或 `MINUTE`。有数值但单位为空时按 `DAY` 处理；只有当前项目的基线事件为 `date_type=DAY_TIME` 时，事件才可使用 `HOUR` 或 `MINUTE`。 |
| `post_window_value` | integer | 否 | 否 | 访视窗后偏移值，非负；基线事件和非随访事件会归零。 |
| `post_window_unit` | string | 否 | 否 | 访视窗后偏移单位：空字符串、`DAY`、`HOUR` 或 `MINUTE`。有数值但单位为空时按 `DAY` 处理；只有当前项目的基线事件为 `date_type=DAY_TIME` 时，事件才可使用 `HOUR` 或 `MINUTE`；基线事件和非随访事件会清空。 |
| `min_window_unit` | string | 否 | 否 | 服务端根据相对目标时间、前窗口和后窗口计算的最小时间单位，可为空字符串、`DAY`、`HOUR` 或 `MINUTE`；只读，客户端不能提交。 |
| `count_rated_total_field` | integer | 是 | 是 | 额定总字段数，服务端只读计算值，非负。 |
| `count_rated_total_form` | integer | 是 | 是 | 额定总表单数，服务端只读计算值，非负。 |
| `alteration` | string | 是 | 是 | 相对已发布方案的设计变更标记，只读。空字符串表示无变更，`ADDED` 表示新增，`EDITED` 表示变更，`MOVED` 表示移位，`DELETED` 表示删除。 |
| `is_invalid` | boolean | 是 | 不适用 | 事件设计是否失效，服务端只读计算值。 |
| `invalid_message` | string | 是 | 不适用 | 事件设计的失效原因文案；没有失效原因时为空字符串。 |
| `is_rtsm_related` | boolean | 是 | 不适用 | 事件是否被 RTSM 关联使用，服务端只读关联标记。 |
| `is_rtsm_drug_supply_related` | boolean | 是 | 不适用 | 事件是否为药物供应发药事件，服务端只读关联标记。 |
| `is_sd_related` | boolean | 是 | 不适用 | 事件是否被源文件分类关联使用，服务端只读关联标记。 |
| `count_total_sd_category` | integer | 不适用 | 是 | 正式事件定义关联的源文件分类数量。 |

只使用平台实际返回的事件 ID 与状态。空列表只表示本次读取没有对应事件；缺失、空列表或部分响应不得被补造为默认事件。

### 事件类别

`type` 表示事件类别：

| 类别 | 接口值 | 含义 |
| --- | --- | --- |
| 初始事件 | `STUDY_START` | 研究开始时的初始事件；同一项目最多一个未删除的初始事件，且不能重复。事件—表单关联限制见[事件 × 表单结构矩阵](design-structure-event-x-form.md) |
| 计划访视 | `SCHEDULED` | 按方案预先计划的访视；随访事件必须使用此类型 |
| 计划外访视 | `UNSCHEDULED` | 不按固定计划发生的访视 |
| 通用事件 | `COMMON` | 不属于上述特定类别的通用研究事件 |

事件还可以通过以下标记表达业务分类：

- **基线事件**：`is_baseline=true`，项目只能有一个；必须是计划访视，且不能允许重复；用于记录基线日期或日期时间。
- **随访事件**：`is_follow_up=true`，必须是计划访视；通过相对目标时间和前后访视窗参与随访计划执行。
- **必填事件**：`is_required=true`，表示该事件是否为必填事件。
- **重复事件**：`is_repeating=true`，表示事件是否允许重复发生；基线事件和初始事件不能设置为重复，RTSM 或药物供应关联事件也可能禁止从不重复改为重复。

`is_baseline=true` 与 `is_follow_up=true` 互斥；一个事件不能同时是基线事件和随访事件。

## 编辑事件设计（写）

### 接口一览

| 用途 | 方法 | 路径 | 请求参数 |
| --- | --- | --- | --- |
| 创建事件设计演练 | `POST` | `/api/project/settings/design/event/create_event_dsn_dry_run/` | 无（省略 `--body`） |
| 创建事件设计 | `POST` | `/api/project/settings/design/event/create_event_dsn/` | `--body`：`vid` = 手动指定并已确认的事件变量名，须满足格式、长度及项目内唯一性约束（必填；不要求来自创建演练）；<br>`name` = 已确认的事件名称（必填）；<br>`type` = 已确认的事件类型（必填）；<br>`date_type` = 已确认的日期记录方式（必填）；<br>`is_baseline`、`is_follow_up`、`is_repeating`、`is_required`、`relative_target_value`、`relative_target_unit`、`pre_window_value`、`pre_window_unit`、`post_window_value`、`post_window_unit` = 已确认的事件标记、相对时间和访视窗配置（可选，约束见上文事件设计字段定义） |
| 变更事件设计 | `POST` | `/api/project/settings/design/event/update_event_dsn/` | `--body`：`id` = 最新事件设计列表返回的事件设计 ID（必填）；<br>`name`、`vid`、`type`、`date_type`、`is_baseline`、`is_follow_up`、`is_repeating`、`is_required`、`relative_target_value`、`relative_target_unit`、`pre_window_value`、`pre_window_unit`、`post_window_value`、`post_window_unit` = 已确认且实际发生变化的字段（可选，约束见上文事件设计字段定义） |
| 排序事件设计 | `POST` | `/api/project/settings/design/event/rank_event_dsn/` | `--body`：`id` = 最新事件设计列表返回的事件设计 ID（必填）；`ranking` = 根据当前完整事件列表确认的目标顺序（必填，正整数） |
| 删除事件设计演练 | `POST` | `/api/project/settings/design/event/delete_event_dsn_dry_run/` | `--body`：`ids` = 从最新事件设计列表唯一定位、去重且非空的事件设计 ID 数组（必填） |
| 删除事件设计 | `POST` | `/api/project/settings/design/event/delete_event_dsn/` | `--body`：`ids` = 与最近一次删除演练完全相同的事件设计 ID 数组（必填，不得新增、删减或替换） |

### 写接口返回内容

各写接口成功时的业务返回内容如下：

| 接口 | 业务返回内容 |
| --- | --- |
| 创建事件设计演练 | 可选的 `vid`（string）：平台预生成的候选事件变量名，正式创建不依赖该值，可直接提交手动指定且已确认的 VID；演练成功不表示事件已创建。 |
| 创建事件设计 | 新创建的设计态事件；字段、类型和必填性见上文事件设计字段定义。响应成功后仍须按返回 `id` 回读确认。 |
| 变更事件设计 | 无 |
| 排序事件设计 | 无 |
| 删除事件设计演练 | 必填的 `will_affect_patient_count`（integer）：正式删除预计影响的研究参与者数量；必填的 `will_delete_event_data_count`（integer）：正式删除预计删除的事件数据数量。两个计数都只表示影响预览，不是已删除结果。 |
| 删除事件设计 | 无 |

变更、排序和删除接口响应成功后仍必须回读事件设计列表，不得仅凭写请求成功推断最终状态。

### 删除和联动限制

- 删除多个事件时，所有 ID 必须属于同一项目；不存在的事件、已删除事件不能作为目标。
- 删除前必须先调用删除演练接口，读取 `will_affect_patient_count` 和 `will_delete_event_data_count`。任一影响计数大于 0 时，向用户说明预计影响；仅当已有授权覆盖同一目标及这些实际影响时正式删除，否则先补充确认；两个影响计数都等于 0 时，无需展示零值影响，也不再提示用户确认，可按用户已明确的删除意图继续正式删除。用户只要求查询影响时，返回演练结果后停止，不执行正式删除。
- RTSM 关联事件、SD 关联事件和药物供应发药事件不能删除；修改 RTSM/药物供应关联事件的重复属性也可能被禁止。
- 已发布方案存在时，删除通常标记 DSN 为删除；尚未正式发布过方案时，删除可直接移除 DSN 记录。
- 删除事件会删除事件与表单的关联，并可能使逻辑核查、自动计算和随访通知规则失效；事件 VID 变更、事件删除或改为重复也可能使引用它的自动计算失效。
- 创建或修改基线事件时，服务端会检查项目内唯一性；创建接口禁止重复的基线事件。

### 结果核验

新增、修改、排序或删除事件时，必须先 GET 获取变更前事件列表，完成写操作后再次 GET 获取变更后列表，并用 Markdown 表格向用户反馈实际 diff。删除演练只返回影响，不算正式变更。

当一次操作包含多个事件或多个变更条目时，必须使用批量变更表格：每行表示一个事件条目，第一列固定为变更类型，只能填写“新增”“变更”“删除”或“排序”；后续各列按条目属性展开，例如 `vid`、名称、事件类型、是否重复、排序等。表格中展示变更后的值，原值紧跟在变更后值后面并使用删除线标记。新增条目的原值留空，删除条目的变更后值留空并只保留删除线原值。

如果用户要求展示全量结果，则表格仍需逐行展示所有事件；没有发生变化的属性留空，不要用“无变化”填充。批量变更表格可在全量结果之前作为变更摘要。

示例：

| 属性           | 变更前      | 变更后              | 结果   |
| -------------- | ----------- | ------------------- | ------ |
| 事件名称       | 第 2 次随访 | 第 2 次随访（修订） | 已生效 |
| `is_follow_up` | `false`     | `true`              | 已生效 |
| 计划目标时间   | —           | 14 天               | 已生效 |
| 事件排序       | `3`         | `2`                 | 已生效 |

批量变更示例：

| 变更类型 | `vid`       | 事件名称（`name`）                     | 是否重复（`is_repeating`） | 排序（`ranking`） |
| -------- | ----------- | -------------------------------------- | -------------------------- | ----------------- |
| 新增     | EVT_FU3     | 第 3 次随访                            | 否                         | 4                 |
| 变更     | EVT_FU2     | 第 2 次随访（修订）<br>~~第 2 次随访~~ |                            |                   |
| 删除     | ~~EVT_FU1~~ | ~~第 1 次随访~~                        |                            |                   |
| 排序     |             |                                        |                            | 2<br>~~3~~        |

全量结果示例中，未变化的属性留空：

| 变更类型 | `vid`      | 事件名称（`name`）               | `ranking` |
| -------- | ---------- | -------------------------------- | --------- |
|          | EVT_SCREEN | 筛选期                           | 1         |
| 变更     | EVT_BASE   | 基线访视（修订）<br>~~基线访视~~ | 2         |

表格中的值必须来自前后两次 GET 响应；如果 GET 失败、事件未出现、删除后仍存在或属性与预期不一致，应报告“变更未确认生效”，不得仅依据写接口返回成功进行结论判断。
