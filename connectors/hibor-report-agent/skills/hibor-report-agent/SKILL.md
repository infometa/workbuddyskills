# 慧博研报搜索与问答 Skill

## 1. 功能概述

本 Skill 通过金融数据 MCP 服务查询慧博研报，支持两类任务：

- **研报分片检索**：查找与问题相关的研报内容片段，便于定位原文依据。
- **研报文档查询**：搜索相关研报文档，或查询指定文档的信息。

所有工具均支持可选的 `doc_id`。提供 `doc_id` 时，应将查询范围限定到该文档；未提供时，不限定具体文档。

## 2. 工具选择规则

根据用户的目标选择最合适的 MCP 工具，不要仅凭问题中出现的关键词机械选择。

| 用户意图 | 使用工具 | 说明 |
| --- | --- | --- |
| 希望查看支持某个观点的具体研报片段或原文内容 | `chat_chunks` | 检索与问题相关的内容分片 |
| 希望查找研报列表、研报摘要或文档信息 | `chat_doc` | 搜索相关研报文档 |
| 已知 `doc_id`，希望查看该文档的相关分片 | `chat_chunks` | 将 `doc_id` 与检索问题一起传入 |
| 已知 `doc_id`，希望查询该文档的详细信息 | `chat_doc` | 将 `doc_id` 与查询问题一起传入 |

如果目标工具不可用，不要声称已经完成查询。可在其他已启用工具能够满足需求时改用该工具，并向用户说明结果范围的差异；否则应明确告知工具当前不可用。

## 3. MCP 工具说明

### 3.1 `chat_chunks`：研报内容分片检索

**用途**

根据问题检索相关研报的内容分片，适合查找原文依据、定位具体论述，或查看某份研报中与主题相关的内容。

**典型场景**

- "查询关于五粮液的研报分片。"
- "找出研报中关于黄金价格走势的相关论述。"
- "查询文档 ID 为 `xxx` 中与营业收入有关的内容。"

**参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `question` | string | 是 | 要检索的主题、关键词或问题 |
| `doc_id` | string | 否 | 指定文档 ID。提供后仅搜索该文档的分片信息 |
| `advanced_search` | array<object> | 否 | 高级搜索配置，指定要检索的数据源；不传则检索全部 5 个数据源。每个对象必须包含 `index_name` 和 `collection_name`，二者取值相同，且为下方数据源枚举之一 |
| `date_filter` | string | 否 | 时间筛选模式，默认 `auto`；可选 `auto`、`all`、`range` |
| `publish` | string | 否 | 研报发布机构名称 |
| `start_date` | string | 否 | 开始日期，格式 `YYYY-MM-DD`；仅在 `date_filter="range"` 时生效 |
| `end_date` | string | 否 | 结束日期，格式 `YYYY-MM-DD`；仅在 `date_filter="range"` 时生效 |

**调用建议**

- 将 `question` 写成具体的检索目标，例如"宁德时代 2025 年营业收入及同比变化"，而不是只传入过于宽泛的单个词。
- 如果用户要查看某份文档的内容片段，必须传入已知的 `doc_id`。
- 分片检索结果是相关内容片段，不应直接称为整篇研报或完整文档。
- 不要将检索到的片段扩写成原文中并不存在的结论。
- 当用户明确限定只看"新闻""公告""英文研报""中文研报"或"个人知识库"时，传入对应的 `advanced_search`；用户未限定数据类型时不要传，默认检索全部 5 个数据源。
- `advanced_search` 只控制检索的数据源，不替代 `publish`、`date_filter`、`doc_id`；机构名仍应放在 `publish` 中。

### 3.2 `chat_doc`：研报文档查询

**用途**

搜索与用户主题相关的研报文档，或在提供 `doc_id` 时查询指定文档的信息。适用于用户想找研报、查看研报摘要或了解文档详情的场景。

**典型场景**

- "查询关于新能源行业的研报文档。"
- "找一下最近关于人工智能的券商研报。"
- "查询文档 ID 为 `xxx` 的详细信息。"

**参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `question` | string | 是 | 文档检索主题或查询要求 |
| `doc_id` | string | 否 | 指定文档 ID。提供后仅获取该文档的信息 |
| `advanced_search` | array<object> | 否 | 高级搜索配置，指定要检索的数据源；不传则检索全部 5 个数据源。每个对象必须包含 `index_name` 和 `collection_name`，二者取值相同，且为下方数据源枚举之一 |
| `date_filter` | string | 否 | 时间筛选模式，默认 `auto`；可选 `auto`、`all`、`range` |
| `publish` | string | 否 | 研报发布机构名称 |
| `start_date` | string | 否 | 开始日期，格式 `YYYY-MM-DD`；仅在 `date_filter="range"` 时生效 |
| `end_date` | string | 否 | 结束日期，格式 `YYYY-MM-DD`；仅在 `date_filter="range"` 时生效 |

**调用建议**

- 用户想找"哪些研报""研报列表""相关报告"时，优先使用 `chat_doc`。
- 用户只想了解文档元信息或摘要时，优先使用 `chat_doc`，不要默认改用问答工具。
- 用户想进一步了解某份研报的观点时，可在取得真实 `doc_id` 后，使用 `chat_chunks` 检索该文档的相关内容分片。
- 只有当工具返回真实 `doc_id` 后，才能将其用于后续调用。
- 当用户明确限定只看"新闻""公告""英文研报""中文研报"或"个人知识库"时，传入对应的 `advanced_search`；用户未限定数据类型时不要传，默认检索全部 5 个数据源。
- `advanced_search` 只控制检索的数据源，不替代 `publish`、`date_filter`、`doc_id`；机构名仍应放在 `publish` 中。

> **重要：** 上述参数表按照项目说明中"所有工具支持以下参数"的描述整理。若 MCP 服务实际注册的各工具 Schema 与此不同，应以运行时暴露的工具参数定义为准。

## 4. 通用参数规则

### 4.1 `advanced_search` 的使用

`advanced_search` 用于指定本次检索的数据源范围。类型为 `array<object>`，可选，默认不传。

- **不传**：默认检索全部 5 个数据源，即中文研报 + 英文研报 + 个人知识库 + 公告 + 新闻。
- **传了**：只检索数组中指定的数据源，不会混入未指定的数据源。
- 每个对象必须同时包含 `index_name` 和 `collection_name`，且二者取值相同。
- 每个对象的取值必须来自下表 5 个数据源之一。

**支持的数据源：**

| `index_name` / `collection_name` | 含义 | 用户提到时应选择该数据源 |
| --- | --- | --- |
| `newyanbao_main` | 中文研报 | 「研报」「研究报告」「行业分析」「公司研究」「宏观经济」「策略」等 |
| `newyanbao_eng_main` | 英文研报 | 「英文研报」「English research」等 |
| `person_knowledge` | 个人知识库 | 个人知识库相关诉求 |
| `notice_main` | 公告 | 「公告」「公司公告」「证监会」「交易所公告」等 |
| `news_main` | 新闻 | 「新闻」「资讯」「快讯」「媒体报道」等 |

**对象结构示例：**

只检索中文研报：

```json
[
  {
    "index_name": "newyanbao_main",
    "collection_name": "newyanbao_main"
  }
]
```

只检索新闻：

```json
[
  {
    "index_name": "news_main",
    "collection_name": "news_main"
  }
]
```

同时检索中文研报和新闻：

```json
[
  {
    "index_name": "newyanbao_main",
    "collection_name": "newyanbao_main"
  },
  {
    "index_name": "news_main",
    "collection_name": "news_main"
  }
]
```

**选择规则：**

- 用户说「查中文研报」「研究报告」「行业分析」「公司研究」「宏观经济」「策略」等 → 传 `newyanbao_main`。
- 用户说「英文研报」「English research」等 → 传 `newyanbao_eng_main`。
- 用户说「公告」「公司公告」「证监会」「交易所公告」等 → 传 `notice_main`。
- 用户说「新闻」「资讯」「快讯」「媒体报道」等 → 传 `news_main`。
- 用户说「个人知识库」相关诉求 → 传 `person_knowledge`。
- 用户未限定数据类型 → 不要传 `advanced_search`，默认检索全部 5 个数据源。
- 用户同时限定多个数据源 → 在数组中传入多个对象。
- 不要将公司名称、股票代码、机构名称误当作数据源；这些应分别放在 `question` 或 `publish` 中。

### 4.2 `date_filter` 的使用

| 值 | 含义 | 适用情况 |
| --- | --- | --- |
| `auto` | 自动时间筛选，也是默认值 | 用户询问近期、最新或未明确指定历史范围 |
| `all` | 查询所有历史数据 | 用户明确要求全部历史、历年或不限时间 |
| `range` | 自定义日期区间 | 用户明确给出开始日期和结束日期 |

使用 `range` 时：

- `start_date` 和 `end_date` 使用 `YYYY-MM-DD` 格式。
- 确保开始日期不晚于结束日期。
- 如果用户只提供一个日期，且无法合理确定区间，不要自行捏造另一个日期；可先询问用户，或在适用时使用默认时间筛选。

### 4.3 `publish` 的使用

- 仅当用户指定了研报发布机构时传入。
- 尽量使用用户提供的机构名称。
- 不要将被分析的公司名称误当成发布机构名称。例如，"查询中信证券关于比亚迪的研报"中，`publish` 应为"中信证券"，公司主题应保留在 `question` 中。

### 4.4 `doc_id` 的使用

- 只有在用户提供了文档 ID，或前序工具结果明确返回了文档 ID 时才传入。
- 不要把公司代码、股票代码、研报标题或其他 ID 擅自当作文档 ID。
- 传入 `doc_id` 后，查询范围应限定在对应文档内；如果该文档未找到相关信息，应如实说明，不要将其他文档的内容混入回答。

## 5. 推荐调用流程

1. **识别目标**：判断用户是需要查找研报文档，还是检索具体内容片段。
2. **选择工具**：查找研报列表、摘要或文档信息时优先选择 `chat_doc`；查找研报原文依据或具体论述时优先选择 `chat_chunks`。
3. **提取筛选条件**：识别 `doc_id`、时间范围、发布机构和数据源范围（`advanced_search`）；用户未限定数据源时不传 `advanced_search`，默认检索全部 5 个数据源；用户明确只查新闻、公告、英文研报、中文研报或个人知识库时，按映射传入对应对象。
4. **执行查询**：调用已启用且参数匹配的工具。
5. **组织结果**：根据检索结果整理文档信息或内容片段；必要时概括研报主要观点，并区分可核实事实、研报观点和基于内容的归纳。
6. **说明限制**：如果结果为空、不完整或未覆盖用户要求的时间范围，应明确说明，不要编造研报、文档 ID、数据或引用。

## 7. 结果整理与回答规范

- 优先直接回答用户的问题，再补充相关研报内容或观点。
- 明确区分客观数据、研报作者观点和综合归纳，不将观点表述为确定事实。
- 仅在工具结果实际提供相关信息时，才报告研报标题、发布机构、发布日期、文档 ID 或具体数据。
- 如果不同研报观点不一致，应简要说明差异，不要强行合并成单一结论。
- 如果用户询问财务数据，应留意指标名称、报告期、单位及同比/环比口径；信息缺失时明确指出。
- 如果用户要求摘要，优先提炼研究结论、关键依据、潜在风险和适用时间范围。
- 不要声称已查询到某份研报，除非 MCP 工具确实返回了该结果。
- MCP 检索结果不足以支持结论时，应明确说明证据不足，而不是凭空补全。

## 8. 敏感主题与合规边界

本 Skill 面向研报检索与内容整理，仅在用户授权及平台许可范围内访问指定数据源。涉及政治、政府政策、国际关系、公共事务、重大社会事件等主题时，以实际检索结果为依据，遵守适用法律法规、平台规则及服务授权范围，不进行超出授权范围的数据获取、存储或分发。对敏感内容将依据平台规则进行标识、复核或限制输出，而非仅因主题类别自动拒绝全部相关查询。

### 检索与回答原则

- **客观、准确、可追溯**：优先使用工具实际返回的研报文档信息和内容分片。明确区分公开事实、研报作者的分析判断、市场传闻以及模型归纳，不将其中一种冒充另一种。
- **明确归属与时间**：涉及政策表述、官方立场、人物言论或事件经过时，尽可能保留原文中的发布主体、时间、适用范围和上下文；不要把分析师观点说成政府或机构的正式表态。
- **不补造、不放大**：不得编造人物言论、政策条文、事件细节、来源或文档信息；不得将片段中的局部表述扩展为研报或相关主体的整体立场。
- **处理争议性说法**：对于未经证实、相互矛盾或具有争议的说法，应注明这是某份研报或某个来源的说法，并说明当前检索结果是否足以验证；不要把未经核实的指控作为事实传播。
- **保留重要限定**：涉及领土、主权、民族、宗教、冲突或其他争议议题时，不要断章取义或删去会改变原意的重要限定；必要时说明不同来源的表述存在差异。
- **时效性与核验边界**：政策、官方声明、国际事件等信息可能快速变化。若工具只返回研报内容，不要声称已经独立核验最新官方信息；应说明信息对应的报告日期或检索范围。若任务明确要求核实最新事实，而当前工具无法完成核验，应如实说明限制。
- **中立呈现**：可以总结和比较来源明确的观点及其依据，但不将政治立场、动机或争议性评价作为未经归属的事实，也不以煽动性措辞代替证据分析。
- **遵守服务边界**：如果请求超出研报检索能力、要求伪造材料或要求协助实施违法行为，不应通过改写检索词或拼接片段来规避限制；应说明可提供的合规替代信息。

### 推荐处理方式

1. 先判断用户要查找研报、检索某份研报的内容，还是比较多个来源的观点。
2. 使用 `chat_doc` 查找文档；需要原文依据时，再使用 `chat_chunks` 检索相关片段。
3. 组织结果时，注明工具实际返回的标题、发布机构、日期和文档 ID（仅限结果确实提供这些字段）。
4. 对结论、争议说法或重要政策信息，明确标注来源及其时间；检索结果不足时，直接说明证据不足，不自行补全。
5. 用户要求最新官方事实而现有工具无法验证时，说明当前结果仅反映已检索到的研报内容，不应将其表述为最新官方结论。

## 9. 错误与边界情况

| 情况 | 处理建议 |
| --- | --- |
| 工具未启用或不可调用 | 检查服务端配置；不要伪造调用结果 |
| `chat_doc` 不可用 | 若用户需要的是问题解答或相关内容片段，可考虑使用其他已启用工具；不要声称已获取完整文档信息 |
| 查询无结果 | 可适当简化关键词、补充公司全称或行业名称，或调整日期筛选；仍无结果时如实告知 |
| 日期格式错误或日期区间无效 | 检查日期格式是否为 `YYYY-MM-DD`，并确认开始日期不晚于结束日期 |
| 指定 `doc_id` 无结果 | 检查 ID 是否来自真实工具结果或用户输入；不要自动移除 ID 后把其他文档结果当作指定文档结果 |
| 返回内容不完整 | 明确指出当前结果的范围，不将分片结果当成完整研报 |
| 用户问题缺少必要信息 | 如果无法可靠查询，再询问一个最关键的澄清问题；不要无必要地连续追问 |

## 10. MCP 连接与认证说明

### 10.1 连接配置

本 Skill 依赖名为 `hibor-report-agent` 的远程 MCP 服务，通过 SSE 方式连接。

- **连接方式**：SSE
- **服务地址**：由 MCP 客户端配置提供
- **请求超时**：60000 毫秒，具体以客户端实现为准
- **认证方式**：HTTP Bearer Token

MCP 连接信息应配置在客户端的 MCP 配置文件（如 `mcp.json`）中，不应要求用户在每次查询时重复提供。

### 10.2 认证配置

客户端通过 HTTP 请求头传递 Bearer Token：

```
Authorization: Bearer <TOKEN>
```

其中，`<TOKEN>` 为实际的访问凭证，应由部署或服务管理员提供。

### 10.3 安全要求

- 不要将真实 Token 写入 `SKILL.md`、示例、日志或公开代码仓库。
- 不要将 Token 放入 `question`、`doc_id` 等业务参数中。
- 不要要求用户在普通对话中提供 Token。
- Token 应由 MCP 客户端安全保存，并在发起连接时自动附加认证请求头。
- 如果出现 HTTP 401 或 403 错误，应提示检查 Token 是否有效、是否过期，以及是否具有相应访问权限。
- 如果连接超时或服务不可用，应检查服务地址、网络连接及服务端状态，不要将连接失败误报为查询无结果。


本 Skill 不负责创建 MCP 连接、保存凭证或刷新 Token。连接建立与认证由 MCP 客户端负责，工具调用由客户端连接的 MCP 服务提供。
