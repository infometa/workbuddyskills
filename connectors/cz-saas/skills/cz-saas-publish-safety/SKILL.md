# 发布、下线与回滚

**发布是全套系统里唯一「顾客立刻可见」的动作**，也是唯一一处「说错话就直接面向顾客」的地方。
这份技能的核心不是怎么点发布，而是**「怎么退」这件事，别说错**。

说错「怎么退」比做错操作更糟 —— 商户按你说的去撤，结果把内容也撤没了。

装修流程见 `cz-saas-page-makeover`；配置类见 `cz-saas-navigation-config`；工具语法见 `cz-saas-cli`。

---

## 一、先分清四个动作

| 动作 | 工具 | 顾客看到什么 | 内容会怎样 |
| --- | --- | --- | --- |
| **发布** | `decoration_publish_page` | 立刻看到新内容 | 草稿变成线上版本 |
| **下线** | `decoration_offline_page` | 立刻看不到这个页面 | **内容全部保留**，只是不展示 |
| **回滚** | `decoration_rollback` | 视快照而定，可能连带状态一起变 | 恢复到某张变更单之前的状态 |
| **改回原值** | `decoration_update_block` 等 | 下次发布才生效 | 手工改，最可控但最慢 |

**这四个不是同义词。** 商户说「撤掉」的时候，先问清他要的是哪一个：

- 「不想让人看到了」→ 下线
- 「内容改坏了，要变回刚才那样」→ 回滚或手工改回
- 「这两天的改动都不要了」→ 回滚到指定变更单

---

## 二、关于「怎么退」的三条硬事实

### 事实 1：撤「发布」用下线，不要用回滚

变更单存的是**包含 `status` 的完整快照**。
回滚一次 `decoration_publish_page` 的变更，页面状态会一并还原成 `DRAFT` ——
效果是**页面下线、内容不变**。

所以：
- 商户要「先下架」→ 用 `decoration_offline_page`，语义明确、影响清晰
- 商户要「退回上一个版本的内容」→ 回滚到编辑前的那张变更单，但要提前说清「页面可能变成草稿」
- 商户要「保留现在的样子，只是先别展示」→ 绝对不要回滚，用下线

### 事实 2：五类配置改错了，没有回滚通道

`SYS_CONFIG` 类型变更的 `rollbackable` **恒为 `false`**，`decoration_rollback` 对它直接 400。

五类配置（`MP_NAVIGATION` / `H5_NAVIGATION` / `USER_CENTER_MENU` / `FLOAT_NAVIGATION` / `SPLASH_AD`）
写错了只能靠**事先读出来的原值**手工写回。

所以写配置之前 `decoration_get_config` 读原值、并把它留在对话里，是**前置条件**，不是建议。

### 事实 3：能不能退，只看 `rollbackable` 字段

不要凭 `changeType` 推测。`CREATE`（新建）与 `SYS_CONFIG`（配置）都是 `false`。
判断依据只有一条：`decoration_get_change` 返回里的 `rollbackable`。

## 三、发布前必须做的自检

```
decoration_get_page --pageId <id>        ← 复核整棵树
```

看两件事：

1. **区块齐不齐**（有没有因为整页 PUT 少传而被删掉的）
2. **warnings 里有没有 `CONTENT_EMPTY`**

发布时服务端会做全量内容校验，任何组件没内容都会被逐条拦下。
**这一步不消耗写配额**，失败了改完再发即可 —— 所以别怕校验，怕的是没校验就发。

内容缺失在草稿阶段只是警告，不拦保存。但**带病发布 = 页面带着空白区块上线**。

---

## 四、strict 动作：退出码 3 不是错误

以下 9 个动作必须先拿到商户确认：发布、下线、回滚、写导航配置、恢复继承、门店继承总部、
活动上下架、改系统设置、调 AI。

机制是这样的：不带 `--confirm` 时 CLI 打印这个动作的具体后果（`PREVIEW`），
然后以**退出码 3** 结束——只打印后果，不执行任何写操作。

```
cz-saas call decoration_publish_page --pageId 123          # → 打印后果，退出码 3
cz-saas call decoration_publish_page --pageId 123 --confirm # → 商户同意后再执行
```

**拿到 3 不是失败，是拦截。** 正确动作是：读它打印的后果 → 讲给商户 → 同意后再加 `--confirm` 重跑。

**不要为了省事直接加 `--confirm`。** 那等于把人按最后一个按钮这个设计绕过去了。

## 五、确认环节怎么说才有价值

「即将执行发布操作，是否继续？」——这句话没有价值。商户听懂的是**动作名**，不是**后果**。

必须说清三件事：

1. **影响范围**：哪个页面 / 单店还是全部门店 / 会不会覆盖门店自配的内容
2. **是否可逆**：能撤 / 不能撤
3. **怎么撤**：哪条工具、哪个 changeId

### 示例

**发布首页**
> 这次会把「秋季新品」设为已发布。它是首页，所以顾客打开小程序**第一眼就是这个页面**。
> 如果哪里不对，随时可以下线，**内容不会丢**。要现在发吗？

**下线**
> 下线后顾客打开小程序就看不到这个页面了，**内容都还在**，随时可以重新发布。要下线吗？

**回滚到编辑前**
> 回滚会把页面恢复到「昨天 18:00 那次编辑之前」的样子，
> 但要注意：**页面状态也会一起变回草稿**，也就是顾客暂时看不到了。
> 如果您只是想把内容改回去、还要继续展示，我可以手工改回那几处，不用回滚。您要哪种？

**门店继承总部 + overwrite=true**
> 这一步会把总部的装修复制到「杭州湖滨店」，并且**覆盖门店自己已经配好的底部导航**。
> 门店之前专门设过的三个入口会消失，**而且没有一键撤销**。
> 要覆盖，还是只补门店还没配的部分？

**商户不同意就不要执行。** 不要用「已为您优化」这类话绕过确认，
也不要在下一轮换个参数偷偷执行。

## 六、变更单怎么查

```bash
cz-saas call decoration_list_changes --pageId 123     # 这个页面的变更历史
cz-saas call decoration_get_change --changeId 456     # 某次变更的详情：rollbackable / 快照
```

回答「最近改了什么」「能不能退回上周那个版本」时，先查变更单再回答。
凭印象说「可以退」，结果 `rollbackable=false`，商户会当场失去信任。

---

## 七、绝对不要做的五件事

1. **不要用整页 PUT 改一个区块** —— 没传的组件等于被删掉，且不报错。
2. **不要改已发布首页的结构再发布** —— 先 `decoration_copy_page` 复制成草稿。
3. **不要在有领取记录的券上改面额** —— 已领未用的券会按新面额核销，等于凭空发钱。调力度请新建券、下线旧券。
4. **不要承诺做不到的事** —— 删页面、发起退款、改商品价格库存、写员工、改角色、读支付密钥，
   这六类刻意没开放，原因是「一次错误调用无法用回滚兜住」。如实告诉商户去 B 端做，并说明为什么这样更安全。
5. **不要说「已经改好了」而不给复核入口** —— 每次写完都要告诉商户：去哪看（`decoration_get_page`）、
   怎么退（`decoration_rollback` + changeId，或手工改回原值）。

---

## 八、一句收尾话术

> 已存草稿，顾客还看不到。要上线告诉我，我会说清上线后顾客会看到什么，你确认了我再发。

比一句「已完成」有用得多 —— 它同时回答了「现在什么状态」和「下一步是什么」。
