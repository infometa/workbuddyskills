# 郑和 TikTok 研究

安装后，用户可以直接用自然语言让 AI 调用郑和数据完成选品、商品研究和竞品分析，不需要自己逐页查数据、整理表格。

可以直接提问：

- “帮我分析一下这个 TikTok 商品最近为什么突然增长。”
- “帮我找 5 个美国美妆类目值得测试的商品。”
- “帮我拆解这个竞争对手店铺最近的增长策略。”

三项能力的用户定位：

- **商品深度研究**：输入一个商品，获得基础资料、销量/GMV/曝光趋势、达人/视频/直播渠道、按需消费者反馈、类目位置、卖点和跟进建议。适合 TikTok Shop 卖家、选品团队、运营、供应链和竞品跟踪人员。
- **AI 机会选品**：输入国家、类目、价格或 GMV 等条件，先看赛道大盘，再筛选和验证候选商品，解释增长是否真实、竞争是否可控，并输出 Top 清单和评分。适合选品、跨境卖家、平台招商、供应链开发和品牌方。
- **竞争店铺拆解**：输入一个店铺，分析店铺规模、Top 商品、商品集中度、达人/视频/直播渠道和增长根因，给出策略、可复制性和风险。适合运营负责人、竞品分析人员、品牌团队和 TikTok Shop 卖家。

## 前置条件：连接郑和 MCP

1. 先检查当前会话的 MCP 工具列表和连接状态。只有能发现并调用郑和数据工具后，才开始下面的分析。
2. 如果未连接、鉴权失败或工具列表为空，暂停数据分析并引导用户：在郑和数据开放平台申请/复制 MCP Key，再在当前客户端新增一个 **Streamable HTTP MCP** 连接。
3. 连接地址使用平台实际提供的地址；本项目默认公网地址为 `https://mcp.zhenghedata.com/mcp`。不要臆造其他域名。
4. 推荐用请求头传 Key：

   ```text
   URL: https://mcp.zhenghedata.com/mcp
   Header: Authorization: Bearer <MCP Key>
   ```

   支持 JSON 配置的连接器可按下例填写（字段名以客户端界面为准）：

   ```json
   {
     "mcpServers": {
       "zhenghe-data": {
         "url": "https://mcp.zhenghedata.com/mcp",
         "headers": {"Authorization": "Bearer <MCP Key>"}
       }
     }
   }
   ```

   若连接器不支持自定义请求头，可兼容拼接 URL（仅限 HTTPS，避免日志泄露）：

   ```text
   https://mcp.zhenghedata.com/mcp?api_key=<MCP Key>
   ```

   认证规则与项目 `auth.py` 一致：优先读取 `Authorization` 中不区分大小写的 `Bearer` 凭据，缺少有效 Bearer 时读取 `api_key` 查询参数；服务端再以 `X-API-Key` 访问下游郑和接口。绝不在回复、日志、报告或附件中回显 Key。Header 方式优先，URL 方式只作兼容。
5. 连接完成后刷新一次 MCP 工具列表并做一个无副作用的轻量调用；若注册有延迟，等待并再次刷新后再判断不可用。不要让用户把 Key 粘贴到对话中。

## 通用执行规则

- 数据渠道只允许已连接的郑和 MCP；报告中注明查询时间范围、站点、语言和调用工具。无法从返回值确认的字段写“未返回”，不得补猜。
- `region` 只能使用 `us`、`id`、`gb`、`ph`、`th`、`my`、`vn`、`sg`、`es`、`mx`、`de`、`fr`、`it`、`br`、`jp`、`pl`、`nl`、`be`、`cz`、`at`、`gr`、`pt`、`hu`；用户说国家名称时先转换并向用户确认不明确的站点。
- 日期使用 `yyyy-MM-dd`，`end_date` 不得晚于昨天（T-1）；优先使用同一地区、同一周期比较。跨周期比较时保持指标口径一致。
- 所有时间字段和日期统计均使用北京时间 GMT+8（服务器时区）。
- 行业大盘不传 `region` 时是全球多地区汇总，返回值中的 `region` 为 `global`；达人榜不传 `region` 时是多国家混合排序。
- `search_type` 仅支持 `1`（短语匹配）和 `2`（分词匹配）。
- 所有分页接口最多每页 20 条、页码不超过 50；需要 Top10/Top3 时排序后取前 N，并注明是否受分页上限影响。
- 先识别实体 ID；只有名称/标题时用搜索工具召回候选，展示候选让用户确认，或在唯一匹配时继续。不要把商品 ID、店铺 ID、视频 ID 混用。
- “销量涨幅/销售额涨幅”优先使用 MCP 返回字段。若只有两个期间值，计算 `(本期-上期)/上期*100%`；上期为 0 时标记“无法计算”，不输出无穷大。
- 不把相关、归因、相关性说成因果。将直接指标、推断和建议分开；数据不足时降低结论强度。
- 评论、视频、直播等明细默认按需调用，避免无触发条件时扩大查询。对空结果区分“该周期无数据”和“接口未返回/连接失败”。

## 功能一：Tiktok-product-research（商品深度研究）

触发例子：

- “这个 TikTok 商品最近表现怎么样，为什么突然增长？”
- “帮我判断这个商品值不值得跟，看看评论风险。”

执行主线：识别商品 → 基础信息 → 市场表现 → 走势判断 → 带货渠道 →（按需）评论 → 报告。

1. **识别商品**：没有 `product_id` 时调用 `search_products`，用关键词、`region`、类目和日期召回；确认目标商品及分析周期。
2. **获取基础信息**：调用 `get_product_info`；整理标题、SKU/商品 ID、评分、店铺、售价、佣金、评论数、关联达人/视频/直播/商品数量、上架时间等实际返回字段。
3. **分析市场表现**：调用 `get_product_trend` 获取日趋势；必要时用 `search_products` 的区间销量、区间销售额、曝光、价格和涨幅字段交叉核对。计算或引用销量、GMV、曝光、售价、销售额涨幅、销量涨幅和曝光涨幅。
4. **走势分支**：以销量环比涨幅为准：`>5%` 为增长；`0% 至 5%（含边界）` 为稳定；`<0%` 为下跌。若涨幅缺失或基期为 0，标为“无法判断”，说明原因，不强行归类。
5. **分析带货渠道**：分别调用 `get_product_authors`、`get_product_videos`、`get_product_rooms`。按销量/销售额/数量及集中度比较达人分销、短视频内容、直播间贡献；不要仅凭数量断言贡献，明确“贡献数据未返回”时的限制。
6. **评论条件调用**：只有用户主动问消费者反馈、商品有明显风险、评分偏低或需要解释差评时，才调用 `get_product_reviews`。按好评/中评/差评和评分筛选，提炼证据、重复问题和潜在风险；无触发条件直接跳过。
7. **输出《TikTok 商品深度研究报告》**，固定包含：
   - 基础概况：商品、售价、佣金、上架时间、评分、店铺；
   - 市场表现：GMV、销量、曝光、涨幅、走势；
   - 增长驱动因素：达人、短视频、直播、店铺贡献；
   - 消费者反馈：核心好评、差评、潜在风险（未调用评论时注明）；
   - 市场位置：类目排名、竞品对比（只有实际排名/对比数据才填写）；
   - 核心卖点提炼；
   - 最终判断：重点关注/观察/谨慎跟进/不建议跟进，给出理由和风险提示。

   报告必须明确回答：当前表现及核心数据、增长来源、增长是否可持续（短期爆发/单一达人依赖/见顶风险）、跟进建议及理由。

## 功能二：Tiktok-product-opportunity（选品机会）

触发例子：

- “帮我找美国美妆类目 GMV 增长快、售价 20–50 美元的商品。”
- “找 5 个最近一个月增长明显、达人竞争还不高的家居商品。”

执行主线：识别类目 → 类目大盘 → 首轮候选 → 单品验证 → 用户规则二筛 → 综合评分 → 报告和附件。

1. **识别类目**：调用 `get_categories` 按名称搜索，确定三级类目 ID、`region`、分析周期；名称歧义时先让用户选定。
2. **分析类目**：调用 `get_industry_overview`、`get_industry_trend`，按需调用市场/价格分布、竞争概览、热卖店铺和热卖商品工具，记录类目 GMV、销量、商品数、店铺数、达人数、增长和价格带。
3. **筛选候选商品**：调用 `search_products`，将国家/三级类目/售价/GMV/销量/佣金等硬性条件直接映射到 `region`、`category_id`、`price_*`、`sales_*`、`sales_volume_*`、`commission_ratio_*`；按用户目标排序（增长可用趋势或对应排序字段）。
4. **验证候选商品**：对初选池逐个调用 `get_product_info`、`get_product_trend`，按需查询关联达人/视频/直播；剔除异常、无有效趋势、指标不满足准入或无法确认身份的商品。
5. **二轮筛选**：应用用户特殊规则，例如排除竞品、限定发货/店铺属性、过滤疑似侵权或单一达人依赖。规则无法由 MCP 字段验证时列为“待人工核验”，不要声称已过滤。
6. **综合评分与排名**：默认使用可解释的 100 分模型，可按用户要求调整：市场表现 35（销量/GMV/趋势），增长质量 25（趋势稳定性、曝光/转化），竞争与渠道 20（达人/视频/直播集中度），商业性 20（售价、佣金、价格带）。先归一化同批候选指标，再按权重排序；缺失字段降权并显示缺失项，禁止用 0 冒充未知。
7. **输出《TikTok 选品机会报告》**：
   - 基础信息：国家、类目、价格、分析周期和筛选条件；
   - 推荐清单：默认 Top10，深度解读 Top3；每款写推荐原因、增长、竞争格局、达人资源、内容生态和主要风险；
   - 总结结论：最值得深度调研的商品及理由；
   - 交付附件：优先生成 Excel（字段至少含商品 ID、标题、店铺、价格、GMV、销量、涨幅、佣金、评分、分数、风险、来源周期）和按商品标题命名的主图文件夹。若当前客户端或 MCP 未提供文件/图片下载能力，交付 CSV/Markdown 表和图片 URL，并明确限制。

## 功能三：Tiktok-shop-research（店铺拆解）

触发例子：

- “这个店最近为什么涨得这么快，主要靠达人还是直播？”
- “帮我看看这个竞争对手的打法有没有值得复制的地方。”

执行主线：识别店铺 → 基础数据 → 商品结构 → 渠道 → 增长原因 → 报告。

1. **识别店铺**：没有 `seller_id` 时调用 `search_sellers` 按名称、地区和类目搜索；确认唯一店铺 ID、站点和周期。
2. **基础数据**：用 `search_sellers` 的结果整理店铺名、国家、主营类目、销量、销售额、在售/动销商品、达人、视频、直播数量和平均售价。当前工具无独立 seller-info 接口，不得伪造未返回字段。
3. **商品结构**：调用 `get_seller_products`，按销售额或销量排序统计 Top 商品、爆款数量、Top1 GMV 占比和 Top3 GMV 占比。依据集中度输出模型：单爆品型（高度依赖 1 个爆款）、多爆品型（多款共同支撑）或长尾型（无显著头部）。阈值若用户未指定，使用相对集中度并说明这是分析口径，不把经验阈值当平台事实。
4. **渠道分析**：分别调用 `get_seller_authors`、`get_seller_videos`、`get_seller_rooms`，比较达人分销、短视频内容和店铺直播的销量/销售额/数量贡献，定位核心渠道及集中度。
5. **增长溯源**：对比当前和上期的商品、达人、视频、直播变化；必要时调用商品趋势、视频/直播详情。把“上新、达人扩张、内容放量、直播提效”等写成有数据支撑的驱动假设，并列出仍需验证的部分。
6. **输出《TikTok Shop 店铺拆解报告》**，固定包含：
   - 基础概况：店铺、国家、主营类目、周期、一句话总结；
   - 店铺表现：GMV、销量、商品数、动销、达人/视频/直播体量；
   - 商品结构：爆款集中度和单爆/多爆/长尾模型；
   - 获客模式：达人/短视频/直播贡献与核心渠道；
   - 增长溯源：近期增长的根本驱动因素及证据；
   - 策略拆解：商品、达人、内容、直播分别采用的打法；
   - 可复制性、风险和最终结论：重点关注/观察/谨慎跟进/不建议跟进，并说明复制前提。

## 结果质量与交付

- 先给结论摘要，再给关键数据表和证据，最后给建议；每个百分比注明比较周期和分母。
- 同时展示“数据事实”“分析判断”“行动建议”，避免把推断伪装成接口字段。
- 失败或部分成功时报告已成功获取的范围、失败工具和影响；不得用搜索摘要替代详情，也不得静默跳过关键步骤。
- 不输出 MCP Key，不把第三方网页抓取、搜索引擎或模型记忆作为郑和数据来源。用户要求其他来源时，先说明这将超出本 Skill 的数据渠道范围。
