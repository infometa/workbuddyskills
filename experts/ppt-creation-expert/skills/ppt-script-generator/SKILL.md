# PPT 讲稿生成器

## 概述

本 skill 在 **PPT 已生成之后** 工作，为演示者产出一份**可直接照着念**的逐页演讲讲稿（口播稿）。

**与上游 skill 的衔接**：

```
solution-ppt-generator-v3 / call-high-deck-generator / guided-ppt-creation-workflow
        │
        ├── 深度研究报告（上游产出的 .md 文件 / 报告正文）        ← 事实、数据、案例的来源
        └── PPT 内容 / 规划（planning + 生成的 PPT 文件）          ← 逐页标题、要点、版式
                                │
                                ▼
        ┌──────────────────────────────────┐
        │   ppt-script-generator（本 skill） │  → 逐页讲稿 + 过渡 + 开场/结尾 + 控场提示
        └──────────────────────────────────┘
```

**核心原则**：讲稿结构与节奏**对齐 PPT 每一页**；若有对应的深度研究报告则**以报告为事实/数据来源**，没有报告就**只依据 PPT 本身的内容**写稿。讲稿不是把页面文字读一遍，而是把页面要点「讲活」——补充背景、解释数据含义、串联逻辑、制造演讲节奏。

**输入构成**：
1. **PPT 内容/规划（必需）** —— 逐页骨架：每页标题、要点、版式类型、所属板块（讲稿的"骨架"与顺序）
2. **深度研究报告（可选，有则读）** —— 提供权威事实、数据、出处、案例细节（讲稿的"血肉"与可信度来源）

**两种典型场景（决定是否读报告 / 是否用 AI 知识库补充）**：

| 场景 | 报告处理 | 写稿依据 |
|------|----------|----------|
| **A. 上游 skill 刚生成 PPT** —— 同会话用过 `solution-ppt-generator-v3` / `call-high-deck-generator` / `guided-ppt-creation-workflow`，存在配套的深度研究报告 | **读取对应报告** | PPT 骨架 + 报告事实数据 |
| **B. 用户自己上传 PPT** —— 仅给 .pptx/.pdf，没有配套报告 | **不找、不现做报告** | **以 PPT 内容为主**；PPT 信息不全/单薄时，用 **AI 知识库** 检索补充背景、产品能力、技术参数、案例 |

> ⛔ **禁止**为了写稿临时发起深度调研（乐享检索/联网搜索）现做报告。只有"PPT 本就对应一份报告"时才去读它。
> ✅ 场景 B 中 PPT 内容往往只是要点、不够撑起口播——此时**用 AI 知识库检索补全**（见 §1.3），而不是为写稿重新发起深度调研。

---

## 核心工作流程

```
Phase 1 收集输入 → Phase 2 解析对齐 → Phase 3 逐页写稿 → Phase 4 衔接润色 → Phase 5 交付
```

---

## Phase 1 — 收集输入

**PPT 内容是必需输入；深度研究报告是可选输入——有对应报告才读，没有就只按 PPT 写。**

### 1.1 PPT 内容 / 规划（必需）

| 来源 | 说明 |
|------|------|
| ① planning 文本 | 上游 skill 产出的 `planning` 字符串（逐页结构，最理想的输入） |
| ② PPT 文件 | 用户上传 .pptx / .pdf / 导出图片 → 用 `pptx` skill 读 .pptx，用 `pdf` skill 读 PDF，逐页提取标题与要点 |
| ③ 会话上下文 | 同会话中上游 skill 已输出逐页规划，直接复用 |
| ④ 用户口述大纲 | 用户仅给出页面标题清单 → 据此写稿，但需提醒讲稿深度受限于所给信息 |

### 1.2 深度研究报告（可选，仅"PPT 本就对应一份报告"时读取）

**判断逻辑**：
- **PPT 由上游 skill 在本会话生成**（场景 A）→ 该 PPT 配套有深度研究报告 .md → **读取它**，按下表获取：

  | 来源 | 说明 |
  |------|------|
  | ① 当前会话上下文 | 上游 skill 刚产出深度研究报告 .md，直接复用该报告文件路径 / 正文 |
  | ② 用户直接提供 | 用户粘贴报告正文 / 提供报告文件路径（md/pdf/docx） |
  | ③ 历史检索 | 用户说"用上次那份研究/方案"→ 用 `conversation_search` 找回上游会话中的研究报告文件/正文与关键数据 |

- **用户自己上传 PPT**（场景 B）、或找不到配套报告 → **直接跳过本步**，按 §1.3 决定是否用 AI 知识库补充。

> ⛔ **禁止现做报告**：不要为了写稿主动发起深度调研生成新报告。报告文件无法直接读取时，让用户粘贴报告正文或提供 .md 路径；不要臆造报告内容。
> ✅ 没有报告不是缺陷：用户上传 PPT 求讲稿，就是要你按 PPT 讲清楚，PPT 不够时用 AI 知识库补（§1.3），不要追着要报告。

### 1.3 AI 知识库补充（**仅场景 B，PPT 内容不全面时**）

用户自己上传的 PPT 往往只有要点、信息单薄，不足以撑起完整口播。此时用 **AI 知识库**（云知 `yunzhi_knowledge` skill：产品知识、技术文档、解决方案）检索补全，**而不是**为写稿重新发起深度调研。

**触发条件**（同时满足）：
- 处于场景 B（用户上传 PPT、无配套报告）
- 某页要点过简（如仅一个标题/几个名词），照此无法写出有信息量的口播

**操作**：
1. 调用 AI 知识库（`yunzhi_knowledge` skill），以 PPT 涉及的**产品名 / 技术名 / 解决方案 / 行业场景**为关键词检索，下载落盘后本地 grep/read 抽取片段（全文不进上下文）。
2. 把检索到的产品能力、技术参数、解决方案、典型案例，**对应补充到相关页面**的"可讲的料"。
3. 知识库补充的内容服务于"把 PPT 讲清楚、讲专业"，仍以 PPT 的骨架与顺序为准，不擅自增删页面。

> 优先级：**PPT 已有信息 > AI 知识库检索补充**。知识库用于补背景、补深度、补佐证；PPT 上明确写了的口径以 PPT 为准。
> 若知识库也检索不到、且 PPT 信息确实太少 → 在该页讲稿中据 PPT 要点稳妥发挥，并在交付备注里标注"此页信息有限，建议演讲者补充"。

### 1.4 需求确认（一次性，用选择题）

收齐输入后，用 `AskUserQuestion`（或 `show_form`，若环境支持）一次性确认讲稿风格，**全部用选择题，不要开放式追问**。若用户初始需求已明确则跳过。需确认维度：

| 维度 | 候选项 | 默认 |
|------|--------|------|
| 演讲场景 | 面客售前 / 内部汇报 / 大会演讲 / 培训宣讲 / 评审答辩 | 面客售前 |
| 讲稿详略 | 关键词提示版（每页3-5条提示）/ 完整口播版（每页可直接照念的成段文字）/ 双版本（提示+口播） | 完整口播版 |
| 单页时长 | 紧凑(约40秒/页) / 标准(约1分钟/页) / 充分(约1.5-2分钟/页) | 标准 |
| 语气风格 | 专业稳重 / 亲和自然 / 激情有感染力 / 数据严谨 | 专业稳重 |
| 称呼/人称 | "我们" / "我" / "本方案" / 直接称呼客户名 | 我们 |

> 同时确认：演讲总时长上限（用于反推节奏）、是否需要英文讲稿、是否需要标注停顿/强调/手势提示。

## Phase 2 — 解析与对齐

### 2.1 建立页面清单

从 PPT 输入中提取**逐页清单**，每页记录：

- `页码 / slide_id`
- `页面类型`：封面 / 目录 / 章节封面 / 内容页 / 数据图表页 / 案例页 / 结尾页
- `页面标题`
- `要点列表`（bullet points）
- `所属板块`（如：行业背景 / 需求挑战 / 解决方案 / 客户案例 / 附录）
- `版式`（时间线 / 对比表 / 架构图 / 卡片 / 图表 等，影响讲法）

### 2.2 报告 ↔ 页面映射（**仅在有报告时执行**）

> 场景 B（用户自己上传 PPT、无报告）改为按 §1.3 用 AI 知识库为信息单薄的页面补料，再进入 2.3。

把研究报告（场景 A）或 AI 知识库检索结果（场景 B）的事实/数据/案例**对应到具体页面**，为每页准备"可讲的料"：

- 数据页 → 从报告中找到该数据的**具体数值 + 出处 + 含义解读**
- 痛点页 → 从报告中找到痛点的**真实背景/案例佐证**
- 方案页 → 从报告中找到**技术参数、对比数据、差异化优势**
- 案例页 → 从报告中找到**客户背景、量化成效、前后对比**

> ⚠️ **数据一致性铁律**：
> - **有报告时**：讲稿中出现的每一个数字、百分比、客户名、产品规格，都必须能在研究报告中找到依据。报告里没有的，**不许编**。报告与 PPT 数字冲突时，以研究报告为准并在备注中提示用户核对。
> - **无报告时（场景 B）**：优先使用 **PPT 页面上已有的**数字与表述；PPT 信息不足时，**用 AI 知识库（§1.3）检索到的内容补充**，并确保补充的数据/参数确有知识库来源。**不得凭空编造**任何 PPT 与知识库都没有的数据。讲稿做的是把信息"讲活"——解释含义、串联逻辑、营造节奏。

### 2.3 节奏预算

根据 Phase 1.4 的"单页时长 × 页数"核算总时长，与用户给的总时长上限比对：

- 超时 → 标注哪些页面应"快速带过"，建议精简口播
- 不足 → 提示哪些核心页面（解决方案/案例）可展开讲

## Phase 3 — 逐页写稿

为**每一页**生成讲稿。统一结构见下，不同页型的讲法差异见 `references/script_patterns.md`。

### 3.1 单页讲稿标准结构

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📄 第 N 页 ·【页面标题】              ⏱️ 建议时长：约 X 秒
板块：XX  |  版式：XX
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🔗 承上（过渡句）
   一句话从上一页自然过渡到本页。

🎙️ 口播正文
   可直接照念的成段讲稿。要求：
   • 开口先点本页核心信息（一句话立靶）
   • 逐个讲清页面要点，把数据"解读"而非"朗读"
   • 关键数字带出处（"根据 IDC 2025 报告……"）
   • 结尾留一个钩子，引向下一页

💡 提示
   [强调] 需重读/放慢的关键词
   [停顿] 建议停顿处
   [互动] 可向听众抛的问题（可选）
   [数据] 本页引用的数据及出处，便于演讲者应对追问
```

### 3.2 写稿要求

1. **照念可用**：完整口播版必须是顺畅的口语，不是书面要点的堆砌；演讲者扫一眼就能开口。
2. **解读数据**：不要只念数字，要讲"这个数字意味着什么"。例：不说"市场规模1200亿"，而说"1200亿的市场，且还在以每年30%往上走，意味着现在入局正当时"。
3. **逻辑显性化**：把页面隐含的逻辑用连接词讲出来（因为→所以、不仅→而且、问题→对策）。
4. **页间钩子**：每页结尾自然引向下一页，避免"翻篇式"断裂。
5. **口语化**：多用短句，少用从句套从句；适度口语词（"那么""其实""大家注意"）但不啰嗦。
6. **控制信息密度**：单页口播字数 ≈ 单页时长 × 每分钟语速（中文约 220-260 字/分钟，英文约 130-150 词/分钟）。

### 3.3 特殊页面

- **封面页**：写**开场白**——自我介绍 + 今天讲什么 + 为什么值得听（30-60秒抓注意力）。
- **目录页**：用一句话串起各板块的逻辑主线（"我会从行业趋势讲起，落到具体方案，最后用真实案例证明"）。
- **章节封面**：写**小结+预告**——承接上一板块结论，预告本板块要点。
- **结尾页**：写**收尾**——核心价值再强调 + 行动号召（CTA）+ 致谢 + 留联系/下一步。

---

## Phase 4 — 衔接与润色

逐页稿完成后做一次整体打磨：

1. **开场强化**：确认开场白有"钩子"（一个数据/一个问题/一个故事），不要平铺直叙。
2. **过渡顺滑**：检查相邻页过渡句是否自然，板块切换处是否有"小结+预告"。
3. **节奏起伏**：标注全场的"高潮页"（通常是核心方案、关键数据、王牌案例），提示演讲者在此提速/提气。
4. **首尾呼应**：结尾回扣开场抛出的钩子，形成闭环。
5. **时长校验**：累计各页建议时长，与目标总时长比对，超/欠时给出调整建议。
6. **风险预案**：在交付备注中列出"演讲者可能被追问的点 + 报告中的应答依据"。

---

## Phase 5 — 交付

### 5.1 输出形式

把全部讲稿写入一个 Markdown 文件，保存到当前工作目录（用户可保留/打开），文件名如 `PPT讲稿_{主题}_{日期}.md`。结构：

```markdown
# 《{PPT主题}》演讲讲稿

> 演讲场景：XX | 目标时长：约 XX 分钟 | 页数：XX | 风格：XX

## 🎬 开场白（封面页）
...

## 📑 逐页讲稿
### 第1页 ...
### 第2页 ...
...

## 🎯 结尾与行动号召
...

## 📌 演讲者备注
- 全场节奏：高潮页在第 X / Y / Z 页
- 可能被追问的问题及应答依据（来自研究报告）
- 数据出处清单
- 需用户核对/补充的内容
```

完成后用 `present_files` 把讲稿文件呈现给用户。

### 5.2 交付自检清单

- [ ] 每一页 PPT 都有对应讲稿，无遗漏
- [ ] 讲稿中的数据/客户名/参数均可在研究报告中找到依据，无编造
- [ ] 有开场白（带钩子）和结尾（带 CTA）
- [ ] 相邻页有过渡句，板块切换有小结+预告
- [ ] 单页时长 × 页数 ≈ 目标总时长（已校验，超/欠时已标注）
- [ ] 完整口播版可直接照念（口语顺畅，非要点堆砌）
- [ ] 关键数据带出处，备注区列了应答依据
- [ ] 报告与 PPT 数字冲突处已在备注中提示用户核对

---

## 关键约束

1. **不造数据**：场景 A 的事实/数字/客户名/规格必须源自研究报告；场景 B 优先用 PPT 已有信息，不足时用 AI 知识库补充——两处都没有的，不写进讲稿。
2. **对齐 PPT**：讲稿页数、顺序、板块严格对应 PPT，不擅自增删页面。
3. **可念性优先**：完整口播版必须是能直接开口的口语稿，不是书面要点。
4. **数据要解读**：讲数字的含义和价值，不做朗读机。
5. **节奏可控**：每页标建议时长，全场可核算，给演讲者控场提示。
6. **报告按需读，不现做**：PPT 本就对应一份报告（场景 A）才读取；用户自己上传 PPT（场景 B）只按 PPT 写，PPT 单薄时用 AI 知识库补充——**严禁为写稿临时发起深度调研现做报告**。
7. **冲突以报告为准**：场景 A 中报告与 PPT 数据不一致时以研究报告为权威，并提示用户核对。
