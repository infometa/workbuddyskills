# 导师与答辩委员会意见落实

## 定位与输入

把导师批注、答辩委员会意见或书面整改要求转为可追踪的修改任务。输入尽量包括：意见原文、批注位置、论文对应版本、学校/学院要求、研究问题、证据矩阵、数据与分析产物、提交节点和用户已经作出的决定。

不把含糊意见擅自解释为确定命令；不模拟导师签字或审核结论，不代用户承诺完成时间、研究结果、显著性、录用或通过答辩。

## 分类规则

每条意见统一分配稳定 ID `A001`、`A002`……，并在来源字段区分导师、答辩委员会或其他意见人；保留原文，不因排序变化复用。

| 分类 | 典型意见 | 核心检查 |
|---|---|---|
| 结构 | 调整章节、删并内容、突出主线、题目与章节不匹配 | 研究问题—章节任务—论证顺序及影响范围 |
| 证据 | 补文献、补数据、核对来源、结论依据不足 | M1/M2/F 等级、证据矩阵、数据可得性和引用边界 |
| 表达 | 概念不清、逻辑跳跃、语言冗余、术语不统一 | 原意、术语账本、段落任务、衔接与结论边界 |
| 格式 | 标题、页码、图表、引用、参考文献、学校模板 | 学校模板优先、Word 操作路径和人工复核 |
| 方法/分析 | 样本、变量、编码、统计或访谈设计需要调整 | 是否改变研究设计、是否需重做分析、是否涉及伦理 |
| 其他 | 选题范围、创新点、进度、手续或无法归类事项 | 先澄清意图、责任人和适用规则 |

一条意见可有主分类和次分类；涉及学术诚信、伦理、核心结论或提交阻塞时列 P0，核心证据/方法/结构不足列 P1，语言和格式列 P2。

## 落实流程

1. **建立意见清单**：记录意见 ID、来源角色、日期、原文、批注位置和论文版本。
2. **解释但不扩写**：写出“可能要求解决的问题”和“仍有歧义的点”；歧义影响范围大时先请用户或导师确认。
3. **定位修改位置**：精确到章节、段落 ID、表图、参考文献或模板要素；一条意见影响多处时列出全部传播范围。
4. **设计改法**：说明删除、补证、重组、重算、重画、改写或格式操作，以及所需材料和完成证据。
5. **检查冲突**：与研究问题、已确认 Canon、其他意见、学校模板、真实数据和伦理要求逐项核对。
6. **用户确认重大取舍**：意见若要求改变主研究问题、研究对象、核心方法、数据口径或结论边界，先展示影响和备选方案，请用户确认，不擅自二选一。
7. **执行与验证**：只把有可检查修改文本、分析、图表或审批的任务标 `VERIFIED_DONE`；用户口述完成但无产物标 `REPORTED_DONE_UNVERIFIED`。
8. **生成回复要点**：逐条说明理解、修改位置、实际改动、依据和仍需确认项，保持事实性，不代用户作保证。

## 落实表

| 意见 ID | 来源/日期 | 原文 | 分类/P级 | 对应位置 | 问题解释 | 具体改法 | 所需证据/材料 | 影响范围 | 完成证据 | 状态 |
|---|---|---|---|---|---|---|---|---|---|---|

“具体改法”必须能执行，例如“在 2.3 节第二段加入 `L012` 与 `L018` 的方法差异比较，并将原绝对结论降级为适用边界内表述”，不能只写“认真修改”“补充完善”。不得为完成意见编造文献、数据、访谈、分析或审批。

## 无法落实与沟通建议

| 无法落实类型 | 记录内容 | 沟通建议 |
|---|---|---|
| 材料/数据不可得 | 缺什么、为何不可得、已核查范围 | 说明限制，提出缩小问题、替代合法数据或降级主张，请导师选择 |
| 时间/资源约束 | 剩余任务、依赖、学校硬节点 | 陈述当前状态和可行取舍，请导师确认优先级；不承诺具体完成时间 |
| 方法前提不满足 | 不满足的假设、受影响分析/结论 | 提供有依据的替代方法或删除该主张，必要时请方法专家判断 |
| 伦理/权限阻塞 | 缺少审批、同意、授权或隐私条件 | 停止实施性步骤，说明合规要求与可替代非敏感方案 |
| 意见之间冲突 | 冲突意见 ID、各自影响 | 并列呈现冲突和备选方案，请用户确认向导师澄清 |
| 与研究问题冲突 | 会改变的问题、对象、方法和既有章节 | 先请用户确认是否接受研究问题变更；未确认前不实施核心改动 |
| 无法理解意见 | 原文歧义及不同解释 | 用封闭式问题确认，如“您更希望补充证据，还是调整结论边界？” |
| 证据不支持预期结论 | 真实结果与意见预期不一致 | 如实报告证据，调整措辞或讨论限制，不篡改数据、不承诺结论 |

建议沟通结构：复述理解 → 说明已核实事实 → 指出阻塞或取舍 → 给出一至两个合规方案 → 请求明确选择。语气尊重、简洁，不把责任推给工具或导师。

## 回复要点模板

逐条回复只生成要点，由用户核对后自行沟通：

- 意见 ID 与意见摘要：
- 我的理解：
- 修改位置：章节/页码/段落/图表/文献
- 已作或拟作修改：
- 修改依据：学校规则/证据 `L___`/数据或分析 ID/导师确认
- 修改后的边界：
- 无法完全落实的部分及原因：
- 备选方案：
- 需要导师/用户确认的问题：
- 附件或完成证据：

避免“保证按时完成”“一定得到预期结果”“已经完全解决”等无证据承诺。可写“已在所附版本的 X 处完成并请核对”或“拟按方案 A 调整，待您确认取舍”。

## 冲突处理

- **研究问题冲突**：立即暂停相关实改，列出原问题、意见要求的新问题、受影响章节/数据/方法、保留原问题与改题两种后果，请用户确认。
- **学校模板与个人偏好冲突**：先确认哪项是强制要求；学校当前有效规定优先，导师明确要求的适用范围需记录。
- **多位意见人冲突**：不自行判定谁优先，按来源、原文和影响并列，建议由用户向主导师或学校指定责任人确认。
- **意见与真实证据冲突**：事实、数据和来源不得为迎合意见而改写；可调整解释、补充分析或诚实报告限制。

## 交付

- 分类后的意见总表与 P0/P1/P2
- 每条意见的定位、具体改法、材料与完成证据
- 无法落实事项、原因和沟通建议
- 研究问题或意见冲突的待确认清单
- 用户核对用回复要点，不代发、不承诺时间或结论
