# 专家查询：槽位优先，按最终语义选择表达方式

仅用于 WorkBuddy 专家渠道。目标是让下游收到准确、完整的查询，不是增加字段数量。由当前专家模型结合用户问题和上下文选择槽位模式或完整 query 模式，不额外调用模型，也不为比较两种写法重复请求接口。

## 查询前澄清

复用已确认条件，不靠接口默认日期；只确认会改变查询请求的硬条件。无偏好、比较、约束或规划的普通票务、酒店、景点/门票直接查询并渲染，不询问“快速查询还是专家解读”。需求已有偏好、比较、预算、时段、席别、星级、人群、取舍、行程，或用户明确要求综合解读时才进入专家分析。`direct_render` 结尾会按资源类型提示可继续补充的偏好；同一对话补充后复用本次快照分析，不重查、不授权。

### 票务快速路径

普通“A到B机票/火车票/汽车票”表示本次单程查询。明确往返且缺返程日期才追加返程日期，不问人数、舱位或预算。

火车票城市对或站点对明确但缺日期时不追问，也不先调用日期助手；直接调用分析包装器。包装器会按 `Asia/Shanghai` 当前日期在代码中补次日，并通过 `queryDefaults.departureDate` 回传实际查询日。已有明确日期、相对日期，或用户明确说日期未定/随便看看时不覆盖。

机票缺日期仍运行一次日期助手，并采用返回的 `askUserQuestion` 只问出发日：

    node "<本 Skill Base directory>/scripts/date-options.js" --base-date "YYYY-MM-DD" --days 3

汽车票缺日期沿用同样的日期询问。数字日期与星期冲突时用助手的 `--check-date`、`--claimed-weekday`；相对日期可按可靠当前日期和用户时区唯一解析时直接使用。不让模型心算日期，不擅选机票日期。

### 其它边界

- 酒店城市/位置不明先问；只有查指定入住的房价/房态才确认入住、离店。“总部附近酒店”可先推荐，不补日期；人数/房间数只在总价、特定房型可订性或多人入住可行性受影响时问，不是普通附近酒店比选的前置条件。
- 景点归属不明先问；只有可订门票或特定日期票价才确认游玩日期。“银川有什么好玩的”“拙政园门票多少钱”不强问日期、人数、偏好。
- 每日行程缺目的地、天数/范围时先问；“苏州两日游”不强问日期。跨城实时资源再确认出发地、日期。
- “上海出发飞哪里便宜”“苏州到银川怎么走”属于开放探索，不强补目的地/日期，也不宣称某天价格或余票。

地点多义、日期歧义或条件冲突只确认冲突点；明确更正时更新该条件并保留其余项。多个需求一次列出阻塞项；某项无效不阻塞其他完整项。不擅选机票日期或承诺精确报价。

## 参数提取

先在当前轮一次完成六项提取：业务类型、城市或城市对、具体对象、对象关系、日期、限制条件。限制条件必须连同归属一起保留，例如“酒店每晚300元以内”“返程不要大兴机场”，不能拆成失去对象的关键词。提取后只在内部展开一次网关最终句；句子能完整复述用户需求才调用。不要先用简写试查，再根据结果改成完整表达。

- 用户补充回答后只合并新条件，立即按模板请求。没有 --date / --depart-date 参数：机票/火车/汽车的出发日期写 --extra "YYYY-MM-DD 出发"；酒店写 --extra "YYYY-MM-DD 入住，YYYY-MM-DD 离店"，地标、预算等已有条件一起保留。无需检查日期解析实现或换表达方式试查。
- 默认不传业务 `--query`，使用原有槽位和 `--extra`；酒店地标、附近关系、地址纠正、否定偏好都写入 extra，不因出现这些信息就切换 query 模式。
- `--departure` / `--destination` 放已确认的出发/目的城市；酒店与景点填所在城市。道路、公司、景点、机场和商圈名称放 extra，不替代城市。
- `--departure-station` / `--arrival-station` 放完整站名；明确查某个班次才用 `--train-number` / `--flight-number`；特价机票用 `--low-price`。已选班次号时，城市/站点不会再被网关自动拼入基础句。
- `--extra` 保留槽位基础句未表达的具体对象、地点关系、地址、主题、人群、时间、预算单位及否定条件。地标查询要把城市和地标连在一起写清楚，例如 destination=北京 时用“北京故宫附近、每晚300元以内的酒店”，不能只写“故宫附近300元以内”，也不能缩成“就近住宿”。不擅自把别名扩成未经确认的门牌地址。基础句已完整表达需求且没有附加条件时可省略，不强制塞入“有哪些/好玩的/推荐一下”等泛问词；不得因此省掉“免费/晚上/带孩子/附近”等有效限制。
- 发送前按下表展开一次网关最终句，检查城市、具体对象、关系、方向、日期与限制是否与本轮需求一致。能清楚表达就沿用槽位；关系复杂、槽位模板使意思模糊时，可在 `--` 后传完整 `--query`，不是所有问题都必须传。
- 完整 query 须写全城市、对象、关系和条件，网关不会补槽位/extra；脚本会先合入另传的 extra，但不能替你补城市或解冲突。仍提供本地必需槽位，不绕过缺参确认。query最多2000字、extra最多500字（含行程前缀），超限报错，不截断。
- 不补造门牌、日期、人数、房间数或距离；用户纠正地址时保留原查询目标及未变条件，替换旧地址。地点不确定先澄清或核验，不能换商圈反复试查。

## 网关实际流程

1. 选择业务脚本，对应七个资源接口之一。模型选择表示方式，代码执行校验与拼接，不是网关再次调用模型提槽。
2. HTTP 请求的 query 无非空文本：网关按该业务校验槽位，然后用基础句加一个空格再追加 `extra.trim()`；extra 为空就只有基础句。
3. HTTP 请求的 query 有非空文本：网关直接使用 query，不再校验或拼入其它槽位。当前 Skill 的本地脚本仍先执行各自的必需参数检查；“网关能透传”不等于可以编造或跳过本地所需参数。
4. 网关把最终句作为下游 POST 表单的 `query` 发送；不会另外发送 destination/extra 让下游补齐语义。channel、callerChannel、surface 是来源/展示信息，不进入查询句。

## 网关模板

| 业务 | 槽位基础句与优先级 |
| --- | --- |
| 酒店 | `{destination}的酒店推荐` |
| 景区/门票 | `{destination}的景点`；未传目的地时为“热门景点推荐” |
| 机票 | 先看航班号：`{flightNumber}航班信息`；否则城市对：`{departure}到{destination}的机票`（lowPrice=true 时为“的低价机票”）；只有出发地且 lowPrice=true：`{departure}出发的低价机票` |
| 火车 | 车次号优先：`{trainNumber}次列车信息`；其次完整站点对：`{departureStation}到{arrivalStation}的火车票`；再其次城市对：`{departure}到{destination}的火车票` |
| 汽车 | 完整站点对优先：`{departureStation}到{arrivalStation}的长途汽车`；否则城市对：`{departure}到{destination}的长途汽车` |
| 综合交通 | `{departure}到{destination}的交通路线` |
| 旅行 | 有出发地：`从{departure}到{destination}旅游`；否则 `{destination}旅游` |

以上每条都在末尾追加 extra。专家旅行 intent=itinerary 时，包装器还会在 extra 前加“行程规划，按天安排交通、住宿与景点。”；selection 不加。不能把行程规划改成套餐比选，或只把行程意图留在 plan.userRequest 中。

## 默认槽位模式的例子

以下示例只说明槽位表达，均不传业务 query，且不代表程序已经核实地址或可以立即调用。具体票务缺日期等情况仍先按“查询前澄清”确认，再将回答合入 extra；用户没有提供的日期、人数等不能套用。

### 酒店与多轮地址纠正

首轮“苏州同程旅行总部附近的酒店”：

```json
{"destination":"苏州","extra":"同程旅行总部附近的酒店"}
```

网关最终句：`苏州的酒店推荐 同程旅行总部附近的酒店`。城市、地标、附近关系和查询对象均保留；不擅自补入住日期。

次轮“总部应该在酝慧路上”：

```json
{"destination":"苏州","extra":"酝慧路同程旅行总部附近的酒店"}
```

网关最终句：`苏州的酒店推荐 酝慧路同程旅行总部附近的酒店`。仍找总部附近酒店，不变成整条道路或某个商圈。“应该”是待核实线索，不宣称地址已确认；不因此新增66号或改名为同程大厦。此前已确认日期、预算等照常保留，没有则不补。

只有用户明确提供或可靠证据确认完整地址后，才可以用：

```json
{"destination":"苏州","extra":"工业园区酝慧路66号同程旅行大厦附近的酒店"}
```

网关最终句：`苏州的酒店推荐 工业园区酝慧路66号同程旅行大厦附近的酒店`。若用户同时已确认入住日期，可在 extra 后追加“；8月28日入住，8月29日离店”，不新增 query。

## 何时选择完整 query

不是因为有地标就用 query。若按上表展开后能准确表达需求，用槽位即可。若多个对象之间的关系、条件归属或比较意图难以清晰地写在基础句后，可由专家直接组织完整句；这只是表达方式变化，不能借此改用户目标或跳过业务路由。

例如用户问“在苏州同程旅行总部附近找酒店，我要每天去总部，同行人要往返苏州北站，希望两边都方便”，完整 query 可以是：

```json
{"destination":"苏州","query":"查找苏州同程旅行总部附近的酒店：我每天前往总部，同行人往返苏州北站，希望兼顾两人的通勤便利。"}
```

这一需求也可用 destination=苏州、extra 写完整约束表达；模型根据最终句是否清楚选择一种，不为两个写法各查一次。总部地址、酒店距离、交通耗时仍需证据，不能把“双向方便”当作已被验证的结果。

完整 query 已包含全部条件时可不传 extra；若另传 extra，当前脚本会合并成实际 HTTP query，网关不会再次追加。只对整段完全一致的尾部 extra 去重，不做语义删词。不要在 query 写新地址，却在 extra 留着旧地址。query 上限2000字，extra上限500字（含专家行程前缀），超限报错，不静默截断。

包装器 `--` 前的 `--query` 始终是脚本路径，不是业务 query；槽位模式同样需要它。只有分隔符后的 `--query` 才会改变业务请求。复盘时分别记录用户原话、实际 requestParams 与网关最终句；没有传 query 时，快照中就不应捏造 query 字段。intent 在快照顶层，不并入原始 HTTP 参数。

## 调用前后核对

调用前在当前轮内部展开并检查最终句：是否保留城市、目标地标/产品、附近/方向等关系、时间、预算单位和否定条件？是否只更新了本轮纠正部分？是否加入用户未提供或未经核实的地址与条件？这一步只是一次静默核对，不向用户解释，不增加工具或网络调用。

返回后只核对会让答案失效的硬条件：城市、方向、日期、明确地标定位和预算。只有这些条件明确冲突，且能指出首轮漏传或写错的内容时，才使用一次 queryCorrection；不能因为想找更好的结果或做第二次确认而重查。定位信息不完整时直接告诉用户目前无法确认，不连续更换商圈碰运气。

对最终采用的查询，HTML/完整MD保留全部资源，聊天精选符合条件的候选并说明关键限制，不把不符合条件的结果凑成推荐。被纠正的旧地点查询不混进新位置推荐；本规则不改变原始资源、预订链接与HTML模板。
