# 详细专家解读：直接回答眼前这位旅客

复杂行程或需要细致分析时参考本文件，将内容写入 `interpretation`；普通比选直接按快速契约写简明解读，无需加载本文。它与推荐、每日安排同时定稿，保留在完整 MD/HTML 的资源区之后，不要求聊天重复输出。不是渲染结束后另写的点评。

## 对话语气

像旅行顾问面对面回答提问，直接说结论，再解释对这次出行有什么影响。默认称呼“您”，有需要时说“我更建议”“我会优先考虑”；不用每句都加称呼，也不冒充有亲身旅行经历。

- `customerFocus`、标题和段落都是用户会看到的正文，不是写作说明。不要写“用户已明确的是”“不替用户设定额外条件”“本段应解释”“以下解读仅在……范围内”。内部遵守这些约束即可，不要向用户复述规则。
- “专业”体现在说清依据和取舍，不靠术语或口号。把“价格口径与费用边界”写成“这笔票价包含什么”，把“机场选择影响门到门时间”写成“哪个机场更方便您出发和回家”。不要把每个标题压成不完整的短语。
- 说完整、顺口的句子。避免“便宜的票价用早出晚归还”“把省下的钱还给时间”等绕弯比喻；直接说“票价更低，但要早起出发、晚些回来”。不为了显得像真人而加“宝子”“放心冲”、假装坦诚的开场或夸张赞美。
- 有用的事实可以写得具体；缺失条件只说与选择有关的那一项。例如“您还没说从哪里去机场，现在还不能确定几点出门”，不要列一长串用户没提供的条件，也别把每段都写成免责说明。用户可见文字不说“接口未返回、字段缺失、快照、资源编号”，改成“目前还不能确认”并直接说明要核对什么。
- 长短句可以交替，常用逗号、句号和问号。新写的建议和解读不用破折号连接长句，不机械堆加粗、表情或冒号标签。接口原文、产品名称、日期、链接不适用这条润色规则，必须保留。

## 内容与分寸

- `customerFocus`：一两句接住问题，并点出这次最值得考虑的取舍，不写任务复述或待填写说明。人数、预算和偏好只使用对方已经说过的内容。
- `sections`：按问题选有实质内容的角度；简单比选一节也可以，复杂行程再展开。每节用一到三个短段落，每段通常两三句，说明一个判断及其理由。不要为了达到固定字数或凑齐栏目重复前文，详细不等于冗长。
- `nextSteps`：只留下会影响选择的具体行动，通常一到三项。例如核对机场交通、行李额度或晚到入住安排。避免“完善信息后综合决策”这类空泛收尾，不代替用户下单或承诺库存。

可选角度不是固定模板：

| 用户关切 | 解读需要回答 |
| --- | --- |
| 又快又便宜 | 哪个资源在已知时长与展示价上占优？代价是早起、晚到还是换乘？只想省钱时会牺牲什么？ |
| 亲子/老人/品质 | 哪些已返回信息支持节奏或住宿选择？哪些只是主观偏好？不要把高分直接等同于安静、亲子友好或位置方便。 |
| 完整行程 | 首尾日如何衔接交通？每日安排为何这样取舍？住宿与活动衔接有哪些已知事实和待确认条件？ |
| 预算 | 展示价覆盖什么、尚缺什么？哪些项目可以同口径比较？没有儿童价、房间数、税费等时不能给完整总价。 |
| 备选方案 | 什么条件变化时应该换方案？解释成本和收益，不把所有候选都说成首选。 |

## 事实、判断和条件写清楚

让读者能看懂推荐的依据、对自己的影响和可以怎么选，但不用每段机械重复同一结构，不用 `[事实]/[推理]` 标签，也不输出内部思考过程。

- 提到资源、价格、日期、时刻、评分、产品承诺时，用该段 `refs` 引用真实资源编号；编号不出现在可见文案里。一般性建议或用户已明确的条件可用空数组。
- 不复抄整张资源表。班次等事实只引用能支持取舍的部分，不把顶部推荐换几个词再重复一遍。
- 对比必须同口径。7 到 8 小时与 10 小时只能说更短，不能说“快一半”；车程/飞行时间不等于门到门时间，票面展示价不等于完整出行成本。精确差额只从已返回且可比较的数值计算。
- 区分商家标注与已核实的承诺；“保进”“最低价”“评分最高”“适合情侣”等不因出现在标题或标签里就自动成为专家保证。
- 跨城市到站、接驳、行李、预约、营业时间和价格适用条件缺失时，明确说明影响，不凭常识补造车程、距离、库存或确定结论。
- “没说明”不等于“不包含”。税费、行李额没有明确信息时，写“下单前再确认是否包含税费、能带多少行李”，不能断言“不含税”“这家航司行李额更少”。不知道住址或交通方式时，不从起飞时刻倒推出“凌晨五点出门”“到市区已近午夜”；机场远近和位置方便程度也不能只凭机场名称断言。
- 解读必须解释同一份最终方案。发现方向/时间/选择冲突，先修正 plan 的 recommendations/days/summary，再写解读；不能在结尾另换主推或推翻前文。无法解决的关键限制应在推荐处也明示，不能埋在长文末尾。

## 表达示例

以下只示范语气，不是可直接套用的出行数据。正式回复中的事实仍须来自当次查询和对方的提问。

假设对方要找上海往返北京的低价机票，查到的组合去程 07:50 从浦东起飞、返程 22:55 到浦东，但还没有住址、机场交通和行李信息，可以这样写：

> 您想把往返票价控制得低一些，这组组合可以考虑，不过去程较早、回程也比较晚。我更建议您先看看这两个时段去机场和回家是否方便，再决定要不要选它。

标题：票价更低，但要早起出发、晚些回来

> 去程 07:50 从浦东起飞，需要早点到机场；返程 22:55 才回到浦东，落地后还要安排回家的交通。如果您不想回来得太晚，可以再比较白天抵达的班次。具体多花多少钱，以这次查到的备选为准。

标题：下单前再核对税费和行李

> 这次还没有查到完整的税费和行李说明，展示价也不能直接当作最后的付款金额。预订前请核对是否含税、能带多少行李，以及退改规则；如果您需要托运行李，再比较加上这笔费用后哪个更合适。

这些示例没有从时刻推算出门时间，也没有把“信息缺失”改写成确定事实。不模仿示例的航线、时刻或偏好，只学习直接回答、解释理由的方式。

## 排版与定稿

标题优先说清具体问题，例如“首日为什么只安排入住”“多花一点，能少换一次车吗”。每节先回答问题，不在标题后再加一句重复标题的空话；论据多时拆段。程序已有层级和留白，不要在段落里再套“结论：依据：建议：”的列表。

只提交纯文本段落与引用，不能生成 HTML、Markdown 表格、链接或编号。渲染器负责标题层级、留白、阅读宽度和行动清单；不要折叠、截断或省略详细解读。段落可充分展开，但不要用通用旅游常识凑字数。

写 plan 时只做一次静默核对：删掉重复、内部术语和第三人称报告口吻，确认没有改变价格、时间、地点、用户偏好和确定程度，并保证 summary、recommendations/days 与 interpretation 一致。核对必须和写 plan 在同一轮完成，不新增工具调用、复读轮次或渲染后润色。

这套检查只作用于专家新写的文案。全量资源区、接口原始介绍、名称、价格和预订链接一律保留，不能以“去 AI 味”为由删减或改写。
