# 快速比选契约

单项机票、火车、酒店、景点、汽车票和套餐比较用 selection；每日行程不用此契约。此页已包含简单查询所需字段，不必读通用契约。

## 决策只做一次

decisionFiles 的 selection-overview-v2 是首轮决策首页：comparisons 给出同组展示价、历时、评分和不同出到达站统计；journeyMix 给出直飞、中转、跨日与联运类型；hotelFacets 给出接口距离、评论数、星级及价格—距离非劣候选；transportFacets 给出出发时段、席别和明确库存。focusRows 是这些维度机械选出的代表候选，不是最终推荐。min/max 是返回数值统计，不是总费用或可订承诺；单位未返回、币种不同或日期不同不能混比。refs 仅列部分并列项，tiedCount 为并列总数，不能宣称“唯一最低”。

先检查用户硬条件，再围绕其目标从 focusRows 选通常2–3项：一项主推，确有不同取舍才加备选。若硬条件在首页没有字段或没有合适候选，才并行读取 candidateFiles，从全部候选中选择；不是每次都读。无需重新计算脚本已有结论，不逐条给全部资源写评价。不足以匹配的条件只说未知，必要时一批展开详情；证据够用就直接写plan并渲染，不再开一轮比较、长篇推演或润色。

事实来源必须分开：接口候选的价格、评分、时间和库存用真实 ref；用户口述的 600/450 等信息只能写“按您提供的报价”，不改写成实时展示价。不从评分差、星级差、价格高低或品牌名称推导卫生、服务、隔音、安静、亲子友好或整体品质；只有接口明确返回对应字段/标签时才可引用，且不升格成保证。

酒店“附近”只比较 hotelFacets.distanceMeters 已明确解析的单点距离，并先核对响应定位名称和距离参照点；区间距离及参照点不明仍视为未知。priceDistanceTradeoffRefs 仅表示价格和距离上没有被另一项同时压过，不等于综合排名。火车/汽车的 inventory 与 seatTypes 仅采信接口明确值；unknown 不作可订判断，0/无票不能推荐成“有票”。用户限定早晚时段时直接用 departureTimeBuckets，不再逐条扫描全表。

保存 plan.json：version=1；snapshotIds 为本次全部快照ID；mode=selection；userRequest 保留完整需求和已确认上下文（最多3000字）。summary 按回执 planLimits.summary：简单比选通常60–140字，复杂中转或混合资源通常140–260字，max 才是动态硬上限；普通直飞中个别航班次日到达不因此升级整轮复杂度，只在相应选择中提示。不要机械凑字或截断。recommendations 通常2–3项、最多5项，每项只有真实 ref 和 reason（通常20–60字、最多500字）。confirmations 默认为空；最终价格、余票、库存和退改规则已有统一提醒，不重复写。只有某一方案特有且会改变选择的风险才增加1项，复杂行程最多3项。各项仅 {text,refs}，refs为证据编号数组。rationales 可省略，不把同一段话写两遍。

只写结论、选择理由、解读和必要提醒，不生成MD、HTML、价格字段或链接。名称、价格、图片、预订入口由程序按ref绑定。所有文本为非空单行纯文本，不能含HTML或链接；不要用R1/R2代替可见名称。一个ref不重复推荐。

## 同一次分析，分成两种展示

simple-selection 不写 interpretation，程序会用 summary、推荐理由和必要提醒组成简短解读。complex-selection 有明显取舍时再写 interpretation，结构如下，不必再读其他契约：
- customerFocus：一两句接住您的需求和关键取舍，最多600字。
- sections：通常2–3节，每节仅 title（最多60字）和 paragraphs（1–3项 {text,refs}，每项最多700字）。每节回答一个具体问题，如多花钱换来什么、哪里需要换乘、哪种条件下改选备选。默认一节一个短段落；信息简单时一节即可，不凑栏目。硬上限6节。
- nextSteps：1–3项可执行的下一步 {text,refs}，硬上限5项、每项500字。会影响预订的关键限制还要放进 summary/reason/confirmations，不能只埋在HTML末尾。

复杂查询的解读通常合计120–260字，只解释实际取舍、代价和下一步；用户明确要求详细时再展开，8000字是硬上限，不是目标。提及资源事实的 refs 必须对应真实编号，每项最多20个；一般性建议可为空。说“您可以先比较这两个时段”，不要写“用户已明确”“本段应分析”“接口未返回”等内部报告口吻。用直接、完整的日常句子解释依据及代价，不复抄明细、编造经历或堆通用免责声明；“没说明”不能改写成“不包含”。

summary、推荐与需要的解读在一次计划中定稿，不能在解读里另换主推或推翻前文。HTML/完整MD使用 interpretation；聊天仅用 summary、推荐表和特有提醒。不要为了写解读重读证据、重新查询或开第二轮润色。

先检查用户硬条件，再比较实际取舍：
- 城市/方向/日期要一致；联运必须看各段交通与中转，不能称为直飞。未知接驳不保证赶得上。
- journeyMix.noDirect=true 时，summary 和关键提醒必须直说本次没有直飞，并说明返回的是哪些中转类型；不要自动扩大成高铁查询。只有用户询问交通方式比较时走 traffic-query，或在最终结果里提供“可继续查高铁对照”的可选下一步。
- 预算要核对币种、计价单位和日期；展示价不是总费用。位置要核对真实距离与参照点，同城不等于附近。
- 不擅自增加偏好，不把商家宣传当保证。字段缺失不是条件已满足；影响选择的长文节选按ref定向展开一次。
- 全部候选都不合适时，recommendations=[]，summary说明原因，confirmations给出下一步；不为凑数量推荐超预算或位置不符的资源。
- 没有可推荐的候选时，可省略 interpretation，直接说明哪些条件未满足。用户要求更深入比较时才参考[自然解读](expert-interpretation.md)，不重复加载已知字段规范。

示例只示范结构，不套用日期或假定偏好：

```json
{
  "version": 1,
  "snapshotIds": ["本次完整snapshotId"],
  "mode": "selection",
  "userRequest": "已确认日期，想找便宜的航班。",
  "summary": "这班展示价较低，可以先比较它的出发时段是否方便。",
  "recommendations": [{"ref": "真实资源ref", "reason": "票价在这次可比结果中较低；前往机场的交通还需结合您的位置确认。"}],
  "confirmations": []
}
```

程序生成精选聊天MD及全量HTML/MD文件，推荐不是完整产物的过滤器。保存plan后渲染一次；报错只修正相关字段一次，不循环扩写、重新取数或全文交付校验。
