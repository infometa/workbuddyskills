# 摘要与汇总方法论（summarization）

> 解决"怎么把原文/多篇报道压缩成可靠摘要"的问题。资讯汇总的核心能力，但它是**纯语义任务**——由 LLM 直接完成，不写脚本（抽取式脚本质量远不如生成式理解）。本文是做这件事的判断标准与红线。

## 一、第一原则：不失真

摘要的唯一底线是**不改变原意**。压缩可以丢"细节"，但绝不能丢/改"语义"：

- **保留关键限定词**：「可能/计划/已经/拟/或将」语义天差地别。"OpenAI 计划发布"≠"OpenAI 已发布"。
- **不夸大、不弱化**：原文"小幅下调"不能写成"暴跌"；"部分用户反馈"不能写成"用户普遍不满"。
- **不补全因果**：原文只说"A 和 B 同时发生"，不要擅自写成"A 导致 B"。
- **存疑保留存疑**：原文用"据称/有消息称"，摘要也要保留这个不确定性，不能变成肯定陈述。

## 二、倒金字塔结构（单条摘要）

新闻摘要按重要性降序排列，最关键的先说：

```
第1句：核心事实（谁 + 做了什么 + 结果）——这一句单独拎出来也成立
第2句：关键数据/影响（数字、规模、波及范围）
第3句：背景/补充（为什么、下一步）——可省
```

> 读者只看第一句也能抓住要点；越往后越是可省的细节。

## 三、关键信息保全清单（压缩时一个都不能丢）

| 类型 | 例 | 为什么不能丢 |
|------|----|------------|
| **数字** | 金额、涨跌幅、数量、占比 | 新闻的硬事实，丢了等于没说清 |
| **时间** | 何时发生/生效 | "今天"和"下月"决定时效价值 |
| **当事方** | 谁做的、涉及谁 | 主体错位是严重失真 |
| **地点/范围** | 全球 vs 中国、全行业 vs 某公司 | 范围口径影响判断 |
| **关键限定** | 计划/已经、可能/确定 | 决定事实的确定性 |

## 四、分层摘要（一鱼三吃，对应不同呈现位）

同一条新闻按使用位置给不同长度——避免每处都现写：

| 层级 | 长度 | 用在哪 |
|------|------|--------|
| **一句话版** | ≤25 字，只留核心事实 | 简报分类表格的标题/摘要列 |
| **三句话版** | 倒金字塔三句 | 🔥头条卡、重点条目 |
| **段落版** | 3-5 句，含背景 | 用户要"展开说说某条"时 |

## 五、多篇聚合成一条（汇总的难点）

同一事件有多个来源时，**不是把几条摘要拼起来，而是融合成一条更完整、更可靠的**：

```
1. 识别"同一事件"：标题/主体/时间高度重合的归为一组
2. 取交集做骨架：多源都提到的事实 = 高置信核心，作为主干
3. 补差集做细节：某源独有的细节，标明来源后补充（如"据 X 报道，还涉及…"）
4. 冲突并列：数字/说法矛盾时，并列各方（见 cross-verification.md），不取平均、不和稀泥
5. 合并来源：聚合条目的来源列出全部（"综合 路透、财新"），链接保留多个
```

> **反面教材**：把 3 篇各自的摘要简单堆叠 → 重复啰嗦、还可能把矛盾信息当成都对。

## 六、摘要的红线（呼应 news-redlines.md）

- **摘要 ≠ 原文**：摘要是我的概括、可能有偏差，**引用原话/关键数字时必须回原文核对**，不凭摘要直接当原文引用。
- **不脑补**：原文没有的信息（背景、原因、影响）不要靠"常识"补进摘要。
- **不带立场**：客观转述，不在摘要里夹带评价、褒贬、倾向。
- **二手摘要不叠加**：aihot 的 `summary`、WebSearch 的结果片段本身已是二手概括，不要在它基础上再概括（误差累积）——要做精确摘要就回 `url` 读原文。

## 七、为什么不做 summary 脚本（设计决策记录）

- 摘要是**生成式语义任务**，LLM 的本职，质量远高于"按词频抽句子"的抽取式脚本。
- 写脚本 = 用更差的工具替代更强的能力，违背家族"脚本做客观计算、LLM 做语义判断"的哲学。
- 多篇去重聚类虽有一点"可复现"成分，但新闻数据量小、直接读即可，写脚本收益低、增维护点——不做。
