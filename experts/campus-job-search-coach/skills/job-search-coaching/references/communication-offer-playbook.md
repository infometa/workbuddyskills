# 求职沟通与 Offer 比较

## 一、沟通成稿

### 最少必要信息

- 沟通对象
- 沟通目的
- 已发生的事实
- 希望对方采取的动作

适用于投递、内推请求、面试确认或改期、面试后感谢、询问进展、补充材料、接受或婉拒 Offer。

用户明确要快速成稿时，使用方括号占位符直接生成。对象、目的、事实和期望动作都不明确时，只先问沟通目的，其余信息后补。

### 输出模板

```markdown
主题：

正文：

需要替换：
- [姓名]
- [岗位]
- [时间]

发送前检查：
- 事实准确
- 收件人正确
- 附件已添加
- 没有不必要的隐私信息
```

### 表达规则

- 首段说明身份和目的。
- 中段只写与当前请求有关的事实。
- 结尾给出明确、礼貌的下一步。
- 不虚构推荐关系、紧急事项或竞争 Offer。
- 不使用威胁、连续施压、骚扰或绕过拒绝的表达。

## 二、Offer 信息分层

| 层级 | 示例 | 比较处理 |
|---|---|---|
| 书面确定 | Offer 邮件、合同或正式制度明确写明 | 可直接进入事实表；满足量表条件时可评分 |
| 官方可核验 | 公司官网、员工手册或招聘方正式说明 | 标明来源和日期后进入比较 |
| 口头承诺 | 晋升、转正、奖金、调岗、培养安排 | 单列，不视为保证；默认不作为高分依据 |
| 用户估计 | 通勤、生活成本、工作感受 | 标为估算；可进入个人情景，不写成公司事实 |
| 待确认 | 工作地点、加班、团队归属、合同主体 | 不评分，生成向 HR 确认的问题 |
| 个人偏好 | 城市、方向、稳定性、节奏、家庭安排 | 用于确定维度和权重，不伪造成客观事实 |

## 三、比较维度

默认从以下维度中选择与用户实际相关的 4—8 项，不为凑表格强行全部使用：

- 固定薪酬、奖金、补贴和福利
- 岗位内容与长期方向匹配
- 学习成长、导师和培养机制
- 团队与业务的已知稳定信息
- 工作地点、通勤和生活成本
- 工作时间、出差和加班要求
- 试用期、转正条件和合同主体
- 个人兴趣、家庭安排和其他硬约束

## 四、先定性，后评分

### 允许评分的条件

只有同时满足以下条件时，才进入数值评分：

1. 用户明确希望量化比较，或接受量化结果；
2. 两个 Offer 在该维度上都有可比信息；
3. 每个分值都能引用书面事实、官方信息或用户确认的个人感受；
4. 量表锚点与用户的最低要求、目标和理想状态已经明确；
5. 用户已核对各维度的初始分值；
6. 如使用加权结果，权重由用户明确给出或确认等权。

任何一项不满足，默认只做定性比较。未知项不是 0 分，也不是 3 分，必须记为 `null` 并单列。

### 通用 1—5 分锚点

| 分数 | 含义 | 使用条件 |
|---:|---|---|
| 1 | 明确违反用户硬约束或存在已确认的重大不利 | 必须有具体事实，不因“没信息”打 1 分 |
| 2 | 低于用户已确认的可接受基线 | 能说明差距在哪里 |
| 3 | 达到基本可接受水平，但无明显优势 | 用户认可该基线 |
| 4 | 明显符合用户优先目标 | 有具体事实或用户确认支撑 |
| 5 | 达到用户理想状态且证据充分 | 不能仅凭口头承诺给 5 分 |
| `null` | 信息不足或不可比 | 不参与计算，必须列入待确认项 |

### 维度锚点补充

| 维度 | 1 分示例 | 3 分示例 | 5 分示例 |
|---|---|---|---|
| 薪酬 | 书面固定部分低于用户硬性底线 | 达到用户可接受目标 | 书面固定部分和可核验福利达到理想目标 |
| 岗位匹配 | 核心职责与目标方向冲突 | 职责基本可接受 | 核心职责与长期方向高度一致且边界清楚 |
| 成长支持 | 已确认缺少必要支持或机制 | 有基本学习空间 | 有明确导师、培养机制和可核验成长路径 |
| 稳定信息 | 有已确认的重大风险信号 | 已知信息中性、无明显优势 | 业务和团队安排清楚，关键条件有正式依据 |
| 城市生活 | 违反家庭、城市或通勤硬约束 | 成本和通勤可接受 | 高度符合城市、生活成本和家庭安排 |
| 工作节奏 | 已确认违反用户健康或时间硬约束 | 工作时间和出差可接受 | 节奏、弹性和出差要求符合用户理想状态 |
| 合同条件 | 已确认存在重大不利且用户不能接受 | 核心条款基本可接受 | 主体、试用期、转正和关键条款清楚且有利 |

没有证据时使用 `null`，不得把“未发现问题”等同于 3 分或 5 分。合同条件评分只反映用户已确认的接受程度，不构成法律意见。

## 五、确定性计算规则

### 权重

- 用户未给权重时，先做等权定性比较，不直接输出数值总分；必须明确说明“等权只是中性基线，不代表你的真实偏好”。
- 用户确认采用等权评分时，可将所有纳入维度设为相同权重并运行脚本。
- 用户只给高/中/低优先级时，继续做情景比较，不擅自换算为精确百分比。
- 用户明确给出数值权重时，按其权重运行脚本；有效权重之和必须大于 0。

### 未知项与覆盖率

- 任一 Offer 的 `null` 项不进入总分，不能按 0 分、3 分或其他默认值处理。
- 为防止不同 Offer 因可评分维度不同而失真，**最终排序只使用所有 Offer 都有有效分值的共同维度**。
- 共同维度覆盖率 = 共同有效维度的权重之和 ÷ 全部维度权重之和。
- 覆盖率低于 60%：不输出排序，只输出待确认清单。
- 覆盖率 60%—79%：允许给低置信度倾向，不下确定结论。
- 覆盖率 80%—94%：输出中置信度比较。
- 覆盖率不低于 95%：可输出高置信度比较，但仍不替用户做决定。

### 分差解释

归一化总分按 0—100 展示：

- 分差小于 5：视为接近，不宣称明显优胜；转为比较关键情景和不可逆风险。
- 分差 5—10：仅说明在当前权重下略占优。
- 分差大于 10：可说明在当前权重和已知证据下优势较明显。

分差结论必须同时显示覆盖率、共同维度和待确认项。评分与计算使用 `scripts/offer_score.py`，模型不得心算后伪装为脚本结果。

脚本输入使用 UTF-8 JSON，格式如下：

```json
{
  "offers": ["Offer A", "Offer B"],
  "dimensions": [
    {
      "name": "薪酬",
      "weight": 30,
      "scores": {"Offer A": 4, "Offer B": 3}
    },
    {
      "name": "成长",
      "weight": 20,
      "scores": {"Offer A": null, "Offer B": 4}
    }
  ]
}
```

运行方式：

```bash
python3 scripts/offer_score.py /path/to/input.json
```

脚本只负责校验和计算；分值与权重必须先由用户确认。

## 六、决策流程

1. 汇总两份 Offer 的书面事实、官方信息、口头承诺、估算和待确认项。
2. 先按同一维度做定性对比，不急于评分。
3. 请用户指出硬约束和三项最重要因素；若用户只要快速初评，可先给等权定性结果。
4. 满足评分条件时，按锚点提出初始分值，并逐项展示依据，请用户确认或修正。
5. 权重和分值确认后，用脚本计算共同维度、覆盖率、归一化得分和分差。
6. 对接近方案做情景比较：成长优先、现金流优先、城市优先或风险厌恶。
7. 输出当前倾向、成立条件、关键风险和向 HR 确认的问题。

## 八、风险与转介

- 合同、竞业、违约、签证、税务和劳动争议：只整理问题，不给确定法律结论。
- 要求先转账、购买培训、缴纳保证金或交出账号凭证：停止普通比较，提示招聘诈骗风险。
- 要求扣押身份证、毕业证原件或使用私人账户收款：建议保存证据并联系学校就业部门、招聘平台或警方。
- 涉及重大权益时，建议向招聘方获取书面确认，并咨询学校就业中心或专业法律人士。
