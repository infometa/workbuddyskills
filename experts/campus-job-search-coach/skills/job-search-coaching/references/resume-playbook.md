# 岗位拆解与可追溯简历优化

## 一、任务模式

先识别用户要完成的任务，不用同一套流程处理所有简历请求：

| 模式 | 典型输入 | 核心交付 |
|---|---|---|
| 生成 | 没有成型简历，只有经历素材 | 事实草稿、缺口问题、首版结构 |
| 岗位定制 | 有 JD + 简历或经历 | 岗位摘要、证据映射、定向改写、待确认项 |
| 通用改写 | 有简历，无具体 JD | 清晰度、证据、结构和一致性优化 |
| 诊断 | 用户只问匹配和问题 | 只读诊断，不改写原文 |
| 单条细修 | 一条经历或一段反馈 | 2—3 个候选版本、改写动作、一个关键追问 |
| 双语改写 | 需要中文和英文版本 | 在相同事实骨架上分别按招聘语境改写，不做逐句直译 |

所有模式先读用户已给材料。用户明确只要快速成稿时，可直接交付带占位符的初稿；不强制一次问完模板、长度和语言。从零制作完整应届生或实习简历时，同时读取 `graduate-resume-playbook.md`，由后者决定模块选择、应届生顺序、文件结构、排版与导出。

## 二、输入状态

| 状态 | 条件 | 处理 |
|---|---|---|
| 完整 | 有目标岗位或 JD，有简历正文或具体经历 | 直接拆解和改写 |
| 可用 | 有岗位名称但没有完整 JD，或只有部分经历 | 先完成可支持部分，并标待确认项 |
| 定位辅助 | 有简历或经历，但没有目标方向 | 提取两至三个可能方向和依据，再只问一个偏好或限制 |
| 阻塞 | 没有目标方向，也没有任何经历材料 | 只问当前最想解决的一个问题 |

原始简历、PDF、Word 或 Markdown 文件一律视为只读底稿，不覆盖原文件。文本提取有错位、乱码或水印时，先让用户确认关键字段；扫描图片无法可靠读取时请用户粘贴文本，不基于猜测改写。

## 三、岗位要求与证据映射

从 JD 中提取：岗位名称、业务方向、核心职责、必备条件、加分项、关键词、可能的证据类型和待核验字段。需要“是否值得投”或量化覆盖时，转用 `application-decision-playbook.md`。

为每项核心要求建立映射：

| 岗位要求 | 用户真实经历 | 证据 | 匹配类型 | 处理 |
|---|---|---|---|---|
| 直接经验 | 明确做过同类任务 | 成果、过程或材料 | 直接匹配 | 优先呈现 |
| 相邻经验 | 做过相似任务 | 可说明迁移关系 | 可迁移 | 克制改写 |
| 当前材料未体现 | 用户未提供相关经历 | 无 | 缺口 | 不虚构，列为提升项 |

## 四、单条经历改写

### 事实骨架

按以下顺序组织，但不强制每条都写满：

1. 用户本人承担的动作或责任；
2. 使用的方法、工具、协作或关键取舍；
3. 真实结果、证据或影响；
4. 与目标岗位相关的表达。

有真实数字时可用“成果—指标—行动”结构；没有数字时优先写清动作、范围、频率、交付物、复用或反馈，不为了“量化”制造空白百分比。确有关键数据需要用户补充时使用明确占位符，例如 `[请补充覆盖人数]`，并集中列入待确认项。

### 合法改写动作

每条关键改写至少标明一种动作：

| 动作 | 允许范围 | 风险 |
|---|---|---|
| 口语转书面 | 不改变事实，只提高可读性 | 低 |
| 合并或拆分 | 合并重复内容或拆分长句 | 低 |
| 调整顺序 | 把最相关的真实信息前置 | 低 |
| 对齐术语 | 用户事实与 JD 术语确实对应时采用其表达 | 中 |
| 补充上下文 | 补充原素材中已有的方法、范围或条件 | 中 |
| 语气升级 | “参与”改成“负责/主导/牵头”等 | 高，默认禁止；只有用户明确确认角色后才可用 |
| 推断缺失细节 | 补技术栈、规模、职责、合作方或结果 | 高，禁止写入终稿 |

## 五、逐条来源追溯

关键改写采用轻量追溯卡，不要求建立长期数据目录：

```markdown
### 经历条目
原文：
建议改写：
改写动作：口语转书面 / 调整顺序 / 对齐术语 / ……
事实依据：引用用户哪一段材料
风险：低 / 中 / 高
需用户确认：数字、个人贡献、工具、范围或结果口径
```

### 风险判定

- **低**：只做书面化、拆分、合并或顺序调整。
- **中**：加入了原素材中的技术上下文、岗位术语或更强动词，需要用户确认表达是否准确。
- **高**：新增数字、技术栈、项目、职级、团队规模、客户、时间跨度，或把“参与”升级为“主导”。高风险内容不得直接进入终稿。

可使用 `scripts/resume_claim_audit.py` 对原文与候选改写做确定性风险检查。脚本只检测新增数字、角色升级词、占位符和明显模板化表达，不替代语义判断。脚本返回码 `1` 表示发现高风险项、需要用户复核，不代表脚本运行失败；返回码 `0` 表示未发现高风险表层差异。

## 六、三种阅读视角

同一份简历不必生成三个版本，但交付前要从三种视角检查：

### 1. ATS 可解析性

- 使用标准节标题和清晰单列结构；
- 联系方式使用文本，不放在图片、页眉或复杂表格中；
- 日期格式统一；
- 只加入用户真实具备的关键词；
- 不承诺 ATS 通过，不把关键词次数当工业标准。

### 2. 招聘者快速扫读

- 顶部定位、最近且相关的经历是否一眼可见；
- 每段前两条是否优先展示与岗位最相关的真实证据；
- 不相关内容是否适当压缩；
- 是否避免大段空泛职责和重复动词。

### 3. 面试追问安全

- 每个数字能否说明来源和口径；
- “我”与“我们”是否分清；
- 技术、方法、角色和结果是否经得住追问；
- 是否保留 1—2 个用户确实能展开的细节，而不是制造华丽但不可回答的钩子。

## 七、双语改写

中文与英文版本共享事实骨架，但不是逐句翻译：

- 英文版使用英文招聘环境常见的节标题和简洁动词；
- 不自动加入年龄、性别、照片、婚姻等与岗位无关的敏感信息；
- 中文材料中的“吃苦耐劳、服从安排、能加班”等不直接翻成英文简历卖点；
- 两版的公司、日期、数字、职责和结果必须一致。

## 八、完整交付结构

1. 岗位能力摘要或简历诊断结论；
2. 匹配优势与主要缺口；
3. 逐条追溯卡；
4. 可直接替换的简历内容；
5. ATS 可解析性与人眼扫读检查；
6. 事实核验清单；
7. 三项以内补强行动。

完整简历制作额外交付“模块取舍说明”和完整正文；用户要求文件时，按 `graduate-resume-playbook.md` 生成 Markdown、HTML，并在明确要求且环境可用时生成 PDF。

单条细修只输出候选改写、改写动作、风险和一个关键追问，不生成不必要的完整报告。

## 九、事实禁区

以下内容没有用户明确确认时不得新增：

- 学校、学历、专业、成绩和排名；
- 公司、组织、职位和任职日期；
- 项目规模、用户量、收入、增长率和效率提升；
- 技能熟练度、技术栈、证书、奖项和语言能力；
- 团队规模、管理职责和决策权限；
- 客户、合作方、推荐关系、Offer 和背调材料；
- 姓名、电话、邮箱、微信、住址等个人联系信息。

数字无法说明来源时，删除精确值、改为有依据的事实描述，或标为待确认。禁止根据行业平均值、常见项目或“看起来合理”补数。

## 十、停止条件

- 用户要求编造经历、数据、证书或推荐关系：拒绝并改为真实经历挖掘。
- 用户提供身份证件、住址、私人联系方式或未公开公司材料：提醒脱敏后再处理。
- 用户要求保证通过筛选或 ATS：说明无法保证，转为检查证据覆盖、可解析性、清晰度和事实一致性。
- 用户要求覆盖或删除原始简历：不执行，改为生成独立候选版本。
