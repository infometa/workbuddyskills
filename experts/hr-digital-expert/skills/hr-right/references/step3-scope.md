## ✅ 执行检查点（步骤三开始前必读）

- **入口条件**：步骤二已声明完成（删除场景跳过本步骤）
- **禁止动作**：禁止用 `ask_followup_question` 询问"维度名是什么"、"维度值编码是什么"、"BBS AI 审核的编码是多少"等本应由本步骤 SQL 自动获取的信息
- **必须动作**：⓪ 维度名称解析 → ① 语义匹配码值 → ② 必选维度瀑布式默认值填充 → ③ 非必选维度不赋值 → ④ 期限识别
- **完成声明**：执行完毕后向用户简述：「步骤三完成：识别到角色分工维度 X 个、权限包必选控权维度 Y 个；期限 = ZZZ」
- **必选维度绝不留空**：角色分工维度全部必填；权限包必选维度即使用户未明确说明，也必须走瀑布式填充得到具体码值（如"全部"、"全公司"），禁止留空待用户填写

输入：步骤一锁定的角色/权限包的维度 + 用户原始需求

**维度必填性判定规则**：
- **角色分工维度**（`role_division_dim`，来源于 `ai_role_def` 表的 `role_division_dim` 字段）：角色的分工维度**全部视为必填维度**。当从用户需求中无法提取到角色分工维度的码值时，必须按照下方"② 瀑布式默认值填充"的逻辑进行填充
- **权限包控权维度**（`pkg_ctrl_dim`，来源于 `ai_role_rightpackage` 表）：区分必选（`pkg_required_ctrl_dim`）和可选（`pkg_optional_ctrl_dim`）。必选维度未匹配到时走"② 瀑布式默认值填充"；可选维度未匹配到时走"③ 不赋值"

> **注意**：上述维度名称（如"组织"、"工作地"等）在本文档中仅为举例，实际维度类型名称以 `v_ai_data_scope` 表的 `dim_type_name` 字段为准。查询维度码值时，应使用 `v_ai_data_scope` 中实际存储的 `dim_type_name` 值进行匹配。

## ⓪ 维度名称解析（前置步骤，在①②③之前执行）

角色/权限包中记录的维度名称（如 `role_division_dim`、`pkg_ctrl_dim`、`pkg_required_ctrl_dim`、`pkg_optional_ctrl_dim` 字段中的值）**可能与 `v_ai_data_scope` 中的 `dim_type_name` 不完全一致**（例如权限包中写"合同地"，但 `v_ai_data_scope` 中实际名称为"合同公司所在地"；权限包中写"组织"，但实际名称为"组织范围"）。

因此，在执行步骤①②③之前，必须**先将所有维度名称解析为 `v_ai_data_scope` 中的实际 `dim_type_name`**，后续所有查询均使用解析后的实际名称。

**解析流程**（对每个待处理的维度名称逐一执行）：

1. **精确匹配**：在 `v_ai_data_scope` 中查询 `dim_type_name` 与维度名称完全相同的记录
```sql
SELECT DISTINCT dim_type_name, dim_type_code FROM v_ai_data_scope
WHERE dim_type_name = '{维度名称}' LIMIT 1
```
2. **模糊匹配**：若精确匹配无结果，改用 `LIKE` 模糊搜索
```sql
SELECT DISTINCT dim_type_name, dim_type_code FROM v_ai_data_scope
WHERE dim_type_name LIKE '%{维度名称}%' LIMIT 10
```
若返回多个结果，选择名称最短（最简洁）的作为匹配结果
3. **反向模糊匹配**：若仍无结果，尝试用维度名称作为被搜索对象
```sql
SELECT DISTINCT dim_type_name, dim_type_code FROM v_ai_data_scope
WHERE '{维度名称}' LIKE CONCAT('%', dim_type_name, '%') LIMIT 10
```
4. **解析失败兜底**：若以上三步均无结果，在最终输出中标注该维度为 `⚠️ 维度名称未在码值表中找到对应类型，需人工确认`

> **解析示例**：
> - `pkg_ctrl_dim` 中写 "合同地" → 精确匹配无结果 → 模糊匹配 `LIKE '%合同地%'` → 命中"合同公司所在地"（`contractCompany_place`）→ 后续使用 `dim_type_name = '合同公司所在地'` 查询码值
> - `role_division_dim` 中写 "组织" → 精确匹配无结果 → 模糊匹配 `LIKE '%组织%'` → 可能命中多个（"组织范围"、"BG组织"、"限制组织(薪酬)"等）→ 选择名称最短的"组织范围"（`Org`）

## ① 从需求语义中匹配维度码值

从用户需求中提取维度相关的关键词，到 `v_ai_data_scope` 维度明细数据表中匹配码值。**查询时使用步骤⓪解析后的实际 `dim_type_name` 和 `dim_type_code`，不能直接使用角色/权限包中记录的原始维度名称。**

**组织维度智能补全规则**：当需求中提到的组织名称为**部分名称**（如"KAIROS中心"、"通途数据中心"、"腾讯会议产品部"）时，需执行以下组织路径补全流程：

> 💡 **前置：获取申请人组织全路径**（仅在本步骤首次进入组织维度匹配时执行一次，缓存至整次会话结束）：
> - 调用 `hr-auth-copilot` MCP 的 `query_session_user` 命令（无需传参）获取当前登录用户的组织全路径，记为 `applicantOrgPath`（形如 `腾讯/CSIG云与智慧产业事业群/云产品一部/XX中心/XX组`）
> - 若 `query_session_user` 调用失败或返回为空，记 `applicantOrgPath = null`，后续匹配跳过与申请人组织路径相关的优先级规则
> - **用途**：仅用于多结果时按"前缀最长公共匹配"择优，绝不用于直接填充组织范围（避免误把申请人自身组织当作申请范围）

1. **精确匹配**：先用需求中的组织关键词在 `v_ai_data_scope` 中按 `dim_item_name` 精确匹配。组织维度的 `dim_type_name` 以 `v_ai_data_scope` 实际存储为准（如可能是"组织范围"而非"组织"），建议先查询 `SELECT DISTINCT dim_type_name FROM v_ai_data_scope WHERE dim_type_name LIKE '%组织%'` 确认实际维度名
2. **模糊匹配**：若精确匹配无结果，改用 `LIKE '%关键词%'` 对 `dim_item_name` 进行模糊搜索
3. **全路径搜索**：若仍无结果，改用 `LIKE '%关键词%'` 对 `dim_item_full_name` 进行模糊搜索
4. **同义词扩展**：若仍无结果，参考 `hr-glossary.md` 中的组织术语同义词映射（如"腾讯会议"→"腾讯会议产品部"），用扩展后的名称重复步骤1-3
5. **结果选取**：
- 若匹配到**唯一结果**：直接采用其 `dim_item_full_name` 作为组织全路径码值
- 若匹配到**多个结果**，按以下优先级**逐级筛选**（前一级能唯一定位则直接采用，不进入下一级）：
  1. **需求原文包含上级组织线索优先**：若需求中同时包含上级组织关键词（如"CSIG通途数据中心"中的"CSIG"、"TEG AI Infra部"中的"TEG"），在多个结果中优先选择 `dim_item_full_name` 包含该上级组织关键词的候选
  2. **🆕 与申请人组织路径前缀最长公共匹配优先**：当 `applicantOrgPath` 非空时，计算每个候选 `dim_item_full_name` 与 `applicantOrgPath` 的**前缀最长公共路径长度**（按 `/` 分段逐级比较），取最长者；若存在并列最长者，保留到下一级
     - 例：`applicantOrgPath = "腾讯/CSIG/云产品技术支持部/安灯产品中心/运营组"`，候选 A=`"腾讯/CSIG/云产品技术支持部/安灯产品中心/产品策划组"`（公共前缀 4 级） vs 候选 B=`"腾讯/WXG/搜索产品部/产品策划组"`（公共前缀 1 级） → 取 A
  3. **层级最短**：上述规则仍未唯一时，选择 `dim_item_full_name` 层级最短（路径分段数最少）的候选
- **🆕 若上述三级筛选后仍有多个候选**：**不强制要求用户输入全路径**，而是主动列出 **Top 3 候选**的完整全路径 + 码值，询问用户确认：
  > "系统中存在多个同名组织，请确认您指的是哪一个：
  >   1. 腾讯/CSIG/云产品技术支持部/安灯产品中心/产品策划组 (code: 26170)
  >   2. 腾讯/WXG/搜索产品部/产品策划组 (code: 30989)
  >   3. 腾讯/TEG/基础架构部/产品策划组 (code: 31118)
  > 请回复序号或直接粘贴所指组织的全路径。"
  - 用户回复后按其选择采用对应结果
  - 在用户明确选择前，**不得擅自填充任何一个候选作为组织范围**
6. **输出**：若步骤1-5中**任意一步匹配到唯一结果或用户确认了选择**，直接采用该结果的 `dim_item_full_name`（全路径名称）和 `dim_item_code`（码值）
7. 若步骤1-5**均未匹配到任何结果**，直接走下方②瀑布式默认值填充

> **核心原则**：组织维度优先级为 **① 语义匹配（含申请人路径辅助）> ②  瀑布填充**。绝不能跳过匹配直接用用户原始描述作为组织范围；也**绝不能以"用户没提供全路径"为由终止匹配**——多候选场景应按上述规则自动收敛或主动询问。

**其他维度匹配规则**：对非组织维度（如工作地、员工子类型、管理主体等），同样先用 `dim_item_name` 精确匹配，无结果再用 `LIKE` 模糊匹配。特别注意：
- 需求中的"海外"关键词，需匹配相应维度的具体码值（如合同地/工作地中的"亚太"、"美洲"、"欧洲"、"中东及非洲"等区域码值）

## ①-A 地域类维度（工作地/合同地）三级码表细化解析

**适用范围**：当待匹配的维度为**工作地**或**合同公司所在地（合同地）**等具有**树形层级结构的地理区域维度**时，执行以下专用解析逻辑。

> ⚠️ **核心硬性约束**：
> - **所有地域节点的 `dim_item_code` 与 `dim_item_name` 必须从 `v_ai_data_scope` 实时查询得到，严禁直接硬编码**（即使本文档下方的"语义映射提示规则"中举例了 `"AP"`、`"NA"` 等编码，也仅为说明示意，实际使用时必须查询码表确认拼写、大小写、层级关系）
> - 码表会变化（新增国家/地区、改名等），任何硬编码都会过期
> - 本节下方的层级结构示意、语义映射表均作为"提示规则"帮助 AI 理解用户语义，**最终落到 JSON 的 `dimItemCode` / `dimItemName` 必须以即时查询结果为准**

**码表层级结构（仅作示意，实际层级以 `v_ai_data_scope` 当时数据为准）**：

> 此类维度的码表通常为 **四级树形结构**：
> ```
> L1 全部
> └── L2 大洲/区域（如 中国大陆 / 亚太 / 美洲 / 欧洲 / 中东及非洲 等）
>     └── L3 国家/地区（如 美国 / 日本 / 阿联酋 等；港澳台通常归在亚太下）
>         └── L4 城市
> ```
> 实际有几级、各级名称、各节点的父子关系，**均需通过下方步骤 2 的 SQL 查询动态获取**。

**解析流程**：

1. **识别地域类维度**：当步骤⓪ 解析后的 `dim_type_name` 属于以下名称之一时（或通过模糊匹配命中），进入本子流程：
- `工作地`、`WorkLocation`、`WorkPlace`、`工作地点`
- `合同公司所在地`、`合同地`、`ContractLocation`、`contractCompany_place`

2. **强制：查询该维度的完整树形结构**（每次匹配前必须执行，不可跳过）：
```sql
SELECT dim_item_code, dim_item_name, dim_item_parent_code, dim_item_full_name
FROM v_ai_data_scope
WHERE dim_type_code = '{步骤⓪解析后的dim_type_code}'
ORDER BY dim_item_full_name
```
通过 `dim_item_parent_code` 字段构建父子关系树，确定 L1(全部) → L2(大洲/区域) → L3(国家) → L4(城市) 的层级映射。**后续所有 dimItemCode / dimItemName 必须取自此查询结果**。

3. **语义关键词 → 码表节点映射（提示规则）**：

> ⚠️ **本表仅为"语义提示规则"**，帮助 AI 理解用户的自然语言描述应该映射到码表的哪一层。**最终输出的 `dimItemCode` 与 `dimItemName` 必须在步骤 2 的查询结果中找到对应记录**——若码表中名称与下表略有差异（如"Asia Pacific" vs "亚太"），以**码表实际值为准**。

| 用户需求中的常见表达 | 应映射到的码表层级 | 处理说明 |
|---|---|---|
| **APAC / APAC地区 / 亚太地区 / 亚太** | L2 区域级 | 在步骤 2 结果中查找 `dim_item_name` ≈ "亚太" 的 L2 节点（即 `dim_item_parent_code` 指向 L1 "全部"），取其 `dim_item_code` |
| **亚太不含港澳台 / 亚太（除港澳台）** | L3 国家集合 | 取上述 L2 "亚太" 节点的全部 L3 子节点，**剔除** `dim_item_name` 含"香港/澳门/台湾"的子节点 |
| **美洲 / 欧洲 / 中东及非洲 / MEA** | L2 区域级 | 同上，分别在步骤 2 结果中按名称查找对应 L2 节点 |
| **所有海外国家 / 全球海外 / 全球除大中华区 / 全球除中国大陆 / 海外全部** | L2 区域集合 | 取所有非"中国大陆"的 L2 节点（通常是 亚太 + 美洲 + 欧洲 + 中东及非洲 等）；**排除"中国大陆"整棵子树**；若用户未明说排除港澳台，"亚太"通常保留 |
| **全球除大中华区且除港澳台 / 全球除中国（含港澳台）** | L3 国家集合 | 取所有非"中国大陆"的 L2 节点，并将"亚太"展开为 L3 节点后剔除港澳台 |
| **具体国家名**（如"美国"、"日本"、"阿联酋"） | L3/L4 节点 | 在步骤 2 结果中精确/模糊匹配 `dim_item_name` 或 `dim_item_full_name`，取对应节点的 `dim_item_code` |
| **常识性区域名**（如"东南亚"、"中东"、"北欧"） | L3 国家集合 | 按常识展开（东南亚 ≈ 新加坡+泰国+马来西亚+印尼+菲律宾+越南；北欧 ≈ 瑞典+挪威+丹麦+芬兰+冰岛 等），然后**逐个**在步骤 2 结果中验证存在性，**未找到的国家需向用户提示** |

4. **多关键词组合处理**：
- 若用户需求同时提及多个地域范围（如"APAC 和欧洲"），则取**并集**
- 若用户需求同时包含包含和排除（如"所有海外国家但排除美国"），则先取全集再排除指定节点
- 若用户需求中出现矛盾描述（如既说"APAC"又说"仅欧洲"），向用户追问确认

5. **输出格式**：地域类维度最终输出为一个 `items` 数组，每个元素对应一个**步骤 2 查询结果中实际存在**的 L2 或 L3 节点：

```json
{
  "dimTypeCode": "<来自步骤⓪>",
  "dimTypeName": "<来自步骤⓪>",
  "items": [
    { "dimItemCode": "<来自步骤2查询结果>", "dimItemName": "<来自步骤2查询结果>" },
    { "dimItemCode": "<来自步骤2查询结果>", "dimItemName": "<来自步骤2查询结果>" }
  ]
}
```

> **关键要求**：
> - `dimItemCode` **必须是步骤 2 查询返回的真实编码**，不能凭印象写（即使本文档其他地方出现过类似 `"AP"`、`"NA"` 等示例编码，也必须每次查询确认）
> - `dimItemName` **必须是步骤 2 查询返回的真实显示名**
> - **禁止使用自行编造的聚合编码**（如 `"Oversea_ExcludeGCT"`、`"Global_ExcludeChina"` 等）
> - "全球除某区域"必须**展开为步骤 2 查到的多个实际存在的子节点**

6. **兜底与确认**：若用户的地域表达无法在步骤 2 的查询结果中找到对应节点（如"北欧国家"、"英语区国家"等非常规表达）：
- 先尝试用该关键词在 `v_ai_data_scope` 的 `dim_item_name` 和 `dim_item_full_name` 中做模糊搜索（额外 SQL）
- 若仍无法唯一确定，在最终填单结果的该维度行末尾追加标注：`⚠️ 地域范围「XXX」未能精确映射到码表节点，已按最佳推测选择【YYY】，请确认或手动调整`

## ② 未匹配到的必选维度：瀑布式默认值填充

对于步骤①中**未能从需求语义匹配到码值**的必选维度，按以下**瀑布式优先级**依次尝试填充。

> ⚠️ **强制规则**：必选维度**绝不能留空或跳过**。无论用户是否在需求中提及该维度，只要是必选维度且步骤①未匹配到码值，就**必须**执行以下瀑布式填充。常见错误：误以为"用户未提及的维度就留空待用户填写"——这是**错误的**，必选维度必须走瀑布式填充。

**必选维度的范围**包括：
- **角色分工维度**（`ai_role_def` 表的 `role_division_dim` 字段中列出的所有维度）— 角色维度全部为必填
- **权限包必选控权维度**（`pkg_required_ctrl_dim` 中列出的维度）

只要属于上述范围且步骤①未能从需求中匹配到码值的维度，均需执行以下瀑布式填充：

| 场景 | 维度类型 | 第一优先级 | 第二优先级 | 第三优先级 | 第四优先级 |
|------|---------|-----------|-----------|-----------|-----------|
| **新增(0)** | 角色维度 | — | ② 全部/顶层码值 | ③ 勾选所有可选码值 | — |
| **新增(0)** | 权限包必选 | ① 权限包默认值 | ② 全部/顶层码值 | ③ 勾选所有可选码值 | — |
| **变更(1)** | 角色维度 | — | ④ 已有值 | ② 全部/顶层码值 | ③ 勾选所有可选码值 |
| **变更(1)** | 权限包必选 | ① 权限包默认值 | ④ 已有值 | ② 全部/顶层码值 | ③ 勾选所有可选码值 |

> **关键差异**：
> - 权限包必选维度比角色维度**多一个第一优先级「①权限包默认值」**
> - 变更场景比新增场景**多一个第二优先级（实际排在全部之前）「④已有有效范围的维度值」**
> - 各优先级对应的具体填充逻辑详见下方 ①②③④ 说明


**① 权限包维度默认值**：
```sql
SELECT default_scope FROM ai_role_rightpackage_default_scope
WHERE pkg_code = '{当前权限包编码}'
AND role_code = '{当前角色编码}'
AND ctrl_dim = '{当前维度名称}'
```
若查询到结果，直接使用 `default_scope` 字段的值作为该维度的填充值。

> **注意**：此处 `ctrl_dim` 字段使用的维度名称是 `ai_role_rightpackage_default_scope` 表中实际存储的值，可能与步骤⓪解析后的 `dim_type_name` 不同。建议先用步骤⓪解析后的名称查询；若无结果，再用角色/权限包中记录的原始维度名称重试一次。

**② 维度顶层"全部"码值**：
查询该维度是否存在表达"全部/全选"含义的顶层码值：
```sql
SELECT dim_item_code, dim_item_name FROM v_ai_data_scope
WHERE dim_type_code = '{步骤⓪解析后的dim_type_code}'
AND (dim_item_name = '全部' OR dim_item_name LIKE '全部%'
OR dim_item_name = '全公司' OR dim_item_name = '全部（含有效、失效和空值）')
LIMIT 5
```
若查询到包含"全部/全公司"等表达全选含义的码值，使用该码值作为填充值。

> **补充说明**：部分维度的"全选"码值不一定字面叫"全部"，例如组织范围维度的顶层码值为"全公司"（`Org-All`）。如上述 SQL 未命中，可进一步查询该维度的**无父级顶层节点**作为候选：
> ```sql
> SELECT dim_item_code, dim_item_name FROM v_ai_data_scope
> WHERE dim_type_code = '{步骤⓪解析后的dim_type_code}'
> AND (dim_item_parent_code IS NULL OR dim_item_parent_code = '')
> LIMIT 10
> ```
> 若顶层节点唯一且语义上表示全选（如"全公司"），直接使用该码值。

**③ 勾选所有可选码值**：
查询该维度下的所有有效码值：
```sql
SELECT dim_item_code, dim_item_name FROM v_ai_data_scope
WHERE dim_type_code = '{步骤⓪解析后的dim_type_code}'
```
将查询到的所有码值全部勾选。

**④已有有效范围的维度值**：
查询对应角色或权限包的有效分工范围，对应维度的值，复制copy值变更申请的维度中。


**新增3级/变更4级均无结果 — 兜底处理**：
若以上三个优先级均无结果（即默认范围表无配置、维度码值表中无"全部/全公司"码值、且该维度下无任何可选码值），则该必选维度**仍然必须在最终输出中展示**，标注为 `⚠️ 无法自动填充，需用户手动选择`。**绝不能因为瀑布式填充失败就跳过不展示必选维度**。

## ③ 未匹配到的非必选维度：不赋值

非必选维度仅指**权限包的可选控权维度**（`pkg_optional_ctrl_dim` 中列出且不属于 `pkg_required_ctrl_dim` 的维度）。角色分工维度不适用此规则，角色分工维度全部为必填，始终走②瀑布式填充。



## ④ 期限规则

需求语义中有明确期限说明则识别并返回；需求语义不涉及期限则按以下逻辑处理：

1. **读取可申请最大有效期配置**：查询 `ai_role_rightpackage` 表中当前自主申请权限包对应记录的 `max_member_expiration` 字段
   - `max_member_expiration` 枚举值含义：`9999` = 不限制，`12` = 一年，`6` = 六个月，`3` = 三个月，`1` = 一个月
2. **根据可申请最大有效期设置默认期限**：
   - 若找到 `max_member_expiration` 且值不为 `9999`（不限制）：开始时间 = 申请日期（当天），结束时间 = 开始时间 + 对应期限（月数）
   - 若 `max_member_expiration` 为 `9999`（不限制）：返回为 ：9999（不限制）
   - 若未找到 `max_member_expiration` 配置（字段为空或记录不存在）：不返回期限信息
