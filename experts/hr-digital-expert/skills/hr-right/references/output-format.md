## 版本A：新增场景 (type=0) 输出规则

适用于以下两种子场景：
1. **全新申请**：角色和权限包均未持有 → 角色和权限包的 `isNewApply` 均为 `true`
2. **已有角色追加权限包**：角色已持有、权限包未持有 → 角色 `isNewApply = false`，待新增权限包 `isNewApply = true`

### 版本A — 输出字段定义

| 序号 | 输出字段 | 说明 | 来源 | 展示规则 |
|------|---------|------|------|---------|
| 1 | **申请场景** | `0`（新增） | 步骤二 | **始终展示**，排在第一位 |
| 2 | **申请角色** | 步骤一锁定的角色名称及编码 | 步骤一 `lockedRole` | **始终展示** |
| 3 | **角色范围** | 角色级别的全部分工维度范围（取角色 `role_division_dim` 中每个维度的码值）。**单维度时**：以维度名作为填单项列名（如"组织范围"），值为步骤③最终确定的码值名称；**多维度时**：列名统一为"角色范围"，内容中各维度分行展示，每行格式为 `【维度名】：码值名称`（最后一个维度末尾无换行）。**所有维度必须展示**——无论来自需求语义匹配还是瀑布式填充，都必须返回具体码值（如"全部"、"全公司"、具体组织全路径等） | 步骤三 维度识别结果 | **始终展示** |
| 4 | **默认权限包** | 该角色下所有规则生成权限包列表，附备注说明：`（默认权限包根据角色授权范围和申请人信息自动计算得出，请以实际生效结果为准）` | 步骤一 `ruleGeneratedPkgs` | **仅涉及时展示**，为空则不展示该行 |
| 5 | **自主申请权限包** | 通过需求语义锁定的自主申请权限包列表 | 步骤一 `selfApplyPkgs` | **仅涉及时展示**，为空则不展示该行 |
| 6 | **自主申请权限包范围** | 每个自主申请权限包的全部必选控权维度码值。**必须展示该权限包 `pkg_required_ctrl_dim` 中列出的每一个必选维度及其值**，不可省略。维度名称用【】包裹，不同维度分行展示，每行格式为 `【维度名】：码值名称`。**每个必选维度的值的来源优先级**：① 需求语义匹配到的码值 > ② 瀑布式填充得到的码值（如"全部"、"全公司"等）。若三级瀑布式填充均无结果，则标注 `⚠️ 无法自动填充，需用户手动选择`。可选控权维度（`pkg_optional_ctrl_dim`）仅在需求语义中匹配到时才展示 | 步骤三 维度识别结果 | **仅存在自主申请权限包时展示**（为空则不展示该行） |
| 7 | **自主申请权限包对应期限** | 需求语义中识别到的期限（若有），需在权限包 `max_member_expiration` 限制范围内 | 步骤三 期限识别结果 | **仅涉及时展示**，未涉及期限则不展示该行 |
| 8 | **申请原因** | 用户原始需求文本，不删减 | 步骤四 | **始终展示** |

### 版本A — 输出格式说明

- 以 Markdown 表格形式输出，两列结构：「填单项 / 内容」
- **申请场景始终排在第一行**
- **不涉及的字段不展示**：若自主申请权限包为空，则"自主申请权限包"及其对应范围/期限的行均不展示；若期限不涉及，则期限行不展示
- **角色范围必须返回所有维度的具体码值（优化点2）**：
  - 角色的 `role_division_dim` 列出的**每一个维度都必须有值**
  - **组织维度优先级（优化点4）**：① 需求语义精确/模糊匹配到系统中的组织（匹配规则遵循 [步骤三 ① 组织维度智能补全规则](#-从需求语义中匹配维度码值)，**多候选时按"申请人组织路径前缀最长公共匹配"择优，仍多候选时主动询问用户**） → 直接使用匹配结果 > ② 匹配不到但判断为新建组织 → 以**匹配到的上级组织全路径 + `/` + 新建子组织名称**作为显示值（码值使用上级组织的 `dim_item_code`）+ 追加标注 `📌 （待新建子组织「XXX」录入系统后调整范围）` > ③ 瀑布式填充得到的具体码值（如"全部"、"全公司"等）
  - 非组织维度优先级：① 需求语义匹配到的具体码值 > ② 瀑布式填充得到的码值
  - 瀑布式填充的结果应返回具体码值名称（如"全部"、"全公司"、"S3职能系统－HR与管理线"等），**不能留空、不能写"待用户填写"、不能省略该维度行**
  - 即使三级瀑布填充都失败，也要标注 `⚠️ 无法自动填充，需用户手动选择`
- **角色范围展示规则（优化点1）**：
  - **单维度**：直接以维度名作为填单项列名，值为步骤③最终确定的码值名称。例如角色只有"组织范围"一个分工维度 → `| **组织范围** | IEG互动娱乐事业群 / 天美工作室群 / 天美J3工作室 |`
  - **多维度**：列名统一为"角色范围"，内容中每个维度用【】包裹维度名后分行展示，每行格式为 `【维度名】：码值名称`。例如：`【组织】：S3职能系统－HR与管理线`（换行）`【工作地】：全部`（换行）`【管理主体】：全部`（换行）`【员工子类型】：全部`
- **自主申请权限包必须展示全部必选控权维度及其值（优化点3）**：
  - 该权限包的 `pkg_required_ctrl_dim` 中列出的**每一个必选维度都要展示**，不可省略任何一个必选维度
  - 每个必选维度的值来源优先级：① 需求语义匹配到的具体码值 > ② 瀑布式填充得到的码值（如"全部"、"全公司"等）
  - 若某必选维度瀑布三级填充均无结果 → 标注 `⚠️ 无法自动填充，需用户手动选择`
  - 可选控权维度仅在需求语义中匹配到时才展示
- 规则生成权限包不需要用户手动选范围，其范围由系统规则自动计算，因此只展示权限包名称，并在下方附备注：`（默认权限包根据角色授权范围和申请人信息自动计算得出，请以实际生效结果为准）`
- 自主申请权限包需要逐个展示各自的控权维度范围，**维度名称用【】包裹，不同维度分行展示**，每行格式为 `【维度名】：码值名称`（最后一个维度末尾无额外符号）
- 多角色申请场景：每个角色独立一个表格，以标题区分

## 版本B：变更/续期场景 (type=1 / type=2) 输出规则

适用于以下场景：
- **type=1（变更）**：用户已有有效授权，本次涉及范围维度变化（权限包本身已有授权，需修改其范围或有效期）
- **type=2（续期）**：用户已有有效授权，本次仅涉及有效期变化（范围不变，仅延长/更新到期日）

> ⚠️ **变更场景的两种子场景**：type=1（变更）内部包含两个子场景，其输出格式和 JSON 组装方式不同，必须严格区分：
>
> | 子场景 | operationType | 说明 |
> |---|---|---|
> | **修改已有记录** | `"Update"` | 修改某条已有记录的维度码值或有效期（rowId 必填） |
> | **新增一组分工** | `"Add"` | 在已有角色/权限包下追加一组新的维度组合（rowId 为 null） |

### 版本B — 输出字段定义

| 序号 | 输出字段 | 说明 | 来源 | 展示规则 |
|------|---------|------|------|---------|
| 1 | **场景** | `1`（变更）或 `2`（续期） | 步骤二 | **始终展示**，排在第一位。标注完整描述如 `type=1（变更）` 或 `type=2（续期）` |
| 2 | **角色** | 步骤一锁定的角色名称及编码 | 步骤一 `lockedRole` | **始终展示** |
| 3 | **角色范围** | 角色级别的全部分工维度范围。**变更场景必须展示变更前后对比**；续期场景因范围无变化，简化展示当前范围即可 | 步骤三 维度识别结果 + `query_staff_role_right` 已有记录 | **始终展示**，格式详见下方"角色范围展示规则" |
| 4 | **默认权限包** | 该角色下所有规则生成权限包列表，附备注说明 | 步骤一 `ruleGeneratedPkgs` | **仅涉及时展示**，为空则不展示该行 |
| 5 | **自主申请权限包** | 通过需求语义锁定的自主申请权限包列表 | 步骤一 `selfApplyPkgs` | **仅涉及时展示**，为空则不展示该行 |
| 6 | **自主申请权限包范围** | 每个自主申请权限包的控权维度码值。**变更场景必须展示变更前后对比**；续期场景因范围无变化，简化展示当前范围 | 步骤三 维度识别结果 + `query_staff_role_right` 已有记录 | **仅存在自主申请权限包时展示** |
| 7 | **自主申请权限包期限** | 变更前后的有效期对比（变更场景），或续期前后的有效期（续期场景） | 步骤三 期限识别结果 + `query_staff_role_right` 已有记录 | **仅涉及时展示** |
| 8 | **申请说明** | 用户原始需求文本，不删减 | 步骤四 | **始终展示** |

### 版本B — 角色范围展示规则

变更/续期场景下，角色范围的展示需区分**多组分工**和**变更前后对比**两种维度，组合为以下规则：

#### 1. 多组分工展示（当 `query_staff_role_right` 返回多条 `roleDataScopes` 记录时）

当同一角色下存在**多组有效分工**（多个 `rowId`），且本次操作涉及其中一组或多组时：

- **每组分工独立一行**：填单项列名按序编号，如"角色范围1"、"角色范围2"、……
- **未被本次操作涉及的分工组不展示**（仅在删除场景的"本次保留的记录"行中提及）
- **若仅有一组分工被涉及**：填单项列名直接用"角色范围"（不加编号）

#### 2. 变更前后对比格式（type=1 变更 — 修改已有记录子场景）

当修改某条已有记录的维度码值时，该组分工的内容栏必须按以下格式展示：

```
变更前：
【维度名1】：变更前的码值名称
【维度名2】：变更前的码值名称
...

变更后：
【维度名1】：变更后的码值名称
【维度名2】：变更后的码值名称
...
```

**关键规则**：
- **所有维度必须完整展示**（变更前和变更后均需列出全部维度），不仅展示变化的维度，不变的维度也要原样列出
- 变更前值来自 `query_staff_role_right` 返回的已有授权记录
- 变更后值来自步骤三的维度识别结果
- 维度名称用【】包裹，不同维度分行展示，每行格式为 `【维度名】：码值名称`
- "变更前"与"变更后"之间空一行

#### 3. 新增一组分工格式（type=1 变更 — 新增分工子场景）

当在已有角色下追加一组新分工（`operationType="Add"`）时，该组分工的内容栏格式为：

```
新增一组分工

变更后：
【维度名1】：码值名称
【维度名2】：码值名称
...
```

**关键规则**：
- 行首标注"新增一组分工"以区分修改已有记录
- **仅展示变更后值**（无变更前值，因为是全新追加的分工组）
- 已有的其他分工组不在本次表格中展示

#### 4. 续期场景格式（type=2）

续期场景因范围维度完全无变化，角色范围简化展示：

```
（范围无变化，省略对比展示）
当前范围：【维度名1】：码值名称；【维度名2】：码值名称；...
```

**关键规则**：
- 无需展示变更前后对比（因为没有变化）
- 列出当前范围供用户参考确认
- 若角色有多组分工且均需续期，按"角色范围1"、"角色范围2"分别展示当前范围

### 版本B — 自主申请权限包范围展示规则

自主申请权限包的范围展示同样区分变更前后对比：

#### 变更场景（修改已有记录）

与角色范围格式一致，展示变更前后对比：

```
变更前：
【维度名1】：变更前的码值名称
【维度名2】：变更前的码值名称
...

变更后：
【维度名1】：变更后的码值名称
【维度名2】：变更后的码值名称
...
```

- **必须展示该权限包 `pkg_required_ctrl_dim` 中列出的每一个必选维度**，不可省略
- 不变的维度也要在变更前和变更后中原样列出
- 可选控权维度仅在需求语义中匹配到时才展示

#### 变更场景（新增一组分工）

```
新增一组分工

变更后：
【维度名1】：码值名称
【维度名2】：码值名称
...
```

#### 续期场景

```
（范围无变化，省略对比展示）
当前范围：【维度名1】：码值名称；【维度名2】：码值名称；...
```

### 版本B — 自主申请权限包期限展示规则

#### 变更场景

当有效期同时发生变化时，展示变更前后的有效期对比：

```
变更前：2025/10/22～2026/12/01
变更后：2026/04/14～2027/12/01
```

当有效期不变时，仅展示当前有效期即可：

```
2025/10/22～2026/12/01（不变）
```

#### 续期场景

展示续期前后的有效期：

```
2026-04-01～2027-03-31
2027-04-01～2028-03-31
```

### 版本B — 输出格式说明

- 以 Markdown 表格形式输出，两列结构：「填单项 / 内容」
- **场景始终排在第一行**
- **不涉及的字段不展示**：若自主申请权限包为空，则"自主申请权限包"及其对应范围/期限的行均不展示
- **变更前后对比是强制要求**：变更场景下，角色范围和自主申请权限包范围**必须**展示变更前后的完整维度值对比，不能只展示变化的部分
- **变更前值来源**：来自 `query_staff_role_right` 返回的已有授权记录中对应 `rowId` 的维度码值
- **变更后值来源**：来自步骤三的维度识别结果（含需求语义匹配 + 瀑布式填充）
- **续期场景简化展示**：因范围无变化，仅列出现有范围值作为参考，不做前后对比；但期限行需展示续期前后的有效期
- 规则生成权限包不需要用户手动选范围，其范围由系统规则自动计算，因此只展示权限包名称，并在下方附备注
- 多角色申请场景：每个角色独立一个表格，以标题区分
- **跨组传播规则**：当用户描述的变更前维度值同时出现在多组有效分工中时，变更操作应同步应用到所有匹配的组，各组均展示变更前后对比

> 📁 **版本B 完整输出示例**：参见 [examples.md → 版本B 输出示例](./examples.md#版本b变更续期场景-type1--type2-输出示例)，包含：
> - **示例七**：变更场景 — 多组分工下的组织范围扩大 + 期限延长（Update）
> - **示例八**：变更场景 — 新增一组分工（Add/Insert）
> - **示例九**：续期场景 — 仅有效期变化

### 最后一步：通过 `hr-auth-copilot` MCP 的 `submit_apply_form` 流程单据地址创建。

> ✅ **执行检查点（最后一步开始前必读）**
> - **入口条件**：步骤一 → 一.5 → 二 → 三 → 四 已全部声明完成，填单表格已输出
> - **禁止动作**：用户未回复肯定词前，禁止调用 `submit_apply_form`（writeOperation=true 的写操作不可逆）
> - **必须动作**：等待用户确认 → 按场景组装 JSON → 调用 `submit_apply_form` → 返回单据链接
> - **完成声明**：调用成功后告知「单据已提交，链接：XXX」；失败时按异常处理规则降级
> - **会话结束声明**：本次申请流程闭环后，向用户简述"本次申请已闭环；若有新的权限相关需求，将重新走 skill 完整流程"，提醒后续请求不会跳步

> ⚠️ **重要：用户确认前置条件**
>
> 在输出填单结果表格后，**必须等待用户回复确认**，才能执行本步骤。
> - 输出表格后，需向用户询问：**「以上为智能填单结果，请确认是否提交？如需修改请告知具体调整内容。」**
> - **用户回复肯定词**（详见 [🔑 用户确认词集](#-用户确认词集通用规则所有场景共用)）后，才继续执行下方的 `submit_apply_form` 调用
> - **用户提出修改意见**时，根据用户反馈调整填单内容并重新输出表格，再次等待确认
> - **禁止自动执行**：未收到用户确认回复前，绝不能调用 `submit_apply_form`

步骤二的场景识别结果可能产生多种场景（新增/变更/续期/删除），输出格式按 **新增、变更、续期、删除** 分成 **多个独立的JSON**，分别调用 `submit_apply_form` 创建对应的流程单据。

**场景与申请类型编码映射**：
- **新增** = `0` = 角色权限包新申请
- **变更** = `1` = 角色权限包变更
- **续期** = `2` = 角色权限包续期

每种场景各自组装一个独立的 `RoleRightApplyFormDTO` JSON，分别调用：

- **工具名称**：`submit_apply_form`
- **参数**：
  - `type`（integer，必填）：申请场景类型（新增/变更/续期/删除），调用前需根据「场景与申请类型编码映射」进行判断，传入对应的类型编码。删除场景的 type=1（变更），通过记录级别的 `operationType="Delete"` 表达
  - `data`（string，必填）：流程表单数据，通过 RoleRightApplyFormDTO java类创建对象，进行json序列化后的值
- **返回值**：流程表单链接地址

> **说明**：若步骤二的场景识别结果中只涉及一种场景（如全部新增），则只需组装并调用一次。若涉及多种场景（如部分权限包新增、部分权限包变更），则需分别组装各场景的JSON并分别调用 `submit_apply_form`。

#### JSON 组装示例

📁 **新增场景（type=0）完整 JSON 示例**：[examples.md → J-1 新增场景](./examples.md#j-1-新增场景type0--add-json-示例)（含校招简历筛选员角色 + 业务分析-海外薪酬权限包的完整组装）

> **组装要点**：
> - `isNewApply`：**按角色和权限包分别独立设置**，取值规则如下：
>   - **全新申请**（角色未持有）：角色 `isNewApply = true`，所有权限包 `isNewApply = true`
>   - **已有角色追加权限包**（type=0 的新增子场景）：角色 `isNewApply = false`（表示该角色已持有，不重复申请），待新增的权限包 `isNewApply = true`
>   - **变更/续期**（type=1/type=2）：角色 `isNewApply = false`，变更/续期的权限包 `isNewApply = false`
> - `roleDataScopes`：角色级别的分工维度范围（对应 `List<DataScopeDimGroupDTO>`），来自步骤三对 `role_division_dim` 的解析
> - `operationType` **统一取值表**（按场景区分）：
>
>   | 场景 | type | operationType | rowId 是否必填 | 说明 |
>   |---|---|---|---|---|
>   | **新增（全新申请）** | `0` | `"Add"` | ❌ 否（传 `null`） | 角色/权限包从未持有，初次申请 |
>   | **变更 — 修改已有记录** | `1` | `"Update"` | ✅ 是（用 `query_staff_role_right` 返回的原 `rowId`） | 改某条已有记录的维度值或有效期。**允许同一条记录同时修改维度码值 + endDate**（即"扩范围+续期"场景强制合并到本行，不拆成 type=1 + type=2）|
>   | **变更 — 在已有角色下追加新记录** | `1` | `"Add"` | ❌ 否（传 `null`） | 在已有角色/权限包下新增一组分工/范围（无历史 rowId） |
>   | **续期** | `2` | `"Update"` | ✅ 是 | 仅改 `endDate`，维度码值完全不变（若维度也要动 → 走 type=1 Update） |
>   | **删除** | `1` | `"Delete"` | ✅ 是 | 移除某条已有 rowId 记录本身 |
>
>   ⚠️ **关键提示**：
>   - 新增场景（type=0）的 `operationType` 是 `"Add"`，**不是 `null`**（之前文档曾写为 `null`，是错的）
>   - 变更场景（type=1）下两种子场景需要严格区分：**修改已有行用 `Update` + rowId**；**追加新行用 `Add` + 无 rowId**
>   - 删除场景仅用 `Delete`，且必须带 `rowId`
> - `packageDataScopes`：权限包级别的控权维度范围（对应 `List<DataScopeDimGroupDTO>`），来自步骤三对 `pkg_ctrl_dim` 的解析。规则生成权限包的 `packageDataScopes` 通常为空数组（范围由系统自动计算）；自主申请权限包需填充具体维度范围
> - `maxExpire`：仅自主申请权限包需填写，取步骤三④的期限识别结果；规则生成权限包传 `null`
> - `memberFrom`：新申请均默认设置为 `"apply"`
> - `endDate`：根据权限包 `maxExpire` 计算。`maxExpire=9999` 时设置为 `"9999-12-31"`；其它值根据当前日期+maxExpire（月数）计算
> - `DataScopeDimGroupDTO` 中的 `dataScopeDimItems` 包含按维度类型分组的 `DataScopeDimTypeItemDTO` 列表，每个维度类型下的具体码值通过 `items`（`List<DataScopeDimItemDTO>`）传递，每个码值仅包含 `dimItemCode` 和 `dimItemName` 两个字段
> - 变更场景下，`DataScopeDimGroupDTO.rowId` 和 `operationType` 的取值见上方 **operationType 统一取值表**（修改已有行：`Update`+rowId；追加新行：`Add` 无 rowId；删除：`Delete`+rowId）

#### 删除场景（type=1, operationType=Delete）专属规则

适用条件：步骤二识别为**情况四（删除场景）**，即用户表达清理/删除/撤销/移除/取消/去掉/剔除/作废/注销 等意图，且 `query_staff_role_right` 中能定位到对应的有效授权记录。

##### 输出表格规范（用户确认前必须输出）

```
| 填单项 | 内容 |
|--------|------|
| **场景** | type=1（变更 — 删除某条记录） |
| **角色** | xxx角色（`role_code`）|
| **目标人员** | 申请人本人（或指定的目标人员） |
| **待删除记录** | 共 N 条，明细如下：<br><br>**[1] 角色级 / 权限包名称（pkg_code）**<br>　rowId：xxxx<br>　范围：【组织】：xxx；【工作地】：xxx；... <br>　有效期：startDate ~ endDate<br>　来源：自主申请 / 规则生成<br><br>**[2] ...** |
| **本次保留的记录** | （提示性展示）该角色/权限包下未被本次删除的其他记录 rowId 列表，方便用户对比确认删错没 |
| **申请说明** | 用户原始需求文本，不删减 |
```

> **关键约束**：
> 1. **必须列出每条待删除记录的完整 `rowId` 和维度明细**，让用户可逐条核对，**严禁只写"清理 hrrightMgr 权限包"等模糊描述**
> 2. **必须同时展示本次保留的记录**，避免用户误以为整个权限包都被清掉
> 3. **必须经用户明确确认后**才能调 `submit_apply_form`（写操作不可逆）
> 4. **多条匹配时**：列出所有候选 rowId 让用户勾选要删的项；用户未明确勾选前，不能擅自删多条

- **J-4.2 角色级 Delete**：删除国内面试官角色下某条角色级分工记录（rowId=4608420）

**关键字段说明（速查）**：
- `operationType`：固定为 `"Delete"`
- `rowId`：**必填**，使用 `query_staff_role_right` 返回的原 `rowId`
- `dataScopeDimItems`：**必须原样回传**待删除记录的原维度值（不能传空，便于后端审计核对）

##### 同一笔 `submit_apply_form` 内的多场景合并（仅限同 type）

> ⚠️ **重要纠正**：**只有 (命令, type) 完全相同**的子操作才能合并到同一笔 `submit_apply_form`。**整包/整角色清理走的是 `clear_role_package`，与 `submit_apply_form` 是不同命令，绝对不能合并到同一笔**。

**可合并的典型场景（同一 `submit_apply_form` type=1 内）**：

| 子操作 1 | 子操作 2 | 合并方式 |
|---|---|---|
| 同权限包：精确删某条 packageDataScopes（Delete）| 同权限包：追加一组新分工（Add）| 一笔 type=1，packageDataScopes 数组并存两条 |
| 同权限包：修改某条 packageDataScopes（Update）| 同权限包：删除另一条（Delete）| 一笔 type=1，packageDataScopes 数组并存两条 |
| 同角色：roleDataScopes 修改（Update） + 该角色下某权限包 packageDataScopes 删除（Delete）| — | 一笔 type=1，同 `roleFormItemList[]` 元素内 |

**典型示例**：
- "C 权限包：把组织范围从 A 改为 A+B（Update），同时删除原有的 D 工作地范围那条（Delete）" → 一笔 type=1
- "C 角色：在 roleDataScopes 追加一组新分工（Add），同时把该角色下 D 权限包的范围扩大（Update）" → 一笔 type=1

**不可合并的反例**（必须拆，详见 [多意图处理 — 7 个标准案例](#多意图处理按-mcp-调用粒度判定-拆不拆)）：
- ❌ 整包清理 + 范围扩大 → 命令不同（`clear_role_package` vs `submit_apply_form`），必须拆
- ❌ 申请未持有的新角色 + 删除已有记录 → type 不同（0 vs 1），必须拆
- ❌ 续期 + 删除 → type 不同（2 vs 1），必须拆

#### 续期场景（type=2）专属规则

> ⚠️ **核心约定**：**续期接口与变更接口传入的信息结构完全一致**——使用相同的 `RoleRightApplyFormDTO` JSON 结构、相同的字段含义、相同的 `operationType` 取值。**唯一区别仅是 `submit_apply_form` 的 `type` 参数不同（续期=`2`，变更=`1`）**。

##### 续期 vs 变更的判断口径（步骤二已识别，此处仅复述）

- **续期（type=2）**：**仅 `endDate` 变化**，所有 `dataScopeDimItems` 维度码值集合无任何增删改
- **变更（type=1）**：维度码值集合发生变化（增/删/改任一码值都算）；`endDate` 可能同时变也可能不变

📁 **完整字段约定表 + JSON 示例**：[examples.md → J-3 续期场景](./examples.md#j-3-续期场景type2--update-json-示例)

> **核心字段速查**：
> - `submit_apply_form.type=2`（与变更场景的 `type=1` 唯一区别）
> - `roleFormItemList[].isNewApply = false`
> - `packageDataScopes[].rowId` 必填（用 `query_staff_role_right` 返回的原值）
> - `packageDataScopes[].dataScopeDimItems` 原样回传已有记录的全部维度值
> - `packageDataScopes[].endDate` 是新的到期日期（按 `max_member_expiration` 计算）
> - `packageDataScopes[].operationType = "Update"`

#### 变更场景（type=1）专属规则

变更场景包含两类子场景，其 JSON 组装方式不同，请严格区分：

| 子场景 | operationType | rowId | 适用情况 |
|---|---|---|---|
| **修改已有记录的范围** | `"Update"` | ✅ 必填（用 `query_staff_role_right` 返回的原 `rowId`） | 调整某条已有记录的维度码值（如组织从 A 改为 A+B） |
| **在已有角色下追加一组新分工** | `"Add"` | ❌ 否（传 `null`） | 已有角色下新增一组维度组合（无历史 `rowId`） |

📁 **完整 JSON 示例**：[examples.md → J-2 变更场景](./examples.md#j-2-变更场景type1-json-示例)，包含：
- **J-2.1 Update 示例**：修改 BA-HRIS 角色 hrrightMgr 权限包的 hrrightDomain 范围（rowId 必填）
- **J-2.2 Add 示例**：在招聘经理角色下追加 PCG/社交平台与应用线 一组分工（rowId=null）

> **关键约束（速查）**：
> - **修改已有行**：`operationType="Update"` + `rowId` 必填 + `dataScopeDimItems` 是**变更后的完整维度集合**（不变维度也要原样带上）
> - **追加新行**：`operationType="Add"` + `rowId=null` + 不要影响原有行（原有行不出现在本次 JSON）

#### 弱校验二次确认（重要 — **所有写操作命令通用**）

> ⚠️ **通用化声明**：本节定义的「弱校验二次确认」机制**适用于所有 `writeOperation=true` 的 MCP 命令**，包括但不限于：
> - `submit_apply_form`（新增 / 变更 / 续期 / 删除）
> - `clear_role_package`（清理整角色 / 整权限包）
> - `revoke_apply_form`（撤回审批中单据）
> - 其他后端可能新增的写操作命令
>
> **任何写操作命令**返回 `success=false` 且 `data` 中含"弱校验场景"标识时，都必须按本节流程处理。

##### 触发条件识别

后端返回结构同时满足以下两个条件即为弱校验提示：

```json
{
  "success": false,
  "code": "-1",
  "msg": "<弱校验提示文案，如：本次申请只涉及授权范围的缩小，无需经过审批，提交后会立即生效,请确认是否提交!>",
  "data": "弱校验场景，提示用户是否确认操作，key:后端校验给出的提示信息，value:用户是否确认操作..."
}
```

> **关键识别点**：`data` 字段中包含"**弱校验场景**"四个字。一旦识别到，**不要把它当作真正的失败**，而要进入下方的二次确认流程。

##### 处理流程（必须严格执行）

```
第一次调用 submit_apply_form
    │
    ▼
返回 success=false 且 data 包含"弱校验场景"
    │
    ▼
┌─ 必须做的事 ─────────────────────────────────────────────────────┐
│ 1. 把后端返回的 msg 文案【原样】展示给用户                          │
│ 2. 明确告知用户：                                                  │
│    - 这是后端的二次确认提示                                        │
│    - 该操作的影响（如"立即生效不可回滚"、"无需走审批"等）          │
│    - 请用户回复肯定词（详见「🔑 用户确认词集」），如"再次确认 / 是 / 取消" │
│ 3. ⚠️ 严禁未收到用户明确回复就自动重试                            │
└───────────────────────────────────────────────────────────────────┘
    │
    ▼
用户回复肯定词（如"确认"、"是"、"提交"等，详见「🔑 用户确认词集」）
    │
    ▼
┌─ 重新组装请求 ───────────────────────────────────────────────────┐
│ 在原 RoleRightApplyFormDTO JSON 的最外层新增字段：                  │
│   "confirmReusltMap": {                                            │
│     "<第一次返回的 msg 原文>": true                                │
│   }                                                                │
│ key 必须是【完全原样】的 msg 文案（包括所有标点、空格、感叹号）    │
│ value 为 true 表示用户确认                                         │
│ 其他参数（roleFormItemList、applyReason 等）保持与第一次完全一致   │
└───────────────────────────────────────────────────────────────────┘
    │
    ▼
第二次调用 submit_apply_form
    │
    ▼
后端返回 success=true，data 中给出操作结果
```

##### 完整 JSON 示例（带 confirmReusltMap）

##### 已知的弱校验场景示例

| 触发场景 | 典型 msg 文案 | 含义 |
|---|---|---|
| 范围缩小 / 删除记录 | `本次申请只涉及授权范围的缩小，无需经过审批，提交后会立即生效,请确认是否提交!` | 免审批、立即生效、不可回滚 |
| 其他后端弱校验 | （以后端实际返回为准） | 由 `data` 字段含"弱校验场景"识别 |

> **多个弱校验同时触发**：若后端一次返回多个弱校验 msg（暂未遇到，但接口设计支持 `Map<String, Boolean>`），需把每条 msg 都作为 key 加入 `confirmReusltMap`，并分别让用户对每条进行确认；用户全部确认后再统一回传。

##### 核心约束

- **禁止自动确认**：弱校验本质是给用户最后一次反悔机会，AI **绝不能**未经用户回复就把所有 msg 设为 `true` 重试
- **禁止改写 msg**：作为 `confirmReusltMap` 的 key，必须是后端 msg 的**完全原文**——任何标点、空格、大小写差异都会导致后端识别失败
- **必须告知影响**：转告用户时要把 msg 中的关键影响（如"立即生效"、"不可回滚"、"免审批"）单独突出，避免用户随手回复"确认"
