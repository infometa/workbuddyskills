## 步骤一详解 — 三方案并行识别

### ✅ 执行检查点（步骤一开始前必读）

- **入口条件**：用户的需求语义已就绪，未跳过任何上游守门规则
- **禁止动作**：禁止在执行三方案前用 `ask_followup_question` 询问"你的角色是什么"、"你要的权限包是哪个"等本应由本步骤自动获取的信息
- **必须动作**：三方案 SQL 查询并行发起 → 计算各自得分 → 选优 → 输出 `lockedRole + ruleGeneratedPkgs + selfApplyPkgs`
- **完成声明**：执行完毕后，向用户简述：「步骤一完成：通过方案 X（角色/权限包/系统反查）锁定角色 = 「XXX」（得分 N），关联规则生成权限包 M 个，自主申请权限包 K 个」
- **零分兜底**：三方案均为 0 分时，输出"未匹配到结果"并终止后续步骤

三个方案**独立并行执行**，每个方案内部都有 Part1→Part2→Part3 三层流水线。每个方案的 Part1 返回第一层匹配分数（方案之间比较的基准分）。三方案全部执行完毕后，**填单内容只用分数最高的方案**；分数相同时按 **方案一 > 方案二 > 方案三** 排序。


### 方案一：基于角色搜索
核心路径：需求语义 → 搜索 ai_role_def → 匹配角色 → 展开权限包 → 锁定自主申请权限包
- **Part1 角色识别**：从需求中提取角色相关的关键词/范围后缀词，在 `ai_role_def` 表中通过**多字段联合搜索**匹配角色，搜索字段按优先级排序：**`role_name`（角色名称） > `role_desc`（角色描述） > `domain_name`（所属领域） > `role_type`（角色类型）** 及其他语义相关字段，返回匹配度最高的角色（含分数）。以 Part1 最高分角色（topRole）作为唯一输入传递给 Part2
  - **角色名命中加分规则**：Part1 完成后，检查 topRole 的 `role_name` 是否在用户需求原文中出现（去掉"角色"后缀后做子串匹配）。若角色名（或去掉"角色"后缀的名称）在需求原文中能找到，则将该方案的 Part1 分数提升至 **95 分**（覆盖原始分数）。例如用户需求中直接写了"SSC-问询业务知识管理员角色"，匹配到的角色名为"SSC-问询业务知识管理员角色"，则方案一得分提升为 95 分
- **Part2 权限包展开**：以 Part1 的 topRole 为唯一输入，在 `ai_role_rightpackage` 中查询该角色关联的所有权限包，区分规则生成权限包与自主申请权限包
- **Part3 自主申请锁定**：仅在 Part2 展开的自主申请权限包范围内，用需求语义进一步匹配锁定具体的自主申请权限包；若未识别出则不影响方案一得分，最终输出中自主申请权限包列表为空，仅包含规则生成权限包


### 方案二：基于权限包搜索
核心路径：需求语义 → 搜索 ai_role_rightpackage → 匹配权限包（可能多个）→ **跨包父角色交集收敛** → 反查父角色 → 锁定角色
- **Part1 权限包识别**：从需求中提取权限/权限包相关的关键词/范围后缀词，在 `ai_role_rightpackage` 表中以 `pkg_name` 字段搜索权限包。
  - **单包场景**：仅命中 1 个权限包 → 直接以该包作为 topPerm 传给 Part2
  - **多包场景**（命中 ≥2 个且均分数 ≥ **60**）：保留所有命中包，组成 `topPerms[]` 一并传给 Part2；Part1 分数取各命中包分数的 **平均值**
- **Part2 反查角色（含跨包父角色交集收敛）**：
  - **多包场景优先走交集收敛**：当 Part1 输出为 `topPerms[]`（≥2 个包）时，先做**跨包父角色交集收敛**：
    1. 对每个 `topPerms[i]`，反查其全部父角色集合 `parentRoles_i`（按 `ai_role_rightpackage.role_code` 聚合）
    2. 计算交集 `S = ∩ parentRoles_i`
    3. **若 S 非空** → 在 S 内按下方"角色排序规则"取第一个作为 `lockedRole`；同时本方案 Part1 分数 **额外 +5 分**（封顶 100）作为"联合置信加成"，反映多包共同锁定同一角色是更高置信度的信号
    4. **若 S 为空** → 降级：退回到单包最高分逻辑，以 `topPerms[]` 中分数最高的那个包为唯一输入继续下一步
  - **单包场景或降级后**：以唯一 topPerm 为输入，按以下**角色排序规则**取第一个作为 `lockedRole`：
    1. **角色名在需求原文中命中**：角色的 `role_name`（或去掉"角色"后缀的名称）在用户需求原文中能找到子串匹配的，排在最前面。例如用户需求中写了"申请数据资源使用角色"，则"数据资源使用角色"排在"其他人员角色"前面
    2. **`pkg_member_source` 规则生成优先**：在需求原文未命中角色名的候选中，该权限包在关联角色下的 `pkg_member_source` 为规则生成者优先于自主申请者
    3. **其他规则**：角色在需求语义中能找到其他关键字匹配者优先
- **Part3 角色锁定**：直接锁定 Part2 反查（或交集收敛）到的父角色

> 📌 **交集收敛典型案例**：用户需求命中权限包 `校招-招聘经理（报表）`、`校招-录用信息查看员（招聘）`、`资源-媒体道具申请人` 共 3 个（均 ≥60 分）。各自父角色集合的交集唯一为 `招聘经理角色(RecruitmentManager)` → 直接锁定，避免按最高分单包误选到 `BA-招活角色` 等其他父角色分支。


### 方案三：基于系统/功能反查
核心路径：需求语义 → 匹配系统/功能 → 命中权限包（可能多个）→ **跨包父角色交集收敛** → 反查关联角色 → 二次校验 → 锁定角色
- **Part1 系统识别**：从需求中提取系统/权限相关的关键词，优先在 `ai_rightpackage_sys_right` 表中匹配 `sys_name`（系统名称），系统匹配不到再匹配 `right_name`（权限项/功能名称）；同时在 `ai_rightpackage_data_rule` 表中匹配 `rule_cn_name`（规则中文名）。匹配命中后通过对应记录的 `pkg_code` 关联到权限包。
  - **单包场景**：仅命中 1 个权限包 → 直接以该包作为 topPerm 传给 Part2
  - **多包场景**（命中 ≥2 个且均分数 ≥ **60**）：保留所有命中包组成 `topPerms[]` 一并传给 Part2；Part1 分数取各命中包分数的 **平均值**
- **Part2 反查角色（含跨包父角色交集收敛）**：
  - **多包场景优先走交集收敛**：当 Part1 输出为 `topPerms[]`（≥2 个包）时，先做**跨包父角色交集收敛**：
    1. 对每个 `topPerms[i]`，通过 `ai_role_rightpackage` 反查其全部父角色集合 `parentRoles_i`
    2. 计算交集 `S = ∩ parentRoles_i`
    3. **若 S 非空** → 在 S 内按下方"角色排序规则"取第一个作为 `lockedRole`；同时本方案 Part1 分数 **额外 +5 分**（封顶 100）作为"联合置信加成"
    4. **若 S 为空** → 降级：退回到单包最高分逻辑，以 `topPerms[]` 中分数最高的那个包为唯一输入继续下一步
  - **单包场景或降级后**：以唯一 topPerm 为输入，通过 `ai_role_rightpackage` 反查关联角色，按以下**角色排序规则**取第一个作为 `lockedRole`：
    1. **角色名在需求原文中命中**：角色的 `role_name`（或去掉"角色"后缀的名称）在用户需求原文中能找到子串匹配的，排在最前面
    2. **`pkg_member_source` 规则生成优先**：在需求原文未命中角色名的候选中，该权限包在关联角色下的 `pkg_member_source` 为规则生成者优先于自主申请者
    3. **其他规则**：角色在需求语义中能找到其他关键字匹配者优先
- **Part3 角色锁定 + 降权二次校验**：锁定 Part2 反查到的角色后，执行以下降权校验：
  - **二次校验规则**：检查最终锁定的角色名（`role_name`）是否在用户需求原文中有任何关键词关联。具体做法：将角色名按常见分隔符（`-`、`_`、`/`、空格）拆分为子词，检查是否至少有一个子词（长度≥2）在需求原文中出现。例如角色名"数据运营-HRIS角色"拆分为["数据运营","HRIS","角色"]，若需求原文中不包含"数据运营"也不包含"HRIS"，则判定为**无关联**
  - **降权处罚**：若二次校验判定为无关联，则将方案三的 Part1 分数 **降低 30 分**（例如原始 80 分降为 50 分）。这确保当方案一/方案二能正确匹配时，方案三不会因为通用关键词的宽泛匹配而错误胜出
  - **不降权**：若二次校验判定角色名在需求原文中有关键词关联，则保持原始分数不变
  - **与联合置信加成的叠加顺序**：若同时触发"联合置信 +5"与"降权 -30"，按先加分后降分的顺序结算（最终分 = Part1 原始均分 + 5 − 30）


### 三方案选优与结果输出

#### 选优决策树（一图速览）

```
三方案全部执行完毕？
├── 否 → 继续等待
└── 是 → 进入选优逻辑
    │
    ├── 是否有方案得分 > 0？
    │   ├── 否 → 返回"未匹配到结果"，终止流程
    │   └── 是 → 取最高分方案
    │       │
    │       ├── 分数相同？
    │       │   ├── 是 → 按 方案一 > 方案二 > 方案三 排序
    │       │   └── 否 → 直接使用最高分方案
    │       │
    │       └── 胜出方案输出
    │           ├── 方案一：topRole → 展开权限包 → 锁定自主申请
    │           ├── 方案二：topPerm → 反查角色 → 二次展开权限包
    │           └── 方案三：topSystem → 反查角色 → 二次展开权限包
```

三个方案全部执行完毕后，执行以下选优逻辑，产出步骤一的最终输出：

#### 1. 选优规则

- 每个方案以其 Part1 分数（含加分/降权调整后的最终分）作为基准分
- 取**分数最高**的方案作为胜出方案
- 分数相同时按 **方案一 > 方案二 > 方案三** 优先级排序
- **零分兜底**：若三个方案的最终分数**均为 0**，则判定为未匹配到结果，直接返回提示信息"未能识别到与您需求匹配的角色或权限包，请检查需求描述或联系权限管理员"，终止后续步骤

#### 2. 胜出方案的权限包组装

不同方案胜出时，权限包列表的组装方式不同：

**方案一胜出**：
- `lockedRole` = Part1 的 topRole
- `ruleGeneratedPkgs` = Part2 展开的规则生成权限包（全部）
- `selfApplyPkgs` = Part3 锁定的自主申请权限包（语义匹配命中的部分，未命中则为空）

**方案二胜出**：
- `lockedRole` = Part2/Part3 反查锁定的角色
- **二次展开**：以 lockedRole 的 `role_code` 查询 `ai_role_rightpackage`，展开该角色关联的**全部权限包**，区分规则生成与自主申请
  ```sql
  SELECT pkg_name, pkg_code, pkg_domain, pkg_ctrl_dim, pkg_required_ctrl_dim,
         pkg_optional_ctrl_dim, pkg_member_source, role_division_dim, max_member_expiration
  FROM ai_role_rightpackage
  WHERE role_code = '{lockedRole.role_code}'
  ```
- `ruleGeneratedPkgs` = 二次展开中 `pkg_member_source = '规则生成'` 的权限包（全部）
- `selfApplyPkgs` = 二次展开中 `pkg_member_source = '自主申请'` 的权限包，在其中用需求语义进一步匹配锁定具体的自主申请权限包（未命中则为空）

**方案三胜出**：
- `lockedRole` = Part2/Part3 反查锁定的角色
- **二次展开**：与方案二相同，以 lockedRole 的 `role_code` 查询 `ai_role_rightpackage`，展开全部权限包
- `ruleGeneratedPkgs` = 二次展开中 `pkg_member_source = '规则生成'` 的权限包（全部）
- `selfApplyPkgs` = 二次展开中 `pkg_member_source = '自主申请'` 的权限包，在其中用需求语义进一步匹配锁定具体的自主申请权限包（未命中则为空）

## 步骤一.5详解 — 角色资格校验

### ✅ 执行检查点（步骤一.5 开始前必读）

- **入口条件**：步骤一已声明完成，已产出 `lockedRole` 候选列表
- **禁止动作**：禁止跳过本步骤直接组装 `submit_apply_form` 提交；禁止用 `query_staff_role_right` 的已有权限结果替代 `role_apply_validation` 的资格判断
- **必须动作**：从最高分候选角色开始调用 `role_apply_validation`（type=0），按返回的 `checkData` 判断角色 + 权限包是否可申请；不通过时降级到下一候选
- **完成声明**：执行完毕后向用户简述：「步骤一.5 完成：资格校验通过，保留角色 = 「XXX」，剔除 N 个不可申请的权限包」；若全部候选均不通过则声明"未匹配到可申请的角色，终止流程"
- **仅允许跳过的情况**：步骤二识别为"纯删除场景"时跳过本步骤（删除已有权限不需要资格校验）

> 🛑 **强制独立执行原则（不可被查询缓存替代）**：
>
> **无论上下文是否已调用过 `query_staff_role_right`，只要本次场景是新增 / 变更 / 续期，步骤一.5 必须独立执行，不可用查询结果复用替代。**
>
> 原因说明：
> - `query_staff_role_right` 只能告诉你"用户当前已持有什么权限"，**回答不了**"用户是否有资格申请 XX 角色"这个问题
> - 资格判断涉及管理者身份、职级、员工类型、部门归属等多维动态规则，**只能通过 `role_apply_validation` 接口实时校验**
> - 即使用户**当前已持有**目标角色的某些权限包（如变更场景、续期场景），仍必须重新走一次 `role_apply_validation`，因为：① 资格规则可能已变化；② 本次申请的权限包组合、范围可能和已有的不同
> - **禁止**以"上下文已查过该用户权限"、"用户已持有此角色"、"刚刚查询过了"等任何理由跳过本步骤
>
> **唯一允许跳过步骤一.5的情况**：本次场景判定为「**纯删除**」（下方"删除场景跳过本步骤"块说明的情况），此时因为是清理已有权限、不涉及新授权，无需校验资格。

> ⚠️ **删除场景跳过本步骤**：
> 若步骤二的「前置删除场景识别」判定本次需求为**删除场景**（含多意图拆任务后的删除子任务），则**直接跳过步骤一.5**，不调用 `role_apply_validation`。原因：用户已经持有要清理的权限，无需再校验"是否有资格申请"。
> 仅当本次场景为 **新增 / 变更 / 续期** 时，才执行下方的资格校验流程。

> ⚠️ **核心原则：资格判断的唯一来源是 `role_apply_validation` 接口返回值**
>
> - 资格是否通过、不通过的原因是什么 —— **全部且仅以 `role_apply_validation` 接口返回的 `checkData` 为准**
> - **禁止**自行推测或预判任何资格要求（例如：不得自行判断"该角色需要管理者身份"、"该职级不够"、"该员工类型不符合"等）
> - **禁止**通过查询员工信息宽表后自行分析"资格风险点"或"资格影响"
> - **禁止**在校验调用前输出类似"预计可能不通过因为 XXX"的预判
> - 唯一正确的做法是：组装参数 → 调用 `role_apply_validation` → 根据返回的 `checkData` 是否为空来判断 → 将接口原文作为不通过原因原样输出

步骤一产出候选角色列表（按分数从高到低排序）后，需对最高分角色调用 `role_apply_validation` 进行资格校验。若角色不可申请，则降级到分数次高的候选角色重试，直到找到可申请的角色或所有候选耗尽。

### MCP 工具

- **工具名称**：`role_apply_validation`
- **参数**：
  - `type`（integer，必填）：申请场景类型编码。新增 = `0`，变更 = `1`，续期 = `2`。此处因尚未完成步骤二场景识别，**默认传入 `0`（新增）** 进行校验
  - `data`（string，必填）：流程表单数据，按 `RoleRightApplyFormDTO` 结构组装 JSON 序列化后的字符串。此时仅需填充角色基本信息和权限包列表，维度范围可传空
- **返回值**：表单校验结果。校验信息通过各层级的 `checkData` 字段返回：
  - **角色级 `checkData`**：位于 `RoleFormItemDTO.checkData`，若不为空则表示该角色不可申请
  - **权限包级 `checkData`**：位于 `RightPackageItemDTO.checkData`，若不为空则表示该权限包不可申请

### 校验流程

```
步骤一输出：候选角色列表（按分数从高到低排序）
    │
    ▼
从最高分候选角色开始（currentRole = 候选列表[0]）
    │
    ▼
组装 RoleRightApplyFormDTO JSON，调用 role_apply_validation（type=0）
    │
    ▼
┌─ 检查角色级 checkData ──────────────────────────────────────────┐
│                                                                   │
│  角色 checkData 不为空（角色不可申请）                              │
│    → 记录不可申请原因                                              │
│    → 从候选列表中移除当前角色                                      │
│    → 如果候选列表还有剩余角色：                                    │
│        · 取下一个最高分角色，重新执行步骤一的权限包展开              │
│          （Part2 权限包展开 + Part3 自主申请锁定）                  │
│        · 重新调用 role_apply_validation 校验                            │
│    → 如果候选列表为空：                                            │
│        · 返回"未匹配到可申请的角色，请检查申请资格或联系管理员"    │
│        · 终止流程                                                  │
│                                                                   │
│  角色 checkData 为空（角色可申请）                                  │
│    → 继续检查权限包级 checkData                                    │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─ 检查权限包级 checkData ────────────────────────────────────────┐
│                                                                   │
│  逐个检查每个权限包的 checkData：                                  │
│    · checkData 为空（null）→ 权限包可申请，保留在列表中            │
│    · checkData 不为空 → 权限包不可申请，从列表中剔除               │
│                                                                   │
│  剔除后检查：                                                     │
│    · 规则生成权限包被剔除 → 正常，不影响角色申请                   │
│    · 自主申请权限包被剔除 → 正常，最终输出中不包含该权限包         │
│    · 所有权限包均被剔除 → 角色仍可申请（仅角色本身，无权限包）     │
│                                                                   │
└───────────────────────────────────────────────────────────────────┘
    │
    ▼
输出：校验通过的角色 + 过滤后的权限包列表
  → 替换步骤一的 lockedRole / ruleGeneratedPkgs / selfApplyPkgs
  → 传递给步骤二继续流程
```

### 候选角色降级规则

当最高分角色校验不通过时，按以下规则选择下一候选角色：

1. **三方案候选池**：步骤一的三个方案各自产出一个候选角色（方案一的 topRole、方案二反查的角色、方案三反查的角色），去重后最多3个候选。若多个方案锁定的是同一个角色（role_code 相同），则视为同一候选，只校验一次
2. **降级顺序**：按步骤一的方案分数从高到低排序（已排除当前不通过的角色），取下一个分数最高的方案对应的角色
3. **去重**：若多个方案锁定了同一角色（role_code 相同），视为同一候选，只校验一次
4. **重新展开**：降级到新角色后，需重新执行该角色的权限包展开（查询 `ai_role_rightpackage`），并重新用需求语义锁定自主申请权限包
5. **零分兜底**：若降级到的候选角色分数为 0，直接跳过，不校验
