# 用户权限查询展示规则（分层展示 + 自然语言优化版）

> 📁 **本文件归属**：`hr-right` Skill 的"用户权限查询"场景详解
> ⬆️ **返回主文档**：[SKILL.md](../SKILL.md)

本文件定义用户查询自己当前持有的权限（非申请操作）时的**分层展示规则**，核心设计原则：
- **信息分层**：概览 → 分类表格 → 单角色详情 → 单权限包明细，逐层展开
- **自然语言**：隐藏技术编码，用用户能看懂的业务语言呈现
- **按需加载**：默认输出概览 + 分类表格，用户追问时再深入下一层

---

## 用户权限查询展示规则

### 适用场景

当用户的需求**仅为查询自己当前持有的权限**（而非新增/变更/续期/删除申请）时，触发本规则。常见触发词：
- "我有什么权限"、"我的权限"、"查询我的权限"、"我有哪些角色"、"我的角色权限"、"我都有什么权限"
- "看下我的权限"、"列一下我的权限"、"展示我的权限"

> ⚠️ **与申请场景的区分**：若用户表述为"申请..."、"新增..."、"变更..."、"续期..."，则走 [步骤一~最后一步] 的标准申请流程，不走本节展示规则。

### 数据获取

#### 主数据

调用 `query_staff_role_right`（传入 `target_staff_name`），返回 `List<RoleFormItemDTO>`。

> **⛔ 查无此人时立即终止，禁止兜底**：
> - 若返回 `"未找到匹配的员工"` 或类似"查不到人"的错误信息 → **直接输出**：
>   ```
>   ❌ 未找到员工「{输入名}」，请确认姓名是否正确。
>      建议：使用英文名（如 keethyxu）或工号查询。
>   ```
> - **禁止**：继续调用 `query_my_staff_role_right`、SQL-R1 或任何其他接口做兜底
> - **禁止**：基于其他接口返回的数据编造权限输出
> - **原因**：`query_staff_role_right` 是权威的身份校验接口；其他接口（如 `query_my_staff_role_right`）可能在查不到人时返回当前登录用户自身数据或模糊匹配结果，用其输出属于伪造被查人权限

#### 补充数据（必须额外查询）

在展示前，需通过 `mysql_query` 补充以下数据：

```sql
-- SQL 1：批量查角色描述、领域、类型（用于职责一句话 + 分类）
SELECT role_code, role_name, role_desc, domain_name, role_type
FROM ai_role_def
WHERE role_code IN ({所有角色code});
```

> 若某角色在 `ai_role_def` 中查不到，则 `role_desc` 为空，后续用兜底策略生成职责描述。

## 第一层：权限概览（默认输出）

用户发起权限查询时，**首先且必须输出**本节。包含概述 + 三类角色表格 + 空角色说明 + 引导语。

### 概述（固定 4 句话，严格按以下模板输出）

```
## {用户姓名}的权限总览

{第1句}。{第2句}。{第3句}。{第4句}
```

| 句号 | 内容 | 数据来源 | 输出规则 |
|------|------|---------|---------|
| **第1句** | 数量 + 分类 + 范围 | `roleFormItemList` 过滤空角色后计数 + 业务语义分类 + Org 维度值去重 | "您当前持有 **N 个有效角色**（管理类 X 个 / 专业类 Y 个 / 基础类 Z 个），管辖范围集中在 **{一级组织列表}**及其下属子中心。" |
| **第2句** | 核心能力关键词 | 所有 `packageName` 提取业务域 | "核心能力覆盖 **{能力1}、{能力2}、{能力3}、{能力4}、{能力5}** 等方向。" 能力从权限包名中提炼，3~5 个，不超 5 个 |
| **第3句** | 是否有需处理事项 | 严格按阈值判断（见下方「到期判定」） | **有命中**："⚠️ 有 **N 条权限将在 30 天内到期**：{pkg1}({剩余X天})、{pkg2}({剩余Y天})，建议关注续期。" <br> **无命中**："目前所有权限状态正常，**无 30 天内到期项**，无需紧急处理。" |
| **第4句** | 引导语 | 固定模板 | "详细信息见下方分类表格，或告诉我您想深入了解某个角色。" |

> **强制约束**：
> - 概述**严格 4 句话**，不多不少
> - 第3句**禁止臆测**：没有 ≤30 天到期的就写"无需紧急处理"，不要写"半年后到期"等中长期信息
> - **禁止出现**：自主申请占比、来源分析、清理建议等主观推断内容
> - 每句话都必须有实际数据支撑，不能凭印象编造

### 到期判定规则（第3句专用）

仅对满足**全部**前置条件 + **任一**触发条件的权限记录进行筛查：

**前置条件（必须同时满足）**：

| 条件 | 说明 |
|------|------|
| `memberFrom = "apply"` | 仅筛查自主申请的权限（规则自动授予的不在此列） |
| `endDate != "9999-12-31"` | 排除长期有效 |
| `remainingDays > 0` | 排除已过期（过期的不叫"即将到期"，是已失效） |

**触发条件（满足任一即提醒）**：

| 条件 | 说明 |
|------|------|
| `totalDays > 30` 且 `remainingDays ≤ 30` | 长期授权但快到期的（如授权 1 年，还剩不到 1 个月） |
| `totalDays ≤ 30` 且 `remainingDays ≤ 7` | 短期授权且快到期的（如授权 1 个月，还剩不到 1 周） |

> **硬编码说明**：阈值 `30 天` 与 `7 天`、永久标记 `9999-12-31` 均为本 Skill 的固定规则。

- 有 ≥1 条命中 → 第3句输出到期警告
- 0 条命中 → 第3句输出"无30天内到期项"
- **禁止**：输出"暂无即将到期"等占位文案；将中长期到期（如193天后）列入提醒

### 角色分类规则（用于第一层表格分组）

分类基于**业务语义**（这个角色的用途是什么），**不依赖** `role_type` 字段。`role_type` 仅作为参考辅助。

#### 分类判定优先级（按顺序匹配，命中即停止）

| 优先级 | 归类 | 判定条件（满足任一即归入此类） | 典型示例 |
|--------|------|---------------------------|---------|
| 1 | **管理类** | 角色名含：负责人 / 上级 / 主管 / 管理者 / 分管人 / 汇报上级；<br>`role_desc` 含：管理 / 查看...下属 / 查看...团队 / 查看...人员 / 审批；<br>权限包用途为：敬满报告 / 人才透视 / 团队分析 / 汇报链 / L1-L4 默认授权 | 部门负责人、中心负责人、各层汇报上级、部门内分管人 |
| 2 | **专业类** | 角色名含：面试官 / 管理员 / 使用者 / 授权 / 平台部负责人（非管理视角）；<br>`role_desc` 含：进行...工作 / 负责...管理（文档/数据资产）/ 查询并审批；<br>权限包用途为：面试 / 薪酬查询 / 文档管理 / 数据规则 / AI问数 | 国内面试官、海外面试官、涉密库管理员、管理者薪酬授权 |
| 3 | **人员类** | 角色名含：正式人员 / 员工 / 用户；<br>`role_desc` 含：通用 / 基础；<br>权限包用途为：S3 访问 / 学习平台 / 门户 / BG 要闻 | 集团本部正式人员 |

> **兜底规则**：无法归入以上三类时 → 归入"其他类"。但正常情况下不应出现。
>
> **注意**：同一角色可能同时满足多类条件（如"各层汇报上级"在 `role_type` 可能是"专业角色"，但业务语义是管理者视角），**以业务语义为准**，`role_type` 不决定归类。

### 空角色处理

#### 定义

`rightPackageList` 为空 **或** 全部 `packageDataScopes` 为空的角色，视为"空角色"。

#### 处理规则

1. **从主表格中排除**：空角色不进入管理类/专业类/人员类表格
2. **概述数量不计入**：第1句的"N 个有效角色"不包含空角色
3. **表格末尾追加一句话**：

```
> 另外还有 {N} 个由系统根据您的汇报关系自动授予的角色（{角色名列表}），当前未绑定活跃权限包，故不在上表列出。
```

- N = 0 时 → 整句话**不输出**
- 角色名超过 3 个时 → 只列举前 2 个 + "等"，如"直接上级、间接上级等"
- **禁止**：写"可考虑清理"/"建议删除"等主观建议

### 第一层表格格式

表格按管理类 → 专业类 → 人员类的顺序排列，每类一个子标题：

```
### 一、管理类（作为管理者可查看的团队/下属信息）

| # | 角色 | 职责 | 管辖范围 | 权限包 |
|---:|------|------|---------|--------|
| 1 | **{角色名}** | {职责一句话} | {管辖范围} | {权限包名1} · {权限包名2} · ... |
| ... | ... | ... | ... | ... |

### 二、专业类（因具体业务工作需要获得的功能权限）

| # | 角色 | 职责 | 管辖范围 | 权限包 |
|---:|------|------|---------|--------|
| ... | ... | ... | ... | ... |

### 三、人员类（基础通用权限）

| # | 角色 | 职责 | 管辖范围 | 权限包 |
|---:|------|------|---------|--------|
| ... | ... | ... | ... | ... |

{空角色说明句（如有）}

---

### 四、数据类权限总览（报表）

{报表权限表格（有数据时）或无数据说明（无数据时）}

💬 {引导语}
```

#### 各列填充规则

| 列 | 数据来源 | 填充规则 |
|----|---------|---------|
| **#** | 表格行号 | 每个类别内部从 1 开始递进 |
| **角色** | `roleName` | **不显示 roleCode**。如有重复角色（如 HRIS 平台部负责人 与 人力资源平台部负责人 权限包相同），在角色名后标注 `*(同#N)*` |
| **职责** | `ai_role_def.role_desc`（优先）→ 兜底生成 | **优先使用 role_desc**：有值直接取原文（去掉过长的技术细节，保留业务含义）<br>**兜底策略**（role_desc 为空或无意义时）：结合 `domain_name` + `role_name` + 权限包名推导一句话，如：<br>- "人力资源平台部负责人" + domain="HR共享" → "负责人力资源平台部的整体管理工作"<br>- "国内面试官" + role_desc 含"面试" → "在指定组织范围内进行招聘面试工作" |
| **管辖范围** | `roleDataScopes`（优先）→ 取该角色下最关键的固定权限边界 | **分两类角色区别对待**：<br><br>**A. 固定管辖类**（负责人/管理者/面试官/管理员等）：<br>- 提取 Org 维度的 dimItemName，多个值用 `· ` 或 `+` 连接<br>- 值为"全部"/"全公司"/`Org-All` → 显示"全公司"<br><br>**B. 汇报链类**（各层汇报上级/直接上级/间接上级/间间接上级等）：<br>**Org 维度值不作为固定管辖边界展示**。原因：汇报链的本质是"**谁向我汇报"的人际关系，不是"我管哪个区域"的地域边界**。下属可能跨组织调动但汇报关系不变。<br><br>- 统一展示为 **"主岗向您汇报的全部人员"**<br><br><br>**禁止事项**：<br>- 禁止使用"主兼岗看主岗"/"主岗兼副岗"/"Major"/"下属分布在N个团队中"等啰嗦或技术性表述<br>- 禁止追加括号说明（如"(含集团本部及全资子公司)"、"（随汇报关系自动匹配)"等）<br>- **禁止将 Org 维度值作为管辖范围展示**<br><br>> **判定是否为汇报链类**：角色名含"汇报上级"、"上级"；或权限包名含"汇报上级"、"汇报链"；或 role_desc 含"查看...下属"、"查看...团队"。命中即归入 B 类。<br><br>**禁止**：展示 dimItemCode 编码（如 4791、46012） |
| **权限包** | `rightPackageList` 中每个权限包的 `packageName` | 用 ` · ` 连接，**不显示数量统计**（不写"(共7个)"）<br>同一权限包有多条 `packageDataScopes` 记录时，权限包名只出现一次；若不同记录的范围差异大，可在名称后备注"（N条不同范围记录）"<br>权限包过多（>8个）时，可适当省略非核心项，用 `...` 收尾 |

### 四、数据类权限总览（报表）

> 本节展示用户当前持有的 **DIY 报表** 类权限明细。
> 报表是 HR 数仓中可由用户自主组合字段、筛选条件生成的数据表，
> 每张报表的访问权限通过「权限包」授予，不同报表的行/列权限范围可能不同。

#### 适用范围

**始终输出**（与第一层角色分类表格同级），不受用户追问触发控制。
若用户无任何报表类权限 → 输出空表格 + 说明文字（见下方「无数据时的处理」）。

#### 数据获取

##### 主数据源：根据查询对象选择不同命令

**这是两个完全不同的 MCP 命令，不可混用**：

| 查询对象 | 命令 | 入参 | 报表相关返回字段 |
|---------|------|------|----------------|
| **查本人** | `query_my_staff_role_right` | 无入参 | `dataRightItemList`（报表清单摘要） |
| **查他人** | `query_staff_role_right` | 必传 `target_staff_name` | `dataRightItemList`（报表清单摘要） |

两个命令均返回 `dataRightItemList` 字段，结构如下（**轻量摘要，不含行列权限明细**）：

```json
{
  "dataRightItemList": [
    {
      "reportCode": "Report_Wide_Public_Staff_Info",
      "reportName": "员工信息宽表",
      "columnCount": 236,
      "mcpFlag": true
    }
  ]
}
```

> **字段说明**：
> - `reportCode`：报表编码（即权限项编码 right_code），用于后续逐表调用详情接口
> - `reportName`：报表中文名
> - `columnCount`：该报表总字段数量（用于判断列权限范围）
> - `mcpFlag`：该报表是否接入 MCP（布尔值，快速判断）
>
> **注意**：`dataRightItemList` 仅提供"报表清单索引"，**不含** `rowDataRight`（行权限明细）和 `columnDataRight`（字段级列表）。这些明细必须通过 `query_my_report_auth_detail` 逐表获取。

> ⚠️ **历史说明（已废弃）**：
> 早期版本中主查询接口曾返回名为 `ReportRowColumnRightList` 的字段（含 rowDataRight + columnDataRight 明细），
> 但当前版本已不再返回此字段。若在其他文档或旧代码中看到此字段名，请视为过时引用。

##### 补充数据源（关联查询）

| 补充项 | 获取方式 | 调用时机 |
|--------|---------|---------|
| 报表 ↔ 权限包 ↔ 角色映射关系 | SQL-R1（见下方） | 首屏展示前（与 `query_my_staff_role_right` 并行） |
| 单张报表 mcp_flag + columnDataRight | `query_my_report_auth_detail(reportCode)` | **首屏展示前**，对 SQL-R1 返回的每张报表逐条调用 |
| 单张报表深度详情（用户追问时复用） | `query_my_report_auth_detail(reportCode)` | 用户追问某张报表时复用缓存或重新调用 |

###### SQL-R1：报表-权限包-角色映射

```sql
-- 用于将 packageName 反向映射到 role_code/role_name 和有效期的辅助查询
SELECT
    sr.right_code,
    sr.right_name,
    sr.pkg_code,
    sr.pkg_name,
    rp.role_code,
    rp.role_name
FROM ai_rightpackage_sys_right sr
JOIN ai_role_rightpackage rp ON sr.pkg_code = rp.pkg_code
WHERE rp.role_code IN ({用户持有的所有 roleCode})
  AND (
      sr.right_type = '规则库档案（报表）'
      OR sr.right_code LIKE 'Report%'
  )
ORDER BY sr.right_name;
```

> **报表识别规则**（硬编码，不得修改）：
> - `right_type = '规则库档案（报表）'` — 权限项类型为报表
> - `right_code LIKE 'Report%'` — 权限项编码以 Report 开头
> - 两者满足任一即归入本表

##### 数据来源规则

**核心原则：必须逐表调用 `query_my_report_auth_detail` 获取完整的多来源权限，不得仅用 `dataRightItemList` 或 SQL-R1 单一来源输出。**

`query_my_staff_role_right` 返回的 `dataRightItemList` 仅携带**触发查询角色的单一来源**，会遗漏同一用户其他角色/权限包对该报表的授权。因此 `dataRightItemList` 只能用作"报表清单索引"（知道有哪些表），**每张表的行权限、列权限、来源角色等详情必须以 `query_my_report_auth_detail` 返回为准**。

具体步骤：

1. 先从 `query_my_staff_role_right` 的 `dataRightItemList` 获取**报表清单**（表名 + reportCode），仅用于确定"有哪几张表"
2. **对清单中每一张报表，在首屏输出前必须逐条调用** `query_my_report_auth_detail(reportCode="{reportCode}")`（参数名用驼峰 `reportCode`，无 targetStaffName 参数）：
   - 该接口返回的是该用户对此报表的**全量授权记录数组**（顶层 `data` 字段，可能包含 1~N 条；另有 `total` 计数和 `hasMore` 分页标记）
   - 每条记录包含：`packageName`（来源权限包名）、`rowDataRight`（行权限：维度中文名→值列表）、`columnDataRight`（列权限：字段对象数组，每项含 assetCode + mcpFlag + displayName）
3. 以 `query_my_report_auth_detail` 返回的全量记录作为第四节表格的**唯一权威数据源**
4. 若某张报表的 `query_my_report_auth_detail` 调用失败或返回空 → 兜底取 `dataRightItemList` 中对应行的信息，并在行范围列标注 **"(数据待补全)"**

#### 去重与合并展示规则

同一张报表（`reportCode`）可能通过多个权限包/多个角色重复授权，`query_my_report_auth_detail` 会返回多条记录：

- **去重粒度**：以 `reportCode` + `packageName` 为联合主键（同一权限包下去重）
- **合并展示（核心规则）**：当同一张报表被多个权限包授权时，**合并为一行展示**，按以下规则聚合各列：

| 列 | 合并方式 |
|----|---------|
| **表名** | 显示一次 |
| **是否接入MCP** | 任一来源有 mcpFlag=true 即显示 ✅ 已接入 |
| **行权限范围** | **组织维度的合并优先级规则**（见下方详述） |

##### 行权限范围 — 组织维度合并优先级

当同一张报表的不同来源包含不同的组织范围码值时，按以下优先级合并为一条摘要：

1. **若有"全公司"** → 直接显示 **"全公司"**（无需罗列其他）
2. **若无全公司但有多个组织码** → 去重后按以下规则选择代表值：
   - **组织层级越少优先**（即 `/` 分隔符越少的优先）：如 "S3职能系统－HR与管理线" 优于 "S3职能系统－HR与管理线/人力资源平台部"
   - **层级相同时，取覆盖面较广的**（如人数较多的）
3. **组织数量过多（>3 个）时** → 采用缩写格式：
   - 显示格式：**"{最优代表组织} 等 {N} 个"**
   - 示例：`"S3职能系统－HR与管理线 等 5 个"` 或 `"全公司 等 3 个主体"`
   - 其中 **"全公司"** 如果出现在候选中必须优先使用，不走缩写

> **设计理由**：行范围列的目的是让用户快速判断"我能看多大范围的数据"，而非列出完整的维度枚举。因此优先展示最宽泛（全公司）或最简洁（层级最少）的代表值，其余用"等 N 个"收起，既保证准确性又避免表格爆炸。

| `"9999-12-31"` | "长期" |
| 其他 | 直接显示日期，或 `{startDate} ~ {endDate}` |
| startDate 为空 | 仅显示 `endDate` |

## 第三层：单权限包数据范围明细（用户再次追问时触发）

当用户说"某个权限包的具体范围"、"XX权限包管哪些部门"时，进入本层。

### 触发词

- "{权限包名} 的具体范围"
- "{权限包名} 详细数据"
- "{权限包名} 管哪些"

### 展示格式

```
## {权限包名} — 完整数据范围

> 这些范围决定了：当您打开「{权限包名}」功能时，
> 系统会筛选出哪些人的数据供您查看。超出这些范围的数据，您看不到。

---

### 您能看到谁的数据？（共 N 个维度）

| 维度 | 取值 |
|------|------|
| 🏢 **{用户友好名称}** | {友好值_1} · {友好值_2} |
| 📊 **{用户友好名称}** | {友好值} |
| ...（逐项列出所有维度） |

```

#### 模板填充约束

| 约束 | 说明 |
|------|------|
| **禁止编造补充说明** | 值本身就是完整信息（如 `全公司`），禁止追加接口未返回的额外文字 |
| **仅在有明确补集时写不包含** | 当范围明显有边界时才提 `❌ 不包含：xxx`；值为全公司/全部时不写 |
| **表格格式** | 使用两列表格：左列=维度名（含emoji），右列=码值（多个值用 `· ` 连接）。这是第三层的标准呈现方式，确保"哪个维度→哪些值"的关系一目了然 |

#### 维度展示规则

**核心原则：与角色展示一致，禁止出现任何技术编码或系统语言。以下规则是对上方通用映射表的补充，冲突时以映射表为准。**

> ⚠️ **第三层 = 全量展开层**：必须逐项列出该权限包 `packageDataScopes` 中的**每一个维度**及其码值，不得省略任何维度。这是第二层（仅摘要）和第三层的本质区别——用户进入此层就是要看到完整的数据边界。

| 规则 | 说明 |
|------|------|
| **维度标题格式** | `🏢 **{用户友好名称}** — {解释性问句}`<br>标题中的维度类型名**必须使用「维度类型友好映射表」中的用户展示名称**，禁止原样输出 `dim_type_name`<br>解释性问句由「权限包名 + 用户友好名称」动态生成：<br>- 组织 → "范围覆盖哪里？"<br>- 专业职级 → "能看到哪些职级的人？"<br>- 管理职级 → "能看到哪些管理层级？"<br>- 用工类型 → "包含哪类用工人员？"<br>- 办公地 → "覆盖哪些办公地点？"<br>- 在职状态 → "包含什么状态的人员？"<br>- 签约公司 → "覆盖哪些签约主体？"<br>- 数据视角 → "能看到哪个视角的数据？"<br>- 数据时间范围 → "能看到多久的数据？"<br><br>**去重规则**：问句中禁止重复维度名中已出现的字词。如"组织/部门"的问句不能用"哪些**部门**"，应改为"范围覆盖哪里？" |
| **维度值** | 使用 `dim_item_name`（中文名），**禁止使用 dim_item_code**<br>所有值**必须经过「维度值友好映射表」转换**后再展示<br>优先使用 `dim_item_full_name`（全路径，如"S3职能系统/HR与管理线/人力资源平台部"），比短名称更有定位感 |
| **值过多时的处理** | 超过 6 个值时，展示前 4 个 + `...（共N个）`，避免刷屏 |
| **同时展示有/无** | 当范围明显受限时（非"全部"），可以在说明中提一句"❌ 不包含：xxx"，让用户感知边界。但不需要刻意构造"无"列表——只在不言自明时顺带一提 |
| **维度排序** | 按"组织 > 员工属性（职级/状态/类型） > 时间 > 其他"排列，最重要的放最前面 |
| **兜底日期处理** | `1990-01-01`、`2007-01-01` 等明显的历史兜底日期 → 展示为 **"不限"** 或直接不显示时间限制说明 |

## 反向兼容：不再使用的旧规则

以下旧规则已被本版本**替代**，执行时不得沿用：

| 旧规则 | 旧行为 | 新行为 |
|--------|--------|--------|
| 展示 roleCode | `` ### N. {角色名} `{code}` `` | **隐藏 code**，只显示角色名 |
| 来源列 | 展示"规则/自主申请" | **移除该列**（对用户无意义） |
| 有效期列 | 每行都显示 | **仅在第二层（单角色详情）展示**，第一层不展示 |
| 范围全量展开 | 所有维度 `【type】: value; ...` | **第一层只显主维度**，第三层才全量展开 |
| 即将到期宽泛阈值 | totalDays > 30 且 remainingDays ≤ 30 **或** totalDays ≤ 30 且 remainingDays ≤ 7 | **不再单独输出中长期到期提醒节**（见第一层概述第3句）；到期判定公式不变（仍为双条件 + 4 前置条件），仅当命中时在角色/权限包行内标注"⚠️ 即将到期 N 天"。不命中则整节不输出 |
| role_type 决定分类 | 用 ai_role_def.role_type 的大类排序 | **改用业务语义分类**（管理/专业/人员），role_type 仅参考 |
| 概览只有一行数字 | "共持有 N 个角色，M 个权限包" | **改为 4 句话概述**（数量/能力/状态/引导） |
| 权限包带数量 | "包A · 包B · 包C（共 7 个）" | **去掉括号数量统计** |
