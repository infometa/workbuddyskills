## 前置：删除场景识别（独立于方案A/方案B 的判断路径）

**触发关键词**（命中任一即视为有"删除"意图）：
- 清理、删除、撤销、移除、取消、去掉、剔除、作废、注销

### ⚠️ 清理粒度二分（极其重要）— 决定走哪个 MCP 命令

用户的"清理/删除"措辞，按**粒度**分为两类，对应**不同的 MCP 命令**——这是后续"拆/不拆"判定的关键：

| 用户描述 | 清理粒度 | 走的 MCP 命令 | type |
|---|---|---|---|
| "清理整个 A 角色" / "整个 A 角色都不要了" / "把 A 角色清掉" | **整角色** | `clear_role_package(roleCode="A")` | — |
| "清理 A 角色下的 A1 权限包" / "把 A1 权限包整个清掉" | **整权限包** | `clear_role_package(roleCode="A", rightPackage="A1")` | — |
| "清理 A 角色下的某条分工"（按 rowId 删某条 `roleDataScopes`） | **角色级一组分工** | `submit_apply_form` | `1` (operationType="Delete") |
| "清理 A1 权限包下的某条范围"（按 rowId 删某条 `packageDataScopes`） | **权限包级一组范围** | `submit_apply_form` | `1` (operationType="Delete") |

> **判定要点**：
> - 用户说"清理**整个** XX" / "XX **都**不要了" / "把 XX **清掉**"（无更细的限定词）→ 整角色/整权限包 → `clear_role_package`
> - 用户说"清理 XX 的**某一组** / 某条" / 用户在多条记录中**勾选某条** → `submit_apply_form` Delete

### 整包/整角色清理的命令选择

| 用户场景 | 推荐命令 | 原因 |
|---|---|---|
| 清理某权限包下的全部记录（用户**没明说**不要列单） | 先 `query_staff_role_right` 列清单 → 用户勾选 → `submit_apply_form` 多条 Delete | 安全优先，可逐条核对 |
| 清理某权限包下的全部记录（用户**明确说**"全部清理 + 不要列单"） | `clear_role_package(roleCode, rightPackage)` | 一次性 |
| 清理整个角色（用户明确说"整个 XX 角色都不要了"） | `clear_role_package(roleCode)` | 不传 rightPackage 即清整角色 |

> **默认偏好**：本 Skill **优先采用"列清单 + 用户勾选 + `submit_apply_form` Delete"**的方式，仅在用户**明确说"全部清理 + 不要列单"**时才使用 `clear_role_package`。

**其他删除触发模式**：
- "不要这个 XX"、"把 XX 清掉"、"我不想要 XX 了"
- 否定 + 移除组合句式

**判定条件**（同时满足）：
1. 用户措辞命中上述关键词之一
2. `query_staff_role_right` 中能找到与用户描述匹配的有效授权记录

**该路径的执行链路**：
```
用户输入
  │
  ▼
关键词识别 → 命中删除关键词
  │
  ▼
跳过步骤一（不做三方案识别）
跳过步骤一.5（删除已有权限不需要资格校验）
跳过步骤三（不做范围识别，直接用已有记录的原维度值）
  │
  ▼
调用 query_staff_role_right 查询用户已有授权记录
  │
  ▼
按用户描述精确定位待删除记录（详见下方"删除场景精确定位流程"）
  │
  ▼
步骤四（申请说明：原文）→ 输出删除场景表格 → 用户确认 → submit_apply_form (type=1, operationType=Delete)
```

### 删除场景精确定位流程

1. **唯一匹配**：用户描述的角色/权限包 + 维度组合，在 `query_staff_role_right` 中**精确匹配到唯一的 `rowId`** → 直接锁定该记录，进入用户确认流程
2. **多条匹配**：若同一权限包下有**多条记录**与用户描述匹配（如同一个 `hrrightMgr` 权限包既有 BP领域 又有 人员领域 等多条），或用户用模糊表达（如"清理我的BA-HRIS角色"未指定具体哪条）→ **必须列出所有匹配候选的明细表（含 rowId、维度值、有效期），让用户明确选择哪些 rowId 需要删除**，**严禁擅自删除多条**
3. **整包/整角色清理**：用户明确表达"把整个 xxx 权限包都清掉"或"整个 xxx 角色都不要了"→ **本 Skill 优先采用"列出该权限包/角色下所有记录的 rowId，让用户确认逐条 Delete"** 的方式（更安全可逐条核对）。**仅当用户明确说"全部清理且不要列单"时**，才改用 `hr-auth-copilot` MCP 的 `clear_role_package` 命令（传 `roleCode + rightPackage` 清整包；仅传 `roleCode` 清整角色）
4. **无匹配**：用户描述的范围在已有记录中不存在 → 提示用户"未找到匹配的有效授权记录，无需清理"，终止流程

### 删除场景对应字段

- **整体 type**：`1`（变更）
- **被删除记录的 `operationType`**：`"Delete"`
- **被删除记录的 `rowId`**：必填，使用 `query_staff_role_right` 返回的 `rowId` 原值
- **角色 `isNewApply`**：`false`
- **删除层级支持**：
  - **角色级删除**：删除 `RoleFormItemDTO.roleDataScopes` 中的某条记录（即清理角色的某条分工）
  - **权限包级删除**：删除 `RightPackageItemDTO.packageDataScopes` 中的某条记录（即清理权限包的某条范围）

> **删除 vs 变更的关键区别**：
> - **变更**：保留 rowId 这条记录，修改其维度码值（`operationType="Update"`）
> - **删除**：移除 rowId 这条记录本身（`operationType="Delete"`）

### 整包/整角色清理：`clear_role_package` 命令文档

当用户明确要求"把整个权限包/整个角色一次性清掉"且**确认不需要逐条核对**时，使用 `clear_role_package` 命令（writeOperation=true，不可逆）。

| 项 | 内容 |
|---|---|
| **MCP 服务** | `hr-auth-copilot` |
| **MCP 工具** | `execute` |
| **命令名** | `clear_role_package` |
| **写操作** | ✅ writeOperation=true（不可逆，可能触发弱校验二次确认） |

**入参**：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `roleCode` | String | ✅ 是 | 待清理的角色编码（如 `BA_HRIS`） |
| `rightPackage` | String | ❌ 否 | 待清理的权限包编码：**留空时清理该角色下的所有权限包**；填写时仅清理指定权限包 |
| `target_staff_name` | String | ❌ 否 | 清理目标人员：**留空时清理调用人本人**；填写时清理指定人员（需要相应授权） |

**调用示例 1：清理某个角色下的某一个权限包（保留其他权限包）**

```json
{
  "command": "clear_role_package",
  "args": {
    "roleCode": "BA_HRIS",
    "rightPackage": "hrrightMgr"
  }
}
```
> 影响范围：BA-HRIS 角色下 hrrightMgr 权限包的**所有记录**（多条 rowId 全部清理），其他权限包不动

**调用示例 2：清理整个角色（含其下所有权限包）**

```json
{
  "command": "clear_role_package",
  "args": {
    "roleCode": "BA_HRIS"
  }
}
```
> 影响范围：BA-HRIS 角色 + 其下所有权限包的**所有记录** — 极大影响，必须二次确认

**调用示例 3：替别人清理（需要本人有相应授权）**

```json
{
  "command": "clear_role_package",
  "args": {
    "roleCode": "BA_HRIS",
    "rightPackage": "hrrightMgr",
    "target_staff_name": "zhangsan"
  }
}
```

### 整角色清理时的提示语规则（⚠️ 重要：角色来源 vs 权限包来源需区分）

> 当执行**整角色清理**（`clear_role_package(roleCode)`）时，列出待清理记录后、等待用户确认前，必须根据 **角色来源（role 级 memberFrom）** 和 **权限包来源（package 级 memberFrom）** 的组合情况输出不同的提示语。**严禁混淆「角色不支持清理」和「权限包不能逐个删」两种完全不同的情况。**

**判定逻辑（基于 `query_staff_role_right` 返回数据）**：

| 角色 memberFrom | 权限包 memberFrom 分布 | 含义 | 提示语模板 |
|---|---|---|---|
| `"apply"`（自主申请角色） | 全部/部分为 `"rule"`（规则生成） | 角色是用户自己申请的 → **整角色可清**；但权限包是系统自动绑定的 → **不可逐个权限包删除** | ✅ 使用模板 A |
| `"apply"`（自主申请角色） | 全部/部分为 `"apply"` 或 `null`（自主申请/用户自选） | 角色和权限包都是用户主动选择的 → **整角色和逐权限包均可清** | ✅ 使用模板 B |
| `"rule"`（规则生成角色） | 全部为 `"rule"`（规则生成） | 角色本身由系统根据员工身份自动授予 → **整角色也不支持自主清理** | ✅ 使用模板 C |
| 无 / 缺失（无法判断） | 任意 | 无法确定角色来源 → 按最保守方式提示 | ✅ 使用模板 C |

> **如何获取角色级 memberFrom**：`query_staff_role_right` 返回的 `RoleFormItemDTO` 本身不直接包含角色级 `memberFrom` 字段。可通过以下方式间接判断：
> - 若该角色的任一权限包的 `memberFrom = "apply"` → 该角色大概率是**自主申请角色**（因为规则生成的权限包不会出现 `memberFrom="apply"`）
> - 若该角色下**所有**权限包的 `memberFrom = "rule"` 且该角色属于**人员角色/集团本部类角色**（如 `GroupHeadquartersRegularStaff`）→ 该角色大概率是**规则生成角色**
> - 若仍无法确定 → 按模板 C（保守）处理

**模板 A — 自主申请角色 + 权限包含规则生成**（最常见的高风险场景）

```
> ⚠️ 该角色为【自主申请】，支持整角色自主清理；
> 但该角色下 N 个权限包均为「规则生成」来源（跟随角色自动绑定），不支持按权限包逐个单独清理。
> 执行整角色清理将一并移除上述所有权限包。
```

**模板 B — 自主申请角色 + 权限包均为自主申请**

```
> ℹ️ 该角色及其下所有权限包均为自主申请来源，支持整角色清理或按权限包逐个清理。
```

**模板 C — 规则生成角色 / 来源不明**（保守提示）

```
> ⚠️ 该角色下的授权全部基于规则配置生成（或无法确定角色来源），可能不允许自主清理。
> 是否仍尝试执行？
```

> **核心纠正原则**：
> - **角色是自主申请的** → `clear_role_package` 整角色清理**可以成功**（如信息安全管理-HRIS角色）
> - **角色是规则生成的** → `clear_role_package` 整角色清理**会被后端拒绝**（如集团本部正式人员角色）
> - **权限包是规则生成的** → 仅影响「能否按权限包逐个删」，**不影响整角色清理是否成功**
> - **错误做法**：看到权限包全是 `memberFrom="rule"` 就暗示"可能不支持清理"——这是把「权限包粒度」的约束错误泛化到了「角色粒度」

### 何时用 `submit_apply_form Delete` vs `clear_role_package`？

| 用户场景 | 推荐方案 | 原因 |
|---|---|---|
| 清理某条具体记录（按 rowId） | `submit_apply_form (type=1, operationType=Delete)` | 精确控制，可保留其他记录 |
| 清理某权限包下的全部记录（数量少，可列） | `submit_apply_form` 多条 Delete 一次提交 | 用户可逐条核对，更安全 |
| 清理某权限包下的全部记录（数量多，且用户明说不要列单） | `clear_role_package(roleCode, rightPackage)` | 一次性，简洁 |
| 清理整个角色（用户明确说"整个 XX 角色都不要了"） | `clear_role_package(roleCode)` | 不传 rightPackage 即清整角色 |
| 整包/整角色清理但用户希望先看清单 | 先 `query_staff_role_right` 列清单 → 用户勾选 → `submit_apply_form` 多条 Delete | 安全优先 |

> ⚠️ **默认偏好**：本 Skill 优先采用"列出待清理记录让用户确认"的方式（即 `submit_apply_form` Delete），仅在用户**明确说"全部清理 + 不要列单"**时才使用 `clear_role_package`。

## 多意图处理（按 MCP 调用粒度判定 拆/不拆）

> ⚠️ **核心规则（强制）**：是否拆任务的**唯一判定标准**——
> **能否用同一个 MCP 命令的同一次调用完成所有子操作**：
> - **能** → **不拆**，组装一笔单据/调用一次性提交
> - **不能** → **拆**，按 (命令, type) 分组，每组一笔，按用户指定顺序逐笔处理

### 「新增"目标对象"」的判定（重要前提）

判定一个操作是 type=0（新增）还是 type=1（变更内追加），**唯一标准是 `query_staff_role_right` 中"用户当前是否持有目标对象"**：

| 用户表达"新增 X" | 当前是否持有 X | 走的命令/type |
|---|---|---|
| 新增 A 角色 | ❌ 否 | `submit_apply_form (type=0)` — 全新申请 |
| 新增 B 权限包 | ❌ 否 | `submit_apply_form (type=0)` — 全新申请（角色 isNewApply=false 若已持角色，否则 true） |
| 新增 C 角色下的一组分工 | ✅ 是（已持有 C 角色） | `submit_apply_form (type=1, operationType="Add")` — 在已有角色下追加分工 |
| 新增 D 权限包下的一组范围 | ✅ 是（已持有 D 权限包） | `submit_apply_form (type=1, operationType="Add")` — 在已有权限包下追加范围 |

> **关键**：用户说"新增" ≠ 一定是 type=0。**先查 `query_staff_role_right`**，再决定 type。

### (命令, type) 分组规则

每个子操作先确定其 **(MCP命令, type)** 元组，然后按元组分组：

| 操作描述 | (命令, type) |
|---|---|
| 申请未持有的角色/权限包 | `(submit_apply_form, 0)` |
| 已持有角色/权限包：追加 / 修改 / 精确删除某条 roleDataScopes 或 packageDataScopes 记录 | `(submit_apply_form, 1)` |
| 已持有角色/权限包：仅延长有效期（范围完全不变） | `(submit_apply_form, 2)` |
| **已持有同一条记录：同时变更范围 + 延长有效期** | `(submit_apply_form, 1)` — **归入 type=1 Update 一笔，不得误判为需拆分成 type=1 + type=2 两笔** |
| 整角色清理 | `(clear_role_package, —)` ※ 该命令无 type 参数 |
| 整权限包清理 | `(clear_role_package, —)` |
| 撤回审批中单据 | `(revoke_apply_form, —)` |

> ⚠️ **重要补充规则：变更 + 续期合并（强制，不得再向用户二次选择）**
>
> 当用户在**同一条 `packageDataScopes` / `roleDataScopes` 记录**（同一 `rowId`）上**同时发起"变更范围"与"延长有效期"**时：
> - **SKILL 必须直接组装一张 type=1 Update 单**，`dataScopeDimItems` 填变更后的完整维度集合，同时修改该条记录的 `endDate`
> - **严禁**让用户在"A：拆 2 笔（type=1 + type=2）"和"B：合一笔 type=1 Update"之间二次选择
> - **严禁**先走 type=1 Update 改范围，等审批通过后再走 type=2 续期（会导致用户多审批一次，且"范围改了但 endDate 没延"的中间态）
> - 直接按最优路径 type=1 Update 一笔提交，填单表内同时展示范围变化行与 endDate 变化行即可
>
> **反例**（SKILL 曾经的错误行为，必须规避）：
> - ❌ 识别为"元组不同（type=1 vs type=2）→ 必拆 2 笔"
> - ❌ 提供"方案 A / 方案 B"让用户选择
>
> **正例**：
> - ✅ 直接输出一张 type=1 Update 填单表（含新范围 + 新 endDate），等用户确认后一笔提交

**判定**：
- 所有子操作的 (命令, type) 元组**完全相同** → **不拆**，合并到同一笔
- 存在不同元组 → **必拆**，每个元组一笔，按用户指定顺序处理

### 8 个标准案例（必读）

| # | 用户场景 | 子操作 (命令, type) | 拆/不拆 | 说明 |
|---|---|---|---|---|
| **1** | 清理 A 角色 + 新增 B 角色 | `(clear_role_package, —)` + `(submit_apply_form, 0)` | ✅ 拆 | 不同命令 |
| **2** | C 角色：清理一组分工 + 新增一组分工 | 都是 `(submit_apply_form, 1)` 内的 `roleDataScopes`：Delete + Add | ❌ 不拆 | 同命令同 type，一笔 type=1 内组合 |
| **3** | 清理 A 权限包 + 新增 B 权限包（用户未持有 B） | `(clear_role_package, —)` + `(submit_apply_form, 0)` | ✅ 拆 | 不同命令 |
| **4** | C 权限包：清理一组分工 + 新增一组分工 | 都是 `(submit_apply_form, 1)` 内的 `packageDataScopes`：Delete + Add | ❌ 不拆 | 同命令同 type |
| **5** | C 权限包：清理一组分工 + 变更一组分工 | 都是 `(submit_apply_form, 1)` 内的 `packageDataScopes`：Delete + Update | ❌ 不拆 | 同命令同 type |
| **6** | A 角色：清理 A1 权限包 + 新增 B1 权限包（用户未持有 B1） | `(clear_role_package, —)` + `(submit_apply_form, 0)` | ✅ 拆 | 不同命令 |
| **7** | 清理 A 角色的 A1 权限包 + B1 权限包新增一组分工（用户已持有 B1） | `(clear_role_package, —)` + `(submit_apply_form, 1)` | ✅ 拆 | 不同命令 |
| **8** | 同一条 packageDataScopes 记录：**扩大/变更范围 + 延长有效期** | 全部归入 `(submit_apply_form, 1)` 的 Update | ❌ 不拆 | **强制合并一张 type=1 Update 单**（同时改维度码值 + endDate），禁止拆成 type=1 + type=2 两笔，也禁止向用户二次确认拆还是合 |

> **观察**：
> - 例 2/4/5/8 都是单命令单 type 内的 Add/Update/Delete 任意组合，**全部不拆**。
> - 例 8 是本 Skill 最常误判场景：用户同时要求"扩范围+续期"，**必须**默认走 type=1 Update 一笔合并，禁止让用户选择 A/B 方案。
> - 例 1/3/6/7 都涉及 `clear_role_package` 和 `submit_apply_form` 两个命令，**全部拆**。

### 拆任务时的执行流程

当判定为"拆"时，按以下流程执行：

1. **逐项摘要呈现**（先告知用户拆分计划）：
   ```
   此次需求涉及多个独立操作（无法用单次 MCP 调用完成），需拆分为 N 笔依次处理：
   - 子任务 1：[描述] —— 走 [命令] [type描述]
   - 子任务 2：[描述] —— 走 [命令] [type描述]
   ...
   现在我们先处理【子任务 1：xxx】，完成后再启动【子任务 2：yyy】。
   ```
2. **可选：让用户调整顺序**（用户没主动调整则按上述顺序执行）
3. **处理子任务 1**：走对应场景路径 → 输出填单表格 → 等用户确认 → 调用 MCP → 告知"子任务 1 已完成"
4. **等用户回复肯定词**（详见「🔑 用户确认词集」）后，开始处理子任务 2
5. **逐项推进**直到全部完成
6. **支持中途中止**：用户在任意子任务表态"先不处理后面的"时立即停下；已完成的不撤回（写操作不可逆），未提交的丢弃

### 不拆任务时的执行流程

当判定为"不拆"时（同命令同 type）：

1. 在**一个** `RoleRightApplyFormDTO` JSON 中组装所有子操作（如同一权限包下 Add+Update+Delete 三条 `packageDataScopes` 元素并存）
2. 输出**一张**填单表格让用户确认（不要拆成多张）
3. 调用**一次** `submit_apply_form`

### 反例（禁止）

- ❌ 因为"操作多"就盲目拆（例 2/4/5 不拆）
- ❌ 因为"用户没说怎么排序"就自己决定（要么按拆分顺序问、要么按默认顺序告知后等用户认可）
- ❌ 用户没回复肯定词就开始下一项
- ❌ 把不同命令或不同 type 的操作合并到一笔（例 1/3/6/7 必须拆）

## 方案A：从申请人已有授权记录判断（仅适用于"非删除"场景）

**适用前提**：前置「删除场景识别」已判定本次需求**不属于纯删除场景**。删除场景请走前述「前置：删除场景识别」路径，不进入方案A 的情况一/二/三。

场景识别**优先执行方案A**（基于申请人已有授权记录精确判断），方案A有输出结果时，直接采用方案A的结论，**不再执行方案B**；仅当方案A失败（如 `query_staff_role_right` 调用异常或无法判断）时，才回退执行方案B（基于需求文本关键词判断）。

**数据源**：通过 `hr-auth-copilot` MCP 的 `query_staff_role_right` 工具查询当前申请人的已有角色权限包授权记录。

**"有效授权记录"判定标准**：`query_staff_role_right` 查询到有记录即视为有效授权记录。

**判断规则**（基于步骤一输出的 `lockedRole` 和 `selfApplyPkgs`/`ruleGeneratedPkgs`）：

### 情况一：角色没有有效授权记录 → 全部新增

- 在 `query_staff_role_right` 返回的数据中，申请人针对步骤一输出的 `lockedRole`（锁定角色）没有有效的授权记录

> - 角色未持有 → 整体 = **type=0（新增）**，角色和所有权限包 `isNewApply` 均为 `true`
- 所有角色和权限包统一判定为 **新增** 场景


### 情况二：角色已有授权、部分selfApplyPkgs（自主申请权限包）无授权 → 角色不变 + 缺失权限包新增

- 在 `query_staff_role_right` 返回的数据中，申请人针对步骤一输出的 `lockedRole` 有有效的授权记录
- 步骤一输出的selfApplyPkgs（自主申请权限包）中，**部分权限包**在该角色授权记录下有有效授权记录，**部分权限包**没有

**以权限包为粒度**判定。同一角色下可能同时存在多种场景：

> - 角色已持有 + 权限包未持有 → 该权限包 = **type=0（新增）** 则`RoleRightApplyFormDTO` 中角色的 `isNewApply = false`，缺失权限包的 `isNewApply = true`
> - 角色已持有 + 权限包已持有 + 范围变化 → 该权限包 = **type=1（变更）**
> - 角色已持有 + 权限包已持有 + 仅有效期变化 → 该权限包 = **type=2（续期）**
>
> 典型案例：用户已有 `Data_Management_HRIS` 角色，现需在该角色下申请新的 `dos_sys_data` 权限包 → 对 `dos_sys_data` 而言是 **type=0（新增）**，角色设为 `isNewApply=false`、该权限包设为 `isNewApply=true`

### 情况三：全部有有效授权记录 → 进一步判断续期/变更

- 在 `query_staff_role_right` 返回的数据中，申请人针对步骤一输出的 `lockedRole` 有有效的授权记录，且步骤一输出的所有selfApplyPkgs（自主申请权限包）均有有效的授权记录
- 需进一步判断具体场景：
- **续期场景**：本次申请仅涉及有效期变化（即权限包的范围维度不变，只是延长/更新有效期），判定为 **续期**
- **变更场景**：本次申请涉及范围变化（即权限包的控权维度码值发生变化，如组织范围扩大/缩小、新增/移除管理主体等），判定为 **变更**

> 情形三的比较细则**激活条件**：当 `query_staff_role_right` 返回的 `RoleFormItemDTO` 中 `rightPackageList` 内的 `RightPackageItemDTO.packageDataScopes`（即 `List<RoleApplyDimItemDTO>`）**非空且包含已有授权的维度码值明细**时，情况三的细分判断即可启用。届时判断逻辑为：
> - 对比本次申请的维度码值与已有授权记录的维度码值，若码值集合无变化且仅涉及有效期延长 → **续期**
> - 若码值集合存在差异（新增/移除/变更了维度码值） → **变更**

> **说明**：当前 `query_staff_role_right` 返回的数据结构为 `List<RoleFormItemDTO>`，详见 [data-schema.md](./data-schema.md) 章节。


## 方案B：从需求文本关键词判断（仅适用于"非删除"场景）

方案A有输出结果时，直接采用方案A的结论，**不再执行方案B**

- 需求中有"续期/续签/延长/延期"等关键词 → 续期
- 需求中有"变更/修改/调整范围/扩大/缩小"等关键词 → 变更
- 需求中有"新增/新申请/首次/新建"等关键词 → 新增
- 以上均不涉及 → 新增（默认）

> **删除关键词不在本方案B 内**：删除意图统一由前置「删除场景识别」处理，不走方案A/方案B。
