# Workflow: 知识检索

> 返回 [SKILL.md](../SKILL.md)

基于 hr-ai-knowledge MCP 的 `knowledge_search` 工具执行语义检索的完整流程。

> 🔴 **首要原则：内部推理与用户可见分离（强约束，违反即降低回答质量）**
>
> 本工作流中所有步骤（打分、扩展、降级、二次检索、覆盖度判定、连接探活…）**都是 Agent 内部推理**，只能存在于"深度思考"中，**绝不能**作为对话正文渲染给用户。
>
> **🔴 正向强制（务必照做，而非仅"别做"）：检索全程零输出。** 从识别意图 → 探活 → 检索 → 判定 → 重试 → 组织答案，这**一整段过程对用户静默**，工具调用之间**不写任何解说词**（不要"边查边解说"）。
>
> **✅ 用户唯一应看到的内容（你对用户的第一句，只能是其中之一）：**
> 1. **最终回答**：正文 + 末尾"参考文档"列表（最常见）
> 2. **追问 / 澄清**（仅在必要时）：地域、空 query、blocked 软选项
> 3. **未连接引导**（仅 MCP 未连接时）
> 4. **检索路径**（仅在降级过/有缺口时，一行极简展示，详见 [Step 6](#step-6-检索路径展示)）
>
> ❌ **禁止以过程句开头**，包括但不限于：`用户选择了…` / `首次检索：…` / `检索结果返回了 N 条` / `Step 3.1 充分性判定…` / `进入 Step 4 内部重试…` / `二次检索：…` / `两次检索已达上限…`。**见到自己要写这类句子，立即删掉、直接写答案。**
>
> > 💡 连接正常时**无需**输出"技能已加载 / 服务已连接 / schema 已加载"之类的过程确认——直接给最终回答即可。仅当 MCP 未连接需引导用户时才提示连接状态。
>
> **❌ 严禁渲染到对话的内容（黑名单，逐项对照截图问题）：**
>
> | 泄漏类型 | 反例（禁止出现在对话正文） |
> |---|---|
> | 参数值 | `top_k=15`、`mode=hybrid`、`sources=["hihr"]` |
> | 打分/命中 | `命中 hihr`、`hihr=36 \| wecom=0`、`命中分数收窄`、`命中 N 条 / 去重 M 条` |
> | 步骤编号 | `Step 0 连接预检`、`按 Step 4 放宽`、`执行首次检索（同时作为连接探活）` |
> | 内部状态 | `schema 已加载`、`本次会话已通过连接预检`、`非地域敏感词，无需追问` |
> | 降级动作 | `二次检索：sources 放宽=全源`、`覆盖度不足 → 放宽` |
> | 推理旁白 | `核心词「梯队/人才梯队…」`、`属概念解释型问题` 等把内部分析念出来的句子 |
>
> **✅ 正确示范**（用户视角）：直接进入正文——
> > 梯队是指……[1]。人才梯队建设通常包括……[2]。
> > \n**参考文档：** - [1] …（hihr） - [2] …（hihr）
>
> **判断标准**：如果某行文字是"解释我打算怎么查 / 我查到几条 / 我用了什么参数"，它就属于内部推理，**移到深度思考里，不要渲染**。用户只关心答案本身。

## Step 0: MCP 连接性预检（每次检索前必做）

在执行任何检索前，先确认 hr-ai-knowledge MCP 服务可用。**首次预检（本 Step）与用户回"已连接"后的复检（[Step 0.3](#03-用户确认已连接后的复检机制)）共用下方 [0.0 三级探测链](#00-三级探测链首检与复检的唯一定义)**，仅进入时机不同。

### 0.0 三级探测链（首检与复检的唯一定义）

> 🔑 MCP 的完整 server 名带命名空间前缀，本服务真实完整名为 **`HRIT/hr-ai-knowledge/hr-ai-knowledge`**（非短名 `hr-ai-knowledge`）。**已连接状态下用短名探测经常返回不到**——这是"手动连接后仍提示未连接"的过往 Bug 根因。故按「完整名 → 短名 → 真实调用」逐级尝试，**任一级成功即视为「已连接」，直接进入 Step 1**。

| 级别 | 动作 | 成功 | 失败 |
|:---:|------|------|------|
| **第 1 级** | `mcp_get_tool_description([["HRIT/hr-ai-knowledge/hr-ai-knowledge", "knowledge_search"]])`（**完整名优先**） | → Step 1 | 进第 2 级（不要据此判未连接） |
| **第 2 级** | `mcp_get_tool_description([["hr-ai-knowledge", "knowledge_search"]])`（短名退回再试） | → Step 1 | 进第 3 级 |
| **第 3 级** | 绕过探活，用最小参数直接调用（连通性探针）：<br>`mcp_call_tool("HRIT/hr-ai-knowledge/hr-ai-knowledge", "knowledge_search", {"query":"连接自检","top_k":1})`；<br>完整名报"未找到 server"时退回短名 `mcp_call_tool("hr-ai-knowledge", ...)` 再试 | 调用成功（含空结果）→ 连接已生效（探测缓存未刷新，属已知问题），**忽略前两级，进 Step 1** | 两个 server 名都失败 → 判定当前会话不可用 |

> 🔴 **三级调用前必做白名单校验**：server 名按 `/` 分段取末段，须严格等于 `hr-ai-knowledge`（短名与完整名末段均为 `hr-ai-knowledge`，✅ 均合法）；tool 须严格等于 `knowledge_search`。
>
> 🔴 **任一级探测成功后进入 Step 1 时（首检与复检通用）**：用**用户的原始问题**构造 query 正式检索，**绝不**把第 3 级探针词"连接自检"当作用户查询带入 Step 1。
>
> 🔴 **探针不计入检索配额**：第 3 级的"连接自检"探针是**连通性检测**，**不计入**"最多 2 次 `knowledge_search` 调用"配额（见 [constraints.md § 4 检索硬约束](../reference/constraints.md#4-检索硬约束)）——正式检索仍可用满 2 次。
>
> 💡 第 3 级用真实调用充当探针属"连接自检例外"，见 [constraints.md § 3](../reference/constraints.md#3-调用前校验)。

### 0.1 MCP 可用

[0.0 三级探测链](#00-三级探测链首检与复检的唯一定义)任一级成功 → 直接进入 Step 1。**三级全失败** → 按 [0.2](#02-mcp-未连接--未启用) 输出启用引导。

### 0.2 MCP 未连接 / 未启用

> 🔴 **唯一正确动作：输出下方启用引导，然后停止本轮检索。禁止用任何其他 skill / MCP / 平台 / web_search / 模型知识替代**（完整禁止清单见 [constraints.md § 6 唯一检索途径约束](../reference/constraints.md#6--唯一检索途径约束禁止一切替代)）。

**严禁的错误反应（真实案例）：**
- ❌ hr-ai-knowledge 未连接 → 加载 `hihr-api` 等其他 skill 改用 HiHR 平台搜索
- ❌ hr-ai-knowledge 未连接 → 调用 `km` / `iWiki` MCP 顶替
- ❌ hr-ai-knowledge 未连接 → 用 `web_search` 或模型知识"先给个大概"

以上都是**违规替代**。hr-ai-knowledge 未连接时**宁可不返回检索结果**，也只做引导。

**输出以下启用引导后，结束本轮：**

```markdown
> ⚠️ **检测到 HR 知识检索服务（hr-ai-knowledge）尚未连接，无法执行本次检索。**
>
> 请按以下步骤启用 HR 知识检索服务（hr-ai-knowledge）：
>
> **1. 安装 / 更新插件**
> - 打开 CodeBuddy → 扩展 / 插件市场
> - 搜索 `hr-ai-knowledge` 并安装（或更新到最新版本）
>
> **2. 启用 HR 知识检索服务（hr-ai-knowledge）**
> - 打开 **设置 → MCP 面板**（或侧边栏的 MCP 图标）
> - 在 MCP 服务列表中找到 `hr-ai-knowledge`（来源：HRIT/hr-ai-knowledge 插件，URL：`https://aia.mcp.it.woa.com`）
> - 点击「连接 / 授权登录」按钮完成 OAuth 登录
> - 确认状态变为「已连接」✅
>
> **3. 回到这里**
> - 连接成功后，在本轮对话中直接回复 **"已连接"** 或 **"OK"**，我将自动重检连接状态并继续检索
> - 无需新建会话、也无需重新发起提问
>
> **常见问题：**
> - 若 MCP 列表中无 `hr-ai-knowledge`：检查 `hr-ai-knowledge` 插件是否已启用，且 `.mcp.json` 中已声明该服务
> - 若连接失败 / 报权限错：联系 HRIT 团队（该服务的 owner）确认账号权限
>
> 💡 在该服务启用前，如需自行查询，可**由你本人**登录 HR / HiHR 等内部系统核实（本技能不代查、不走替代途径）。
```

> 🔴 **重要约束**：白名单仅 `hr-ai-knowledge`，禁止用 `hihr-api` / `hihr-mcp服务` / `iWiki` / `km` / `sqlink` 等其他 skill 或 MCP 替代。

### 0.3 用户确认已连接后的复检机制

**触发条件**：用户在 [0.2](#02-mcp-未连接--未启用) 引导后回复"已连接""连接好了""OK 连上了""好了""done""ready"等确认性表述。

**处理**：**不再重新输出完整引导**，直接重跑 [0.0 三级探测链](#00-三级探测链首检与复检的唯一定义)：

- 任一级成功 → 进入 Step 1（按 §0.0 说明，用用户**原始问题**检索，不带探针词）
- 三级全失败 → 输出下方提示并结束，**不再循环引导**：

```markdown
> ⚠️ 已尝试三级复检（完整名探测 + 短名探测 + 直接调用），当前会话仍无法识别 MCP 连接。
>
> CodeBuddy 的 MCP 连接状态在**会话启动时初始化**，中途连接偶尔需要**新建会话**才能生效。
>
> **操作步骤：**
> 1. 确认 MCP 面板中 `hr-ai-knowledge` 状态为「已连接」✅
> 2. **新建一个会话**，重新提问即可正常检索
>
> 不便新建会话？你也可以直接让我的回答基于通用知识（我会标注结果未经 hr-ai-knowledge 检索验证）。
```

> 💡 **为何第 3 级用真实调用当探针**：`mcp_get_tool_description` 反映的是**会话启动时初始化的连接状态缓存**，中途手动连接后该缓存可能未刷新，导致前两级探测（无论完整名还是短名）都"探测不到"，但实际链路已通。此时唯有**发起一次真实调用**才能确认连通性——因本服务仅暴露 `knowledge_search` 一个工具（无 `ping` / `version` 类轻量探活工具），故用它的最小查询（`top_k:1`）充当"连通性探针"：调用能返回（哪怕空结果）即证明已连接。

## Step 1: 意图识别与参数构造

### 1.1 提取 query 并做关键词扩展（🔴 首次检索即执行，非可选）

**两步走：**

**① 提取核心词**：从用户问题中提取核心检索关键词，去除礼貌用语和口语化表述。

> 🔴 **空 query 校验**：若去除口语化表述后**提取不到任何有效实体/主题词**（如用户仅说"帮我查一下""搜索一下""看看有什么"），**不得**带空 query 或无意义词盲调工具，**先追问澄清**：
> ```markdown
> 请问你想查询哪方面的 HR 或公司知识？（如：年假政策、公积金比例、绩效考核、离职流程 …）
> ```
> 用户补充后再继续 ②。

**② 强制做一轮关键词扩展**：对提取出的核心词，**首次检索前**就补充同义词 / 全称缩写 / 上下位词，一起拼进 query（而非留到二次检索才补）。只做**一轮**扩展，禁止无限发散。

| 扩展类型 | 示例 |
|----------|------|
| 同义词 | 年假 → 年假 年休假 带薪年休假；婚假 → 婚假 结婚假；调薪 → 调薪 薪酬调整 加薪 |
| 全称/缩写 | 公积金 → 住房公积金 公积金；社保 → 社会保险 社保；RSU → 限制性股票 RSU |
| 上下位词 | 福利 → 福利 补贴 保险 假期；假期 → 假期 年假 病假 事假 |

**扩展后示例：**

| 用户输入 | 提取核心词 | ✅ 扩展后 query（首次即用） |
|----------|-----------|---------------------------|
| "我想知道腾讯的年假政策是什么样的" | 腾讯 年假 政策 | 腾讯 年假 年休假 带薪年休假 政策 规定 |
| "帮我查一下安居计划的最新规定" | 安居计划 规定 | 安居计划 购房补贴 安居 规定 政策 |
| "团队空间里有没有关于绩效的文档" | 绩效 | 绩效 绩效考核 KPI 晋升 |

> 💡 原因：`knowledge_search` 是语义 + 全文混合检索，首次就带同义词可显著降低"关键词表述不一致导致的漏召回"（实测中 `年假` 单词首查易 0 命中，扩展 `年休假 带薪年休假` 后命中）。

### 1.2 推断 sources（🔴 按命中分数决策 · 内部推理，不输出）

按 [knowledge-search-guide.md — sources 路由规则](../reference/knowledge-search-guide.md#sources-路由规则优先级--命中分数) 的**命中分数算法**（命中关键词去重数 × 来源优先级）决策，**不要"撞到第一个词就定"**。

> 🔴 **内部推理，不输出到对话**：打分结果用于 Agent 内部决定 `sources` 参数，**不渲染** `🎯 sources 打分：...` 这种标志性中间态行。决策后直接进入 Step 1.3 / 1.4。

**打分速查（优先级：hihr=9 / wecom=6 / space=6）：**

| 打分结果 | 决策 sources |
|----------|-------------|
| 单一来源分数明显最高 | 收窄该来源（如 `["hihr"]`） |
| 多来源命中 / 分数接近 | **不传**（全源，由 `score` 决定相关性） |
| 零命中且含技术等负向词 | 走[负向边界](../reference/knowledge-search-guide.md#不适用场景负向边界)，多数不检索 |
| 零命中但非负向 | 不传（全源） |

> 🔴 **收窄仅用于首次检索**：首次按分数收窄 `sources` 提升精度；一旦命中不足（Step 3 判定），**Step 4 首选动作就是放宽为全源**，不要把收窄当作固定不变的过滤条件。

> ⚠️ **负向边界**：若问题属于"纯技术 / 架构 / 竞对分析 / 与公司 HR 无关的通用知识"，见 [knowledge-search-guide.md — 不适用场景](../reference/knowledge-search-guide.md#不适用场景负向边界) —— 不应收窄到 `["hihr"]`，多数情况根本不应进入检索或应走全源。

### 1.3 构造完整参数

其他参数使用默认值，仅在用户有明确需求时覆盖：

| 参数 | 默认值 | 动态调整时机 |
|------|--------|-------------|
| `space_id` | 不传 | 用户明确指定空间时才传 |
| `mode` | `"hybrid"` | 同义词密集型首次用 `hybrid`；二次召回不足切 `vector`；精确匹配用 `fulltext` |
| `top_k` | `10` | 宽泛问题（"有哪些福利"）提到 `15~20`；精确问题保持 `10` |

### 1.4 地域相关性检查（🔴 检索前追问，避免跨城市误召回）

HR 中大量政策**按城市差异化执行**。当问题命中下列**地域敏感词**且用户**未指定城市/地区**时，**先追问地区，再带地区词检索**——否则会召回多个城市的混杂结果，命中率骤降。

| 地域敏感词 | 说明 |
|------------|------|
| 社保 / 五险一金 | 各地缴纳基数、比例不同 |
| 公积金 / 住房公积金 | 各地缴存比例、上限不同 |
| 落户 / 户口 | 各城市落户政策差异大 |
| 安居计划 / 购房补贴 / 租房补贴 | 按城市分档 |
| 个税 / 专项附加扣除 | 部分与地区相关 |
| 医保 / 生育津贴 | 各地报销与津贴标准不同 |

**追问模板：**

```markdown
你咨询的{政策名}在各地执行标准不同，请问你所在的工作城市是？（如：深圳 / 北京 / 上海 / 成都 / 广州 …）
```

> 💡 例外：用户问题已含城市名（"深圳的公积金比例"）→ 直接把城市词并入 query，不追问。
> 用户明确表示"不限地区 / 所有城市"→ 走全源检索，不追问。

## Step 2: 白名单与工具校验

> 🔴 **复用 Step 0 结论，不重复探测**：Step 0 的 [§0.0 三级探测链](#00-三级探测链首检与复检的唯一定义)已调用 `mcp_get_tool_description` 完成探活，其返回**已包含 `knowledge_search` 的参数签名**——本步**不再重复调用** `mcp_get_tool_description`，直接沿用该结果。

调用前确认（均沿用 Step 0 已得结论，无需再次探测）：

1. **参数签名**：复用 Step 0 探活返回的 `knowledge_search` 签名
2. **server 白名单**：末段严格等于 `hr-ai-knowledge` → 不满足则停止
3. **tool 名**：严格等于 `knowledge_search` → 不满足则停止

## Step 3: 首次检索

用 Step 1 构造的参数（已含扩展词 + 收窄的 `sources`）调用 `hr-ai-knowledge/knowledge_search`。

### 3.1 充分性判定（🔴 二维判定，非只数条数）

不要只看"命中几条"——3 条低相关结果同样答不到点上。按以下**三个条件同时满足**才算充分：

| 维度 | 判定标准 |
|------|----------|
| ① 数量 | 去重后命中 ≥ 3 条 |
| ② 质量 | 至少有 1 条高分结果（`score ≥ 0.9`） |
| ③ 覆盖度 | 结果**覆盖用户问题的全部子要点**（拆出问题的每个独立要点，逐一核对是否被结果覆盖） |

**评估结论：**
- ✅ **充分**：①②③ **全部满足** → 进入 Step 5
- ⚠️ **不足**：**任一不满足**（数量少 / 全是低分 / 有要点没覆盖）→ 进入 Step 4

> 💡 覆盖度自检示例：问"年假天数怎么算、离职时未休的怎么补偿"含 2 个子要点。若结果只讲了天数计算、没讲离职补偿 → 覆盖度不满足 → 进 Step 4（且在 Step 6 标注信息缺口="离职补偿"）。

> 🔴 反模式：命中 5 条但全是 `score < 0.85` 的边缘结果，却因"条数够"判为充分 —— 这会导致答非所问，必须进 Step 4。

### 3.2 返回异常态识别（🔴 区分"空结果"与"被拦截/无权限"）

`knowledge_search` 已连接但仍可能返回**非空结果异常态**，不能一律当"空结果"走二次检索：

| 返回特征 | 含义 | 处理 |
|----------|------|------|
| `hihr_blocked: true` / 含 "外部模型不支持查询司内知识" | 已连接，但当前模型无权查 hihr（服务端安全策略） | **一次性**给出切换混元大模型的完整 UI 步骤（不要求用户先回复"切换"）；并列附上 space / wecom 降级兜底 |
| 权限/鉴权类报错（403 / unauthorized / 登录过期） | 登录态失效 | 提示用户在 MCP 面板**重新授权登录**后重试 |
| 正常空结果（`total: 0` 且无 blocked 标志） | 确实无命中 | 走 Step 4 内部重试 |

**blocked 提示模板（🔴 一轮给全，用户照做即可，不设"先回复切换"的前置往返）：**

> 🔴 **切换模型是用户在 UI 上的操作，Agent 无可代做的动作**——因此直接把 3 步操作一次性列出，让用户照做，而**不是**让用户先回一句"切换"再由 Agent 补步骤（那样白白多一轮空往返）。将下方模板中的 `{用户原问题}` 替换为用户本轮的实际问题。

```markdown
> ⚠️ 当前模型不支持查询司内 HR 知识（服务端安全策略，hihr 来源被拦截）。
>
> **要取回完整 HR 结果，请切换到混元大模型（照以下 3 步操作即可）：**
> 1. 点击对话框顶部的模型切换按钮（当前模型旁的下拉菜单）
> 2. 选择 **混元大模型（Hunyuan）**
> 3. 切换后直接回复 **"已切换"**，我会立刻重新检索，无需重新输入问题
>
> 💡 如暂不便切换：可回复 **"跳过"**，我仅用 space / wecom 来源检索非涉密内容（可能不覆盖 HR 政策）。
```

### 3.3 模型切换后重试机制（🔴 不要求用户新建会话）

> 🔑 **背景**：同一会话内切换模型后，新模型的 Agent 实例**可能未继承** `use_skill` 加载状态和检索流程上下文——若用户只是重新提问，新模型可能不走完整检索流程导致报错。因此 blocked 引导让用户回复"已切换"而非"重新提问"，由 Agent 主动重新执行检索，**避免依赖 Rules 重新触发或用户新建会话**。

**触发条件**：用户在 blocked 引导后回复 **"已切换"**"切换好了""换好了""切好了"等**明确表示模型切换已完成**的表述。

> 🔴 **与"跳过"严格区分**："已切换"= 用户已完成模型切换 → 重新查 hihr；"跳过"= 用户不切换 → 降级 space/wecom。两者**不可混淆**——若用户回复含义模糊（如"OK""好""继续"），**必须先追问**"请问你是已切换到混元模型（回复'已切换'），还是不切换走非涉密来源（回复'跳过'）？"，不得擅自假设。

**处理流程：**

1. **确认 skill 已加载**：若当前模型未加载 hr-ai-knowledge skill（如切换模型后上下文重置），先 `use_skill("hr-ai-knowledge")` 重新加载
2. **跳过 Step 0 连接预检**：MCP 连接是会话级的，切换模型不会断开连接——**无需重新探活**，直接进入检索
3. **重新调用 `knowledge_search`**：用**用户原始问题**（非"已切换"这个词）作为 query，`sources` 恢复为首次的收窄值（如 `["hihr"]`），重新检索
4. **判定结果**：

| 返回 | 处理 |
|------|------|
| 正常命中（无 blocked） | ✅ 切换生效 → 组织回答（Step 5） |
| 仍 `hihr_blocked: true` | 切换未生效 / 未切对模型 → 输出下方提示 |
| 报错（MCP 未识别 / 工具不可用） | 新模型上下文中 MCP 未初始化 → 走 [§0.0 三级探测链](#00-三级探测链首检与复检的唯一定义) 重新探活 |

**仍 blocked 时的提示（不引导新建会话）：**

```markdown
> ⚠️ 重新检索后 hihr 仍被拦截，模型切换可能未生效。
>
> 请确认：
> 1. 当前模型已切换为 **混元大模型（Hunyuan）**（检查对话框顶部模型名）
> 2. 确认后再次回复 **"已切换"**，我会再试一次
>
> 💡 若多次仍被拦截，可能是该会话的模型上下文未刷新——可尝试在输入框重新发送一次"{用户原问题}"。
```

> 🔴 **重试时的静默约束**：重试过程（确认 skill、调用 knowledge_search、判定结果）均为内部推理，**对用户零输出**——用户只看到最终的检索结果或仍 blocked 的提示，不看到重试中间态。

---

## Step 4: 内部重试（结果不足时，🔴 不得输出"二次检索"等中间态）

> 🔴 **不输出任何"二次检索""放宽 sources""切 mode"等中间态文字**。Agent 在内部默默执行下列降级，**仅在 Step 6 检索路径做一句极简总结**（如"已扩展检索范围"），不暴露过程细节。

**降级优先级（按此顺序执行）：**

**① 首选：放宽 `sources`（解决"来源收窄导致的漏召回"）**

首次若传了收窄的 `sources`（如 `["hihr"]`），二次检索**第一件事就是去掉 `sources`（改为全源检索）**，而不是先换关键词。

| 首次 sources | 二次 sources |
|--------------|-------------|
| `["hihr"]` | **不传**（全源 space + hihr + wecom） |
| `["wecom"]` / `["space"]` | **不传**（全源） |
| 首次已是全源（不传） | 跳过本步，直接走 ② 换关键词 |

> 💡 依据：HR 政策类内容可能同时落在 hihr 与 wecom；实测 `sources:["hihr"]` 首查 0 条、放宽全源后命中 5 条。**放宽来源比换关键词更能挽回漏召回。**

**② 次选：换关键词 / 调参数**

放宽来源后仍不足，再调整查询本身：

- 进一步提炼核心概念词，去除干扰词
- 追加更多同义词 / 换表述角度（如"离职补偿"→"离职结算 经济补偿金 N+1"）
- 添加限定范围（如"腾讯"、具体城市名）
- 切换到纯 `vector` 模式提升语义召回，或 `fulltext` 做精确匹配
- 宽泛问题可将 `top_k` 提到 15~20

> **约束**：最多 2 次检索（① 与 ② 合计算作第 2 次）。第 2 次仍无结果 → 如实告知知识缺口，不得继续检索。

## Step 5: 组织回答

### 5.0 结果预处理（排序 + 去重 + 相关性过滤）

组织回答前，先对 `knowledge_search` 返回结果做三步清洗：

1. **按 `score` 降序排序**：高相关性结果优先展示，作为回答主依据。
2. **去重合并**：同一 `display_name` 且内容高度重叠的 chunk 合并为一条，只保留信息最全的片段（实测同一份《离职测算 FAQ》会返回多个近似 chunk，需合并）。
3. **相关性阈值过滤**：
   - `score ≥ 0.9`：高相关，正常引用
   - `0.85 ≤ score < 0.9`：中相关，可引用但排在后面
   - `score < 0.85`：低相关，**标注"相关性较低，仅供参考"**或在结果充足时丢弃，不作为主要结论依据

> 🔴 禁止：把低分结果与高分结果混同展示，或用低分结果拼凑出"确定性结论"。

### 5.1 回答原则

- 基于检索结果回答，不凭模型自身知识编造
- 每条信息标注来源（hihr / space / wecom）
- 不同来源的信息明确区分
- 外部知识注明获取时间
- 结论主要依据高分（`score ≥ 0.9`）结果；低分结果仅作补充并标注相关性

### 5.2 引用格式

按 [knowledge-search-guide.md — 引用规范](../reference/knowledge-search-guide.md#引用规范) 的标准格式标注来源。核心要求：
- 每条信息用 `[序号]` 标注
- **文档标题必须为可点击的 markdown 链接**（`[《文档名》](url)`），禁止纯文本
- 来源按域名判定：`s3.woa.com` → **HiHR**（hr-ai-knowledge 是对 hihr 的二次包装）；`km.woa.com` / `iwiki.woa.com` → **iWiki**；企微域名 → **企微文档**
- 末尾附参考文档列表，注明获取时间（`YYYY-MM-DD`）

### 5.3 无结果处理

按 [knowledge-search-guide.md — 无结果处理](../reference/knowledge-search-guide.md#四无结果处理) 的标准模板告知用户知识缺口与建议（更换关键词 / 换 sources / 走内部 HR 系统核实），不另造格式。

## Step 6: 检索路径展示（🔴 面向用户的极简摘要，不暴露过程细节）

> 🔴 **用户看到的检索路径 ≠ 内部过程**。禁止展示 query 原文、sources 列表、mode/top_k、命中条数、score 分布、Step 编号、降级动作等参数。**只展示一句"摘要+缺口"**，让用户感知"查了 / 没全查到"，不暴露怎么查的。

### 6.1 展示时机与模板

| 场景 | 模板 |
|------|------|
| 一次命中、覆盖完整 | **不展示检索路径**（最常见，保持简洁） |
| 发生过降级（`sources` 放宽 / 换关键词） | `> 已扩展检索范围，整理后回答如下。` |
| 存在信息缺口 | `> 已整理部分内容；<缺口描述>未在当前文档中查到，建议咨询 HRSSC。` |
| 同时降级 + 缺口 | `> 已扩展检索范围；<缺口描述>未在当前文档中查到，建议咨询 HRSSC。` |

> 用户明确说"显示检索过程"时，才输出技术性长版（含 query/sources/mode 等）作为临时调试手段，默认不展示。

### 6.2 「信息缺口」判定（仅用于决定是否走缺口模板）

满足任一即视为有缺口：

1. 用户问题含多个子问题，仅部分被结果覆盖
2. 结果全部为低分（`score < 0.85`）
3. 地域敏感问题但结果未区分/未覆盖用户所在城市
4. 放宽全源后仍未命中核心要点

> 缺口描述**用自然语言**（如"离职补偿"），不用"Step 3.1 覆盖度不满足"等内部话术。
