# knowledge_search 工具规范

> 返回 [SKILL.md](../SKILL.md) | [search.md](../workflows/search.md)

本文件是 `hr-ai-knowledge/knowledge_search` 工具的权威参数规范与使用指引。

---

## 工具概述

| 属性 | 值 |
|------|-----|
| MCP Server | 短名 `hr-ai-knowledge` / 完整名 `HRIT/hr-ai-knowledge/hr-ai-knowledge`（末段严格等于 `hr-ai-knowledge`；**探测连接时优先用完整名**） |
| Tool Name | `knowledge_search` |
| 功能 | 在团队空间内执行语义检索，返回文档片段、文件元信息和关联概念 |

---

## 输入参数

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:---:|------|------|
| `query` | string | ✅ | — | 检索查询语句 |
| `space_id` | string \| null | ❌ | `null` | 目标空间 ID（GUID 格式）；不传时检索所有有权访问的空间 |
| `mode` | string | ❌ | `hybrid` | 检索模式：`vector`（向量检索）/ `graph`（知识图谱检索）/ `fulltext`（全文检索）/ `hybrid`（混合检索，默认，包含以上全部模式） |
| `top_k` | integer | ❌ | `10` | 返回结果数量上限，范围 1-20 |
| `sources` | array \| null | ❌ | `["space", "hihr", "wecom"]` | 搜索来源过滤：`space`（本地空间）/ `hihr`（HR 知识库）/ `wecom`（企微文档） |

## 适用场景

`knowledge_search` 通过 `sources` 参数覆盖三类来源，各来源下细分场景如下：

| 场景 | 来源 | 关键词示例 |
| --- | --- | --- |
| 团队空间 | `space` | 团队空间、本地空间、项目文档、知识库内容 |
| 政策制度 | `hihr` | HR 政策、公司制度、员工手册、组织管理 |
| 假期 | `hihr` | 年假、产假、婚假、陪产假、丧假、病假、事假、工伤、调休 |
| 薪酬福利 | `hihr` | 薪酬、福利、社保、公积金、商业保险、安居计划、长期激励 |
| 绩效与发展 | `hihr` | 绩效、晋升、职级、培训 |
| 劳动关系 | `hihr` | 劳动合同、试用期、竞业限制、工时、加班、离职、调动 |
| 招聘与党建 | `hihr` | 招聘、党建、员工服务 |
| 企微文档 | `wecom` | 企微文档、wecom、聊天中的文档 |
| 综合检索 | 不传 | 不限定来源的全团队知识检索 |

> 💡 hr-ai-knowledge 已包含全部 hihr 内容，`hihr` 类场景通过 `sources: ["hihr"]` 路由。

## 不适用场景（负向边界）

🔴 **以下场景禁止把 `sources` 收窄到 `["hihr"]`，多数情况根本不应进入 HR 检索流程。** 这是防止"非 HR 问题被误判为 HR 检索、召回一堆不相关 HR 政策"的硬边界。

| 问题类型 | 典型信号词 | 正确处理 |
|----------|-----------|----------|
| 纯技术 / 编程 | 代码、报错、API、部署、架构、数据库、算法、框架 | ❌ 不走本插件检索，直接按技术问答处理 |
| 行业研究 / 竞对分析 | 竞品、市场、行业趋势、友商、对标分析 | ❌ 不属 hr-ai-knowledge HR 知识范围；如需资料走 `web_search`，不收窄 hihr |
| 通用常识 / 闲聊 | 与公司 HR 完全无关的百科、生活、闲聊 | ❌ 直接回答，不检索 |
| 其他公司 / 外部政策 | 明确指向非本公司的 HR 政策 | ❌ hr-ai-knowledge 仅覆盖本公司 HR；如误命中要如实说明 |

**判定规则：**

1. 问题**不含任何** HR/人事/薪酬/福利/假期/制度 等正向信号词，且**含**上表负向信号词 → **不进入检索**（或按普通问答处理）。
2. 问题**同时含**正负向信号（如"HR 系统的技术架构"）→ **不收窄 `["hihr"]`**，改为全源检索（不传 `sources`），由结果 `score` 决定相关性。
3. 边界模糊、无法判断是否属于 HR → **宁可全源检索，不要收窄**；收窄错了会直接漏掉正确来源。

> 💡 与正向"适用场景"表配合使用：先查负向边界排除，再查正向表收窄 `sources`。

## `sources` 路由规则（优先级 + 命中分数）

不再"撞到第一个关键词就定 sources"，而是按**命中分数**决策，使路由可解释、可消歧。

### 关键词 → 来源 映射表（带优先级）

| 来源 | 优先级 | 命中关键词 |
|------|:---:|------|
| `hihr` | 9 | HR / 人事 / 政策 / 制度 / 员工手册 / 薪酬 / 福利 / 假期 / 年假 / 年休假 / 产假 / 婚假 / 陪产假 / 丧假 / 病假 / 事假 / 工伤 / 调休 / 社保 / 公积金 / 商业保险 / 安居计划 / 长期激励 / RSU / 绩效 / 晋升 / 职级 / 培训 / 劳动合同 / 试用期 / 竞业限制 / 工时 / 加班 / 离职 / 调动 / 招聘 / 党建 / 员工服务 |
| `wecom` | 6 | 企微 / wecom / 企业微信 / 聊天文档 / 群文档 / 在线文档 |
| `space` | 6 | 团队空间 / 本地空间 / 项目文档 / 空间内 |

### 命中分数算法

1. **提取**：从用户问题提取 2~5 个关键词，做**一轮**同义词/缩写扩展（与检索 query 的扩展保持一致）。
2. **匹配**：小写归一后做**双向子串匹配**（用户词 ⊆ 表内词 或 表内词 ⊆ 用户词，任一成立即命中）。
3. **打分**：每个来源的分数 = 命中该来源关键词的**去重数量 × 优先级**。
4. **决策**：
   - **单一来源分数明显最高** → 收窄到该来源（如仅命中 hihr 词 → `["hihr"]`）
   - **多来源都有命中 / 分数接近** → **不收窄**，传全源（不传 `sources`），由 `score` 决定相关性
   - **零命中**（无任何来源关键词）→ 先查[不适用场景](#不适用场景负向边界)：属负向边界则不检索；否则全源检索

### 决策示例

| 用户问题 | 命中 | 决策 sources |
|----------|------|-------------|
| "年假怎么算" | hihr（年假） | `["hihr"]` |
| "企微文档里的报销流程" | wecom（企微文档）+ hihr（报销弱相关） | wecom 分数高 → `["wecom"]` |
| "公司对远程办公的规定" | hihr（规定/制度弱）+ 可能 wecom | 分数接近 → **不传**（全源） |
| "微服务怎么部署" | 零命中 HR，含技术负向词 | 负向边界 → 不检索 |

> 💡 `sources` 是**过滤条件**而非"开关"：不传 = 全部；传 `[]` = 全部；传 `["hihr"]` = 仅 hihr。
> 🔴 收窄仅用于**首次**检索；命中不足时按 [检索流程 Step 4](../workflows/search.md) 放宽为全源。

## `mode` 与 `top_k` 动态选择指南

### `mode` 选择

| 场景 | 推荐 `mode` |
|------|------------|
| 复杂查询 / 首次检索（默认） | `hybrid` |
| 同义词/语义匹配（如"年假"匹配"年休假"） | `vector` |
| 概念关联/跳转（如"绩效"→"晋升"） | `graph` |
| 关键词/编号精确匹配（如"RFC""第 5 条"） | `fulltext` |

> 💡 **二次检索切换**：首次 `hybrid` 召回不足时，第 2 次优先切 `vector` 提升语义召回；若用户查的是精确条款/编号，切 `fulltext`。

### `top_k` 选择

| 问题类型 | 推荐 `top_k` | 示例 |
|----------|:---:|------|
| 精确单点问题 | `10`（默认） | "年假怎么算" |
| 宽泛/枚举型问题 | `15~20` | "有哪些福利""离职要办哪些手续" |
| 二次放宽全源后 | 适当提高（`15`+） | 全源检索覆盖面更广，需更多结果兜住召回 |

> 🔴 `top_k` 范围 1~20；提高 `top_k` 会引入更多低分结果，务必配合 [检索流程 Step 5.0](../workflows/search.md#50-结果预处理排序--去重--相关性过滤) 的 `score` 排序与阈值过滤，避免低相关结果干扰结论。

### mode × top_k 联动建议

| 检索阶段 | mode | top_k |
|----------|------|:---:|
| 首次（收窄 sources） | `hybrid` | 10（宽泛问题 15） |
| 二次（放宽全源 + 召回不足） | `vector` | 15~20 |
| 精确条款查询 | `fulltext` | 10 |

## 引用规范

### 一、来源识别规则

每条检索结果需按文档链接域名判定并标注真实来源。hr-ai-knowledge 是对 hihr 的二次包装，因此域名决定显示标签：

| 文档 URL 域名 | 显示来源 | 含义 |
|---------------|----------|------|
| `s3.woa.com` | **HiHR** | HiHR 内部 HR 制度文档（最常见） |
| `km.woa.com` / `iwiki.woa.com` | **iWiki** | 团队空间 / Wiki 文档 |
| `weixin.qq.com` / `wxwork.qq.com` | **企微文档** | 企业微信文档 |
| `doc.weixin.qq.com` | **企微文档** | 企业微信在线文档 |
| 无 URL / 仅含 `space_file_id` | `hihr` / `space` / `wecom` | 按 `sources` 入参对应标签 |

> 🔴 重要：来源必须与 hr-ai-knowledge 的下层系统一致，不要把所有结果都笼统标注为"HR 知识检索服务"。

### 二、标准引用格式

每条信息用 `[序号]` 标注，文档标题**必须为可点击的 markdown 链接**（使用 `display_name` + 文档 URL 构造），末尾附参考文档列表，并注明获取时间：

```markdown
腾讯员工每年可享有 7~15 天带薪年休假[1]，具体计算方式详见制度文档[2]。

---

**参考文档：**
- [1] [《腾讯员工假期及工时管理制度》](https://s3.woa.com/teams/.../...doc) — 年假天数与计算规则（HiHR · 2026-07-23 获取）
- [2] [《ER 合规问题集》](https://s3.woa.com/teams/.../...doc) — 年假相关问答（HiHR · 2026-07-23 获取）
- [3] [《团队周报 2026Q2》](https://km.woa.com/...) — 团队空间内文档（iWiki · 2026-07-23 获取）
```

**格式要点：**
1. **可点击**：文档标题必须包裹在 `[...](url)` 中，禁止使用纯文本（如 `《XX》` 后不跟链接）
2. **URL 优先级**：chunk 文本中已包含的 s3.woa.com / km.woa.com 链接 → 直接使用；若没有，可基于 `space_file_id` 拼接
3. **来源标签**：按"一、来源识别规则"表判定，s3.woa.com 必标 **HiHR**（即使原始 `sources` 传的是 hihr，因为 hr-ai-knowledge 是对 hihr 的二次包装）
4. **获取时间**：使用当前会话日期（`YYYY-MM-DD`）

### 三、无 URL 时的降级格式

若 chunk 中确实无法提取任何 URL（如返回结果无 `display_name` 对应的链接），降级为：

```markdown
- [1] [《ER 合规问题集》]()（来源未知 · 2026-07-23 获取）— 描述
```

仍保留 `[...]()` 形式以保持格式统一，避免直接写文本标题。

### 四、无结果处理

```markdown
> ⚠️ HR 知识检索服务中未查到相关信息。建议：
> - 尝试更换关键词重新检索
> - 分别指定 sources 尝试不同来源
> - 通过内部 HR 系统确认准确信息
```

### 五、数据时效性

HR 政策会随时间更新，检索结果不保证为最新版本。回答时按以下规则处理时效：

1. **必标获取时间**：每条引用附 `YYYY-MM-DD 获取`（即当前会话日期）。
2. **时效提醒阈值**：默认 **365 天**。若结果内容含明确的政策发布/更新日期，且距今超过 365 天，追加提醒：
   ```markdown
   > ⏳ 该政策文档最近更新于 {日期}，距今已超 365 天，可能已调整。建议通过内部 HR 系统核实最新版本。
   ```
3. **"最新"类提问**：用户问"最新政策"时，即使命中结果也需说明"以下为知识库中检索到的版本，如需确认是否为最新请通过内部 HR 系统核实"。
4. 无法判断结果发布日期时，不臆造日期，仅注明获取时间。
