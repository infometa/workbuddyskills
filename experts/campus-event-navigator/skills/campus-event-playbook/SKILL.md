# Campus Event Playbook

把校园活动从模糊想法推进为可执行、可检查、可复盘的工作方案。根据用户当前阶段选择最小必要流程，不一次加载或输出全部模板。

## 进入条件与场景判定

用户请求活动方案比较、任务拆解、人员岗位、预算物料、宣传报名、现场流程、风险检查、就绪评估或活动复盘时使用本 Skill。

按当前任务路由：

1. 只有初步想法、尚未确定形式：想法成形。
2. 需要策划书、预算或完整方案：完整策划。
3. 需要排任务、分工、追进度或解决阻塞：筹备推进。
4. 活动临近或当天需要流程、岗位、彩排和预案：现场准备。
5. 需要总结、数据分析和经验沉淀：活动复盘。
6. 用户明确指定单项任务：直接进入对应产物，不强制补齐其他阶段。

## 最小信息与证据状态

只询问会改变当前方案的信息，一次优先确认一个关键问题。常见关键字段是目标、对象、人数、日期、场地、预算、人员、设备、审批状态和当前最急任务。

统一使用以下证据状态：

- 已确认：有用户提供的材料、明确记录或已核验官方来源。
- 用户陈述：用户明确说明但尚无材料佐证。
- 暂定假设：为了比较方案而临时采用，必须标注。
- 待官方核验：涉及具体学校制度、审批、场地、安全、报销或联系方式。
- 暂不处理：当前任务不依赖的信息。

禁止把未确认的日期、预算、审批、人员和规则写成事实。

## 轻量输出合同

用户只需要单项结果时，默认先输出：

1. 当前结论。
2. 最关键的 1—3 项发现或选项。
3. 判断依据与信息缺口。
4. 最近行动项。
5. 最多一个需要用户决定的问题。

只有用户要求完整文档、确需多人协作或当前信息复杂时，才展开完整表格。

## 专业工作流

### 1. 建立活动 Brief

建立一页式 Brief，包含目标、对象、规模、时间、地点、形式、资源、审批、成功指标、限制条件和当前最急任务。需要详细字段时读取 `references/campus-event-templates.md` 的“一页式活动 Brief”。

### 2. 比较活动方案

生成 2—3 个可执行方案，比较参与机制、适用对象、人员场地物料、预计成本、筹备难度、主要风险和适用条件。明确推荐项及成立条件，获得用户选择后再展开。

### 3. 建立活动工作台

将方案拆为里程碑、任务、人员、预算、物料、宣传、现场流程、风险和最近行动项：

- 每项关键任务指定一个最终负责人。
- 标明协作人、截止时间、依赖、交付物和验收标准。
- 识别关键路径和缓冲。
- 日期、规模或预算变化后重新检查受影响任务。
- 将已发生事项从 Risk 转为 Issue。

需要持续维护时使用 `assets/event-workspace-template.md`。创建或更新用户文件前先说明文件、变更和影响并取得授权。

### 4. 安排人员与岗位

小型团队使用“主负责人 + 协作人”；复杂任务使用精简 RACI。生成签到、引导、主持、舞台、摄影、宣传、物料、设备、秩序和机动岗岗位卡，并设置活动前确认、换班、候补和升级路径。医疗、驾驶、设备和安全岗位不得只依据个人自评分配。

### 5. 管理预算、物料和 RAID

区分预算、已承诺、实际、预计最终和预备金，不机械套用商业活动比例。RAID 区分 Risk、Assumption、Issue、Dependency。

每项判断至少记录：

- 事实依据或用户输入。
- 证据状态与来源。
- 触发条件、概率和影响。
- 预防或下一步、备用方案、负责人和期限。
- 仍需核验的事项。

需要字段模板时读取 `references/campus-event-templates.md`。

### 6. 设计宣传与报名节奏

按需选择预热、正式发布、报名推动、截止提醒、活动前提醒、现场记录和活动回顾。针对公众号、海报、群聊、朋友圈和报名页调整文案。报名表只收集活动组织必需的信息并说明用途。输出均为草稿，未获明确确认不得发送或发布。

### 7. 生成 Run of Show

至少包含时间、环节、地点、负责人、入场条件、物料设备、主持口令、交接动作、完成标准、延误缓冲、取消条件、备用流程和问题升级路径。同时按需生成岗位检查表、紧急联络表和撤场清单。

### 8. 开展就绪检查

只在用户要求就绪评估或提供对应检查信息时评估：场地审批、核心流程、关键岗位、预算物料、宣传报名、设备彩排、安全预案和数据收集。

- 状态只允许 `ready`、`needs_work`、`missing`。
- 每项记录证据、证据状态、缺口、负责人、期限和降级方案。
- 缺少场地审批、核心流程、关键岗位或安全预案时，不输出“可以照常举行”；提供补齐、简化、延期或取消相关环节的选择。
- 没有就绪数据时输出 `not_evaluated`，不得推断为 `missing` 或 `blocked`。

### 9. 完成活动复盘

只使用用户提供或可核验的数据。整理报名、到场、任务、预算、反馈和传播结果；没有的数据明确标为缺口。按有效做法、主要问题、意外情况、根因、保留、调整、新增、删除组织，并为改进动作补充负责人和期限。

## 确定性计算

只有用户提供对应数值或明确要求计算时，才运行 Python 3.10+ 的 `scripts/event_metrics.py`。

```bash
python scripts/event_metrics.py --input event-data.json
```

计算语义：

- 到场率 = 到场人数 / 报名人数。
- 任务完成率 = 已完成任务 / 总任务。
- 预算偏差 =（实际或预计最终金额 - 预算）/ 预算；正值表示超预算，负值表示低于预算。
- 未提供 `readiness` 时返回 `not_evaluated`；只有明确提供该对象时才计算就绪状态。

脚本输出只反映输入数据，不等于学校审批、安全认证或最终举办决定。出现人数、任务数或预算异常告警时，先请用户核对口径，再解释结果。

## 校园规则与安全边界

- 处理审批、消防、食品、体育、夜间活动、未成年人、个人信息和校外人员时，读取 `references/campus-safety-and-privacy.md`。
- 核验具体学校制度、联系方式或近期政策时，读取 `references/school-rule-verification.md`，优先学校官方页面和用户提供的正式材料。
- 社区文章、论坛、搜索摘要和其他学校经验不得作为高风险操作的唯一依据。
- 不虚构制度、审批状态、联系人或许可，不协助规避审批或制作虚假材料，不替代校方及专业责任主体作最终决定。
- 对外发送、发布、提交或创建外部事项前展示最终内容、对象和范围并取得明确确认。
