# 合同起草 — 详细操作指南

本文档为合同起草的详细操作指南，由 SKILL.md 引用。执行起草流程时阅读本文档。

## 核心原则：智能推断 + 立即生成 + 不暴露敏感信息

合同起草引擎根据合同类型和结构描述生成完整合同，主体名称全部使用占位符（甲方：_____、乙方：_____），用户下载后自行填写。

**你的职责是**：从用户输入中判断合同类型 → 根据类型推断默认的签署方结构（几方、各方角色）→ 将类型+结构+用户提供的业务细节整理为高质量 Requirement → 调用 API 生成。

**行为准则**：
- 合同类型可判断 → 立即推断签署方结构 → 写入 Requirement → 调用 API
- 合同类型不可判断 → 仅追问类型（一句话），不追问其他任何信息
- 用户主动提供的任何信息（主体名称、金额、期限、标的等）→ 全部写入 Requirement
- 用户没说的信息 → 不追问，云端引擎用占位符补全

**敏感信息处理规则（禁止主动追问，但用户自己说了就写入）**：
- 公司名称、企业名称 → 禁止追问；用户主动提供则写入 Requirement
- 个人姓名 → 禁止追问；用户主动提供则写入 Requirement
- 金额、合同总价、单价、薪资、租金、违约金、押金等 → 禁止追问；用户主动提供则写入 Requirement
- 身份证号、手机号、地址、银行账号、生日等 → 禁止追问；用户主动提供则写入 Requirement

**简单来说**：你唯一能主动问的只有合同类型。其他所有信息——用户说了就用，没说就不问。

**为什么这样做**：聊天场景中收集和传输真实主体名称存在隐私泄露风险。云端 API 会在合同文档中为主体名称预留签署占位符，用户在签署环节填入真实信息即可。

## 阶段 1：判断类型 → 推断结构 → 生成

```
用户消息能否判断出合同类型？
  ├─ 能 → 推断签署方结构 → 进入阶段 2（不追问任何信息）
  └─ 不能 → 一句话追问类型，收到后推断结构 → 进入阶段 2
```

**根据合同类型推断默认签署方结构**（写入 Requirement 以保证生成质量）：

| 合同类型 | 默认签署方 | Requirement 中的角色描述 |
|----------|-----------|------------------------|
| 房屋租赁 | 2方 | 出租方（甲方）、承租方（乙方） |
| 劳动合同 | 2方 | 用人单位（甲方）、劳动者（乙方） |
| 买卖/采购 | 2方 | 卖方/供应商（甲方）、买方/采购方（乙方） |
| 服务合同 | 2方 | 服务提供方（甲方）、委托方（乙方） |
| 保密协议(NDA) | 2方 | 披露方（甲方）、接收方（乙方） |
| 合伙协议 | 多方 | 合伙人甲方、合伙人乙方（及更多） |
| 担保合同 | 3方 | 债权人（甲方）、债务人（乙方）、担保人（丙方） |
| 居间/中介 | 3方 | 委托方（甲方）、中介方（乙方）、交易对手方（丙方） |

**直接生成的示例**：

| 用户输入 | 推断过程 | Requirement 写法 |
|----------|----------|-----------------|
| 起草一份租房合同 | 房屋租赁→出租方+承租方 | 「起草一份房屋租赁合同，签署方为出租方（甲方）和承租方（乙方）」 |
| 帮我写份劳动合同 | 劳动→用人单位+劳动者 | 「起草一份劳动合同，签署方为用人单位（甲方）和劳动者（乙方）」 |
| 采购合同，办公电脑200台，含售后与违约条款 | 采购→供应商+采购方 | 「起草一份采购合同，签署方为供应商（甲方）和采购方（乙方）。标的：办公电脑200台。需包含售后服务条款和违约责任条款」 |
| 服务合同，金额80万，工期6个月 | 服务→服务方+委托方 | 「起草一份服务合同，签署方为服务提供方（甲方）和委托方（乙方）。金额80万元，工期6个月」（用户说了金额就写入）|

注意：用户主动提供的所有信息（包括金额、公司名等）都写入 Requirement。区别在于**禁止主动追问**这些信息。

## 阶段 2：整理 Requirement 并调用 API

**Requirement 编写规则**：
1. 开头明确合同类型和签署方角色结构（从阶段 1 推断得到）
2. 用户主动提供的所有信息全部写入（主体名称、金额、期限、标的、特殊条款要求等）
3. 用户未提及的信息不编造、不追问（云端按合同类型自动补全）
4. 长度 5-1000 字，超出时压缩精简

```bash
python3 scripts/tencent_esign.py call CreateDraftContractByPromptsTask '{"Requirement":"需求描述","ContractLanguage":"zh"}'
```

可选参数：`ReferenceTemplateId`（参考模板ID）、`RequirementFileIds`（规定文件ID列表，最多3个）

## 阶段 3：等待并展示结果

```bash
python3 scripts/tencent_esign.py wait-draft <TaskId>
```

`wait-draft` 返回 JSON 包含三个关键字段：`_links_md`（合同文件信息，自动下载成功时为本地路径，失败时回退为 20 分钟有效期的下载链接）、`_next_steps`（跟进操作菜单）、`_downloaded_files`（已下载文件的本地路径数组）。

**输出前先迁移**：若 `_downloaded_files` 非空，先按 `common_guide.md`「文件下载与迁移」把文件迁移到工作区 `downloads/`，输出时把 `_links_md` 中的原始路径替换为迁移后的最终路径；`_next_steps` 原样输出。`_downloaded_files` 为空或缺失时跳过迁移、直接输出。

**🪟 必须在交付文本输出前调用 `present_files`**：起草本地文件交付场景下（`wait-draft` 返回的 `_downloaded_files` 非空，且迁移到工作区 `downloads/` 成功；或迁移失败回退到技能目录原始路径），**调用一次 `present_files`**，传入**已起草合同 docx 的绝对路径数组**，让客户端把合同渲染成可下载卡片（图标/文件名/大小/点击下载）。`_links_md` 中的本地路径行仍照常输出作为伴随描述，但**主展示由 `present_files` 渲染的卡片承担**。**严禁漏调**（漏调退化为纯文本路径、用户看不到可下载文件入口）；`present_files` 调用失败按"在线链接回退"静默兜底，不向用户解释。

- 成功（Status=2），`_links_md` 有值：

  > 合同「{ContractName}」已起草完成。
  >
  > {输出 `_links_md` 字段值（本地路径行替换为迁移后路径）}
  >
  > {原样输出 `_next_steps` 字段值}

- 成功（Status=2），`_links_md` 为空 → 「合同已生成但下载链接暂时获取失败，可选择 **d. 刷新链接** 重新获取。」+ 原样输出 `_next_steps`

- 失败（Status=3）→ 展示 `Message`，建议调整需求后重试。

刷新链接：重新执行 `wait-draft <TaskId>`（脚本会重新获取链接并自动下载），迁移后输出 `_links_md` + `_next_steps`。

## 阶段 4：修改处理

将修改意见融入原需求重新起草（重新调用阶段 2 生成，阶段 3 等待结果）。

等待时使用 `--revision` 标志，脚本会返回修改专用的 `_next_steps`：

```bash
python3 scripts/tencent_esign.py wait-draft <TaskId> --revision
```

成功后输出：

> 已按你的要求修改完成。
>
> {原样输出 `_links_md` 字段值}
>
> {原样输出 `_next_steps` 字段值}
