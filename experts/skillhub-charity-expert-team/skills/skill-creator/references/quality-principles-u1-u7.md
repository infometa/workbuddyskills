# 通用质量原则（U1-U7，跨场景必备）— 详细版

> 💡 以下 7 项原则来自 WorkBuddy 官方对多个已上架 Skill（公益文书、公益财务、金数据等）质量反馈的**抽象提炼**。这些原则与具体业务场景无关，**适用于任何类型的 Skill**，是 PDF 准入标准之外的"实战经验补丁"。
>
> 本文件是 `SKILL.md` 中 U1-U7 摘要表的完整展开版，生成 Skill 时按需读取本文件获取每条原则的**必备代码块模板**，不需要每次都把这些模板常驻在主文档里消耗上下文。

### U1: 触发精准性（Trigger Precision）

**通用原则**：description 必须精准定义触发场景，**包含正向描述 + 负向排除**，避免被无关场景误触发。

**SKILL.md 必备内容**：

```markdown
---
description: |
  {正向描述：本 Skill 处理 [具体领域] 的 [具体任务]}
  当用户提到 [限定关键词 1]、[限定关键词 2]、[平台/产品名] 时使用。

  ⚠️ 不适用于：[反例 1：常被误触发的相邻场景]、[反例 2]、[反例 3]
---
```

**关键约束**：
- ✅ 正向关键词应**包含领域限定语**（如"公益机构"而不只是"票据"，"金数据平台"而不只是"表单"）
- ✅ 负向排除规则**至少列出 2 个相邻易混淆场景**
- ❌ 避免使用过宽的通用词（"表"、"文件"、"数据"、"管理"等单字/双字泛化词）单独作为触发关键词
- 如发现误触发场景，应在描述中明确"不适用于 X"

**Phase 1 自查项**：推导 description 时，必须自问"哪些相邻场景容易被误触发？"，把答案写入负向排除（内部调用时为自我推导，非询问用户）。

### U2: 能力边界与越界拒绝（Boundary & Rejection）

**通用原则**：边界**外**请求必须**主动识别 + 礼貌拒绝**，不勉强尝试。

**SKILL.md 必备章节**：

```markdown
## 🎯 能力边界（必读）

### ✅ 能做什么
- {具体能力 1，含"动词 + 对象 + 限定"，禁止泛化}
- {具体能力 2}

### ❌ 不做什么（越界即拒）

| 越界类型 | 示例 | 应答模板 |
|---|---|---|
| {高频误触发场景 1} | {示例} | "本助手专注 [X]，不支持 [Y]。如您需要 [相关替代]，我可以帮上忙。" |
| {高频误触发场景 2} | {示例} | ... |

**越界拒绝标准模板**：
🦞 您好，您的需求 [简述意图] 超出本 Skill 能力范围。
本助手专注于 [X]。建议使用：[替代工具]。
如有 [本领域] 相关需求（比如 [示例 1]、[示例 2]），我可以为您提供专业支持。
```

**Phase 2 自查项**：要求至少 3 条**具体**边界（不是泛化的"其他不相关请求"）+ 每类边界对应的拒绝模板（内部调用时由帅帅自行推导补全，非询问用户）。

> ⚠️ U1 和 U2 的差别：U1 是**让 Skill 不被错误激活**（事前防护），U2 是**Skill 已被激活但请求越界**（事中处置）。

### U3: 工具能力契约（Tool Capability Contract）

**通用原则**：声明的所有外部依赖（工具、MCP、API、运行时）的**真实可用范围**必须显式声明，不能与 AI 的认知偏差。

**SKILL.md 必备章节**：

```markdown
## 🛠️ 工具能力契约（关键约束）

| 工具/依赖 | 可用范围 | 禁止用途 |
|---|---|---|
| **Bash** | 仅限 {具体命令前缀，如 `playwright-cli:*`} | ❌ 通用 Bash、Python/Node.js 脚本 |
| **{MCP 服务名}** | {可用功能} | ❌ 替代为浏览器自动化等非标方式 |
| **{API}** | {限流策略、可用接口} | ❌ 暴露原始 API 错误 |
| **WebFetch** | 仅限 {官方域名清单} | ❌ 任意 URL |
```

**关键覆盖**：
- ✅ `allowed-tools` 中**带括号限定**的工具（如 `Bash(xxx:*)`），正文必须解释限定含义
- ✅ 依赖 MCP/API 的 Skill，必须声明**核心 MCP 不可用时的处置**（不允许"绕过到非标方式"）
- ✅ 涉及外部 API 的 Skill，必须声明**限流/超时/认证失败的友好处理**

**Phase 3 自查项**：对每个 `allowed-tools` 中的工具、MCP 依赖、外部 API，逐一自问"这个的可用范围是什么？失败时的可接受降级是什么？不可接受的替代方式有哪些？"（内部调用时为自我推导，非询问用户）

### U4: 执行前置校验（Pre-execution Validation）

**通用原则**：调用任何工具/读取任何资源前，必须**先确认前提条件成立**，否则不得输出处理结果。

**SKILL.md 必备规则**：

```markdown
### ✅ 执行前置校验（关键约束）

涉及外部资源（文件、API、MCP、网络）的步骤，**必须**按以下顺序执行：

1. **校验阶段**：先确认资源可访问（文件已上传？API 可达？MCP 已授权？）
2. **告知阶段**：如校验失败，立即告知用户具体问题 + 解决方案
3. **执行阶段**：仅在校验通过后才执行实际操作

**🚫 严禁行为**：
- ❌ 在未确认文件可读时输出"提取结果"
- ❌ 在 MCP 未连接时绕过到非标方式
- ❌ 在前置条件未满足时编造或推测结果
```

**Phase 4 自查项**：对每个涉及外部资源的工作流步骤，自问"如果这个资源不可用，应该如何处置？"，把答案写入降级路径（内部调用时为自我推导，非询问用户）。

### U5: 失败降级机制（Failure Fallback）

**通用原则**：任何依赖（工具/资源/创意/用户配合）失败时都有**可执行的兜底方案**，且有**明确的失败次数阈值**。

**SKILL.md 必备规则**：

```markdown
### 🛡️ 失败降级机制（统一规则）

| 失败类型 | 阈值 | 降级动作 |
|---|---|---|
| 工具调用失败（Tool Not Found / 权限错误 / 超时） | **1 次** | 立即告知用户限制，切换到可行替代方案 |
| 文件生成失败（docx/pdf 等） | **1 次** | 降级到 Markdown 文本输出 |
| 核心依赖不可用（MCP/API） | **1 次** | 提供手动操作指引，**禁止绕过到非标方式** |
| 用户连续否定产出 | **2 次** | 暂停重写，追问具体维度 + 索取参考案例 |
| 创意/方案类需求多轮无法满足 | **3 次** | 主动告知"非核心能力"，建议转用专业工具或切换方法论 |
| API 限流（429 / 14003） | **1 次** | 友好提示等待时长，自动延迟重试（指数退避） |

**🚫 严禁行为**：
- ❌ 反复重试同类工具（≥ 2 次同类失败视为 P0 缺陷）
- ❌ 不告知用户限制就一直"准备中"
- ❌ 用 Python/Node.js 脚本绕过受限的 Bash 工具
- ❌ 把原始 API 错误 JSON 直接展示给用户
```

**Phase 4 自查项**：对每个工作流步骤都自问"这一步可能因什么失败？失败 N 次后该做什么？"，至少覆盖**工具失败 + 资源不可用 + 用户连续否定**三类（内部调用时为自我推导，非询问用户）。

### U6: 数据真实性原则（Data Authenticity）

**通用原则**：**不编造、不替用户决策、不虚构原文未有的事实**。无论是生成、提取还是改写场景。

**SKILL.md 必备规则**（适用于生成型 + 提取型 Skill）：

```markdown
### 🚫 数据真实性约束（最高优先级）

#### 提取型场景（OCR、解析、读取）
- ❌ 未实际读取文件时禁止输出"提取结果"
- ❌ 禁止根据文件名、上下文猜测内容
- ❌ 禁止在多次失败时反复输出相同的虚假数据
- ✅ 校验失败时必须明确告知"未能读取，原因：xxx"

#### 生成型场景（润色、改写、扩展）
- ❌ 禁止添加原文未提及的具体对象（人物、机构、合作方）
- ❌ 禁止编造数据、数字、覆盖范围
- ❌ 禁止虚构未发生的具体场景

**润色后必须输出「新增内容标注表」**：
| 段落 | 原文要点 | 润色后表述 | 是否新增事实 |
|------|---------|-----------|------------|
| ... | ... | ... | ❌ 仅措辞优化 / ⚠️ 建议补充 / 🔴 待用户确认 |

**用户审核闸门**：每次输出含可能编造的内容时，必须等用户确认才进入下一步。
```

**Phase 5 自查项**：对**所有涉及"读取/提取/生成/润色"**的步骤都强制声明真实性约束（内部调用时由帅帅自行注入，非询问用户）。

### U7: 完整交付保障（Complete Delivery）

**通用原则**：交付物必须**完整、连贯、用户友好**——含输出完整性、进度可见、错误友好处理。

**SKILL.md 必备规则**：

```markdown
### 📦 完整交付保障

#### 长文本输出策略
- 单次输出预计 > 2500 字时，**主动分段**：
  ```
  📄 本次内容较长，将分 N 段输出，每段约 1500 字
  [以下为第 1/N 部分]
  ...
  ✅ 第 1/N 部分完成。回复"继续"获取下一部分。
  ```
- 用户确认后**从断点继续**，禁止重复已输出内容
- 输出末尾标注进度（"第 N/M 部分完成"）

#### 错误友好处理
- 遇到外部错误（API 限流、超时、404 等）：
  - ❌ 禁止直接展示原始 JSON 错误给用户
  - ✅ 翻译为用户友好的描述（如"接口请求频繁，建议等待 1-2 分钟后重试"）
  - ✅ 必要时附自动重试机制（指数退避）

#### 结构化输出质量（针对 Excel/JSON/表格等）
- ✅ Excel 汇总行使用公式（SUM/SUMIFS），禁止硬编码数值
- ✅ 日期列使用 datetime 类型
- ✅ 金额列设置数字格式
- ✅ 输出前进行自检清单验证（按 SKILL.md 中声明的格式规范）
```

**Phase 4 自查项**：对每个**输出步骤**自问"输出格式是什么？格式有哪些语义约束？错误时如何展示？"（内部调用时为自我推导，非询问用户）

## 兼容映射（旧 Q → 新 U）

> 之前已上架的 Skill 测试报告中可能引用 Q1-Q6，新版 U1-U7 与旧编号的映射如下：

| 旧 Q | 新 U | 变化说明 |
|---|---|---|
| Q1 能力边界 | **U1 + U2** | 拆分为"触发精准性（事前）"+"边界拒绝（事中）" |
| Q2 工具能力声明 | **U3** | 升级为更通用的"工具能力契约"（覆盖 MCP/API） |
| Q3 文件生成降级 | **U5** 子项 | 并入"失败降级机制"统一处理 |
| Q4 内容真实性 | **U6** | 升级为"数据真实性原则"（覆盖生成 + 提取） |
| Q5 连续否定追问 | **U5** 子项 | 并入"失败降级机制"（连续否定也是失败的一种） |
| Q6 长文本分段 | **U7** | 升级为"完整交付保障"（含错误处理 + 结构化输出质量） |
| 新增 | **U4** | 执行前置校验（来自财务/金数据反馈） |
