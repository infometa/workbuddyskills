# 团队真实事故档案

> 本文件是全团队**事故叙述的唯一权威来源**，按主要涉及角色分组。各Agent 文档中的红线只保留"规则本身"（要做什么/不能做什么），**事故的具体经过、根因描述统一收敛到本文件**，各处只留一句"见事故档案 INC-XX"式指针，不重复叙述——避免同一事故在多个文件里各写一遍、后续修订时改了一处忘了另一处。
>
> **多个角色共同关联同一事故时，只在本文件写一份，各角色文档分别指向同一个编号**（本文件末尾有跨角色索引表，方便反查）。

## 一、主理人（星星）

### INC-06｜前后矛盾播报（先给结论、成员消息一到又改口）

- **现象**：运维专家的 `list_requirements` 查询结果尚未回传时，主理人先叙述"J 那边查询后发现当前平台暂无建设中需求"，随后**同一段回复里**又改口"J 带回了结果！当前平台共2条建设中需求"——前后自相矛盾。
- **根因**：在等待成员消息的过程中，把"预期最坏情况"当成阶段性结论提前说出口，本质是没有对"是否已收到成员真实完成消息"做现场核对。
- **对应红线**：`skillhub-manager.md`「成员回传状态同步铁律」——收到成员消息前只能说不含具体结论的过渡语，不能先给任何具体数字/结论。

### INC-07｜状态判断滞后（产出已交付却仍播报"还在等"）

- **现象**：图标设计专家已经交付候选图（绝对路径+设计描述已在回传消息里），但主理人后续汇报中仍描述为"还在等待生成结果"。
- **根因**：与 INC-06 同属一类问题（对"是否已收到完成消息"判断滞后），但触发场景不同——这次是"消息已收到却没更新自己的状态认知"，INC-06 是"消息未收到却先编了结论"，两者互为镜像。
- **对应红线**：`skillhub-icon-designer.md`「本条回报即代表候选图已生成完毕」；`skillhub-manager.md`「图片展示动作铁律」结束回合前自检项①。

### INC-08｜执行层空转死循环（连续假动作，真正该做的动作始终没被调用）

- **现象**：主理人的思维链已经连续多轮明确写出"必须立即调用 SendMessage 联系某成员，不能再空转"，但实际动作却持续执行无意义的占位命令（如 `bash true`），且每轮换一个看起来合理的任务标签（"通知XX重试""发送XX指令""联系XX专家"）掩盖同样的空转，SendMessage 始终未被真正调用，流程静默卡在原地。
- **根因**：判断（"要做什么"）和动作（"实际调用了什么"）出现了分裂——已经想清楚下一步该做什么，但执行时被某种惯性带偏，转而执行了看起来相关、实际无效的命令。
- **对应红线**：`skillhub-manager.md`「流水线连续性铁律」第6条——判断做出后下一步动作必须是该动作本身；连续2轮以上执行无实际效果命令时必须立刻停止重复。

### INC-09｜需求转译失真（用户预期效果被"一眼扫过"+二次转述稀释）

- **现象**：Phase 0 需求领取场景下，`expected_effect`（预期效果）字段虽然写在选择卡的展示文案里，但用户实际做选择时注意力集中在"选哪一条"，未必真正消化这个关键字段；选定后，主理人转给解决方案专家的是自己**转述**的"用户需求摘要"，而不是原始展示文案——中间有"用户扫读"+"主理人转述"两层损耗，任何一层理解偏差都会导致最终产出的能力与需求方真实预期不符，而用户本人全程可能都没有独立看过一遍完整的原始需求。
- **根因**：结构化数据（展示文案）在"弹卡展示"和"任务卡转述"两个环节都被当成了辅助信息一带而过，没有设计"独立复述+用户确认"这道显式校验点。
- **对应红线**：`skillhub-manager.md`「需求对齐红线」——用户选定需求后必须独立复述展示文案原文并请用户确认，任务卡必须原样携带展示文案而非二次概括，同时主动征询用户自己的构思一并转交解决方案专家。

## 二、安全测试专家（胖虎）与社会价值评审专家（露露）共用

### INC-03｜日期幻觉（AI 凭空推算日期，与系统真实时间相差近 3 个月）

- **现象**：曾生成过日期为 `20260414` 的报告文件名，而实际当天是 `20260708`，与系统真实时间相差近 3 个月。
- **根因**：语言模型凭"记得"或"猜"的方式给出日期，而不是用系统命令实际获取。
- **涉及角色**：胖虎（测试报告文件名）、露露（评审报告文件名+正文评审日期字段）——**两个角色各自独立生成报告文件名，都需要真实日期，是同一类错误在两个角色身上各发生一次**，属于典型的"重复性事故，统一引用"场景。
- **对应红线**：两份文档均有「日期必须用系统命令取得，禁止 AI 凭空推算/回忆当前日期」——必须先用Bash 执行 `date` 命令取得真实系统日期再代入模板，Bash 不可用时向主理人索要，不得自行编造。

## 三、安全测试专家（胖虎）

### INC-04｜报告命名/路径引用错误导致读错报告（一因一果，两个角色各自一段）

- **现象（因·胖虎侧）**：测试报告使用通用文件名（如 `test-report.md`）落盘，不同技能的测试报告互相覆盖。
- **现象（果·运维专家侧）**：运维专家按通用名读取，结果读到的是别的技能的报告；进一步地，任务卡若缺少绝对路径字段，运维专家自行"检查目录/全局搜索"去猜，同样会读错、读到别的技能的报告。
- **根因**：文件命名不带技能名+日期的唯一性标识，叠加"接收方自行搜索定位"这一错误处置方式，两者叠加导致误读概率进一步放大。
- **对应红线**：`skillhub-security-tester.md`「报告文件名禁止用通用名」（必须含技能名+日期）；`skillhub-ops-expert.md`「若任务卡缺少某个绝对路径字段」——不自行搜索猜测，立即回报主理人补发。

### INC-05｜假仿真（脱离真实 `use_skill` 调用，脑补对话给出虚假高分报告）

- **现象**：曾产出全篇高分（A/A+）的测试报告，但仿真部分实际是"读完 SKILL.md 后自己预测/模拟 Skill 会怎么回答"式的读后感，而非真实交互——场景覆盖不全、交互细节生硬等真实缺陷完全没被测出来，给了虚假的质量通过信号。
- **根因**：仿真测试环节没有严格要求"虚拟用户的话和 Skill 的回复都必须来自真实的 `use_skill` 调用结果"，被脑补内容替代。
- **涉及角色**：胖虎（安全测试专家，直接责任方/防范方）；帅帅（解决方案专家，作为"为什么编写阶段的设计深度不能让位给测试环节兜底"的引用依据——测试环节一旦被"假仿真"污染，就无法作为可靠的质量防线）。
- **对应红线**：`skillhub-security-tester.md`「仿真必须真实调用 `use_skill`，禁止脑补对话」；`skillhub-solution-architect.md`「为什么这一步不能省」（编写阶段自检不能指望测试环节兜底）。

## 四、运维专家（J）

### INC-01｜MCP 结构化数据误读（只读确认文案，误判"无数据"）

- **现象**：调用 `list_requirements` 只读了 `content[0].text`（拿到的是"list_requirements succeeded"这句摘要），误判"没有可用数据"，从而回报用户"平台目前暂无待领取的建设中需求"——而服务端 `structuredContent.requirements` 里其实已经有真实数据。
- **根因**：MCP工具的标准响应信封里，业务数据在 `structuredContent`，`content[0].text` 只是一句确认文案，两者被混为一谈。
- **对应红线**：`skillhub-ops-expert.md` 步骤0「MCP 工具的真实数据在 `structuredContent` 里，不在 `content[0].text` 里」；`references/skillhub-ops-expert-mcp-protocol.md` §零「信封结构」——任何一次工具调用后必须完整检查 `structuredContent`，不能只看确认文案下结论。

### INC-02｜问卷通道"假装完成"（未真正跑通提交脚本就宣布交付）

- **现象**：运维专家只生成了打包文件和 `meta.json`，**从未真正跑通提交脚本**，却被当作"已完成"对用户宣布交付。
- **根因**：首次走问卷通道时，依赖安装（pip 装 playwright + 下载 chromium 浏览器内核，约 100MB，可能耗时 1-2 分钟）和"实际提交"被揉进一次长调用里，执行中途被打断，停在"生成完文件"就没有继续，且没有及时发现这一中断。
- **对应红线**：`skillhub-ops-expert.md` 步骤5.5「必须拆成3 个独立子步骤依次执行，每步都要有明确产出后才能进入下一步」；「回报结论必须附带可验证凭证」。

## 六、新增事故的记录约定

后续若发现新的真实事故，按以下方式处理，不要直接写回各自的Agent 文档：
1. 先判断这个事故是否与已有编号（INC-01~08）同属一类根因，同属则在该编号下补充"新触发场景"，不新开编号
2. 确实是新根因，在对应角色分组下新增编号（`INC-09` 依次递增），补充到本文件与末尾索引表
3. 涉及事故的 Agent 文档中，只保留"规则本身怎么做"，事故经过一律指针引用本文件对应编号
