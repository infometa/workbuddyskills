# 字段映射表（源文档 → 磐石新字段）

> 本文件是「搬运式同步」的核心：把 iWiki/腾讯文档跟进记录里的每个字段，
> 映射到磐石 `customer_visit` 主表 + 子表的**重构后新字段**上。
>
> ⛔ 铁律重申：
> - **分支 A（文档类）**：映射只做"字段对齐 + 原文填入"，**不做任何 AI 加工**，沟通内容/下一步计划 = 原文摘取。
> - **分支 B（对话流 / 纯文本）**：仅允许对**沟通进展 / 下一步计划**做**忠于输入的总结提炼**（见「六、」）；其余字段仍须取自输入、不得生成。
> 源文读不到的字段一律留空，禁止编造。

## 字段口径权威来源

以磐石数据字典 `customer_visit`（拜访纪要主表）及子表为准：
- **主表 customer_visit**：type、source、from_type、cid、customer_name、visit_time、time_section、conclusion、location、summary_type、customer_participants、tx_participants、department_name、follow_up_channel、customer_intent 等
- **子表 customer_visit_business_info**（补充信息）：plan、current_progress、main_risk、pain_problem、product_difficult_point、meeting_address、cooperate_progress、bevisited_role
- **子表 customer_visit_contact**（联系人）：name、position、tel、is_decision_man、decision_explain
- **子表 customer_visit_goal**（拜访目的）：goal_key、result、is_goal_reached

> 标红新增字段（数据字典中 `!!#ff0000 ...!!` 标记）即"重构后的新字段"，搬运时优先使用这些新字段。

## 〇、对象类型识别与 from_type 取值（Gate 3②，标题优先）

**商机 = 项目**（同义）。搬运前必须先识别跟进对象类型，决定 `from_type`。

> ⚠️ **核心原则：从文档标题/文件名优先判断，不从正文"客户：XXX"提取。**

| 识别结果 | 判定依据（标题优先） | from_type | 定位标识 | 一致性校验接口 |
|---------|---------------------|-----------|---------|--------------|
| **客户** | 文档**标题**只提客户主体名称（公司/集团/银行等），未提项目/商机 | **1** | cid | `GetCustomerListForVisitForMcp`（cid 命中=在名下） |
| **商机（项目）** | 标题提到"商机""项目"字样，或标题**主要讨论某个具体项目** | **2** | 项目编号(code) | `ltc.project/list`（businessManager主销售/architect架构师/projectMembers[].rtx成员三处之一是你=在名下） |
| ~~线索~~ | — | — | — | **本期不支持，识别到则跳过** |

### 关键区分：跟进对象 ≠ 拜访对象

| | 跟进对象 | 拜访对象 (contact_info) |
|--|---------|----------------------|
| **对应表单区域** | 表单上方「跟进对象：客户 / 商机 / 线索」 | 表单红框「拜访对象：姓名 - 职位(枚举)」 |
| **数据来源** | **文档标题 / 文件名**（优先） | **正文内容**（人员字段、参会人描述等） |
| **作用** | 决定这条记录挂在哪个客户或项目上 | 记录这次拜访见了谁、对方什么职位 |
| **常见混淆** | 正文写的「**客户**：栗子、苹果」→ 这里的"客户"是**拜访时见的人**，不是跟进对象 | 正文的「客户：XXX / 人员：XXX」中的对方人员 = 拜访对象 |
| **提取时机** | Gate 3②（最早步骤，先于读正文其他字段） | Gate 3⑦（对象确认后，从正文提取） |

**识别 → 不单独确认**：类型与实体名由标题直接判定，不在此征求确认；最终在 **确认 1（Gate 3-D）** 中连同候选一并回显供用户确认/改判（见 STEPS.md Gate 3② 与 3-D）。
**名下一致性校验（强制，第八条铁律对应）**：定位到对象后必须校验其在当前用户名下；不一致 → 提示"不在您名下" + 列出你名下相近对象让用户重选（Gate 3-C）。

## 一、通用字段映射（Sales / Owner 都适用）

| 源文档常见字段（iWiki/腾讯文档） | 磐石新字段（提交路径） | 说明 |
|-------------------------------|---------------------|------|
| 跟进对象 / 客户名称 / 拜访对象单位 | `base_info.customer_name` + `base_info.cid` | ⚠️ 不直接搬源文名；用源文名搜磐石，取命中的标准名+cid |
| 跟进时间 / 拜访时间 / 日期 | `base_info.visit_time` | 转 `YYYY-MM-DD HH:mm:ss` **单一时刻**（禁止范围/时间戳）；Gate3 提取（非阻塞确认）；超 15 天拒绝 |
| 地点 / 拜访地点 / 会议地点 | `base_info.location` | Gate3 提取（非阻塞确认）；源文无则留空，在预览展示 |
| 沟通内容 / 拜访纪要 / 会议内容 / 纪要正文 | `base_info.conclusion`（拜访 10000）/ `business_info.current_progress`（跟进进展 10002） | **按跟进方式分流**：拜访(10000) → `conclusion`（必填，原文照搬）；**跟进进展(10002) → `current_progress`（必填，原文照搬，即"项目当前进展"）**。**分支 A（文档类）= 原文摘取、禁加工**；**分支 B（对话流/纯文本）= 总结提炼**（见「六、」）。实测：进展场景缺 `current_progress` 后端报 2001「项目当前进展为必填项」 |
| 纪要类型 | `base_info.summary_type` | 映射到 ENUMS 纪要类型枚举；无法对应则留空 |
| 下一步计划 / 后续计划 / 待办 | `business_info.plan` | 原文照搬 |
| 联系人 / 参与人（姓名+职位） | `contact_info[].name` / `contact_info[].position` | **拜访对象（=表单红框"拜访对象：姓名-职位枚举"），从正文对方人员提取，非跟进对象。name 必填；position 必填（枚举值，见 ENUMS.md「拜访对象职位」），源文未写则必须让用户从枚举编号菜单中选择（见 STEPS.md Gate 3⑦-B），禁止留空、禁止猜测、禁止自由输入职位名** |
| 客户参与人 | `base_info.customer_participants` | 原文照搬（新字段） |
| 腾讯参与人 / 我方参与人 | `base_info.tx_participants` | 原文照搬（全部我方人员含当前用户）；由 ⑦-C 提取 |
| 协同跟进人（其他腾讯人员） | `base_info.collaborators[]` | 数组，每项 `{name, rtx, rtx_role}`；来自 ⑦-C：除当前用户外的我方参与人。rtx 优先取源文「rtx 中文名」写法里的 rtx（无则留空）；rtx_role 源文能看出角色则填（如售前/销售），看不出留空；当前用户自动排除，不重复入 |
| 部门 | `base_info.department_name` | 原文照搬（新字段） |

固定值（非源文，系统规则）：
- `base_info.source` = **11**（crm-ai 对话，固定）
- `base_info.from_type` = 由 Gate 3② 识别决定：**客户=1 / 商机(项目)=2**（不再固定 1）
- `base_info.time_section` = **noon**（源文无时段信息时的默认）

## 二、Sales（销售）字段映射与必填

### 跟进方式识别（type，由 AI 从内容识别线下会面信号）
磐石跟进方式仅两种，**由 AI 在 Gate 3⑥ 从跟进记录内容自动识别**（用户可能对两概念不清晰），判据是"能否看出双方进行了线下会面"：
- `type = 10000`（**拜访**）→ 内容能看出**双方线下会面**（上门/到访/现场/客户办公室/线下会议等）→ 需关联签到打卡（见「签到 / 关联打卡说明」）。
- `type = 10002`（**跟进进展**）→ 内容**看不出线下会面**（电话/线上会议/企微/邮件沟通，或纯进展记录）→ 打卡非必填（Sales 跟进进展仍显示打卡供可选关联，Owner 跟进进展不显示，见 shouldShowSignIn）。

> ⚠️ 仅标题写「拜访纪要」但正文无任何线下会面/地点/在场信息 → 信号不足，判为跟进进展，不武断判拜访。
> 识别的是**客观事实信号（有无线下会面）**，非对内容做总结/生成；识别结果一律经用户确认后才落定，误判可即时改判（详见 STEPS.md Gate 3⑥）。

### Sales × 客户 × 拜访（type=10000）必填
| 磐石字段 | 源文对应 | 缺失处理 |
|---------|---------|---------|
| `contact_info`（拜访对象）✱ | 联系人姓名+职位（**真实姓名，禁止昵称/角色占位**） | 源文无 → 必须追问补充真实姓名与职位（拜访方式下必填，不可留空占位） |
| `conclusion`（沟通内容）✱ | 纪要正文 | 源文无 → 拒绝提交（拜访纪要不应无内容） |
| `plan`（下一步计划）✱ | 后续计划 | 源文无 → 提示补充 |
| `visit_time`（拜访时间）✱ | 日期 | Gate3 强制确认 |
| `visit_check_ins_id`（签到打卡）✱ | — | ⚠️ 见下方「签到 / 关联打卡说明」，必须关联一条已有打卡 |

### Sales × 客户 × 跟进进展（type=10002）必填

> ⚠️ 跟进进展**不收集、不传 `contact_info`（拜访对象）**——该字段仅在拜访(10000)场景挂载；本场景确认 2 不展示、提交体不含该字段。

| 磐石字段 | 源文对应 |
|---------|---------|
| `current_progress`（项目当前进展，= 源文「沟通内容」原文）✱ | 当前进展（必填，原文照搬；拜访 10000 场景无此字段，不传） |
| `plan`（下一步计划）✱ | 后续计划 |
| `visit_time`（跟进时间）✱ | 日期（Gate3 确认） |

> 跟进进展(10002，非线索) 的 `visit_check_ins_id`（关联打卡）**非必填但需显示供选（无论 Sales/Owner）**：进入 Gate 3.5 拉最近 15 天打卡列表，用户可关联或跳过（见下方「签到 / 关联打卡说明」）。

> **签到 / 关联打卡说明**：是否显示/处理关联打卡由 `shouldShowSignIn` 决定（对齐参考 skill），逻辑对齐磐石表单「关联打卡记录」弹窗（详见 STEPS.md Gate 3.5、API_REFERENCE.md「查询签到打卡」+「签到规则」）：
> - **关联对象**：仅最近 **15 天** 内的小程序打卡记录，**每条打卡只能被关联一次**。
> - **查询接口**：`csm/GetVisitCheckInsListForMcp`（仅查询，PC 端**禁止**调用 `AddCustomerVisitCheckIns` 创建打卡）。⚠️ 后端**不过滤**已关联打卡，返回含 `is_bind_visit` 字段；**skill 须客户端过滤 `is_bind_visit=0`** 作为可关联候选，`is_bind_visit=1` 排除（重复关联被后端 2001 拒绝）。
> - **拜访(10000) → 签到必填（无论 Sales/Owner）**：必须从已有打卡中选一条关联，不允许跳过、不允许留空。若无可关联打卡 → 提示用户去磐石小程序补打卡，或改用「跟进进展(10002)」方式同步；**绝不伪造 visit_check_ins_id**。
> - **跟进进展(10002，非线索) → 显示打卡供关联，但非必填（无论 Sales/Owner）**：在确认 2 展示最近 15 天打卡候选供选，有合适的可关联，不想关联/无打卡可跳过（不传 visit_check_ins_id）。
> - **任何角色 × 线索(from_type=12) → 不显示/不处理关联打卡。**
>
> 打卡规则已改为**按方式统一，不分角色**：拜访必填、进展非必填。

## 三、Owner（售前架构师）字段映射与必填

### Owner × 客户 × 拜访（type=10000）必填
| 磐石字段 | 源文对应 |
|---------|---------|
| `contact_info`（拜访对象）✱ | 联系人姓名+职位 |
| `conclusion`（沟通内容）✱ | 纪要正文 |
| `visit_time`（拜访时间）✱ | 日期（Gate3 确认） |

> Owner × 拜访 的 `visit_check_ins_id`（关联打卡）**必填**（按方式统一，与 Sales×拜访 一致）：必须从已有打卡中选一条关联，不允许跳过；无可关联打卡 → 提示去磐石小程序补打卡或改判跟进进展（见「签到 / 关联打卡说明」）。

Owner 拜访的选填新字段（源文有才填）：`summary_type`、`plan`、`goal_info`（拜访目标/是否达成）、`meeting_address`。

### Owner × 客户 × 跟进进展（type=10002）必填
| 磐石字段 | 源文对应 |
|---------|---------|
| `current_progress`（项目当前进展，= 源文「沟通内容」原文）✱ | 当前进展（必填，原文照搬；拜访 10000 场景无此字段，不传） |
| `plan`（下一步计划）✱ | 后续计划 |

> ⚠️ **Owner × 跟进进展 无 visit_time 字段**：该场景磐石前端不渲染拜访时间，提交时由后端兜底当前时间。
> 因此本搬运工具在此场景**不采集、不传 visit_time**。但 **15 天时间闸仍需校验**——用源文写明的跟进时间判断是否在 15 天内；超期仍拒绝（避免搬运陈旧记录）。

Owner 跟进进展选填新字段：`main_risk`（风险）、`product_difficult_point`（产品卡点，注意字典里该字段名有历史拼写，提交按接口 schema 的 `product_difficult_point` 为准）。

## 六、chat_forward（企微聊天合并转发）来源映射

> chat_forward 与**纯文本输入**同属分支 B，处理逻辑一致；以下"源"指**从对话流 / 纯文本中解析或总结出的要素**（清洗规则见 STEPS.md 1.3 分支 B）。分支 A（文档类）的沟通内容/下一步计划 = 原文摘取；**本分支 = 基于输入总结提炼（忠于输入、禁编造）**。其余字段口径与「一、通用字段映射」完全一致。

| 对话流解析要素 | 磐石新字段（提交路径） | 说明 |
|--------------|---------------------|------|
| 客户公司名 / 商机名（从对话抽取） | `base_info.customer_name` + `cid` / `opp_cid` | 用抽取名搜磐石取标准名（同通用映射）；⚠️ 对话里的"人名"是联系人（拜访对象），"公司名 / 项目名"才是跟进对象实体 |
| 业务沟通时间（绝对 / 相对时间换算） | `base_info.visit_time` | 单一时刻；相对时间（今天 / 昨天 / 上周三）须结合系统"今天"换算，换算结果在确认 2 展示核对；仍走 Gate 3① 双向时间闸 |
| 现场 / 上门 / 他们办公室 | `base_info.location` + `type=10000`（拜访） | 地点抽取 + 线下会面信号 |
| 线上 / 腾讯会议 / 电话 / 微信 | `base_info.location` + `type=10002`（进展） | 远程信号 |
| 业务讨论（对话流 / 纯文本） | `conclusion`(10000) / `current_progress`(10002) | **分支 B = 基于输入总结提炼**：归纳对话/叙述中的业务核心要点成连贯内容，闲聊 / 表情 / 寒暄丢弃；**忠于输入、禁编造未提及事实** |
| 后续动作 / 待办（对话流 / 纯文本） | `business_info.plan` | **分支 B = 总结提炼**；输入无则留空，走保底确认补充 |
| 客户方发言人（对话中，非我方） | `contact_info[].name` / `contact_info[].position` | 群昵称 / 微信昵称标 `name_unverified=true`，确认 2 提示核对真实姓名；`position` 必填枚举（同 ⑦-B，源文无则确认 2 选） |
| 我方发言人（对话中，腾讯域） | `base_info.tx_participants` + `base_info.collaborators[]` | 当前用户排除；其余我方人员进协同人（同 ⑦-C） |
| 图片截图（OCR 失败 / 读不到文字） | — | 提示用户粘贴文本或确认留空，**禁止编造** |

**固定值**：`base_info.source` = **11**（crm-ai 对话固定值，企微号助手 chat_forward 与**纯文本输入**均属对话入口，**沿用 11，不新增枚举值**）。
