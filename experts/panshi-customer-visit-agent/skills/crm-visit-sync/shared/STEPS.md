# 执行步骤（Gate 0 → Gate 5）

> 搬运式跟进记录同步的分步操作手册。内部严格按 Gate 推进、禁止跳步；**对用户只触发 2 次确认**（跟进对象实体 / 职位+打卡+预览），其余步骤静默自动完成。
> 全程遵守 SKILL.md「八条铁律」。

> **交互样式约定（对话式确认）**：本技能最终上到企微以对话形式承载，所有需要用户决策/选择的环节以**编号列表 + 自然语言**呈现，用户回复序号或名称即可选择，**不模拟按钮、不使用"点击"话术**。
> - 候选列表、职位枚举菜单、打卡选项 → 以编号列表呈现，用户回复序号或名称即选中。
> - 最终提交 → 全字段预览后用自然语言请用户确认（如"确认无误请回复'提交'，需要修改请直接说明"），用户回复"提交"即落库。
> - 用户也可直接用自然语言告知修改项（如"把职位改成产品经理""时间改成下午"），按其说明调整后重新预览。

## Gate 0 · 静默加载规则（不向用户输出）

1. 读取 SKILL.md、shared/API_REFERENCE.md、shared/FIELDS_MAPPING.md、shared/ENUMS.md。
2. 初始化 SYNC_STATE（见 SKILL.md）。
3. 确认 omp-service MCP 可用（如未连通，提示用户先在连接器管理页"信任"omp-service，并配置 dev 环境令牌）。若来源含腾讯文档链接，额外确认 tencent-docs MCP 已连接且 `TENCENT_DOCS_TOKEN` 已授权（未授权会返回 400006）；若来源含企微文档链接（`doc.weixin.qq.com`），额外确认企业微信连接器（wecom-cli）已信任且其「文档」机器人权限未过期（权限过期会返回 `851014` authorization expired，多为之前扫码授权过期，需运行 `wecom-cli init` 扫码重新接入授权，不要点击接口返回的「智能机器人重新授权」链接）。

## Gate 1 · 读取来源内容（分两条预处理分支）

> **来源分两类，预处理逻辑完全不同，必须分开设计、分开承载**：
> - **分支 A · 文档类来源**（iWiki / 腾讯文档 / 企微文档 / 粘贴的结构化纪要）：内容已是"写好的跟进记录"，相对固定、有字段结构。预处理 = **结构化抽取**（定位原文片段 → 原样摘出）；沟通内容/下一步计划 = **原文摘取**（禁 AI 加工）。
> - **分支 B · 非结构化文本来源**（企微聊天合并转发 chat_forward + 用户自由输入的纯文本）：内容无字段结构，需 AI 从输入中**推断并提炼**对象/时间/方式/内容；沟通内容/下一步计划 = **基于输入总结提炼**（区别于分支 A 的原文摘取，但须忠于输入、禁编造）。
>
> 两条分支的产出统一为 `SYNC_STATE.records[].extracted`，**从 Gate 2 起两路完全共用**同一套角色鉴权 / 对象校验 / 时间闸 / 方式判定 / 确认 / 提交逻辑。本 Gate 只解决"把不同来源读进来并整理成 extracted"，不在本 Gate 做对象类型判定、对象定位等下游动作。

用户可能提供：多个 iWiki / 腾讯文档 / 企微文档链接、直接粘贴文本（结构化纪要 / 对话流 / 纯文本）、合并转发的聊天记录、或**图片**（拜访纪要截图 / 聊天记录截图 / 手写纪要照片等，可混合，一次可多条）。

### 1.1 识别来源类型（先定分支，再走对应预处理）

- **iWiki 链接**（`iwiki.woa.com/p/<docId>`）→ 分支 A，用 iWiki MCP `getDocument` 读取。
- **腾讯文档链接**（`docs.qq.com/...`）→ 分支 A，用腾讯文档 MCP 读取（步骤见 1.2.1）。
- **企微文档链接**（`doc.weixin.qq.com/doc/...`）→ 分支 A，用企业微信连接器读取（步骤见 1.2.1）。
- **粘贴文本 / 自由输入**：做三分类判定——
  - 文本带清晰字段（标题/时间/地点/人员/沟通内容分块）→ **分支 A 结构化纪要**，走 1.2（沟通内容/下一步计划 = 原文摘取）。
  - 文本是**多人对话流**（多条「发送者：内容」、常带时间戳、无字段结构）→ 判为 **分支 B chat_forward**，走 1.3（沟通内容/下一步计划 = 基于对话总结）。
  - 文本是**单人自由叙述的纯文本**（无字段结构、无多发言人、像一段自然语言描述，如「今天去了 XX 客户，聊了方案，他们下周给回复」）→ 判为 **分支 B 纯文本**，走 1.3（与对话流同源：无字段，沟通内容/下一步计划 = 基于输入总结）。
- **企微聊天合并转发（chat_forward）**：用户把与客户的聊天合并转发给企微号助手（或直接收到合并转发消息）→ **分支 B**，走 1.3。
- **图片输入**（用户直接发送/上传图片：拜访纪要截图、聊天记录截图、手写纪要照片、表格截图等）→ **分支 B**，走 1.3（图片 = 非结构化，需多模态识别后按对话流/纯文本清洗，规则见 1.3.9）。

> 判断入口：一条长文本，内部含多个不同发言人的对话行 → 分支 B（chat_forward）；带字段标题的纪要 → 分支 A；无字段、单人叙述的自由文本 → 分支 B（纯文本）；**图片** → 分支 B（图片解读，见 1.3.9）。分支 A 与分支 B 不要混用——分支 B 严禁按"字段位置"取数，分支 A 严禁按"对话发言人"推断。

### 1.2 分支 A · 文档类来源预处理（结构化抽取）

#### 1.2.1 读取
- **iWiki**：用 iWiki MCP `getDocument`（传 docId）读取；并取 `metadata.title` 作为 `source.title`。
- **腾讯文档**（`docs.qq.com/...`）：
  1. **从链接提取 file_id**：URL 路径最后一段即文档 file_id。例：`https://docs.qq.com/doc/DV2h5cWJ0R1lQb0lH` → `DV2h5cWJ0R1lQb0lH`；`https://docs.qq.com/sheet/xxxxx` 同理。提取不到时改用 `manage.search_file` 按关键词搜。
  2. **读内容**：文档/智能文档（`/doc/`、`/smartcanvas/`）→ 调 `doc.get_content({file_id})` 取 `content`（Markdown）；在线表格（`/sheet/`）→ 先 `sheet.get_sheet_info` 拿 sheet_id 再 `sheet.get_cell_data` 取单元格（或先试 `doc.get_content`，表格类优先走 sheet 工具）。
  3. **取标题**（供 Gate 3② 对象类型识别）：调 `manage.query_file_info({file_id})` 或 `doc.get_outline` 取文档标题，存入 `source.title`。
  ⚠️ 腾讯文档依赖 `TENCENT_DOCS_TOKEN` 授权；若返回 `400006`（Token 鉴权失败），提示用户先在腾讯文档连接器完成授权后再试。
- **企微文档**（`doc.weixin.qq.com/doc/...`）：
  1. **读内容**：调 `wecom-cli doc get_doc_content '{"url":"<链接>","type":2}'`（异步轮询：首次不传 task_id，若返回 `task_done=false` 则带返回 `task_id` 再调，直到 `task_done=true` 取 `content` Markdown）。也可传 `docid`（URL 中 `w3_xxx` 段）替代 `url`。
  2. **取标题**：企微文档无独立取标题接口，标题以用户随链接给出的文档名（链接前文字）或正文首行标题为准，存入 `source.title`。
  ⚠️ 企微文档依赖企业微信机器人「文档」权限；若返回 `851014`（authorization expired，多为之前扫码授权过期），提示用户运行 `wecom-cli init`（扫码接入）重新授权后再试，不要点击接口返回的「智能机器人重新授权」链接。
- **粘贴文本（结构化纪要）** → 直接作为原始纪要；`source.title` 以用户给出的文件名 / 正文首行标题为准。

#### 1.2.2 结构化抽取（只做抽取，不加工）
对每条来源，抽取出**一条或多条**跟进记录的原始字段，存入 `SYNC_STATE.records[].extracted`：
- **文件名 / 文档标题**（存入 `source.title`）——用于 Gate 3② 对象类型识别，务必采集。
- 对象名原文、时间原文、地点原文、沟通内容/纪要正文、进展、计划、联系人（姓名+职位）、参与人、风险、痛点、纪要类型等。
- ⛔ 抽取 = 定位原文片段并原样摘出，**不得改写、归纳、翻译、补写**。
- 一个文档里若含多条记录（如按日期分段的多次拜访），拆成多条 record，各自独立走后续 Gate。

> 分支 A 完成后，直接进入 1.4 公共回显，再进 Gate 2。

### 1.3 分支 B · 对话流来源预处理（chat_forward 对话清洗）

> **场景**：用户把与客户的企微聊天**合并转发**给企微号助手（或直接收到合并转发消息），skill 识别聊天内容 → 生成磐石跟进记录。这是与"分支 A 文档类来源"**并列的独立来源分支**，输入是无字段的非结构化文本，需从对话中推断对象/时间/地点/方式等。
> ⚠️ 与分支 A 粘贴文本（结构化纪要）的区分：分支 A 有清晰字段且沟通内容**原文摘取**；分支 B 是**无字段文本**，沟通内容/下一步计划**基于输入总结提炼**（见 1.3.7）。若粘贴内容其实是结构化纪要，应走 1.2 而非本分支。

#### 1.3.1 识别特征
- 输入呈现为**多人对话聚合**：多条「发送者：内容」行，常带各自时间戳（如「张三 14:32：…」「李四 14:35：…」）。
- 合并转发常见前缀：「以下为聊天记录」「聊天内容」「— 以下为新消息 —」「xxx 和 xxx 的聊天记录」等。
- 也可能以**图片**（聊天截图）形式进入 → 需 OCR / 多模态解析；读不到文字则提示用户粘贴文本或确认留空（禁止编造，见铁律）。
- 判断入口：一条长文本、且内部含多个不同发言人的对话行 → 分支 B；带字段标题的纪要 → 分支 A。

#### 1.3.2 说话人分离
逐行解析「发送者：内容」（+可选时间戳），把每句归到发言人，保留相对/绝对时间。

#### 1.3.3 我方 / 客户方判定
- 我方人员 = 腾讯域（rtx / 中文名可识别为本公司）；优先用 `SYNC_STATE.user`（当前用户）+ 已知同事；可用通讯录接口（`omp-service` 或企业微信通讯录）比对 rtx / 中文名是否本公司。
- 客户方人员 = 非我方、在对话中代表客户发言的人 → 作为**拜访对象候选**（见 Gate 3⑦-A）。
- ⚠️ 群昵称 / 微信昵称 ≠ 真实姓名：客户方发言人的昵称（如「老王」「客户A」）**不直接当真实姓名落库**，标记 `name_unverified=true`，在确认 2 提示用户核对 / 补全真实姓名。

#### 1.3.4 跟进对象实体抽取（客户 / 商机）
- 从对话内容 / 转发附言提取客户公司名或商机名（如「跟 XX 公司的 XX」「XX 客户的项目」「XX 项目推进」）。
- 区分「客户公司名」vs「客户联系人姓名」：对话里出现的"人名"多为联系人（拜访对象），"公司名 / 项目名"才是跟进对象实体。
- 无明确提及客户 / 商机名 → `object_name_raw` 留空，走 Gate 3②-A 降级（chat_forward 无标题，对象实体完全从对话内容抽取；仍无法判断 → 确认 1 追问）。

#### 1.3.5 时间解析（聊天时间戳是「聊天发生时间」，非必等于「跟进时间」）
- 绝对时间戳（如「07-10 14:32」）→ 作为候选跟进时间。
- 相对时间（「今天」「昨天」「上周三」）→ 结合系统"今天"换算为绝对日期。
- 对话中明确说的业务沟通时间（「上午跟他们开了会」「上周去拜访了」）优先采用。
- 多轮对话取**业务沟通主要时间 / 最后一条业务消息时间**；归一为单一时刻，仍走 Gate 3① 双向时间闸。
- ⛔ **反效时间范围（开始 > 结束，如「16:00-17:00」写反成「17:00-16:00」）→ 一律拒绝并提示用户重新提供/确认，不静默归一**（防止开始/结束颠倒后误取某一端；确认 2 不接受反效范围直接提交）。
- ⚠️ **模糊时间（相对时间如"今天/昨天/上周三/上午/下午"，或缺时分）→ 必须向用户二次确认，确保精确到天/时/分**，不直接用 AI 换算值落库；换算结果须让用户确认或补充具体时分后再写入 visit_time。

#### 1.3.6 地点 / 跟进方式信号（同 Gate 3⑥ 判据）
对话提「现场 / 上门 / 他们办公室 / 到场」→ 拜访(10000)；提「线上 / 腾讯会议 / 电话 / 微信」→ 进展(10002)；未提 → 默认进展，确认 2 可改判。

#### 1.3.7 沟通内容 / 进展 / 计划（分支 B = 基于输入总结提炼）
> ⚠️ **分支 B 与分支 A 的核心差异**：分支 A（文档类）的沟通内容/下一步计划 = **原文摘取**（不得改写）；**分支 B（对话流 / 纯文本）的沟通内容/下一步计划 = 基于输入总结提炼**——对话/叙述分散、需归纳成连贯要点，这是产品侧明确允许的 AI 加工范围。
- **沟通内容 / 进展**：从对话/叙述中**归纳业务核心要点**（客户诉求、方案、报价、推进节点、待解决项等），提炼成一段连贯的 `conclusion` / `current_progress`；闲聊、表情、寒暄、客套丢弃。
- **下一步计划**：归纳对话/叙述中的「后续动作 / 待办 / 承诺」（如「下周发方案」「改天再约」「等客户预算答复」）→ 提炼成 `plan`。
- ⛔ **总结护栏（不可突破）**：总结必须**忠于输入事实**，只整合输入中已提及的信息，**禁止编造**输入未出现的诉求/报价/时间/节点/人员；若输入本身无任何业务内容 → 标记为空，走「必填字段保底确认」让用户补充（不靠 AI 脑补）。

> 识别出的对象 / 时间 / 方式仍需用户在确认环节核对（同分支 A）；仅"沟通进展/下一步计划"在分支 B 允许总结，其余字段仍须取自输入、不得生成。

#### 1.3.8 纯文本输入（分支 B 的另一种形态）
- **识别特征**：用户直接输入的一段**单人自由叙述**（无字段标题、无多发言人、非对话流），如「今天去睿智网络办公室聊了 POC 排期，他们 IT 下周配合，定下周三进场」。
- **处理**：与 chat_forward 同源——无字段，直接走 1.3.2~1.3.7 的对话流清洗逻辑（说话人分离时我方=当前用户、客户方从叙述中识别；对象/时间/方式/内容按同样规则推断与总结）。
- **source 沿用 11**（企微号助手文本入口属对话入口，不新增枚举值）。

#### 1.3.9 图片输入（分支 B 的另一种形态）
- **识别特征**：用户直接发送/上传图片（拜访纪要截图、聊天记录截图、手写纪要照片、表格截图等），无文本或仅附少量文字说明。
- **解读方式**：用**多模态/视觉能力**识别图片内容并转为文本，再按内容形态走对应清洗：
  - **聊天记录截图** → 识别为「发送者：内容」对话流，走 1.3.2~1.3.7 对话流清洗。
  - **纪要截图 / 手写照片 / 表格截图** → 识别为自由叙述文本，走 1.3.8 纯文本清洗（沟通内容/下一步计划 = 基于识别内容总结提炼）。
  - **多张图片** → 逐张识别后合并为一条记录（或按用户说明拆多条）。
- ⛔ **识别护栏（不可突破）**：
  - 仅整合图片中**实际可见**的文字信息，**禁止编造**图片未呈现的诉求/报价/时间/人员/节点。
  - 图片模糊 / 手写难辨 / 读不到文字 → 标记识别失败，提示用户「图片内容识别不全，请粘贴文本或补充说明」，**不得靠 AI 脑补**。
  - 识别结果（尤其时间、人名、数字、金额）在确认 2 展示供用户核对（OCR 可能有误）。
- **source 沿用 11**（图片入口属对话入口，不新增枚举值）。

> 分支 B（对话流 / 纯文本 / 图片）清洗完成后，产出与分支 A **完全同构**的 `extracted`，进入 1.4 公共回显，再进 Gate 2。后续 Gate 2-5 两路一致，不再区分来源类型。

### 1.4 回显识别结果（公共，不阻塞）

两分支都完成后，列出共识别到几条记录、每条的**来源类型**（文档类 / 聊天合并转发）与对象名原文，作为进度提示；**不阻塞、不要求用户确认"是否就搬这几条"**，直接进入 Gate 2。

## Gate 2 · 读用户信息 + 角色鉴权

1. **读当前用户信息 + 拿角色**：调用 omp-service 通用工具 `get_user_info(showDetail=true)`，拿到当前登录用户的 rtx / 中文名（存入 `SYNC_STATE.user`，作为后续"对象是否在你名下"校验的身份基准），并从返回 `detail.roles[]` 读取当前用户的角色标签（如 `sales` / `architect`）。`staffName` 应与 `USER` 一致，可作交叉校验。
2. **计算 finalRole（一步直映射，见 API_REFERENCE #2）**：
   - 角色标签含销售族（`sales*`）→ `finalRole = Sales`
   - 角色标签含售前架构师族（`architect*`）→ `finalRole = Owner`
3. **校验**：finalRole ∈ {`Sales`, `Owner`} → 继续；否则按下面两种场景分别输出并**终止**：
   - **roles 非空但不含 `sales*`/`architect*`**（如产研架构师、分包、POC、VP、海外角色）→ 输出「本次版本仅支持销售和售前架构师，您的角色为 {finalRole}，暂不支持」。
   - **roles 为空**（rare 兜底）→ 输出「当前用户为 {rtx}（{中文名}），但系统返回的角色标签为空（`roles: []`），无法判定您属于销售 (Sales) 还是售前架构师 (Owner)。本次版本仅支持销售和售前架构师使用。」
4. 记录 `SYNC_STATE.role`，`role.checked = true`。**角色由后台自动处理，查询/提交接口均无需传 `role` 参数。**

> 💡 关于「拉取用户负责的客户和商机」的时机：**开场不做全量拉取**（你名下客户/商机可能很多，全量拉取慢且未必用得上）。改为在 Gate 3③ 识别出具体对象后，**按 cid / 项目编号做定向命中校验**——校验用的接口本身已按你的权限过滤，命中即证明在你名下。

## Gate 3 · 静默抽取（核心，每条 record 独立执行）

对 `records` 中的每一条，依次**静默**完成 ①②③④⑤⑥⑦（不向用户提问），随后在 3-D 触发**确认 1（跟进对象实体）**；Gate 3.5 静默查打卡；最后 Gate 4 = **确认 2（职位+打卡+预览一次性确认并提交）**。全程仅这 2 次用户交互。

> 概念约定：**商机 = 项目**（同义）。识别为商机时定位「项目编号」（商机 id）。「线索」本期不做。

### ① 时间有效性闸（双向：不能晚于今天、不能早于 15 天前）
- 从 `extracted.时间原文` 解析跟进时间，**归一为单一日期**（忽略时分，仅比日期）。
- 解析不出确切日期 → 走 ④ 让用户补充，再回来判断。
- **上限 · 不能大于今天**：跟进日期 **晚于今天（{今天}）** → 输出「该记录跟进时间为 {日期}，大于今天（{今天}），按规则不能同步（拜访时间不能晚于今天）」并**跳过此条**（其余条继续）。⚠️ 此为先于 15 天闸的上限校验，未来日期一律拦截，不提交。
- **下限 · 不能早于 15 天前**：今天 − 跟进日期 > 15 天 → 输出「该记录跟进时间为 {日期}，已超过 15 天，按规则不能同步」并**跳过此条**（其余条继续）。
- 今天 − 15 天 ≤ 跟进日期 ≤ 今天 → `within_15d = true`，时间有效。

> 获取"今天"用系统时间，不要臆测。比较仅按日期（YYYY-MM-DD），避免时分干扰。

### ② 对象类型识别与实体提取（标题优先，强制）

> ⚠️ **核心原则：跟进对象的「类型」和「实体」必须优先从文档标题/文件名判断，而不是从正文内容里的"客户：XXX"提取。**
>
> **关键区分（极易搞混，必须严格遵循）：**
> - **跟进对象**（= 磐石表单的「跟进对象」区域）：选「客户 / 商机 / 线索」，决定这条记录挂在哪个客户或项目上。→ **从文档标题/文件名识别**
> - **拜访对象**（= 磐石表单的「拜访对象」区域）：填写「姓名 - 职位(枚举)」，记录这次见了谁。→ **从正文内容提取**（见下方步骤 ⑦）
>
> 正文里写的「**客户**：栗子、苹果」「**人员**：客户 XXX / 腾讯 YYY」中的"客户 XXX"是**拜访时见的人（拜访对象）**，不是跟进对象（不是挂在哪个客户上）。**禁止把正文的"客户名"当成跟进对象实体去搜索。**

#### ②-A 从标题判定对象类型和实体名称

读取 `source.title`（文件名 / 文档标题），按以下规则判定：

- 标题只提到**客户主体名称**（如公司名/集团名/银行名），未提项目/商机 → 判为 **客户（customer）**，从标题提取客户名作为搜索关键词。
- 标题提到"**商机**""**项目**"字样，或标题主要讨论某个具体项目（如"XX 项目研讨""XX 商机推进""XXX POC"）→ 判为 **商机（opportunity，= 项目）**，从标题提取商机名/项目名作为搜索关键词。
- **「线索」类**：本期不支持。若识别为线索，提示「线索类跟进对象本期暂不支持同步」并跳过此条。

**标题信息不足时的降级：**
- 标题无法判断类型或提取不出实体名 → 可参考正文首段/表格主题行辅助判断，但必须在确认话术中注明"根据标题（及正文辅助）"。
- **chat_forward（无标题）场景**：合并转发聊天没有文档标题，对象实体完全从对话内容抽取（见 1.3.4）；仍无法判断 → 追问用户：「这条聊天记录对应的跟进对象是哪个客户 / 商机（项目）？」。
- 仍无法判断 → 追问用户：「这条跟进记录的对象是客户还是商机（项目）？对象名称是什么？」

**类型判定不单独确认**：类型与实体名由标题直接判定，无需在此征求确认；最终会在 Gate 3「确认 1（跟进对象实体）」中连同候选一并回显供用户确认/改判。
- 记录 `object_type`、`object_type_basis`（判定依据）、`extracted.对象名原文`（用于后续 ③ 搜索）。
- `object_type=customer` → `from_type=1`；`object_type=opportunity` → `from_type=2`。

### ③ 对象定位 + 名下一致性校验（强制）

#### 3-A 若为客户（object_type=customer）

> **判定规则：「我相关（type:[1]）」或「长尾（type:[2]）」命中均可作为候选落定提交（方案B：直接允许，不额外校验权限）。**
> - `type:[1]`（我相关）命中 → 我的客户，可用（3-D 预选该条）。
> - `type:[1]` 为空但 `type:[2]`（长尾）命中 → 长尾客户也可作为候选落定提交（直接允许，不强制走 checkUserCustomerScope 二次校验）。
> - `type:[1]` 与 `type:[2]` 均为空 → 拦截，通知用户更换跟进实体。

1. **模糊搜索用户名下客户（文档名搜）**：用 `extracted.对象名原文` 调 `GetCustomerListForVisitForMcp`，传 `type:[1]`（我相关）+ `customer_name`（**无需传 `role`**，后台按登录态自动过滤权限）。该接口已按当前用户权限过滤，返回即"我负责的客户"——这是候选主池。
2. **叠加模糊搜索（文档内容 + 名下客户）**：若第 1 步命中少，对 `对象名原文` 做**关键词松化**（去掉"银行 / 科技 / 有限公司 / 核心系统"等后缀、取核心字号），再以松化关键词用 `type:[1]` 重搜一次，把新增的"我相关"客户并入候选池。
3. `type:[1]` 命中 ≥1 条 → **合并两次结果、按 cid 去重**，把候选列表（磐石标准名 + cid）暂存，进入 3-D 由用户**回复序号选择**（仅 1 条时预选该条）；记录 `cid`、`customer_name`（磐石标准名）、`from_type=1`、`object_located=true`、`object_matched=true`、`owner_check.in_scope=true`、`hit_by=list_hit`。
4. `type:[1]` 返回 0 条 → **改查 `type:[2]`（长尾）**：
   - 长尾命中 ≥1 条 → 把长尾候选（磐石标准名 + cid）暂存，进入 3-D 由用户**回复序号选择**（直接允许落定，不额外校验权限）；记录 `cid`、`customer_name`、`from_type=1`、`object_located=true`、`object_matched=true`、`hit_by=list_hit`。
   - 长尾也为空 → 提示「「{对象名原文}」未在磐石找到匹配客户（我相关/长尾均无），请提供更准确的客户全称或 CID」，等用户输入后重搜。
   - 用户需回复正确的客户全称 / CID 重新定位，或明确"跳过"本条（换实体）；**绝不把源文原名当磐石对象直接用**。

> 说明：客户详情接口拿不到架构师字段，故不去客户详情比对负责人；`GetCustomerListForVisitForMcp` 已按当前用户"销售/架构师"权限过滤，cid 能命中本身即等价于"该客户在你名下"，故不再做二次复校（提速）。

#### 3-B 若为商机（object_type=opportunity，= 项目）
1. **模糊搜索用户名下商机（文档名搜）**：用 `extracted.对象名原文` 调 `ltc.project/list`（MCP: omp-service）：
   - 源文给的是**商机名称** → 传 `name`（模糊搜）；源文给的是**项目编号**（纯数字串，如 20250328690198）→ 传 `code`（精确搜）。
   - 固定参数：`type:12`、`switchPanshiBase:1`、`projectArea:[0,1]`、`page:1`、`size:100`（编号搜可 size:20）。
   - ⚠️ 该接口**不做名下过滤、返回全公司匹配结果**，禁止不传 `name`/`code` 拉全量（70 万+ 条）。
2. **叠加松化关键词二次搜**：若第 1 步命中少，对 `对象名原文` 做关键词松化（取核心字号）再搜一次 `name`，并入候选（仍全公司结果，后续统一按名下过滤）。
3. 两次均无结果 → 提示「未找到商机「{对象名原文}」，请提供更准确的商机名称或项目编号」，等用户输入后重搜。
4. 有结果 → **不在此阻塞**，先做名下一致性校验（`ltc.project/list` 不按权限过滤，必须逐个校验）：读每个候选的 `businessManager`(主销售 rtx)、`architect`(架构师 rtx，逗号分隔逐个比)、`projectMembers[].rtx`(项目成员，逐个比)，**仅保留 `== 当前用户` 的候选**（= 用户自己负责的商机）暂存进 3-D；三处都不是你 → `in_scope=false` 不纳入，若全部不在名下 → 走「3-C 不一致处理」。
5. （3-D 中用户选定后）命中的候选记 `hit_by=manager|architect|member`；校验通过记 `project_code`(= code)、`opp_name`(= name)、`opp_cid`(= cId)、`from_type=2`、`object_located=true`、`object_matched=true`，并把命中的负责人 rtx 记入 `owner_check`。

#### 3-C 不一致处理（in_scope=false）
1. 先明确提示：
   ```
   ⚠️「{对象名}」不在您名下（您不是该{客户/商机}的销售/架构师），按权限规则不能代填跟进记录。
   ```
2. 再**列出你名下相近的对象让你重选**（同样以编号列表呈现）：
   - 客户：用同一 `对象名原文` 关键词（或去掉后缀重新提炼的关键词）以 `type:[1]` 查 `GetCustomerListForVisitForMcp`，列出你名下相近客户。
   - 商机：用更宽的 `name` 关键词查 `ltc.project/list`，在返回结果里筛出 `businessManager`/`architect`/`projectMembers[].rtx` 含当前用户的商机，列出让你重选。
   ```
   以下是您名下相近的{客户/商机}，请**点击**选择正确的对象；或点击「跳过」不同步本条：
   [1] ...
   [2] ...
   ```
3. 用户选中名下对象 → 回到 3-A/3-B 第 5/4 步完成校验；用户"跳过" → 跳过本条（其余条继续）。

#### 3-D 确认 1 · 跟进对象实体（唯一组装前闸门，强制）

定位与一致性校验通过后，**只在这里向用户确认一次跟进对象**（类型 + 实体 + 候选选择合并为一问）：

- **有候选时**（候选 = 「文档名搜 + 用户名下模糊搜」合并去重后的结果）：以**编号列表**呈现，供用户回复序号选择（仅 1 条时预选该条）：
  ```
  第 {i} 条：根据标题「{title}」判定跟进对象为「{客户 / 商机(项目)}」，在磐石（含您名下的客户/商机）模糊匹配到以下候选，请**点击**选择：
  [1] {customer_name}（CID: {cid}）          ← 预选
  [2] {customer_name_2}（CID: {cid_2}）
  …（商机则显示：[n] {name}（项目编号: {code}，客户: {companyName}））
  👉 点击对应候选即可选中；如需换对象，点击「重选/换对象」或告知正确的类型与名称。
  ```
  > 交互：候选以编号列表呈现，用户**回复序号或名称**即选中。
- **0 候选（对象搜不到）**：提示「未找到「{对象名原文}」，请提供更准确的名称或 CID」，等用户输入后重搜（不编造、不终止其它条）。
- **全部候选都不在名下（触发 3-C）**：按 3-C 提示并列出你名下相近对象重选。

⛔ 用户未明确确认前，禁止进入 ④ 及后续任何步骤（含 ⑥ 方式、⑦ 拜访对象、Gate 3.5 打卡、确认 2）。
确认/选定 → `object_confirmed = true`，进入 ④。

### ④ 时间提取与格式化（非阻塞，供确认 2 整体核对，不再单独确认）
- 从 `extracted.时间原文` 解析跟进时间，归一化为 **单一时刻** 字符串 `YYYY-MM-DD HH:mm:ss`（24 小时制）。
- ⚠️ **格式铁律**：必须是单一时刻（如 `2026-07-02 16:00:00`），**禁止**写成时间范围（如 `2026-07-02 16:00-17:00`）、**禁止** Unix 时间戳；只写日期未写时刻时需补 `00:00:00` 并在预览中注明。
- 解析不出确切日期 → 直接请用户提供跟进时间（必填，用于 ① 的 15 天校验），**不得默认当前时间**。
- 时间**不再单独向用户确认**：提取/格式化后直接进确认 2 整体核对。`time_extracted = true`。
- ⚠️ Owner × 跟进进展(10002) 场景**不传 visit_time**（前端不渲染），但仍用此时间做 ① 的 15 天校验。

### ⑤ 地点提取（非阻塞，供确认 2 整体核对，不再单独确认）
- 从 `extracted.地点原文` 提取拜访/会议地点。
- 地点**不再单独向用户确认**：提取后直接进确认 2 整体核对；源文无地点 → 留空（非必填，不强制追问）。
- 记录 `location`，`location_extracted = true`。
- ⛔ **location 与打卡强耦合**：`location` 仅在**已关联 `visit_check_ins_id`（即用户确实有打卡记录被关联）时才写入 `base_info`；未关联打卡或跳过打卡时，即使提取到了地点也**不得传 `location` 字段**（否则 CRM 会把 location 值显示在「签到打卡」列，造成"有关联打卡"的假象）。

### ⑥ 跟进方式识别（AI 从跟进记录内容判定线下会面信号）

磐石跟进方式有两种，**关联打卡逻辑完全不同**。考虑到用户可能对"拜访 / 跟进进展"两个概念不清晰，**由 AI 从跟进记录内容自动识别**，判据是"能否看出双方进行了一次线下会面"：

- **拜访（type=10000）**：从内容能看出**双方进行了线下会面**（面对面见面/上门/到访/线下会议/现场交流等）→ 认定为拜访，需关联签到打卡（见 Gate 3.5）。
- **跟进进展（type=10002）**：从内容**看不出**存在线下会面（如电话/线上会议/邮件/微信沟通，或纯粹的进展记录）→ 认定为跟进进展，**不强制关联打卡**（但 Sales 的跟进进展仍会在 Gate 3.5 显示打卡供可选关联，非必填可跳过，见 shouldShowSignIn）。

**识别判据（只依据源文客观信号，禁止臆测）：**

「线下会面」正向信号（命中任一 → 倾向拜访 10000）：
- 明确地点是**线下物理地址**：客户现场 / 客户办公室 / xx 大厦 / 会议室 / 门店 / 园区 / 上门 / 到访 / 驻场。
- 会面动词：拜访、上门、到访、面谈、当面、现场、走访、陪访、参观、见面。
- 标题/正文出现"拜访纪要""现场交流""线下研讨"等且有具体地点或在场人员描述。

「非线下会面」信号（命中且无上述正向信号 → 倾向跟进进展 10002）：
- 沟通方式明确是**远程**：电话沟通 / 电话会议 / 线上会议 / 腾讯会议 / 视频会议 / 企微 / 微信 / 邮件 / IM。
- 内容是纯进展汇报、方案推进记录，无任何见面/地点信息。

**判定规则：**
1. 命中「线下会面正向信号」→ 判为 **拜访（10000）**。
2. 明确是远程沟通、或通篇无任何线下会面线索 → 判为 **跟进进展（10002）**。
3. ⚠️ **仅凭标题有"拜访"二字但正文无任何线下会面/地点/在场信息** → 信号不足，**不武断判拜访**，判为跟进进展并在确认时说明理由（标题≠事实）。

**识别结果不单独确认（在确认 2 预览中整体展示，可现场改判）**：AI 按客观信号自动判定 `type`（10000 拜访 / 10002 跟进进展），记录 `type`、`type_basis`（命中信号原文），`type_confirmed = true`。判定结果会在最后「确认 2」的预览中展示，用户若认为误判可在那一步直接改判方式。
- 是否进入 **Gate 3.5**（打卡）由 `shouldShowSignIn` 决定（按方式统一，不分角色）：
  - `type=10000`（拜访） → 进入 Gate 3.5（签到必填，无论角色）。
  - `type=10002`（跟进进展）AND `from_type≠12`（非线索） → **也进入 Gate 3.5**（无论 Sales/Owner，拉打卡供选，非必填可跳过）。
  - 其余（线索 × 任意方式，即 `from_type=12`） → 跳过 Gate 3.5，直接进入 Gate 4。

> 说明：此处 AI 识别的是**客观事实信号（有无线下会面）**，不是对沟通内容做总结/生成，未违反"禁 AI 加工"铁律；且识别结果一律经用户确认后才落定，误判可即时纠正。

### ⑦ 拜访对象提取（contact_info，从正文内容提取）

> ⛔ **进入条件（由跟进方式 type 决定，强约束）**：
> - **type=10000（拜访 / 线下会面）** → 本步骤**必须执行**，拜访对象**存在且强制填写**（真实姓名 + 枚举职位）；缺失真实姓名或职位即阻断提交。
> - **type=10002（跟进进展 / 线上或纯进展）** → **整段跳过**，不提取、不收集、不传 `contact_info`（磐石跟进进展类不挂载拜访对象）；确认 2 不展示拜访对象区块，提交体也不含该字段。
> - 本步骤不重新判定方式，只按 Gate 3⑥ 已定 `type` 决定进不进。

> **进入时机**：type=10000 时在 ③-D 确认 1（跟进对象实体）通过之后执行；拜访对象提取与职位映射在静默阶段完成，缺失职位留待「确认 2」与打卡合并一次确认。
> **核心区分**：此步骤提取的「拜访对象」= 磐石表单红框区域「拜访对象：姓名 - 职位(枚举)」，**不是**步骤 ② 的「跟进对象（客户/商机）」。

#### ⑦-A 从正文识别拜访对象

读 `source.raw`（正文 / 表格内容），查找以下模式之一：

1. **明确标注「客户」「人员」「对方」「参会人员」等字段**：
   - 如 `客户：栗子、苹果` → 提取姓名列表 `["栗子", "苹果"]`
   - 如 `人员：客户：XXX；腾讯：YYY` → 提取客户方人员 `["XXX"]`
2. **正文描述中提到的对方人员**：
   - 如「与 XX 公司的 A 总、B 经理进行了沟通」→ 提取 `["A总", "B经理"]`
3. **无任何对方人员信息（且 type=10000）** → `contact_info = []`；type=10002 不进入本步骤，不组装该字段（见本步骤开头 ⛔）。
4. **chat_forward（合并转发聊天）场景**：对话中发言的**客户方人员**（非我方、代表客户说话）即拜访对象候选。

   ⛔ **真实姓名强制 + 禁止占位（仅 type=10000 适用）**：
   - 群昵称 / 微信昵称 / 角色称呼（如「老王」「客户A」「对接人」「接口人」）**绝不得直接当真实姓名落库，也绝不允许用此类称呼占位提交**。
   - 提取时标记 `name_unverified=true`，并在确认 2 **强制向用户追问真实姓名**（补全前禁止提交）。
   - 若用户无法提供真实姓名，提示：「拜访方式下拜访对象为必填，请提供真实姓名；或确认本次实际为线上/纯进展沟通，改判为跟进进展(10002) 以跳过该字段」。

> ⛔ **只从正文提取对方人员姓名**，我方人员（腾讯/我方参与人）不纳入拜访对象。
> ⛔ 禁止把跟进对象实体名称（客户公司名/项目名）当拜访对象姓名。

#### ⑦-B 职位确认（position 枚举，必填）

对每个提取到的拜访对象姓名，需要确认其**职位**（position）。职位是**枚举值**，必须从以下选项中匹配（详见 ENUMS.md「拜访对象职位」）：

**默认枚举（销售场景）：**
```
董事长、总裁、CEO、CTO、运维总监、技术总监、首席运营官、首席财务官、
首席信息官、运管总监、市场总监、总经理、副总裁、产品总监、产品经理、
运维经理、研发总监、研发经理、市场负责人、商务负责人、技术负责人、
一线运维、一线研发、一线商务、其他
```

**售前架构师额外增加：**
```
省部级、厅局级、县处级、乡科级、科员、办事员
```

**处理规则：**
1. **源文写了职位，且精确等于某枚举值**（如「产品经理」= 枚举[15] 产品经理）→ 直接采用该枚举值，在确认 2 预览标注「已精确匹配，可改」。
2. **源文没写职位，或写的职位不在枚举内**（模糊/自由文本，如「业务负责人/项目经理」「项目经理」）→ 一律标记 `position_pending = true`，**禁止 AI 私自就近硬套某一个值**；其职位在「确认 2」中以 ENUMS.md 的**完整编号菜单**（[1]~[25] 销售默认，Owner 额外 [26]~[31]）一次性请用户选择（与打卡合并一次确认）。
3. 所有对象的 `name` 收集完后即组装 `contact_info`：已精确匹配的填实际枚举值（**文字标签，非序号**）；`position_pending` 的暂留空，待确认 2 补全。

> ⛔ **position 是必填字段（仅 type=10000 拜访）**：拜访方式下每个拜访对象都必须有职位，不允许留空。pending 项**必须在确认 2 补全**后才可提交，禁止猜测、编造或把自由文本直接写入。type=10002（跟进进展）不收集拜访对象，无此字段。
> 职位编号菜单（[1]~[25] 销售默认，Owner 额外 [26]~[31]）见 ENUMS.md「拜访对象职位」，确认 2 中直接展示给用户选。
> 🔴 **序号→文字还原（防序号入库，实测踩坑：后台出现 position=「19」「20」纯数字）**：菜单里 `[19]`「市场负责人」等编号**仅为交互序号**，不是 position 取值。用户回复序号（如 `19`）时，**必须先按菜单还原成对应枚举文字**（`19`→`市场负责人`、`20`→`商务负责人`）再写入 `contact_info[].position`，**严禁把序号数字原样入库**（详见 ENUMS.md「入库值铁律」）。

#### ⑦-C 腾讯参与人 / 协同跟进人（collaborators）提取

> **进入时机**：与 ⑦ 同步（对象确认后、Gate 3.5 之前）。本步从正文提取**我方（腾讯）参与人**，拆分出「协同跟进人」并填充 `base_info.collaborators[]`。

**① 识别我方（腾讯）参与人**：从 `source.raw` 查找以下模式（与 ⑦-A 的"对方人员"区分开）：
1. 明确标注「腾讯」「我方」「我司」字段：如 `腾讯：vickyzypan 潘子烨 ruixianshi 史瑞先` → 提取全部我方人员。
   - **chat_forward 场景**：对话中发言的**我方人员**（腾讯域 rtx / 中文名可识别）即腾讯参与人，连同当前用户一并纳入 `tx_participants`；其余我方人员进 `collaborators`（当前用户排除，见 ⑦-C ②）。
2. 正文提到的腾讯侧人员：如「腾讯云团队 A、B 一同参会」→ 提取 `["A", "B"]`。
3. 无任何我方人员信息 → `participants.tx_participants_raw = ""`，`collaborators = []`。

**② 拆分当前用户 vs 其他腾讯人员**：
- 将提取到的每个我方人员，与 `SYNC_STATE.user`（当前登录用户，rtx + 中文名）比对：
  - **命中当前用户** → 视为**主跟进人**（记录创建人，由登录态决定），**不**放入 `collaborators`，避免重复。
  - **其余人员** → 进入 `collaborators[]`（协同跟进人）。

**③ 填充 `collaborators[]`**：每项 `{ name, rtx, rtx_role }`：
- `name`：人员中文名/称谓（原文）。
- `rtx`：**优先取源文「rtx 中文名」写法里的 rtx**（如 `ruixianshi 史瑞先` → rtx=`ruixianshi`）；若源文仅给中文名无 rtx → **rtx 留空**（字段可选），并在确认 2 预览中标注「源文未识别到 RTX，请确认/补充」。
- `rtx_role`：源文能看出角色则填（如「售前」「销售」）；看不出则**留空**（字段可选，不强制）。

**④ `tx_participants`（腾讯参与人）原文照搬**：把**全部**我方参与人（含当前用户）按源文原样填入 `participants.tx_participants_raw`，提交时原样写入 `base_info.tx_participants`。该字段是"腾讯侧参会人"文本记录，保持原文照搬，与结构化的 `collaborators` 并存不冲突。

> ⛔ 协同跟进人**只来自源文明确写出的我方人员**，不得把拜访对象（客户方）当协同人；当前用户不得重复入 `collaborators`。

## Gate 3.5 · 关联打卡记录（按 shouldShowSignIn 判定是否执行）

> **进入条件（shouldShowSignIn，按方式统一，不分角色）**：`type=10000`（拜访）；或 `type=10002`（跟进进展）AND `from_type≠12`（非线索）。即拜访和进展（非线索）都进入本 Gate，不再按 finalRole 区分。其余场景（线索）不进入本 Gate。
> 逻辑对齐磐石跟进记录表单的「签到打卡 → 关联打卡记录」弹窗（见截图）：
> **仅支持关联最近 15 天的小程序打卡记录，每条打卡记录只能被关联一次。**
> ⚠️ 本 skill（PC 端）**只能查询和关联已有打卡**，禁止调用创建签到接口（`AddCustomerVisitCheckIns`）凭空造打卡（违反铁律 #8）。

### 3.5.1 判定签到是否必填（isSignInRequired，按方式统一，不分角色）
按 API_REFERENCE「签到规则」：
- **type=10000（拜访）→ 签到必填**（无论 Sales/Owner，不允许跳过、不允许留空）。
- **type=10002（跟进进展，非线索）→ 签到非必填**（无论 Sales/Owner，拉列表供选，有则关联，无/不想关联可跳过）。

### 3.5.2 静默查询已有打卡记录
调用 `csm/GetVisitCheckInsListForMcp`（MCP: omp-service，见 API_REFERENCE）：
```json
{ "page": 1, "page_size": 10, "type": 1, "cid": "{客户类型时传已确认的cid}" }
```
- 客户对象（from_type=1）传 `cid`；商机对象（from_type=2）按接口要求传项目编号相关参数（若接口仅支持 cid，则以商机关联的客户 cid 查询，具体以接口 schema 为准）。
- 可选 `address`：用户想按地址搜索时，把关键词传入过滤。
- 返回 `list[]`，每条**重点取「打卡地址 address + 签到时间 create_time + id(即 visit_check_ins_id) + creator」**暂存，供「确认 2」展示。
- **只拉「未填写跟进的打卡」**：⚠️ 实测后端**不会**过滤已关联打卡，返回 list 可能含 `is_bind_visit=1`（已绑定其他跟进）的记录。**skill 必须客户端过滤：仅保留 `is_bind_visit=0` 的记录作为可关联候选**；`is_bind_visit=1` 的一律排除（重复关联会被后端 2001 拒绝）。过滤后 `is_bind_visit=0` 为 0 条 → 走 3.5.4 无可用打卡分支。
- **仅保留最近 15 天**：以 `create_time` 为准，skill 侧对超过 15 天的记录做兜底过滤后再暂存。
- 本步**静默执行，不向用户展示、不阻塞**；候选列表在「确认 2」中随职位一并请用户选择。

### 3.5.3 候选打卡（在确认 2 中展示与选择）
将 3.5.2 暂存的候选在「确认 2」预览里列出：
```
📍 请选择要关联的打卡记录（最近 15 天、每条仅可关联一次）：
[1] 📍 {address}  🕐 {create_time}  👤 {creator}
[2] ...
（可输入地址关键词重新搜索；非必填场景另有 [0] 跳过）
```
- **签到必填时（type=10000 拜访，无论角色）**：确认 2 中**不提供**「跳过」选项，用户必须选一条；若此时无候选 → 在确认 2 提示「拜访方式必须关联打卡，请先去磐石小程序补打卡，或在此将方式改判为跟进进展」。
- **签到非必填时（type=10002 跟进进展，无论角色）**：确认 2 末尾追加 `[0] 跳过（不关联打卡）`。
- 用户选定 → 记录该条 `id` 为 `visit_check_ins_id`，`check_in_linked = true`。

### 3.5.4 无可用打卡记录时（在确认 2 中处理）
若 3.5.2 返回空列表：
- **签到必填（type=10000 拜访，无论角色）**：在「确认 2」明确提示「未找到最近 15 天可关联打卡，拜访方式必须关联打卡——请先去磐石小程序补打卡，或把方式改判为『跟进进展』」，**不允许提交空 `visit_check_ins_id`**。
- **签到非必填（type=10002 跟进进展，无论角色）**：在「确认 2」标注「无可关联打卡，将不关联直接同步」，`visit_check_ins_id` 不传。

> ⛔ **兜底防护**：签到必填场景下，即使用户主动说「跳过打卡」，也必须拒绝并引导（去小程序打卡 / 改为跟进进展）。绝不凭空提交空 `visit_check_ins_id`。

## 必填字段保底确认（提交前安全网 · 缺失逐一确认）

> **保底原则**：写入过程中，凡是**无法仅从用户输入确认**的字段，都必须在提交前逐一向用户确认；**优先确认表单必填字段**。自动可生成的字段（跟进人、创建时间）不询问。
> 本步是防幻觉的最后兜底：确保没有任何必填字段被"留空提交"或"AI 擅自填值"。

对每条 record，在 Gate 3 静默抽取 + Gate 3.5 打卡查询完成后、进入 Gate 4 预览前，做**必填字段兜底扫描**：

### 必填字段清单与兜底规则（按确认优先级排序）

| 优先级 | 必填字段 | 无法从输入确认时的兜底动作 | 分支差异 |
|--------|---------|--------------------------|---------|
| 1 | **跟进对象** | 必须确认其是**当前用户负责（有权限）**的对象；无法判定 → 走 Gate 3-D 追问；判定到但不在名下 → 走 3-C 拦截，**绝不提交** | 两分支一致（须权限校验） |
| 2 | **跟进方式** | 源文无明确信号、AI 无法判定 → 询问用户选「拜访(10000) / 跟进进展(10002)」；判为**拜访(10000)** → 触发 Gate 3.5 关联打卡（必填） | 两分支一致 |
| 3 | **沟通进展**（current_progress / conclusion） | 分支 A → 从文档原文**摘取**，原文无则询问补充（必填）；分支 B → 基于输入**总结**核心要点，输入无业务内容则询问补充 | **A 摘取 / B 总结** |
| 4 | **下一步计划**（plan） | 同沟通进展的分支规则（A 摘取 / B 总结）；无则询问补充 | **A 摘取 / B 总结** |
| 5 | **跟进时间**（visit_time） | 须过 Gate 3① 双向时间闸（≤今天 且 ≥今天−15天）；**反效时间范围（开始>结束）→ 拒绝并提示用户重新提供/确认，不静默归一**；源文无时间或换算超界 → 询问用户补充/确认，**不默认今天** | 两分支一致 |
| — | **跟进人** | = 当前登录用户（创建人），由登录态生成 | 自动，不询问 |
| — | **创建时间** | = 提交时系统时间，由系统生成 | 自动，不询问 |

### 兜底执行方式
- **逐一确认、必填优先**：扫描出"未确认必填字段"后，按上表优先级从高到低，每次向用户提出**一问**（给出"系统判定值 / 源文读到的值 + 请确认或修改"），用户回复即继续，直到所有必填字段齐备。
- **自动字段跳过**：跟进人、创建时间由系统生成，不在兜底询问范围内。
- **所有必填字段确认/补齐后**，才进入 Gate 4（确认 2）做最终预览与提交；任一必填仍缺失 → 禁止提交。
- 兜底询问可与 Gate 4 预览合并展示（必填缺失项在预览中以"请补充"高亮），但**缺失必填字段不得以"留空"跳过**。

## Gate 4 · 确认 2 · 最终确认与提交（职位 + 打卡 + 全字段预览，一次性确认）

> 前提：必填字段缺失已在「必填字段保底确认」中逐一补齐；本步做整体预览 + 一次性确认提交。

> 这是第 2 次也是最后一次用户交互。把「关联打卡（选一条或确认无）+ 全字段预览」合并在这一步，**以编号列表 + 自然语言呈现，用户回复即可补全并确认**。结尾用自然语言请用户确认（如"确认无误请回复'提交'，需要修改请直接说明"），**用户回复"提交"即落库**。
> 👉 **拜访对象区块仅在 type=10000（拜访）时展示**；type=10002（跟进进展）不展示、不收集、不提交该字段（磐石进展类不挂载拜访对象）。

1. 按 finalRole × from_type × type，参照 FIELDS_MAPPING 组装完整提交体。
2. **逐条展示合并预览**：
   - 跟进对象：{类型 + 全称 + CID/项目编号}（确认 1 已确认）
   - 跟进方式：{拜访 / 跟进进展}（标注判定依据信号，用户可在此改判）
   - 时间：{visit_time}　地点：{location}（源文未提供标"留空"）
   - 沟通内容 / 进展 / 计划：{原文}（源文未提供标"留空"）
   - **拜访对象（仅 type=10000 拜访显示）**：每人一行 `姓名 — 职位`；
     - **姓名补全（禁止占位）**：若 `name_unverified=true`（源文只给昵称/角色称呼如「对接人」「客户A」），**必须提示用户补全真实姓名**，明确「不得使用昵称/角色称呼占位提交」；补全前不得进入提交。
     - **职位选择**：`position_pending`（或源文为模糊/自由文本、未精确匹配枚举）的项附 ENUMS.md **完整编号菜单**，请回复序号或枚举名选择：
     ```
     拜访对象「{姓名}」职位请回复序号或枚举名：
     （此处完整列出 ENUMS.md 的 [1]~[25] 销售默认菜单，Owner 额外 [26]~[31]，勿省略）
     ```
     > 🔴 **入库必须写文字、禁写序号**：用户回复序号（如 `19`）后，**先按菜单还原成对应枚举文字**（`19`→`市场负责人`）再写入 `contact_info[].position`；严禁把序号数字原样入库（详见 ENUMS.md「入库值铁律」）。
   - **关联打卡**：进入过 Gate 3.5 且有候选 → 列出 `[1] 地址 时间` 等编号项供选（必填场景无"跳过"；非必填场景追加 `[0] 跳过`）；无候选 → 展示「未找到可关联打卡」（必填场景提示需补打卡或改判进展）。
   - **协同跟进人**：展示 Gate 3⑦-C 自动提取的 `collaborators[]`「姓名（rtx，如有）」；若某人带「源文未识别到 RTX」标注则在此提示用户确认/补充；**当前用户已自动排除**（不重复入协同人）。无任何其他腾讯人员 → 标「无协同跟进人」。
3. 用户在该步**回复**补全缺失职位、选择/确认打卡，并确认整体无误 → 回复"提交" → 组装最终体并**直接提交**。
4. 必填校验：按 FIELDS_MAPPING「必填速查」检查；
   - **type=10000（拜访）**：`position_pending` 未补全 / 拜访对象 `name` 仍为占位或未补全真实姓名 / Sales×拜访未关联打卡 → **禁止提交**，提示补全或改判进展。
   - 🔴 **position 格式自检**：组装提交体前逐项检查 `contact_info[].position`，若为**纯数字**或不在 ENUMS.md 职位枚举文字列表内 → 判定为「序号未还原」，回到序号→文字还原，**禁止提交**。
   - **type=10002（跟进进展）**：不校验拜访对象（该字段本身不收集、不传）；仅校验其它必填项（进展/计划/时间等）。
5. 提交成功取 `base_info_visit_id` 反馈（见 Gate 5 反馈格式）。

> ⛔ 预览是防幻觉的最后关卡：用户必须能看到"每个字段填了什么、来自哪里"，且职位与打卡都在同一确认步内完成。

## Gate 5 · 提交

1. 对 `field_preview_ok = true` 的每条，组装提交体调用 `csm/AddCustomerVisitForMcp`（见 API_REFERENCE #5）。
   - 进入过 Gate 3.5 且用户关联了打卡（`type=10000` 拜访，或 Sales×`type=10002` 跟进进展）→ `base_info.visit_check_ins_id` 传关联到的打卡 id；**同时传 `location`**（Gate 3⑤ 提取的地点）。
   - 未进入 Gate 3.5、或用户跳过了关联（线索×任意方式 from_type=12、或非必填场景用户选跳过）→ **不传 `visit_check_ins_id`，也不传 `location`**（location 与打卡强耦合，见 Gate 3⑤ ⛔）。
   - `base_info.collaborators`：若 Gate 3⑦-C 提取到「其他腾讯人员」则写入 `collaborators[]`（每项 `{name, rtx, rtx_role}`），当前用户不入；无则整字段不传（不写空数组）。
   - `base_info.contact_info`：**仅 type=10000（拜访）时写入**，每项 `{name: 真实姓名（禁止昵称/角色占位）, position: 枚举文字标签（🔴 只能写文字如「市场负责人」，严禁写序号数字如「19」；用户回序号先还原成文字）}`；type=10002（跟进进展）**整字段不传**（不写空数组、不留占位）。
   - `base_info.tx_participants`：把 ⑦-C 收集的「全部我方参与人（含当前用户）」按源文原样写入（原文照搬，与结构化 `collaborators` 并存）。
   - ⛔ Sales×拜访 若 `visit_check_ins_id` 为空 → **禁止提交**，回到 Gate 3.5 / 让用户改跟进进展。
2. 成功 → 取响应 `base_info_visit_id`，记录并向用户反馈：
   ```
   ✅ 已同步：{customer_name} · {visit_time} · {type中文}
      跟进记录ID：{base_info_visit_id}
   ```
3. 多条时逐条提交并汇总结果（成功 N 条 / 跳过 M 条〔超期或缺必填〕/ 失败 K 条）。
4. 失败处理：见下方降级链路。

## 异常处理与降级链路

- **omp-service 未连通 / 令牌失效**：提示去连接器管理页信任 omp-service、检查 dev 环境太湖令牌，不硬试。
- **对象搜不到 / 不在名下**：按 Gate 3③ 流程处理——客户场景 `type:[1]`（我相关）为空时改查 `type:[2]`（长尾），长尾命中即可落定（直接允许，不额外校验权限）；`type:[1]` 与 `type:[2]` 均为空 → 拦截并提示用户换跟进实体；商机场景按 3-C 列出名下相近对象重选。均**不硬提交、不编造**。
- **提交接口报错**：重试 1 次；仍失败 → 输出该条已组装好的字段 JSON，供用户复制到磐石端手动录入，并说明失败原因。
- **源文无法解析出跟进内容**：提示「该来源未能读到有效跟进记录内容，请检查链接权限或直接粘贴正文」，跳过此条。

## 话术风格

- 简洁、结构化，逐条处理时明确标"第 X 条 / 共 N 条"。
- **仅两次确认（均为对话式交互）**：① 跟进对象实体（类型 + 全称 + CID/编号，候选来自"文档名搜 + 用户名下模糊搜"合并，回复序号选择）；② 职位 + 打卡 + 全字段预览，以编号列表 + 自然语言呈现，**用户回复"提交"即落库**。其余步骤不向用户提问。
- 任何确认都给出"源文读到的值 / 系统判定值"+「确认 / 修改」选项，降低用户成本；用户回复序号或名称选择，也可直接用自然语言说明修改项。
- 绝不替用户拍板跟进对象（客户/商机）；时间、地点、跟进方式由源文提取/AI 判定后在确认 2 预览中整体展示，不再单独确认。
