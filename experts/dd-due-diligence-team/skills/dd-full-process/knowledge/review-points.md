# 人机审阅层（Human-in-the-Loop Review Points）

本文件定义 dd-full-process 的"人机审阅"能力：把全流程中"必须人拍板"的动作显式建模为审阅点，提供补充/纠偏入口、风险分级徽章、证据链路，让结果呈现更直观、风险可追溯。

**核心约束**：审阅层只负责"确认/纳入/纠偏"交互，**不改变**状态推进契约（红线 5/6）与专业能力解耦。任何审阅点的确认，走 `update_project_stage` 推进 `done`（**禁止**重新调用 `save_*_data` 传内容，避免覆盖已落库 section；`save_*_data(complete:true)` 仅在不携带新内容时兼容）。

---

## 一、审阅点（Review Point）定义

每个审阅点含以下字段：

| 字段       | 说明                                                 |
| ---------- | ---------------------------------------------------- |
| `id`       | 审阅点编号（如 `RP-S4-Profile`）                     |
| `所属环节` | S1~S7 + 子环节                                       |
| `审阅类型` | 内容审阅 / 补充材料 / 风险判断 / 等级确认 / 纳入范围 |
| `默认动作` | 确认 / 修改 / 重新分析 / 暂不纳入 / 带风险继续       |
| `影响范围` | 确认后影响哪些下游（报告 / 风险总览 / 定稿）         |
| `可否跳过` | 是否允许带风险跳过                                   |

## 三、补充与纠偏入口

### 3.1 补充入口（HL-3）

- 每个审阅点提供"补充材料/补充信息"快捷入口，用户可即时上传材料或追加说明，不必退出当前环节。
- 追加的补充信息需**标记来源为"用户补充"**，与 AI 检索数据区分，纳入 provenance 可追溯。
- 触发方式：审阅点选项中加入 `[补充材料/信息]`。

### 3.2 纠偏入口（HL-4）

- 每个分析结论提供"纠正/覆盖"入口，用户可指出错误或覆盖 AI 建议。
- 纠偏动作需记录：**原始结论、用户纠正内容、原因、影响范围**。
- **红线 6 兼容**：不静默覆盖。纠偏即显式标记，并触发下游 `⟳ 待重新确认`。
- 触发方式：审阅点选项中加入 `[纠正/覆盖]`，用户给出纠偏内容后，按"要求修改"路径处理。

### 3.3 纳入范围四档（HL-5）

| 档位                     | 含义                           |
| ------------------------ | ------------------------------ |
| 纳入最终报告             | 作为正式结论进入最终报告       |
| 纳入专项报告（不上最终） | 进入对应专项报告，不进最终报告 |
| 仅作参考                 | 展示但不落正式结论             |
| 暂不纳入                 | 保留展示，标记不采纳，记录原因 |

## 四、风险提示机制

### 4.1 风险分级徽章（HL-6）

每个风险项用等级徽章 + 颜色直观呈现（银行惯例，红=高风险）：

| 等级 | 徽章        | 触发           | 提示动作                       |
| ---- | ----------- | -------------- | ------------------------------ |
| 高   | 🔴 高风险   | `level=high`   | 必须人工判断，默认不可静默放行 |
| 中   | 🟠 中风险   | `level=medium` | 建议人工审阅，可带风险继续     |
| 低   | 🟡 低风险   | `level=low`    | 提示关注，可自动记录           |
| 关注 | 🔵 一般关注 | 提示类         | 记录备查                       |

### 4.2 风险证据链路（Evidence Chain）（HL-7）

每个风险点展示"结论 ← 证据 ← 来源"，形成可追溯证据链。呈现格式：

```
🔴 高风险｜客户集中度高
  └─ 证据：前五大客户占营收约 68%（画像数据）
       └─ 来源：进件-销售合同汇总 v2 / 2025-12 报道
  └─ 印证：行业分析 E8 客户账期压力
       └─ 来源：行业分析报告（同项目）
  └─ 建议：进件后核查前五大客户回款周期
```

### 4.3 跨维度风险印证（HL-8，P2 二期）

当某风险同时出现在多个专项分析中，自动高亮"多维度印证"，提示更需关注。当前版本标记为`【跨维度印证：中优先级】`即可，不强求自动聚合。

## 五、结果呈现直观化

### 5.1 结论先行 + 证据后置（HL-10）

每个审阅点先展示"**结论一句话 + 风险等级徽章**"，再展开证据、来源、待核事项，用户可展开/折叠。

### 5.2 审阅点汇总视图（HL-11，P2 二期）

用户可要求查看"全部待审阅点"汇总（类似待办清单），逐个处理或批量确认。

---

## 六、审阅点与状态推进的衔接（关键）

审阅点的确认**仍走原契约**，不新增状态字段：

| 审阅点确认结果          | 对应状态动作                                                                                                                       |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 确认全部 / 逐项确认完成 | 调用 `update_project_stage` 置 `<dimension> = 'done'`（S4/S6 均用此方式；**禁止**重新调用 `save_*_data` 传内容覆盖已落库 section） |
| 要求修改 / 纠正         | 保持 `doing`，修订后重新展示                                                                                                       |
| 重新分析                | 保持 `doing`，回到分析重跑                                                                                                         |
| 带风险继续              | 记录风险原因，允许进入下游，下游标注"待披露"                                                                                       |
| 暂不纳入                | 显式 `update_project_stage` 置 `pending`，记录不采纳原因                                                                           |

> **红线 5**：审阅点的"确认"是用户行为信号，AI 不得自动替用户确认。
> **红线 6**：纠偏走"显式标记 + 触发 ⟳"，不静默覆盖用户已确认结果。
> **红线 7**：`RP-S7-Final` 未确认前，不得把最终报告标记为定稿。
